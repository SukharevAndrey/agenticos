# Отделы и группы { #departments-and-groups }

Компании организованы в отделы: продажи, финансы, HR, поддержка. В AgenticOS
отдел — это [группа](directory.md#groups), а группа решает, кто чем может
пользоваться. У отдела «Финансы» могут быть свои агенты, навыки, файлы контекста,
базы знаний и MCP-серверы, которых никогда не видит отдел «Продажи», а то, что
нужно всем, остаётся открытым всей организации.

## Добавление отделов { #adding-your-departments }

**Группы** (Groups) в главной навигации перечисляют группы организации. Участник
с `members:manage` добавляет их по одной через **Новая группа** (New group) или
несколько сразу через **Добавить отделы** (Add departments) — этот вариант
предлагает Продажи, Финансы, HR, Поддержку, Разработку, Маркетинг, Юридический
отдел и Операции, каждый со значком и кратким описанием. После этого переименуйте
их, смените значки или удалите, как любую другую группу.

Просматривайте отделы карточками со значком, описанием и числом участников или
ищите по названию и описанию. В окне **Новая группа** выберите значок рядом с
названием; необязательный месячный лимит находится в разделе **Лимит бюджета**
(Budget limit).

Людей добавляют в группу с её страницы, вручную, или через
[сопоставление групп каталога](directory.md#directory-group-mappings), если ваша
компания уже ведёт свои команды в каталоге.

### Руководитель группы { #a-groups-lead }

Администратор может сделать участника **руководителем** (Lead) группы — корона
рядом с ним в списке участников. Руководитель добавляет людей в свою группу и
убирает их, не администрируя организацию, поэтому глава отдела может ввести нового
сотрудника, не спрашивая ИТ. Назначить или снять руководителя может только тот, у
кого есть `members:manage`, ведь руководитель раздаёт доступ ко всему, что открыто
группе.

## Кто может пользоваться новой вещью { #who-can-use-a-new-thing }

При создании агента, навыка, базы знаний, файла контекста или общего MCP-сервера
задаётся один вопрос: **Кто может пользоваться** (Who can use it).

| Вариант | Кто получает доступ | Как хранится |
|---|---|---|
| **Все** (Everyone) — по умолчанию | Каждый участник организации | Видимость `org` |
| **Только я** (Only me) | Вы и те, кому вы откроете доступ позже | Видимость `private` (база знаний становится личной) |
| **Выбранные люди** (Some people) | Участники выбранных вами групп и люди, которых вы назовёте | Видимость `private`, каждому открыт доступ на уровне `use` |

Группы предлагаются, как только вы выбираете третий вариант; людей находят, вводя
имя или адрес электронной почты. Каждый выбранный остаётся меткой, пока вы его не
уберёте.

Участники группы находят то, что ей открыто, пользуются этим и привязывают к своим
агентам. Люди вне группы не видят этого в списках, в поиске, в списках выбора
Конструктора, через API или через Архитектора, который действует с разрешениями
того, кто спрашивает. Участники, чья роль достигает каждого ресурса, — владелец,
администратор, Builder по умолчанию — по-прежнему видят всё; см.
[Разрешения](permissions.md).

Приложения публикуются агентами и изначально приватны для человека, для которого
был запуск; откройте доступ к приложению для группы на его панели **Доступ**
(Share). Панель «Доступ» каждого ресурса тоже добавляет или убирает группы после
создания.

## MCP-серверы отдела { #a-departments-mcp-servers }

MCP-сервер организации — одна общая учётная запись, подключённая один раз, — можно
сузить так же, поэтому сервер бухгалтерии отдела «Финансы» принадлежит «Финансам».
Участники, которые управляют MCP-серверами, видят серверы организации, те, что
подключили они, и те, что открыты их группам или им; владельцы и администраторы
видят все. Builder вне «Финансов» не находит их сервер в списке, не может открыть
его по id и не может опубликовать привязанного к нему агента. См.
[MCP](mcp.md#personal-or-organization-wide).

Агент, уже привязанный к такому серверу, продолжает работать для всех, кто может
запускать агента. Выбор решает, кто может выбрать сервер, а не кто получает через
него ответы, — см.
[откуда агент берёт знания](#where-an-agents-knowledge-comes-from).

## Страница группы { #a-groups-page }

Открытие группы показывает её людей и всё, что ей открыто, сгруппированное по
виду, — агенты, базы знаний, навыки, контекст, приложения и MCP-серверы, — с
уровнем, на котором открыт каждый.

Открытые ресурсы показываются перед панелями использования и качества ответов. На
телефонах откройте дополнительные действия страницы, чтобы изменить группу. Пока
изменение членства или доступа сохраняется, его элементы управления и закрытие
заблокированы; при отказе ваш выбор сохраняется, чтобы можно было повторить.

**Добавить в эту группу** (Add to this group) открывает доступ сразу к нескольким
вещам: он перечисляет всё, что читатель может редактировать и чего у группы ещё
нет, с поиском, отметкой для каждого и уровнем доступа. Каждый — тот же выданный
доступ, что записывает панель «Доступ», поэтому требует того же права на
редактирование.

Участникам сообщают, когда их группе что-то открывают, — во «Входящих» и, если они
хотят, по электронной почте; *Поделились с вами или вашей группой* в настройках
уведомлений отключает это. Карточки по всей консоли говорят, для кого каждая вещь:
*Все*, её отделы по названию (и то и другое, когда она для всех и принадлежит
отделу) или *Личное*. Читатель видит только то, что мог бы открыть и так, поэтому
участник отдела «Продажи», читающий страницу «Финансов», не узнаёт, что хранят
«Финансы».

## Группировка списка по отделам { #grouping-a-list-by-department }

На страницах «Приложения», «Навыки», «Контекст» и «Базы знаний» есть фильтр
**Группа** (group). Выбор «Финансы» сужает список до того, что открыто «Финансам»,
и выбор остаётся в адресе, поэтому представление — ссылка, которую можно кому-то
отправить. Группа — единственная группировка, которая есть: папок нет, потому что
группа уже решает, кому доступен ресурс, а вторая иерархия была бы вторым ответом
на тот же вопрос.

Фильтр никогда не расширяет список: то, что читатель не может открыть, не
показывается. В списках выбора Конструктора рядом с каждым ресурсом названы его
отделы, а четыре эндпоинта списков принимают `group_id` для того же сужения
через API.

## Бюджет отдела { #a-departments-budget }

Администратор может задать отделу **Месячный бюджет** (Monthly budget) при
создании или изменении. Он считает то, что запускают участники отдела, — любого
агента, в этом календарном месяце, — и останавливает запуск участника, как только
отдел его исчерпал, с отказом, называющим отдел. Человек в двух отделах под обоими
лимитами. См. [уровни бюджета](governance.md#budgets).

Когда отдел израсходовал 80% своего месяца, его руководителю и администраторам
сообщают один раз — во «Входящих» и по электронной почте, если они не отключили
*Бюджет отдела израсходован на 80%*. Когда лимит останавливает запуск, об этом
узнают те же люди.

Страница группы показывает месяц относительно лимита и выгружает его в CSV, по
строке на участника и агента. Карточка **Расходы по отделам** (Spend by department)
на странице «Обзор» перечисляет месяц каждого отдела. И тому и другому нужен
`runs:view`; руководитель отдела также может скачать его CSV через
`GET /orgs/{org_id}/groups/{group_id}/spend.csv`.

## Насколько хорошо отвечают его людям { #how-well-its-people-are-answered }

Рядом с бюджетом страница группы показывает, как люди отдела оценивали ответы за
последние 30 дней: долю полезных, агентов, которых они запускали чаще всего, и
последние ответы с оценкой «Бесполезно», — каждый с комментарием и ссылкой на
его запуск. Оценка засчитывается отделу того, кто её поставил, и каждому отделу, в
котором этот человек состоит. Карточка **Качество ответов по отделам** (Answer
quality by department) на странице «Обзор» ранжирует отделы, начиная с наименее
полезных, за выбранный там период.

Карточка на странице доступна всем с `runs:view` и руководителю отдела; обычный
участник или участник другого отдела не видит ничего из этого. Карточке на «Обзоре»
нужен `runs:view`. API: `GET /orgs/{org_id}/groups/quality` и
`GET /orgs/{org_id}/groups/{group_id}/quality`, обе принимают `from` и `to`.

## Откуда агент берёт знания { #where-an-agents-knowledge-comes-from }

Агента можно привязать к базе знаний, навыку, файлу контекста или MCP-серверу,
открытому более узкому кругу, чем сам агент, и ничто это не отклоняет. Тогда
каждому, кому доступен агент, отвечают из этого источника, включая тех, кто сам не
мог бы его открыть.

`GET /agents/{agent_id}/knowledge-reach` отвечает, откуда агент берёт знания: кому
доступен агент и по каждому источнику — принадлежит ли он всей организации или
каким группам, с пометкой у источников, открытых более узкому кругу, чем агент.
Сузьте агента до тех же групп или расширьте источник, если вы имели в виду не это.

## Группы человека в инструкциях { #the-persons-groups-in-instructions }

Инструкции могут называть группы человека, с которым говорит агент, через
`{{groups}}` — например, *«Вы помогаете кому-то из {{groups}}»*. Подставляются
названия его групп через запятую, а для посетителя — ничего. См.
[Переменные](reference/spec.md#variables).

## Что пока не охвачено { #what-is-not-covered-yet }

Запуск, который не начал никто из организации, — расписание, посетитель в канале, —
не засчитывается ни одному отделу, ведь месяц отдела — это то, что запустили его
участники.

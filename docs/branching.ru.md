# Ветки и что их защищает { #branches-and-what-protects-them }

Одна долгоживущая ветка.

```
feat/… fix/… ──pull request──▶ main
```

`main` — это то, что клонирует читатель этого репозитория и от чего создаются теги. Всё, что в него попадает, приходит одним сквош-коммитом из короткоживущей ветки после того, как CI отработал на пул-реквесте.

Пуш в `main` и тег `v*` ещё и публикуют два образа контейнеров — `ghcr.io/vstorm-co/agenticos-backend` и `-frontend`, `edge` и `sha-<short>` из ветки, версию и `latest` из тега — через `.github/workflows/images.yml`. У этого рабочего процесса нет триггера на пул-реквест, поэтому ответвление репозитория не может публиковать под именем организации, и он отклоняет коммит не из `main`, поэтому тег, отправленный из ветки, тоже не может сдвинуть `latest`; [Развёртывание](deploy.md#the-images) рассказывает, что их забирает.

Ветки `dev` нет. Она была недолго: работа попадала туда и доходила до `main` в релизных пул-реквестах. При таком размере она давала промежуточную ветку, которая никому не была нужна, и стоила второго места, где отлёживалась каждая правка, поэтому её убрали.

## Что обеспечивается и чем { #what-is-enforced-and-by-what }

| Правило | Чем обеспечивается |
|---|---|
| Прямой пуш в `main` запрещён | Набор правил — обязателен пул-реквест |
| CI зелёный до слияния | Обязательные проверки статуса: `lint`, `test`, `test-frontend`, `e2e`, `docs`, `Security Scan` |
| Ни одно новое оповещение сканирования кода не проходит в слияние | Защита слияния при сканировании кода в наборе правил. **Не** собственный статус заданий `analyze`, который зелёный независимо от того, что нашёл анализ, — см. [CodeQL](#codeql-runs-on-the-pull-request) ниже |
| Сквош при слиянии | Набор правил — единственный разрешённый способ слияния |
| Обсуждения решены | Набор правил |
| Устаревшие одобрения сбрасываются при новом пуше | Набор правил |
| Никакой принудительной отправки, никакого удаления | Набор правил |
| Коммит не создаётся, пока вы стоите на `main` | `no-commit-to-branch` в `.pre-commit-config.yaml` |
| Орфография во всех отслеживаемых файлах | codespell — как хук на файлах, которых касается коммит, и как `make lint-spelling` в задании `lint` в CI по всему дереву |
| В маршрутах только роутеры, никаких баннерных комментариев, никакого мёртвого кода | `check_routes.py`, `check_comments.py` и `vulture` — хуки в `.pre-commit-config.yaml` (каждый сканирует всё дерево, `pass_filenames: false`) и шаги `make lint-backend` в задании `lint` в CI |
| Нет объявленной зависимости, которую никто не импортирует | `deptry` — шаг `make lint-backend` в задании `lint` в CI, с проверкой DEP002 и DEP004. Не хук pre-commit: он читает весь манифест против всего дерева, поэтому для этого вопроса нет варианта по отдельным файлам |
| Форматирование YAML, безопасность рабочих процессов, основы pre-commit во всех отслеживаемых файлах | yamlfmt, zizmor и `pre-commit-hooks` (`end-of-file-fixer`, `trailing-whitespace`, `check-yaml/json/toml`, `detect-private-key` …) — как хуки на файлах, которых касается коммит, и как `make lint-precommit` в задании `lint` в CI по всему дереву. Как и орфография, они по своей природе работают по файлам, поэтому обновление `rev:`, приносящее новое правило, ломает каждый существующий файл, и никто этого не замечает, пока несвязанная правка не будет им отклонена |

Хук читает только то, чего касается коммит, и потому сам по себе он плохая защита: опечатка, попавшая в файл вместе с коммитом, лежит там, пока кто-нибудь не отредактирует этот файл по несвязанной причине, — и его коммит отклоняется из-за слова, которого он не писал. Вот почему проверка орфографии стоит в таблице дважды: хук — быстрая обратная связь, а `make lint-spelling` — то, что делает утверждение верным для всего дерева.

Сейчас проверки статуса перечислены по отдельности. Их стоит свести в одно агрегирующее задание `All Checks Passed`, чтобы добавление задания CI перестало означать «не забудьте отредактировать набор правил»: список обязательных проверок, который расходится с рабочим процессом, — так сборка и оказывается зелёной, ничего не проверив.

### Обязательная проверка может законно сообщать `skipped` { #a-required-check-may-legitimately-report-skipped }

!!! info "Пропущенная (`skipped`) обязательная проверка — это успех, а не проблема"

    GitHub считает обязательную проверку статуса выполненной при `success`, `skipped` **или**
    `neutral`. Поэтому ветка только с backend-правками вообще не получает ответа от
    frontend — а значит, «зелёный» на такой ветке — это утверждение о меньшем числе
    заданий, чем запускает `make check`.

Три из этих шести не запускаются на каждом пул-реквесте. `test`, `test-frontend` и `e2e` стоят 8,2, 5,3 и 5,1 оплачиваемой минуты соответственно, а задание `changes` решает, на какие из них набор изменений доказуемо не влияет, — `scripts/ci_changed_scope.py`, поэтому правило можно проверить тестом, а не глобом в YAML-файле ([#317](https://github.com/vstorm-co/agenticos/issues/317)).

Вот почему условие — это `if:` на уровне задания, а **не** фильтр `paths:` в рабочем процессе: отфильтрованный рабочий процесс вообще не публикует свои проверки, поэтому набор правил ждёт шесть контекстов, которые никогда не появятся, и кнопка слияния навсегда остаётся серой.

Классификатор написан по осторожному принципу: **задание пропускается, только когда каждый изменённый путь доказуемо к нему не относится**, поэтому нераспознанный путь запускает всё.

Мягкий вариант той же идеи позволил бы новой папке молча отключить набор проверок — это не красная сборка, а зелёная, из которой пропала проверка, и этот репозиторий уже дважды за это заплатил (#143, #165).

Есть только два исключения, и оба проверяются, а не предполагаются:

- `docs/**`, `mkdocs.yml` и `*.md` верхнего уровня, потому что их не читает ни один тест;
- противоположная половина дерева — для каждого из двух модульных наборов проверок.

`e2e` не освобождён ни от одной половины, а `lint` не ограничивается вовсе — потому что `make lint-spelling` и `make lint-precommit` читают каждый отслеживаемый файл.

Второе исключение не доходит до одной папки. `frontend/src/app/api/**` — это BFF, а `backend/tests/api/test_bff_forwarded_paths.py` сверяет жёстко заданные в этих обработчиках пути `/api/v1/…` с собственной таблицей маршрутов backend — поэтому изменение прокси запускает и backend-набор. Пропустить его здесь означало бы тот же отказ «зелёная сборка без проверки», что выше, причём в единственном тесте, написанном, чтобы его поймать.

Две детали, без которых осторожный принцип на самом деле не держится; в обеих первая версия этого ошибалась:

- У каждого задания под условием рядом с проверкой вывода стоит `!cancelled()`. Без него **неудавшееся** задание `changes` — 502 от API, лимит частоты — пропустило бы все три набора, даже не прочитав их условия, а так как `changes` сам не является обязательным контекстом, кнопка слияния стала бы зелёной над веткой, где не прошёл ни один набор.
- Задание передаёт `previous_filename` наравне с `filename`. Переименование сообщает только путь, куда файл пришёл, поэтому модуль, перенесённый из `backend/`, иначе был бы одним frontend-путём, и изменение, удалившее backend-модуль, пропустило бы backend-набор.

Что пропускает набор изменений, печатается в журнале задания `changes`. Локально ничего не пропускается: `make check` запускает весь набор.

### Пул-реквест поверх другого тоже проходит CI { #a-stacked-pull-request-runs-ci-too }

Две ветки, правящие один файл, принято ставить в стек — второй пул-реквест открывают против первого, а не против `main`, — поэтому триггер `pull_request` в `ci.yml` **не несёт фильтра `branches:`**. Этот фильтр срабатывает по *базе*, и пока он там был, пул-реквест в стеке не совпадал ни с одним триггером и не запускал вообще ничего ([#359](https://github.com/vstorm-co/agenticos/issues/359)).

Опасен был не пропавший запуск, а то, как он читался. Пул-реквест без заданий показывает **пустой** список проверок, а не красный: `gh pr checks` отвечает «о проверках не сообщено», и сводка пуста, что выглядит как ещё не начавшийся запуск. В тот день так слили четыре пул-реквеста, и каждый проверили только на ноутбуке. Пробел не закрывался, пока дочерний пул-реквест не перенаправляли на `main` после слияния родителя, — а это ровно тот момент, когда свежий семиминутный запуск никто не ждёт.

Это стоит немного: задание `changes` классифицирует дочерний пул-реквест по его собственному диффу — оно читает `pulls/{n}/files`, то есть сравнение с собственной базой этого пул-реквеста, — а группа параллелизма ниже отменяет устаревшие запуски дочернего пул-реквеста, как и любые другие.

То, что у триггера нет фильтра по базе, проверяется утверждением, а не предполагается, в `backend/tests/test_ci_workflow.py`. Иначе нельзя: рабочий процесс, который не срабатывает, не оставляет доказательств, что он не сработал, поэтому ничто в запуске не выдаст регрессию. Тот же файл утверждает и другое свойство, которое не покажет ни один запуск, — что каждое задание ограничивает собственное время выполнения (ниже).

Об одном ограничении стоит сказать прямо: **зелёный пул-реквест в стеке проверялся против родителя, а не против `main`** — проверки принадлежат головному коммиту, поэтому перенаправление переносит старый результат без изменений; это присуще стекам, а не что-то, что может исправить триггер, и это причина держать стеки короткими.

### CodeQL работает на пул-реквесте { #codeql-runs-on-the-pull-request }

CodeQL раньше был здесь вторым ограничением. Он работал из настроек GitHub по умолчанию по недельному расписанию, чьи триггеры были не в этом репозитории, поэтому результат анализа приходил в `main` уже после слияния, которое его внёс. `.github/workflows/codeql.yml` заменяет это ([#1415](https://github.com/vstorm-co/agenticos/issues/1415)): анализ идёт на пул-реквесте, по тому же триггеру, что и всё остальное здесь, а недельный полный запуск сохранён для наборов запросов, которые обновляются между слияниями.

С рабочим процессом идут две настройки репозитория, и ни одну из них он сделать не может. Первая: настройку по умолчанию нужно выключить — GitHub отклоняет расширенную загрузку, пока она настроена, поэтому они не могут сосуществовать:

```bash
gh api -X DELETE repos/vstorm-co/agenticos/code-scanning/default-setup
```

Вторая — то, что на самом деле отклоняет слияние. **Зелёное задание `analyze` означает, что анализ выполнился, а не что он ничего не нашёл**: `codeql-action/analyze` загружает свои результаты и завершается с кодом 0, что бы в них ни было. Слияние блокирует [защита слияния при сканировании кода](https://docs.github.com/en/code-security/code-scanning/managing-code-scanning-alerts/about-code-scanning-alerts), правило в наборе правил `main` рядом с шестью обязательными проверками статуса, настроенное с указанием инструмента и порога серьёзности. Без неё оповещение видно в пул-реквесте и на вкладке «Безопасность», и ничто не останавливает слияние — именно так репозиторий и жил раньше, только медленнее.

### Каждое задание ограничивает собственное время выполнения { #every-job-bounds-its-own-runtime }

`changes` было единственным заданием в `ci.yml`, у которого был `timeout-minutes`, поэтому остальные семь наследовали значение GitHub по умолчанию — **360 минут** ([#364](https://github.com/vstorm-co/agenticos/issues/364)), и зависшее задание держало бы свою обязательную проверку статуса шесть часов, а в этом репозитории ничто не закончило бы его раньше. Это было написано как предосторожность против того, чего никто не видел. Четырнадцать запусков `e2e` упёрлись в ограничение в течение четырёх дней до 18 августа ([#879](https://github.com/vstorm-co/agenticos/issues/879)) — а как выглядит задание, когда это происходит, описано ниже.

| Задание | Ограничение | Наблюдалось |
|---|---|---|
| `changes` | 5 | 7 с |
| `lint` | 10 | 22 с |
| `Security Scan` | 10 | 14 с |
| `docs` | 15 | 4 мин 34 с |
| `test-frontend` | 45 | 20 мин 07 с |
| `backend-shards` | 45 | — |
| `test` | 10 | — |
| `e2e` | 25 | 8 мин 01 с |

Большинство наблюдавшихся времён — из запуска 31116003994, полной матрицы на `main`. Время backend — из запуска 41102882122, время frontend — из 41108431368, оба 30 октября 2026 года. Сборка образов идёт отдельно в `images.yml`. Каждое ограничение в несколько раз больше своего задания, а не чуть выше: таймаут существует, чтобы оборвать зависание, а слишком тесное ограничение, которое обрывает законно медленный холодный кеш, — это красная сборка по причине, не связанной с диффом.

### Один запуск на ветку { #one-run-per-branch }

`ci.yml` несёт группу параллелизма с ключом `github.ref`, поэтому повторный пуш в ветку отменяет её предыдущий запуск. Это важно, потому что `AGENTS.md` требует коммит и пуш на каждую законченную часть: если бы ничто не отменяло, 75 из 369 запусков за первые шесть дней августа были бы заменены, ещё находясь в работе, — около 1800 оплачиваемых минут на ответы о коммитах, которых никто не ждал.

**Пуш в `main` освобождён, и то, как это сделано, — самое интересное.**

Собственный запуск слияния — то, что придаёт смысл истории и значку, поэтому запуск в `main` не должен ни отменяться, ни вставать в очередь.

`cancel-in-progress: false` даёт только первое из этого. `false` означает *очередь*, а GitHub отменяет любой ранее **ожидающий** запуск в группе, когда в очередь ставится новый.

При одной группе для `main` — слияние A выполняется, B ждёт — приход C отменил бы B целиком, и коммит B вообще не получил бы CI. При четырнадцати выпусках за шесть дней и запуске `main` примерно на 10 минут два слияния в одном окне — не редкая картина.

Поэтому при пуше группа несёт `github.run_id`, уникальный для запуска: каждое слияние получает собственную группу и ни с чем не сталкивается. У всех пул-реквестов получается один и тот же суффикс, и они продолжают отменять друг друга по `github.ref`.

### Две вещи сообщают `cancelled`, и только одна из них — действительно отмена { #two-things-report-cancelled-and-only-one-of-them-is-that }

Раздел выше — это отмена, работающая как задумано, и именно её все вспоминают. **Другая — задание, у которого кончились его `timeout-minutes`**: GitHub записывает задание, оборванное по ограничению, как `cancelled`, а не как сбой, — и обязательная проверка со статусом `cancelled` *не* считается успехом так, как считается `skipped`, поэтому слияние остаётся заблокированным на диффе, который в порядке.

Отличить их — один взгляд:

| | Заменённый (#317) | Оборванный по ограничению (#879) |
|---|---|---|
| Что ещё есть в запуске | все идущие задания отменены вместе | **одно** задание; остальные зелёные |
| Собственный вывод запуска | `cancelled` | `success`, кроме одного задания |
| Длительность отменённого задания | сколько оно успело | его `timeout-minutes`, до секунды |
| Более новый пуш в ветку | да — в этом причина | нет |
| Последняя строка журнала | `The operation was canceled.` | та же строка, и в ней ловушка |

Выдаёт длительность. `gh api repos/vstorm-co/agenticos/actions/runs/<id>/attempts/<n>/jobs` даёт `started_at`, `completed_at` и выводы по шагам — **и это должна быть форма `attempts/<n>`**, потому что повторный запуск переписывает то, что отвечает обычный эндпоинт `runs/<id>/jobs`: задание, перезапущенное в зелёный, сообщает там `success`, а первоначальный вывод исчез.

Общим у этих четырнадцати был один шаг: `playwright install --with-deps`, вызывающий `apt-get`, который зависает без ограничения, когда зеркало Azure у раннера недоступно. Задание e2e больше вообще не устанавливает системные пакеты, а `backend/tests/test_ci_workflow.py` отклоняет шаг, который стал бы это делать. Общий урок, впрочем, переживёт этот шаг: **шаг, обращающийся к третьей стороне, — это шаг, который может зависнуть без собственного ограничения**, а зависший тратит весь бюджет задания и потом отчитывается как чья-то чужая отмена.

## Сквош, и почему важен заголовок пул-реквеста { #squash-and-why-the-pull-request-title-matters }

!!! important "Описание пул-реквеста *и есть* сообщение коммита, которое остаётся"

    `main` хранит один коммит на пул-реквест, собранный из заголовка и описания, а не из
    собственных коммитов ветки. Формат — в `AGENTS.md`.

Поэтому `wip`, `fixup` и `try again` туда не доходят — и описание здесь не любезность.

## Аварийный выход { #the-escape-hatch }

!!! warning "Нет участников, обходящих правила"

    Владелец, которому нужно слить что-то сейчас, отключает набор правил, сливает и
    включает его обратно — три щелчка и запись в журнале аудита, ровно столько трения,
    сколько нужно для того, что должно быть редким.

Это намеренно: обход, который доступен всегда, — это обход, которым пользуются каждую неделю, и путь выпуска, который никто не может описать.

## Обновления зависимостей { #dependency-updates }

Backend обновляется еженедельно, причём фреймворки для агентов выделены в отдельную группу — они меняются быстро, и эта кодовая база должна за ними успевать. Frontend обновляется ежемесячно, после семидневного периода ожидания.

Dependabot предлагает обновления для **прямых** зависимостей. Всё под ними двигается, только когда прямая зависимость тянет это за собой, — вот почему существует `.github/workflows/dependency-freshness.yml`: раз в неделю он обновляет весь файл блокировки, включая транзитивные пакеты, запускает против него весь набор проверок и открывает задачу на GitHub (issue), если что-то сломалось. Ничего не коммитится; обновление выбрасывается вместе с раннером. `make deps-upgrade-all` делает то же самое локально и позволяет воспроизвести красную задачу из него.

Две вещи в нём неочевидны, и обе стоили времени, прежде чем их поняли:

- **Шаблон группы должен нести завершающую `*`, чтобы совпасть с зависимостью, записанной с extras.** `pydantic-ai-slim[openrouter,…]` не совпадает с `pydantic-ai-slim`. Это молчание стоило месяцев: группа `agent-frameworks` не открыла ни одного пул-реквеста, а среда выполнения ехала в `backend-everything-else` вместе со своими мажорными версиями. Наоборот, `fastapi` остаётся точным, потому что объявлен без extras и не нуждается в шаблоне; когда-то ему нужно было избегать шаблона, так как `fastapi*` ловил и `fastapi-cache2`, пока эту зависимость не убрали в #155.
- **Dependabot не может обновить `frontend/bun.lock`.** Его экосистема npm знает `package-lock.json`, `yarn.lock` и `pnpm-lock.yaml`, но не файл bun. Поэтому обновление frontend приходит одним `package.json`, а `bun install
  --frozen-lockfile` отклоняет несовпадение, делая `test-frontend` и `e2e` красными по причине, не связанной с зависимостью. **Пересоздайте его вручную** в ветке пул-реквеста:

  ```bash
  cd frontend && bun install --lockfile-only && git commit -am "build(deps): sync bun.lock"
  ```

  Автоматизировать это сложнее, чем кажется: рабочий процесс на `pull_request` получает токен только для чтения, когда его запустил Dependabot, что бы ни говорил блок `permissions`, поэтому он не может отправить результат обратно.

**Dependabot не может прочитать backend, пока тот требует Python 3.15.** Его задание uv останавливается на строке `requires-python`, поэтому он не открывает пул-реквесты для backend — `make deps-upgrade` двигает файл блокировки вручную, — а его оповещения продолжали бы совпадать с версиями, закреплёнными раньше. Поэтому `.github/workflows/dependency-graph.yml` отправляет граф сам: при каждом пуше в `main`, который двигает `backend/uv.lock`, `scripts/dependency_snapshot.py` перечисляет каждую закреплённую версию, и оповещения открываются и закрываются по ним.

## Проверки кода { #reviews }

[Автоматический проверяющий](code-review.md) работает на каждом пул-реквесте. Он никогда не бывает обязательной проверкой, поэтому не может завалить сборку, — но его результаты — это цепочки обсуждения, а набор правил выше требует, чтобы их решили. Ответить недостаточно — кто-то должен пометить цепочку решённой, прежде чем кнопка слияния вернётся. См. [code-review.md](code-review.md).

Качественная половина CodeQL открывает цепочки на тех же условиях, как `github-code-quality[bot]`. Её нельзя фильтровать по правилу или по пути — единственный выключатель — «выкл» для целого языка, а это не тот обмен, на который стоит идти, — поэтому [code-review.md](code-review.md#codeql-and-the-findings-that-block-a-merge) вместо этого перечисляет уже разобранные результаты, и решение одного из них стоит щелчка, а не сочинения.

## Итог { #recap }

- **Одна долгоживущая ветка.** Ветка, пул-реквест, сквош при слиянии.
- Пуш отменяет идущий запуск, поэтому повторный пуш — это ещё и решение перестать заботиться о предыдущем ответе.
- CI запускает **меньше заданий, чем `make check`**; пропущенная обязательная проверка считается успехом, а не проблемой.
- `main` освобождён от отмены, и способ этого освобождения — группа параллелизма с `github.run_id`: он уникален для запуска, поэтому ни один запуск `main` не отменяет другой.

## Черновые пул-реквесты { #draft-pull-requests }

Черновики запускают lint для backend и frontend и проверки зависимостей и безопасности. Наборы тестов backend и frontend, производственная сборка, E2E, сборка документации и CodeQL ждут, пока пул-реквест не станет **Ready for review** (готов к проверке). Этот переход запускает проверки без нового пуша. Последующие пуши в готовый PR запускают применимые проверки, как раньше. Возврат в черновик отменяет его заменённый запуск и оставляет лёгкие проверки активными. Пока идёт работа, используйте локальные тесты по нужным файлам; помечайте PR готовым, когда нужен полный CI. Черновик не может слиться. Готовые PR сохраняют существующие обязательные проверки и защиту сканирования кода; смена статуса черновика их не отменяет.

## Релизные срезы и релизные поезда { #release-cuts-and-release-trains }

Держите отдельные PR и используйте один **ручной ежедневный релизный поезд**, когда есть невыпущенные изменения. Планового среза и автоматической публикации нет. Рабочий процесс команды таков:

1. Во время разработки используйте черновики, локальные тесты по нужным файлам и лёгкие проверки CI.
2. Помечайте PR готовым к проверке, чтобы запустить полный применимый CI и CodeQL.
3. Сливайте каждый проверенный зелёный PR независимо. Не ждите выпуска предыдущего PR.
4. Раз в день готовьте один срез со всеми слитыми невыпущенными изменениями. Для новых функций и ломающих изменений используйте минорное повышение версии, для одних исправлений — патч.
5. Перед публикацией требуйте успешных CI и CodeQL для SHA слияния среза, включая разрешённое переиспользование проверенных источников. Публикуйте выпуск и тег вместе. Развёртывание в production сохраняет отдельное одобрение.
6. Срочные исправления выпускайте немедленно через тот же процесс проверки, проверок, среза и одобрения, вне ежедневного ритма.

PR в стеке сливаются в порядке зависимостей и могут делить один выпуск. Объединять несвязанные изменения в один большой PR не нужно. Каждый готовый PR и каждое слияние обычных изменений по-прежнему проходят применимый к ним CI: пакетирование выпусков снижает накладные расходы на выпуск, а не проверку, которую должно пройти отдельное изменение.

Сначала слейте PR с новыми функциями, затем подготовьте один срез для поезда. Выберите наибольшее выпускаемое повышение: `make release-cut BUMP=patch` или `BUMP=minor` печатает план из свежего `origin/main`. Добавьте `CREATE_PR=1`, чтобы создать отдельный worktree, обновить только CHANGELOG и три версии приложения, закоммитить, отправить и открыть PR среза из своей учётной записи `gh`. Он отклоняет пустые разделы Unreleased и одновременные открытые срезы. Он никогда не сливает и не публикует. После слияния среза создайте выпуск и его тег вместе, нацелившись на коммит слияния среза, как описано в `AGENTS.md`.

И CI, и CodeQL узнают срезы по их фактическим git-деревьям. Отличаться могут только CHANGELOG и версии приложения; зависимости, конфигурация, режимы файлов и весь остальной исходный код должны совпадать с предыдущим успешным полным запуском. CI требует, чтобы прошли все три тяжёлых набора проверок, а CodeQL — все четыре анализа. Пропущенные задания не доказательство. Доказательство для PR записывает фактически проверенный синтетический SHA слияния, а не доверяет SHA головы ветки из API запусков.

Ищутся последние 30 успешных запусков; при отсутствии доказательств или сбое API запускаются полные проверки. Это относится к PR среза и его слиянию в `main`. Обычные изменения исходного кода проходят существующие проверки, а плановый CodeQL остаётся полным. Набор правил и защита слияния при сканировании кода остаются включёнными.

Для переиспользования CodeQL дополнительно нужны все четыре сохранённых отчёта SARIF из полного анализа. Он загружает их для нового коммита и ждёт обработки, поэтому защита слияния при сканировании кода всё равно получает результаты для этого коммита. Переиспользованные запуски не дают основания для дальнейшего переиспользования; плановые анализы остаются полными.

Образы по-прежнему собирают backend и frontend для SHA среза, потому что эти образы содержат версию приложения. Тег переиспользует опубликованные манифесты этого SHA; сканирования и все шесть SBOM всё равно выполняются, а SBOM прикрепляются к существующему выпуску. Каждый недостающий образ собирается отдельно. Образы для браузера тоже могут переиспользовать манифест, ключ которого строится из их полного контекста Docker, закреплённого дайджеста базового Debian и номера недели ISO: обновления пакетов заставляют обновиться при первой сборке каждой недели. Псевдонимы SHA и версии остаются доступными для развёртывания и отката.

Развёртывание в production предлагается, когда опубликован стабильный выпуск. Черновики и предварительные выпуски его не предлагают. Одобрение для production, проверка происхождения от `main` и ручной `workflow_dispatch` сохраняются; для отката явно выберите коммит или тег. Наблюдатель за очередью сравнивает с последним стабильным выпуском, а не с невыпущенными коммитами в `main`, и сообщает о неизвестном отставании после ручного развёртывания.

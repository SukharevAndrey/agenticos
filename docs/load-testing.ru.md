# Нагрузочное тестирование и устойчивость { #load-and-resilience-testing }

AgenticOS отдаёт ответы потоком, выполняет фоновую работу и держит сокеты
открытыми, но ничто из этого не говорит о том, сколько такого один экземпляр
может делать одновременно. Асинхронный код — ещё не результат измерения ёмкости, а
зелёный набор модульных тестов — не нагрузочный тест. Поэтому есть набор, который
это измеряет, в `loadtest/`, и эта страница о том, что он измеряет, что считает
успехом и как запустить его снова.

Цифры, которые выдаёт запуск, принадлежат машине, на которой он шёл. Ничто здесь
не доказывает архитектурную цель NFA-006 в тысячу пользователей, а один запуск на
одном хосте доказывает цель NFA-001 по задержке только для этого хоста: оба
обстоятельства отмечены там, где они касаются порога, а не выданы молча за факт.

## Нагрузка { #the-workload }

Трафик экземпляра — это в основном люди, читающие списки, часть из них
разговаривает с агентом, немногие загружают документ, и тонкой струйкой идут
события, запускающие автоматизации, за которыми никто не следит. Смесь говорит об
этом цифрами:

| Нагрузка | Доля | Что такое один запрос |
|---|---|---|
| `api_read` | 45% | Аутентифицированный список — агенты, запуски, диалоги |
| `chat_stream` | 20% | Ход чата по WebSocket, каждый пятый отменяется на середине |
| `agent_run` | 15% | `POST /agents/{id}/run` — тот же механизм выполнения, но без сокета |
| `rag_query` | 12% | Поиск: один эмбеддинг, один векторный поиск |
| `ingest` | 5% | Загруженный документ: API его принимает, а воркер индексирует |
| `trigger_fire` | 3% | Подписанная доставка вебхука, запускающая автоматизацию |

Доли заданы в `loadtest/scenario.py`, каждая — одна строка, и именно с ними и
стоит спорить. Экземпляр, чей трафик выглядит иначе, правит их и запускает заново;
недопустимо другое — цифра, взятая из смеси, на которую никто не смотрел.

### Интенсивность поступления, а не пул воркеров { #arrival-rate-not-a-worker-pool }

Запросы подаются по **расписанию**. Замкнутый цикл из N воркеров, каждый из
которых ждёт предыдущего, снижает собственную интенсивность поступления ровно
тогда, когда сервер замедляется, — и упавший сервер отчитывается удобными
задержками и пропускной способностью, которая тихо упала вдвое. Открытая модель
поступления продолжает подавать работу с заданной интенсивностью и даёт очереди
расти — а проверяется именно это.

Какая нагрузка достанется каждому запросу, решает последовательность с низким
расхождением, а не бросок кубика, поэтому два запуска с одной интенсивностью
выдают одинаковое число загрузок, и любое различие между ними — это различие
платформы.

### Фазы { #the-phases }

| Фаза | Секунд | Подаётся в секунду | Для чего |
|---|---|---|---|
| `ramp` | 60 | 4 | Холодный кеш — не установившийся режим |
| `sustain` | 180 | 12 | **По ней судят о каждом пороге** |
| `burst` | 45 | 36 | Втрое выше интенсивность — именно так выглядит веер запросов |
| `recover` | 60 | 12 | Платформу, которая восстанавливается, и платформу, которая остаётся деградировавшей, во время всплеска не отличить |

## Что считается успехом { #what-counts-as-a-pass }

Эти пороги **предложены, а не согласованы**. Приёмка NFA-004 требует
согласованных; изложив их здесь, мы даём запуску вердикт вместо стены цифр и
переводим разговор на конкретную величину, а не на вопрос, должен ли он быть вообще.
Ничто здесь не является обязательством, взятым от чьего-либо имени.

| Нагрузка | Метрика | Предел | Почему такой |
|---|---|---|---|
| `api_read` | p95 | 300 ms | Один запрос за проверкой разрешений; всё выше — это ожидание в очереди, а не работа |
| `api_read` | error rate | 0.1% | Запас на пересозданное соединение, и ничего больше |
| `chat_stream` | p95 first token | 1500 ms | Доля платформы: сокет, аутентификация, спецификация, возможности, строка запуска |
| `chat_stream` | error rate | 1% | Потерянный сокет стоит человеку ответа |
| `agent_run` | p95 | 5000 ms | Весь путь запуска против заглушки, от начала до конца |
| `rag_query` | p95 | 1200 ms | Этот предел ограничивает pgvector и пул перед ним |
| `ingest` | error rate | 0% | Принятая и затем потерянная загрузка — худший отказ из возможных здесь |
| `trigger_fire` | error rate | 0% | Ответ 2xx означает, что за событие взяли ответственность |

Каждый порог оценивается отдельно по нагрузке намеренно. Одно число по смешанному
запуску не описывает ничего: загрузка и список — не один и тот же запрос.

Нагрузка, не давшая ни одного образца, читается как **не измерено**, а не как
успех. Запуск, который пропустил сценарий и отчитался зелёным по нему, — тот самый
отказ, ради предотвращения которого и существует весь этот файл.

## Модель — заглушка, и медленная намеренно { #the-model-is-a-stub-and-slow-on-purpose }

`loadtest/stub_model.py` обслуживает API Chat Completions и эндпоинт эмбеддингов, с
задержкой до первого токена и темпом на токен, которые задаёт запуск. Нагрузочный
тест, чья модель отвечает мгновенно, измеряет платформу под нагрузкой, которой не
бывает: любой настоящий провайдер тратит сотни миллисекунд, а сколько параллельных
запросов держит экземпляр, решает то, как долго запуск держит свои ресурсы
занятыми в ожидании.

Ей можно также велеть вести себя плохо: `--error-rate` отклоняет заданную долю ответом
500, а `--timeout-rate` держит их открытыми — это половина NFA-004 про
устойчивость. То, что платформа делает, когда её провайдер отказывает, — свойство
самой платформы, и измерить его на провайдере, который ведёт себя хорошо, нельзя.

Ничто в запуске по умолчанию не обращается к платному провайдеру. Эмбеддинги тоже
от заглушки, и обращаются к ним так же, как к эндпоинту Ollama без ключа, поэтому
измерить можно даже экземпляр вообще без ключа провайдера. Сквозное измерение на
настоящем провайдере — осознанный шаг: направьте профиль модели из фикстуры на
него и ждите в цифрах его собственные задержки и ограничения частоты.

## Запуск { #running-it }

Нужны четыре вещи, и `run.py` отказывается стартовать без любой из них, вместо
того чтобы измерять экземпляр, который не может выполнить работу:

1. база данных с применёнными миграциями и Redis;
2. отвечающая модель-заглушка, **по адресу, доступному из API**, — см. ниже;
3. фикстура — `make load-seed`, один раз;
4. воркер (`python -m app.worker`), если нагрузка `trigger_fire` должна что-то
   значить. Без него вебхук принимается, а его срабатывание ждёт в очереди, так
   что нагрузка измеряет входную дверь, а не запуск.

### Где должна слушать заглушка { #where-the-stub-has-to-listen }

К заглушке обращается *API*, а не драйвер, поэтому адрес, записанный в профиль
модели, должен работать оттуда, откуда работает API. Две топологии:

| Где работает API | Привязка | Что записать |
|---|---|---|
| На этом хосте (`uv run uvicorn …`) | `127.0.0.1` (по умолчанию) | `http://127.0.0.1:4020` (по умолчанию) |
| В стеке Compose (`make dev`) | `LOAD_STUB_BIND=0.0.0.0` | `LOAD_STUB_URL=http://host.docker.internal:4020` |

Loopback внутри контейнера `app` — это сам контейнер, а не хост, поэтому вторая
строка там обязательна. Из-за ошибки здесь проверка перед запуском завершается
с сообщением о пустой коллекции, а не об адресе, потому что эмбеддинги тоже
не доходят до заглушки.

```bash
make load-stub-model                       # terminal one
make load-seed                             # once
make load-test API_PID=$(pgrep -f uvicorn | head -1) \
  DATABASE_URL=postgresql://postgres:postgres@127.0.0.1:5432/agenticos \
  > loadtest/results/$(date +%F)-thismachine.md
```

`API_PID` и `DATABASE_URL` необязательны. Без них запуск измеряет запросы и
**называет в отчёте замеры, которые не удалось снять**, а не печатает вместо них
нули.

Файл фикстуры **не содержит учётных данных**. Запуск сам входит по `--email` и
`--password` (это значения по умолчанию, записанные при засеве), поэтому
Bearer-токен не попадает на диск, а фикстура, засеянная вчера, работает и
сегодня: истекающий токен в файле был и секретом в состоянии покоя, и запуском,
который отказывался по непонятной причине.

Для измерения ёмкости стоит поднять две настройки, и строка топологии в отчёте
должна говорить, когда они были подняты:

- **`RATE_LIMIT_RUN_PER_MINUTE`**. Лимит действует на каждого вызывающего, а драйвер
  — одна учётная запись, выступающая за многих, поэтому при значении по умолчанию
  30 эксперимент измеряет лимит частоты, а не платформу.
- **`UVICORN_WORKERS`**, если вопрос о хосте, а не об одном воркере.

`--scale 0.1` сокращает каждую фазу и не меняет больше ничего — для проверки самого
стенда. Сократить запуск, снизив его *интенсивность*, — значит провести другой
эксперимент под тем же названием.

`--connections` ограничивает собственные сокеты драйвера и по умолчанию равен
пиковой интенсивности сценария, умноженной на самый медленный запрос, — 3 240 для
поставляемых фаз. Потолок ниже этого превращает запуск с открытым поступлением в
замкнутый во время всплеска, ровно когда это важнее всего: запросы встают в
очередь внутри клиента, и часть задержки в отчёте — задержка самого драйвера.

### С холодного старта и в CI { #from-a-cold-start-and-in-ci }

`make load-cold` — это весь запуск с пустой базы данных: он применяет миграции,
создаёт владельца, запускает на этом хосте заглушку, API и воркер, засевает
фикстуру, проводит сценарий и всё снова останавливает. Засев загружает свой корпус
через API и ждёт, пока каждый документ станет находимым, поэтому ему нужен воркер.
Код выхода и есть вердикт: порог, который не выполнен или не измерен, проваливает
запуск. А `LOAD_SCALE` и `LOAD_REPORT` задают длину и место отчёта.

Рабочий процесс `Load` запускает ровно это каждую ночь на `main`, по запросу и на
пул-реквесте с меткой `load-test`, и публикует отчёт как сводку задания и артефакт.
Это не обязательная проверка: процессор общего раннера — общий ресурс, поэтому он
ловит регрессию другого порядка, а не просто более медленный день.

## Как читать отчёт { #reading-the-report }

Четыре раздела — в том порядке, в каком задаются вопросы: что запускалось, что
происходило во время `sustain`, что происходило во время `recover` и пройден ли
порог. Вердикт стоит последним намеренно: вердикт в начале приглашает прочитать
только его, а число образцов под ним и говорит, значим ли хвост или это
всего три запроса.

В шапке два числа, которые стоит проверить прежде всего. **Подано и записано**
должны совпадать: каждый поданный запрос оставляет образец, успешный
или неуспешный, включая запрос, брошенный при завершении запуска; недостача
значит, что доли ошибок считаются по знаменателю, который меньше нагрузки, —
отчёт говорит об этом баннером и называет себя непригодным. **Поздние отправки**
— это признание драйвера, что он отстал от собственного расписания и стал частью
измерения.

Пропускная способность для устойчивой фазы показана дважды: завершения, попавшие в
окно, и запросы, поданные за это время. Они расходятся, когда экземпляр отстаёт, —
и это единственный случай, когда число интересно.

Перцентили — **по ближайшему рангу**, без интерполяции: интерполированный p99 по
девяноста образцам — это число между двумя измерениями, которых никто не наблюдал.
А задержка измеряется только по **успешным** запросам. Запрос, отклонённый за 3 мс,
— не быстрый запрос, и пустить его в распределение — это способ, которым упавший
запуск отчитывается лучшими перцентилями за всю историю; отказы считаются отдельно
и называются.

CPU — это разность накопленного процессорного времени процесса на каждом интервале
замера, а не `%CPU` из `ps`: procps определяет его как процессорное время за всё
время жизни процесса и прямо говорит, что это не загрузка, поэтому замер по нему
усреднил бы ту короткую перегрузку, которую и должен вызвать всплеск. Разрешение
поэтому — шаг часов `ps` в пределах интервала замера, а на Linux — одна секунда при
интервале замера в две секунды.

## Чего этот набор не измеряет { #what-this-suite-does-not-measure }

Сказано прямо, а не оставлено на самостоятельное открытие:

- **Пропускная способность воркера.** Нагрузки `ingest` и `trigger_fire` измеряют
  *приём* — API отвечает 202 и передаёт работу в очередь. Как быстро воркер разбирает
  эту очередь — измеряется там, где находится воркер, и здесь это не
  утверждается.
- **Всё, что касается настоящего провайдера.** Каждая задержка в запуске по
  умолчанию — это задержка платформы плюс заявленная задержка заглушки.
- **Консоль.** Фронтенд не задействован; это пути API.
- **Сколько стоит передача ответа.** Драйвер работает на той же машине, что и
  экземпляр, поэтому каждое число здесь — задержка без канала под ней. Поэтому же
  запуски ниже ничего не говорят о сжатии ответов: на loopback это потраченный
  CPU и несэкономленная полоса пропускания, а нагрузки, которая выигрывает от него больше
  всех, — длинного транскрипта, — в смеси нет.
- **Кластер.** Один экземпляр, одна база данных. Цель NFA-006 архитектурная, и
  запуск на одном хосте не говорит о ней ничего ни в ту, ни в другую сторону.

## Измеренные запуски { #the-measured-runs }

Закоммичены в `loadtest/results/`, каждый — с машиной, топологией и датой в
начале, потому что число без них — не результат.

Пока закоммичены два запуска, на одной машине, отличающиеся одной настройкой:

| | `2026-09-16-macbook-default-pool.md` | `2026-09-16-macbook-pool-raised.md` |
|---|---|---|
| Пул | 5 + 10 переполнения (значения по умолчанию) | 20 + 30 переполнения |
| Устойчивая фаза 12/с | все пороги выполнены, отказов нет | все пороги выполнены |
| Весь запуск, включая всплеск | **1 537 из 4 740 не прошли**, 6 559 тайм-аутов пула | 13 не прошли, тайм-аутов пула нет вовсе |
| **После всплеска** | **66–100% по-прежнему не проходят** | **отказов нет; задержка спадает** |

Вывод, и причина, по которой запусков два: **на этой нагрузке ограничивает пул
соединений, а не CPU.** Оба запуска упирались примерно в 90% *одного* ядра на
десятиядерной машине, потому что воркер был один. Значит, поднимать надо сначала
пул, потом `UVICORN_WORKERS`, — и их произведение должно оставаться ниже
`max_connections` базы данных, ведь один воркер уже доходил до 84 из 100 по
умолчанию.

Строку про восстановление читайте первой. С пулом по умолчанию запрос, которому не
досталось соединения, ждёт все тридцать секунд `DB_POOL_TIMEOUT`, поэтому завал
переживает создавший его всплеск, и экземпляр всё ещё отказывает с частотой,
которую десять минут назад держал с запасом. Каждый файл результата несёт все
рассуждения целиком.

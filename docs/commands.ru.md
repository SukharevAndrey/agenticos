# Команды { #commands }

Этот проект даёт команды через два интерфейса: цели **Make** для частых рабочих
процессов и **CLI проекта** для точного управления.

## Команды Make { #make-commands }

Запускайте их из корневого каталога проекта.

### Быстрый старт { #quick-start }

| Команда | Описание |
|---------|-------------|
| `make quickstart` | Запустить Docker, выполнить миграции, создать администратора. **Не** устанавливает зависимости — сначала `make install` |
| `make install` | Весь путь настройки: `backend/.env` из примера, если его нет, зависимости бэкенда через uv, `frontend/node_modules` через bun и хуки pre-commit. Всё это, потому что `make check` нужно всё это: `db-check` читает файл окружения, а eslint, prettier, tsc, vitest и next живут только в `node_modules`. И то и другое делается для каждой рабочей копии, так что на каждом клоне это нужно заново; существующий `.env` никогда не перезаписывается |

### Разработка { #development }

| Команда | Описание |
|---------|-------------|
| `make run` | Запустить сервер разработки с горячей перезагрузкой |
| `make run-prod` | Запустить боевой сервер (0.0.0.0:8000) |
| `make routes` | Показать все зарегистрированные маршруты API |
| `make test` | Набор тестов бэкенда плюс порог в 100% покрытия слоя платформы. Выполняется в нескольких процессах-воркерах (`-n auto --maxprocesses 4`); `pytest-cov` объединяет их данные, поэтому порог не меняется |
| `make test-cov` | Запустить тесты с отчётом о покрытии (HTML + терминал). Выполняется в нескольких процессах-воркерах, как `make test` |
| `make format` | Автоформатирование кода — ruff на бэкенде, prettier на фронтенде |
| `make lint` | Все статические проверки: ruff, ruff format, ty, vulture, deptry, eslint, prettier, tsc, скрипты защитных проверок (backtick, i18n, routes, banner comments), проверка зависимостей knip и codespell по всему дереву |
| `make lint-backend` / `make lint-frontend` | Одна половина перечисленного. CI запускает их в двух разных задачах, поэтому любую можно запускать отдельно |
| `make dead-code` | Неиспользуемые функции и методы — vulture с меньшей уверенностью, чем у порога `lint`, плюс полный отчёт knip по фронтенду. Отчёт для чтения, а не порог: на кодовой базе, движимой реестрами, он идёт с ложными срабатываниями (команда CLI, хук возможности), так что читайте каждое, прежде чем удалять. Ту же роль `dependency-freshness` играет для зависимостей. Его единственная однозначная половина — пакет в `package.json`, который никто не импортирует, — проверяется в `lint-frontend` (`bun run lint:deps`), потому что именно зависимость, месяцами пережившая неиспользование, и стала поводом |
| `make lint-spelling` | codespell по каждому отслеживаемому файлу. Хук pre-commit читает только файлы, которых касается коммит, поэтому опечатка, пришедшая со своим файлом, ждёт там, чтобы отклонить чей-то ещё несвязанный коммит |
| `make lint-precommit` | yamlfmt, zizmor и основы `pre-commit-hooks` по каждому отслеживаемому файлу. По той же причине, что `lint-spelling`: эти хуки работают по файлам, так что обновление `rev:`, приносящее новое правило, ломает дерево, и никто этого не замечает. `SKIP` убирает хуки, которые уже проверяют `lint-backend`/`lint-frontend`/`lint-spelling`, так что это не удваивает их время и не позволяет автоисправлению переписать файл посреди проверки |
| `make build-frontend` | `next build`. Проверяет типы дерева маршрутов и падает на серверном компоненте, который не может отрисоваться, — чего не видят ни tsc, ни vitest |
| `make desktop-dev` / `make desktop-build` | Открыть или упаковать оболочку для компьютера — окно Tauri вокруг консоли, которую вы называете по адресу. Нужны Rust и веб-представление платформы; остальное — в `docs/desktop.md` |
| `make desktop-check` | `bun test` по питомцу, затем rustfmt, clippy с запретом предупреждений и Rust-тесты оболочки. Не входит в `lint` и `check`, потому что в CI пока нет набора инструментов Rust |
| `make audit` | Проверить набор зависимостей из файла блокировки на известные уязвимости. Нужна сеть — один запрос на каждый зафиксированный пакет, — поэтому последняя строка говорит, в каком из четырёх состояний запуск закончился, а не оставляет красный запуск двусмысленным. См. ниже |
| `make sandbox-token` | Сгенерировать собственный `SANDBOXD_TOKEN` сервиса песочницы в `backend/.env`, один раз. `make dev` запускает это за вас; он никогда не перегенерирует, потому что новый токен осиротит каждое рабочее пространство, которое держит сервис. Форма подключения предлагает сохранить то же значение в хранилище секретов, так что вставлять его куда-либо не нужно |
| `make seed-skills-lab` | Собрать организацию Skills lab на работающем стеке, чтобы прокликать улучшение навыков: один навык, `returns-policy`, которым пользуются несколько агентов, их тестовые вопросы и оценённые чаты. Общается со стеком по HTTP, поэтому создаёт только недостающее, а повторный запуск сохраняет то, что люди изменили. Логин владельца и ключ провайдера берутся из `SKILLS_LAB_EMAIL`, `SKILLS_LAB_PASSWORD` и `SKILLS_LAB_OPENROUTER_KEY`; `SKILLS_LAB_URL` называет стек. `PROBE=v1`, `broad`, `narrow` или `gift` измеряет одну формулировку навыка в отдельной организации, а `DROP_PROBES=1` удаляет эти организации |
| `make clean` | Удалить файлы кэша (__pycache__, .pytest_cache и т. п.) |

### Перед пул-реквестом { #before-a-pull-request }

!!! success "`make check` — это каждая задача CI, кроме `e2e`"

    Равенство поддерживается, а не постулируется, и
    `backend/tests/test_ci_parity.py` следит, чтобы оно оставалось верным. Оно
    расходилось четыре раза.

`.github/workflows/ci.yml` вызывает те же цели Make, а не повторяет их команды,
поэтому проверяющая задача, в которой появляется шаг, не выполняемый `check`,
роняет тест паритета — как и обратное.

```bash
make check   # lint, test, db-check, test-frontend-cov, build-frontend, docs-build, audit
```

Около пяти минут, последовательно, на прогретом кэше. Что он намеренно пропускает:

| Чего нет в `check` | Почему, и что запускать вместо |
|---|---|
| `e2e` | Нужна база после миграций, организация с начальными данными и работающий бэкенд: `make dev && make platform-bootstrap && make test-e2e` |
| Сборка образов, публикация и сканирование Trivy | `.github/workflows/images.yml` запускает их при отправке в `main` и на теге `v*` и публикует в GHCR |
| `make test-migrations` | CI проходит цепочку на одноразовой `test_db`. На ноутбуке `alembic downgrade base` смотрит на то, что говорит `backend/.env`, — обычно это база с вашей собственной работой. `uv run pytest tests/test_migrations.py` задаёт тот же вопрос на собственной базе, и `make test` уже запускает его |

!!! warning "Одна дыра, которую не закроет никакая команда"

    У задачи `test` в CI рядом есть Postgres, поэтому `tests/integration/` там
    выполняется; локально эти тесты пропускаются, когда на 5432 никто не отвечает.
    `make check` говорит об этом в конце, когда так выходит, — запустите
    `make docker-db` заранее, если изменение хоть как-то связано с базой.

### Что означает красный `make audit` { #what-a-red-make-audit-means }

`make audit` выгружает то, во что разворачивается файл блокировки, — а это то, что
устанавливает экземпляр, — и передаёт в `pip-audit`, который по очереди спрашивает
ленту уязвимостей о каждом из 254 зафиксированных пакетов. Сам по себе `pip-audit`
не может сказать, какая из двух очень разных бед случилась: он выходит с кодом 1 и
когда нашёл предупреждение, и когда умер на `ReadTimeout`, пытаясь его получить, — а
`Security Scan` — обязательная проверка состояния, так что один медленный ответ из
254 блокирует слияние, читаясь ровно как настоящее замечание, пока кто-нибудь не
откроет журнал
([#855](https://github.com/vstorm-co/agenticos/issues/855)).

`scripts/audit_dependencies.py` стоит между ними и **завершает каждый запуск одной
строкой**:

```
AUDIT: CLEAN — no known advisories against 254 locked dependencies
AUDIT: VULNERABLE — 6 known advisories in 1 of 254 locked dependencies
AUDIT: NETWORK — unreachable (ReadTimeout) after 3 attempts; no audit was performed
AUDIT: FAILED — pip-audit reached no verdict in 3 attempts and did not say why; no audit was performed
```

| Состояние | Значит | Что делать |
|---|---|---|
| `CLEAN` | Каждая зафиксированная зависимость проверена, ни у одной нет известного предупреждения | Ничего |
| `VULNERABLE` | У зафиксированной зависимости есть известное предупреждение. Идентификаторы, исправленные версии и псевдонимы CVE печатаются над вердиктом | Обновить её |
| `NETWORK` | Проверки не было, и причиной явно была сеть | Запустить снова |
| `FAILED` | Проверки не было, и причина не распознана. Собственный вывод pip-audit — в stderr | Прочитать этот вывод |

**Строка, а не код выхода, потому что make не может его передать.** GNU Make
превращает любой неудачный рецепт в собственный код выхода 2, поэтому `make audit`
возвращает 2 и для `VULNERABLE`, и для `NETWORK`, и никакая форма цели этого не
меняет. Всё, что читает результат через этот интерфейс, — включая задачу
`Security Scan`, — читает строку: `make audit | tail -1` или
`make audit 2>&1 | grep '^AUDIT:'`. Внутри задачи GitHub та же строка дописывается в
`$GITHUB_STEP_SUMMARY`, так что страница сводки запуска говорит, какое это было
состояние, без того чтобы кто-то открывал журнал.

При прямом вызове `scripts/audit_dependencies.py` код выхода действительно есть: `0`
для `CLEAN`, `1` для `VULNERABLE`, `75` (`EX_TEMPFAIL`) одинаково для `NETWORK` и
`FAILED` — проверка, которой не было, никогда не считается зелёной, потому что
непроверенный набор зависимостей, названный чистым, — тот же дефект с другой
стороны.

**Каждый неполный запуск повторяется, что бы он ни сказал.**

`AUDIT_ATTEMPTS` (по умолчанию 3) с паузами 5 и 10 секунд и `AUDIT_TIMEOUT` (по
умолчанию 30 с) как тайм-аут сокета на запрос, поднятый с 15 секунд у самого
pip-audit.

Совпадение с фразой в выводе решает только, будет вердикт `NETWORK` или `FAILED`,
и никогда — повторять ли попытку. Две ошибки не симметричны: повтор
детерминированного сбоя стоит секунд и даёт тот же ответ, а вот *отсутствие*
повтора при временном сбое — это ложный красный на обязательной проверке, который
всё это и призвано предотвратить.

Так что сбой, изложенный словами, которых нет в списке, всё равно получает свои
повторы. Просто имя у него расплывчатее.

В списке две группы формулировок, потому что к сети обращаются две программы:
`uv`, забирающий сам `pip-audit` на холодном кэше инструментов, а затем `pip-audit`,
забирающий предупреждения.

### Фоновые задачи { #background-jobs }

Воркер работает одним контейнером в стеке разработки и запускается с `make dev`:

- **`worker`** — `python -m app.worker`, из образа бэкенда. Он забирает задачи из
  таблицы `background_jobs`, запускает пул индексации в дочерних процессах и
  запускает расписания экземпляра.

Виды задач объявлены в `app/worker/jobs.py`, их обработчики живут в
`app/worker/tasks/` и привязаны в `app/worker/handlers.py`, а расписания — в
`app/worker/schedules.py`. Наблюдайте, повторяйте, отменяйте и возобновляйте на
странице **Администрирование → Фоновые задачи** (Admin → Background jobs) консоли,
как владелец экземпляра.

## CLI проекта { #project-cli }

Все команды CLI проекта вызываются так:

```bash
cd backend

```

### Команды сервера { #server-commands }

```bash
uv run agenticos server run              # Start dev server
uv run agenticos server run --reload     # With hot reload
uv run agenticos server run --port 9000  # Custom port
uv run agenticos server routes           # Show all registered routes
```

`--reload` запускает перезагрузчик uvicorn под нашим собственным супервизором
(`backend/cli/reload_supervisor.py`), потому что у uvicorn он лишь следит за файлами
и больше ничего: когда ядро завершает воркер — а реалистичный сценарий — это
принудительное завершение из-за нехватки памяти, — перезагрузчик не убирает его и не
заменяет, так что продолжает следить, пока ни один порт не слушается. Под
супервизором воркер, завершённый сигналом, заменяется примерно за пять секунд, а
тот, что завершился сам, всё равно ждёт правки, которая его исправит, — для этого
`--reload` и нужен.

Он также заменяет воркер, который **заклинило** — он жив, но его цикл событий
перестал крутиться; кода выхода у этого нет, поэтому для любого другого пути
восстановления он выглядит здоровым.

Воркер сообщает о своём цикле через хук `callback_notify` uvicorn раз в секунду, и
воркер, молчащий пятнадцать секунд на двух опросах подряд, завершается и
заменяется. Около двадцати пяти секунд от взаимной блокировки до обслуживания.

Два опроса, а не один, потому что `docker pause` и ноутбук, проснувшийся от сна,
останавливают и супервизор, и воркер, и первый опрос после этого читает устаревший
сигнал, который ничего не говорит.

Это **проверка «жив ли процесс», а не проверка готовности**, и намеренно: сигнал —
обратный вызов таймера, а не запрос, так что медленная база не может заставить
здоровый сервер выглядеть заклинившим.

| | |
|---|---|
| `EVENT_LOOP_WEDGED_AFTER` | Секунды молчания до замены воркера. По умолчанию `15`; `0` или меньше отключает проверку |

Отключайте её при отладке. Точка останова блокирует цикл событий, и никакой опрос
не отличит это от взаимной блокировки, так что воркер, застрявший на точке
останова, будет заменён, пока вы отлаживаете.

Ту же переменную читает сам воркер: он следит за своим циклом событий и завершает
собственный процесс — это покрывает стеки разработки и боевой, где нет супервизора,
читающего сигнал снаружи. Одно число, так что отключение проверки ради точки
останова отключает обе проверки.
[Настройка](configuration.md#a-worker-whose-event-loop-has-stopped-turning)
показывает всю картину.

`server run` также выбирает реализацию `websockets-sansio` в обоих режимах. `auto` у
uvicorn выбирает устаревшую, которая проваливает рукопожатие с websockets >=14 с
HTTP 500, — а чат на странице «Обзор» работает через WebSocket.


### Команды базы данных { #database-commands }

```bash
uv run agenticos db init                  # Run all migrations
uv run agenticos db migrate -m "message"  # Create new migration
uv run agenticos db upgrade               # Apply pending migrations
uv run agenticos db upgrade --revision e3f  # Upgrade to specific revision
uv run agenticos db downgrade             # Rollback last migration
uv run agenticos db downgrade --revision base  # Rollback to start
uv run agenticos db current               # Show current revision
uv run agenticos db history               # Show migration history
```

### Команды пользователей { #user-commands }

```bash
# Создать пользователя (интерактивный запрос почты и пароля)
uv run agenticos user create

# Создать пользователя без интерактивных запросов
uv run agenticos user create --email user@example.com --password secret

# Заодно выдать app-admin — администратора платформы, который управляет всем
# экземпляром
uv run agenticos user create --email admin@example.com --password secret --superuser

# То же самое, короткой командой
uv run agenticos user create-admin --email admin@example.com --password secret

# Список всех пользователей
uv run agenticos user list
```

**Флага `--role` и команды `set-role` нет.** Полномочия пользователя внутри
организации — это строка членства плюс [каталог
разрешений](reference/permissions.md), которые выдаются на странице
**Пользователи и роли** (Users & Roles) в интерфейсе; столбец `users.role` удалили
ещё до того, как цепочку миграций свели к одной базовой. Единственная привилегия,
которую может выдать эта группа команд, — глобальная, и это `--superuser`. Чтобы
выдать или отозвать её позже:

```bash
uv run agenticos cmd create-app-admin user@example.com
uv run agenticos cmd create-app-admin user@example.com --revoke
```

### Настройка и диагностика { #setup-and-diagnostics }

```bash
# Организация, владелец, профиль модели и опубликованный агент. Идемпотентно.
# --org называет организацию, которую создаёт bootstrap. У существующей
# учётной записи появится организация с этим именем, даже если она работает в
# другой; её личную организацию это не трогает. Без --org берётся та, в которую
# попадает владелец. Организация по умолчанию всё равно открывается первой при
# входе.
uv run agenticos cmd bootstrap \
    --email owner@example.com --password secret \
    --org "Acme" --provider anthropic --api-key sk-ant-...

# Без ключа агент создаётся, но запуститься не может
uv run agenticos cmd bootstrap --org "Acme"

# Может ли этот экземпляр вообще запустить агента? База данных, хранилище
# секретов, пригодная модель и каждое зарегистрированное подключение песочницы —
# проверяются по одному, вместе с учётными данными, потому что `/healthz`
# неаутентифицирован и отвечает и за сервис с неверным токеном. Затем — идёт ли
# фоновая работа: если от воркера ничего не слышно две минуты, минутное
# расписание не срабатывало пять интервалов подряд или какой-то вид задач
# приостановлен своим предохранителем, проверка не проходит.
uv run agenticos cmd doctor

# То же самое плюс второй лист: по строке на каждую меру профиля безопасности, с
# названием настройки, которая её выполняет, или той, что не выполняет. `--`
# помечает меру, которая действительно лежит на операторе, — шифрование томов:
# её называют, а не тихо засчитывают, и команда из-за неё не падает. Завершается
# с ненулевым кодом при любой невыполненной мере, так что на это можно повесить
# CI клиента. Свидетельство, а не сертификация: профиль HIPAA отвечает на
# §164.312 и ни на что больше.
uv run agenticos cmd doctor --profile hipaa

# Найти опубликованных агентов, которые выдают навык, недоступный их
# публикующему. Проверка skill_ids при публикации закрывает только новые
# публикации; это её офлайн-половина: она называет версии, замороженные раньше и
# всё ещё отдающие приватный навык запуску. Она обходит каждую версию, которую
# может загрузить запуск, а не только текущую: закреплённую версию каждого
# именованного окружения, каждую версию, которую перезагружает незавершённый
# запуск (выполняется или ждёт согласования), и каждого агента-исполнителя,
# закреплённого в спецификации, — последнего лишь настолько глубоко, насколько
# max_depth позволяет дойти запуску, поэтому правнук за потолком не помечается.
# Только отчёт: спецификация выгружается в git клиента, так что отвязывать —
# решение человека. Завершается с ненулевым кодом, когда что-то находит, чтобы
# cron мог на это опереться.
uv run agenticos cmd audit-skill-bindings

# Пересчитать цепочку хешей, доказывающую неизменность журнала аудита
# администратора платформы, и сообщить о любом разрыве. Каждая запись ссылается
# на хеш предыдущей, поэтому правка, перестановка, вставка или удаление строки из
# середины меняет все хеши после неё; контрольная точка по каждой организации
# ловит самые новые записи или выпавшую целиком цепочку, чего обход хешей не
# видит. Без --org проверяются все цепочки, включая цепочку всего экземпляра.
# Обнаружение, а не предотвращение: суперпользователь Postgres может снять защиту
# контрольной точки и удалить и записи, и точку, — так что чистый запуск
# остаётся свидетельством, а не доказательством. Завершается с ненулевым кодом,
# когда падает любая цепочка, чтобы на это мог опереться cron.
uv run agenticos cmd audit-verify
uv run agenticos cmd audit-verify --org <org-id>

# Вывести конфигурацию, которую запрашивает проверка защиты данных этого
# экземпляра: настройки, решающие, что уходит наружу; каждого провайдера и
# эндпоинт, до которых может дотянуться агент; учётные данные по
# назначению; коллекции и того, кто строит для них эмбеддинги; серверы в вашей
# сети; MCP-серверы, источники синхронизации и ботов каналов; где трассируются
# запуски и сколько содержимого несёт спан; какую часть каждого хранилища затронул
# бы срок хранения; и файлы в MEDIA_DIR, на которые больше не указывает ни
# одна строка. Только конфигурация и счётчики — ни текста сообщений, ни
# документов, ни значения секрета и ни намёка на него, поэтому вывод можно
# приложить как есть. --older-than — рассматриваемый срок хранения в днях.
uv run agenticos cmd data-protection-report
uv run agenticos cmd data-protection-report --older-than 90

# Переобернуть каждый сохранённый секрет под текущий мастер-ключ — та поэтапная
# ротация, которую описывает docs/secrets.md. Старый и новый ключ сначала
# задаются рядом в VAULT_MASTER_KEYS; --dry-run полностью распаковывает каждый
# сохранённый конверт, ничего не записывая, так что сбои всплывают до того, как
# что-то сдвинется. Завершается с ненулевым кодом, если хоть одна строка не
# смогла переехать, чтобы скрипт не выбросил старый ключ при незавершённой
# ротации.
uv run agenticos cmd vault-rotate --dry-run
uv run agenticos cmd vault-rotate

# Установить встроенные навыки (refund-policy, code-review, incident-report,
# artifact-pages) и обновить до версии этого выпуска те копии, которые никто не
# правил. Изменённая копия остаётся нетронутой без --replace; --dry-run печатает
# план по каждому навыку.
uv run agenticos cmd seed-skills
uv run agenticos cmd seed-skills --org <org-id> --dry-run
uv run agenticos cmd seed-skills --replace

# Примеры данных для разработки
uv run agenticos cmd seed --count 10 --clear
```

### Приглашение команды и как достать ссылки { #inviting-a-team-and-getting-the-links-out }

```bash
# Приглашения сразу на несколько адресов, выводятся как `address  link`.
uv run agenticos cmd invite-members <org-id> ada@example.com grace@example.com

# Одна роль на всю пачку; `member`, если не указать иное.
uv run agenticos cmd invite-members <org-id> ada@example.com --role admin

# Под чьими полномочиями они создаются. По умолчанию — первый владелец
# организации, а проверке по роли нужна роль, с которой можно сверить
# предлагаемую.
uv run agenticos cmd invite-members <org-id> ada@example.com --as owner@example.com
```

Так сделано из-за двух половин приглашения. **На экземпляре без `SMTP_*` письма
не отправляются**, а токен принятия возвращается один раз и не сохраняется
нигде, откуда его можно прочитать снова, — поэтому ссылку приходится печатать,
иначе её никак не передать. Команда говорит, что из двух произошло, а один
отклонённый адрес (уже участник, уже приглашён) попадает в отчёт и пропускается,
не срывая остальные.

Она идёт через тот же сервис, что и интерфейс, поэтому потолок роли, лимит мест
и проверки на дубликаты действуют точно так же, как для человека, нажимающего
кнопку, — включая то, что никто не выдаёт роль, которую его собственная строго
не превосходит.

`make platform-bootstrap BOOTSTRAP_API_KEY=sk-...` оборачивает `bootstrap`
нужными миграциями. Когда что-то работает локально, но не на чистом окружении,
сначала запустите `doctor` — это быстрее, чем читать журналы.

### Как поднять экземпляр { #getting-a-deployment-up }

```bash
# Docker, один скачанный compose-файл, четыре вопроса — и работающий агент.
curl -fsSL https://raw.githubusercontent.com/vstorm-co/agenticos/main/scripts/quickstart.sh | bash
# Только сообщить, чего не хватает этой машине.
./scripts/quickstart.sh --check
# Напечатать каждую команду, которую он выполнил бы, и не выполнить ни одной.
./scripts/quickstart.sh --dry-run
# Без вопросов.
./scripts/quickstart.sh --yes --provider anthropic --api-key sk-ant-... --org Acme
```

Это обёртка вокруг `docker compose up` на опубликованных образах (`make dev` в
клоне), `agenticos cmd bootstrap` и `agenticos cmd mcp-registry-sync`: всё, что он
делает, доступно и вручную, а нужен ему один Docker.

### Зеркало реестра MCP { #the-mcp-registry-mirror }

```bash
# Заполнить или обновить `mcp_registry_servers` из встроенного снимка.
uv run agenticos cmd mcp-registry-sync

# Или из живого реестра: именно так содержимое зеркала и переносится между
# экземплярами.
uv run agenticos cmd mcp-registry-sync --fetch

# Сохранить строки, которые реестр больше не перечисляет, вместо их очистки.
uv run agenticos cmd mcp-registry-sync --no-prune
```

**`make platform-bootstrap` уже загружает зеркало** из встроенного снимка, так что
при первой настройке ничего из этого не нужно. Загрузка пропускается, если в
таблице уже есть строки: повторный запуск bootstrap не должен тратить секунды на
перезапись пяти тысяч неизменившихся строк, а обновление зеркала — работа этой
команды, а не bootstrap.

Запустите её вручную на экземпляре, который старше этой таблицы, или чтобы
подхватить более новый снимок. Синхронизация идемпотентна: второй запуск
проставляет `synced_at` и больше ничего не меняет, если не изменился сам реестр.

Именно очистка убирает сервер, исключённый из реестра. Без неё зеркало только
растёт, а мёртвый эндпоинт предлагается вечно, поэтому очистка включена по
умолчанию и опирается на `synced_at`, а не на сравнение пяти тысяч
идентификаторов.

### Боты каналов { #channel-bots }

Что поддерживает каждая платформа, см. в разделе [Каналы](channels.md).

Каждая команда здесь действует для **одной организации**, потому что бот канала
принадлежит одной. `--org <id>` называет её, а экземпляру ровно с одной
организацией флаг не нужен. Экземпляр с несколькими отказывается выбирать и
перечисляет их с идентификаторами: догадка задела бы чужих ботов.

```bash
# Зарегистрировать бота
uv run agenticos cmd channel-add-bot \
    --platform telegram --name "Support" --token <token> --mode jwt_linked

# Mattermost размещается на собственной инфраструктуре, поэтому его бот несёт
# адрес собственного сервера. --webhook-secret — токен, который Mattermost
# показывает при создании исходящего вебхука; опустите его, чтобы использовать
# поток событий и ничего не открывать наружу.
uv run agenticos cmd channel-add-bot \
    --platform mattermost --name "Support" --token <token> \
    --api-base-url https://mattermost.acme.internal \
    --webhook-secret <token-from-mattermost>

uv run agenticos cmd channel-list-bots
uv run agenticos cmd channel-list-bots --platform telegram

# Отправить через него тестовое сообщение — самое дешёвое доказательство, что
# токен и адрес верны. --chat-id — id чата Telegram или канала Mattermost.
uv run agenticos cmd channel-test-message --bot-id <uuid> --chat-id <chat> --text "ping"

# Доставка через вебхук или удаление вебхука с возвратом к опросу. Telegram —
# единственная платформа с API для этого; для Slack и Mattermost команда
# печатает URL, который нужно вставить в их собственных настройках.
uv run agenticos cmd channel-webhook-register --bot-id <uuid>
uv run agenticos cmd channel-webhook-delete --bot-id <uuid>
```

Регистрация бота из CLI — единственный способ для экземпляра, к которому не
направлен браузер; сервер Mattermost за VPN обычно именно таков.

Режимы доступа — `open`, `whitelist`, `jwt_linked` и `group_only`; `jwt_linked`
отвечает только учётным записям чата, связанным с участником, — в канале так же,
как в личном сообщении. Упоминание выполняется от имени *отправителя*, а не
бота, а несвязанная личность отклоняется, а не запускается без роли — см.
[Каналы](channels.md#what-every-channel-shares).

### Команды RAG { #rag-commands }

Все команды RAG — собственные команды, которые вызываются через `cmd`:

#### Индексация документов { #document-ingestion }

Коллекция по умолчанию — `default`. Имя, для которого модели уже объявляют
векторную таблицу, — например `documents`, чья форма с префиксом и есть таблица
учёта индексации, — отклоняется с кодом 400, а не считается её псевдонимом; см.
[Обработка файлов](file-processing.md#vector-storage).

```bash
# Проиндексировать один файл в коллекцию по умолчанию
uv run agenticos cmd rag-ingest ./docs/guide.pdf

# Проиндексировать каталог
uv run agenticos cmd rag-ingest ./docs/

# Проиндексировать рекурсивно в указанную коллекцию
uv run agenticos cmd rag-ingest ./docs/ --collection knowledge --recursive

# Проиндексировать в режиме синхронизации
uv run agenticos cmd rag-ingest ./docs/ --sync-mode new_only
uv run agenticos cmd rag-ingest ./docs/ --sync-mode update_only

# Не заменять существующие документы
uv run agenticos cmd rag-ingest ./docs/ --no-replace
```

#### Поиск { #search }

```bash
# Поиск в коллекции по умолчанию
uv run agenticos cmd rag-search "what is fastapi"

# Поиск в указанной коллекции
uv run agenticos cmd rag-search "deployment guide" --collection docs

# Больше результатов
uv run agenticos cmd rag-search "deployment" --top-k 10
```

#### Управление коллекциями { #collection-management }

```bash
# Список всех коллекций со статистикой
uv run agenticos cmd rag-collections

# Общая статистика системы RAG
uv run agenticos cmd rag-stats

# Удалить коллекцию (с подтверждением)
uv run agenticos cmd rag-drop my_collection

# Удалить без подтверждения
uv run agenticos cmd rag-drop my_collection --yes

# Очистить одну из нескольких баз знаний с одинаковым именем
uv run agenticos cmd rag-drop docs --knowledge-base <knowledge-base-id> --yes
```

`rag-drop` очищает базу знаний, которая держит это имя, как и удаление в
консоли, а воркер убирает векторную таблицу и сохранённые файлы после того, как
команда зафиксирует транзакцию. Имя, которое держат несколько баз знаний —
возможно, в разных организациях, — отклоняется вместе с их идентификаторами,
пока `--knowledge-base` не назовёт одну; тогда таблица остаётся для остальных. В
отличие от удаления в консоли, она убирает и таблицу последнего держателя, если в
ней лежат фрагменты, которыми не владеет ни одна база.

#### Синхронизация с Google Drive { #google-drive-sync }

```bash
# Синхронизировать из корня Google Drive
uv run agenticos cmd rag-sync-gdrive --collection docs

# Синхронизировать из указанной папки
uv run agenticos cmd rag-sync-gdrive --collection docs --folder-id abc123
```

#### Синхронизация с S3/MinIO { #s3minio-sync }

```bash
# Синхронизировать из корня бакета S3
uv run agenticos cmd rag-sync-s3 --collection docs

# Синхронизировать из указанного префикса (папки)
uv run agenticos cmd rag-sync-s3 --collection docs --prefix documents/

# Синхронизировать из указанного бакета
uv run agenticos cmd rag-sync-s3 --collection docs --bucket my-bucket
```


#### Управление источниками синхронизации { #sync-source-management }

```bash
# Список настроенных источников синхронизации
uv run agenticos cmd rag-sources

# Добавить источник синхронизации. `--org` обязателен, а коллекция должна уже
# принадлежать этой организации: синхронизация *пишет в* названную коллекцию,
# поэтому источник, указывающий на имя, которым никто не владеет, упадёт позже в
# воркере, а указывающий на чужую организацию — это инъекция, а не чтение.
# Источник записывает, какой организации принадлежит база знаний; если это имя
# держат несколько её баз, назовите нужную через `--knowledge-base <id>`.
uv run agenticos cmd rag-source-add \
    --name "My Drive" \
    --type gdrive \
    --org 0c8f2b1e-... \
    --collection docs \
    --config '{"folder_id": "abc123"}' \
    --sync-mode new_only \
    --schedule 60

# Удалить источник синхронизации
uv run agenticos cmd rag-source-remove <source-id>
uv run agenticos cmd rag-source-remove <source-id> --yes  # Skip confirmation

# Запустить синхронизацию для указанного источника
uv run agenticos cmd rag-source-sync <source-id>

# Запустить синхронизацию для всех активных источников
uv run agenticos cmd rag-source-sync --all
```

`rag-source-sync` **ждёт запущенные ею синхронизации** — до часа — и сообщает об
этом, пока ждёт. Сама синхронизация идёт в фоновой задаче, а процесс команды
завершается, когда возвращается её корутина, — поэтому команда, которая только
запускала и выходила, отменяла работу, о запуске которой только что сообщила.
Через API эта задача принадлежит долгоживущему воркеру, и ждать её никому не
нужно.

## Добавление собственных команд { #adding-custom-commands }

Команды обнаруживаются автоматически в `app/commands/`. Создайте новый файл:

```python
# app/commands/my_command.py
import click
from app.commands import command, success, error

@command("my-command", help="Description of what this does")
@click.option("--name", "-n", required=True, help="Name parameter")
def my_command(name: str):
    """Your command logic here."""
    success(f"Done: {name}")
```

Запустите команду:

```bash
uv run agenticos cmd my-command --name test
```

Подробнее — в `docs/adding_features.md`.

## Обновление Архитектора { #refreshing-the-architect }

После обновления просмотрите установленные инструкции Архитектора и его
руководство по AgenticOS, затем обновите копии, которые никто не правил:

```bash
uv run agenticos cmd refresh-assistant --dry-run
uv run agenticos cmd refresh-assistant --org <org-id>
uv run agenticos cmd refresh-assistant --org <org-id> --replace-edited
```

Опустите `--org`, чтобы обработать каждую организацию. Отчёт различает
`current`, `update`, `edited` и `untracked`; `--dry-run` ничего не пишет. Копии
`edited` и `untracked` пропускаются, если `--replace-edited` явно не заменит
изменения организации.

Изменения инструкций создают и публикуют новую версию агента, сохраняя
опубликованную историю, модель, бюджет, возможности, навыки и настройки
помощника. Если другие поля черновика отличаются от опубликованной версии, всё
обновление блокируется, пока эти изменения не опубликуют или не отбросят; флаг
замены эту проверку не обходит. Помощник, который никогда не публиковался,
получает обновлённые инструкции черновика и всё ещё нуждается в модели и
публикации в Конструкторе. Отсутствующие и архивные помощники пропускаются. Об
отсутствующем или отсоединённом руководстве сообщается без изменения привязок
навыков.

Руководство — обычный общий навык: обновление его содержимого и ресурсов
увеличивает его версию и влияет на каждого агента, использующего эту копию.
Изменённые руководства защищены так же, как изменённые инструкции.
Существующие копии неизвестного происхождения остаются вне учёта; обновление
распознаёт только точные инструкции, которые AgenticOS поставлял раньше.
Обновление экземпляра не перезаписывает установленного Архитектора
автоматически: запустите эту команду, чтобы принять новый шаблон.

Массовые запуски сообщают об организациях без владельца как о пропущенных и
продолжают с остальными. Запуск с указанным `--org` явно завершается ошибкой,
если у этой организации нет владельца.

# Тестирование { #testing }

Четыре слоя, один механизм выполнения и порог покрытия, который роняет сборку ниже
100% на слое платформы.

Короткая версия того, что запускать: тесты, покрывающие изменение, пока вы пишете,
и полные наборы — один раз перед отправкой.

## Запуск тестов { #running-tests }

!!! tip "Пока пишете, запускайте то, что покрывает изменение; полный набор — это проверка перед отправкой"

    Файл отвечает примерно за секунду там, где полный набор занимает полторы
    минуты, и говорит об изменении то же самое.

```bash
cd backend

uv run pytest tests/test_capability_registry.py -q         # one file
uv run pytest tests/test_capability_registry.py -k drift   # one behaviour
uv run pytest tests/api/test_workspace_routes.py -x -v     # stop at the first failure
uv run pytest tests/integration -v --no-cov                # the ones needing a database
```

Эти команды намеренно остаются **последовательными**: породить воркер-процессы
ради одного файла дороже, чем стоит сам файл. Цели для всего набора — `make test`,
`make test-fast`, `make test-integration`, `make test-cov` — запускаются в нескольких
воркерах (`pytest -n auto --maxprocesses 4`), что примерно вдвое сокращает
интеграционный набор, ограниченный вводом-выводом; `pytest-cov` объединяет данные
отдельных воркеров, поэтому порог в 100% не меняется. Потолок — четыре, потому что
набор модульных тестов упирается в импорт (каждый воркер импортирует приложение
один раз) и дальше ничего не выигрывает, а `auto` без потолка на многоядерном
ноутбуке *медленнее* последовательного запуска, и весь этот проигрыш — запуск
воркеров (#520).

!!! warning "Каждый запуск перемешан, и тест, прошедший вчера, мог полагаться на порядок"

    `pytest-randomly` печатает seed в заголовке
    (`Using --randomly-seed=1697040112`). Повторите этот seed **последовательно**,
    чтобы вернуть тот же порядок, — `-n auto` не определяет, какой воркер что
    выполняет.

Тест, зависящий от порядка, — тот, что проходит только потому, что что-то до него
оставило состояние, — это классическое «зелено у меня на ноутбуке, красно в CI», а
набор, который всегда идёт в порядке сбора, никогда не задаёт этого вопроса. CI
задаёт его в новом порядке при каждом запуске.

```bash
uv run pytest tests/ -q --randomly-seed=1697040112   # that order again, serially
uv run pytest tests/ -q -p no:randomly               # collection order, while bisecting
```

Seed выбирается один раз контроллером и передаётся каждому воркеру xdist, поэтому
`-n auto` собирает один порядок, а не четыре. Но он не определяет, какой воркер что
выполняет: `make test` оставляет xdist на значении по умолчанию `--dist load`,
которое отдаёт каждый тест тому воркеру, что освободился. Так что сбой, зависевший
от того, что оказалось в одном воркере (например, `InterfaceError`, найденный в #571), возвращается повтором seed *последовательно*, как выше, а не повторным
запуском `make test`. Плагин к тому же одинаково пересоздаёт `random` перед каждым
тестом, поэтому всё, что берёт оттуда уникальность, уникально внутри теста и
повторяется между ними.

До #571 плагин был описан в документации, но не установлен, `-p no:randomly` молча
ничего не делал, и это утверждение никто ни разу не проверял.

Один раз, перед отправкой, — `make check` запускает всё это, в таком порядке:

```bash
make lint               # ruff, ruff format, ty, vulture, deptry, eslint, prettier, tsc, the guards
make test               # the suite plus the 100% gate on the platform layer
make db-check           # alembic check — a model change with no migration fails here
make test-frontend-cov  # the frontend suite plus its own gate
make build-frontend     # next build — the route tree, which tsc and vitest do not see
make docs-build         # mkdocs --strict — a dead link is a failure
make audit              # the locked dependency set against the advisory database
```

CI выполняет независимые проверки параллельно. Рабочий процесс GitHub Actions
вызывает те же цели Make, что и локальные проверки; `tests/test_ci_parity.py`
следит за их паритетом. Намеренные исключения — в разделе
[Команды](commands.md#before-a-pull-request).

!!! info "CI может запускать меньше задач, чем `check`, и это не расхождение"

    `test`, `test-frontend` и `e2e` пропускаются в пул-реквесте, изменённые пути
    которого не могут на них повлиять, а обязательная проверка со статусом
    `skipped` всё равно пропускает слияние. Локально эквивалента нет: `check`
    запускает всё.

Изменение только в документации не запускает ни одну из трёх; изменение только в
бэкенде не запускает набор фронтенда. Решает `scripts/ci_changed_scope.py`, он
склоняется в сторону запуска, а правило — в разделе
[Ветки](branching.md#a-required-check-may-legitimately-report-skipped).

!!! danger "Два способа отправить непроверенное"

    `make test-fast` пропускает покрытие, поэтому он не годится как последнее
    слово перед отправкой: порог — это большая часть того, ради чего нужны эти
    команды. А `pytest` без `uv run` подхватывает какой угодно интерпретатор из
    `PATH`, а не закреплённый 3.12.

## Структура тестов { #test-structure }

Четыре слоя, и принадлежность теста к одному из них решает то, что ему нужно, а
не то, о чём он.

```
backend/tests/
├── conftest.py          # the shared fixtures, and the test database's name
├── test_*.py            # unit: one module, its dependencies mocked at the repository boundary
├── api/                 # the app driven through `client`, grouped by the question asked
└── integration/
    └── conftest.py      # creates a database of its own, and drops it afterwards
```

`tests/api/` сгруппирован по **тому, какой вопрос задаётся**, а не по модулю
маршрута: одни файлы берут один эндпоинт (`test_admin_ratings_window.py`), а
`test_platform_routes.py` разом обходит целое семейство — поэтому у `agents.py` нет
своего файла. Ищите вопрос, прежде чем искать путь.

| Слой | Где | Для чего |
|---|---|---|
| Модульные | `tests/test_*.py` | Один модуль. Репозитории замокированы; сервис под тестом — никогда |
| API | `tests/api/`, а некоторые — в корне | Маршрут: его проверка разрешений, его код состояния, что доходит до сервиса |
| Интеграционные | `tests/integration/` | То, на что отвечает только база: `ORDER BY`, каскад, уникальное ограничение, запрос, который действительно привязан к организации |
| E2E | `frontend/e2e/` | Пути через всю систему — см. [Тесты фронтенда](#frontend-tests) |

Каталога `tests/unit/` нет: модульный тест — это `test_*.py` в корне `tests/`. Слой
— это **то, что нужно тесту, а не то, где он лежит**, и в корне немало тестов,
которые запускают приложение через собственный `AsyncClient`, —
`test_rag_document_listing.py`, `test_oauth_signin_exchange.py`,
`test_security_headers.py`. Если искать существующее покрытие маршрутов только в
`tests/api/`, вы их пропустите.

**Одно исключение, и оно в корне, а не в `integration/`.** `tests/test_migrations.py`
проходит всю цепочку Alembic — вперёд и обратно — на настоящей базе, которую сам
создаёт и удаляет под собственным именем: `downgrade base` удаляет все таблицы, а
унаследованный `POSTGRES_DB` однажды опустошил рабочую базу разработчика. Его
запускает обычный `pytest tests/`. Он не в `integration/`, потому что вовсе не
использует фикстуру `db` того пакета: он запускает `alembic` в подпроцессах.

## Асинхронные тесты работают на anyio, а не на pytest-asyncio { #async-anyio-not-pytest-asyncio }

```python
import pytest

pytestmark = pytest.mark.anyio   # at the top of the module
```

или `@pytest.mark.anyio` на тесте, как делает `tests/api/test_users.py` там, где
асинхронна только часть файла. Годится и то и другое; форма на уровне модуля —
привычка этого проекта, потому что большинство файлов асинхронны целиком.

!!! warning "`@pytest.mark.asyncio` здесь не работает, и нет `asyncio_mode`, чтобы его включить"

    Набор работает на **anyio**. Непомеченный `async def` падает уже при сборе с
    сообщением о фреймворке, а не о тесте, так что на входе это читается как
    сломанное окружение.

Непомеченный `async def` — не молчаливый проход: pytest 9 роняет его при сборе с
*"async def functions are not natively supported"* и перечисляет плагины, которые
это исправили бы. Фикстура `anyio_backend` закрепляет `asyncio`, потому что именно
его запускает uvicorn.

## Ключевые фикстуры (`tests/conftest.py`) { #key-fixtures-testsconftestpy }

Пять. Ни одна из них не `test_user` и не клиент с уже выполненным входом, и в
этом весь смысл: аутентифицированный вызывающий — это переопределение зависимости,
поэтому тест сам говорит, какие полномочия он задействует, а не наследует их.
`tests/api/test_users.py` собирает собственный `auth_client` ровно из этих
переопределений — локальная фикстура для файла, которому она нужна, а не общая,
которую наследует каждый файл.

| Фикстура | |
|---|---|
| `anyio_backend` | Закрепляет `asyncio`, и никто её не называет — её запрашивает anyio |
| `client` | `httpx.AsyncClient` поверх `ASGITransport(app=app)` — **не** `TestClient` из Starlette. Переопределяет `get_db_session` и `get_redis`, а после себя очищает `app.dependency_overrides` |
| `mock_db_session` | `AsyncMock`. Его `info` — настоящий словарь, потому что именно там `spawn_after_commit` ставит работу в очередь |
| `mock_redis` | `MagicMock(spec=RedisClient)` с заглушёнными асинхронными методами |
| `api_key_headers` | Заголовок межсервисного вызова, для маршрута за `ValidAPIKey` |

`tests/integration/conftest.py` добавляет те, что работают с базой. Пакет
отклоняет любую базу, в имени которой нет ни `test`, ни `ci`, и между тестами
опустошает каждую таблицу. **Он пропускает себя, когда недоступна ни одна база,
только вне CI**: при заданном `CI` он вместо этого падает, потому что пропуск и сервис
Postgres, который не запустился, выглядят в выводе pytest одинаково, а на раннере
допустим только один из них.

| Фикстура | |
|---|---|
| `db` | Настоящая `AsyncSession` — её берёт почти каждый интеграционный тест |
| `engine` | `AsyncEngine` за ней, для теста, которому нужна сессия, которой `db` быть не может: *больше одной* (гонка, параллельная запись, две транзакции, которым нужно чередоваться, где одна `AsyncSession`, разделённая между ними, — не второе соединение, а испорченное), — или та, которую код под тестом создаёт себе сам, — так тесты RAG передают `PgVectorStore` собственный `async_sessionmaker`. Её берут восемнадцать файлов |
| `database_url`, `schema_url` | Живут на уровне сеанса и обеспечивают безопасность двух предыдущих: называют одноразовую базу и один раз создают её схему |

## Как писать тесты { #writing-tests }

Называйте поведение, а не функцию, чтобы сбой говорил, что сломалось:
`test_a_grant_widens_access_without_promoting_the_member`, а не `test_resolve`.

### Тест сервиса { #a-service-test }

```python
import pytest
from unittest.mock import AsyncMock
from uuid import uuid4

from app.core.exceptions import NotFoundError
from app.repositories import user as user_repo
from app.services.user import UserService

pytestmark = pytest.mark.anyio


async def test_an_unknown_user_is_a_refusal_rather_than_a_none(monkeypatch, mock_db_session):
    monkeypatch.setattr(user_repo, "get_by_id", AsyncMock(return_value=None))
    service = UserService(mock_db_session)

    with pytest.raises(NotFoundError):
        await service.get_by_id(uuid4())
```

Репозиторий замокирован, а сервис — нет. Тест, который мокает то, что он проверяет,
проходит и тогда, когда реализацию удалили.

### Тест API { #an-api-test }

Вызывающий — это переопределение, и именно поэтому отказ можно проверить:

```python
import pytest
from httpx import AsyncClient
from uuid import uuid4

from app.api import deps
from app.core.permissions import AuthContext, OrgRoleName
from app.main import app

pytestmark = pytest.mark.anyio


async def test_creating_an_agent_without_agents_edit_is_refused(client: AsyncClient):
    # Роль, а не список разрешений: `AuthContext` сам читает свои разрешения
    # из `ROLE_PERMS` по имени, так что тест проверяет каталог, а не набор,
    # который он выдумал.
    viewer = AuthContext(
        user_id=uuid4(), organization_id=uuid4(), role=str(OrgRoleName.VIEWER)
    )
    app.dependency_overrides[deps.get_auth_context] = lambda: viewer

    response = await client.post("/api/v1/agents", json={"name": "Support"})

    assert response.status_code == 403
```

`tests/api/test_platform_routes.py` делает это обходом, а не по одному утверждению
на маршрут: проверка разрешений, которую несёт маршрут, — это таблица, а таблицу
обходят, а не пересказывают заново. Он обходит **префиксы платформы** — `/agents`,
`/runs`, `/approvals`, `/spend`, `/stats`, `/skills` и остальные из
`_PLATFORM_PREFIXES` — поэтому у большинства из них нет своего файла, и поэтому
`/auth`, `/organizations` и `/users` всё ещё нужны собственные файлы: обход их
пропускает.

### Интеграционный тест { #an-integration-test }

Только для того, на что замокированная сессия ответить не может, а это обычно
порядок, ограничение или каскад. `tests/integration/test_message_order.py` задаёт
форму: ход диалога записывает свой вопрос и свой ответ внутри одной транзакции,
поэтому обе строки несут одинаковый `created_at` с точностью до микросекунды, и
ничью разрешает столбец, а не планировщик.

```python
import pytest

from app.repositories import conversation as conversation_repo
from app.services.transcript import TranscriptService

pytestmark = pytest.mark.anyio


async def test_the_question_precedes_the_answer_it_got(db):
    # `_conversation` и `_run` — собственные построители этого файла: по строке
    # на таблицу, добавленной в `db` и сброшенной flush. Ничего не замокировано;
    # в этом весь смысл.
    conversation = await _conversation(db)
    run = await _run(db, conversation)

    await TranscriptService(db).record(run, prompt="ask", answer="answer")

    written = await conversation_repo.get_messages_by_conversation(db, conversation.id)
    assert [message.role for message in written] == ["user", "assistant"]
```

Ошибка там *была* в Postgres, и замокированная сессия прошла бы на схеме, где
никакого разрешения ничьей не было вовсе.

### Что здесь стоит покрыть тестом { #what-is-worth-a-test-here }

!!! important "Покрывайте отказ"

    Большая часть ценности этой платформы — в том, от чего она отказывается,
    поэтому отказ — это тот случай, который обязан существовать:

    - чтение через границу организаций — **включая случай, где вызывающему
      принадлежит сама строка**;
    - невыданная область доступа;
    - бюджет, проверенный *до* запроса к модели и записанный даже тогда, когда
      запуск падает;
    - спецификация, отклонённая при публикации, а не во время выполнения;
    - ни одного секрета в открытом виде ни в одном ответе, строке журнала или
      записи аудита.

`.claude/rules/testing.md` и навык `backend-tests` несут остальное — ловушки,
разобранные примеры и историю каждой. Эта страница — форма набора; они не
повторяют друг друга.

## Тесты фронтенда { #frontend-tests }

Запускайте их из `frontend/`. В корне репозитория vitest не находит конфигурации,
сообщает больше сотни фантомных сбоев и оставляет после себя лишний `node_modules/`.

```bash
cd frontend

bunx vitest run src/components/chat/usage-meter.test.tsx   # one spec, ~2s
bunx vitest run src/components/chat                        # one directory
bun run test                                               # watch mode
bun run test:coverage                                      # the suite plus the gate CI applies
bun run test:e2e                                           # Playwright
bun run test:e2e --headed                                  # ...with a browser to watch
```

**`bun run test:run` не измеряет покрытие**, поэтому он не может ответить, пройдёт
ли задача `test-frontend`: порог требует 100% строк, инструкций и функций и 97,5%
ветвей по `src/{app/api,lib,stores,hooks}` и большей части `src/components`.

### Два ограничения по времени, оба рассчитаны на загруженную машину { #two-deadlines-both-sized-for-a-loaded-machine }

Тест с тяжёлым рендерингом медленный не потому, что плохо написан, а потому, что
несколько тысяч таких тестов делят десять ядер с тем, что ещё выполняется.
`testTimeout` в `vitest.config.ts` — **15 с**, а `asyncUtilTimeout` из Testing
Library в `vitest.setup.ts` — **5 с**; оба подняты с значений по умолчанию,
которые держатся только на простаивающей машине.

Эти числа получены запуском всего набора четырьмя способами
([#862](https://github.com/vstorm-co/agenticos/issues/862)):

| Самый медленный одиночный тест | Без покрытия | Под `--coverage` |
|---|---|---|
| Десять простаивающих ядер | 1,7 с | 2,9 с |
| 32 занятых цикла рядом | 5,4 с | 6,1 с |

Под такой нагрузкой старое значение по умолчанию в 5 с валило три теста за запуск
— каждый раз *другие* три, потому что то, какие файлы делят воркер, решает тайминг,
и в запуске без покрытия так же, как в инструментированном. Инструментирование
стоит около 1,6× общего времени тестов на спокойной машине и даёт меньший
множитель; остальное — задержки планирования. Поэтому ни одно из двух ограничений
не зависит от `--coverage`: предел, насчёт которого быстрый цикл и порог
расходятся, не может воспроизвести порог.

`asyncUtilTimeout` намеренно остаётся заметно ниже `testTimeout`. Элемент, который
никогда не появится, должен проиграть гонку, чтобы сбой говорил *"Unable to find an
element with the text: …"* и называл его, а не *"Test timed out"* и не называл
ничего.

Ни одно из этих чисел не даёт права тесту делать больше работы, чем нужно его
утверждениям: монтирование сорока строк таблицы дважды, чтобы доказать количество,
стоило около двух секунд в `rag/[id]/counts.integration.test.tsx`, пока его
фикстуру не сократили до трёх.

Playwright запускает то, что нужно набору: фронтенд и совместимый с OpenAI
**сервер-заглушку модели** (stub model server) — `frontend/e2e/stub-model-server.ts`
— по умолчанию на `127.0.0.1:4010`. Бэкенд и его база должны быть уже подняты —
владелец, профиль модели и опубликованный агент из начальных данных приходят от
`agenticos cmd bootstrap`.

Оба порта настраиваются, поэтому набор может работать рядом с другой копией
репозитория, которая уже заняла значения по умолчанию: с `bun run dev`,
оставленным на 3000, или со вторым рабочим деревом. `E2E_PORT` сдвигает фронтенд,
`E2E_STUB_MODEL_PORT` — заглушку, а `playwright.config.ts` выводит из них `baseURL`,
оба `webServer.url` и `PORT`/`E2E_STUB_MODEL_PORT` серверов, так что никому не
сообщают порт дважды. `make test-e2e` читает все три (вместе с `E2E_BACKEND`) и
печатает их перед запуском:

```bash
E2E_PORT=3100 make test-e2e          # frontend on 3100, stub on its default
```

Заглушка — то, что позволяет `journey.spec.ts` провести агента от начала до конца
без ключа провайдера: она отдаёт Chat Completions API, включая потоковую передачу, а
профиль модели доходит до неё через поле **Эндпоинт** (Endpoint). Она возвращает
тот токен, который инструкции агента велят ей произнести, — в этом и
утверждение, ведь ничто другое не могло бы положить этот токен в ответ, — и отдаёт
`usage`, так что запуск тарифицируется и последнему утверждению пути есть что
искать в стоимости. Она ничего не аутентифицирует и не вызывает инструментов; чего
она не доказывает — что отвечает настоящий провайдер.

Заглушка слушает loopback, а бэкенд ходит к ней по `127.0.0.1:<port>` через этот
сохранённый профиль — значит, бэкенд должен делить с хостом его loopback. Это тот
путь, который CI проходит с uvicorn на хосте; бэкенд в контейнере до `127.0.0.1`
хоста не достанет, и смена порта этого не изменит.

### Красный `e2e` — это часто фикстура, а не продукт { #a-red-e2e-is-often-the-fixture-not-the-product }

`setup` и `seed` — это *зависимости проектов* Playwright, поэтому сбой в любой из
них вообще не даёт запуститься проектам, которые от неё зависят. Тогда сводка
читается как `1 failed`, `7 passed` и `17 did not run`, что в пул-реквесте выглядит
точно как сломанная функциональность, — а это не так: **не выполнился ни один тест
продукта.** Три ветки в один день заплатили за это диагностикой
([#132](https://github.com/vstorm-co/agenticos/issues/132)), поэтому
`frontend/e2e/fixture-reporter.ts` теперь печатает баннер, который об этом говорит,
а под CI — ещё и аннотацию ошибки GitHub, которая видна на странице проверок, не
открывая журнал.

### Ждать строку — не то же самое, что ждать записи { #waiting-for-a-row-is-not-waiting-for-the-write }

Тест, который создаёт что-то через диалог, **не должен** нажимать кнопку отправки,
а затем утверждать, что новая строка на экране. Эта схема встречалась в шести
местах, а в четырёх из них тест вёл себя нестабильно. Причины две, и вторая
дороже:

- Окно между завершением мутации и отрисовкой списка реально, и более длинный
  тайм-аут `expect` только заставляет гонку падать медленнее.
- **Открытый диалог Radix убирает остальную страницу из дерева доступности.** Пока
  он на экране, `getByRole("main")`, `getByRole("row")` и любой локатор,
  построенный на них, разрешаются в *ничто*, поэтому утверждение падает по
  тайм-ауту с `element(s) not found` независимо от того, есть строка или нет, — и
  называет единственное, что причиной быть не может. Отклонённое создание
  выглядело точно так же, как медленная повторная выборка, в четырёх отдельных
  случаях.

`submitDialog` из `frontend/e2e/helpers.ts` — это способ пройти через это: он ждёт
собственный ответ записи и утверждает её статус (так что отказ читается как
`409 … already exists`, за миллисекунды), а затем ждёт закрытия диалога — это
приложение говорит, что оно закончило всё, что делает вокруг записи.

Чего он намеренно не обещает — что строка уже отрисована, потому что сейчас это
неправда: на повторную выборку списка иногда отвечают списком до записи, хотя
строка зафиксирована и оба слоя сервера её возвращают
([#230](https://github.com/vstorm-co/agenticos/issues/230), примерно один запуск из
восьми). Итак:

- **Шаг фикстуры спрашивает API и продолжает спрашивать.** Каждый шаг
  `seed.setup.ts` утверждает через `/api/…`, потому что его работа — чтобы фикстура
  существовала, а упавший шаг фикстуры уносит с собой каждый тест продукта. После
  записи он спрашивает опросом (`nowThere`), а не одним чтением. Это начиналось как
  обходной путь: 2xx от этого бэкенда раньше значил, что запрос получил ответ, а не
  что запись читается, потому что коммит выполнялся в зависимости, которую FastAPI
  сворачивает уже после отправки ответа
  ([#353](https://github.com/vstorm-co/agenticos/issues/353)). **Это исправлено** —
  теперь коммит происходит до ответа, — и опрос всё равно остаётся: фикстура —
  неподходящее место, чтобы обнаружить, что какая-то *другая* запись медленнее
  своего подтверждения, и потому что `nowThere` печатает строки, которые он
  действительно видел, тогда как одно чтение не печатает ничего. Проверка
  `alreadyThere`, с которой начинается каждый шаг, — намеренно одно чтение, ведь
  она идёт до записи. Единственная проверка *после записи*, которая читала один
  раз, трижды за день обошлась в 87 пропущенных тестов
  ([#335](https://github.com/vstorm-co/agenticos/issues/335)).
- **Тест продукта, который про отрисовку, говорит об этом**, и сначала
  перезагружает страницу, если ему нужен список, которому можно верить. В
  `vault.spec.ts` три вызова `page.reload()` помечены `#230`; когда эта задача на
  GitHub (issue) закроется, их уберут.
- **Тест продукта, который сделал запись, ждёт так же, как фикстуры.** `nowListed` и
  `nowMatching` в `e2e/helpers.ts` — это `nowThere`, вынесенный из `seed.setup.ts`,
  так что примитив один, а не два
  ([#162](https://github.com/vstorm-co/agenticos/issues/162)). Он разделяет один
  сбой на два: сбой в опросе — это запись, которая так и не легла, а сбой в
  утверждении после него — это страница, которая не нарисовала строку, которую
  отдавал API. `journey.spec.ts` заканчивается доказательством того, что запуск
  *тарифицирован* — должны были произойти пять вещей, а голый `toBeVisible()` на
  строке говорил только, что одна из них не случилась.

### Каждое ожидание говорит, чего оно ждало { #every-wait-says-what-it-was-waiting-for }

`expect(locator).toBeVisible()` падает с `element(s) not found`, что называет
единственное, что причиной быть не может. Playwright принимает сообщение вторым
аргументом, и длинные пути набора им пользуются:

```ts
await expect(
  row,
  `run ${id} is priced at ${cost}, but Activity draws no row for ${modelLabel}`,
).toBeVisible();
```

Четыре теста были нестабильны с анонимной формой, и каждый стоил диагностики,
начинавшейся с нуля ([#130](https://github.com/vstorm-co/agenticos/issues/130),
[#132](https://github.com/vstorm-co/agenticos/issues/132),
[#154](https://github.com/vstorm-co/agenticos/issues/154),
[#162](https://github.com/vstorm-co/agenticos/issues/162)). Сообщение стоит одну
строку и составляет всю разницу между «он снова был нестабилен» и диагностикой.
Когда один всё-таки падает в CI, `playwright-results` рядом с `playwright-report` —
это снимок экрана, видео, трасса и собственный `error-context.md` от Playwright.

## Тестовая база данных { #test-database }

Большинство тестов не доходят до настоящей базы. Фикстура `client` в
`tests/conftest.py` переопределяет `get_db_session` замокированной асинхронной
сессией (`AsyncMock`) через `app.dependency_overrides` FastAPI, поэтому набор идёт
быстро и не требует контейнера Postgres:

- `mock_db_session` — `AsyncMock`, заменяющий `AsyncSession` (`execute`, `commit`,
  `rollback`, `close`)
- Переопределения регистрируются перед каждым тестом и очищаются после него
- Утверждайте по вызовам мока или задайте заглушки возвращаемых значений
  `execute(...)` для проверяемого пути

Всё в `tests/integration/` — исключение: оно просит фикстуру `db` из
`tests/integration/conftest.py`, а не строит собственный движок, — эта фикстура и
создаёт схему.

**Схема строится один раз на весь процесс, а данные сбрасываются между тестами.**

Фикстура `schema_url` запускает `create_all` один раз. Затем фикстура `engine`,
живущая на уровне функции, отдаёт каждому тесту пустую базу, делая `TRUNCATE`
каждой модельной таблицы, в которой есть строки, — и удаляя любую таблицу, которую
тест создал вне моделей: созданную во время выполнения таблицу `rag_<collection>` или
пробу порядка, — вместо того чтобы перестраивать схему. Один `EXISTS` на таблицу находит
заполненные, и каждая последовательность сбрасывается на месте, поэтому пустая
таблица, чей счётчик ушёл вперёд, всё равно начинает с 1.

Раньше она делала `drop_all` + `create_all` перед *каждым* тестом: ~0,4 с DDL, что
составляло почти всё время работы набора, чьи утверждения — микросекунды работы
Postgres. Построение один раз сократило `tests/integration` с ~125 с до ~50 с
([#215](https://github.com/vstorm-co/agenticos/issues/215)).

**`make test`, `make test-fast`, `make test-integration` и `make test-cov` работают
с одноразовым Postgres, а не с вашим для разработки.**

`make docker-test-db` запускает его из `docker-compose.test.yml` (отдельный проект
`agenticos-test` на `localhost:5433`), а те цели запускают его за вас и направляют
на него pytest. Он работает с `fsync=off`, `synchronous_commit=off` и
`full_page_writes=off`, а его каталог данных — `tmpfs`, так что при падении кластер
теряется, — и это нормально, потому что набор создаёт и удаляет в нём собственную
базу.

Причина — fsync. Каждый `TRUNCATE` даёт каждой затронутой таблице новые файлы
отношений, которые Postgres должен сбросить на диск, а на WSL2 или в томе Docker
один сброс стоит ~7 мс: полный запуск занимал около трёх часов там, где CI тратит
десять минут. Без сброса тот же запуск идёт со скоростью CI, а база для разработки
остаётся нетронутой и долговечной.

```bash
make docker-test-db        # start it (idempotent); waits until it is healthy
make docker-test-db-down   # stop it and discard its data
make test TEST_DB_PORT=5434          # another port, when 5433 is taken
make test TEST_DB=external           # no container: use the database POSTGRES_* / .env name
```

Запуск `pytest` по отдельным файлам не оборачивается `make`, поэтому направьте его
туда сами:
`POSTGRES_HOST=localhost POSTGRES_PORT=5433 POSTGRES_USER=postgres POSTGRES_PASSWORD=postgres uv run pytest tests/integration/test_x.py`.
CI задаёт `CI`, а это выбирает `TEST_DB=external`: его сервисный контейнер и есть база.

`TRUNCATE`, а не откат транзакции, потому что тесты потока API фиксируют изменения
через настоящий `get_db_session`, и их строки переживают откат.

**База, с которой он работает, принадлежит тому процессу pytest, который её
запросил**: `<POSTGRES_DB>_p<pid>`, создаётся при старте сеанса и удаляется при его
конце, включая случай падения.

Именно это делает безопасными два одновременных запуска — два рабочих дерева или
рабочее дерево и `make test` — против одного контейнера Postgres, и для этого
ничего не нужно передавать в командной строке.

Имя было постоянным до [#189](https://github.com/vstorm-co/agenticos/issues/189).
Поскольку каждый тест удалял и создавал заново схему в этой общей базе, два запуска
проводили время, удаляя таблицы друг друга, и сообщали о сбоях, которые не
принадлежали ни одной из веток.

!!! danger "Набор отклоняет любую базу, в имени которой нет `test` или `ci`"

    Он удаляет таблицы без всяких условий, поэтому эта защита — единственное, что
    отделяет его от базы для разработки.

**Учётные данные определяются один раз, в `tests/conftest.py`, а всё остальное
читает их обратно из объекта настроек.**

До этой базы достают два движка: движок фикстуры и движок приложения, построенный
во время импорта в `app/db/session.py`, — и тесту, который спрашивает, видна ли
запись, нужны оба.

Раньше они определяли пароль по отдельности: фикстура по умолчанию брала `postgres`,
тогда как `app/core/config.py` по умолчанию пуст, и заметить это было нельзя, пока
каждый тест подключался через фикстуру.

Первый тест, который задействовал движок приложения, не смог аутентифицироваться на
копии репозитория без `backend/.env` — а это **каждое рабочее дерево git**, потому
что файл не отслеживается. Два падения на фоне сплошной зелени во всём остальном,
читающиеся ровно как регрессия ветки
([#485](https://github.com/vstorm-co/agenticos/issues/485)).

Теперь набор подставляет `POSTGRES_PASSWORD=postgres` до того, как будет построен
объект настроек, и только если ни окружение, ни `.env` не дают пароля, поэтому
настоящий пароль никогда не подменяется значением по умолчанию.

`app/core/config.py` по-прежнему оставляет его пустым по умолчанию — именно поэтому
отсутствующий `.env` заявляет о себе в `alembic check`, а не доходит до базы с
догадкой.

### У набора миграций есть третья база { #the-migration-suite-has-a-third-one }

`tests/test_migrations.py` применяет всю цепочку к пустой базе и откатывает её до
base, поэтому не может использовать ни одну из предыдущих: в интеграционной базе
схема уже есть (построенная из моделей, а это другой вопрос), а `downgrade base` в
базе модульного набора опустошил бы её посреди запуска. Он получает
`agenticos_migrations_test_p<pid>`, создаваемую перед его первым тестом и удаляемую
после последнего, и каждый подпроцесс alembic получает это имя явно, а не наследует
`POSTGRES_DB`.

Раньше эта база должна была уже существовать, а создавать её было некому, поэтому
каждый тест модуля пропускался в каждом запуске CI за всю историю проекта, — зелёная
сборка над единственными утверждениями о том, что `downgrade()` вообще работает
([#234](https://github.com/vstorm-co/agenticos/issues/234)). Теперь он создаёт её
сам, а уцелевший пропуск значит только то, что говорит: **ни один Postgres не
ответил.** В CI, где объявлен сервисный контейнер, это, наоборот, падение: контейнер,
который не запустился, — не окружение, которое не может ответить, и в выводе pytest
их не различить.

`make test-migrations` всё ещё существует и всё ещё та цель, которую запускают
вручную после правки `alembic/versions/`, и на ноутбуке она идёт по собственной базе
в одноразовом тестовом Postgres (:5433), так что не достанет ту, где лежит ваша
собственная работа. В CI (`TEST_DB=external`) она использует базу, которую называют
`POSTGRES_*`. `uv run pytest tests/test_migrations.py` — более быстрая проверка.

## Тесты воркера { #the-workers-tests }

**Гарантии очереди проверяются там, где они действуют: в PostgreSQL и в настоящих
процессах.** `FOR UPDATE SKIP LOCKED`, частичные уникальные индексы за `dedupe_key`
и `concurrency_key` и `NOTIFY`, который отзывает откат, — всё это то, с чем
замокированная сессия просто согласилась бы. Поэтому
`tests/integration/test_background_job_queue.py` проверяет их на настоящей таблице, а
`tests/integration/test_worker_runtime.py` запускает целый воркер: разбор, который
съедает память, пока его не остановит сторожевой процесс памяти, дочерний процесс, посылающий
себе `SIGKILL`, базу, отказывающую в двадцати соединениях, остановку посреди задачи.

Дочерние процессы, которые запускают эти тесты, загружают
`tests.worker_handlers:handlers` — набор видов задач, которые нарочно ведут себя
плохо: задача, пожирающая память, задача-самоубийца, задача, выходящая посреди
работы. Новый способ, которым
задача может закончиться, принадлежит туда, вместе с тестом, который заставляет это
произойти по-настоящему.

**Редкие ветви тоже закреплены заглушками.** Строку, до которой доходят только через
настоящий дочерний процесс или настоящую ошибку базы, после `await`, трассировщик
покрытия записывает не всегда, так что порог на ней мерцал бы.
`tests/test_worker_runtime_edges.py` и `tests/test_worker_child_run.py` проводят те
же ветви по замокированным репозиториям и подставному процессу при каждом запуске.

Здесь ничего не требует сервера или переменной окружения. Модульный тест сервиса,
который ставит задачу в очередь, патчит `enqueue` там, откуда сервис его
импортировал, и утверждает полезную нагрузку — как это делает фикстура
`queued_fires` в `tests/test_agent_triggers.py`.

## Итог { #recap }

- **Четыре слоя**: модульные, интеграционные, API, E2E. Выбирайте по тому, что
  тесту нужно сделать истинным, а не по тому, о чём он.
- Асинхронные тесты используют **anyio**. `@pytest.mark.asyncio` здесь ничего не
  делает.
- **Покрывайте отказ.** Большая часть ценности этой платформы — в том, от чего она
  отказывается.
- Слой платформы держится на **100%**, и добавление в него модуля означает правку
  двух списков в `backend/pyproject.toml`.
- Порядок перемешивается при каждом запуске; повторите сбой с напечатанным seed,
  прежде чем делать выводы об изменении.

## Распределение по CI { #ci-distribution }

Набор бэкенда идёт в четырёх изолированных задачах, у каждой свой PostgreSQL, Redis
и объектное хранилище. Целые тестовые файлы назначаются ровно один раз, изначально
уравновешенные по размеру исходников. Каждый шард держит до четырёх воркеров pytest и
собирает покрытие без порога для части набора. Обязательная задача `test` отклоняет
любой неуспешный шард и отсутствующие, лишние, пустые или испорченные данные
покрытия, затем объединяет все четыре отчёта и применяет неизменный **порог в 100%
покрытия платформы**. Пути покрытия относительные, чтобы данные из разных копий
репозитория можно было объединить.

Отчёты JUnit и 30 самых медленных фаз тестов сохраняются для каждого шарда, чтобы
поддерживать настройку по времени выполнения. Размер файла — лишь первая оценка;
фактическое ускорение нужно измерить в CI. `make test` сохраняет свой полный
локальный набор и порог; `make coverage-all REUSE_COVERAGE=1` использует объединённые
данные, не запуская тесты заново.

Линтер фронтенда, производственная сборка и четыре шарда тестов идут независимо.
Шарды сохраняют изоляцию файлов и откладывают неизменные пороги покрытия до одного
объединённого отчёта. Обязательная проверка `test-frontend` падает, если задача или
шард отсутствует, неожиданно пропущен или неуспешен. E2E переиспользует
производственную сборку и запускает четыре шарда, у каждого своя база, Redis, бэкенд,
начальные данные и сервер-заглушка; файлы внутри шарда по-прежнему выполняются
последовательно, без повторов.

PostgreSQL в CI использует одноразовый каталог данных в оперативной памяти и
отключает fsync, синхронные коммиты и полностраничную запись только внутри своего
сервисного контейнера. Производственные базы и базы для разработки сохраняют обычные
настройки долговечности.

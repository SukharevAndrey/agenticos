# Масштабирование за пределы одного хоста { #scale-beyond-one-host }

Поставляемый путь — [один хост с Docker Compose](deploy.md). Эта страница — про шаг
после него: управляемый Postgres, несколько хостов API, отдельные воркеры или несколько
экземпляров рядом. Она говорит, что нужно каждой части при переезде и чего платформа
пока не делает, чтобы план строился на том, что работает.

Сначала измерьте. Один хост [рекомендуемого размера](deploy.md#sizing-the-host) тянет
команду в несколько десятков человек, и большая часть медлительности на небольшом хосте
— это украденное процессорное время или маленький пул, а не отсутствующая реплика. [Набор нагрузочных
тестов](load-testing.md) запускает одну и ту же нагрузку против любого экземпляра.

[Helm-чарт для Kubernetes](kubernetes.md) применяет эту модель внешних сервисов к подам
API, воркеров и консоли. OpenShift остаётся непроверенным.

## Что хранит состояние, а что нет { #what-holds-state-and-what-does-not }

| Часть                 | Что хранит                                                                                                    | Как растёт                                                                                 |
| --------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| API (`app`)           | Ничего своего. Сеансы, присутствие, выполняющиеся ходы чата и поток живых обновлений — в Postgres и Redis     | Больше воркеров uvicorn, затем больше хостов за балансировщиком нагрузки                    |
| Воркер                | Ничего. Задачи, аренды и расписания — строки в Postgres                                                       | Больше процессов на любых хостах с разделёнными между ними пулами                          |
| Консоль (`frontend`)  | Брендинг, который она кэширует на пять минут                                                                  | Больше экземпляров                                                                         |
| Postgres              | Всё долговечное: организации, агенты, диалоги, векторы, очередь задач                                         | Более крупный экземпляр или управляемый сервис                                             |
| Redis (Valkey)        | Кэш и его каналы pub/sub, перестраиваемые после перезапуска                                                   | Один экземпляр, общий для всех хостов                                                      |
| Загруженные файлы     | Том на хосте или бакет                                                                                        | Бакет, как только файлы читает или пишет больше одного хоста                               |
| Служба песочниц       | Песочницы, в которых агенты выполняют команды                                                                 | Собственный хост, см. [Рабочие пространства агентов](configuration.md#running-the-service-on-another-host) |

## Одна база данных на экземпляр { #one-database-per-deployment }

Все организации на одном экземпляре делят одну базу Postgres, и каждый запрос ограничен
организацией. Векторы каждой базы знаний тоже в ней, через pgvector, и очередь задач там
же. `POSTGRES_DB` называет единственную базу, которую использует экземпляр: отдельной
векторной базы нет, нет ни реплики для чтения, ни шардирования по организациям.

Поэтому несколько баз — это несколько экземпляров. Такой ответ нужен данным, которые
должны оставаться в одном регионе, подразделению со своими администраторами и
организации, чья нагрузка не должна доходить до остальных. У каждого экземпляра свои
имена хостов, `SECRET_KEY` и `VAULT_MASTER_KEY`, и во время выполнения между ними ничего
не разделяется.

Инфраструктуру они делить могут. Двум экземплярам на одном сервере Postgres нужны
собственные базы (`POSTGRES_DB`), а на одном Redis — собственные номера `REDIS_DB`, чтобы
корзины лимитов частоты и кэшированные ответы оставались врозь. Корзина тоже своя у
каждого экземпляра. Агент переезжает между ними в виде своей спецификации: выгрузите его в
YAML на одном (`GET /agents/{id}/spec.yaml`) и импортируйте в агента на другом.

Два экземпляра на одном имени хоста, но на разных портах, ещё и делят cookie консоли:
браузер различает cookie по хосту, а не по порту, поэтому вход в один выводит вас из
другого. Дайте каждому своё имя хоста или задайте
[`SESSION_COOKIE_NAMESPACE`](configuration.md#docker-production) на каждой консоли.

## Внешний Postgres { #an-external-postgres }

Управляемый или собственный Postgres работает, если у него есть следующее:

- **PostgreSQL 16 с pgvector.** Управляемые сервисы называют его расширением `vector`.
  Платформа создаёт его при первой записи в коллекцию, поэтому роли, которая
  подключается, нужен `CREATE` на базе, либо администратор создаёт расширение заранее.
  То же с `pg_stat_statements`: миграция добавляет его там, где может, и пропускает с
  предупреждением там, где не может.
- **Зашифрованное соединение** для базы на другом хосте. См. [Зашифрованные
  соединения](configuration.md#encrypted-connections-tls): переопределение должно дойти до
  `app`, `migrate` и `worker`, потому что файлы compose задают хост в каждом из них.
- **Миграции выполняются один раз.** Служба `migrate` применяет их до старта API. При
  нескольких хостах запускайте его из одного развёртывания, а не из каждого.

После управляемого переключения на резерв первый запрос в каждом процессе, который
застаёт разорванное соединение, падает, и затем пул отбрасывает все соединения старше
того. Движки не проверяют соединение перед использованием, потому что это стоило бы
кругового запроса на каждое взятие из пула.

### Как считать соединения { #counting-connections }

Рассчитайте `max_connections` прежде всего остального, иначе Postgres отклоняет
соединения с «too many clients» раньше, чем пул успевает поставить их в очередь или
сбросить нагрузку.

Каждый процесс API открывает два пула по `DB_POOL_SIZE + DB_MAX_OVERFLOW`, по умолчанию
15 каждый: один для запросов и один для векторного поиска, который идёт внутри запроса,
уже держащего соединение. Процесс воркера открывает те же два плюс короткоживущее
соединение на каждую выполняемую задачу. Каждый дочерний процесс индексации — отдельный
процесс, и задача, которую он выполняет, пишет свои векторы через собственный движок с
пулом по умолчанию на 15, закрываемый по её окончании. Поиск по знаниям, который делает
агент, подключается один раз на поиск, без пула.

```text
max_connections ≥ API hosts × UVICORN_WORKERS × 30
                + worker processes × 30
                + ingest children × 15
                + headroom for migrations and an administrator's session
```

Два хоста API по четыре воркера uvicorn и два воркера по одному дочернему процессу
индексации дают 330, так что 400 — разумное значение. Это потолки: простаивающий
экземпляр держит куда меньше. Файл compose для продакшена задаёт 200 для одного хоста.

### PgBouncer { #pgbouncer }

Только в режиме сеансов. Режим транзакций ломает две вещи, на которые платформа опирается:
подготовленные выражения asyncpg, которые здесь ничем не отключаются, и рекомендательную
блокировку уровня сеанса, не дающую одному источнику синхронизации запуститься дважды
одновременно. Режим сеансов ограничивает число серверных соединений, но больше почти
ничего не экономит, поэтому рассчитывать пулы под `max_connections` обычно выгоднее.

## Больше хостов API { #more-api-hosts }

Поставьте впереди балансировщик нагрузки, пропускающий WebSocket: живые обновления и чат
консоли используют `/api/v1/ws/*`. Привязка сеанса к одному серверу не нужна. Человек, чей
сокет переподключился к другому хосту, следит за выполняющимся ходом через Redis, и
присутствие и лимиты частоты тоже хранятся там.

Каждому хосту нужно:

- **Те же секреты.** `SECRET_KEY` подписывает токены, которые должен проверить любой хост,
  а `VAULT_MASTER_KEY` расшифровывает все сохранённые учётные данные.
- **Бакет.** При `FILE_STORAGE_BACKEND=local` файл, загруженный через один хост, отсутствует
  на другом, а воркер, который его разбирает, может быть ни на том ни на другом.
  Используйте `s3` (см. [Загруженные файлы на диске](configuration.md#uploaded-files-at-rest)).
- **Тот же Redis** — один экземпляр или одна точка входа перед основным. Клиент не умеет
  работать с кластером, поэтому Redis Cluster не поддерживается.
- **`RATE_LIMIT_TRUST_FORWARDED_FOR`**, когда до хостов дотягивается только балансировщик,
  иначе все посетители делят его корзину.

Ход чата выполняется в том процессе API, который его принял, а не в воркере, поэтому
нагрузку чата несут хосты API, и `UVICORN_WORKERS` рассчитывается под неё так же,
[как на одном хосте](deploy.md#sizing-the-host).

Несколько экземпляров консоли — это нормально. Брендинг, который они кэшируют, у каждого
свой: изменение администратора сразу видно на экземпляре, который его сохранил, и в
течение пяти минут на остальных.

## Больше воркеров { #more-workers }

Запускайте столько процессов воркеров, сколько требует работа, на любых хостах. Они
захватывают задачи через `SKIP LOCKED`, поэтому одну задачу не выполняют двое, а
расписание, срок которого наступил, запускает любой из них. Воркер, который умирает,
возвращает свои задачи в течение `WORKER_LEASE_SECONDS`. Почему очередь — это строки в
Postgres, в сравнении с девятью другими движками, написано в [тесте фоновой
очереди](task-queue-benchmark.md).

Разделите пулы, когда разбор документов конкурирует с запусками агентов.
`WORKER_POOLS=agent,eval,system,workflow` на одном наборе процессов и `WORKER_POOLS=ingest`
на хостах с запасом памяти не дают загрузке большого файла задерживать автоматизацию. Проверка
работоспособности и `agenticos cmd doctor` сообщают о пуле, который не обслуживает ни один
живой воркер. Настройки в разделе [Фоновая работа](configuration.md#background-work)
задают размер каждого процесса.

## Redis { #redis }

Каждый хост API и каждый воркер используют один и тот же Redis: он переносит между ними
поток живых обновлений, присутствие, выполняющиеся ходы и лимиты частоты. Это кэш,
поэтому перезапуск не теряет ничего долговечного. Живые обновления переподключаются, и
человек, следящий за выполняющимся ходом, видит ответ в транскрипте, когда тот
появляется, а не кадр за кадром.

## Измерьте, прежде чем добавлять хосты { #measure-before-you-add-hosts }

- **`agenticos cmd doctor`** сообщает, до каких Postgres и Redis дошло каждое подключение,
  было ли оно зашифровано и живы ли воркеры.
- **`pg_stat_statements`** показывает, какие выражения дороже всего стоят базе.
- **Logfire** с заданным на каждый экземпляр `LOGFIRE_ENVIRONMENT` отделяет трассы одного
  экземпляра от другого (см. [Наблюдаемость](configuration.md#observability-logfire)).
- **[Набор нагрузочных тестов](load-testing.md)**, запущенный до и после изменения,
  говорит, помогло ли оно.

## Чего платформа пока не делает { #what-it-does-not-do-yet }

- Реплик для чтения и отдельной векторной базы.
- Шардирования организаций по базам внутри одного экземпляра.
- PgBouncer в режиме транзакций и Redis Cluster.

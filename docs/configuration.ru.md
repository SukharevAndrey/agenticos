# Конфигурация { #configuration }

Конфигурация сервиса задаётся переменными окружения, которые загружаются из
`backend/.env` с помощью [pydantic-settings](https://docs.pydantic.dev/latest/concepts/pydantic_settings/).

Оформление консоли и время показа уведомлений сохраняются в базе данных через
интерфейс. То, что доступно в экземпляре, ограничивает, какие элементы главной
страницы чата и напоминания о настройке могут появиться; настройки организации по
умолчанию и личные предпочтения участника выбирают среди доступных элементов.
Отклонение напоминания действует 1, 3 или 7 дней. Срок действия объявления
проверяет сервер, а запланированное окончание работ — лишь справочное: оно не
открывает экземпляр заново. Настройки и правила наследования см. в разделе
[Консоль](console.md#console-experience).

Настройки определены в `app/core/config.py` и доступны через глобальный объект
`settings`:

```python
from app.core.config import settings

print(settings.MAX_UPLOAD_SIZE_MB)
print(settings.DEBUG)
```

## Начало работы { #getting-started }

`make install` создаёт `backend/.env` из `backend/.env.example`, если его нет, и
больше его не трогает: на свежем клоне копировать нечего, а на существующем нечего
потерять.

Прежде чем что-либо выйдет в сеть, где есть кто-то ещё, задайте значения, которые
пример поставляет как заглушки:

```bash
openssl rand -hex 32   # SECRET_KEY — signs every access token
openssl rand -hex 32   # VAULT_MASTER_KEY — unwraps every credential stored at rest
```

!!! danger "`SECRET_KEY` поставляется общеизвестной строкой"

    Пустой `VAULT_MASTER_KEY` подменяется им, чтобы свежий клон вообще смог
    запуститься. Оба хороши на ноутбуке — и составляют всю безопасность экземпляра
    где угодно ещё. Явно заданный `VAULT_MASTER_KEY` ещё и позволяет сохранённым
    секретам пережить ротацию `SECRET_KEY`.

Конфигурация отклоняет незаданный `VAULT_MASTER_KEY` вне `local`/`development`.

| `CHAT_MAX_UPLOAD_SIZE_MB` | `10` | Что можно приложить в чате. Он равен собственным 25 МБ клиента транскрипции — наименьшему потолку движка за этим способом доступа |
| `ML_MAX_CONCURRENT_PARSES` | `4` | Сколько документов один воркер разбирает одновременно для [ML-сервисов](ml-services.md). Лимит частоты считает запуски и не видит, что ещё выполняется, поэтому без этого минутная квота вызовов OCR — это столько же распознаваний в работе. Сверх этого вызывающему отказывают с `Retry-After`, а не ставят в очередь |
| `BROWSER_CDP_ALLOWED_HOSTS` | `[]` (пусто) | Имена хостов, на которых агент, просматривающий сайты, может управлять Chromium. `cdp_url` приходит из спецификации агента, а её пишет любой, у кого есть `edit` на этого агента, поэтому адрес контролирует организация, а запрос исходит от этого экземпляра — вот почему здесь список разрешённых хостов, а не защита от SSRF, через которую проходит любой другой URL, заданный организацией. Сравнение точное и без учёта регистра, без шаблонов. Пустое значение отклоняет автоматизацию браузера полностью |

Адрес приходит из спецификации агента или из секрета, который она называет, а подключение выполняется с этого экземпляра. Сравнение точное и без учёта регистра. Публикация проверяет введённый хост, а каждый запуск — хосты внутри секретов. Пустое значение не разрешает ни одного введённого адреса. Проверяется при публикации и снова каждый раз, когда запуск открывает демона, так что удаление хоста останавливает уже опубликованных агентов. Токен — не настройка: он принадлежит организации и лежит в её хранилище секретов, поэтому любая организация может назвать разрешённый хост, но попадёт только та, что держит токен этого рабочего стола. Пустое значение отклоняет серверную часть демона; рабочему столу в песочнице агента запись не нужна |
| `BROWSER_SIGN_IN_CDP_URL` | `""` (пусто) | Браузер, через который человек входит на сайт из **Настройки → Входы** (Settings → Sign-ins), когда ни один агент своего не назвал: compose-сервис `browser` — это `http://browser:9222`. Его хост должен быть в `BROWSER_CDP_ALLOWED_HOSTS`. Сайт должен быть публичным адресом, и смотреть на него может только тот, кто его открыл. Пустое значение скрывает эту возможность |
| `VISUAL_RENDER_CDP_URL` | `""` (пусто) | Браузер, которым [визуализация](reference/capabilities.md#visuals) рисуется в картинку там, где её не может отрисовать ни один фрейм: ответ в Slack, Telegram или Mattermost и миниатюра страницы в разделе «Обзор». Compose-сервис `browser` — это `http://browser:9222`; его хост должен быть в `BROWSER_CDP_ALLOWED_HOSTS`. Рисунок оттуда ничего не достигает: на каждый его запрос отвечает экземпляр или приходит отказ. Пустое значение отправляет в чат ответ без картинки |
| `BROWSER_EGRESS_PROXY` | `""` (пусто); compose задаёт `http://browser-egress:3128` | Прокси, через который собственный браузер экземпляра открывает любой сайт. Compose-сервис `browser-egress` — это `http://browser-egress:3128` (`docker compose --profile browser up -d browser-egress`): он сам разрешает каждый хост, отклоняет приватные адреса, loopback, link-local и адреса метаданных и подключается к тому адресу, который проверил, поэтому ни перенаправление, ни DNS rebinding не заведут страницу внутрь сети. Используется при каждом просмотре, у которого нет прокси организации и который идёт не в размещённом браузере. Внутреннему инструменту, который агенту нужно просматривать, нужно исключение в `docker/browser-egress/squid.conf`. Пустое значение выпускает браузер напрямую: задавайте `BROWSER_EGRESS_PROXY=` в корневом `.env` только для браузера вне compose, который не может дойти до прокси. Без прокси каждый сайт проверяется на первом запросе во вкладке, а дальше браузер сам разрешает его имя, поэтому имя, которое позже в той же вкладке перепривяжется к приватному адресу, так и останется незамеченным |
| `OUTBOUND_PRIVATE_ALLOWLIST` | `[]` (пусто) | Хосты и сети в вашей сети, до которых запрос может дойти, хотя они разрешаются в приватный адрес, — вики, Git-сервер или MCP-сервер: `["wiki", ".corp.example", "10.1.2.0/24"]`. Запись — это точный хост (`wiki`, без учёта регистра), суффикс с ведущей точкой (`.corp.example` совпадает с `mcp.corp.example` и `a.b.corp.example`, но не с самим `corp.example`), IP-адрес (`10.0.0.5`, `fd00::1`) или диапазон CIDR (`10.1.2.0/24`). Одна завершающая точка отбрасывается, так что `wiki.` — это `wiki`. Читается шагами сценария `http.request`, `http.download` и `http.upload`, коннекторами `git`, `web` и `s3`, клиентом A2A и MCP-подключениями. Цепочка запросов получает список, только когда он нужен её первому URL — тому, который ввёл или привязал человек: цепочка, начинающаяся с публичного хоста, не получает его никогда, поэтому перенаправление публичного сайта, метаданные OAuth, карточка A2A или обход сайта не дотянутся до хоста из списка. Каждая учётная запись каждой организации может дойти до любого порта допущенного хоста, поэтому вносите только сервисы, которые проверяют собственные учётные данные: URL, привязанный из публичного триггера (вебхука, формы, письма) или из аргументов инструмента агента, может назвать любой хост из списка. Адреса loopback, link-local, multicast и метаданных облака отклоняются, что бы ни было в списке: имя из списка, которое отвечает таким адресом, отклоняется везде, где это имя разрешается (шаги HTTP сценария, git, web, S3, A2A, поток OAuth для MCP и собственный URL MCP-подключения; имя из списка, которое пока не разрешается, всё ещё можно сохранить), как и имя с одним приватным ответом вне списка — с указанием этого адреса. Запуск отклоняет запись, которая некорректна, которая достигает таких адресов (`localhost`, `.internal`, `169.254.169.254`, `127.0.0.0/8` или те же адреса, записанные через общеизвестный префикс NAT64 или 6to4, например `64:ff9b::/96` и `2002::/16`; собственный префикс NAT64 другой сети распознать нельзя, поэтому не вносите его, если он транслирует в такие адреса), или которая называет хост базы данных, хост Redis или собственный хост API — по имени или адресу (суффикс, покрывающий имя API, допускается; `doctor` ловит диапазон, покрывающий разрешённый адрес хранилища). `agenticos cmd doctor` сообщает о ней как `private network`: предупреждение для диапазона шире /16 (IPv4) или /48 (IPv6), ошибка, когда диапазон покрывает базу данных или Redis. [Лист HIPAA](security.md#the-sheet) перечисляет её как `private-network`. Пустое значение отклоняет каждый приватный адрес. См. [Сервисы в вашей сети](deploy.md#services-on-your-own-network) и [подключение](mcp.md#a-connection) |
| `MCP_ALLOWED_HOSTS` | `[]` (пусто) | Хосты, которые может назвать один URL MCP-подключения, хотя они разрешаются в приватный адрес, например compose-сервис: `["postgres-mcp"]`. Должно быть положительным; оставьте **пусто**, чтобы организации создавались без лимита (прежний подход с явным включением) |
| `STAV_NOK_PER_USD` | пусто | Курс NOK за USD, который оператор задаёт для выставляемых Stav расходов. Конечный и положительный; например, `10` делит NOK на 10 (для примера, это не текущий курс). USD настройки не требует. Курс ниоткуда не загружается; без пересчёта используется каталог цен, а неизвестные модели остаются посчитанными частично |

Для картинок в каналах на production задайте `VISUAL_RENDER_CDP_URL=http://visual-render:9222` и `BROWSER_CDP_ALLOWED_HOSTS=["visual-render"]` в `backend/.env`. Тогда `scripts/deploy.sh` включает профиль `visuals` в `docker-compose-prod.yml`; при ручном запуске добавьте `--profile visuals`.

Интерактивному публичному просмотру нужен отдельный браузер: задайте `BROWSER_SIGN_IN_CDP_URL=http://browser:9222`, `BROWSER_EGRESS_PROXY=http://browser-egress:3128` и `BROWSER_CDP_ALLOWED_HOSTS=["browser","visual-render"]`. Развёртывание включает профиль `browser`. Агенты, использующие **Встроенный** (Built in), наследуют `BROWSER_SIGN_IN_CDP_URL`, когда их собственный `cdp_url` пуст. У интерактивного браузера выход только через прокси; Squid отклоняет приватные адреса и адреса метаданных. Оставьте `VISUAL_RENDER_CDP_URL=http://visual-render:9222` для изолированной отрисовки. Отсутствие ограничения по домену у агента разрешает публичные сайты; явный список доменов при этом действует.

AgenticOS по умолчанию использует **Встроенный** обзор — до 100 шагов на вызов — и **Управление компьютером → Docker / Песочница** (Computer use → Docker / Sandbox) на среде выполнения `desktop`. Эта среда включает инструменты рабочего стола для
работы с кодом и документами. Без подключения контейнера рабочий стол и личная
облачная работа с кодом остаются отключены. Отсутствующий эндпоинт браузера или недоступный контейнер браузера влияют только на вызовы браузера; это не мешает опубликовать агента или ответить его остальными инструментами. Настроенные эндпоинты всё равно требуют списка разрешённых хостов оператора.

AgenticOS работает напрямую, если пользователь явно не попросил субагентов или параллельную работу агентов. Его настройки «Агенты-исполнители» включают всех доступных опубликованных агентов текущей организации; разрешения при этом действуют, явные закрепления сохраняют свои версии, а запуски автоматизаций без участия человека этого каталога не получают. Динамическое создание специалистов выключено.

У отрисовщика нет опубликованного порта и маршрута в интернет, его делят API и воркер, и ему отведены 1 CPU и 1 GiB RAM. Опубликованные образы бэкенда включают дополнительный набор `browser`; собственному образу нужно `EXTRAS="--extra browser"`. Если отрисовка не удалась, ответ в канале прямо говорит, что картинку приложить не удалось. Каждая отрисовка допускает не больше 256 запросов и 32 ожидающих ответов; тайлы карт вдобавок делят `RATE_LIMIT_MAP_TILES_PER_MINUTE` между отрисовщиками.

### Размер запроса, а не размер файла { #the-size-of-a-request-as-opposed-to-the-size-of-a-file }

Каждый предел выше измеряется по байтам, которые уже пришли. FastAPI разбирает
составное тело, чтобы получить параметр `UploadFile`, _до_ запуска обработчика,
поэтому к моменту, когда один из этих пределов сравнивают с `len(data)`, тело уже
сброшено во временный файл и прочитано в память. За сеансом это не большой риск;
на `POST /api/v1/embed/{key}/files`, до которого может дойти посторонний со
ссылкой, — риск.

Запрос, объявляющий `Content-Length` больше наибольшего из
`MAX_UPLOAD_SIZE_MB`, `CHAT_MAX_UPLOAD_SIZE_MB`, `EMBED_MAX_UPLOAD_SIZE_MB` и
`ML_MAX_UPLOAD_SIZE_MB` плюс 5 MiB на разметку multipart, получает **413** до
чтения тела. Этот потолок следует за настройками загрузки автоматически.

`Content-Length` задаёт вызывающий; chunked-запросы его не объявляют и остаются
под пределами маршрута, которые измеряют реальные байты. Задайте предел тела и на
обратном прокси, чтобы ограничить и их. В Nginx это ещё и нужно, чтобы разрешить
загрузки больше его стандартного 1 MiB: поставляемый шаблон ставит
`client_max_body_size 55m;` на хосте API и в местах составной загрузки консоли.
Страницы консоли, аутентификация и обычный JSON сохраняют предел 1 MiB. Поднимайте
оба допуска загрузки, когда поднимаете наибольшую настройку загрузки. См.
[Развёртывание в Nginx](deploy.md#option-b-nginx). Файлы Compose запускают uvicorn
без собственного предела тела.

### Хранилище секретов { #secret-vault }

Любые учётные данные, которые платформа хранит, — ключи
провайдеров, токены ботов каналов, учётные данные MCP и секреты организаций, —
запечатываются в `app/core/vault.py`, чей конверт выводится из мастер-ключа **и
владельца** (организации или участника, которому принадлежит личное подключение).
Поэтому шифротекст бесполезен вне организации, для которой его запечатали.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `VAULT_MASTER_KEY` | (пусто, подменяется `SECRET_KEY`) | Мастер-ключ хранилища секретов — сокращение для версии 1 из `VAULT_MASTER_KEYS`. Обязателен вне `local`/`development` (если не задана карта ниже), чтобы staging-хранилище не могло подняться запечатанным под опубликованным значением `SECRET_KEY` по умолчанию. Сгенерировать: `openssl rand -hex 32` |
| `VAULT_MASTER_KEYS` | `{}` | Каждый мастер-ключ, который ещё используется, по версии, в JSON — `{"1": "<old>", "2": "<new>"}`. Наибольшая версия запечатывает новые секреты; более старые версии позволяют читать существующие строки, пока `agenticos cmd vault-rotate` не переобернёт их. Если задана, это вся правда: `VAULT_MASTER_KEY` тогда должен быть пустым. См. [Секреты](secrets.md#operations) |

### OAuth2 (Google) { #oauth2-google }

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `GOOGLE_CLIENT_ID` | (пусто) | Идентификатор клиента Google OAuth2 — для входа **и** для согласия триггера Gmail |
| `GOOGLE_CLIENT_SECRET` | (пусто) | Секрет клиента Google OAuth2 |
| `GOOGLE_REDIRECT_URI` | `http://localhost:8000/api/v1/oauth/google/callback` | URL обратного вызова OAuth2 |
| `FRONTEND_URL` | `http://localhost:3000` | URL фронтенда для перенаправлений OAuth2 |
| `DESKTOP_DEEP_LINK_SCHEME` | `agenticos` | Схема, которую оболочка приложения для компьютера регистрирует для входа, переданного системному браузеру ([приложение для компьютера](desktop.md#signing-in)). Обратный вызов строит из неё перенаправление, поэтому это настройка, а не то, что может выбрать вызывающий |

Как получить пару: [консоль Google Cloud](https://console.cloud.google.com/) →
APIs & Services → Credentials → Create OAuth client ID → **Web application**.

Разрешённый URI перенаправления — обратный вызов **бэкенда**, а не фронтенда: по
умолчанию `http://localhost:8000/api/v1/oauth/google/callback`, а на экземпляре —
то, что говорит `GOOGLE_REDIRECT_URI`. Google обменивает код с API, и тот
отправляет браузер дальше на `FRONTEND_URL`. Регистрация вместо этого URL
фронтенда — ошибка, которую стоит назвать: экран согласия работает, а обратный
вызов отвечает 404.

Браузер отправляют дальше с одноразовым кодом на одну минуту, а не с самими
токенами сеанса: токен в URL перенаправления попадает в адресную строку, журнал
доступа сервера фронтенда и `Referer` следующего запроса с того же источника, а
токен обновления живёт неделю. Фронтенд обменивает код на пару токенов по схеме
сервер-сервер через `POST /api/v1/oauth/exchange`, который принимает его ровно
один раз.

### Единый вход (общий OIDC) { #single-sign-on-generic-oidc }

Любой провайдер удостоверений, который публикует документ обнаружения: Microsoft
Entra ID, Okta, Keycloak, Auth0, Authentik, Google Workspace через его эндпоинт
OIDC. Компания, которая размещает это у себя, уже держит такой и не станет
заводить сотрудникам локальные пароли — без этого её MFA и её отключение
сотрудников решаются дважды.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `OIDC_ISSUER` | (пусто) | URL издателя. Пустое значение означает отсутствие SSO, и обратный вызов отвечает 404 |
| `OIDC_CLIENT_ID` | (пусто) | Клиент, который провайдер выдал этому экземпляру |
| `OIDC_CLIENT_SECRET` | (пусто) | Его секрет |
| `OIDC_REDIRECT_URI` | `http://localhost:8000/api/v1/oauth/oidc/callback` | Обратный вызов, зарегистрированный у провайдера |
| `OIDC_SCOPES` | `openid email profile` | Через пробел. Добавьте собственный scope провайдера, если он нужен ему для утверждений |
| `OIDC_VERIFIED_CLAIM` | (пусто) | Третье утверждение, которое принимается как «адрес подтверждён», для провайдера, который называет его по-своему |
| `OIDC_GROUPS_CLAIM` | (пусто) | Утверждение со списком групп человека, обычно `groups`. Если задано, каждый вход применяет [сопоставления групп каталога](directory.md#directory-group-mappings); пустое значение не трогает членства. Отклоняется вместе с `LDAP_URL` |

Издатель — единственный URL. Авторизация, токен, userinfo и JWKS берутся из
`<issuer>/.well-known/openid-configuration`, который провайдер поддерживает верным
при смене ключа или переезде эндпоинта, поэтому больше нет эндпоинтов,
где можно незаметно ошибиться. Поток — authorization-code с PKCE.

Утверждения читаются из ID-токена, а из **эндпоинта UserInfo** — когда
ID-токен их не несёт. Провайдер вправе держать `email` и его утверждение о
подтверждении в UserInfo и не класть ни то, ни другое в токен, поэтому чтение
одного только токена отклонило бы вполне корректного провайдера, не дотянув
одного запроса до подтверждённой личности.

Две кнопки на фронтенде, которые настраиваются там:

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `OAUTH_PROVIDERS` | `google` | Добавьте `oidc`, чтобы показать кнопку SSO; задайте только `oidc` для одного SSO. `ldap` добавляет форму каталога, а `kerberos` — кнопку входа через Windows, см. ниже |
| `OIDC_DISPLAY_NAME` | `SSO` | Как кнопка называет провайдера: `Acme SSO`, `Okta` |
| `OIDC_ICON` | (пусто) | `google`, `github` или `microsoft` — значки, которые страница входа уже поставляет. Любое другое значение рисует простой ключ |

Где живёт каждый издатель и что регистрировать:

| Провайдер | Издатель | Как зарегистрировать URI перенаправления |
| --- | --- | --- |
| **Entra ID** | `https://login.microsoftonline.com/<tenant-id>/v2.0` | URI перенаправления для платформы **Web** в регистрации приложения. Выдайте `openid`, `email`, `profile` в разрешениях API. В **Token configuration** добавьте необязательные утверждения `email` и `xms_edov` в **ID-токен** |
| **Okta** | `https://<org>.okta.com` (или `/oauth2/<id>` собственного сервера авторизации) | URI перенаправления входа в приложении **Web** |
| **Keycloak** | `https://<host>/realms/<realm>` | Действительный URI перенаправления у конфиденциального клиента с включённым standard flow |

Две вещи, которые платформа требует от любого провайдера, на которого её
нацелили:

- **Адрес должен быть подтверждён.** Принимаются два утверждения: стандартное
  `email_verified` и `xms_edov` от Entra ID — именно его Entra присылает вместо
  `email_verified`: `email_verified` Entra не выдаёт вовсе, а `xms_edov` — это
  **необязательное утверждение**, которое включается в регистрации приложения,
  поэтому клиент Entra, где его не включили, не присылает ни одного, и каждый
  вход отклоняется. `OIDC_VERIFIED_CLAIM` называет третье утверждение для
  провайдера, который называет его иначе. Отсутствие считается
  неподтверждённостью:
  неподтверждённый адрес означает, что любой у этого провайдера может назваться
  чьим угодно рабочим адресом, а список разрешённых доменов ниже строится на
  том, что адрес что-то значит.
  В Entra утверждение должно быть в **ID-токене**: её эндпоинт UserInfo
  возвращает только `sub`, `name`, `family_name`, `given_name`, `picture` и
  `email`. `OIDC_VERIFIED_CLAIM` должен называть утверждение, чьё *значение*
  истинно для подтверждённого адреса; если назвать то, что несёт каждый токен,
  например `sub`, это ничего не подтверждает и не принимается. Отклонённый вход
  пишет в журнал `oauth_callback_claims_rejected` с невыполненным условием
  (`reason`) и именами — никогда значениями — полученных утверждений.
- **Устойчивый `sub`.** Учётная запись привязана к нему, а не к адресу, поэтому
  человек, сменивший имя или чей домен купили, сохраняет свою историю, а следующий
  владелец освободившегося адреса её не наследует. Он хранится **в пространстве
  имён издателя**, потому что `sub` уникален в пределах своего издателя и больше
  нигде: нацеливание экземпляра на другого клиента или realm не сможет тогда
  записать нового субъекта в учётную запись старого.

Политика регистрации действует здесь точно так же, как для формы регистрации:
экземпляр с `invite_only` отклоняет вход через SSO от того, кого никто не
приглашал, а список разрешённых доменов отклоняет адрес вне его — с тем же
предложением на странице входа. См.
[Кто может зарегистрироваться](deployment.md#who-may-register).

Когда задан `OIDC_GROUPS_CLAIM`, членства решают группы провайдера:
[сопоставления групп каталога](directory.md#directory-group-mappings) каждой
организации связывают людей с ролью и помещают их в группы, а сопоставленная
группа допускает первый вход на экземпляре с `invite_only` так же, как
приглашение. Переполнение групп Entra ID отклоняется, а не читается как «групп
нет», — см. [Утверждение групп в OIDC](directory.md#the-groups-claim-over-oidc).

SAML и SCIM не реализованы. Большинство провайдеров удостоверений, которые
держит средняя компания, говорят на OIDC, и этих настроек — всё, что им нужно.
Каталог без провайдера удостоверений перед ним можно использовать напрямую — см.
ниже.

### Вход через каталог (LDAP) { #directory-sign-in-ldap }

Вход с учётной записью Active Directory, OpenLDAP или FreeIPA: он выполняется
привязкой от её имени. [Вход через каталог и группы](directory.md) объясняет вход, что он
отклоняет и как читаются группы. Пустой `LDAP_URL` отключает его, и маршрут
отвечает 404.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `LDAP_URL` | (пусто) | `ldaps://host[:port]`, или `ldap://` с StartTLS |
| `LDAP_START_TLS` | `false` | Перевести соединение `ldap://` на TLS до привязки |
| `LDAP_ALLOW_PLAINTEXT` | `false` | Принимать `ldap://` без StartTLS, что отправляет пароли открытым текстом. Иначе отклоняется при запуске |
| `LDAP_CA_CERT_FILE` | (пусто) | PEM-связка для проверки сертификата каталога, для корпоративного CA |
| `LDAP_BIND_DN` / `LDAP_BIND_PASSWORD` | (пусто) | Служебная учётная запись, от имени которой выполняется поиск при входе. Обе или ни одной; без них поиск анонимный |
| `LDAP_USER_BASE_DN` | (пусто) | Где искать учётные записи. Обязательно вместе с `LDAP_URL` |
| `LDAP_USER_FILTER` | совпадает с `uid`, `sAMAccountName`, `userPrincipalName` или `mail` | Должен содержать `{username}`, который экранируется перед подстановкой |
| `LDAP_EMAIL_ATTRIBUTE` | `mail` | Адрес учётной записи |
| `LDAP_NAME_ATTRIBUTE` | `displayName` | Отображаемое имя учётной записи |
| `LDAP_ID_ATTRIBUTE` | `entryUUID` | Устойчивый идентификатор, к которому привязана учётная запись, — `objectGUID` в Active Directory |
| `LDAP_GROUP_ATTRIBUTE` | `memberOf` | Откуда читаются группы учётной записи |
| `LDAP_GROUP_BASE_DN` | (пусто) | Искать группы здесь вместо этого — для каталога без `memberOf` |
| `LDAP_GROUP_FILTER` | `(member={dn})` | Поиск групп, с `{dn}` или `{username}` |
| `LDAP_TIMEOUT_SECONDS` | `10` | Тайм-аут соединения и чтения для каждого запроса к каталогу |

## Redis { #redis }

Файлы compose запускают **Valkey** (`valkey/valkey:8-alpine`) — ответвление Redis
7.2 под лицензией BSD-3-Clause, — а не сам Redis, который с 7.4.0 распространяется
по RSALv2 или SSPL-1.0, и ни одна из них не является лицензией открытого исходного
кода ([лицензии](licenses.md)). Он говорит на том же протоколе на том же порту,
поэтому настройки ниже, схема `redis://` и имя сервиса `redis` не меняются, а
экземпляр, который нацеливает их на управляемый Redis, Valkey или Elasticache,
работает точно как раньше.

Он работает только как кэш, и ничего больше: `--save ''`, без тома, поэтому после
каждого перезапуска стартует пустым. Всё, что платформа держит здесь, — корзины
для лимитов частоты, отметки дедупликации каналов, ответы о членстве, — несёт TTL
и восстанавливается само.

Снимок ничего не давал и стоил одного простоя: Valkey 8 ответвляется от Redis 7.2 и
отклоняет RDB, записанный Redis 7.4, поэтому первое развёртывание на хост, где
работал `redis:7-alpine`, уходило в цикл падений и уносило с собой каждый сервис,
ждущий кэша. Управляемый экземпляр, который всё-таки хранит данные, тоже подходит;
платформа на это в любом случае не рассчитывает.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `REDIS_HOST` | `localhost` | Хост Redis |
| `REDIS_PORT` | `6379` | Порт Redis |
| `REDIS_PASSWORD` | (нет) | Пароль Redis (необязательно) |
| `REDIS_DB` | `0` | Номер базы данных Redis |
| `REDIS_SSL` | `false` | Шифровать соединение (`rediss://`). См. [Зашифрованные соединения](#encrypted-connections-tls) |

## Зашифрованные соединения (TLS) { #encrypted-connections-tls }

Оба хранилища по умолчанию подключаются открытым текстом. На одном хосте, где
Postgres и Redis в одной сети Docker, это нормально, и именно так работают
поставляемые файлы compose. На управляемом Postgres или Redis на другом узле
шифрование соединения — та мера безопасности передачи, о которой проверяющий
спросит первым (HIPAA §164.312(e), SOC 2 CC6.7).

`POSTGRES_SSLMODE` строит URL, который понимает каждый драйвер: `?ssl=<mode>` для
asyncpg приложения, `?sslmode=<mode>` для psycopg2 в Alembic; а `REDIS_SSL`
переключает схему Redis на `rediss://`. `require` шифрует соединение; `verify-ca` и
`verify-full` ещё и проверяют сертификат сервера.

`REDIS_SSL` ещё и требует действительной цепочки сертификатов и совпадающего имени
хоста в самом URL, а не оставляет и то и другое на умолчания redis-py.

!!! warning "Собственный CA — это файл, который читают драйверы, а не хранилище доверия ОС"

    Ни один драйвер не обращается к хранилищу доверия контейнера, а образ работает
    от непривилегированного пользователя без entrypoint, который мог бы его
    пересобрать. asyncpg и libpq читают файл CA, названный `PGSSLROOTCERT`;
    redis-py доверяет тому пакету, на который указывает OpenSSL, а его
    переопределяет `SSL_CERT_FILE`. Смонтируйте CA один раз и задайте на него обе
    переменные: без `PGSSLROOTCERT` проверки `verify-ca` и `verify-full` не
    работают, потому что тогда asyncpg ищет `~/.postgresql/root.crt` и ничего не
    находит.

!!! note "Изменение нужно каждому сервису, который открывает соединение с хранилищем"

    `app`, `migrate` и `worker` подключаются к Postgres и Redis, а
    поставляемые файлы compose закрепляют `POSTGRES_HOST=db` и `REDIS_HOST=redis`
    в `environment` каждого из них, что важнее файла окружения. Поэтому управляемое
    хранилище — это файл переопределения, который доходит до всех трёх, а не строка
    в `.env`.

```yaml
# docker-compose.managed.yml — управляемые Postgres и Redis, проверенные по
# частному CA. Запуск: `docker compose -f docker-compose.yml -f docker-compose.managed.yml up -d`.
x-managed: &managed
  environment:
    POSTGRES_HOST: db.internal.example.com
    POSTGRES_SSLMODE: verify-full
    PGSSLROOTCERT: /run/tls/managed-ca.crt
    REDIS_HOST: redis.internal.example.com
    REDIS_SSL: "true"
    SSL_CERT_FILE: /run/tls/managed-ca.crt
  volumes:
    - ./ca/managed-ca.crt:/run/tls/managed-ca.crt:ro

services:
  app: *managed
  migrate: *managed
  worker: *managed
```

Поставляемые сервисы `db` и `redis` продолжают запускаться, но не используются;
`agenticos cmd doctor` показывает, до какого хранилища дошло каждое соединение и было ли оно
зашифровано (`postgres: tls=on/off`, `redis: tls=on/off`, по `pg_stat_ssl` и схеме
URL).

## Почта (SMTP) { #email-smtp }

Экземпляр отправляет почту через SMTP-сервер, а экземпляр без настроенного SMTP не падает:
он работает, и каждый зависящий от почты процесс молча останавливается, ни один из
них об этом не сообщая:

- **вход без пароля и сброс пароля** — письма со ссылкой для входа и для сброса и
  есть способы попасть в учётную запись самостоятельно;
- **приглашения** — на приглашённый адрес письмо не уходит (теперь консоль так и
  говорит, а не заявляет, что отправила, #1484);
- **уведомления** — превышение бюджета, запрос на согласование, отчёт об
  использовании, извещение, когда администратор действует от имени другой учётной
  записи.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `SMTP_HOST` | `localhost` | Хост SMTP-сервера |
| `SMTP_PORT` | `587` | Порт SMTP-сервера. `587` и `25` согласуют STARTTLS; `465` открывает TLS сразу |
| `SMTP_USER` | (пусто) | Имя пользователя, которым аутентифицируется ретранслятор, вместе с `SMTP_PASSWORD`. Оставьте пустым для ретранслятора без аутентификации |
| `SMTP_PASSWORD` | (пусто) | Пароль этого пользователя |
| `SMTP_TLS` | `true` | Шифровать ли соединение. Схему выбирает порт — STARTTLS на `587`, неявный TLS на `465`, — если `SMTP_TLS_MODE` не скажет иначе. Ставьте `false` только для ретранслятора без шифрования, например локального сервера на `25` |
| `SMTP_TLS_MODE` | `auto` | Как открывается зашифрованное соединение. `auto` отдаёт выбор порту; `implicit` открывает TLS с первого байта, а `starttls` согласует переход на TLS, каким бы ни был порт. Игнорируется при `SMTP_TLS=false` |
| `EMAIL_FROM` | `noreply@agenticos.com` | Адрес `From` в каждом сообщении |
| `EMAIL_FROM_NAME` | `agenticos` | Отображаемое имя рядом с этим адресом |

!!! note "Как шифруется соединение"

    `SMTP_TLS` — это выключатель; схему выбирает порт. Поставляемое умолчание —
    `587` при `SMTP_TLS=true` — согласует STARTTLS, чего и ждёт сервер отправки
    (submission), соблюдающий стандарты. Для сервера, которому нужен неявный TLS, используйте
    `465`, а для ретранслятора без шифрования — `SMTP_TLS=false` на `25`.

    Сервер, который говорит неявным TLS на порту, отличном от `465`, — скажем,
    `8465`, — требует `SMTP_TLS_MODE=implicit`, потому что `auto` предложил бы ему
    рукопожатие открытым текстом, и каждая отправка падала бы. `starttls` —
    зеркальный случай.

## Фоновая работа { #background-work }

Задачи встают в очередь в PostgreSQL и выполняются в воркере, `python -m app.worker`,
из того же образа, что и API. Указывать ему не на что, и ключ не нужен: воркер
обращается к той же базе, что и API. Каждая настройка ниже — на один процесс воркера.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `WORKER_POOLS` | `agent,eval,ingest,system,workflow` | Пулы, которые обслуживает этот процесс. Запустите второй воркер с `ingest`, чтобы вынести разбор на отдельный хост. Хотя бы один воркер должен обслуживать `eval`, иначе запуски оценки ждут в очереди, пока через сутки их не пометят как неудачные, а в список, заданный до появления пула `workflow`, нужно добавить этот пул, иначе узлы сценариев не выполнит ни один воркер; `agenticos cmd doctor` назовёт пул, который не обслуживает ни один живой воркер |
| `WORKER_AGENT_CONCURRENCY` | `10` | Запусков агентов и срабатываний триггеров одновременно |
| `WORKER_EVAL_CONCURRENCY` | `4` | Запусков оценки одновременно. Каждый занимает свой слот на весь запуск, поэтому у оценок собственный пул и они никогда не занимают слот, нужный запуску агента |
| `WORKER_WORKFLOW_CONCURRENCY` | `5` | Узлов сценария одновременно. Рассчитывайте память воркера так, чтобы на столько узлов хватило самого большого файла, который может держать узел |
| `WORKER_SYSTEM_CONCURRENCY` | `4` | Проходов, очисток и отчётов одновременно |
| `WORKER_INGEST_CHILDREN` | `2` (`1` в поставляемых файлах compose) | Дочерние процессы для разбора и построения эмбеддингов, каждый — по одной задаче за раз |
| `WORKER_INGEST_MEMORY_MB` | `1536` | Сколько может занимать один дочерний процесс вместе со всем, что он запустил, прежде чем сторожевой процесс остановит его |
| `WORKER_INGEST_MAX_JOBS` | `100` | Задач, которые выполняет дочерний процесс до замены |
| `WORKER_LEASE_SECONDS` | `60` | Как долго захваченная задача удерживается без сигнала активности |
| `WORKER_BREAKER_DEATHS` | `5` | Смертей воркера подряд на задачах одного типа, после которых этот тип приостанавливается |
| `WORKER_HEALTH_FILE` | `/tmp/agenticos-worker-alive` | Файл, который читает проверка контейнера |
| `WORKER_MEMORY_LIMIT` | `4g`, `2560M` в production compose | Собственный лимит памяти контейнера — переменная compose, а не настройка |
| `BACKGROUND_JOB_RETENTION_DAYS` | `14` | Завершённые задачи, которые хранятся для страницы «Фоновые задачи» |

**Считайте память от дочерних процессов, а не от числа задач.** Воркер занимает
около 450 МБ под импортированное приложение, и каждый дочерний процесс индексации —
ещё столько же плюс документ, который он разбирает. `WORKER_INGEST_MEMORY_MB`
намеренно ниже лимита контейнера: сторожевой процесс останавливает дочерний, который
его перерос, и записывает причину в задачу, тогда как ядро, принудительно завершая процесс из-за нехватки памяти, оставило бы
только мёртвый процесс. Увеличивайте `WORKER_INGEST_CHILDREN` на хосте с запасом
памяти — и лимит контейнера вместе с ним.

**Задача, которая приводит к гибели своего процесса, не может зациклиться.** Попытка
засчитывается при захвате задачи, поэтому дочерний процесс, который ядро принудительно завершило посреди
разбора, уже израсходовал одну, и после `max_attempts` задача больше не повторяется.
Тип, задачи которого `WORKER_BREAKER_DEATHS` раз подряд приводят к смерти воркера,
приостанавливается, и об этом сообщают каждому владельцу экземпляра; его не берёт
никто, пока один из них не возобновит его на странице «Фоновые задачи». Счёт ведётся
по организациям: организация, задачи которой постоянно приводят к гибели воркера,
приостанавливает тип только для себя, а задачи, не принадлежащие ни одной
организации, делят один счёт на весь экземпляр.

**То, что задача оставляет после себя, закрывается, даже если с первого раза не
вышло.** Задача, завершившаяся окончательно, может оставить документ в состоянии
`processing`, а журнал синхронизации — в `running`. Воркер закрывает их, когда задача
завершается, а восстановление в течение суток повторяет закрытие, которое не удалось,
— например, из-за недоступной в тот момент базы.

Умерший воркер возвращает свои задачи в течение `WORKER_LEASE_SECONDS`: восстановление
другого воркера забирает задачу с истёкшим сроком удержания и записывает её как смерть
воркера. Развёртывание не стоит задаче попытки: воркер перестаёт захватывать задачи,
даёт выполняющимся 30 секунд на завершение и возвращает остальные. Файлы compose дают
ему 45 секунд, прежде чем принудительно завершить его.

Проверка работоспособности контейнера читает `WORKER_HEALTH_FILE`, который сигнал
активности обновляет после каждого такта, дошедшего до базы, поэтому живой воркер,
отрезанный от Postgres, показывает `unhealthy`. Это файл, а не HTTP-эндпоинт, потому
что воркер ничего не обслуживает.

В `backend/Dockerfile` нет `HEALTHCHECK`. Образ запускают как разные процессы — API,
воркер и миграции, — и проверка, годная для одного, для другого навсегда остаётся ложной
тревогой, поэтому своя проверка есть в каждом определении сервиса.

### Истечение согласований { #approval-expiry }

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `APPROVAL_EXPIRY_HOURS` | `72` | Сколько ждёт отложенный вызов инструмента, прежде чем ежечасный проход отклонит его по таймауту |
| `QUESTION_EXPIRY_HOURS` | `24` | Сколько запуск ждёт ответа на неотвеченный вопрос агента, прежде чем тот же проход завершит его |

Три дня — потому что срок должен покрывать выходные: согласование, пришедшее в пятницу
после обеда, — то самое, по которому никто не принимает решения, и закрыть его в субботу
значило бы закрыть его за то, что его запросили не в тот час. Сократите срок там, где
очередь смотрят в течение рабочего дня и устаревший запрос хуже медленного;
увеличьте там, где согласования — еженедельный ритуал. Истечение вызова также
**завершает его запуск** — о том, что это решает и что намеренно оставляет как есть,
см. [Управление](governance.md#a-decision-nobody-makes).

### Уборка зависших запусков { #stale-run-reaping }

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `RUN_HEARTBEAT_SECONDS` | `15` | Как часто процесс, выполняющий запуск, отмечает его живым, пока работает его модель |
| `STALE_RUN_REAPED_AFTER_SECONDS` | `120` | Сколько запуск в состоянии `running` может идти без признаков жизни, прежде чем поминутный проход решит, что его процесс умер, и завершит его как `failed`. Не меньше трёх `RUN_HEARTBEAT_SECONDS` — это проверяется при запуске; ноль или меньше отключают проход |

Строка запуска сохраняется в базе до вызова модели, поэтому воркер, принудительно завершённый посреди запуска,
оставляет его в состоянии `running`, и завершить его больше некому. Порог не обязан
быть точным — живой запуск, который проход всё-таки пометит завершённым, вернётся в прежнее состояние
собственной финальной записью, — поэтому задайте его заметно больше самого долгого
вашего законного запуска, но не вплотную к нему. См.
[Управление](governance.md#a-run-whose-process-died).

### Запуски сценариев { #workflow-runs }

| Переменная | По умолчанию | Описание |

Ограничение запусков на вызывающего (`RATE_LIMIT_RUN_PER_MINUTE`) списывает один
токен за старт и не отличает сценарий из одного узла от сценария из пятисот узлов.
Эти два потолка отличают: они ограничивают работу по узлам — в очереди и
выполняющуюся — за общим механизмом выполнения, чтобы один вызывающий не мог ниже
лимита частоты запустить много широких сценариев и нарастить очередь, которая
лишит ресурсов другие организации.

Запуск сценария — это цепочка задач. Каждая попытка узла — одна задача
`workflow-dispatch-node` в пуле сценариев, поставленная в очередь в той же транзакции,
что и строка диспетчеризации узла, поэтому запуск никогда не начинается без своей
задачи, а откаченный старт не оставляет ни одной. Таймер или пауза перед повтором —
та же задача с `run_after`, установленным на время, когда она должна выполниться.

Положение запуска хранит строка в базе, а не задача: задача выполняется один раз, а
воркер, умерший посреди узла, восстанавливается проходами ниже, а не повтором задачи.

В системном пуле работают пять проходов:
`workflow-dispatch-poll` (каждую минуту) ставит в очередь задачу для узла, чей срок наступил, а собственная задача которого так и не выполнилась, `workflow-reconcile` (каждые
30 секунд) восстанавливает захваты и попытки, оставленные мёртвым воркером,
`workflow-schedules-check` (каждую минуту) запускает расписания сценариев,
`workflow-table-triggers` (каждые 10 секунд) выполняет триггеры на записях таблиц, а
`workflow-run-retention` (ежедневно) удаляет запуски старше срока хранения их
сценария.

У задач узлов свой пул, поэтому веерное разветвление не может занять слоты, которых
ждут запуски агентов, а агент, который вызывает сценарий и ждёт его, не может ждать на
слоте собственного пула. `WORKER_WORKFLOW_CONCURRENCY` ограничивает число узлов,
выполняющихся на каждом воркере. Запуск, которого кто-то ждёт (вебхук, которому нужен
ответ, чат, API), идёт впереди того, который запустил себя сам, а сценарий, который
вызывает другой, получает приоритет вызвавшего его запуска.

Узел работает на собственном событийном цикле воркера и в его памяти: рассчитайте
память воркера на `WORKER_WORKFLOW_CONCURRENCY` узлов, каждый с самым большим файлом,
который может держать узел (`WORKFLOW_RUN_MAX_FILE_BYTES`), потому что воркер,
принудительно завершённый ядром из-за нехватки памяти, теряет все задачи, которые выполнял. Эти смерти не засчитываются в
`WORKER_BREAKER_DEATHS`: одно падение завершает все узлы, которые держал воркер, а
узел, который постоянно приводит к смерти воркера, останавливает собственный потолок
повторов сценария. Страница «Фоновые задачи» показывает по задаче на каждую попытку
узла, а проходы добавляют около 14 400 строк в день, и хранятся они
`BACKGROUND_JOB_RETENTION_DAYS` дней. Отменить поставленную в очередь задачу узла там не
предлагается: отменяйте запуск.

## Наблюдаемость (Logfire) { #observability-logfire }

Необязательно и выключено, пока не задан токен. Ничего из этого раздела настраивать не
обязательно: без `LOGFIRE_TOKEN` платформа работает полностью, а запуск всё равно
записывает свой идентификатор трассировки локально. Токен даёт трассировки, а
трассировка — это копия запуска: сообщение пользователя, вывод модели и каждый
аргумент и результат инструмента, — потому что ровно для такой записи и существует
бэкенд наблюдаемости. Поэтому установка токена — это решение о том, куда может уходить
содержимое запусков, а не только о панелях. Экземпляр, работающий с медицинскими,
юридическими или кадровыми данными, читает [что покидает машину](data-protection.md#traces),
прежде чем его задать.

Направить запуски в проект могут три вещи, и они складываются:

- `LOGFIRE_TOKEN` здесь инструментирует Pydantic AI глобально, поэтому каждый запуск
  экспортируется в собственный проект экземпляра. Настраивают его два процесса: API
  при старте (`app/main.py`) и воркер один раз при запуске (`app/worker/__main__.py`),
  поскольку жизненный цикл API он не проходит. Спаны воркера несут
  `<service name>-worker`, поэтому в одном проекте можно отличить медленный запуск по
  расписанию от медленного хода диалога.
- [Окружение](environments.md#tracing-per-environment) может нести собственный токен
  записи, запечатанный в хранилище секретов, и он перенаправляет привязанные к нему
  запуски.
- Блок [`observability`](reference/spec.md#observability) агента называет собственный
  проект — обычно проект клиента.

Режим `content` агента решает, сколько несёт каждый спан: `full`, значение по
умолчанию, записывает сообщение, вывод и каждый вызов инструмента; `none` записывает
только время, токены, стоимость и имена инструментов. Он применяется там, где агент
инструментируется, поэтому действует независимо от того, какой токен трассирует запуск:
при общем токене экземпляра агент вместо этого получает инструментирование без
содержимого, а специалист, которому агент поручает, — записанный внутри или придуманный
моделью посреди запуска, — наследует режим. Одно ограничение, прежде чем на это
полагаться: подключение такого инструментирования выполняется по мере возможности, и
сбой записывается в журнал, а запуск продолжается.

Журналы приложения от API, воркера, дочерних процессов индексации и CLI идут в stderr
с отметкой времени, уровнем и именем журнала. Они работают без токена Logfire и видны
через `docker compose logs -f`. `LOG_LEVEL` по умолчанию `INFO`; задайте `DEBUG`,
`WARNING`, `ERROR` или `CRITICAL`, чтобы изменить подробность. Существующее вырезание
персональных данных и учётных данных охватывает и трассировки исключений.

Журналирование SQL-запросов выключено, если не задан `DB_ECHO=true`. Сообщения
INFO/DEBUG транспорта HTTP подавляются. Спаны Logfire по умолчанию тоже не выводятся в
консоль ни в каком окружении; задайте `LOGFIRE_CONSOLE=true`, чтобы печатать их при
отладке. Это не меняет экспорт трассировок в Logfire. Без токена спаны не
экспортируются; `agenticos cmd doctor` сообщает об этом в строке `tracing`.

Задайте каждому экземпляру собственный `LOGFIRE_ENVIRONMENT` — например, `local` на
ноутбуке и `production` на сервере. Тогда один проект может держать оба и всё равно их
различать.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `LOG_LEVEL` | `INFO` | Уровень журнала приложения: `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` |
| `LOGFIRE_CONSOLE` | `false` | Печатать спаны Logfire в консоль для отладки |
| `LOGFIRE_TOKEN` | (нет) | Токен Pydantic Logfire. Получить: https://logfire.pydantic.dev |
| `LOGFIRE_SERVICE_NAME` | `agenticos` | Имя сервиса на панели Logfire |
| `LOGFIRE_ENVIRONMENT` | `development` | Метка окружения |
| `LOGFIRE_ORGANIZATION` | (нет) | `slug` организации — для построения ссылки **в** сохранённую трассировку. Токен — это учётные данные с правом _записи_ и не содержит ни одного из двух `slug` |
| `LOGFIRE_PROJECT` | (нет) | `slug` проекта, вместе с организацией. Если не задан любой из них, `logfire_trace_id` запуска всё равно записывается, но ссылка не предлагается |
| `LOGFIRE_BASE_URL` | `https://logfire-us.pydantic.dev` | К какому развёртыванию Logfire относятся эти `slug`. `logfire-eu` — другой хост, и ссылка, построенная для неверного, отдаёт 404 |

## RAG (генерация, дополненная поиском) { #rag-retrieval-augmented-generation }

### Векторная база данных { #vector-database }

pgvector использует существующее подключение к PostgreSQL. Дополнительная настройка не
нужна — но **образ** должен быть `pgvector/pgvector:pg16`, и это закреплено в каждом
файле compose здесь.

!!! note "«Векторное хранилище: не настроено» (Vector store: unconfigured) на свежем экземпляре — не неисправность"

    Расширение создаётся при первой записи в коллекцию, поэтому до первого документа
    его действительно нет, и об этом говорят и страница «Система» в
    администрировании, и `agenticos cmd doctor`. Само разрешается при первой
    индексации.

    Неисправность — это `unhealthy` там же, и она называет одну из трёх причин: образ
    не содержит pgvector; роль, которой подключаются, не может его создать; или
    каталог данных содержит строку расширения, а образ, на котором он теперь
    работает, лишился библиотеки. Все три приводят к ошибке загрузки уже после того, как
    байты приняты, и все три раньше выглядели так же, как здоровый первый день
    ([#1504](https://github.com/vstorm-co/agenticos/issues/1504)).

### Эмбеддинги { #embeddings }

Здесь ничего. Каждая коллекция называет провайдера, которым строит эмбеддинги,
модель и либо ключ из хранилища секретов организации, которым это оплачивается, либо
— для провайдера `ollama`, которому ключ не нужен, — **локальный сервис**, строку в
разделе **Знания → Интеграции** (Knowledge → Integrations), которая говорит, где
отвечает Ollama экземпляра или организации. См.
[Обработка файлов](file-processing.md#embeddings-the-model-whose-endpoint-answers-and-whose-key-pays).

Раньше было две переменные. `EMBEDDING_MODEL` заранее выбирала модель для новых
коллекций и удалена: форма предлагает модели, которые обслуживает выбранный провайдер.
`EMBEDDING_OLLAMA_BASE_URL` называла одну Ollama на весь экземпляр, а теперь это
локальный сервис — для организации или для всего экземпляра.

### Разбор документов — настраивается для каждой коллекции, а не здесь { #document-parsing-configured-per-collection-not-here }

Парсер, OCR, размер фрагмента, перекрытие фрагментов, стратегия разбиения и модель
описания изображений — **не** переменные окружения. Они хранятся в каждой базе знаний
(`knowledge_bases.ingestion_config`) и редактируются на `/rag`, и любую из них
вдобавок можно переопределить для одной загрузки.

Причина в том, что одно значение на весь экземпляр заставляло одну и ту же форму давать
разные коллекции на двух экземплярах, и ничто в продукте не показывало, какие именно,
— а архив отсканированных договоров и папка заметок в Markdown хотят разных ответов на
одном и том же экземпляре. `PDF_PARSER`, `CHAT_PDF_PARSER`, `LLAMAPARSE_TIER`,
`LITEPARSE_OCR_LANGUAGE`, `LITEPARSE_TIMEOUT_SECONDS`, `RAG_ENABLE_OCR`,
`RAG_CHUNK_SIZE`, `RAG_CHUNK_OVERLAP` и `RAG_CHUNKING_STRATEGY` были удалены; теперь
их установка ничего не делает.

Две вещи, которые раньше оставались здесь, теперь строки в продукте. Ключ LlamaParse —
это запись в хранилище секретов, которую называет конфигурация индексации коллекции
(`llamaparse_secret_id`), и коллекция на LlamaParse без неё отклоняется уже в форме —
`LLAMAPARSE_API_KEY` больше нет. Сервер OCR, на который LiteParse отправляет страницы,
— это локальный сервис вида `ocr` в разделе **Знания → Интеграции** (Knowledge →
Integrations), выбираемый для каждой коллекции (`ocr_endpoint_id`) и зарегистрированный
оператором организации или, для всех организаций, администратором экземпляра;
`LITEPARSE_OCR_SERVER_URL` тоже больше нет. Ни то, ни другое не было видно организации,
о документах которой оно решало.

Вложения в чате читаются через PyMuPDF и не настраиваются: вложение не принадлежит ни
одной коллекции, поэтому сохранённой конфигурации, которую можно прочитать, нет.

## Загруженные файлы при хранении { #uploaded-files-at-rest }

Где хранятся вложения из чата, аватары, изображения брендинга и оригиналы документов
базы знаний. Один бэкенд на экземпляр, никогда не на организацию, и его переключение не
переносит то, что уже лежит в другом.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `FILE_STORAGE_BACKEND` | `local` | `local` пишет в `MEDIA_DIR`; `s3` пишет в совместимый с S3 бакет |
| `FILE_STORAGE_S3_BUCKET` | (пусто) | Бакет. Обязателен, когда бэкенд — `s3`; без него API отклоняет начало загрузки |
| `FILE_STORAGE_S3_ENDPOINT` | (нет) | Пусто для AWS. Адрес сервиса для MinIO или другого совместимого хранилища |
| `FILE_STORAGE_S3_REGION` | `us-east-1` | Регион AWS |
| `FILE_STORAGE_S3_ACCESS_KEY` | (пусто) | Оставьте **пустым на AWS**: тогда отвечает собственная цепочка учётных данных boto3 — профиль экземпляра или роль IRSA, а не долгоживущий ключ в файле окружения |
| `FILE_STORAGE_S3_SECRET_KEY` | (пусто) | Вторая половина, так же |
| `FILE_STORAGE_S3_PATH_STYLE` | `false` | `true` для MinIO и большинства совместимых хранилищ, которые адресуют бакет по пути. Запрос с виртуальным хостом к такому падает по DNS, а не по S3 |
| `FILE_STORAGE_S3_PREFIX` | (пусто) | Под ним лежит каждый ключ, который пишет этот экземпляр, поэтому один бакет может держать несколько экземпляров, и их ключи не пересекаются |
| `FILE_STORAGE_S3_ENCRYPTION` | `sse-s3` | Что запрашивается у хранилища при каждой записи: `sse-s3` (собственный ключ бакета), `sse-kms` (ключ ниже) или `none` |
| `FILE_STORAGE_S3_KMS_KEY_ID` | (нет) | Идентификатор или ARN ключа KMS. **Обязателен**, когда режим — `sse-kms`: S3 читает `aws:kms` без имени как собственный ключ AWS `aws/s3`, а не как ключ бакета по умолчанию, поэтому пустое значение шифровало бы ключом, который никто не выбирал |

!!! warning "`none` — для хранилища, за которым нет KMS, и это не шифрование"

    MinIO отклоняет SSE-S3, если не настроен сервер KES, поэтому совместимому
    хранилищу без KMS нужен `none`, чтобы работать вообще, — и экземпляр, работающий
    так, имеет только то шифрование, которое дают его тома. `agenticos cmd doctor`
    сообщает о такой конфигурации как о не настроенной, а не как о находящейся в норме, и строка о
    шифровании данных при хранении в разделе [Безопасность](security.md#what-is-encrypted-where)
    говорит то же самое.

Бакету, в который пишет экземпляр, нужны `s3:PutObject`, `s3:GetObject`,
`s3:DeleteObject` и `s3:ListBucket` на нём, а при режиме `sse-kms` — ещё `kms:Encrypt`,
`kms:Decrypt` и `kms:GenerateDataKey` на ключе. Для локального MinIO
`make docker-minio` запускает его на `:9000` с `minioadmin` / `minioadmin`.

### Сгенерированные медиафайлы { #generated-media }

Изображения, речь и видео, которые генерируют агенты, хранятся в том же хранилище, в
`generated_<org>/`, и каждая запись привязана к своей организации и диалогу, в котором
создана. То, что хранит организация, ограничено дважды. О том, что удаляется когда, см.
[Защита данных](data-protection.md#generated-media).

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `GENERATED_MEDIA_QUOTA_MB` | `5120` | Сколько сгенерированных медиафайлов может хранить одна организация, в MiB. Считается каждый файл, включая созданный без диалога — предпросмотр или тестовый запуск, побочный вопрос `/btw` в канале, запуск через API без указания диалога; такие файлы проход удаляет через 7 дней. Проверяется перед каждым платным вызовом генерации: сверх него инструмент отвечает, что организация израсходовала своё хранилище, и ничего не тратит. Принятый вызов держит против квоты оценку своего файла, пока файл не сохранён, — 16 MiB на изображение, 8 KiB на символ речи, 2 MiB на секунду видео, — поэтому вызов, оценка которого вывела бы организацию за квоту, отклоняется, и одновременные запуски или параллельные вызовы в одном ответе не могут все пройти по одной и той же цифре. Файл больше своей оценки считается по реальному размеру. `0` — без квоты |
| `GENERATED_MEDIA_RETENTION_DAYS` | `90` | Возраст, по достижении которого ежедневная задача `sweep-generated-media` удаляет сгенерированный файл и его запись, есть ли ещё его диалог или нет. `0` хранит их, пока не удалён их диалог или организация. Файл без диалога уходит через 7 дней в любом случае |

Файл отдаётся потоком только в запрошенном проигрывателем диапазоне байт, — с
диска или через `GetObject` с диапазоном, — поэтому длинный клип никогда не держится
целиком ни в API, ни на сервере консоли.

### Синхронизация с S3/MinIO { #s3minio-sync }

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `S3_RAG_ENDPOINT` | (нет) | URL эндпоинта S3/MinIO. Источник синхронизации может его переопределить |
| `S3_RAG_ACCESS_KEY` | (пусто) | Ключ доступа, только для команды CLI `rag-sync-s3` |
| `S3_RAG_SECRET_KEY` | (пусто) | Секретный ключ, так же |
| `S3_RAG_BUCKET` | `agenticos-rag` | Имя бакета |
| `S3_RAG_REGION` | `us-east-1` | Регион AWS. Если у учётных данных есть собственный регион, используется он |

Это _коннектор синхронизации_, который читает бакет, принадлежащий организации, а не

**Пара ключей здесь — для CLI, а не для источника синхронизации.** Источник

регион всё же берутся из этих настроек, потому что ни один из них не называет субъекта:
они говорят, где находится хранилище, а не кто спрашивает.

## Опубликованные приложения { #published-artifacts }

Страницы, которые агенты публикуют с помощью возможности `artifacts`. Их байты лежат в файловом
хранилище выше; эти настройки ограничивают их и говорят, откуда они отдаются. См.
[Приложения](artifacts.md).

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `ARTIFACT_MAX_BYTES` | 5 MiB | Одна версия одной страницы. Публикация сверх него отклоняется с сообщением, которое читает модель |
| `ARTIFACT_MAX_VERSIONS` | `20` | Версий, которые хранятся на одно приложение. Самая старая удаляется, когда появляется более новая, если публичная ссылка не закреплена за ней |
| `ARTIFACT_VIEW_TTL_SECONDS` | `300` | Сколько открывается подписанный адрес содержимого, не более 3600. А также сколько открытая страница живёт после отзыва выданного доступа или ссылки |
| `ARTIFACT_PUBLIC_DATA_CACHE_BYTES` | 32 MiB | Наибольший объём записей в байтах, который один процесс API держит 30 секунд для [публичных ссылок и встраивания страниц](artifacts.md#the-cache-and-the-cap). Только в памяти процесса, никогда в Redis. Первыми уходят чтения, к которым дольше всего не обращались, а чтение сверх бюджета не сохраняется. Не менее 1024 |
| `ARTIFACT_ORIGIN` | (пусто) | Откуда отдаётся содержимое — страницы, их [набор библиотек](artifacts.md#the-library-set) и документ встраивания. Пусто — отдаётся с `PUBLIC_BASE_URL`, изолированно его политикой `sandbox`. Задайте хост на отдельном регистрируемом домене, направленный на этот API, чтобы вдобавок разместить страницу на другом сайте |
| `ARTIFACT_RENDER_CDP_URL` | (пусто) | Эндпоинт Chromium DevTools, в котором [`preview_artifact`](artifacts.md#seeing-the-page-preview) рисует страницы, например `http://artifact-render:9222`. Настраивается только на уровне экземпляра: он не сверяется с `BROWSER_CDP_ALLOWED_HOSTS`, который перечисляет, чем могут управлять авторы агентов, и агенту, просматривающему сайты, этот хост запрещён, даже если он есть в том списке. Бэкенду нужна дополнительная зависимость `browser`. Пусто — предпросмотр возвращает свой отчёт без картинки |
| `VISUAL_MAP_TILES` | (пусто) | Единственный сервер тайлов, на котором [визуал](artifacts.md#visuals) или приложение может рисовать карту: `openstreetmap`, `usgs-topo` или шаблон URL `https://` с `{z}`, `{x}` и `{y}` по одному разу. Экземпляр скачивает каждый тайл и отдаёт его страницам по своему пути тайлов; ни одна страница не обращается к серверу. Без этой настройки новые карты используют встроенные SVG-контуры стран, маркеры и маршруты. Существующие страницы маршрутов могут показывать контур своих остановок. Значение, которое нельзя обслужить, отклоняется при запуске |
| `VISUAL_MAP_TILES_ATTRIBUTION` | (пусто) | Подпись, показываемая под картой на вашем собственном сервере тайлов, например `© OpenStreetMap contributors`. Обязательна вместе с шаблоном URL; у предустановки своя |

**Тайлы карты скачивает экземпляр, а не браузер читателя.** Страница запрашивает
`/api/v1/artifact-content/tiles/{z}/{x}/{y}`; API проверяет числа, скачивает тайл с
сервера, держит в памяти последние 2 048 и отвечает, поэтому ключ в шаблоне никогда не
покидает сервер. Маршрут не принимает сеанс — его загружает каждая страница, — поэтому
он ограничен по адресу (`RATE_LIMIT_MAP_TILES_PER_MINUTE`). Учитывайте условия
провайдера: публичные тайлы OpenStreetMap — для лёгкого использования, и нагруженному
экземпляру стоит запустить свой сервер или платить провайдеру.
**Администрирование → Система** (Admin → System) показывает, отвечает ли сервер.

**`ARTIFACT_ORIGIN` читается дважды, и обе стороны должны его видеть.** Бэкенд
подписывает на нём адреса содержимого, а фронтенд добавляет его маршрут содержимого,
`/api/v1/artifact-content/`, в `frame-src` консоли. Задайте его в окружении бэкенда и в
окружении фронтенда; файлы compose передают его обоим. Значение только в одном из них
даёт пустой фрейм, потому что браузер отказывается загружать страницу с источника,
который консоль не разрешила.

## Наборы данных { #datasets }

Тестовые кейсы, по которым идут оценки. См. [Наборы данных](datasets.md).

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `DATASET_MAX_VERSION_ROWS_PER_ORG` | `5000000` | Ревизии кейсов, которые наборы данных одной организации могут хранить вместе. Каждый добавленный кейс и каждая правка — ревизия, и она хранится для версий, которые её содержат; версия хранит только то, что изменила, поэтому набор из 10 000 кейсов, отредактированный 500 раз, хранит 10 500, а не 5 миллионов. Добавление или правка сверх лимита отклоняется с указанием, сколько уже хранится; удаление кейса ничего не хранит и разрешено всегда, а удаление ненужных наборов освобождает их ревизии. Имя старше этого смысла: оно считало каждый кейс каждой версии, пока версии не перестали копировать свои кейсы. Лимит приблизительный: каждое изменение проверяется само по себе, поэтому изменения, сделанные в один момент в разных наборах, могут немного его превысить. Он защищает хранилище; это не счёт |

**Если `ARTIFACT_ORIGIN` пуст, `PUBLIC_API_URL` фронтенда должен точно совпадать с
`PUBLIC_BASE_URL` бэкенда, включая путь.** Тогда бэкенд подписывает адреса содержимого
на `PUBLIC_BASE_URL`, а `frame-src` консоли называет маршрут содержимого под
`PUBLIC_API_URL`, так что `https://example.com/agenticos` с одной стороны и
`https://example.com` с другой — тот же пустой фрейм.

**Рендерер — собственный браузер, без сети.** Compose поставляет его как включаемый
вручную профиль `artifact-render`: закреплённый headless Chromium во внутренней сети, к
которой подключаются только API и воркер. На каждый запрос, который делает рендер,
отвечает API — страница, её файлы библиотек и документ-хост — или отказ, поэтому
браузеру не нужен выход наружу, а он отрисовывает записи людей, поэтому это не должен
быть браузер, которым управляет [агент с браузером](reference/capabilities.md#browser-automation).
Запустите его командой `docker compose --profile artifact-render up -d`, затем задайте
`ARTIFACT_RENDER_CDP_URL=http://artifact-render:9222`. Не добавляйте `artifact-render` в
`BROWSER_CDP_ALLOWED_HOSTS`: этот список — для агентов с браузером, и записи там
рендереру не нужно. Один процесс рисует две страницы за раз, каждую в пределах 15
секунд.

## Рабочие пространства агентов { #agent-workspaces }

Рабочее пространство `state` здесь ничего не требует. Оно хранится в этой базе,
работает на любом экземпляре и достаётся агенту по умолчанию, поэтому настройки ниже —
только для пространства на контейнере.

| Переменная | По умолчанию | Примечания |
| --- | --- | --- |
| `SANDBOX_STATE_MAX_BYTES` | 32 MiB | На каждое **сохранённое** рабочее пространство. Сверх него запись отклоняется с сообщением, которое читает модель |
| `SANDBOX_INLINE_IMAGE_MAX_BYTES` | 5 MiB | Сверх этого приложенное изображение записывается в рабочее пространство и не отправляется ещё и встроенным |

**Процент в чате — это два разных потолка, и он говорит, какой именно.** Сохранённое
рабочее пространство заполняется до `SANDBOX_STATE_MAX_BYTES` выше — это байты, и
исчерпание _отклоняет запись_. Контейнер сообщает резидентную **память** относительно
потолка, который задал его хост для этой среды выполнения, — `1g`, если список
разрешённых не говорит иного, — и исчерпание этого потолка означает принудительное завершение из-за нехватки памяти, а
не отказ. Поэтому индикатор показывает `workspace 12% full` для первого и
`sandbox memory 12% full` для второго; назвать одно другим значило бы указать лимит,
который здесь не действует.

**Где работают песочницы — не настройка.** Это строка на организацию — «Песочницы» в
консоли, `sandbox_connections` в базе — а токен сервиса лежит в хранилище секретов.
Причин две, и ни одну нельзя выразить переменной окружения: экземпляр может держать
больше одного хоста, а один адрес на экземпляр давал всем организациям один и тот же; и
токен разрешает открыть сеанс, который выполняет команды на хосте с сокетом Docker,
поэтому ему место там, где лежат все остальные учётные данные при хранении.

Оператор регистрирует подключение с именем, адресом и ключом из хранилища секретов.
Агент называет его по id — точно так же, как называет профиль модели, — или не называет
ничего и берёт значение по умолчанию организации, поэтому переезд на другой хост — одна
правка, а не перепубликация каждого агента.

**Токен сервиса стоит столько же, сколько сокет Docker.** Сервис держит этот сокет,
сокет — это неаутентифицированный API для root на хосте, а токен — то, что открывает на
нём сеанс. Никогда в браузере, никогда в журнале, никогда в коммите — поэтому экран
оператора показывает только то, что учётные данные привязаны, и поэтому `GET /policy`
проксируется через этот API, а не запрашивается браузером. Собственная панель сервиса
(`SANDBOXD_UI_ENABLED`) выключен во всех поставляемых файлах compose по той же причине:
он просит человека вставить это значение в браузер.

`SANDBOXD_TOKEN` в `backend/.env` — собственный токен _сервиса_, то, что примет демон из
файла compose.

`make sandbox-token` генерирует его, а форма подключения сама сохраняет то же значение в
хранилище секретов. API читает эту настройку ровно для одной цели: предложить её
хранилищу. Просить человека скопировать секрет из файла, который его собственный стек и
так читает, — трение без всякой пользы.

Он **никогда** не используется, чтобы достучаться до хоста: разрешение подключения
снимает печать с записи хранилища, которую это подключение называет, и это остаётся
единственным путём. Поэтому экземпляр, оставивший его незаданным, теряет одну кнопку и
ничего больше — и вставляет токен вручную.

Та же форма спрашивает, отвечает ли уже какой-нибудь сервис, вместо того чтобы
заставлять оператора знать, что сервис песочниц из `make dev` живёт на
`http://sandboxd:8080`. Этот адрес не конфигурация, и намеренно: это строка, потому что
экземпляр может держать несколько хостов, — поэтому API опрашивает неаутентифицированный
`/healthz` по адресу, который использует файл compose этого проекта, и подставляет то,
что ответило. Опрос ничего не решает: нет сервиса — поле пустое, а подключение, уже
указывающее туда, называется, чтобы никто не зарегистрировал один хост дважды.

**Адрес запрашивает сам этот API, поэтому его и проверяют как адрес, который API вправе запросить.** Регистрация
или опрос подключения заставляют контейнер API выполнить аутентифицированный `GET` и
вернуть тело JSON, а это готовое средство для подделки запросов, если адрес принимается на
веру. Поэтому `base_url` отклоняет всё, что не `http(s)` с хостом, и отклоняет адреса
link-local и имена хостов метаданных экземпляра безоговорочно: `169.254.169.254` и
`metadata.google.internal` никогда не бывают сервисом песочниц.

Частные адреса остаются разрешёнными, и должны: `http://sandboxd:8080` внутри compose и
`http://localhost:8080` для разработчика, запускающего API на своём хосте, — оба
частные, поэтому список запрещённых частных диапазонов отклонял бы экземпляр, который
описывает эта страница. Значит, валидатор сужает дыру, а не закрывает её: имя хоста,
которое разрешается во что-то внутреннее, всё равно пройдёт проверку. **Граница, которая
действительно держится, — это `connections:manage` плюс политика исходящих соединений
контейнера API**: кто может зарегистрировать хост, тому и доверяют этот хост, а экземпляр в сети с неаутентифицированными внутренними API должен говорить об
этом на уровне сети, а не здесь.

### Какие среды выполнения может запросить агент { #which-environments-an-agent-may-ask-for }

Поставляются две среды выполнения. `workbench` (1,93 ГБ) содержит Python 3.12, Node 24,
LibreOffice и библиотеки, нужные агенту, чтобы читать, писать, преобразовывать и строить
графики по файлам, о которых идёт диалог, включая liteparse с OCR. `desktop` — это
рабочий стол Linux с XFCE и Firefox для работы с компьютером. Обе определены в
`backend/app/core/catalog/sandbox_runtimes.json`. Добавить свою — значит отредактировать этот файл и выполнить
`make sandbox-runtimes`, которая записывает `SANDBOXD_RUNTIMES` во все три файла compose;
эта переменная — единственный канал, по которому сервис принимает среды выполнения, и
`PUT /policy` намеренно отклоняет изменение состава списка.

`sandbox.md#which-environments-an-agent-may-ask-for` содержит формат по полям, три
ловушки (первая запись — значение по умолчанию, `network_mode` не наследуется, сборка
оплачивается при старте через `prewarm`) и объяснение, почему сгенерированная копия в
файлах compose не может разойтись с каталогом.

### Собственные настройки сервиса { #the-services-own-settings }

Каждое поле конфигурации сервиса — это `SANDBOXD_` плюс его имя, так что здесь
подмножество, а не весь словарь. Вот те, что задают поставляемые файлы compose или что
решают, переживут ли файлы:

| Переменная | Что задано | Что решает |
| --- | --- | --- |
| `SANDBOXD_WORKSPACE_ROOT` | путь на хосте | Где живёт рабочий каталог каждого сеанса, смонтированный из _хоста_. **Если не задан, файлы существуют только внутри работающего контейнера** — уборка простаивающих сеансов их отбрасывает, и следующий запрос открывает пустое рабочее пространство, и в журнале ничего нет. Это же делает возможным просмотр: чтение рабочего пространства никогда не запускает контейнер |
| `SANDBOXD_SANDBOX_UID` | `10001` | Непривилегированный пользователь, от имени которого работает песочница, вместо root: побег из контейнера начинается с той учётной записи, от имени которой он работает, и каждый файл, который пишет агент, принадлежит на хосте этому uid. **Это должен быть собственный uid сервиса**: открытие сеанса делает `chown` рабочего пространства на этого пользователя, а непривилегированный сервис может сделать это только для себя. Применяется к среде выполнения, которую экземпляр _собирает_, потому что у готового образа такой учётной записи нет, и агент внутри него ничего не смог бы установить |
| `SANDBOXD_CONTAINER_TTL` | 86400s | Сколько хранится _остановленный_ сохранённый контейнер. Освобождает то, что установил сеанс, — сборку, wheel-пакеты, `node_modules` — и оставляет рабочее пространство нетронутым, потому что файлы и есть работа. Если не задано, они хранятся вечно |
| `SANDBOXD_PERSIST_CONTAINERS` | `true` | Контейнер закрытого сеанса сохраняется, а не удаляется, поэтому следующий сеанс на этом рабочем пространстве начинается без сборки. Стоит остановленного контейнера на рабочее пространство; `SANDBOXD_CONTAINER_TTL` это ограничивает |
| `SANDBOXD_MAX_SESSIONS_PER_TENANT` | `5` | Одна организация не может занять весь пул. `SANDBOXD_MAX_SESSIONS` (20) — это пул |
| `SANDBOXD_NETWORK_MODE` | `none` | Сеть по умолчанию для песочницы. `none` — сети нет вообще; среда выполнения может назвать `bridge` для себя |
| `SANDBOXD_UI_ENABLED` | `0` | Собственная панель сервиса. Выключен, потому что просит человека вставить в браузер токен, равносильный root |
| `SANDBOXD_IDLE_TIMEOUT` | 1800s | Сколько живёт простаивающий сеанс, прежде чем его закроют и уберут |
| `SANDBOXD_MEM_LIMIT` | `1g` | Потолок памяти по умолчанию и, значит, то число, долю которого показывает процент `sandbox memory` в чате |

### Запуск сервиса на другом хосте { #running-the-service-on-another-host }

Ничто в подключении не предполагает локальный адрес: это строка с URL и учётными
данными из хранилища секретов, и форма опрашивает то, что ей дали. Хосту в другом месте
нужны три вещи и никакого кода:

1. **Сокет Docker**, потому что сервис запускает контейнеры. Это root на той машине, и
   поэтому токен ниже так и ценен.
2. **`SANDBOXD_WORKSPACE_ROOT` на настоящем диске, смонтированный по одному и тому же
   пути с обеих сторон.** Сервис создаёт каталог и затем просит _демон_ смонтировать
   его, а демон разрешает путь на хосте, поэтому именованный том или путь,
   существующий только внутри контейнера сервиса, отклоняется с `mounts denied`.
3. **TLS и токен, который ни с кем не делят.** Внутри compose адрес —
   `http://sandboxd:8080` во внутренней сети; через интернет это сервис, который выполнит
   команды для любого, у кого есть токен, поэтому ему место за HTTPS и со своим
   собственным значением.

Затем зарегистрируйте его в разделе **Песочницы** (Sandboxes) как любое другое подключение и
укажите на него агенту по имени. Сервис из compose — один экземпляр того же образа.

### Когда сеанс открыт { #when-a-session-is-open }

Вкладка **Работающие** (Running) перечисляет сеансы, которые держит сервис, и
обновляется каждые десять секунд; сеанс — это одно рабочее пространство на одном
хосте. Состояний три, и видны только первые два:

- **running** — контейнер существует и находится в памяти. Открывается первым вызовом
  инструмента агентом в диалоге, а не при запуске диалога.
- **hibernated** — строка есть, а контейнера нет. Сеанс, простаивающий дольше
  `SANDBOXD_EVICT_IDLE_AFTER`, усыпляется, чтобы освободить слот, и следующий запрос
  его будит. Для этого нужен `WORKSPACE_ROOT`: иначе пробуждение открыло бы пустое
  рабочее пространство, и сервис отклоняет такую комбинацию, а не делает это.
- **gone** — по истечении `SANDBOXD_IDLE_TIMEOUT` сеанс закрывается и убирается. С
  `PERSIST_CONTAINERS` контейнер это переживает, поэтому следующий сеанс на том же
  рабочем пространстве начинается без сборки.

Так что пустая вкладка «Работающие» значит, что ни один агент давно не пользовался
оболочкой, а не что ничего не настроено, — а рабочее пространство с файлами и без
сеанса — это обычное состояние покоя.

Сервис работает за профилем compose `sandbox`, который включён по умолчанию в локальной
разработке и выключен в остальных местах, пока оператор его не включит: монтировать
сокет Docker на общем хосте — осознанное действие. `COMPOSE_DEV_PROFILES` в Makefile —
единственное место, где это меняется. `uv run agenticos cmd doctor` проверяет каждое
зарегистрированное подключение: отвечает ли оно, принимает ли свои учётные данные и
разрешает ли вообще какую-нибудь среду выполнения. Отсутствие зарегистрированных
подключений — предупреждение, а не сбой: рабочему пространству `state` подключение не
нужно.

**Просмотр того, что сохранили агенты.** Рабочие пространства — отдельный экран, не часть
«Песочниц», которые про _хосты_.

Каждая строка называет агента, диалог, которому принадлежат файлы (или сколько чатов до
них доходит, если рабочее пространство не принадлежит ни одному диалогу), кто их видит,
сколько они занимают и когда их последний раз использовали.

**Открыть** (Open) ведёт на собственную страницу этого рабочего пространства, в том виде,
что использует редактор навыков: дерево слева — папки раскрываются по одной, а поиск идёт
по всему дереву, а не по папке на экране, — и сам файл, отрисованный рядом. Так чтение
трёх файлов — это три клика, и список никогда не закрывается.

Скачивание — в строке, а не рядом с просмотрщиком, потому что выбор файла читает его, а
большой архив — это то, копию чего хотят получить, не платя за это чтение.

Второй вид списка раскладывает каждый файл, который видит читатель, в одну таблицу —
вопрос «у кого есть копия этого CSV», на который страница одного рабочего пространства
ответить не может.

**Щелчок по файлу открывает его в просмотрщике, и в панели чата просмотрщик тот же.**
Изображение — это картинка, PDF — собственный просмотр PDF браузера, аудио и видео играют
в собственном проигрывателе браузера, markdown предлагает _Просмотр_ (Preview) и
_Источник_ (Source) — оба и есть файл, а `#`, который молча превратился в крупный шрифт, — это способ не заметить, что
агент пишет markdown туда, где ничто не читает markdown, — а всё остальное
показывается текстом. Скачивание есть всегда, в том числе для того, что вообще нельзя
показать. Один компонент — потому что когда «открыть этот файл» значит на двух экранах
разное, второй из них в итоге и упускает случай.

Байты приходят из `GET /sandbox-workspaces/{id}/raw?path=…`, а для панели рядом с чатом —
из `GET /conversations/{id}/workspace/raw?path=…`.

Два маршрута, а не один, потому что они авторизуют разных вызывающих — до маршрута
диалога доходят через получение диалога, поэтому тот, кому чат _открыли_, сохраняет
доступ, — и один модуль решает, что можно показать, поэтому ответ не может отличаться по
месту показа.

Почти всё отдаётся как вложение. **Растровые изображения, PDF, аудио и видео** (MP3, WAV,
Ogg, Opus, M4A, MP4, WebM) отдаются для показа: растровое — потому что не может ничего
выполнить, PDF — потому что браузер отрисовывает его в собственном просмотрщике, который
никогда не получает DOM страницы, а аудио и видео — потому что браузер передаёт их своему
медиаконвейеру, который их проигрывает и ничего не выполняет на странице.

!!! danger "SVG и HTML можно скачать, но нельзя показать"

    SVG, отданный встроенным с этого источника, — это сохранённый межсайтовый скрипт,
    написанный тем, что агент решил сохранить, а «агент это написал» — не граница
    доверия.

Всё остальное помечается типом `application/octet-stream` с
`X-Content-Type-Options: nosniff`, чтобы браузер не мог решить, что такое тело всё-таки
HTML. Имя файла передаётся только как `filename*`, потому что путь рабочего пространства
может содержать любой UTF-8, а простая форма не может об этом сказать.

Произвольные байты может отдавать только **сохранённое** рабочее пространство.
Пространство на контейнере читается через архив рабочего пространства, единственный
читатель которого текстовый, поэтому текстовый файл отдаётся в виде закодированного, а
всё остальное отклоняется, а не тихо портится, — рядом с отказом браузер предлагает
скачать, так что ответ никогда не заходит в тупик.

Файлы читаются только тогда, когда рабочее пространство открывают или когда включают
плоский вид: экземпляр может держать по одному на каждый недавно активный диалог, поэтому чтение
каждого ради отрисовки таблицы было бы запросом на строку ради страницы, по которой ещё
никто ничего не спрашивал. По той же причине плоский вид ограничен и говорит об этом:
сколько рабочих пространств он прочитал, сколько не смог и есть ли ещё. Иначе более
короткий список неотличим от меньшего числа файлов.

**Кто видит какое рабочее пространство, решается для каждого читателя, в запросе.**
Вызывающий с `connections:manage` видит пространства организации — честный порог для
списка, который пересекает чужие чаты. Все остальные видят рабочие пространства, частью
которых они являются: свои файлы с областью `user`, рабочие пространства своих диалогов и
общее рабочее пространство агента, с которым они говорили. «Говорили», а не «могли
открыть», намеренно: область `agent` делит одно рабочее пространство между пользователями
агента, и панель чата уже показывает эти файлы любому в диалоге с ним, так что
_возможность_ открыть агента — более широкое утверждение, чем делает этот список.

Область `channel` видна только оператору, и это правильно, а не упущение: она привязана к
чату Slack или Telegram, поэтому людей, которые её делят, определяет та платформа, а не
строка в `users`.

Рабочее пространство, запрошенное по id, применяет те же три условия и при их
невыполнении отвечает **не найдено**, а не «запрещено»: id не должен служить для того,
чтобы выяснить, какие рабочие пространства существуют в диалоге коллеги. Ничто здесь не
пересекает организацию: администратор платформы, просматривающий файлы другой
организации, был бы тем единственным чтением, которое эта платформа отклоняет, поэтому он
переключает организацию, как и все остальные.

**Рабочее пространство на контейнере читается с хостового тома, а для этого он нужен.**
Сервис песочниц отдаёт эти файлы из `SANDBOXD_WORKSPACE_ROOT`, и именно это позволяет
диалогу с прошлого месяца перечислить свои файлы после того, как его сеанс убрали: чтобы
ответить, контейнер не запускается. Сервис, настроенный _без_ него, ничего не держит на
диске, поэтому его файлы существуют только пока песочница работает, и прочитать их нельзя,
не запустив её: панель **Файлы** (Files) тогда могла бы только сообщить об этом — про
файл, который агент, судя по всему, только что записал.

Поэтому каждый файл compose задаёт этот путь, и его можно переопределить через
`SANDBOX_WORKSPACE_ROOT` — переменную окружения там, где compose её подставляет, то есть в
корне проекта, а не в `backend/.env`, кроме целей `dev` и `prod`, которые передают этот
файл явно.

Один путь на хосте, смонтированный в одно и то же место с обеих сторон, потому что сервис
создаёт каталог и затем просит _демон_ смонтировать его, а демон разрешает путь на хосте.
Именованный том или любой путь, существующий только внутри контейнера сервиса,
отклоняется с `mounts denied`.

|  | По умолчанию |  |
| --- | --- | --- |
| Локальная разработка | `/tmp/agenticos-sandbox-workspaces` | `make dev` создаёт его доступным на запись всем до запуска стека. Docker на Linux, включая Docker Desktop под WSL, создаёт отсутствующий каталог от root, а uid 10001 не может в него писать, и тогда каждая песочница падает с `SANDBOX_START_FAILED`; `make dev` сообщает о таком каталоге и о `sudo chown 10001` + `sudo chmod u+wx`, которые это исправляют |
| Файлы на сервере | `/var/lib/agenticos/sandbox-workspaces` | Должен существовать и быть доступен на запись uid 10001 — `sudo mkdir -p <path> && sudo chown 10001:10001 <path>`, один раз. Не `install -d -o 10001`: `install` разрешает владельца через базу passwd и отклоняет uid, которым не владеет ни одна учётная запись. Ему место на хранилище, для которого кто-то делает резервные копии |

Перезагрузка вычищает `/tmp`, и это единственная причина не направлять туда настоящий
экземпляр.

Об этом сообщают, а не выбрасывают исключение. Каждый список несёт `unreadable_reason`, и
клиент показывает это как объяснение, а не как ошибку, — потому что ни одна из причин не
является сбоем: сервис, ничего не держащий на диске, — это конфигурация с правкой в одну
строку, которую сообщение и называет, а упавший хост поднимется позже.

Исключение превращало это в ответ 500, которое браузер мог показать только как «что-то пошло не
так», рядом с пустым списком, который читается как «файлов нет». Два неверных ответа
сразу.

Чтение _одного файла_ с такого хоста отклоняется той же фразой, а не сообщается как «нет
такого файла», что сказало бы, что файла нет, хотя он есть.

**Что работает, тоже читается из сервиса.**

Экран «Песочницы» держит это на отдельной вкладке, отдельно от таблицы подключений, и
перечисляет открытые песочницы этой организации на хосте, который называет, — подключение
по умолчанию, пока оператор не выберет другое.

Каждая строка несёт среду выполнения, то, что делит эту песочницу, время простоя и — по
запросу — память относительно её собственного потолка. Сортировка по времени простоя и
памяти. Рядом — журнал активности по каждой песочнице: какие пути читались, какие команды
выполнялись и как прошла каждая.

Сервис не записывает ни содержимое файлов, ни вывод команд, и именно это не даёт журналу
аудита превратиться в способ прочитать работу другого агента.

Страница «Обзор» отвечает на те же три вопроса в своём разделе — для вызывающего с
`connections:manage`. Память там за переключателем по той же причине, что и на экране:
сервис замеряет её для каждой песочницы отдельно.

**Теперь делятся все три потолка.**

Список сеансов фильтруется по организации вызывающего, но `SANDBOXD_MAX_SESSIONS` и
`SANDBOXD_MAX_OPEN_SESSIONS` проходят из сервиса без изменений, поэтому эти два считают
все организации на хосте, а строки — одну. `len(sessions)` делится только на
`SANDBOXD_MAX_SESSIONS_PER_TENANT`.

Поэтому ответ несёт два числителя по всему хосту для другой пары, взятые из
нефильтрованного списка до того, как фильтр его сузит:

- `host_session_count` — резидентные песочницы, которые сервис помечает
  `state == "running"`, против `limit`;
- `host_open_count` — каждый существующий сеанс, резидентный или усыплённый, против
  `open_limit`.

Теперь карточка ёмкости может сказать, почему сеанс отклонён, хотя эта организация далека
от своего потолка: сам хост полон чужой работы.

То, что эти два — по всему хосту, — намеренное и узкое раскрытие: два агрегатных целых,
ничего не называющих, далеко от строк сеансов, которые фильтр скрывает, — а список закрыт
за `connections:view`, правом наблюдать за хостом, а не полномочием участника.

На подключении Daytona они `None`: оно не применяет ни одного нашего потолка, на который
можно делить.

Этот список **фильтруется, а не пересылается**. Один `sandboxd` отвечает за все
организации, зарегистрировавшие подключение по его адресу, поэтому пересылка его ответа
показала бы одной организации контейнеры другой. Сеансы сопоставляются по метке `tenant`,
которую эта платформа ставит при открытии сеанса, и называются по `agent_workspaces`, а не
через декодирование id сеанса: id кодирует ключ области, и его разбор сделал бы этот
формат схемой.

**Что разрешает сервис, читается из сервиса.** Список разрешённых сред выполнения и
потолок за каждым псевдонимом (`SANDBOXD_RUNTIMES`, `SANDBOXD_MEM_LIMIT`,
`SANDBOXD_NETWORK_MODE`, `SANDBOXD_MAX_SESSIONS_PER_TENANT` и остальные) — его собственная
конфигурация загрузки, и эндпоинта для их записи намеренно нет: браузер, который мог бы
перенастроить процесс, держащий сокет Docker, владел бы хостом. Экран «Песочницы» и
карточка сред выполнения на странице «Обзор» их _читают_, чтобы было видно, что действует, а
Конструктор предлагает агенту только те псевдонимы, которые сервис действительно примет.

Ни один из этих экранов не спрашивает у подключения Daytona ничего такого. Оно не публикует
собственного списка разрешённого и не держит наших сеансов, которые можно перечислить: то,
что оно разрешает, — настройка той учётной записи, а что там работает, видно на его
собственной панели.

## Голосовые звонки { #voice-calls }

[Голосовые звонки](voice.md) включаются в каждом агенте и ограничены
максимальной длительностью его звонка и бюджетами. Два потолка задаёт сам
экземпляр:

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `VOICE_MAX_CALLS_PER_USER` | `1` | Сколько звонков один человек может держать одновременно. Звонок из второй вкладки почти всегда ошибка, и каждый оплачивается; второй запуск отклоняется как `busy` |
| `VOICE_MAX_CALLS_PER_EMBED` | `3` | Сколько звонков могут одновременно держать один виджет или одна размещённая страница — все посетители вместе; следующий отклоняется как `line_busy`. У посетителей нет учётной записи, на которую можно отнести счёт, поэтому именно это мешает утёкшей ссылке параллельно тратить бюджет организации |

Оба предела считают звонки, у которых сигнал активности свежий, поэтому звонок, процесс
которого умер, перестаёт учитываться в течение 45 секунд. Запуск звонков в виджете для
встраивания тоже подпадает под лимит частоты (`RATE_LIMIT_EMBED_VOICE_*`,
[ниже](#rate-limiting)). Собственный `rate_limit_per_minute` встраивания,
заданный в Конструкторе, считает **сообщения** посетителя, а не запуски звонков,
поэтому звонки он не ограничивает.

Остальное зафиксировано в коде, а не настраивается: звонок никогда не длится
дольше 50 минут, сигналы активности отправляются каждые 15 секунд, а очистка
голосовых звонков выполняется каждую минуту — как расписание `reap-voice-calls`
у воркера.

## Лимит частоты { #rate-limiting }

Действует для тех способов доступа, до которых может добраться посторонний, и
только для них: публичный API запуска, скрипт виджета, его конфигурация,
рукопожатие сокета на обоих способах доступа, конфигурация и логотип
размещённой страницы, а также загрузка, диктовка и голосовой звонок посетителя.
Собственные маршруты консоли закрыты сеансом и не учитываются, с одним
исключением: записи в [виртуальные таблицы](virtual-tables.md), которые хранят
снимок при каждом изменении. Стоит ли покрывать потолком всё API — отдельное
решение, не это.

**Что получает отклонённый вызывающий** — собственный формат ошибки этого API с
`code: "RATE_LIMIT_EXCEEDED"`, интервалом в `error.details.retry_after_seconds` и
тем же интервалом в заголовке `Retry-After` — именно на него на самом деле
ориентируется обёртка над fetch или CDN, выдерживая паузу. Исключение — рукопожатие сокета: у
WebSocket нет статуса, которым можно ответить, поэтому он закрывается кодом
`4029` (см. [каналы](channels.md#the-raw-websocket)).

**Два счётчика, а не один, и причина арифметическая.**

Загрузка страницы с виджетом стоит трёх запросов к этому API: скрипт,
конфигурация и сокет. Если считать их вместе, `20` давали холодному браузеру
около семи загрузок страницы вместо двадцати допусков — а лимит, ошибочный
втрое, хуже отсутствия лимита, потому что читается как число, которое вы задали.

Поэтому у `widget.js` свой отдельный счётчик. Он кэшируется, и отказ здесь ломает виджет
целиком, а не задерживает одно сообщение.

Конфигурация и рукопожатие остаются вместе, потому что вдвоём они _и есть_ один
допуск: браузер, который прочитал конфигурацию и не открыл сокет, внутрь не
попал.

Счётчики живут в Redis экземпляра, поэтому сохраняются между воркерами — в
production их четыре, и счётчик на процесс пропускал бы вчетверо больше, чем
говорит. Если Redis недоступен, лимит не применяется, а в журнал пишется
предупреждение: отказать посетителю в ответе из-за сбоя кэша — худший из двух
сбоев.

Сколько посетитель может _сказать_, будучи допущен, — другое число: оно задаётся
для каждого виджета в Конструкторе (`rate_limit_per_minute`) и считается на
посетителя. Эти два — потолок на вход.

### `RATE_LIMIT_HOSTED_PAGE_PER_MINUTE`, и почему он не на адрес { #rate_limit_hosted_page_per_minute-and-why-it-is-not-per-address }

Конфигурацию размещённой страницы загружает **на стороне сервера** фронтенд,
чтобы страница с первого кадра рисовалась в фирменном оформлении. Значит, адрес
в запросе — это адрес контейнера фронтенда, а не посетителя, поэтому из-за счёта
по нему каждая загрузка размещённой страницы во всём экземпляре попадала в один
счётчик, а посетитель, который его исчерпал, получал 404 без всякого объяснения.
`RATE_LIMIT_TRUST_FORWARDED_FOR` тут не поможет: серверный `fetch` такого
заголовка не отправляет, и доверять нечему.

Поэтому этот счётчик ведётся на публичный ключ. Он ограничивает одну страницу, а
не нормирует посетителя, — оттого значение по умолчанию широкое: **расходы
ограничивает не он.** Расход начинается с сокета, который страница открывает
следом и который открывает браузер, а он считается на адрес в рамках
`RATE_LIMIT_EMBED_PER_MINUTE`. А угадывание ключа — не стратегия против 192 бит
`secrets.token_urlsafe`.

### `RATE_LIMIT_AUTH_PER_MINUTE`, и почему у аутентификации собственный лимит { #rate_limit_auth_per_minute-and-why-the-auth-surface-has-its-own }

Каждый маршрут в `auth.py` несёт этот лимит, считаемый **на IP** и — там, где
тело несёт адрес (вход, регистрация, запросы сброса и ссылки для входа), — **ещё
и на отправленный адрес**, оба в пределах этого лимита. Эти двое отражают разные
атаки: IP ограничивает поток из одного источника, адрес — перебор по одной
учётной записи.

Он отдельный и ниже, чем лимит на запуски, потому что он защищает именно стоимость
**одной попытки**. `verify_password` — это bcrypt, ~170 мс без точек
приостановки, поэтому неограниченный поток на `/login` для любого адреса, у
которого есть учётная запись, насыщает цикл событий воркера вообще без учётных
данных.

Ещё две вещи закрывают остальное в этой области и не требуют настройки:

- bcrypt выполняется в потоке, поэтому никогда не блокирует цикл;
- адрес **без** учётной записи проверяется по фиктивному хэшу, а не пропускается,
  поэтому известный и неизвестный адрес отклоняются за одинаковое время и время
  ответа больше не выдаёт, какие адреса существуют.

### `RATE_LIMIT_TRUST_FORWARDED_FOR`, и почему он выключен { #rate_limit_trust_forwarded_for-and-why-it-is-off }

Лимиты на адрес считают `request.client.host`. **За прокси или CDN это адрес
прокси, а не посетителя** — все посетители делят один счётчик, поэтому загруженный
сайт за Cloudflare исчерпывает двадцать допусков виджета в минуту сразу для
всех. Если включить эту настройку, вместо него читается **самый правый** переход
`X-Forwarded-For` — адрес, который дописал сам доверенный прокси.

По умолчанию она выключена, потому что заголовок задаёт тот, кто вызывает. При
безусловном доверии лимит на адрес превращается в лимит на заголовок, который
любой обходит, меняя одну строку.

**Самый правый** переход читается, а не самый левый, по той же причине:
`X-Forwarded-For` — список, который начинает клиент и дописывает каждый прокси,
поэтому начало — это то, что набрал клиент, и только хвост — то, что написал
подконтрольный вам прокси.

**Аутентификации это тоже нужно, и фронтенд теперь это позволяет.**
Запросы аутентификации доходят до API на стороне сервера через собственные
маршруты фронтенда `/api/auth/*`, поэтому без этой настройки их адрес — адрес
контейнера фронтенда, и половина `RATE_LIMIT_AUTH_PER_MINUTE`, считающая по IP,
складывает весь экземпляр в один счётчик: примерно одиннадцать входов — и все
заперты на минуту, а исчерпанный счётчик обновления завершает сеансы. В отличие от
загрузки конфигурации размещённой страницы, эти маршруты **пересылают
`X-Forwarded-For` вызывающего**
([#1047](https://github.com/vstorm-co/agenticos/issues/1047)), поэтому при
включённой настройке лимит считается по настоящему клиенту. Включайте её для
лимита аутентификации по тому же правилу, что и для всего остального — один
подконтрольный вам прокси впереди, дописывающий клиента самым правым переходом:
именно такое решение о развёртывании и воплощает эта настройка; выключенная, она
остаётся безопасной, но общей.

!!! danger "Включайте её, только если единственный, кто может достучаться до API, — один подконтрольный вам прокси"

    Если порт контейнера тоже опубликован, вызывающий задаст заголовок сам, и
    лимит перестанет что-либо значить.

    **Порт фронтенда здесь считается портом API.** Его маршруты `/api/auth/*`
    пересылают любой полученный `X-Forwarded-For`, поэтому вызывающий, который
    может достучаться до порта 3000 в обход прокси, выбирает адрес, на который
    засчитываются его попытки входа, столь же уверенно, как и тот, кто может
    достучаться до порта 8000, — а каждая принятая попытка по ничейному адресу
    всё равно стоит одного bcrypt. Поэтому и `docker-compose-prod.yml`, и
    `docker-compose-prod.frontend.yml` по умолчанию публикуются на `127.0.0.1`,
    куда до них добирается обратный прокси хоста и больше никто.
    `BIND_HOST=0.0.0.0` снова их открывает — для прокси, который действительно
    работает в другом месте, и тогда обещание держит собственная сеть этого
    прокси.

    Если впереди два прокси, схлопните заголовок до одного перехода на своей
    границе — доверять можно только последнему переходу.

## Лимиты и хранение виртуальных таблиц { #virtual-tables-limits-and-retention }

Что одна организация может хранить в
[виртуальных таблицах](virtual-tables.md#limits-and-retention) и как долго
хранятся копии, которые оставляет после себя запись. Запись сверх лимита
отклоняется с `QUOTA_EXCEEDED` (402) и записью в аудите, где названа квота, а
содержимое — никогда.

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `TABLES_MAX_PER_ORGANIZATION` | `200` | Таблиц на организацию. Архивные считаются, потому что ничто не удаляет таблицу |
| `TABLES_MAX_RECORDS_PER_TABLE` | `100000` | Записей в одной таблице |
| `TABLES_MAX_RECORD_BYTES` | `1000000` | Сериализованный размер значений одной записи в байтах. Минимум `1`. Он же ограничивает объём, который держат строка истории создания, строка истории удаления и квитанция; запись, уже превысившая лимит, всё равно удаляется, сохраняя вместо значений маркер с числом байт |
| `TABLES_MAX_STORAGE_BYTES_PER_ORGANIZATION` | `1073741824` | Байты полезной нагрузки JSONB, хранимой в PostgreSQL, на организацию — по записям, истории, квитанциям и исходящей очереди; физические накладные расходы таблиц и индексов отдельны |
| `TABLES_RECEIPT_TTL_HOURS` | `24` | Сколько времени квитанция идемпотентности отвечает на повтор. После этого тот же ключ — новая запись |
| `TABLES_OUTBOX_RETENTION_DAYS` | `3` | Сколько хранится отправленная строка исходящей очереди |
| `TABLES_OUTBOX_UNDISPATCHED_RETENTION_DAYS` | `30` | Сколько хранится неотправленная строка исходящей очереди. Сигнал активности [триггера таблицы](virtual-tables.md#triggers) отмечает каждую строку, которую он проверяет, поэтому строка такого возраста значит, что воркер был недоступен всё это время. Это порог для недоставленных событий, а не утверждение, что событие доставлено: после него строки нет, и по этой записи не запустится никакой триггер |
| `TABLES_HISTORY_RETENTION_DAYS` | `365` | Сколько хранится история записи, считая от изменения, в том числе для удалённой записи |
| `TABLES_MAX_CONCURRENT_QUOTA_AUDITS` | `4` | Сколько записей аудита об отказе по квоте этот процесс пишет одновременно, чтобы всплеск отказов не открыл неограниченное число подключений к базе данных. Остаток всплеска ждёт этого предела |

Три срока хранения применяет ежедневная
[уборка по срокам хранения](governance.md#retention) для каждой организации; это
не настройки отдельной организации.

Бюджет уборки на один проход для этих трёх классов масштабируется по
`RATE_LIMIT_TABLE_WRITES_PER_MINUTE`, а не задаётся фиксированным числом партий, —
но этот лимит считается на _участника_ (`limit_table_write` считает записи
каждого участника по его собственному лимиту), поэтому бюджет масштабируется и
по числу активных участников организации: до
`RATE_LIMIT_TABLE_WRITES_PER_MINUTE * 60 * 24` строк на активного участника в
день, партиями по 500.

Это число удваивается для запаса, чтобы уже существующая очередь сокращалась, а
не просто держалась на месте, и ограничивается величиной для 50 участников,
чтобы одна необычно большая организация не могла растить свой проход без
предела — он всё равно разгружается, просто за большее число проходов, как и
любой другой класс хранения, когда накопленное перерастает его бюджет.

## Воркер, у которого перестал крутиться цикл событий { #a-worker-whose-event-loop-has-stopped-turning }

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `EVENT_LOOP_WEDGED_AFTER` | `15` | Сколько секунд цикл событий может не проворачиваться, прежде чем воркер будет принудительно завершён и заменён. `0` или меньше отключает проверку |
| `UVICORN_WORKER_HEALTHCHECK_TIMEOUT` | `60` | Сколько секунд супервизор uvicorn ждёт ответа воркера на свой пинг, прежде чем заменить его, если `--workers` больше 1. Читают compose-файлы, а не приложение |

Воркер, который _жив, но не отвечает_, — завис на блокировке, крутится в
синхронном вызове, заблокирован на сокете, который никогда не ответит, — не
имеет кода выхода, поэтому каждый путь восстановления в каждом стеке считал его
здоровым, пока запросы истекали по таймауту. Контейнер становится
`unhealthy`, а статус — не механизм.

Поэтому воркер сам судит свой цикл событий. Колбэк таймера ставит отметку на
цикл раз в секунду; поток читает отметку, и если цикл не проворачивался
`EVENT_LOOP_WEDGED_AFTER` секунд на протяжении двух проверок подряд, он завершает процесс —
`SIGKILL` или `os._exit(137)`, когда воркер — это PID 1, потому что ядро не
доставляет сигнал init пространства имён, если у init нет для него обработчика. В
любом случае `docker inspect` сообщает `137`, и состояние «завис», с которым ничего не
справлялось, становится состоянием «исчез», с чем справляется каждый стек:

| Стек | Что заменяет воркер |
| --- | --- |
| `docker-compose.yml` | супервизор перезагрузки на следующем опросе |
| `docker-compose-dev.yml` | PID 1 — это сервер, поэтому контейнер завершается и срабатывает `restart: unless-stopped` |
| `docker-compose-prod.yml` | `Multiprocess` uvicorn — примерно за полсекунды; остальные три воркера продолжают обслуживать |

Две особенности — причина такой конструкции, и обе стоит знать, прежде чем менять
число:

- **Он проверяет, жив ли процесс, а не готов ли он.** Отметку ставит колбэк таймера, а не
  запрос, поэтому медленная база данных или провайдер модели, отвечающий двадцать
  секунд, — не зависание: цикл проворачивается, он ждёт. HTTP-проба была бы проще
  по устройству, но она зациклила бы перезапуски здорового сервера из-за сломанной
  зависимости.
- **Две проверки, а не одна.** `docker pause`, замороженная cgroup и ноутбук,
  просыпающийся от сна, останавливают сторож не хуже, чем сам цикл,
  поэтому первая проверка после этого читает устаревшую отметку, которая ничего
  не говорит.

Супервизор перезагрузки локального стека читает ту же переменную для суждения,
которое он выносит _снаружи_ воркера, поэтому одно число покрывает оба случая.

!!! tip "Задайте `0`, пока отлаживаете"

    Точка останова блокирует цикл событий, и ничто не отличит это от
    взаимоблокировки, поэтому воркер, остановленный на точке останова, иначе будет
    принудительно завершён прямо во время вашей отладки.

Он не видит процесс, который вообще не выполняется, — `kill -STOP`, замороженная
cgroup, — потому что сторож внутри остановленного процесса тоже остановлен. Этот
случай уже покрывают супервизоры: сигнал супервизора перезагрузки устаревает, а
пинг через канал в production остаётся без ответа.

Этот пинг ждёт `UVICORN_WORKER_HEALTHCHECK_TIMEOUT` секунд, по умолчанию 60.
Собственное значение uvicorn по умолчанию — 5, а хост, которому не хватает CPU, —
украденное время CPU на общем VPS, сборка образа, накопившиеся запуски сценариев, — пропускает
5 секунд с воркерами, которые живы и обслуживают.

Тогда супервизор завершает их и их замены, не дав тем закончить импорт
приложения, и каждый перезапуск добавляет к нагрузке, которая его вызвала, ещё
стоимость импорта по CPU. В журнале это выглядит как `Child process [N] died` без
единой строки сторожа над ней. Поскольку заблокированный цикл — дело сторожа,
пингу достаточно заметить остановленный процесс, и минуты для этого вполне
хватает.

| `ACME_EMAIL` | `admin@example.com` | Почта для сертификатов SSL от Let's Encrypt |

Строчные буквы, цифры и дефисы, не более 48: cookie сеанса становятся `agenticos_<namespace>_access_token` и `agenticos_<namespace>_refresh_token`. ## Контрольный список для production { #production-checklist }

!!! danger "Каждая из этих настроек поставляется со значением по умолчанию, неверным в production"

    В экземпляре, доступном откуда-либо ещё, все девять заданы осознанно.

- [ ] `SECRET_KEY` — уникальный 64-символьный hex-ключ: `openssl rand -hex 32`
- [ ] `API_KEY` — уникальный ключ: `openssl rand -hex 32`
- [ ] `VAULT_MASTER_KEY` — уникальный ключ: `openssl rand -hex 32`. Конфигурация
      отклоняет пустое значение вне `local`/`development`
- [ ] `ENVIRONMENT` — `production`
- [ ] `DEBUG` — `false`
- [ ] `POSTGRES_PASSWORD` — надёжный уникальный пароль
- [ ] `REDIS_PASSWORD` — надёжный пароль
- [ ] `CORS_ORIGINS` — только ваши настоящие домены фронтенда

Почты в этом списке намеренно **нет**: экземпляр работает и без неё. Но
приглашения, сброс паролей и уведомления молча не отправляются, пока `SMTP_HOST`
и остальные настройки [почты (SMTP)](#email-smtp) не указывают на настоящий
сервер, — поэтому экземпляр, который её пропускает, должен пропускать её
сознательно.

## Диагностика экземпляра { #diagnostics }

`DIAGNOSTICS_ENABLED` по умолчанию равно `true`, в том числе при обновлениях, где
в существующем `.env` его нет. Чтобы отключить отправку, задайте
`DIAGNOSTICS_ENABLED=false` в окружениях бэкенда и фронтенда и перезапустите
сервисы. Страница настроек платформы показывает состояние и последний успешный
отчёт; переключателя на ней нет.

`DIAGNOSTICS_COLLECTOR_URL` — адрес сборщика для сервера;
`DIAGNOSTICS_PUBLIC_URL` — адрес, доступный из браузера, его же читает
фронтенд для своей политики безопасности содержимого. Оба по умолчанию равны
`https://analytics-agenticos.testapp.ovh`. Для локально запущенного сборщика,
доступного из Docker Desktop, используйте `http://host.docker.internal:8010` как
адрес сервера, а публичный адрес оставьте `http://localhost:8010`. Удалённые
адреса требуют HTTPS. Не включайте пути, учётные данные и строки запроса.

Существующий постоянный воркер отправляет данные раз в час. Его seed Ed25519
запечатан в хранилище секретов, сохраняется до первого сетевого вызова,
разделяется репликами и переупаковывается командой `vault-rotate`. Отсутствующий
сборщик не блокирует вход, чат или запуск воркера. Отчёты содержат версию,
состояние базы данных и воркера, явное «неизвестно» о состоянии Redis, число
запусков за 30 дней и число созданных проектов, навыков и документов по
диапазонам. За пределы экземпляра уходят только названия функций из закрытого
перечня. Ошибки — это сгруппированные неудачные запуски, задачи без повторов и
неудачная индексация за последний полный час UTC, не более 1 000 на категорию.
Свободные тексты исключений API не экспортируются.

Активность на переднем плане в веб-приложении, приложении для компьютера и
мобильном приложении использует подписанные 60-секундные утверждения для
аутентифицированной учётной записи. Вместо идентификатора учётной записи
подставляется псевдоним, привязанный к экземпляру. Видимые окна в фокусе
отправляют отчёт после взаимодействия и не чаще раза в пять минут; фоновые или
простаивающие вкладки не держат пользователя в сети. Браузер отправляет
утверждение напрямую, без cookie и referrer, что позволяет сборщику
приблизительно группировать по стране и региону. Ни промпты, ни диалоги, ни имена
файлов, ни имена учётных записей, ни адреса почты, ни ключи провайдеров, ни
тексты исключений не отправляются.

Сопутствующий [сборщик аналитики](https://github.com/vstorm-co/agenticos-analytics)
хранит сырые события семь дней, а ежедневную псевдонимную активность и агрегаты —
90 дней. «В сети» значит активность за последние десять минут; «активный
экземпляр» значит контакт за последние 24 часа. Отсутствие контакта значит
«неизвестно», а не подтверждённый сбой. Код сборщика не хранит IP-адреса и
координаты GPS; хранение журналов доступа прокси — ответственность оператора.
Отдельный деморежим сборщика показывает карту на синтетических данных; AgenticOS
никогда не наполняет диагностические записи production.

## Обновления из панели администрирования { #updates-from-the-administration-panel }

Страница «Платформа» ссылается на список изменений последнего выпуска и
показывает состояние подготовки, планирования и восстановления обновлений.
Обновления включаются по желанию: установите помощник хоста один раз в
поддерживаемом однохостовом развёртывании Linux/systemd Compose, затем подключите
API и воркер через оверлей обновления. См.
[руководство по настройке и восстановлению для оператора](https://github.com/vstorm-co/agenticos/tree/main/deploy/updater).

Подготовка проверяет конфигурацию и место на диске, скачивает и закрепляет
опубликованные образы и делает предварительную резервную копию, не перезапуская
приложение. Примените сразу или запланируйте в пределах семи дней. Помощник
приостанавливает приём, ждёт активные запуски, задачи и звонки, останавливает
запись со стороны приложения, делает окончательную резервную копию PostgreSQL,
медиафайлов и конфигурации, выполняет миграции и проверяет готовность, прежде чем
снова открыть трафик. Прогресс переживает перезапуски приложения; панель
переподключается, когда API снова становится доступен.

Сбой после начала миграции оставляет обслуживание включённым для восстановления
оператором; автоматического отката базы данных нет. Резервные копии остаются на
хосте, пока оператор их не удалит, и не заменяют копии вне хоста. Проверьте
восстановление на одноразовом экземпляре, прежде чем включать обновления в
production. Несколько хостов, собственные оверлеи Compose и внешнее хранилище —
вместо этого используйте свой конвейер: `UPDATE_PIPELINE_URL` открывает свою
HTTPS-ссылку, не запуская развёртывание.

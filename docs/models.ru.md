# Модели и провайдеры { #models-and-providers }

!!! tip "Решить, а не настроить?"

    Эта страница — про механику. [Выбор модели](choosing-models.md) отвечает,
    *какую* модель должен использовать агент — закрытую или с открытыми весами,
    что на самом деле формирует счёт и почему выбор можно изменить.

Шаблон, из которого выросла эта платформа, собирал одну модель из переменных
окружения.

Это перестаёт работать, как только один экземпляр делят несколько организаций:
каждой нужен свой ключ, своя модель по умолчанию и возможность сменить и то и
другое без повторного развёртывания.

Поэтому модель собирается **за запуск**, из базы данных:

```
model profile → credential → unsealed secret → provider client → Model
```

Ничего о том, какую модель использует агент, не хранится в `.env`.

## Личные ключи модели { #personal-model-keys }

В разделе **Доступ к модели** (Model access) Конструктора оставьте **Использовать
ключ организации** (Use the organization’s key) — так по умолчанию — или выберите
**Каждый пользователь подключает свой ключ** (Each user connects their own key).
Личный режим держит модель и эндпоинт администратора фиксированными. Он
поддерживает чат-провайдеров с API-ключом, но без резервных моделей и без смены
модели внутри диалога.

Вошедший в систему участник открывает агента в веб-чате и подключает свой ключ
через личную форму над полем ввода или в элементах управления чата. Ключи никогда
не попадают в сообщения, промпты или инструкции агента. Одно и то же подключение
используется всеми агентами организации с тем же провайдером и тем же
эндпоинтом. Отсутствующий ключ блокирует запуск до запроса к модели; ошибка
аутентификации никогда не переключает на ключ организации. Замените ключ в
настройках чата или удалите подключение в разделе **Секреты → Ваше подключение к
модели** (Vault → Your model connection). Сохранение ключа не проверяет его у
провайдера.

Форма личного ключа отправляет именно тот профиль, провайдера, эндпоинт и
модель, которые показаны пользователю. Если назначение изменится до сохранения,
сервер отклоняет ключ с конфликтом; форма перезагружает назначение и очищает
введённый ключ перед новой попыткой.

Сейчас личный режим исключает каналы (частные и групповые), виджеты, размещённые
страницы, запуски через HTTP API, расписания, триггеры, фоновые темы, голос,
проверяющих и отдельные модели возможностей. Прежде чем опубликовать этот режим,
приостановите или удалите активные каналы, публичные способы доступа и
автоматизации. Создание или повторная активация несовместимого способа доступа
отклоняется, и среда выполнения применяет то же правило. Размещённые страницы и
JWT виджетов не определяют вошедшего в систему участника экземпляра.

Делегирование поддерживается в веб-чате для вошедших пользователей. Субагент
личного режима должен использовать ровно тот профиль модели, который выбран у
корневого агента личного режима. Родитель в режиме организации не может тратить
личные ключи, а личный агент-исполнитель не может выбрать другую модель или
эндпоинт. Эти ограничения проверяются при публикации, при допуске способа
доступа, при переводе в окружение и во время выполнения, включая вложенные
делегирования и продолжение после согласования.

Агенты-исполнители в режиме организации сохраняют свои учётные данные. Встроенные
специалисты наследуют режим родителя; динамические специалисты в личном режиме
остаются на модели, настроенной у родителя. Личный доступ к MCP сохраняет
существующие границы вызывающего.

Если у субагента нет подключения, сообщение называет агента и подключение к
модели. Откройте настройки чата этого агента, чтобы подключить свой ключ; если
подключение не видно, попросите владельца агента открыть доступ. Механизм
выполнения проверяет дерево делегирования перед вызовами модели и повторно при
продолжении. Ключ для другого эндпоинта, ключ другого участника или ключ
согласующего никогда не заменяют отсутствующее подключение вызывающего.

Учётные данные шифруются в хранилище секретов для своего владельца и удаляются
вместе с его членством или учётной записью. Смена одобренного эндпоинта
требует нового подключения. Замена ключа одного участника не меняет ключ другого
участника и общий профиль модели.

Вход от имени другого пользователя никогда не даёт доступа к его личным
подключениям к модели: запросы на просмотр, изменение или использование его ключа
отклоняются до обращения к хранилищу.

История личных диалогов следует за одобренными назначениями модели, включая
резервные; о переключении подключений и продолжении ожидающих запусков см.
[историю чата](console.md#chat).

## Профиль модели { #a-model-profile }

Строка в организации: название, провайдер, идентификатор модели, настройки по
умолчанию и [секрет в хранилище](secrets.md), которым проходить аутентификацию.

Спецификация агента указывает профиль через `model_profile_id`, и запуск
разрешает его.

!!! tip "Идентификатор модели — свободный текст намеренно"

    Есть список выбора для удобства, но поле принимает всё, что вы введёте.

    Провайдер выпускает новинку наутро после того, как любой здешний список
    прогрелся, а поле, не умеющее выразить «вон ту», люди обходят правкой
    спецификации вручную.

### Профиль, на котором агент не может работать { #a-profile-an-agent-cannot-run-on }

Профиль может указывать модель, которая не умеет вести диалог: модель синтеза
речи, например `gpt-4o-mini-tts`, модель голоса в реальном времени, модель
транскрипции, модель изображений, модель видео или модель эмбеддингов. Агент на
такой модели падает на первом же ходе. Синтез речи, генерация изображений и
транскрипция не используют профили: каждая функция указывает своего провайдера и
свою модель.

Платформа знает такие модели из собственных каталогов (списки голоса в реальном
времени, синтеза речи, транскрипции, изображений, видео и эмбеддингов).
`GET /providers/model-profiles` помечает каждый профиль полями `chat_capable` и
`output_modalities`, а `GET /providers/{provider}/models` помечает каждое
предложение полем `chat_capable`. Эти два поля также читают список провайдера,
где сказано, что выдаёт каждая модель (так делают OpenRouter и роутер Hugging
Face), если процесс API уже его загрузил. Такой список меняет только то, что
предлагает список выбора. Он никогда не отклоняет публикацию, потому что другой
процесс API мог его не загрузить. Консоль также обновляет сохранённые профили,
когда список появляется позже. Псевдонимы провайдеров, такие как `openai_codex` и
`google_cloud`, используют каталоги соответствующего вендора. Далее:

- Панель модели в Конструкторе, списки выбора для проверяющего и специалистов,
  поля модели для последующих сообщений и шага браузера, а также список выбора
  для описания изображений в базе знаний такую модель не предлагают. Если агент
  уже указывает её, Конструктор всё равно её показывает с пометкой «не чат-модель».
  Участнику, который может управлять подключениями, Конструктор также перечисляет
  остальные — помеченными и недоступными для выбора, чтобы их можно было удалить.
- Список выбора модели в чате и форма добавления модели в Конструкторе такую
  модель не предлагают и отклоняют её, если её ввести.
- Публикация отклоняет такую модель в роли модели агента, проверяющего,
  специалиста, модели шага браузера или модели последующих сообщений и называет
  её. Она также отклоняет профиль, среди резервных моделей которого есть такая. Та
  же проверка выполняется при откате, при проверке черновика, при тестовом запуске
  в Конструкторе и при включении возможности из чата. Сохранённая версия на такой
  модели по-прежнему загружается, но её нельзя восстановить, пока её профиль
  указывает модель, не умеющую вести диалог, или перечисляет такую среди резервных.
  Переведите этот профиль на чат-модель или опубликуйте новую версию.
- Запуск исключает такую резервную модель из своей цепочки — как и удалённую, —
  если её добавили в профиль после публикации.
- Диалог, который указывает такую модель вместо модели самого агента, из чата или
  через API, отклоняется до начала запуска.
- Модель, которую каталоги не классифицируют, например модель Ollama или
  выпущенная сегодня утром, разрешена. Неизвестная модель — не повод для отказа.
  Профиль со своим эндпоинтом (`base_url`) не классифицируется никогда, каким
  бы ни был идентификатор модели: каталоги описывают собственный API провайдера, а
  OpenAI-совместимый сервер может отдавать чат-модель под любым именем.

Список выбора модели для проактивности подчиняется тому же правилу. Проверка по
стабильному каталогу также выполняется при настройке проактивности и всякий раз,
когда профиль разрешается для обычного текстового запроса, включая описание
изображений при настройке и в воркере. Старые конфигурации по-прежнему
загружаются; замените несовместимую модель, прежде чем ими пользоваться.
Отключить проактивность по-прежнему можно. Имена развёртываний Azure не
классифицируются по идентификаторам базовых моделей из каталога.

### Модель, на которой стартует новый агент { #the-model-a-new-agent-starts-on }

Модели по умолчанию для всей организации нет. Спецификация агента называет свою
модель, а публикация отклоняет спецификацию, которая не называет ни одной.

Новый агент, который не называет модель, стартует на модели организации, когда у
организации есть ровно одна модель, на которой агент может работать. Это
чат-модель с ключом или самостоятельно размещённая модель, сохранённая для работы
без ключа, которую публикация принимает как есть, вместе с резервными. Правило
действует для любого способа создания агента: **Новый агент** (New agent) в
консоли, `POST /agents` без `model_profile_id`, шаблон, копия черновика без модели
и специалист, сделанный черновиком агента.

«Архитектор», помощник организации, выбирает себе модель сам, когда публикуется:
первую чат-модель, которую принимает публикация, и никогда модель на [входе через
ChatGPT](#running-on-a-chatgpt-subscription). «Архитектор» обслуживает всю
организацию, а вход — это подписка одного человека: запуски участников, которые
не видят этот вход в хранилище секретов, отклоняются, а запуски тех, кто видит,
например владельцев и администраторов организации, тратят её. Если есть только
вход, «Архитектор» ждёт другую модель.

Вход, который кто-то выбрал в черновике, или модель, у которой вход среди
резервных, остаются на месте, но публикуются только тогда, когда это сделает в
Конструкторе тот, кто может менять настройки организации. «Архитектор», уже
опубликованный на входе, сохраняет эту модель, пока кто-нибудь, кто может менять
настройки организации, не выберет другую в разделе **Конструктор → Модель**
(Build → Model) и не опубликует её.

Модель записывается в черновик, поэтому агент публикуется без того, чтобы кто-то
открывал **Модель**, а его история показывает, на какой модели он опубликован.
Спецификация, которая называет модель, сохраняет её. После этого черновик
считается использующим модель, поэтому модель нельзя удалить, пока агент не
перейдёт на другую или не будет удалён; архивирования недостаточно. Чтобы сменить
только ключ или эндпоинт модели, отредактируйте её на месте
([Смена ключа или эндпоинта профиля](#changing-a-profiles-key-or-endpoint)).

Черновик остаётся без модели, когда у организации нет ни одной или их больше
одной. Профили, на которых агент не может работать, не считаются: профиль без
ключа, модель синтеза речи и остальные модели из раздела [Профиль, на котором
агент не может работать](#a-profile-an-agent-cannot-run-on), а также профиль,
который отклонила бы публикация, например тот, у которого среди резервных есть
такая модель. Модель на [входе через ChatGPT](#running-on-a-chatgpt-subscription)
никогда никому не выбирается, потому что это подписка одного человека, но в число
моделей она входит.

Новый агент также не стартует на модели, у которой среди первых трёх резервных —
тех, что пробует запуск, — есть вход: если модель откажет, запуск любого, кто
видит этот вход, перейдёт на эту подписку. «Архитектор» такую модель тоже не
выбирает. Автор всё же может выбрать её намеренно и опубликовать.

Тогда публикация отклоняет черновик с сообщением *No model selected - pick one
under Build > Model before publishing*. Отказ также помечает поле
(`model_profile_id` в `details.fields`), и консоль показывает рядом **Перейти к
модели** (Go to Model) — кнопка открывает вкладку **Конструктор** на карточке
**Модель**.

### Смена ключа или эндпоинта профиля { #changing-a-profiles-key-or-endpoint }

Агенты называют профиль по его id. Чтобы перевести модель на другой ключ, другой
эндпоинт или другой API OpenAI, отредактируйте профиль на месте:
`PATCH /providers/model-profiles/{id}` меняет `secret_id`, `base_url`, `api`,
`params` или `label` и сохраняет id. Каждый агент на этом профиле использует
изменение со следующего запуска. Никому не нужно ничего публиковать заново.

На панели модели в Конструкторе смените ключ, эндпоинт или API используемой
модели. Тогда кнопка называется **Обновить модель** (Update model), а панель
сообщает, что вместе с ней переключаются все агенты на этой модели. **Добавить
модель** (Add model) по-прежнему служит для другого провайдера или модели, а также
для модели, которой вы даёте собственное имя. С помощью **Назовите иначе** (Name
it something else) отдельная модель достаётся только этому агенту.

Правка подчиняется тем же правилам, что и создание, и требует того же разрешения
`connections:manage`. Новый ключ должен быть в хранилище секретов этой
организации, быть видимым вам и быть сохранённым для провайдера профиля. Новый
эндпоинт проверяет сохранённый ключ так же, потому что именно на эндпоинт
отправляется ключ. Провайдер, которому нужен ключ, не может его лишиться.
Провайдер без ключей, у которого ключа нет, сохраняет эндпоинт. Название
должно оставаться уникальным.

Если вы меняете эндпоинт и не передаёте `api`, API, который был лишь
значением по умолчанию для старого эндпоинта, переходит к значению по
умолчанию нового, а API, выбранный кем-то, остаётся. Журнал аудита записывает
`model_profile.updated` с именами изменённых полей, а не их значениями. Провайдера
и идентификатор модели изменить нельзя. Другая модель — другой профиль.

Таким образом, `connections:manage` — это полномочие перевести всех агентов на
модели, включая агентов, которых вы не можете редактировать: новый эндпоинт
начнёт получать их запросы со следующего запуска. Выдавайте его тем, кто управляет
моделями организации.

### Профиль без ключа { #a-profile-without-a-key }

Если удалить ключ из хранилища секретов, его профили остаются с `secret_id`,
равным null, а `GET /providers/model-profiles` помечает их `missing_key: true`.
Профиль, сохранённый без ключа намеренно, — другое дело: самостоятельно
размещённая модель или шлюз, который ничего не аутентифицирует, у провайдера без
ключей с эндпоинтом, например Ollama в вашей сети или OpenAI-совместимый
сервер. Он записывает это как `runs_without_key` и продолжает работать. Профиль
шлюза, у которого был ключ и пропал, помечается `missing_key`, как и любой другой.
Далее:

- Списки выбора модели у агента и в чате её не предлагают. Если агент уже
  указывает её, Конструктор показывает её со значком **без ключа** (no key) и
  предлагает задать ключ.
- Публикация отклоняет профиль и называет модель. Она также отклоняет профиль, у
  которого среди первых трёх резервных есть профиль без ключа, потому что запуск
  его пропустил бы. Запуск на нём падает с «no key configured».
- Чтобы починить его, откройте агента на этой модели, выберите ключ в разделе
  **Модель** и нажмите **Обновить модель**. Все агенты на модели снова работают.

### Удаление профиля { #deleting-a-profile }

`DELETE /providers/model-profiles/{id}` отклоняет профиль, который используют
агенты. Ответ — `409 IN_USE`, а `details.agents` перечисляет каждого видимого вам
агента по id и имени. `details.hidden_agents` считает агентов, которых вы не
видите. Профиль используется, когда его называет где угодно черновик агента, его
действующая версия или версия, закреплённая в окружении: как модель агента,
проверяющего или специалиста либо в возможности, например как модель последующих
сообщений или модель шага браузера.

Архивированные агенты считаются, потому что разархивирование восстанавливает
версию, которую они обслуживали. Отказ помечает их `archived`: архивированный
агент не может публиковаться, поэтому удалите его или восстановите и переведите.
Старые версии, которые никто не обслуживает, не считаются. Сначала переведите
остальных агентов на другую модель. Чтобы сменить только ключ, отредактируйте
профиль.

### Резервные модели { #fallbacks }

Профиль может перечислять резервные профили, которые пробуются по порядку.
Механизм выполнения использует только первые три, и при публикации проверяются
только они. Сбой одного провайдера не должен ронять агентов организации, когда
настроены второй ключ или второй провайдер.

!!! warning "Резервная модель не видна в записи запуска"

    Строка запуска пишется до первого запроса и несёт название, провайдера и id
    секрета **основного** профиля. Если ход обслужила резервная модель, запуск
    всё равно называет основной.

    Поэтому на вопросы «сколько мы потратили в OpenAI» и «какой ключ стоит дороже
    всего» отвечает профиль, который *спросили* первым, а не тот, что ответил.
    Стоит знать это, прежде чем полагаться на такие цифры во время сбоя.

### Настройки модели { #model-settings }

Задаются для профиля и переопределяются для каждого агента через `model_settings`
спецификации: `temperature`, `top_p`, `max_tokens`, `parallel_tool_calls`,
`timeout`. См. [справочник по спецификации](reference/spec.md#model-settings).

**Кэширование промптов включено по умолчанию**, через провайдер-нейтральную
настройку `cache` в Pydantic AI. Каждый запрос запуска заново отправляет
инструкции, схемы инструментов и всю историю, поэтому стабильный префикс и диалог
помечаются как точки кэширования, и каждый запрос читает из кэша предыдущий. Это
работает везде, где провайдер поддерживает явное кэширование — Anthropic, модели
Anthropic и Nova в Bedrock, модели Anthropic и Gemini в OpenRouter, OpenAI начиная
с GPT-5.6, — и ничего не меняет у того, кто кэширует сам, например у Google.
Профиль отключает его через `cache: false` или кэширует только инструкции и
инструменты через `cache: {"messages": false}`. Флаг конкретного провайдера,
который профиль уже задаёт, например `anthropic_cache_messages`, по-прежнему
побеждает для этого профиля.

Ежедневная сводка, подсказки и обслуживание памяти показывают эти значения по
умолчанию в списке выбора модели организации вместе с глубиной рассуждений.
Изменения сохраняются явно в общий профиль модели и влияют на каждого потребителя
этого профиля. Незаданные элементы управления не отправляют переопределений;
оставляйте неподдерживаемые параметры на значениях провайдера по умолчанию.
Агенты могут переопределить рассуждения через [возможность
`thinking`](reference/capabilities.md#thinking), которая использует
провайдер-нейтральную настройку Pydantic AI. У фоновых ролей нет спецификации
агента, и они используют значение `thinking` профиля напрямую.

### Responses или Chat Completions { #responses-or-chat-completions }

OpenAI предоставляет два API для одних и тех же моделей, и профиль на `openai`,
`azure` или `stav` сохраняет, в какой из них уходят его запросы: `responses` или
`chat`. Любой другой провайдер обслуживает один API и здесь ничего не сохраняет.

Ни один из них не подходит везде. Новейшие модели OpenAI отдаются только через
Responses и отвечают на Chat Completions ошибкой 400, а большинство
OpenAI-совместимых серверов — vLLM, LM Studio, прокси LiteLLM — реализуют только
Chat Completions. Поэтому выбор — это поле профиля, в разделе **Агенты →
Добавить модель → API** (Agents → add a model → API), и форма открывается на
значении по умолчанию:

| Профиль | По умолчанию |
|---|---|
| `openai`, без эндпоинта (собственный API OpenAI) | `responses` |
| `openai` с эндпоинтом | `chat` |
| `azure` | `chat`, потому что Responses API нужен свежий `api_version`, а секрет может закреплять более старый |
| `stav` | по модели: `chat` там, где модель доступна, иначе `responses` |

Значение по умолчанию определяет лишь, с чего начинается форма. Региональный
эндпоинт OpenAI, например `https://eu.api.openai.com/v1`, — это эндпоинт, который
обслуживает Responses, поэтому выбирайте там `responses`. Пропущенный
выбор сохраняется как значение по умолчанию, поэтому более поздняя смена значения
по умолчанию не переводит существующий профиль.

**Профиль Responses не хранит диалоги на стороне OpenAI.** Responses API сохраняет
каждый ответ у OpenAI, если не указано обратное, а Chat Completions по умолчанию
не сохраняет ничего, поэтому модель Responses отправляет `store: false`.
Рассуждения передаются между ходами как зашифрованное содержимое, а не по
сохранённому id ответа, так что сохранённая копия никому не нужна. Профиль,
которому она нужна, задаёт `openai_store` равным `true` в своих настройках.

### Где выполняются запросы профиля Stav { #where-a-stav-profiles-requests-run }

Профиль на `stav` сохраняет регион: `eu`, `eea` или `global`. Stav отвечает только
с эндпоинтов, которые обрабатывают запросы в этом регионе, переключается при сбое
только внутри него и отклоняет запрос, который не может там обслужить. `global`
сам по себе ничего не ограничивает. Регион лишь сужает то, что разрешает
собственная политика рабочего пространства Stav.

Задайте его в разделе **Агенты → Добавить модель → Регион** (Agents → add a model →
Region). Форма начинается с `eu`, и пропущенный регион сохраняется как `eu`,
поэтому профиль не выходит за пределы ЕС, если его не сохранили с `eea` или
`global`.

Регион передаётся заголовком `X-Stav-Runs-In` в каждом запросе, а не в теле,
поэтому `extra_body` в настройках профиля не может его заменить.

Пользовательские каталоги Stav используют ключ из хранилища секретов, выбранный в
форме. Вызывающий должен видеть этот ключ; приложение никогда не выбирает скрытый
ключ организации для пользовательского URL. Кэши каталогов с аутентификацией
разделяются по учётным данным. `extra_headers` уровня запроса не могут отменить
ограничение профиля по ЕС или ЕЭЗ.

### Шлюз Otari { #otari-gateway }

Выберите **Otari** при добавлении модели, сохраните API-ключ Otari в хранилище
секретов и выберите его для профиля. Поле **Эндпоинт** (Endpoint) обязательно:
для облачного Otari укажите `https://api.otari.ai/api/v1`. Для учётной записи
Otari в ЕС задайте `https://eu.api.otari.ai/api/v1`; для шлюза на собственной
инфраструктуре используйте его корень API, оканчивающийся на `/api/v1` и доступный
из API и воркеров.

Нажмите **Загрузить модели** (Load models) после выбора эндпоинта и ключа.
Изменение любого из них требует заново подтвердить назначение; ввод адреса
никогда не отправляет ключ.

Предложения моделей приходят из аутентифицированного эндпоинта `/models` этого
шлюза с использованием выбранного ключа. Пользовательский эндпоинт требует
`connections:manage` и доступа к этому ключу. Кэши каталогов разделяются по
эндпоинту и учётным данным; неудачный пользовательский запрос списка никогда
не подменяется каталогом самого Otari. Поле модели также принимает селектор
модели, например `anthropic:claude-sonnet-4-6`, или псевдоним либо политику
маршрутизации, настроенную в Otari.

Интеграция использует
[`pydantic-ai-otari`](https://github.com/mozilla-ai/otari/tree/main/integrations/pydantic-ai-otari):
его `OtariProvider` передаёт профиль семейства моделей в модель Chat Completions
от Pydantic AI, как это делает `OtariModel`. Запросы всегда идут через Chat
Completions; форма не предлагает ни Responses, ни региональные настройки Stav.
Ключи и эндпоинты передаются явно из профиля, без запасного варианта через
переменные окружения `OTARI_*` или `OPENAI_API_KEY`. Бюджеты и маршрутизация шлюза
Otari — дополнительные механизмы контроля; AgenticOS по-прежнему применяет свои
бюджеты и согласования.

Прямые селекторы `provider:model` используют для бюджетов AgenticOS цену
вышестоящей модели из встроенного каталога; чистые псевдонимы маршрутизации и
неизвестные модели остаются явно частично оценёнными. Это оценки цен вышестоящего
провайдера: для начислений шлюза смотрите отчёт об использовании Otari.

## Провайдеры { #providers }

Чат-провайдеры, поддерживаемые Pydantic AI, а также Otari через его пакет
интеграции и Stav с региональной маршрутизацией.

Стандартные провайдеры используют вывод модели и провайдера в Pydantic AI.
Платформа хранит формы учётных данных и там, где нужно, подключает пакеты
провайдеров.

!!! info "Что означает Custom URL"

    В SDK провайдера есть параметр эндпоинта, поэтому профиль можно направить
    на шлюз, прокси LiteLLM или модельный сервер в вашей сети вместо публичного API
    вендора.

    Это поле **профиля**, а не ключа. Ключ говорит, чем проходить аутентификацию, а
    эндпоинт — куда уходит запрос, поэтому один и тот же ключ может стоять
    перед тестовым прокси и перед рабочим как два профиля.

    Задайте его в разделе **Агенты → Добавить модель → Эндпоинт** (Agents → add a
    model → Endpoint); поле появляется только у провайдеров, отмеченных ниже.
    Сохранение эндпоинта для провайдера, у которого его нет, отклоняется, а не
    принимается и отбрасывается.

### Самостоятельно размещаемые { #self-hosted }

| Провайдер | id | Учётные данные | Пользовательский URL |
|---|---|---|---|
| System One API | `system-one` | API-ключ или нет | ✓ |
| Ollama | `ollama` | нет | ✓ |
| LiteLLM proxy | `litellm` | нет | ✓ (`api_base`) |

Эти два — причина, по которой «нет учётных данных» хранится как **вид** (kind), а
не как пустая строка. У модельного сервера в вашей сети обычно нечего
аутентифицировать, а хранилище секретов отклоняет пустой секрет — поэтому механизм
разрешения переключается по полному набору, а не считает отсутствующее
значение особым случаем.

**Профилю без ключа нужен его эндпоинт, и это единственное, что ему нужно.**
Поле ключа становится необязательным, как только он заполнен. Без эндпоинта
профиль отклоняется: запасного публичного API нет, и аутентифицироваться не с чем.

!!! note "Эндпоинт, а не `keyless`, делает профиль самостоятельно размещённым"

    `keyless` верно и для `openai`. OpenAI-совместимые серверы (vLLM, LM Studio,
    прокси LiteLLM) говорят на его API Chat Completions — поэтому профиль `openai`
    с эндпоинтом по умолчанию использует его; см. [Responses или Chat
    Completions](#responses-or-chat-completions).

    Поэтому одно «нет ключа» не отличает намеренно локальную модель от профиля,
    чей ключ удалили, — а внешний ключ на секрет объявлен как
    `ON DELETE SET NULL`, что делает второй случай обычным. Запуск разрешает
    профиль без ключа, только если у того есть эндпоинт; иначе он
    отклоняется с тем же сообщением «no key configured», что и всегда.

### Свой эндпоинт { #your-own-endpoint }

| Провайдер | id | Учётные данные | Пользовательский URL |
|---|---|---|---|
| Custom (OpenAI-compatible) | `openai_compatible` | API-ключ | ✓ |
| Custom (Anthropic-compatible) | `anthropic_compatible` | API-ключ | ✓ |

Эти два — скорее *форма* API, чем вендор. Вы вводите адрес сервера, который
запускаете сами, или шлюза, которому доверяете, и ключ, который его
аутентифицирует. Выберите тот, что соответствует тому, что отвечает ваш эндпоинт:

| Ваш эндпоинт отвечает | Выберите | Адрес, который ввести |
|---|---|---|
| `POST /chat/completions` — vLLM, LM Studio, прокси LiteLLM, большинство шлюзов | `openai_compatible` | корень `/v1`, например `https://llm.example/v1` |
| `POST /v1/messages` — собственная форма API Anthropic | `anthropic_compatible` | корень API, например `https://llm.example` |

Обоим нужны эндпоинт и ключ. Публичного API, на который можно отступить,
нет, поэтому профиль без эндпоинта отклоняется, а не отправляется куда-то
ещё.

Ключ хранится в хранилище секретов под именем самого провайдера, и это говорит,
что он аутентифицирует *тот* эндпоинт, а не публичный API вендора. Поэтому
они — отдельные записи, а не профили `openai` или `anthropic` с эндпоинтом:
ключ, лежащий под вендором, называет этого вендора.

!!! info "Адрес Anthropic не содержит `/v1`"

    SDK Anthropic отправляет запросы на `<endpoint>/v1/messages`, поэтому
    эндпоинт — это корень API. Адрес, который уже оканчивается на `/v1`,
    обрезается автоматически, так что работает любое написание, — но платформа
    просит именно корень.

**Загрузить модели** (Load models) читает список с того же эндпоинта и тем же
ключом, поэтому список выбора предлагает то, что ваш сервер действительно отдаёт.
Идентификатор модели остаётся свободным текстом: сервером, который не публикует
список, всё равно можно пользоваться, введя id.

### Когда учётные данные — не API-ключ { #when-the-credential-is-not-an-api-key }

| Провайдер | id | Учётные данные |
|---|---|---|
| Azure OpenAI | `azure` | ключ **+** эндпоинт **+** закреплённая версия API |
| AWS Bedrock | `bedrock` | id ключа доступа, секретный ключ, регион, необязательный токен сеанса |
| Google Vertex AI | `google_cloud` | JSON сервисной учётной записи |
| ChatGPT (Codex subscription) | `openai_codex` | вход через ChatGPT, сохраняемый при входе, а не вводом |

Первые три — причина, по которой у секрета вообще есть *вид*. Форма, которая
собирала бы для Azure один непрозрачный токен, собрала бы поле, которое можно
заполнить правильно, и всё равно получила бы отказ на первом запуске. См.
[виды секретов](secrets.md#kinds).

!!! note "Два id переписываются по пути в SDK"

    Профиль `openai` собирается как `openai-chat` или `openai-responses`, а
    `azure` — как `azure` или `azure-responses`, по сохранённому API, а не по
    Responses API, который выводит простой `openai`. См. [Responses или Chat
    Completions](#responses-or-chat-completions).

    `google_cloud` собирается как `google-cloud`. Ни то ни другое не меняет того,
    что вы сохраняете.

### Работа на подписке ChatGPT { #running-on-a-chatgpt-subscription }

`openai_codex` запускает модели OpenAI на бэкенде Codex через подписку ChatGPT, а
не через тарифицируемый API-ключ. Он предназначен для **личного использования**:
вход — это подписка одного человека, и каждый запуск на профиле, который им
пользуется, расходует лимиты ChatGPT этого человека.

Учётные данные нельзя ввести вручную. Вместо этого вы входите через ChatGPT:

1. В разделе **Секреты → Добавить ключ** (Vault → add a secret) или в разделе
   **Агенты → Добавить модель** (Agents → add a model), выбрав **ChatGPT (Codex
   subscription)**, нажмите **Войти через ChatGPT** (Sign in with ChatGPT). Вход
   через ChatGPT откроется в новой вкладке.
2. Подтвердите его. Затем ChatGPT перенаправит браузер на
   `http://localhost:1455/...`, который не откроется. Так и должно быть: OpenAI
   закрепляет этот адрес за всеми клиентами, кроме собственного.
3. Скопируйте весь адрес из адресной строки и вставьте его обратно в форму.

Код в этом адресе действует один раз, только для человека, начавшего вход, и
только в течение 15 минут.

Токен доступа истекает и обновляется во время работы моделей. Каждое обновление
расходует токен обновления, поэтому новая пара сразу же запечатывается обратно в
тот же секрет в хранилище. Два запуска, обновляющих токен в один и тот же момент,
всё равно могут столкнуться в гонке. Проигравший отклоняется; исправление —
**Переподключить** (Reconnect) на секрете: он выполняет вход заново, не меняя id
секрета.

!!! warning "Чем вход через ChatGPT не является"

    - **Это не `auth.json` Codex CLI.** В том файле лежит собственный выданный
      доступ CLI. Токены обновления одноразовые, поэтому тот из двух, кто обновился
      первым, вывел бы другого из системы.
    - **Это не учётные данные организации.** Секрет по умолчанию создаётся
      личным, и модель на нём работает только для того, кто видит вход в хранилище
      секретов и спрашивает от своего имени. Для всех остальных — посетителя на
      размещённой странице или во встроенном виджете, вызывающего с API-ключом — и
      для фоновой работы, например описания изображений документа, модель
      отклоняется, а резервная модель на нём пропускается.
    - **Публиковать на нём может не каждый.** Публикация, откат к версии агента
      или перевод версии в окружение отклоняются для того, кто не видит вход в
      хранилище секретов, когда модель, до которой доходят его запуски, работает
      на нём: модель агента, проверяющего, встроенного специалиста или включённой
      возможности, модель [агента-исполнителя, которого он
      закрепляет](reference/capabilities.md#delegation), и того, до чего этот
      агент-исполнитель доходит в свою очередь, либо одна из первых трёх резервных
      моделей любой из них. Владелец входа, владельцы и администраторы, а также
      все, кому он был открыт, могут. API-ключ не может, что бы ни видел тот, кто его выпустил, потому что запуск под ключом никогда не тратит вход. Версия,
      опубликованная на нём раньше, продолжает работать.
    - **Его не предлагают специалисту, которого придумывает модель.** При
      [`allow_dynamic`](reference/capabilities.md#delegation) модель запуска может
      выбрать модель специалиста из профилей организации. Профиль на входе или
      профиль, первые три резервных которого доходят до него, попадает в этот
      список, только когда спецификация агента называет ровно этот профиль одной
      из моделей выше.
    - **Показанные расходы — не ваш счёт.** Запуск оценивается по тарифам API
      OpenAI для той же модели — именно с этим может работать
      [бюджет](governance.md#budgets). Сама подписка оплачивается OpenAI по
      фиксированной ставке.
    - **Некоторые настройки игнорируются.** Бэкенд Codex отбрасывает `max_tokens`,
      `temperature` и `top_p`.

### Намеренно отсутствуют { #deliberately-absent }

Четырёх имён, известных Pydantic AI, здесь нет. `sentence-transformers` и
`voyageai` — модели эмбеддингов, `bedrock-mantle` — не чат-провайдер, на который
может указывать профиль, а `gateway` не разрешается в класс провайдера: это
префикс маршрутизации поверх остальных.

`tests/test_model_profiles.py` конструирует каждую запись каталога, поэтому
провайдера нельзя выбрать в Конструкторе, если его нельзя сконструировать во
время выполнения.

## Какой список отвечает на какой вопрос { #which-list-answers-which-question }

Шесть вещей в этом репозитории знают что-то о моделях и провайдерах, и это **не**
шесть копий одного списка. Каждая отвечает на свой вопрос, а та, из которой все
они выводятся, — первая:

| Вопрос | Кто отвечает |
|---|---|
| На каких провайдеров может указывать профиль и какие учётные данные нужны каждому? | `PROVIDERS` в `backend/app/agents/model_resolver.py` — **источник истины**, и только в той части, которую не может знать вывод модели |
| Как построить клиент? | Собственные `infer_provider_class` / `infer_model` из `pydantic_ai`. Не дело этой платформы, и здесь намеренно не пересказано |
| Как прочитать актуальный список моделей этого провайдера? | `backend/app/core/catalog/model_listings.json` |
| Что предложить, когда провайдера нельзя спросить? | `backend/app/core/catalog/curated_models.json` |
| Сколько стоит эта модель и сколько контекста она вмещает? | Снимок `genai-prices` через `model_catalog.priced_model` |
| Какие модели рисуют изображения? | `backend/app/core/catalog/image_models.json` плюс собственный ответ SDK о том, какие провайдеры умеют рисовать вообще |

!!! info "Всё ниже первой строки выводится из неё"

    Производная копия, которая разошлась с источником, ничего не ломает во время
    выполнения. Она показывает список выбора для несуществующего провайдера или
    пропускает существующего.

    `tests/test_model_catalog.py::TestOneAnswerPerQuestion` превращает это в
    упавшую сборку — и требует, чтобы каждый провайдер был на **этой странице**.

Каждый ключ в обоих файлах каталога должен называть провайдера, который есть в
`PROVIDERS`. То же относится к каждой записи каталога изображений. И каждый
провайдер должен быть на этой странице. Добавление двадцать девятого — это одна
правка плюс то, что затем попросит этот тест.

Стоит знать о двух переходах, потому что это поиски, которые могут ничего не
найти:

- Снимок цен пишет четырёх провайдеров иначе: `xai` там `x-ai`, `bedrock` —
  `aws`, `google_cloud` — `google`, а `openai_codex` оценивается как `openai`.
  Их связывает `_PRICE_PROVIDER_ALIASES`.
- Каталог изображений несёт свою пару `provider` и `prefix`, а это уже третий
  словарь.

## Какие модели предлагает провайдер { #which-models-a-provider-offers }

Поле идентификатора модели заполняется из двух источников в этом порядке — а у
семи провайдеров ни из одного, и ответ говорит это прямо.

### Актуальный список { #live }

Двадцать провайдеров публикуют эндпоинт со списком, и это единственный
источник, который знает о модели, выпущенной сегодня утром:

`anthropic`, `openai`, `google`, `openrouter`, `groq`, `mistral`, `together`,
`cohere`, `deepseek`, `xai`, `sambanova`, `vercel`, `ovhcloud`, `huggingface`,
`cerebras`, `fireworks`, `nebius`, `moonshotai`, `zai`, `alibaba`.

Формы ответов расходятся — массив лежит в `data`, в `models` или в корне
документа; id называется `id`, `name` или `model`; Gemini добавляет к нему префикс
`models/` — поэтому каждый описывается данными, а не ветвлением кода. Кэшируется в
процессе на час; такие списки меняются в масштабе недель.

**Пять из них вообще не требуют учётных данных** — `openrouter`, `sambanova`,
`vercel`, `ovhcloud` и `huggingface` — и именно поэтому они полезны: список выбора
заполняется ещё до того, как кто-то сохранил ключ для этого провайдера. Остальные
пятнадцать запрашиваются с ключом самой организации, когда он есть.

Шесть провайдеров по-прежнему не публикуют ничего, что можно было бы прочитать:
`github` (его путь каталога исчез), `heroku`, `azure`, `bedrock`, `google_cloud` и
прокси `litellm`, чей список — то, что за ним развернули. `ollama` отвечает
в собственной сети экземпляра, а не на фиксированном хосте, поэтому его тоже нет в
списке.

!!! warning "Пустой список модальностей означает *не указано*, а не «только текст»"

    `openrouter` и роутер Hugging Face несут `architecture.output_modalities`, и
    запись списка может называть этот путь. Больше никто его не указывает.

    Клиент, фильтрующий по нему, обязан считать отсутствие неизвестным, иначе
    он скроет работающие модели. Это метаданные, по которым клиент может сужать
    выбор; это *не* то, как возможность генерации изображений выбирает свои
    модели, — там файл каталога плюс собственный ответ SDK о том, какие провайдеры
    умеют рисовать вообще; см.
    [Генерация изображений](reference/capabilities.md#image-generation).

### Отобранный вручную { #curated }

Короткий список для каждого провайдера, используемый, когда провайдер ничего не
публикует, когда вызов не удаётся или когда нет ключа, чтобы его сделать.

Он лежит в `backend/app/core/catalog/curated_models.json` рядом с другими
каталогами экземпляра, поэтому добавить модель — это одна запись, а не правка
Python, а сами списки — это `model_listings.json` в том же каталоге, и именно это
делает данными и эндпоинт нового провайдера.

Он намеренно короток и намеренно **не** взят из `genai-prices`, который уже есть в
зависимостях и действительно перечисляет модели.

Это набор данных о *ценах*. В нём есть `ada` и `babbage` у OpenAI, `claude-2` у
Anthropic, 690 строк у OpenRouter, и почти ничего не помечено как устаревшее: при
сортировке по алфавиту первым, что список выбора предложил бы для OpenAI, была бы
`ada`. Короткий актуальный список лучше длинного вводящего в заблуждение.

Библиотека же нужна для той половины, которая портится. **Всякая длина контекста
берётся из снимка во время чтения**, поэтому здесь не записано ни одно окно; два,
что были записаны, уже устарели, причём одно из них значилось дважды с двумя
разными числами.

И id из отобранного списка, о котором снимок никогда не слышал, роняет набор
тестов — так опечатка или снятая с производства модель ловится, а не уходит в
список выбора, на который провайдер отвечает 404. У модели, которую снимок знает,
но не оценивает, просто нет окна — это и есть null, описанный ниже.

Список выбора для подписки при открытии читает отобранный список экземпляра. У
него нет актуального каталога для конкретной учётной записи. Записи GPT-6.2
сверены с сервером приложения Codex и оставляют контекст пустым, пока снимок цен
его не зафиксирует.

| Провайдер | Id из отобранного списка |
|---|---|
| `anthropic` | `claude-opus-5`, `claude-sonnet-5`, `claude-fable-5`, `claude-haiku-4-5` |
| `openai` | `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, `gpt-5.3-codex` |
| `openai_codex` | GPT-6.2 Sol и Astra, GPT-6.1 Sol и Terra, GPT-6 Sol, Astra и Luna, а также более ранние id Codex |
| `google` | `gemini-3.6-flash`, `gemini-3.5-flash`, `gemini-3.5-flash-lite`, `gemini-3.1-pro-preview` |
| `deepseek` | `deepseek-v4-pro`, `deepseek-v4-flash` |
| `xai` | `grok-4.5`, `grok-4.3` |
| `groq` | `openai/gpt-oss-120b`, `llama-3.3-70b-versatile` |
| `openrouter` | пять распространённых id от разных провайдеров |

### Ни то, ни другое, и ответ это говорит прямо { #neither-and-it-says-so }

Семь провайдеров не публикуют списка, который эта платформа умеет читать, и не
имеют отобранной записи: `github`, `heroku`, `ollama`, `litellm`, `azure`,
`bedrock` и `google_cloud`.

У них поле `source` в ответе — `unlisted`, а **не** `curated`. Пустой короткий
список — не короткий список, и именно заявление о нём превращает «эта платформа не
может перечислить модели этого провайдера» в «у этого провайдера нет моделей»
(#923). Вместо этого список выбора просит ввести id.

`ollama` и `litellm` стоило бы подключить: оба публикуют `/v1/models` в форме
OpenAI на эндпоинте, который профиль уже хранит, — а для этого списку нужно
передать базовый URL; фиксированный `ListingSpec.url` на это не способен.

Ни один источник не авторитетен, поэтому поле остаётся свободным текстом.

## Окно, которое принимает модель, читается один раз и сохраняется { #the-window-a-model-accepts-is-read-once-and-kept }

Список обычно указывает, сколько токенов принимает модель, и профиль записывает это
в `context_length` при создании.

Именно по этому числу срабатывает
[управление контекстом](reference/capabilities.md#context-management): сжатие при
доле окна — единственная настройка, которая остаётся верной, когда агент переходит
на другую модель.

!!! danger "Почему оно хранится, а не определяется при каждом запуске"

    Путь запроса не должен обращаться к провайдеру, а единственное, что он мог бы
    иначе посмотреть, — встроенный снимок цен, и здесь он ошибается в ту сторону,
    которая ломает запуск.

    Тот снимок записывает 1 000 000 для `anthropic:claude-sonnet-4-5` против
    реальных 200 000, поэтому срабатывание на 90 % оказывается выше настоящего
    потолка, и сжатие не срабатывает до того, как провайдер отклонит запрос.
    Профиль с резервными моделями хуже: он строит `FallbackModel`, чей составной
    id не соответствует ничему.

Null означает **не записано**, а не ноль: профиль старше этого столбца, провайдер,
который не публикует длину, отобранный список или список, до которого не удалось
достучаться. Тогда возможность определяет окно сама, ровно как раньше.

Если вы знаете лучше обоих, задайте `context_window` в привязке. Провайдер
публикует максимум, который модель *может* принимать, а развёртывание
с ограничением по бете или тарифу получает меньше.

Цепочка резервных моделей несёт число **основной**. У `FallbackModel` нет своего
окна, а какая модель достанется запуску, неизвестно, пока одна не откажет.

## Сколько стоит запуск { #what-a-run-costs }

Цены берутся из встроенного снимка
[`genai-prices`](https://github.com/pydantic/genai-prices). За ними никуда не ходят
по сети, и это значит две вещи, о которых стоит знать:

- Модель, слишком новая для снимка, **не имеет цены**, и запуск с ней записывается
  как *частично оценённый*, а не как ничего не стоящий. Бюджет, который молча счёл
  бы неизвестную модель бесплатной, был бы бюджетом с дырой.
- Запись агрегатора `vendor/model`, которой нет в снимке, оценивается как
  собственная модель вендора, а версия с точками пробуется ещё и с дефисами:
  `anthropic/claude-sonnet-5.5` у OpenRouter стоит столько же, сколько
  `claude-sonnet-5-5` у Anthropic.
- Обновление цен — это обновление зависимости.

!!! warning "Провайдер без ключей не записывает расходов"

    Расходы приписываются [секрету в хранилище](secrets.md), к которому пришёл
    запуск, а у провайдера без ключей нет никого, кому их приписать.

Стоимость проверяется *до* каждого запроса к модели и записывается, даже если
запуск завершился ошибкой. См. [Бюджеты](governance.md#budgets).

### Делегирование находит свой профиль { #a-delegation-resolves-its-own-profile }

Один запуск может задействовать несколько моделей.

[Агент-исполнитель](concepts.md#delegate-vs-inline-specialist) работает на профиле,
который называет *его собственная* спецификация; профиль определяется, когда
механизм выполнения обходит дерево делегирования. Встроенный специалист, который
ни одного не называет, работает на профиле агента, вызвавшего его, — это и самый
неудивительный ответ, и единственный работающий, когда профиль родителя —
единственный, который выбрал автор.

Эти запросы учитываются по единому журналу родительского запуска, но
**оцениваются по провайдеру**: контроль бюджета агента-исполнителя делит общий
журнал, лимиты и месячные базовые значения, но берёт своего провайдера.

Делить журнал родителя целиком означало бы оценивать агента-исполнителя
на Anthropic по каталогу OpenAI — молча и обычно как не имеющего цены, что
занижает стоимость запуска и помечает вполне оценимый запуск как нижнюю границу.

Строка дочернего запуска, которую пишет делегирование, называет модель, ответившую
на него, поэтому панель стоимости группирует ход, выполненный по делегированию,
под моделью, которая действительно работала, а не под моделью родителя.

## Модели реального времени { #realtime-models }

[Голосовой звонок](voice.md) не использует профиль модели. Его модель — это выбор
из каталога, который поставляется с экземпляром,
`backend/app/core/catalog/realtime_models.json`; его читает
`backend/app/services/realtime_models.py`, а Конструктору он отдаётся по адресу
`GET /api/v1/providers/realtime-models`. Ключ указывается в разделе «Голос» агента
как секрет в хранилище, а не в профиле. Это та же схема, что и у распознавания
речи: выбор из каталога плюс явный ключ.

Каждая запись называет провайдера, его модели, а для каждой модели:

| Поле | Что оно определяет |
|---|---|
| `transport` | `webrtc` (браузер общается с провайдером; этот экземпляр держит вспомогательный канал) или `relay` (аудио идёт через сокет этого экземпляра) |
| `input_sample_rate`, `output_sample_rate` | Частоты PCM, на которых браузер записывает и воспроизводит звук через ретрансляцию |
| `voices`, `default_voice` | Что предлагает раздел «Голос» и что означает пустой выбор |
| `supports_thinking` | Переносится ли возможность «Размышления» агента на собственную настройку рассуждений модели |
| `context_window` | При каком объёме переподключение переключается с повторного воспроизведения ходов на сводку более старых |
| `pricing` | `kind` (`tokens` или `per_minute`), `worst_case_usd_per_minute` для проверки перед звонком и `usd_per_minute` для модели с оплатой за минуту |

Семейство `gpt-realtime` от OpenAI работает через WebRTC, и это единственный
провайдер, проверенный вживую. Azure OpenAI, Gemini Live и xAI работают через
ретрансляцию и **вживую не проверены**. GPT-Live нет в каталоге: он не принимает
историю после начала сеанса, поэтому переподключение не смогло бы продолжить
звонок.

**Azure — это развёртывание плюс базовая модель.** Имя развёртывания выбирает его
владелец, и оно ничего не говорит о том, что в нём работает, поэтому раздел «Голос»
принимает имя развёртывания как свободный текст, а модель каталога, которая в нём
работает, — как `base_model`. Базовая модель определяет голоса и цену: токены
звонка Azure оцениваются как эта модель в OpenAI. Эндпоинт и версия API
берутся из секрета `azure_openai`.

**Цены.** Модели с оплатой за токены оцениваются за каждый ответ по тому же
встроенному снимку, что и текстовые запуски. Модель с оплатой за минуту (xAI)
тарифицируется по времени соединения по `usd_per_minute` из каталога. Модель с
оплатой за токены, которую снимок не может оценить, отклоняется при начале звонка,
а не запускается с бюджетом, который нельзя обеспечить.

## Итог { #recap }

- **Профиль** — это названная модель плюс названный ключ, и агенты указывают на
  профили, чтобы замена любого из них задевала одну строку.
- **28 провайдеров**, и единственное, что эта платформа знает о каждом, — форма
  учётных данных; конструирование — дело Pydantic AI.
- Идентификатор модели — **свободный текст**, потому что ни один список не
  авторитетен.
- **Длина контекста** читается один раз и сохраняется, потому что снимок цен
  ошибается в ней в ту сторону, которая ломает запуск.
- **Стоимость** берётся из встроенного снимка, неизвестная модель записывается как
  не имеющая цены, а не как бесплатная, и провайдер без ключей вовсе не записывает
  расходов.
- **Модели реального времени** для голосовых звонков — это выбор из каталога плюс
  названный ключ, без профиля; вживую проверены только модели OpenAI.

## Как это настроить { #setting-one-up }

[Пошаговое руководство по первому агенту](first-agent.md) проходит это целиком.
Коротко: сохраните ключ провайдера в разделе **Настройки → Секреты** (Settings →
Secrets), добавьте профиль модели, который его называет, затем направьте
спецификацию агента на профиль.

```bash
make platform-bootstrap BOOTSTRAP_API_KEY=sk-...
```

делает все три вещи для нового экземпляра.

Для регионального API OpenRouter оставьте **OpenRouter** провайдером и задайте в
поле **Эндпоинт** (Endpoint) значение `https://eu.openrouter.ai/api/v1` в форме
модели. Профиль сохраняет свой ключ OpenRouter в хранилище, нативную работу с
моделями и настройки кэширования. Предложения моделей приходят с этого эндпоинта
и кэшируются отдельно; неудачный региональный запрос списка не откатывается
к глобальному каталогу. Для баз знаний задайте **Эндпоинт** для эмбеддингов
отдельно при создании коллекции или правке провайдера эмбеддингов. Существующие
конфигурации сохраняют глобальный эндпоинт. Маршрутизация в ЕС требует
подходящего тарифа OpenRouter Business или Enterprise;
[региональная маршрутизация](https://openrouter.ai/docs/guides/get-started/sovereign-ai)
и ZDR — отдельные политики OpenRouter.

Региональный эндпоинт отдаёт меньше моделей эмбеддингов, чем глобальный:
`eu.openrouter.ai` отдаёт `mistralai/mistral-embed-2312`,
`mistralai/codestral-embed-2505` и `google/gemini-embedding-2`, и ни одной модели
OpenAI. Форма создания предлагает только те модели, что перечисляет эндпоинт,
а коллекция, чью модель эндпоинт не отдаёт, отклоняется — и при
создании, и при переносе туда. Двух моделей Mistral нет во встроенном снимке цен,
поэтому их расходы записываются как частично оценённые.

Обновите каждый процесс API и каждый воркер, прежде чем настраивать региональные
эндпоинты. Более ранние сборки игнорируют переопределение эндпоинта
OpenRouter.

Для другого эндпоинта с тем же провайдером и моделью выберите **Добавить
отдельную модель** (Add separate model) в Конструкторе. Её автоматическое имя
включает эндпоинт, а существующий профиль остаётся неизменным. **Обновить
модель** (Update model), напротив, правит общий профиль. Загрузки пользовательских
каталогов ограничены 2 МиБ, 2 048 моделями и ограниченными длинами полей, а в
процессе кэшируется не более 16 каталогов. Сжатый или слишком большой ответ
оставляет идентификатор модели доступным для правки, не откатываясь к глобальному
списку.

## Модели решений { #decision-models }

Профили решений используют нативный API `decisions` вместо генерации текста.
Выберите провайдера, модель и ключ из хранилища в конструкторе модели. OpenAI,
Google и OpenRouter предлагают и чат-API, и API решений; TypeSafe и
пользовательский эндпоинт System One обслуживают решения. Профиль решения не
может быть диалоговой моделью агента или резервной моделью для чат-модели.

Нативные адаптеры берутся из Pydantic AI. Текущие предложения включают OpenAI
`gpt-6-luna`, Google `gemini-decision-1` и TypeSafe `jev-1.14.0` / `jev-latest`.
OpenRouter читает каталог моделей решений отдельно от каталога текстовых моделей.
Пользовательский эндпоинт System One требует собственного URL и
идентификатора модели. Доступность и доступ по учётной записи зависят от
провайдера; предложения не гарантируют доступа.

Шаги **Модели решений** (Decision models) в сценарии выбирают нативный профиль.
Существующие id `decide.*` и конфигурации ключей TypeSafe по-прежнему загружаются.
Ответы ниже заданной уверенности идут по порту `unsure`. Учётные данные и
авторизация проверяются заново при каждом выполнении, а расходы провайдера идут в
бюджеты сценария и организации.

Настройка канала **Автоматически присоединяться к разговорам** (Join conversations
automatically) может использовать нативный профиль решения или обычную LLM со
структурированным выводом. Нативное решение «да/нет» возвращает вероятность
присоединиться; ограниченный числовой вывод сохраняет эту вероятность. LLM
возвращает оценку полезности от 0 до 100, а не откалиброванную вероятность. Оба
сравниваются со значением **Запускать агента при значении от (%)** (Run the agent
from (%)), включая сам порог. У классификатора нет инструментов. Присоединение
остаётся добровольным и использует заданные интервалы; основной агент может
использовать учётные записи MCP организации, но никогда — личные учётные данные
участника.

Ссылки на провайдеров: [Pydantic AI](https://pydantic.dev/docs/ai/models/decision/),
[OpenAI](https://developers.openai.com/api/docs/guides/decisions),
[Google](https://ai.google.dev/gemini-api/docs/decisions-api),
[TypeSafe](https://docs.typesafe.ai/models),
[OpenRouter](https://github.com/OpenRouterTeam/skills/tree/main/skills/openrouter-decisions).

ElevenLabs Realtime добавляет `eleven_realtime_v1_mini` и `eleven_realtime_v1_max`
через ретрансляцию PCM с частотой 24 кГц, с голосом по умолчанию `brian` и
семантическим определением смены хода.

SDK не сообщает о начислениях за токены. Звонки с заданным бюджетом расходов
отклоняются до подключения; звонки без бюджета расходов сохраняют ограничение по
времени и записывают соединённое аудио как нижнюю границу стоимости, а не полный
счёт. Тариф аудио в каталоге — $0.08 в минуту ($0.16 при пиковой нагрузке);
начисления за токены добавляются сверху. Значение контекста 16k — консервативный
бюджет платформы на начальное заполнение истории, а не опубликованное вендором
контекстное окно. Интеграция тестируется офлайн на конструировании SDK и
управляемых транспортах, а не на живых учётных записях.
[SDK](https://pydantic.dev/docs/ai/api/realtime/elevenlabs/),
[Тарифы API ElevenLabs](https://elevenlabs.io/pricing/api).

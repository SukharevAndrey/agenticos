# Бенчмарк фоновых задач { #the-background-job-benchmark }

До 1.9.0 каждая фоновая задача в AgenticOS выполнялась на Prefect, который
запускал новый процесс Python для каждого запуска. 18 октября 2026 года около
1 650 просроченных запусков скопилось на хосте, который уже терял процессорное
время из-за кражи (CPU steal), и сайт упал. Прежде чем заменить Prefect, мы
прогнали десять движков в семнадцати конфигурациях через одни и те же нагрузки,
измеряя одинаково. Эта страница о том, что измерялось, что решило выбор и чего
числа не показывают. Стенд — `experiments/task-queues` на коммите `a239dfdd7` в
ветке `spike/task-queue-benchmark`, и сырые события каждого запуска тоже там.

## Что сравнивали { #what-was-compared }

| Вариант | Движок | Как выполняет работу |
|---|---|---|
| `prefect-serve` | Prefect 3 `serve`, лимит 5; пробовали и с лимитом 20, и с базой данных Prefect на Postgres | Новый процесс Python на каждый запуск: AgenticOS до 1.9.0 |
| `prefect-tasks` | Фоновые задачи Prefect | Долгоживущий воркер задач |
| `celery-prefork`, `celery-threads` | Celery 5.6 и Beat на Redis | Пул процессов или потоков |
| `taskiq` | Taskiq на Redis Streams, со своим планировщиком | Асинхронно, один цикл событий на процесс |
| `dramatiq` | Dramatiq на Redis | Процессы × потоки |
| `saq` | SAQ на Redis | Асинхронно, один цикл событий на процесс |
| `procrastinate` | Procrastinate 3.10 на Postgres | Асинхронно, один цикл событий |
| `pgqueuer` | PgQueuer 1.6.0 на Postgres | Асинхронно, один цикл событий |
| `dbos`, `dbos-poll100` | DBOS 3.3.0 на Postgres; `-poll100` опрашивает каждые 0,1 с вместо 1 с | Долговечные сценарии |
| `hatchet`, `hatchet-fair` | Hatchet Lite на Postgres; `-fair` чередует организации | Асинхронные слоты воркеров |
| `pgqueue`, `pgqueue-fair` | Обычная очередь на Postgres: `SKIP LOCKED`, `LISTEN/NOTIFY`, аренды | Асинхронные слоты; `-fair` забирает задачи по очереди между организациями |

Каждый процесс задачи сначала импортирует настоящее приложение AgenticOS. Этот
импорт — та плата, которую Prefect вносил на каждом запуске, поэтому бенчмарк без
него скрыл бы изучаемую цену. Воркеры получили 3 CPU и 4 ГБ — долю
производственного хоста, отведённую фоновой работе. Сервис, который приносит
движок, например сервер Prefect или движок Hatchet, получил свои лимиты, и его
процессор и память считаются частью цены этого движка.

## Сценарии { #the-scenarios }

- **`workflow`**: 50 запусков по 10 последовательных лёгких шагов, запускаемых
  одновременно. Каждый шаг делает обращение к базе данных и ставит в очередь
  следующий. Измеряет накладные расходы движка на переход.
- **`mix`**: 5 минут вызовов модели (2 в секунду, каждый ждёт от 2 до 10 с) и
  разбора PDF (один каждые 2 с, около 1 с CPU каждый), плюс собственный плановый
  обход движка раз в минуту. Измеряет, как ожидающая работа и работа процессора
  делят воркеры и насколько регулярно выполняется расписание.
- **`tenants`**: одна организация ставит в очередь 1 000 задач сразу, пока другая
  отправляет одну задачу в секунду в течение 90 с. Через 20 с каждый воркер
  принудительно завершают и запускают снова через 10 с. Измеряет справедливость
  и то, сколько стоит сбой.
- **`oom`**: одна задача растит свою память, пока ядро не завершит принудительно
  её воркер из-за нехватки памяти на отметке 1 ГБ, а рядом работают 210 обычных
  задач. Мёртвый воркер перезапускается через 3 с, запуск наблюдают 240 с, и
  каждый движок с лимитом повторов настроен на 3 попытки.

Каждая задача пишет строку `started` и строку `finished`, а отправитель — строку
`enqueued`, в одну таблицу Postgres по одним часам. Ожидания, промежутки между
шагами, потерянные и продублированные задачи берутся из этих строк. Драйвер раз в
секунду снимает `docker
stats` и читает счётчик WAL Postgres до и после.

## Накладные расходы на шаг { #overhead-per-step }

| Вариант | Переход, p50 | Переход, p95 | Шагов в секунду | Пиковая память воркеров |
|---|---|---|---|---|
| `taskiq` | 0.01 s | 0.02 s | 948 | 184 MB |
| `saq` | 0.01 s | 0.05 s | 818 | 564 MB |
| `dramatiq` | 0.02 s | 0.05 s | 1,338 | 583 MB |
| `pgqueue` | 0.03 s | 0.06 s | 506 | 288 MB |
| `pgqueuer` | 0.03 s | 0.08 s | 609 | 584 MB |
| `procrastinate` | 0.05 s | 0.06 s | 829 | 294 MB |
| `celery-prefork` | 0.05 s | 0.13 s | 485 | 1,294 MB |
| `hatchet` | 0.42 s | 0.82 s | 92 | 642 MB |
| `dbos-poll100` | 0.56 s | 1.11 s | 71 | 601 MB |
| `dbos` | 2.51 s | 3.12 s | 19 | 1,488 MB |
| `prefect-tasks` | 2.60 s | 6.82 s | 11 | 861 MB |
| `prefect-serve` | 218 s | 246 s | 0.2 | 1,736 MB |

`prefect-serve` не завершился: за 20 минут он выполнил 273 шага из 500. Повышение
лимита до 20 процессов не завершило ни одного шага, потому что 20 копий приложения
не поместились в 4 ГБ. Все движки начиная с `dbos-poll100` добавляют к каждому шагу
сценария минимум полсекунды.

## Ожидание рядом с работой процессора { #waiting-work-beside-cpu-work }

| Вариант | Ожидание вызова модели, p50 | Ожидание вызова модели, p95 | Самое позднее начало обхода |
|---|---|---|---|
| `taskiq` | 0.00 s | 0.01 s | 0.0 s |
| `pgqueue` | 0.01 s | 0.57 s | 0.0 s |
| `pgqueuer` | 0.01 s | 0.41 s | 0.6 s |
| `celery-threads` | 0.01 s | 0.04 s | 0.0 s |
| `hatchet` | 0.01 s | 0.27 s | 1.0 s |
| `procrastinate` | 0.01 s | 0.61 s | 29.4 s |
| `dbos` | 0.60 s | 1.48 s | 3.7 s |
| `prefect-tasks` | 0.10 s | 2.15 s | Обход не запускался |
| `celery-prefork` | 148 s | 279 s | 63.1 s |

Вызов модели почти всё время ждёт, поэтому движок, который держит целый процесс на
каждый вызов, ставит следующие в очередь за ним: `celery-prefork` заставил вызовы
ждать больше двух минут. Сам Postgres под `pgqueue`, `pgqueuer` и `dbos`
использовал от 3 до 6% одного CPU. DBOS записал в WAL в 2,3 раза больше, чем
`pgqueue` (4,4 МБ против 1,9 МБ), потому что каждый его сценарий — это несколько
строк статуса и шагов.

## Наплыв и сбой { #a-flood-and-a-crash }

| Вариант | Потеряно | Продублировано | Ожидание малой организации, p95 | Самая долгая пауза |
|---|---|---|---|---|
| `pgqueue` | 0 | 0 | 11.1 s | 17.5 s |
| `pgqueuer` | 0 | 0 | 11.0 s | 16.8 s |
| `taskiq` | 0 | 0 | 12.0 s | 17.5 s |
| `procrastinate` | 0 | 0 | 14.0 s | 20.4 s |
| `dbos-poll100` | 0 | 0 | 14.1 s | 18.3 s |
| `hatchet-fair` | 0 | 0 | 18.3 s | 24.0 s |
| `dbos` | 0 | 0 | 64.8 s | 18.8 s |
| `celery-prefork` | 0 | 0 | 50.3 s | 39.5 s |
| `saq` | 0 | 0 | 10.0 s | 551.5 s |
| `pgqueue-fair` | 0 | 137 | 10.1 s | 15.4 s |

Ни один движок в таблице не потерял задачу; у `prefect-tasks` всё ещё оставались
две незавершённые задачи, когда его запуск истёк по времени. Большинство движков
выполнили одну задачу второй раз: ту, которую держал принудительно завершённый
воркер, — а любая очередь, возвращающая задачу мёртвого воркера, обязана так
делать. Прототип `pgqueue-fair` завершил 137 задач дважды. Поочерёдный захват из
него в поставку не вошёл, и причина — эти дубликаты. SAQ держал задачи
принудительно завершённых воркеров больше девяти минут, прежде чем забрать их
обратно.

## Задача, из-за которой принудительно завершается воркер { #the-job-that-kills-its-worker }

Это тот сценарий, который и определил выбор. В одном прошлом инциденте в
производственной среде, в другом проекте на Celery, задачу, которую ядро
принудительно завершило из-за нехватки памяти, запускало снова и снова, а её сбой
нигде не записывался. Новая очередь не должна была допустить ни того, ни другого.

| Вариант | Запусков задачи за 240 с | Что произошло | Обычные задачи |
|---|---|---|---|
| `pgqueue` | 3 | После третьей попытки помечена `dead`, сбой записан при плановом обходе | Все завершены |
| `dbos` | 3 | `MAX_RECOVERY_ATTEMPTS_EXCEEDED`, записано перезапущенным процессом | Все завершены |
| `procrastinate` | 4 | Запускалась снова каждую минуту; описанный в документации рецепт для зависших задач считает попытки, но ничего не ограничивает | Все завершены |
| `taskiq` | 5 | Запускалась снова каждые 60 с; контейнер так и не умер, потому что его менеджер процессов перезапускает дочерний процесс, и снаружи этого не было видно | Все завершены |
| `pgqueuer` | 8 | Забиралась заново каждый раз, когда пропадал её сигнал активности, без засчитывания попытки; принудительно завершены 7 воркеров | Все завершены |

DBOS тоже остановился на 3, но вторая проверка нашла другой запрещённый исход.
Когда воркер погибал, держа три задачи, и возвращался новым контейнером — как при
каждом развёртывании, — эти три через 120 с всё ещё были `PENDING` под id старого
исполнителя. Новый процесс их не видит. DBOS Conductor распознаёт погибшего
исполнителя, но лицензируется отдельно для коммерческого самостоятельного
размещения. Celery через этот сценарий не запускали. Его документация описывает оба
сбоя: сообщение возвращается без ограничения числа доставок либо задача теряется
молча.

## Что в итоге выпустили { #what-shipped }

В 1.9.0 место Prefect заняли простая очередь на Postgres (`pgqueue`) и
долгоживущие воркеры на asyncio. Попытка засчитывается в момент, когда задачу
забирают, а не когда она завершается. Каждый воркер заодно выполняет функцию
восстановления: когда один гибнет, следующий, кто берётся за восстановление, —
уцелевший воркер или перезапущенный погибший — находит его просроченную аренду и
записывает гибель, как бы воркер ни погиб. Oban, River и Solid Queue используют
то же правило.

Индексация тоже идёт в дочерних процессах под наблюдением сторожевого процесса
памяти, так что один тяжёлый документ не уносит свой воркер. [Отправка фоновой работы из
запроса](architecture.md#dispatching-background-work-from-a-request) показывает, как
код ставит задачу в очередь, а [Масштабирование за пределы одного
хоста](scaling.md#more-workers) — как добавлять воркеры.

Справедливость между организациями оставлена такой, какой её измерили. Простая
очередь дала малой организации почти тот же p95, что и прототип с поочерёдным
захватом (11,1 с против 10,1 с), но без его дублей.

## О чём цифры не говорят { #what-the-numbers-do-not-say }

- **Одна машина.** Все запуски шли в Docker Desktop на Apple silicon. На сервере
  абсолютные числа будут другими. Кража циклов CPU на общем хосте замедляет
  каждый запуск процесса, а это лишь расширяет разрыв для схемы «процесс на каждый
  запуск».
- **Один запуск на каждую ячейку.** Разрывы между движками настолько велики, что
  упорядочить их можно по одному запуску. Там, где два движка близки — например,
  `pgqueue` и `pgqueuer` по накладным расходам, — таблицы не говорят, что один из
  них быстрее.
- **Каждый движок в своей обычной конфигурации.** У всех движков был одинаковый
  бюджет CPU и памяти, но не одинаковая конкурентность: у пула процессов и у цикла
  событий нет общей единицы. Другая настройка может изменить счёт, особенно счёт в
  сценарии OOM.
- **Ошибка стенда, исправленная.** Первый запуск `tenants` на Procrastinate потерял
  задачу: стенд вызывал метод, которого в 3.10 больше нет. Это была наша ошибка, а
  не Procrastinate. Повторный запуск выше завершил все 1 090 задач.

## Запустите снова { #run-it-again }

```bash
# Из корня репозитория, на измеренном коммите.
git switch --detach a239dfdd7
docker build -f backend/Dockerfile -t agenticos-backend:bench-base .
cd experiments/task-queues
docker build -t tqbench:latest .
./run.sh pgqueue oom          # one variant, one scenario, on a fresh project
./matrix.sh                   # every cell; a few hours
python3 -m bench.report results > results/TABLES.md
```

[Набор нагрузочных тестов](load-testing.md) отвечает на другой вопрос: сколько может
обслужить один экземпляр AgenticOS, а не какой движок должен выполнять его
задачи.

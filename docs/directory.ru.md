# Вход через каталог и группы { #directory-sign-in-and-groups }

Компания, которая ведёт Active Directory, OpenLDAP или FreeIPA, уже знает, кто в
ней работает и к каким командам эти люди относятся. На этой странице — три
способа, которыми AgenticOS может пользоваться этими знаниями. Люди могут
входить со своей учётной записью каталога. Браузер на машине в домене может
ввести их с помощью билета Kerberos. А группы каталога могут определять, в какие
организации человек попадает, с какой ролью и в каких группах он окажется.

Из этого складываются три части, и работают они независимо:

| Часть | Что делает | Кем настраивается |
|---|---|---|
| [Группы](#groups) | Именованные наборы участников организации, которым можно открыть доступ к ресурсу | Участники с `members:manage`, в консоли |
| [Сопоставления групп каталога](#directory-group-mappings) | «Все, кто в этой группе каталога, вступают с этой ролью и в эту группу» | Участники с `members:manage` и `roles:manage` |
| [Вход через каталог](#signing-in-with-a-directory-account) | Вход по паролю LDAP и вход по Kerberos (SPNEGO) | Оператор, в `backend/.env` |

Сопоставления действуют и для тех, кто входит через
[OIDC](configuration.md#single-sign-on-generic-oidc), когда провайдер
идентификации сообщает их группы. Если в вашей компании перед каталогом уже
стоит Keycloak или Entra ID, встроенный вход по LDAP может не понадобиться
вовсе. См. [Через провайдера идентификации](#through-an-identity-provider-instead).

## Группы { #groups }

Группа — это именованный набор участников внутри одной организации: *Финансы*,
*Команда поддержки*, *Администраторы платформы*. Вы открываете агенту, навыку,
коллекции, файлу контекста, секрету из хранилища или приложению доступ для группы
так же, как открываете его человеку: из панели **Доступ** (Sharing) на странице
ресурса. После этого один выданный доступ доходит до всех в группе.

Доступ, выданный группе, доходит до того, кто в ней **на момент проверки
доступа**. Кто вступит в группу в следующем месяце — получит доступ к ресурсу;
кто выйдет — перестанет его получать. Отзывать что-либо у отдельного человека не
нужно.

Группа не несёт роли. Что участник может делать в организации, по-прежнему
решает роль его членства, а группа лишь добавляет выданные ей доступы.
Действующий доступ остаётся тем правилом, что описано в
[Разрешениях](permissions.md#how-the-layers-combine):

```
effective access to one row = max(role scope, the person's grant, their groups' grants)
```

Когда человек доходит до строки через несколько выданных доступов, побеждает
наивысший уровень. Просмотр по собственному доступу и редактирование по доступу
группы — это редактирование.

| Действие | Кто может |
|---|---|
| Просматривать группы и видеть, кто в них | Любой участник организации |
| Создавать, переименовывать и удалять группу; добавлять и убирать людей | `members:manage` |
| Открыть доступ к ресурсу для группы | Тот, кто может редактировать этот ресурс |

Группы находятся в разделе **Организации → Участники → Группы** (Organizations →
Members → Groups). Добавлять можно только участников организации, а если убрать
человека из организации, он уходит и из всех её групп. Удаление группы удаляет
каждый выданный ей доступ и каждое сопоставление каталога, которое её называет,
поэтому для него нужны те же права, что и для удаления таких сопоставлений:
администратор не может удалить группу, на которую указывает сопоставление уровня
Admin.

## Сопоставления групп каталога { #directory-group-mappings }

Сопоставление говорит, что означает одна группа каталога внутри одной
организации:

> Все, кто входит в `CN=Finance,OU=Groups,DC=corp,DC=example,DC=com`, получают
> здесь роль **member** и попадают в группу **Финансы**.

Сопоставления находятся в разделе **Организации → Участники → Каталог**
(Organizations → Members → Directory). Для их просмотра нужно `members:manage`.
Для создания или удаления — `members:manage` и `roles:manage`, потому что
сопоставление и принимает людей, и выдаёт им роль.

Роль ограничена так же, как у приглашения. Сопоставить группу каталога можно
только с ролью, которую ваша собственная роль строго превосходит. Никто не может
сопоставить группу с `owner`, и администратор не может сопоставить группу с
Admin. Удаление сопоставления требует тех же прав, потому что оно понижает всех,
кого поставило.

### Что происходит при входе { #what-happens-at-sign-in }

Каждый раз, когда человек входит по LDAP, по Kerberos или через OIDC с заданным
[`OIDC_GROUPS_CLAIM`](#the-groups-claim-over-oidc), его группы каталога сверяются
с сопоставлениями каждой организации:

1. **Организация с подходящим сопоставлением**: человек вступает в неё, если ещё
   не участник, с ролью из сопоставления. Членство помечается как **Каталог**
   (directory).
2. **Членство из каталога** — его роль приводится в соответствие с
   сопоставлениями.
3. **Человек вступает в группы из сопоставлений** и покидает те членства в
   группах, созданные каталогом, которые больше не названы ни одним
   сопоставлением.
4. **Членство из каталога, для которого не осталось подходящего сопоставления**,
   удаляется вместе с членством человека в группах этой организации.

Группы сравниваются без учёта регистра и пробелов по краям, потому что так их
сравнивает любой каталог.

Когда в одной организации подходит несколько сопоставлений, роль — первая из
этих, которую называет любое из них:

**admin → builder → operator → member → viewer**

Роли не выстроены в одну линию старшинства. У Builder есть то, чего нет у
Operator, и наоборот, поэтому порядок здесь задан, а не выводится.

### Чего синхронизация не касается { #what-the-sync-never-touches }

Автоматическое согласование членства соблюдает четыре правила:

- **Членство, созданное администратором, сохраняет свою роль.** Тот, кого
  пригласили вручную, сохраняет выданную роль, даже если ему подходит
  сопоставление. В группы из сопоставлений он всё равно вступает.
- **Ручная смена роли участника из каталога переводит членство под ручное
  управление.** Оно становится ручным членством, и последующие входы его роль не
  трогают.
- **Членство в группе, добавленное вручную, остаётся**, когда каталог убрал бы
  человека из этой группы.
- **Владельца никогда не понижают и не удаляют**, и ни одно сопоставление не
  может сделать человека владельцем. Владение передаётся только через
  **Передать владение** (Transfer ownership).

В личную организацию никогда не вступают через сопоставление, и для неё нельзя
создать сопоставление.

Когда человека принимают и сопоставление каталога, и
[сопоставление ролей Discord](channels.md#discord-roles), при входе приоритет у
каталога: он забирает членство, которым управлял Discord, вместе с ролью из
каталога. После этого потеря роли Discord уже не может убрать этого человека.
Когда действие доступа из каталога заканчивается, вход проверяет, даёт ли ещё
членство привязанная учётная запись Discord, прежде чем удалять его. Оставшийся
доступ передаёт ту же строку под управление **Discord**, сохраняя API-ключи,
согласие подключённых приложений и посторонние членства в группах.

Если оставшегося доступа нет, членство удаляется обычным порядком. Нечитаемое
сопоставление допуска Discord — включая истечение десятисекундного лимита на
сеть — передаёт сохранённое членство под управление Discord, чтобы периодическая
сверка повторила попытку без нового входа. Его роль ограничена правами, которые
оправданы и прежней ролью, и возможным непрочитанным доступом. Все организации,
проверяемые при одном входе, делят этот сетевой срок.

Ручные членства и владельцев никогда не забирают. Передачи записываются в аудит
как `directory.member_taken_over` и `directory.member_handed_to_discord`.
Членства в группах сохраняют собственный источник и собственные правила
согласования.

!!! warning "Удаление сопоставления убирает людей, которых оно поставило"

    Удаление происходит при **следующем входе** каждого человека, а не сразу.
    Чтобы сохранить кого-то после удаления сопоставления, которое его привело,
    сначала смените его роль вручную. Это переведёт членство под ручное
    управление.

### Сопоставления принимают новые учётные записи { #mappings-admit-new-accounts }

Сопоставление считается приглашением. В экземпляре с политикой `invite_only` или
со списком разрешённых доменов первый вход, группы при котором подходят под
сопоставление любой организации, создаёт учётную запись. Тот, у кого есть и
`members:manage`, и `roles:manage`, решил, что все в этой группе должны быть
приняты. Экземпляр с политикой `closed` всё равно отклонит его. См.
[Кто может зарегистрироваться](deployment.md#who-may-register).

## Вход с учётной записью каталога { #signing-in-with-a-directory-account }

Задайте `LDAP_URL`, и страница входа предложит форму каталога. Люди вводят имя
пользователя, которое используют везде, и свой пароль каталога. AgenticOS
проверяет пароль стандартной двухшаговой привязкой:

1. Он ищет в `LDAP_USER_BASE_DN` по `LDAP_USER_FILTER`, от имени служебной
   учётной записи (`LDAP_BIND_DN`), ровно одну учётную запись с этим именем
   пользователя.
2. Он привязывается **от имени этой учётной записи** с введённым паролем. Пароль
   проверяет только каталог. Здесь он не хранится, не хешируется и не попадает в
   журналы.

Учётная запись привязана к собственному стабильному идентификатору каталога:
`LDAP_ID_ATTRIBUTE`, `objectGUID` в Active Directory и `entryUUID` в OpenLDAP и
FreeIPA. Она не привязана к адресу, поэтому человек, сменивший имя, сохраняет
свою историю. При первом входе учётная запись создаётся по
[политике регистрации](deployment.md#who-may-register), а существующая учётная
запись с тем же адресом привязывается к ней.

```bash
# backend/.env — Active Directory поверх LDAPS
LDAP_URL=ldaps://dc01.corp.example.com
LDAP_CA_CERT_FILE=/etc/ssl/certs/corp-ca.pem
LDAP_BIND_DN=CN=agenticos,OU=Service Accounts,DC=corp,DC=example,DC=com
LDAP_BIND_PASSWORD=...
LDAP_USER_BASE_DN=OU=Staff,DC=corp,DC=example,DC=com
LDAP_ID_ATTRIBUTE=objectGUID
```

```bash
# frontend — показать форму на странице входа
OAUTH_PROVIDERS=ldap
LDAP_DISPLAY_NAME=Active Directory
```

Все параметры и их значения по умолчанию — в разделе
[Конфигурация](configuration.md#directory-sign-in-ldap).

### Что вход отклоняет { #what-the-sign-in-refuses }

| Отклоняется | Почему |
|---|---|
| Пустой пароль | Привязка LDAP с именем и без пароля — это *неаутентифицированная* привязка, которую многие серверы принимают (RFC 4513). До каталога она не доходит |
| Две учётные записи с одним именем пользователя | Привязка от имени той, что вернулась первой, могла бы ввести одного человека под видом другого |
| Имя пользователя с синтаксисом фильтра | Оно экранируется (RFC 4515), поэтому `*` не находит никого вместо того, чтобы найти всех |
| Учётная запись без адреса или без идентификатора | На них построены и учётная запись, и приглашение, и политика регистрации |
| `ldap://` без StartTLS | Он передаёт каждый пароль открытым текстом. Процесс отказывается запускаться, если `LDAP_ALLOW_PLAINTEXT=true` не говорит об этом намеренно |

Неверное имя пользователя и неверный пароль получают один и тот же ответ.
Недоступный каталог, отклонённая служебная учётная запись и поиск, на который
каталог не смог ответить (скажем, из-за неверного base DN), сообщаются как
недоступность каталога. Они не сообщаются как неверный пароль — иначе каждый
человек в компании пошёл бы сбрасывать свой.

Сертификат проверяется по системному хранилищу доверия или по
`LDAP_CA_CERT_FILE` для корпоративного удостоверяющего центра, и имя узла — так
же. Вход ограничен по частоте для каждого адреса и каждого имени пользователя,
как и вход по паролю.

### Группы из каталога { #groups-from-the-directory }

По умолчанию группы человека — это DN в его атрибуте `memberOf`. Каталог без
`memberOf` можно опрашивать: задайте `LDAP_GROUP_BASE_DN` и `LDAP_GROUP_FILTER` с
`{dn}` или `{username}` внутри. Для вложенных групп Active Directory ищите
правилом сопоставления, которое идёт по цепочке:

```bash
LDAP_GROUP_BASE_DN=OU=Groups,DC=corp,DC=example,DC=com
LDAP_GROUP_FILTER=(member:1.2.840.113556.1.4.1941:={dn})
```

Чтобы вообще пускать на вход только одну группу, впишите её в
`LDAP_USER_FILTER`:
`(&(objectClass=user)(sAMAccountName={username})(memberOf=CN=AgenticOS Users,OU=Groups,DC=corp,DC=example,DC=com))`.

## Встроенный вход Windows (Kerberos) { #integrated-windows-sign-in-kerberos }

На машине в домене браузер, открытый на узел, которому доверяет его политика,
отвечает на `WWW-Authenticate: Negotiate` билетом Kerberos. При
`KERBEROS_ENABLED=true` страница входа предлагает кнопку, которая вводит человека
с этим билетом, и никто не вводит пароль.

Билет называет принципала, `jane@CORP.EXAMPLE.COM`. AgenticOS разрешает его через
тот же каталог, с помощью `LDAP_KERBEROS_FILTER` (по умолчанию
`(userPrincipalName={principal})`), в **ту же учётную запись**, до которой доходит
вход по паролю LDAP. Поэтому Kerberos нужен и `LDAP_URL`, а адрес и группы каталог
определяет одинаково для обоих способов.

Что для этого нужно:

1. **Образ, собранный с дополнением `kerberos`.** `gssapi` компилируется против
   системных библиотек Kerberos, поэтому его нет в образе по умолчанию:
   `docker build --build-arg EXTRAS="--extra kerberos" -f backend/Dockerfile .`
2. **Служебный принципал и его keytab.** В Active Directory создайте служебную
   учётную запись, выдайте ей SPN `HTTP/agenticos.corp.example.com` и
   экспортируйте keytab командой `ktpass`. Смонтируйте его в контейнер backend.
3. **Настройки backend.**

    ```bash
    KERBEROS_ENABLED=true
    KERBEROS_KEYTAB=/etc/agenticos/http.keytab
    KERBEROS_SERVICE_PRINCIPAL=HTTP/agenticos.corp.example.com@CORP.EXAMPLE.COM
    ```

4. **Кнопка** — с `kerberos` в `OAUTH_PROVIDERS` у frontend и
   `KERBEROS_DISPLAY_NAME=Windows sign-in`, если хотите назвать её так.
5. **Политика браузера**, которая разрешает ему согласовывать аутентификацию с
   узлом API. Это локальная зона интрасети в Windows, `AuthServerAllowlist` для
   Chrome и Edge или `network.negotiate-auth.trusted-uris` для Firefox.

Служебный принципал должен называть узел, по которому браузер обращается к
**API**. Это `PUBLIC_API_URL`, потому что согласование происходит там, а не на
узле консоли.

Браузер, который не может ответить на запрос, сразу возвращается на страницу
входа с пояснением. Это касается любой машины вне домена и любого браузера, в
политике которого этого узла нет. Билет принимается, только если проверка
проходит за один шаг. NTLM не предлагается.

## Через провайдера идентификации { #through-an-identity-provider-instead }

Если в вашей компании перед каталогом уже стоит провайдер идентификации,
направьте AgenticOS на него по
[OIDC](configuration.md#single-sign-on-generic-oidc). Используйте его claim групп
для сопоставлений. Встроенный вход по LDAP и Kerberos тогда не нужен. Это же
ответ и для многофакторной аутентификации, которую встроенный вход не
поддерживает.

**Keycloak** объединяет оба. В разделе **User federation** добавьте провайдер
**LDAP** для своего каталога и включите там **Allow Kerberos authentication**, если
нужен встроенный вход. Его **group-ldap-mapper** переносит группы каталога. Затем
выдайте клиенту AgenticOS маппер **Group Membership** с claim токена `groups` и
задайте:

```bash
OIDC_ISSUER=https://id.corp.example.com/realms/staff
OIDC_GROUPS_CLAIM=groups
```

Тогда группа каталога в сопоставлении — это то, что Keycloak кладёт в claim: путь
группы, например `/Finance`, или голое имя, если **Full group path** выключен.

**Microsoft Entra ID** с группами, синхронизированными из Active Directory,
кладёт claim `groups` в токен, как только в регистрации приложения он появится в
разделе **Token configuration**. По умолчанию он несёт object id каждой группы, и
сопоставляете вы именно этот id.

### Claim групп через OIDC { #the-groups-claim-over-oidc }

`OIDC_GROUPS_CLAIM` называет claim со списком групп человека. Пока он не задан,
входы через OIDC членства не трогают. Когда задан, каждый вход через собственного
провайдера экземпляра применяет сопоставления точно так же, как вход через
каталог. Вход через Google — никогда, потому что только собственному провайдеру
экземпляра доверено говорить, в каких его группах кто состоит.

Claim читается из ID-токена или из эндпоинта UserInfo, когда в токене его нет.
Если настроенный claim отсутствует, это читается как **групп нет**. Keycloak и
Okta опускают пустой список, а не присылают его, а человек, убранный из последней
группы, должен потерять то, что она давала. Если в токене claim нет и UserInfo
недоступен, вход вместо этого отклоняется: это ничего не говорит о группах
человека, а прочтение как «групп нет» отняло бы их у него.

`OIDC_GROUPS_CLAIM` и `LDAP_URL` нельзя задать вместе. Каждый сообщает группы в
своих идентификаторах, и каждый вход забирал бы членства, созданные другим,
поэтому процесс отказывается запускаться с обоими.

!!! warning "Переполнение списка групп Entra ID отклоняется"

    Свыше 200 групп Entra ID присылает указатель на Microsoft Graph вместо групп
    (`_claim_names`). Такой токен не говорит, в каких группах человек, поэтому
    вход отклоняется с пояснением, что исправить. Прочтение как «групп нет»
    лишило бы его всех членств, которые дал каталог, а игнорирование сохранило бы
    те, которые каталог мог отобрать. Настройте регистрацию приложения присылать
    **groups assigned to the application**.

## Чего это пока не делает { #what-this-does-not-do-yet }

- **Между входами каталог никто не перепроверяет.** Отключение учётной записи в
  каталоге останавливает её следующий вход, а следующий вход — это когда
  сопоставления читаются заново. Уже открытый сеанс живёт, пока не истечёт его
  токен обновления, то есть `REFRESH_TOKEN_EXPIRE_MINUTES`, по умолчанию семь
  дней.
  Чтобы закончить его раньше, деактивируйте учётную запись в разделе
  **Администрирование → Пользователи** (Admin → Users): это отклоняет её везде и
  сразу. SCIM нет, и синхронизации каталога по расписанию тоже.
- **Учётная запись каталога всё ещё может пользоваться сбросом пароля и
  волшебной ссылкой.** Они уходят на адрес учётной записи, как и у любой другой.
  Если каталог должен быть единственным путём внутрь, держите эти адреса под
  контролем компании, как и для учётных записей OIDC.
- **SAML нет.** Провайдер идентификации, работающий только по SAML, может
  добраться до AgenticOS через Keycloak, который говорит с ним по SAML, а с
  AgenticOS — по OIDC.

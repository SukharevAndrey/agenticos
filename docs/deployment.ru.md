# Сам экземпляр { #the-deployment-itself }

Большая часть этого продукта — про агентов. Эта страница — про то, внутри чего они
работают.

**Одна установка — с названием, знаком, правилом о том, кому можно к ней
присоединиться, и выключателем, который её закрывает.** Всё это живёт в одной строке
базы данных, и его правит из `/admin/settings` тот, у кого есть `is_app_admin`, — без
повторного развёртывания, без переменной окружения, без пересборки.

!!! info "Почему это полномочие, а не разрешение"

    Разрешение действует в пределах организации. Эта строка ни в одной организации не
    лежит.

    Это то же полномочие, которое уже администрирует пользователей и организации во
    всём экземпляре.

Консоль делит эти настройки на разделы **Название и оформление** (Identity), **Доступ
и учётные записи** (Access & accounts), **Объявления и обслуживание** (Announcements &
maintenance), **Голос и мобильное приложение** (Voice & mobile) и **Обновления и
диагностика** (Updates & diagnostics). У каждого раздела есть URL с параметром `?section=`,
которым можно поделиться. Переход по ссылке на другой раздел сохраняет несохранённые
правки. **Сохранить** (Save) применяет изменённые поля всех разделов; **Отменить
изменения** (Discard changes) возвращает сохранённые значения. Загрузка изображений и
учётные данные push-уведомлений сохраняются сразу, своим действием.

## Название и оформление { #identity }

| Поле | Где показывается |
|---|---|
| Название | Боковое меню, шапка страницы входа, вкладка браузера, карточка OpenGraph и каждое письмо, которое отправляет этот экземпляр |
| Слоган | Рядом с названием в заголовке вкладки и в предпросмотре общей ссылки |
| Описание | Описание страницы и предпросмотр ссылок |
| Логотип | Везде, где появляется название, — ссылка на бренд, шапка страницы входа, правовые страницы |
| Favicon | Вкладка браузера |
| Текст в подвале | Под формой входа |
| URL условий, URL политики конфиденциальности | Каждая ссылка, которая иначе ведёт на встроенные страницы `/legal/*` |

!!! note "Столбец со значением null означает *встроенное*, а не *пустое*"

    Оператор, очищающий поле, хочет вернуть значение по умолчанию, а не шапку входа
    без названия. API отвечает *переопределениями*, а каждый рендерер подставляет
    вместо null своё встроенное значение.

У оператора, который ни разу не открывал страницу, строки нет вовсе. Консоль
подставляет вместо null `APP_NAME` и `SITE` из `frontend/src/lib/`; бэкенд подставляет
`settings.PROJECT_NAME` в письмах, которые отправляет сам.

Две константы для одного названия продукта могут разойтись, поэтому
`backend/tests/test_deployment_settings.py` закрепляет их равенство. Тест читает
`constants.ts` фронтенда и сравнивает его со значением класса `Settings.PROJECT_NAME`
по умолчанию — та же договорённость, что у `TestFrontendToolCatalog` с каталогом
инструментов.

### Два изображения { #the-two-images }

Загружаются через `POST /api/v1/admin/settings/{logo,favicon}` и хранятся так же, как
любое другое изображение на этой платформе: байты уходят в настроенное файловое
хранилище, а ключ — в столбец. **Ключ никогда не берётся из тела запроса**:
вызывающий, который мог бы его назвать, сумел бы направить публичный логотип этого
экземпляра на что угодно из хранилища — а имя сохранённого файла создаётся из
проверенного типа содержимого, а не из имени загруженного файла, потому что эти файлы
отдаются с того же origin, где работают страницы самого приложения, и `logo.html` там
— это скрипт.

JPEG, PNG, WebP и GIF до 2 МБ — это единственное определение «изображения, которое
платформа принимает».

!!! danger "SVG намеренно отсутствует"

    Это документ, который может нести скрипт, а эти файлы отдаются с того же origin,
    где работают страницы самого приложения. ICO не даёт ничего такого, чего не даёт
    favicon в PNG.

Ответ с фирменным оформлением несёт **версию**, а не URL. Адрес постоянный
(`GET /api/v1/branding/{logo,favicon}`), а байты отдаются как `immutable` на год,
поэтому клиенту нужно из строки только то, есть ли изображение и когда оно последний
раз менялось; `?v=`, собранный из этого, — единственная причина, по которой замена
вообще появляется. URL пришлось бы переписывать каждому клиенту, ведь в любом
настоящем экземпляре API находится не на том же origin, что страницы.

## Экземпляр в среде с требованиями соответствия { #a-deployment-inside-a-compliant-environment }

`deploy/profiles/hipaa/` — это готовая конфигурация для работы там, где действуют
технические меры защиты HIPAA: оверлей compose, который отказывается запускаться
без настроек, для которых у него нет значения по умолчанию, и env-файл с
комментариями, — плюс `agenticos cmd doctor --profile hipaa`, который сверяет
работающий экземпляр с этой конфигурацией и завершается с ненулевым кодом при любой
невыполненной мере защиты.

Это доказательство, а не сертификация, и оно отвечает только за §164.312:
административные и физические меры защиты — забота оператора. См.
[Профиль HIPAA](security.md#the-hipaa-profile-and-what-it-does-not-claim) — там таблица
и строка о том, кто такой business associate.

## Заголовки безопасности { #security-headers }

Каждая страница консоли несёт Content-Security-Policy и обычные заголовки усиления
защиты, заданные в `frontend/src/lib/csp.ts` и
`frontend/src/lib/security-headers.ts`; и то и другое проверяется тестами. Политика —
`default-src 'self'`, где `connect-src` называет ровно этот origin, `PUBLIC_API_URL` и
`PUBLIC_WS_URL`, `img-src` разрешает `data:` для фирменных значков и аватаров,
`frame-src` разрешает `'self'` и `blob:` для предпросмотра документов и маршрута
содержимого приложений (`{ARTIFACT_ORIGIN or PUBLIC_API_URL}/api/v1/artifact-content/`),
`object-src
'none'`, `base-uri 'self'` и `frame-ancestors 'none'`. Маршрут содержимого
назван путём, а не origin, поэтому фрейм может загрузить опубликованную страницу и
ничего другого из того, что отдаёт API; см.
[Как изолирована страница](artifacts.md#how-the-page-is-isolated).

В `script-src` нет `'unsafe-inline'`. Промежуточный слой создаёт nonce для каждого
запроса, вписывает `'nonce-…' 'strict-dynamic'` в директиву, а Next проставляет этот
nonce своим встроенным скриптам — поэтому внедрённый в страницу скрипт не имеет nonce
и не выполняется. `'unsafe-eval'` остаётся, потому что он нужен среде выполнения Next в
режиме разработки.

Политику проставляет промежуточный слой фронтенда при каждом запросе, потому что оба
публичных URL читаются из окружения сервера во время выполнения, а заголовок, заданный
при сборке, мог бы называть только `localhost`. Остальные заголовки постоянны и
задаются конфигурацией Next. Измените публичные URL — и политика изменится со
следующим запросом; ничего не пересобирается.

Рядом с ней стоят `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
`Referrer-Policy: strict-origin-when-cross-origin` и `Permissions-Policy`, который
запрещает камеру и геолокацию и разрешает микрофон только на этом origin — для
распознавания речи в чате.

!!! warning "Обратный прокси не должен добавлять свои копии этих заголовков"

    Nginx, Traefik или ALB перед приложением пропускают их без изменений, а не задают
    свои. Два заголовка `Content-Security-Policy` в одном ответе браузер объединяет в
    пересечение, поэтому прокси, добавляющий второй — даже более мягкий, — только
    ужесточает политику до состояния, в котором блокируется панель, которую никто не
    собирался блокировать; а второй `X-Frame-Options` позволяет браузеру выбрать любое
    из значений. Поставляемый `nginx/nginx.conf` задаёт только
    `Strict-Transport-Security`, который принадлежит тому, что завершает TLS;
    существующая конфигурация прокси, добавляющая остальные, должна их убрать.

## Кто может зарегистрироваться { #who-may-register }

`signup_mode` применяется в `app/services/signup_policy.py` — в одном месте, и от него
зависят **все** пути, создающие учётную запись: форма регистрации и вход через
провайдера удостоверений. В обратном вызове OAuth или OIDC ничто не выглядит как
регистрация, и экземпляр с единым входом и закрытой формой регистрации не был бы
закрыт вовсе, если бы эта ветка оставалась без проверки, поэтому
`get_or_create_oauth_user` спрашивает ту же политику, прежде чем создать учётную
запись. Отклонённый вход через SSO возвращает на страницу входа с той же формулировкой
политики, какую показывает форма регистрации.

| Режим | Действие |
|---|---|
| `open` | Регистрироваться может любой. Значение по умолчанию и то, чем был каждый экземпляр до появления этой возможности. |
| `invite_only` | Только адрес, который какая-либо организация действительно пригласила. |
| `closed` | Не регистрируется никто и никаким путём — приглашение это не отменяет. |

Во всех трёх режимах непустой `allowed_email_domains` сужает круг тех, кто может
зарегистрироваться вообще. **Приглашение переопределяет этот список**: тот, у кого
есть `members:invite`, назвал адрес намеренно, а список доменов — это политика
экземпляра для посторонних, а не вето на осознанное действие. `closed` не
переопределяется ничем, потому что «закрыто», пропускающее часть регистраций, — не
закрыто.

**Сопоставление группы каталога считается приглашением.** Первый вход через каталог
(LDAP или Kerberos) или через OIDC с утверждением о группах, чьи группы совпадают с
сопоставлением какой-либо организации, допускается и при `invite_only`, и по списку
доменов: тот, кто составил сопоставление, имел `members:manage` и
`roles:manage`, и решил, что все в этой группе свои. `closed` всё равно отклоняет его.
См. [Сопоставления групп каталога](directory.md#directory-group-mappings).

**`closed` значит закрыто, и пути «администратор создаёт учётную запись» нет.**
Намеренно: учётной записи нужен пароль, который выбрал её владелец, поэтому добавить
человека — значит открыть регистрацию *для него*, для этого и есть `invite_only`.
Режим, позволяющий администратору создавать учётные записи, стал бы третьим таким
путём, а два существующих — вся причина, по которой `signup_policy` — это модуль, а не
проверка внутри `register`. Поэтому экземпляр, которому нужно впустить ещё одного
человека, переключается на `invite_only` и приглашает его.

Ещё три вещи, в которых легко ошибиться, — и ошибались:

**Первый пользователь допускается всегда.** В свежей установке нет учётных записей.
Первая зафиксированная учётная запись становится администратором экземпляра
(`is_app_admin`), создана ли она паролем или через OAuth. Блокировка транзакции отдаёт
это исключение только одной одновременной регистрации. Последующая регистрация должна
удовлетворять настроенной политике; если первая откатится, начальные полномочия может
получить другая.

**`invite_only` существует потому, что закрытие регистрации иначе сломало бы
приглашения.** `InvitationService.accept` требует уже вошедшего пользователя, поэтому
приглашённому нужно сначала зарегистрироваться. Политика спрашивает
`invitation_repo.first_pending_admitting`, который по построению межорганизационный:
регистрация происходит раньше, чем выбрана организация. Безопасность
держится на том, куда уходит ответ: политика превращает его в булев отказ, поэтому
посторонний, пробующий форму регистрации, узнаёт, что адрес кто-то пригласил, и
никогда — какая организация.

**Как распознаётся приглашение, зависит от того, несёт ли регистрация его токен**, и
два ответа покрывают разные случаи:

| Приходит с | Распознаётся по | Какие случаи допускает |
|---|---|---|
| Токеном (взятым из отложенного приглашения, никогда из тела регистрации) | `invitation_admission.admits` | Любое действующее приглашение, которое допускает этот адрес, — включая ссылку, не ограничивающую **никакого** адреса, а такой случай больше ничто не видит |
| Без токена | `invitation_repo.first_pending_admitting` | Приглашение по почте для этого адреса или ссылка, ограниченная его доменом |

Токен — единственное доказательство для ссылки, которой можно поделиться и на которой
нет ни адреса, ни домена. Запрос по отправленному адресу такую ссылку не распознает,
поэтому выполнить её *без* доказательства обладания значило бы превратить одну
открытую ссылку где угодно в экземпляре в открытую регистрацию для всего интернета.
Обладание токеном и есть доказательство.

Токен, который не указывает ни на что действующее, уступает место вопросу об адресе, а
не отказу: устаревшая ссылка в закладке не должна превращать регистрацию, которая иначе
была бы разрешена, в ошибку из-за того, что человек не может исправить.

**Регистрация с токеном не принимает приглашение.** Она допускает учётную запись и
ничего больше; вступление в организацию по-прежнему делает `InvitationService.accept`,
который клиент вызывает, когда у него есть сеанс. Токен в неаутентифицированном теле
регистрации, который вдобавок давал бы членство, был бы выдачей доступа к членству на
публичном маршруте.

Консоль никогда не проносит токен через цикл входа. Приглашённый без учётной записи
открывает `/invitations/<token>`; `AuthGuard` обменивает токен на сервере на
непрозрачный дескриптор, который держит в cookie с `httpOnly`, недоступной браузеру, и
отправляет человека на `/login?returnTo=/invitations/pending?flow=…` — точку входа, в
которой нет учётных данных, поэтому токена нет ни в `returnTo`, ни в истории браузера,
ни в хранилище сеанса. Если обмен не удался — сервер недоступен, сработал лимит
частоты, — `AuthGuard` остаётся на ссылке приглашения и предлагает попробовать снова,
а не уходит ни с чем, ведь ссылка — единственные учётные данные, которые есть у
приглашённого.

`flow` — случайный идентификатор, который обмен создаёт при каждом откладывании, и
cookie называется по нему. Это не учётные данные: без cookie он ничего не называет. Он
нужен потому, что одно фиксированное имя cookie — это одно место: две
ссылки-приглашения, открытые рядом без входа, перезаписывали друг друга, и обе
ожидающие вкладки потом погашали вторую. Теперь каждая вкладка погашает ровно ту
cookie, которую называет её собственный `flow`.

«Создать учётную запись» тянет за собой эту точку входа без учётных данных, а прокси
регистрации передаёт отложенный дескриптор названного `flow` заголовком, поэтому допуск
при регистрации получает нужный токен, а сам токен никогда не попадает ни в URL, ни в
тело. После входа страница ожидания погашает дескриптор и принимает приглашение — та же
форма, что обмен кода OAuth: непрозрачная одноразовая временная замена учётных данных с
истечением срока, чтобы сами учётные данные никогда не ехали в URL. Cookie очищается,
когда погашение выполнено; ответ 401, 429 или сбой сервера оставляет её, потому что
дескриптор может быть ещё не потрачен и для повтора он нужен.

**Ссылка с `max_uses` ограничивает учётные записи, а не только вступления.**

`used_count` считает принятия, а принятие требует сеанса, поэтому потолок, прочитанный
только по нему, не ограничивал ничего, что делала регистрация. Одна одноразовая ссылка,
выложенная в канал, допускала столько учётных записей, сколько кому угодно было
создать, — на экземпляре, который только что закрыл регистрацию.

Поэтому использование сначала **резервируется** за регистрирующимся адресом:
`reserved_emails` в строке, и «использовано» означает `used_count + reserved_emails`.
Резервирование — один условный `UPDATE`, иначе две регистрации, гоняющиеся за последним
использованием, прочитали бы один и тот же счётчик.

Принятие убирает адрес из списка одновременно с увеличением счётчика, и это сохраняет
использование: тот, кто зарегистрировался по одноразовой ссылке, всё ещё может вступить.

Резервирование, за которым так и не пришли, остаётся потраченным (`max_uses` — сколько
людей ссылка допускает, а учётная запись, созданная по ней, была допущена) и умирает
вместе с приглашением.

**Вход через провайдера тоже несёт приглашение, в виде его дескриптора.** Вход через
провайдера начинается на том же origin, по адресу `/api/oauth/<provider>/login`, чтобы
отложенный дескриптор `httpOnly` можно было приложить к межсайтовому переходу, который
браузер затем делает: `/oauth/google/login?invitation_handle=…`, а бэкенд заглядывает в
него за токеном, который держит в сеансе на время цикла. Токена в этом URL нет никогда.
Без этого `invite_only` отклонял кнопку Google ровно для тех ссылок, которым нужен
токен, — не ограничивающих ни адреса, ни домена, — а форма с паролем рядом принимала
того же человека.

**Вход через провайдера — тоже регистрация.** `get_or_create_oauth_user` — второй путь,
создающий учётную запись, и в обратном вызове Google ничто не выглядит как регистрация,
поэтому экземпляр с `closed` и кнопкой Google был настежь открыт, пока не закрыли и то
и другое. Того, у кого учётная запись *уже* есть, заново не проверяют: закрытие
регистрации закрывает регистрацию, а не пустить участника в экземпляр, которому он
принадлежит, настройка не требует.

Форма регистрации читает политику из публичного эндпоинта оформления и сообщает
правило **до** того, как кто-то начнёт печатать. Форма, которая принимает адрес, а
потом сообщает «этот домен почты не может зарегистрироваться», лжёт: посетитель никак
не может знать, что правило существует, и читает отказ как поломку продукта. Поэтому
разрешённые домены и публикуются: они не секрет, а экземпляр стоит на собственном
хосте компании.

## С чего начинает новая учётная запись { #where-a-new-account-starts }

Это решают две настройки рядом с режимом регистрации, обе в разделе **Новые учётные
записи** (New accounts) на `/admin/settings`, и обе действуют на учётные записи,
созданные позже: существующая личная организация сохраняется (#2156).

| Настройка | По умолчанию | Действие |
|---|---|---|
| `personal_organizations` | включено | Каждая новая учётная запись получает собственную организацию, где она сама — Owner. |
| `default_organization_id` | нет | Каждая новая учётная запись вступает в эту организацию с ролью `default_organization_role`. |
| `default_organization_role` | `member` | Любая роль, кроме `owner`; настройка, делавшая каждого новичка владельцем, раздала бы им всем ключи компании. |

Экземпляр, открытый для независимых людей, оставляет значения по умолчанию. Экземпляр
для одной компании отключает личные организации и указывает организацию компании,
чтобы коллега начинал там, где лежат агенты и знания компании, и никто не запускал
агентов со своим бюджетом, политикой согласования и журналом аудита отдельно от неё.
Личная организация не может быть организацией по умолчанию, а удаление организации по
умолчанию сбрасывает настройку.

**Приглашение в организацию по умолчанию важнее.** Приглашение называет свою роль, а
принять приглашение в организацию, где человек уже состоит, нельзя, поэтому новичок,
регистрирующийся с приглашением в организацию по умолчанию или с ожидающим
приглашением для своего адреса, при регистрации в неё не вступает. Он вступает, когда
принимает приглашение, с его ролью.

**В организацию по умолчанию человек попадает только по правилу самого экземпляра.**
Учётная запись, допущенная самим режимом регистрации — открытый экземпляр, адрес в
разрешённом домене, — вступает в организацию по умолчанию. Та, что допущена только
приглашением другой организации или сопоставлением каталога, — нет: руководители той
организации поручились за человека перед своей организацией, а вступление в организацию
по умолчанию позволило бы им добавлять людей в организацию, которой они не управляют.

**В организацию по умолчанию попадает и сеанс.** Запрос с токеном сеанса и без
`X-Organization-Id` действует в организации по умолчанию, если человек в ней состоит,
затем в его личной, затем в его единственной. Человек, у которого есть выбор и нет
заголовка, получает `400` с именем заголовка вместо догадки — см.
[заголовок организации](api.md#the-organization-header). Консоль выбирает ту же
организацию, когда не выбрано ничего другого, а принятие приглашения переключает
консоль на организацию, в которую человек вступил.

## Как найти одну организацию среди всех { #finding-one-tenant-among-all-of-them }

`GET /admin/organizations` — единственное место, где можно узнать, *какие организации
существуют*, и он доступен только администратору экземпляра как раз потому, что
полезен: он по построению охватывает все организации. Он отдаёт страницу организаций с
числом участников и агентов в каждой и её самым ранним владельцем — к кому по ней
обращаться. Все поля владельца пусты разом, если последний владелец организации ушёл, а
это состояние может исправить только администратор экземпляра, поэтому ему его и
показывают.

| Параметр | |
|---|---|
| `search` | Название, слаг или адрес владельца. Строка поиска — текст, а не шаблон: `100%` находит организацию с таким названием, а не все подряд |
| `sort_by` | `name`, `slug`, `members`, `agents`, `created_at`. Всё остальное — 422 |
| `sort_dir` | `asc` / `desc`, по умолчанию сначала новые |
| `kind` | `personal`, `team` или `all`. При регистрации каждой учётной записи выдаётся личная организация, если экземпляр это не отключил, поэтому в большинстве экземпляров они составляют большую часть списка |
| `skip`, `limit` | Одна страница сервера, до 100 |

**Всё это происходит в SQL, до `OFFSET`/`LIMIT`**, и `total` считает то, до чего сузили
выборку, а не весь экземпляр. В этом разница между сортировкой и её видимостью:
страница, отсортированная после получения, заявляет порядок по всей коллекции, которого
пятьдесят строк дать не могут, — поэтому список организаций у администратора вообще не
имел элементов управления, пока маршрут не отвечал ни на что (#921). Порядок разрешает
совпадения по id, поэтому листание столбца, где у строк одинаковое значение,
перечисляет каждую из них один раз.

Столбец вне набора отклоняется с указанием имени, а не сопоставляется ни с чем, по двум
причинам, по которым его отклоняет `GET /runs`: пустая страница читается как *в этом
экземпляре нет организаций*, а `ORDER BY`, собранный из строки запроса, — это
поверхность для инъекции.

## Администратор экземпляра не может закрыть себе доступ к экземпляру через консоль { #an-app-admin-cannot-lock-the-deployment-out-through-the-console }

!!! warning "Самоблокировка, которую это предотвращает"

    В установке с одним администратором, которую создаёт `make platform-bootstrap`,
    случайное нажатие на собственную строку прекращало администрирование, пока
    кто-нибудь не добирался до терминала. Восстановление —
    `agenticos cmd create-app-admin <email>` из оболочки; адрес почты — обязательный
    аргумент.

`is_active` проверяется на следующем запросе, а `is_app_admin` — то, что читают страницы
администрирования, поэтому администратор экземпляра, действующий на **своей** строке из
`/admin/users`, мог бы завершить свой сеанс, лишиться `/admin` или удалить учётную
запись. `UserService.admin_update` и `admin_delete` отклоняют самоблокировку и
самоудаление, а
панель не предлагает для вашей строки **Заблокировать** (Suspend), **Снять
администратора** (Demote) или **Войти как пользователь** (Impersonate) — удаление
остаётся видимым и отклоняется, потому что у вопроса «почему я не могу удалить себя»
есть ответ, который стоит показать. API тоже отклоняет работу от собственного имени:
работа от своего имени не является входом от имени другого пользователя.

Через API экземпляр вообще нельзя оставить без администратора: единственное глобальное
полномочие выдаётся только из CLI (`agenticos cmd create-app-admin`), и нет запроса,
который его снимает, поэтому набор администраторов экземпляра уменьшается только
удалением — а удаление *последнего* и есть удаление себя, которое отклоняется. Снятие
администратора, который действительно уходит, — действие другого администратора, и это
же сохраняет журнал аудита читаемым. Восстановление, если оно когда-нибудь
понадобится, всё так же `create-app-admin` из оболочки на экземпляре.

Это рассуждение про *набор*, а код какое-то время был про одну строку.

Двое администраторов удаляли друг друга — и ни один не удалял себя. Они блокировали разные
целевые строки, не сталкивались и оба зафиксировали транзакцию — ноль администраторов
экземпляра, восстановить можно только записью в базу данных (#1208).

Поэтому удаление администратора берёт `SELECT ... FOR UPDATE` по набору администраторов
экземпляра, упорядоченному по id, ещё до принятия решения. Второй запрос ждёт,
перечитывает набор после фиксации первого и отклоняется, потому что опустошил бы его.

Упорядоченно, потому что два запроса, берущие одни и те же строки в разном порядке, —
это взаимоблокировка, а не очередь. И берётся оно при каждом удалении администратора, а
не только при удалении самим администратором: удаление пользователя — действие
администратора, а не горячий путь, и полный порядок важнее того состязания за блокировки,
которого он стоит.

## Работа от имени другой учётной записи { #acting-as-another-account }

**Войти как пользователь** (Impersonate) на `/admin/users` начинает работу от имени
этого человека из вашего собственного браузера. Ничего никуда не копируется: консоль
меняет cookie доступа сеанса на ту, что называет цель, каждая страница отрисовывается
так, как её увидел бы он, а полоса сверху говорит, чья это учётная запись и кто на самом
деле действует, и содержит единственную кнопку, которая это прекращает.

Вход от имени другого пользователя — это **сеанс**, а не просто учётные данные. Токен
называет строку в `sessions` с заполненным `impersonator_user_id`, и API отклоняет его,
как только эта строка завершена или истекла либо тот, кто стоит за ней, больше не
действующий администратор экземпляра, — поэтому он прекращается, когда вы нажимаете **Завершить
работу от имени** (End impersonation), когда человек выходит на всех устройствах или
меняет пароль, когда истекает час или когда администратора блокируют, снимают или
удаляют — что наступит раньше. Обновить его нельзя: окно — это срок жизни самого токена
доступа, и час — потолок, а не возобновляемая аренда.

!!! note "Открытый диалог в чате заканчивается вместе с ним"

    Диалог в чате идёт по WebSocket, который аутентифицируется один раз, при
    рукопожатии. Теперь та же проверка повторяется при каждом сообщении, поэтому
    завершение работы от имени — или блокировка учётной записи — закрывает и открытый
    чат, а не только отклоняет следующий HTTP-запрос, пока сокет продолжает отвечать.

!!! note "В списке устройств самого человека его нет"

    Вход от имени другого пользователя — это строка под его id, которой владеет
    администратор, а не устройство, с которого он входил, поэтому его нет ни в списке
    устройств, ни в счётчике открытых сеансов на панели, ни в «последней активности».
    Сообщают ли человеку вообще — решает настройка ниже, а строка в том списке решила
    бы это за него.

**Сообщают ли человеку, решает политика, заданная в этой строке.**
`notify_impersonated_users` по умолчанию выключена; включённая, она разово отправляет
человеку письмо в начале работы от его имени с именем администратора. Журнал аудита
записывает такой вход в любом случае — и начало, и конец, вместе с сеансом, к которому
они относятся, — как и описывает [Управление](governance.md#audit).

## Объявления и закрытие экземпляра { #notices-and-closing-the-deployment }

**Объявление** — это одна фраза в одном из трёх стилей, которая показывается над
каждой страницей вошедшим пользователям, пока они его не закроют. Это единственное
поле этой строки, которого *нет* в публичном эндпоинте: объявление — это оператор,
говорящий людям, которые пользуются экземпляром, — об окне обновления, о том, к кому
обращаться, — поэтому у него свой маршрут, `GET /api/v1/branding/notice`, за сеансом.

Закрытие привязано к **самому сообщению** в собственном хранилище браузера. Флаг сделал
бы следующее объявление невидимым для всех, кто закрыл предыдущее; отметка времени в
строке настроек снимала бы закрытие при каждом переименовании экземпляра. Изменился
текст — значит, ключом служит текст. Хранилище, которое отказывается читаться или
писаться, — режим приватности, встроенный webview, — означает «ничего не закрыто», а не
исключение: выброшенное во время отрисовки, оно уронило бы «Обзор» у каждого
вошедшего пользователя, а баннер всё равно закрывается, пока страница открыта.

**Режим обслуживания закрывает API**, а не только консоль. `app/core/maintenance.py` —
это чистый ASGI-промежуточный слой над маршрутами, поэтому уже открытая страница
перестаёт работать — в этом вся разница между режимом обслуживания и баннером. Его
список разрешённых путей короток, и его проверяют по каждой записи:

- `/health*` — проверка готовности, которая падает во время окна, — это оркестратор,
  перезапускающий контейнер, в котором работает оператор.
- `/api/v1/branding` — закрытая страница должна уметь сказать, как называется этот
  экземпляр и почему он закрыт.
- `/api/v1/auth/*` — администратор должен уметь войти **пока** окно открыто.
- `/api/v1/admin/*` — и затем добраться до выключателя.
- Документация и схема OpenAPI, которые не отдают данных.

Всё остальное — 503 с `Retry-After`. Он не читает сеанс вовсе: это означало бы проверять
токен над графом зависимостей, поэтому расширение пути до `/api/v1/admin/*` не расширяет
полномочий: `CurrentAppAdmin` отклоняет неадминистратора там ровно так же, как всегда.

**При сбое он пропускает.** Шлюз, который не может прочитать собственный выключатель —
сбой Redis, невыполненная миграция, — пропускает трафик, потому что альтернатива
превращает сбой инфраструктуры в полный простой, которого никто не планировал.

Вердикт кэшируется в Redis, который и так делят все воркеры: запись делается **после
фиксации**, поэтому выключатель срабатывает сразу, а кэш никогда не может показать
состояние, которое база данных откатила. Опубликованный заранее, он оставлял бы экземпляр
открытым на время до истечения TTL после запроса, который затем откатился, — хотя окно
обслуживания так и не выключилось. У вердикта есть и TTL
в 30 секунд, поэтому запись, не дошедшая до Redis, лечится сама, а не оставляет
экземпляр открытым всё запланированное окно.

**И уже открытая страница узнаёт об этом.** Контекст оформления вычисляется один раз
корневым серверным макетом и не меняется до конца жизни страницы, поэтому открытое после
этого окно оставляло каждую вкладку на «Обзоре», где каждый запрос уже начал
отвечать 503, и на экране не было ничего о причине — а закрытие окна оставляло вкладку
на экране обслуживания, пока кто-нибудь не перезагружал её. `GET /api/v1/branding/notice`
несёт вердикт обслуживания рядом с объявлением и опрашивается раз в минуту: один запрос
на оба ответа вместо двух, которые могут разойтись насчёт одной строки.

В консоли администратор видит полосу, а не закрытую страницу. Он единственный, кто может
завершить окно, а режим обслуживания, который вдобавок скрывает выключатель, — это
простой.

## Сколько может занимать одна учётная запись { #how-much-one-account-may-take-up }

Два потолка, оба в той же строке и оба **по умолчанию null, и null — это отсутствие
предела, а не «не настроено»**. Самостоятельно размещаемый экземпляр для одной компании
не хочет ни одного из них; экземпляр, открытый для регистрации, хочет оба, потому что
иначе одна учётная запись может без ограничений создавать организации.

| Настройка | Считает | Не считает |
|---|---|---|
| Организации на учётную запись | Организации, которыми учётная запись **владеет**, включая личную | Те, куда её пригласил кто-то другой |
| Агенты на организацию | Агентов, которые есть у организации | Агентов в архиве |

**Проверяется каждый переход в подсчитываемое состояние, а не только создание.** Потолок,
который действует только на новые строки, обходят сбоку: организация на пределе числа
агентов отправляет одного в архив, создаёт замену и восстанавливает отправленного, а
учётной записи на пределе числа организаций передают чужую через `transfer_ownership`.
Поэтому `unarchive` и `transfer_ownership` задают тот же вопрос, что и `create`.

**И счётчик берётся под блокировкой.** Чтение `count(...) >= limit` и затем запись — это
два оператора, поэтому два запроса оба проходят проверку счётчика и оба вставляют строку:
потолок превышен закономерно, двумя нажатиями. Ни одно ограничение не выражает «не больше
N таких строк», поэтому `app/db/locks.py` берёт рекомендательную блокировку в пределах
транзакции на *субъекта* потолка: два запроса об одной учётной записи встают в очередь,
запросы о разных учётных записях никогда не встречаются, а блокировку снимает фиксация или
откат. Только там, где предел задан, поэтому экземпляр без потолков ничего не платит.

Оба исключения — суть замысла, а не его подробности. Приглашение в десять организаций —
чужое решение, а потолок, которым человек не управляет, не даёт ему создать собственную. А архив — это способ вывести агента из работы: потолок, который выведенный
агент продолжал бы занимать, сделал бы удаление единственным способом вернуться под этот
потолок, а оно забирает с собой историю версий и привязку запусков.

Отказ называет потолок и счётчик, с которым его сравнили (`{"limit": 5, "held": 5}`),
поэтому на «почему нельзя» отвечает сам ответ, а не память администратора. Он
выбрасывается в сервисе, который создаёт вещь, а не в маршруте, потому что маршрут — не
единственный вход.

Консоль не ждёт этого отказа. `GET /agents/ceiling`, доступный вызывающему с
`agents:edit`, отвечает пределом (`limit`, null там, где он не задан) и тем, упрётся ли в
него создание (`at_limit`), а на пределе страница агентов отключает **Новый агент** (New
agent) и установку шаблонов и говорит почему — до того, как кто-то заполнит форму.

Если во время пошагового создания агента предел заполнит другое создание, пошаговое
создание заканчивается, а не замораживает страницу вокруг отключённой кнопки. Успешное
создание из этого прохождения записывается до обновления потолка, поэтому занятие
последнего места не прерывает оставшиеся шаги в Конструкторе.

Сам счётчик (`held`) уходит только вызывающему, чей `agents:view` достаёт до каждого
агента организации: он включает агентов, которых Member не видит, и в сравнении с
собственным списком сказал бы, сколько от него скрыто. **Дублировать** (Duplicate) и
**Восстановить** (Restore) по-прежнему отклоняются только при попытке. Отказ остаётся
гарантией: счётчик — это прогноз, прочитанный без блокировки.

Ноль отклоняется схемой: учётная запись, которой нельзя владеть ни одной организацией, —
это учётная запись, которую нельзя создать, ведь регистрация даёт каждой личную
организацию.

## В каком виде можно загрузить диктовку { #what-a-dictation-may-be-uploaded-as }

`dictation_compressed_audio`, **по умолчанию выключенная**, задаёт формат каждой
[диктовки](ml-services.md#dictation-in-chat) в экземпляре — в поле ввода `/chat`, на
размещённых страницах и в виджетах, во всех организациях. Выключенная, она оставляет
серверу один формат: WAV с моно PCM 16 кГц и 16 битами, который записывает каждый браузер.
Его длина равна его размеру, 32 000 байт в секунду, поэтому сервер считает отсчёты, и
самая длинная диктовка точно ограничивает стоимость одной записи.

Включённая, она принимает ещё WebM, Ogg и MP4, и загрузки примерно в восемь раз меньше.
Их длину читают из заголовка самого файла, а собранный вручную файл может её занизить:
тогда одна диктовка может нести примерно в сорок раз больше самой длинной диктовки в
пределах лимита размера. На [публичной странице или
в виджете](channels.md#what-it-costs-and-what-bounds-it) её может отправить любой, у
кого есть ссылка, — за счёт учётной записи провайдера организации и вне любого бюджета.

Поэтому переключатель на `/admin/settings` сначала спрашивает. Включение открывает диалог,
называющий эти риски, и делает кнопку подтверждения доступной только после того, как
отмечен пункт о том, что их прочитали; выключение ничего не спрашивает. В любом случае оно
сохраняется вместе с остальной формой и попадает в аудит, как любое другое поле. Браузеры
следуют ему в следующий раз, когда страница спрашивает: формат, в котором они записывают,
— тот, что объявляет сервер, а не список, хранимый в клиенте.

## Строка { #the-row }

Одна строка на всю установку, охраняемая базой данных, а не соглашением, которого никто
не видит: `singleton` уникален и ограничен значением true, поэтому вторая идентичность —
это `IntegrityError`, а не экземпляр, у которого тихо две строки и который отдаёт ту,
которую запрос вернул первой. Запись — один `INSERT ... ON CONFLICT DO UPDATE`, потому что
чтение с последующей вставкой гоняет само себя, как только два администратора сохраняют
из двух вкладок.

**Ничего не засевается.** Нет строки — значит, всё по умолчанию, и это ровно состояние
экземпляра, который никто не настраивал, — и это важно, потому что публичный эндпоинт
оформления не требует аутентификации и вызывается при каждой холодной загрузке страницы,
поэтому чтение с созданием строки позволило бы постороннему спровоцировать `INSERT`.

Каждая запись попадает в аудит в `app_admin_audit_logs` с именами **полей** и никогда с
их значениями: объявление и список доменов — оба текст оператора, а строка аудита живёт
дольше тела запроса, из которого пришла.

## Отказ от этого экземпляра всегда выглядит одинаково { #a-refusal-from-this-deployment-always-looks-the-same }

Стоит сказать здесь, потому что закрытие экземпляра — та возможность, которая скорее
всего выдаст отказ, какого человек никогда не видел. `app/api/exception_handlers.py`
складывает **каждый** отказ в `{"error": {"code", "message", "details"}}`:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Agent not found",
    "details": { "agent_id": "…" }
  }
}
```

Это покрывает доменные исключения, валидацию схемы, а с #917 и `HTTPException`, то есть
ответ 405, несовпавший путь и двадцать два маршрута, которые выбрасывают его напрямую. Две
формы в протоколе означают, что каждый вызывающий либо обрабатывает обе, либо молча
ошибается на одной.

Запрос с неправильным методом раньше отвечал **500** вместо 405 на каждом маршруте.
Инструментирование FastAPI в OpenTelemetry выводит имя спана, обходя `app.routes`, и его
ветка `Match.PARTIAL` — а это ровно «путь совпадает, а метод нет» — читает `.path` без
проверки; FastAPI 0.141 кладёт в этот список объекты `_IncludedRouter`, а у них такого
нет. `app/core/otel_compat.py` подставляет для этой ветки тот же запасной вариант,
который upstream уже использует в ветке, где он проверку делает. В upstream
это не исправлено и на 0.65b0, а `tests/test_otel_route_details.py` падает, когда
исправят, — тогда модуль и уйдёт.

## Фоновые задачи { #background-jobs }

**Администрирование → Фоновые задачи** (Admin → Background jobs)
(`/admin/background-jobs`) — это очередь, как её видит владелец экземпляра, и открыть её
может только администратор экземпляра: очередь принадлежит экземпляру, поэтому владельцу
организации в ней отказывают. Шапка считает задачи в каждом состоянии, называет
приостановленный вид задач и причину, перечисляет живые воркеры и время следующего
срабатывания каждого расписания. Ниже — задачи, сначала новые, с фильтром по состоянию и
пулу, каждая со своими попытками и ошибкой, на которой она в последний раз закончилась.

Под счётчиками **Активность** (Activity) показывает графиком, что завершилось за последние
24 часа или 7 дней, с разбивкой по тому, как оно закончилось, рядом с самым долгим
ожиданием задачи, срок которой уже наступил. **По типам** (By kind) даёт объём каждого
типа, сколько его задач завершилось без повторов, время выполнения по медиане и 95-му
процентилю и сколько его задачи ждали воркера: растущее ожидание говорит, что пулу нужно
больше воркеров. «Обзор» показывает тот же день карточкой.

Три действия, каждое попадает в аудит вместе с тем, кто его выполнил:

- **Повторить** (Retry) даёт задаче без повторов свежий набор попыток. Индексации
  документа без повторов отказывают: её копия для разбора ушла вместе с ней, поэтому
  повторите документ из его базы знаний — она разберёт сохранённый файл заново.
- **Отменить** (Cancel) отзывает задачу, которую никто не начал.
- **Возобновить** (Resume) снова позволяет воркерам брать приостановленный вид задач.

Вид задач приостанавливается предохранителем воркера: его задачи убили своего воркера
`WORKER_BREAKER_DEATHS` раз подряд — чаще всего это документ, при разборе которого
закончилась память. Каждому владельцу сообщают в приложении и письмом, и уведомление нельзя
отключить: работа такого вида копится, пока один из них её не возобновит. Пауза называет
организацию, чьи задачи её вызвали, а для всех остальных вид продолжает работать.
Повторяйте задачи без повторов только после того, как причина устранена, иначе они умрут
так же; а индексацию документа без повторов вместо этого запустите из его базы знаний.
Настройки — в разделе [Конфигурация](configuration.md#background-work).

## Итог { #recap }

- Идентичность экземпляра — **одна строка**, которую правят из `/admin/settings`, а
  столбец со значением null означает *встроенное*, а не *пустое*.
- `signup_mode` применяется в **одном месте** и закрывает оба пути, создающие учётную
  запись. Приглашение переопределяет список доменов; `closed` не переопределяет ничто.
- Новая учётная запись получает **личную организацию, если это не отключено**, и
  вступает в **организацию по умолчанию**, когда она задана; сеанс без организации тоже
  попадает туда.
- Администратор экземпляра **не может закрыть себе доступ к экземпляру** через консоль.
- **Работа от имени другого пользователя — это сеанс**: начинается из консоли без токена
  в буфере обмена, называется в полосе сверху, заканчивается администратором, выходом
  человека на всех устройствах или истечением часа. Сообщают ли человеку, решает
  `notify_impersonated_users`, по умолчанию выключенная.
- Диктовка — **сырой PCM, если не включена `dictation_compressed_audio`**, а включает её
  администратор только после диалога о том, во что она обходится.
- Каждый отказ от этого экземпляра выглядит одинаково, какой бы слой его ни породил.

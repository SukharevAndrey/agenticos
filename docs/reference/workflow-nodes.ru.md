# Узлы сценария { #workflow-nodes }

Каждый шаг, который может содержать сценарий: чем он настраивается, что читает,
что производит и что означает сбой. Палитра в редакторе перечисляет те же узлы
из того же реестра. Документация по полям ниже сгенерирована из исходного кода.

Для каждого узла действуют несколько правил:

- **Связь задаёт порядок, привязка несёт значение.** Входные поля узла
  привязаны к более ранним выходам, к литералу или к ссылке на файл или
  таблицу. См. [Настройка узла](../workflows.md#configuring-a-node).
- **Путь внутрь значения произвольной формы проверяется при запуске узла.**
  Полезная нагрузка триггера, сопоставленная запись и структурированный ответ
  агента не имеют фиксированной формы, поэтому привязка вроде `payload.email`
  принимается при публикации и проверяется по своей цели, когда узел
  отправляется на выполнение. Значение, которое не подходит, завершает запуск с
  ошибкой `INVALID_BINDING`, и обработчик его не видит.
- **Ресурсы проверяются дважды.** Публикация отклоняет коллекцию, версию
  агента, учётные данные или получателя, до которых автор графа не может
  добраться. Каждый запуск проверяет их снова по собственному субъекту запуска,
  потому что доступ может быть отозван между делом.
- **Вид эффекта и повторы** решают, что движок может сделать после сбоя. Шаг
  `pure` или `idempotent` повторяется. Шаг, который уже мог сработать и ничего
  не гарантирует, вместо этого останавливается ради человека. Собственная
  [политика](#error-handling) узла задаёт, сколько раз его повторять, сколько
  может длиться вызов и куда уходит сбой.

## Триггеры { #triggers }

Сценарий начинается с одного триггера — узла, с которого начинается его граф.
Публикация версии включает её триггер; см.
[Запуск сценария извне консоли](../workflows.md#starting-a-workflow-from-outside-the-console).
Каждый триггер передаёт следующим за ним шагам то, с чем запуск пришёл через
его способ запуска; вход фиксируется при допуске запуска и не превышает
`WORKFLOW_RUN_MAX_INPUT_BYTES`. Тестовый запуск, начатый со входом другой формы,
завершает триггер с ошибкой `TRIGGER_INPUT_INVALID`. Второй триггер или триггер
не в начале графа отклоняется при публикации.

### core.input { #core-input }

**Запрос API** (API request). Запускается HTTP-запросом или через WebSocket.
Отдаёт графу вход запуска как `payload`, что бы ни прислал вызывающий, и
называет способ запуска в `triggered_by`. Его идентификатор остаётся
`core.input`, поэтому граф, написанный до того, как «Вручную» и API
разделились, по-прежнему начинается с API.

::: app.workflows.contracts.io.WorkflowInputPayload

Его **Поля входа** (Input fields) делают вход контрактом. У поля есть имя, тип —
текст, список текстов, число, целое число, да или нет, дата или выбор — и
признак обязательности. Без полей и без схемы запуск принимает любой объект
JSON. С полями **Запустить сценарий** (Start a run) спрашивает каждое поле по
имени; запуск, во входе которого нет одного из полей, есть поле не того типа
или есть необъявленное поле, отклоняется до начала с ошибкой
`WORKFLOW_RUN_INPUT_INVALID`, а привязка к `payload.<field>` проверяется по
типу при публикации.

**Список текстов** (List of text) (`string_list`) принимает массив JSON из
строк, например `{"devices": ["leaf-01", "leaf-02"]}`. Скаляры и элементы не из
строк отклоняются. API принимает пустой массив; обязательное поле должно
присутствовать и не может быть `null`, а необязательное можно опустить или
передать как `null`. Следующие шаги читают `payload.devices` как массив строк.

Через **Запустить сценарий**, **Проверить черновик** (Test draft) и публичные
формы вводите по одному элементу в строке. Форма обрезает пробелы в каждой
строке и выбрасывает пустые строки, сохраняя порядок и повторы. Пустой
обязательный список требует хотя бы одного элемента; пустой необязательный
список опускается. Значения из API сохраняются точно, включая пробелы и пустые
строки. Тот же тип поля есть у триггеров **Вручную** (Manual), **Форма** (Form)
и **Вызов из сценария** (Called by a workflow).

::: app.workflows.contracts.fields.InputField

#### Контракты входа JSON Schema { #json-schema-input-contracts }

Для вложенного входа задайте в триггере `config.input_schema` документ JSON
Schema Draft 2020-12. **Запрос API**, **Вручную** и **Вызов из сценария**
принимают эту альтернативу простым `fields`. Используйте один контракт за раз:
схему и непустой список `fields` совмещать нельзя. Публичные триггеры **Форма**
сохраняют свой контракт простых полей.

Контракт поддерживает вложенные объекты, массивы объектов, `enum`, `required`,
длины строк (`minLength` и `maxLength`), длины массивов (`minItems` и
`maxItems`) и `additionalProperties`. Повторно используйте определения через
`$defs` и локальные ссылки `$ref`. Ссылки должны разрешаться внутри того же
документа; внешние ссылки отклоняются и никогда не запрашиваются. Абсолютный
или относительный URI допустим, если он разрешается в ресурс, уже заданный в
документе. Своя модель Python или фреймворк вызывающего не нужны.

Вход сценария всегда объект JSON. Публикация отклоняет контракт, если его явные
корневые `type`, `const`, `enum`, статический локальный `$ref` или ограничения
`allOf`/`anyOf`/`oneOf` доказывают, что его не может удовлетворить ни один
объект. Эта осторожная проверка совместимости не доказывает, что схема
выполнима вообще: ограничения с `not`, условиями или `$dynamicRef` могут
остаться нерешёнными и проверяются по фактическому входу при допуске.
Примитивные подсхемы и подсхемы массивов по-прежнему поддерживаются внутри
свойств объекта.

Поместите эту конфигурацию в триггер, чтобы принимать клиента и одну или
несколько строк заказа:

```json
{
  "input_schema": {
    "$schema": "https://json-schema.org/draft/2020-12/schema",
    "type": "object",
    "properties": {
      "customer": {
        "type": "object",
        "properties": {
          "name": {"type": "string", "minLength": 1, "maxLength": 120},
          "tier": {"enum": ["standard", "priority"]}
        },
        "required": ["name"],
        "additionalProperties": false
      },
      "items": {
        "type": "array",
        "minItems": 1,
        "maxItems": 100,
        "items": {"$ref": "#/$defs/line"}
      }
    },
    "required": ["customer", "items"],
    "additionalProperties": false,
    "$defs": {
      "line": {
        "type": "object",
        "properties": {
          "sku": {"type": "string", "minLength": 1},
          "quantity": {"type": "integer", "minimum": 1}
        },
        "required": ["sku", "quantity"],
        "additionalProperties": false
      }
    }
  }
}
```

Публикация фиксирует схему внутри версии сценария. Вход проверяется по
контракту этой версии до допуска запуска, в том числе при вызовах через API,
WebSocket, MCP и из дочернего сценария; тесты используют контракт черновика.
Неверный вход возвращает `WORKFLOW_RUN_INPUT_INVALID` с путями полей и
сообщениями. Схема не приводит значения к типу и не подставляет значения по
умолчанию. Без простых полей и без схемы, включая пустой объект схемы,
сохраняется прежний нетипизированный вход — объект JSON.

Размер самой схемы ограничен 256 KiB при публикации. До допуска сериализованный
запрос проверки JSON, содержащий схему и вход, должен укладываться в 1 MiB.
Проверка идёт в изолированном процессе со сроком в две секунды, включая
запуск. Каждый цикл событий API или воркера допускает не более двух
одновременных проверок; когда оба места заняты, допуск отклоняется сразу с
`429`. Существующие контракты простых полей по-прежнему проверяются на месте.

Linux дополнительно применяет предел адресного пространства в 256 MiB и предел
CPU. Разработка на нативном macOS сохраняет пределы CPU и реального времени, но не
имеет предела адресного пространства, потому что Darwin не поддерживает
`RLIMIT_AS`.

Тайм-аут, исчерпание памяти валидатора или предел размера протокола проверки
отклоняют допуск с `422 WORKFLOW_RUN_INPUT_INVALID`, указывая `input` в
`error.details.fields`, а `validation_limit` — как `type` проблемы в прежнем
формате.
Сбой запуска валидатора, аварийное завершение (в том числе принудительное из-за
предела ресурсов ОС) или неверный вывод возвращают
`503 WORKFLOW_INPUT_VALIDATION_UNAVAILABLE`. Ни один из отказов не создаёт
запуск. Диагностика ограничена 50 записями и 4 KiB JSON в UTF-8. Когда
достигнут любой из пределов, последняя запись обобщает усечение. Диагностика
никогда не цитирует присланные значения.

Схемы или регулярные выражения, превышающие пределы вложенности или повторений
валидатора, отклоняются при публикации, а не приводят к ошибке сервера.

Вызывающие могут посмотреть действующий контракт до выполнения через
[API входной схемы сценария](../api.md#running-a-workflow) или
[обнаружение MCP](../mcp.md#workflow-and-table-tools). Существующие контракты
простых полей тоже предоставляются как JSON Schema.

Обнаружение по HTTP показывает только первую точку входа **Вызов из
сценария**, причём точка входа по умолчанию идёт первой, потому что вызовы из
дочернего сценария не могут выбрать другую. Обнаружение MCP платформы
показывает только точки входа «Вручную» и «Запрос API», которые поддерживает
его инструмент запуска.

Отдельно стоящие ветки `then`/`else` и ветки, исключённые литеральным булевым
`if`, проверяются на безопасность ссылок, но не создают связей рекурсии при
выполнении.

Контракты с `$dynamicRef` при проверках публикации ограничены 2048 контекстами
разрешения и 64 разными ресурсами в динамической области видимости. Превышение
любого из пределов даёт явный отказ конфигурации.

### trigger.manual { #trigger-manual }

**Вручную** (Manual). Запускается человеком — кнопкой **Проверить черновик** в
редакторе или **Запустить сценарий** на странице запусков сценария. Графу
передаётся то же, что и у **Запрос API**, и принимаются те же поля входа или
контракт JSON Schema. Редактор спрашивает вход до начала запуска.

### trigger.chat { #trigger-chat }

**Сообщение в чате** (Chat message). Запускается сообщением в чате, когда для
ответа выбран этот сценарий. Текст его `core.output` записывается обратно в
этот диалог.

::: app.workflows.nodes._triggers.ChatTriggerOutput

### trigger.webhook { #trigger-webhook }

**Вебхук** (Webhook). Запускается подписанной доставкой на собственный адрес
сценария, который создаётся при первой публикации узла вместе с секретом
подписи.

До публикации **Ждать тестовый вызов** (Listen for test event) на панели
«Вывод» триггера открывает тестовый URL для черновика на две минуты.
Единственный вызов, отправленный на него, — объект JSON — закрепляется как вывод
триггера, так что каждый следующий за ним шаг можно проверить на реальной
доставке. Тестовый URL не проверяет подпись и никогда не создаёт запуск.

::: app.workflows.nodes._triggers.WebhookTriggerOutput

### trigger.schedule { #trigger-schedule }

**Расписание** (Schedule). Запускается по часам, в часовом поясе сценария и не
чаще раза в минуту.

::: app.workflows.nodes._triggers.ScheduleTriggerConfig

::: app.workflows.nodes._triggers.ScheduleTriggerOutput

### trigger.table_record { #trigger-table-record }

**Запись таблицы** (Table record). Запускается, когда запись её таблицы
добавлена, изменена или удалена — смотря что называют её `events` — и
соответствует каждому фильтру. Изменение запускает его, только если изменился
один из столбцов, выбранных для таблицы, когда такие столбцы выбраны. Публикация
требует доступа на чтение к таблице.

::: app.workflows.nodes._triggers.TableRecordTriggerConfig

::: app.workflows.nodes._triggers.TableRecordTriggerOutput

### trigger.workflow_call { #trigger-workflow-call }

**Вызов из сценария** (Called by a workflow). Запускается шагом
`workflow.run` другого сценария, с контрактом входа, который объявляет, —
простыми полями или JSON Schema, как у **Вручную**, — и никогда вручную или
через API. Вход вызывающего проверяется по этому контракту до начала запуска.

### trigger.form { #trigger-form }

**Форма** (Form). Запускается, когда кто-то заполняет публичную страницу
сценария по ссылке, которую создаёт первая публикация узла. Страница показывает
его название, описание и по одному полю ввода на каждое поле — те же поля, что
у **Вручную**, — а отправка, которая им соответствует, начинает запуск от имени
участника, опубликовавшего сценарий. `triggered_by` равен `form`.

::: app.workflows.nodes.trigger_form._handler.FormTriggerConfig

### trigger.github { #trigger-github }

**GitHub.** Запускается доставкой, которую GitHub подписывает для репозитория:
одним из событий и — если они названы — одним из действий, которые называет
узел. Публикация регистрирует хук через подключённую учётную запись GitHub
организации, когда может, или один раз показывает секрет, чтобы его вставили.
`triggered_by` равен `github`.

::: app.workflows.nodes.trigger_github._handler.GithubTriggerConfig

::: app.workflows.nodes._triggers.GithubTriggerOutput

### trigger.gmail { #trigger-gmail }

**Gmail.** Запускается новым сообщением в подключённом почтовом ящике Gmail
организации, которое соответствует каждому заданному фильтру; ящик
опрашивается с интервалом **Проверять новую почту каждые** (Check for new mail
every) — по умолчанию минута. Публикация отклоняется, пока не подключён
почтовый ящик. `triggered_by` равен `gmail`. **Отправитель содержит** (Sender
contains) совпадает с адресом отправителя, а не с отображаемым именем:
`@acme.com` — ровно этот домен, без его поддоменов. С ним сообщение должно ещё
пройти проверку подлинности отправителя (DMARC или подпись DKIM от домена
отправителя). Письма с ярлыками `SENT`, `DRAFT`, `SPAM` или `TRASH`
пропускаются, если **Ярлык** (Label) не называет именно этот ярлык.

Вывод несёт цепочку — `thread_id`, `rfc_message_id`, `in_reply_to`,
`references`, `received_at` — и тело `html`, прочитанное до 20 000 символов.
Поля заголовков пишет отправитель, поэтому они связывают ответ в цепочку и
ничего не доказывают о том, кто отправил письмо.

Запуск, начатый почтовым ящиком, сохраняет вложения сообщения как файлы запуска,
но только когда сценарий их читает: граф, который не привязывает ни
`attachments` триггера, ни весь его вывод, оставляет каждое вложение
`not_fetched`. Каждый сохранённый файл идёт в счёт квоты файлов организации, а
писать на триггер без **Отправитель содержит** может кто угодно, поэтому
привязывайте `attachments`, только когда файлы нужны шагу.

Ящик перечисляет не более 20 вложений на сообщение, и рассматриваются только
первые 10 из перечисленных — вместе до 25 MiB, каждое в пределах лимита
размера загрузки в чат, списка разрешённых типов файлов и квоты хранения
организации. Пропущенное вложение сохраняет своё место в `attachments` с полем
`reason`: `too_many`, `too_large`, `type_not_allowed`, `quota`, `unreadable`
или `not_fetched`. Запуск, начатый не ящиком, — тестовый запуск, — ничего не
читает, поэтому каждое вложение `not_fetched`.

`unreadable` — это ответ 400, 401, 403 или 404 на вложение либо выданный доступ
к ящику, которого нет, который отключён или не продлевается. Любой другой сбой
провайдера завершает шаг с ошибкой `MAIL_ATTACHMENT_UNREACHABLE`, и она
повторяется. Оба почтовых триггера принимают вход извне.

::: app.workflows.nodes.trigger_gmail._handler.GmailTriggerConfig

::: app.workflows.nodes._triggers.EmailTriggerOutput

::: app.workflows.nodes._triggers.MailAttachment

### trigger.outlook { #trigger-outlook }

**Outlook.** Запускается новым сообщением в папке подключённого почтового
ящика Microsoft 365 организации, которое соответствует каждому заданному
фильтру; ящик опрашивается с интервалом **Проверять новую почту каждые** — по
умолчанию минута. Публикация отклоняется, пока не подключён почтовый ящик.
`triggered_by` равен `outlook`. Microsoft Graph читается по одной папке за раз,
поэтому **Папка** (Folder) и **Общий почтовый ящик** (Shared mailbox) задают и
то, куда смотрит опрос, и фильтр, а первое чтение папки начинается с момента,
когда сценарий опубликован или последний раз включён. Указание общего ящика,
который может открыть выданный доступ Microsoft организации, требует
разрешения на управление подключениями, как и для триггеров агента Outlook; оно
нужно при каждой публикации, которая его указывает, потому что публикующий
становится участником, от имени которого читается ящик, а сообщение, пришедшее
в сценарий, чей публикующий больше не имеет этого разрешения, не начинает
запуск. **Отправитель содержит** совпадает с адресом отправителя, как и в
Gmail, и требует, чтобы домен отправителя прошёл проверку подлинности или
письмо пришло изнутри клиента. Папка или общий ящик, про которые Outlook
говорит, что их нельзя прочитать, выключают сценарий и оставляют
`mailbox_folder_unreadable` в журнале аудита. Опрос пропускает сохранённую
конфигурацию, которая больше не проходит проверку. Вложения готовятся так же,
как для [trigger.gmail](#trigger-gmail), а `labels` содержит категории
сообщения. Его вывод — тот же, что у [trigger.gmail](#trigger-gmail).

### trigger.channel_message { #trigger-channel-message }

## data.value { #data-value }

**Данные** (Data) хранят одно значение для последующих шагов: объект, список
или отдельное число, текст или булево значение. Введите его как JSON или
привяжите целиком из более раннего вывода. Шаг передаёт его дальше без
изменений как `value`, а более поздний шаг привязывается ко всему значению или к
пути внутрь него, например `value.customer.email`.

Значение задаётся один раз за запуск и никогда не перезаписывается. Вывод шага
фиксируется, когда шаг завершается, поэтому ни один последующий шаг не может
его изменить: «Данные» — именованная константа, а не переменная. Чтобы изменить
значение, добавьте шаг, который строит из него новое. Чтобы собрать значения из
элементов цикла, используйте `loop.yield`. Запуск черновика шага «Данные» без
значения завершается с ошибкой `DATA_NOT_SET`.

## text.compare { #text-compare }

**Сравнить тексты** (Compare texts) оценивает, насколько похожи два текста, `a`
и `b`: 1 — когда они совпадают после того, как отброшены игнорируемые различия,
0 — когда у них нет ничего общего. Шаг не вызывает модель и ничего не стоит, и
одни и те же два текста всегда дают одни и те же числа (оценки округляются до
шести знаков). **Метод** (Method) говорит, что считается:

- `char_ratio` (по умолчанию) — доля символов, которых редактору не пришлось бы
  касаться, по точному редакционному расстоянию между символами.
- `token_f1` — доля слов, общих для двух текстов, без учёта порядка.
- `line_diff` — доля неизменённых строк.

Составные и разложенные диакритические знаки никогда не считаются правкой, как
и концы строк. Остальное — дело шага. **Без учёта пробелов** (Ignore whitespace)
включено по умолчанию: оно схлопывает пробелы внутри строки, обрезает пробелы по
краям каждой строки и отбрасывает пустые строки. Переносы строк по-прежнему
учитываются, поэтому только `token_f1`, который считает слова, не смотрит, где
кончается строка. **Без учёта регистра** (Ignore case) и **Без учёта знаков
препинания** (Ignore punctuation) по умолчанию выключены. Слова в `token_f1` —
это последовательности букв, цифр и подчёркиваний: он разбивает по апострофам и
не размечает текст, написанный без пробелов.

**Без цитируемой почты и подписей** (Leave out quoted mail and signatures)
отбрасывает каждую строку, первый непробельный символ которой — `>` (включая
цитаты с отступом), строку с автором цитаты над цитатой и всё после разделителя
подписи `-- ` или голого `--`, а также после строки
`----- Original Message -----`. Это эвристика для почты в виде простого текста:
она не ловит цитаты в HTML, ответ, цитата в котором не помечена `>`, строку с
автором цитаты, перенесённую на две строки (она остаётся), или подпись без
разделителя.

Каждый текст — не более 100 000 символов, считая до любого нормализующего
преобразования; сравнение двух текстов такого размера занимает несколько секунд.
Более длинный текст завершает запуск с `INVALID_BINDING` до выполнения шага,
поэтому `error.handle` не может его перенаправить. Шаг, у которого не привязано
ничего к `a` и `b`, завершается с ошибкой `TEXT_COMPARE_NOT_CONFIGURED`; если
привязан один, а другой нет, запуск завершается с `INVALID_BINDING`. Пустые
тексты допустимы: два пустых текста дают оценку 1, один пустой — 0. Палитра
рисует шаг значком сравнения, среди шагов с данными.

::: app.workflows.nodes.text_compare._handler.TextCompareConfig

## html.parse { #html-parse }

Начиная с 1.72.0 селекторы документов и извлечение ссылок исключают инертное
содержимое `<template>`. Выбор самого `template` по-прежнему возвращает его
HTML и текст. Soup Sieve 4 также приводит селекторы состояния формы в
соответствие с поведением браузера; при обновлении проверьте сценарии, которые
зависят от прежних правил сопоставления. Сопоставление селекторов кэшируется;
ограничения времени и памяти при чтении остаются.

**Разобрать HTML** (Parse HTML) читает HTML в текст, ссылки и элементы, которые
выбирает CSS-селектор. Он для HTML, который встречает сценарий: тела письма,
тела ответа `http.request`, страницы, сохранённой через `http.download`.
`text.extract` читает документы, а не разметку — он отдал бы теги как текст.
Привяжите `html` (не более 2 000 000 символов) или `file` (не более 5 000 000
байт, проверяется до чтения файла), но не оба. Файл декодируется по маркеру
порядка байтов, по `<meta charset>` или по своим байтам, при необходимости с
потерями, и его объявленный тип не проверяется: PDF читается как искажённый
текст и не отклоняется. Символ NUL читается как U+FFFD.

У шага три вывода, каждый ограничен:

- `text` — читаемый текст в виде Markdown, обрезанный по **Макс. символов
  текста** (Most characters of text) (100 000, если не задано; `text_truncated`
  говорит, что он обрезан). Заголовки, списки и код остаются; скрипты, стили,
  меню (`nav`), подвалы и `<head>` — нет. Веб-коннектор коллекции знаний читает
  страницу так же. `title` — это `<title>` страницы, обрезанный до 500
  символов, или null, когда его нет (при пустом `<title>` тоже).
- `links` хранит каждую `a[href]` один раз, в порядке документа, с текстом её
  первого якоря (обрезанным до 500 символов). Ссылка разрешается относительно
  поля **Базовый адрес** (Base address), когда он задан, а без него сохраняется
  как написана. Ссылки на адреса `javascript:`, `vbscript:` и `data:`
  опускаются, так что более поздний шаг, запрашивающий все ссылки, никогда не
  получает скрипт; опускаются и `href` длиннее 2 048 символов, и такой, который
  нельзя прочитать как адрес. Сохраняется не более 500 ссылок, а просматриваются
  первые 5 000 якорей; `links_truncated` говорит, что на странице их было
  больше.
- `matches` хранит элементы, которые выбирает **CSS-селектор** (CSS selector),
  в порядке документа, не больше, чем задаёт **Макс. совпадений** (Most matches)
  (20, если не задано, до 200); `match_count` говорит, сколько выбрал селектор до
  обрезки. У каждого совпадения есть его `text` и внешний `html` (оба обрезаны до
  10 000 символов) и первые 50 `attributes`; многозначный атрибут вроде `class`
  соединяется пробелами, а каждое значение обрезается до 2 000 символов. Без
  селектора совпадений нет. Селектор, который не является допустимым CSS,
  отклоняется при публикации с указанием поля.

Ничего не загружается и ничего не выполняется. Ни изображение, ни таблица
стилей, ни **Базовый адрес**, ни ссылка не запрашиваются, скрипт — только текст,
а синтаксический анализатор взят из стандартной библиотеки, а не XML, поэтому ни
одна сущность не раскрывается извне страницы.

Разбор идёт в дочернем процессе с 20 секундами реального времени, пределом CPU
и пределом памяти, потому что селектор вроде `p div div` по глубоко вложенной
разметке может занять минуты. Когда 20 секунд истекают, дочерний процесс
завершается принудительно, а шаг завершается с ошибкой `HTML_TOO_COMPLEX`, которая не
повторяется. Работа для каждого якоря и каждого совпадения тоже ограничена,
поэтому одна страница не может сделать шаг медленным или его вывод большим.

| Что произошло | Результат |
|---|---|
| Нет настроек или нет входа | `HTML_PARSE_NOT_CONFIGURED` |
| `html` длиннее 2 000 000 символов, или привязаны и `html`, и `file` | `INVALID_BINDING`, до выполнения шага |
| Файл отсутствует или больше 5 000 000 байт | `FILE_NOT_FOUND`, `FILE_TOO_LARGE` |
| Ни один декодер не может прочитать байты, или процесс чтения погибает | `HTML_NOT_READABLE`, в подробности `reason` сказано, что именно |
| Страница занимает больше 20 секунд | `HTML_TOO_COMPLEX` |

`INVALID_BINDING` завершает запуск до выполнения шага, поэтому `error.handle` не
может его перенаправить; слишком большой файл — это `FILE_TOO_LARGE`, с которым
шаг завершается, а его перенаправить можно. Палитра рисует шаг значком кода,
среди шагов с данными.

::: app.workflows.nodes.html_parse._handler.HtmlParseConfig

::: app.workflows.nodes.html_parse._handler.HtmlParseOutput

## Преобразование { #transform }

Шаги **Преобразование** (Transform) меняют форму списка объектов без шага с
кодом. Каждый принимает `items` — список, привязанный к более раннему шагу, — и
большинство передаёт дальше `items`, поэтому они выстраиваются в цепочку.

| Шаг | Что делает |
|---|---|
| `transform.edit_fields` | Задаёт поля по выражениям JMESPath над каждым `item`, удаляет поля или оставляет только заданные |
| `transform.sort` | Сортирует по полям по очереди, по возрастанию или убыванию |
| `transform.limit` | Оставляет первые или последние элементы |
| `transform.remove_duplicates` | Оставляет первый из каждой группы элементов, равных по названным полям или по всему элементу |
| `transform.aggregate` | Собирает значения каждого поля по всем элементам в один список на поле, как `values` |
| `transform.split_out` | Превращает список внутри каждого элемента в отдельные элементы |
| `transform.summarize` | По группам считает количество, сумму, среднее, находит наименьшее или наибольшее или считает различные значения |
| `transform.date_time` | Сейчас или привязанный `value`, сдвинутый на величину, записанные в часовом поясе — часовом поясе сценария, если шаг не называет свой |
| `transform.crypto` | Хеширует или кодирует в base64 привязанный `text` либо создаёт UUID или случайный hex |

Поле — это путь через точку, `customer.email`, и элемент без него никогда не
ошибка. «Сортировать» ставит его в конец, «Удалить дубликаты» считает
«missing» собственным значением, «Агрегировать» и «Сводка» его опускают,
«Развернуть в элементы» оставляет элемент как есть, а «Изменить поля» ставит
`null` там, где выражение ничего не находит. «Криптография» не для секретов:
ничто в ней не использует ключ.

Выстроенные в цепочку, они отвечают на частые вопросы без шага с кодом:

- **Лучшие лиды, по одному** — **Удалить дубликаты** (Remove duplicates) по
  `email`, **Сортировать** (Sort) по `score` по убыванию, **Ограничить** (Limit)
  до 10, затем **Изменить поля** (Edit fields), оставив только `name` и `score`,
  — готово для сообщения.
- **Итоги по регионам** — **Развернуть в элементы** (Split out) `lines`, так что
  каждая строка заказа — элемент, затем **Сводка** (Summarize) `sum` по `amount`
  с группировкой по `region`: один элемент на регион с `sum_amount`.
- **Один список адресов** — **Агрегировать** (Aggregate) `email` передаёт
  `values.email`, все адреса в одном списке, для любой настройки, которая
  принимает список.

Каждый шаг читает `items` у предыдущего.
`tests/integration/test_workflow_transform_composed.py` запускает первые два как
есть.

## logic.if и logic.merge { #logic-if-and-logic-merge }

`logic.if` вычисляет условие JMESPath над привязанным `value` и продолжает по
порту `true` или `false`. Каждый узел на невыбранной ветке записывается как
`skipped`. `value` должен быть привязан: публикация и тестовый запуск черновика
отклоняют шаг без него; версия, опубликованная раньше, продолжает работать и
читает null.

`logic.merge` сводит ветки обратно. По умолчанию он ждёт, пока до него дойдёт
**Ветка, которая выполнилась** (The branch that ran): выполняется, когда эта
ветка до него доходит, и передаёт дальше вывод ветки как `value`. Публикация
проверяет, что это безопасно, и отклоняет соединение, входы которого могут
выполниться в одном запуске. Входы, которые выходят из одного шага через разные
порты, не могут выполниться в одном запуске, если шаг принимает ровно один порт
за запуск, — «Если / иначе», «Переключатель», шаг решений, `ai.classify`,
проверка таблицы, согласование или шаг, направляющий свои ошибки. Ветви разных
таких шагов, которые исключают друг друга, например вложенный «Если / иначе»,
разделяющий свою ветку else, тоже не могут.

Соединение может принимать два или больше портов такого шага напрямую, без
ничего между ними, например `needs_reply` и `unsure` у `ai.classify`: оно
выполняется один раз — для порта, который выбрал шаг. Две связи из одного порта
по-прежнему отклоняются.

Ветки, которые идут бок о бок, например ветви [Разделить](#logic-split),
требуют, чтобы **Ждать** (Wait for) было задано как **Все ветки** (All
branches) (`wait_for: all`). Тогда соединение выполняется, когда устоял каждый
вход, и передаёт дальше вывод каждой ветки в `branches` — объект по именам
веток, — а не в `value`. Ветка называется по своей записи `branch_keys`:
редактор заполняет её для каждой связи из имени шага или ветки «Разделить», а
шаг ниже читает `branches.<name>`. Публикация отклоняет имя, которого ни у чего
нет, и две ветки с одним именем.

Публикация также отклоняет **Все ветки**, когда какой-то вход не обязательно
придёт при каждом выполнении соединения (и называет этот вход), и когда может
выполниться только один вход, а для такого случая нужна **Ветка, которая
выполнилась**. `branches` хранится как результат любого шага: превышение
встроенного предела завершает шаг с ошибкой `NODE_OUTPUT_TOO_LARGE`, поэтому
передавайте файлы дальше ссылками.

Старый сохранённый граф, который ждёт все ветки, а доходит до него только часть
из них, завершает запуск с ошибкой `JOIN_INCOMPLETE`, называя соединение.
Публикация отклоняет такой граф; код остаётся страховкой. У `wait_for` и
`branch_keys` есть значения по умолчанию, поэтому соединение, сохранённое без
конфигурации, продолжает ждать ветку, которая выполнилась.

Любой шаг с несколькими входящими связями — это объединение, и соединение ему не
нужно. Он выполняется, когда устоял каждый шаг, который к нему ведёт, если хотя
бы одна связь жива, и пропускается, когда живых нет. Он пропускается и тогда,
когда источник сбоил без маршрута ошибки: этот сбой уже должен сообщить запуск.
Привязки объединения могут читать только шаги, которые наверняка выполнились до
него, поэтому объединение может читать каждый луч параллельной группы, но не
одну ветвь «Если / иначе».

Правило, категория, ветка или выбор, которые вы называете, становятся выходным
портом, поэтому имя не может повторять порт, который у шага уже есть: `in`,
`otherwise`, `other`, `default`, `approved` и `rejected` у шага, где они есть,
`unsure` у классификатора с минимальной уверенностью и `error` у шага,
направляющего свои ошибки. Редактор помечает имя, а публикация отклоняет его,
говоря, какое имя конфликтует и что его нужно переименовать.

Выражения умеют выбирать, фильтровать и сравнивать, а также вызывать
фиксированный набор чистых функций: `abs`, `avg`, `ceil`, `contains`,
`ends_with`, `floor`, `join`, `keys`, `length`, `max`, `merge`, `min`, `not_null`,
`reverse`, `sort`, `starts_with`, `sum`, `to_array`, `to_number`, `to_string`,
`type` и `values`. Null, `false` и пустая строка, список или объект ложны, а всё
остальное истинно, включая `0`. Выражение, которое не разбирается или вызывает
что-то другое, опубликовать нельзя.

## logic.split { #logic-split }

**Разделить** (Split). Направляет запуск по всем своим веткам сразу. У каждой
ветки есть имя, и оно же её выходной порт; веток от двух до двадцати. Ничего не
выбирается и никакое условие не читается: каждая ветка берётся всегда, а шаги
после них выполняются бок о бок. Шаг ничего не передаёт дальше, поэтому шаг в
ветке привязывается к тому, что выполнилось до «Разделить». Имя ветки не может
быть `in` или повторять имя, которое у шага уже есть.

«Разделить» не может направлять свои ошибки, потому что при сбое «Разделить» не
начинается ни одна ветка: публикация отклоняет `on_error: route` у него, а ошибки
направляют собственные шаги каждой ветки. Ветки снова встречаются у
[`logic.merge`](#logic-if-and-logic-merge), который ждёт их все, или у любого
шага, для которого они входы. Любой другой шаг тоже может отправить один порт
нескольким шагам, и те выполняются сразу, так же; «Разделить» даёт веткам имена
и держит их на виду.

::: app.workflows.nodes.logic_split._handler.LogicSplitConfig

## logic.switch { #logic-switch }

**Переключатель** (Switch). Направляет запуск по первой из многих веток, чьё
правило выполняется. У каждого правила есть имя, и оно же порт его ветки, и
условие JMESPath над привязанным `value`; правила проверяются по порядку, а
`otherwise` принимает запуск, когда не выполнилось ни одно. `value` должен быть
привязан: публикация и тестовый запуск черновика отклоняют шаг без него; версия,
опубликованная раньше, продолжает работать и читает null. Его ветки снова
сходятся у `logic.merge`, который ждёт выполнившуюся ветку, — публикация это
принимает, потому что берётся всегда ровно одна. Если правило не срабатывает на
своих данных, шаг завершается с ошибкой `CONDITION_FAILED`, и ошибка называет правило.

## Шаги с моделью { #model-steps }

Четыре шага спрашивают у одной из моделей организации одну вещь, без
инструментов. Каждый работает как собственный агент шага — создаётся при первом
запуске, публикуется заново при изменении настроек — через тот же механизм
выполнения, что и `agent.run`, поэтому `max_cost_usd` шага, бюджет сценария и
лимит организации проверяются до запроса, его стоимость записывается на запуск,
и он виден в «Активности». Публикация проверяет, что автор может пользоваться
моделью.

| Шаг | Что делает | Что передаёт |
|---|---|---|
| `ai.prompt` | Отвечает на привязанный `prompt` по `instructions` шага | `text`, а `structured`, когда `structured_output_schema` просит объект |
| `ai.classify` | Помещает привязанный `text` в одну из `categories` шага или в `other` | Выходит через порт категории, с `category`, `reason` в одно предложение, `text` и `confidence`; ниже `min_confidence` — через `unsure` |
| `ai.extract` | Извлекает поля, которые называет `output_schema`, из привязанного `text`, опуская то, чего там не сказано | `data`, объект такой формы |
| `ai.rewrite` | Пересказывает (`short`, `medium`, `long`), переводит на `language` или переписывает привязанный `text` в `style` | `text` |

Категории классификатора — его порты, по порядку, и модель может ответить только
одним из их имён или `other`. Ответ, который не является объектом, запрошенным
шагом, завершает шаг с ошибкой `STRUCTURED_OUTPUT_MISMATCH`; израсходованный
лимит — с `AGENT_BUDGET_EXCEEDED`.

Когда задан `min_confidence`, модель ещё сообщает свою уверенность в категории,
от 0 до 1. Это её собственное утверждение, а не вероятность, и оно не
откалибровано: проверьте порог на своих кейсах с помощью
[оценок](../workflows.md#evals-for-a-model-step) шага, прежде чем ему доверять.
Минимум добавляет порт `unsure` после `other`: ниже порога шаг выходит через этот
порт с тем же выводом, поэтому `category` остаётся и сценарий может её
использовать.

Без минимума у модели не спрашивают число, промпт не меняется, `confidence`
равен null, и категория всегда побеждает. Ответ без числа никогда не выходит
через `unsure`, а пока порт существует, `unsure` не может быть именем категории.

Шаг выходит ровно через один порт, поэтому `logic.merge` может снова свести его
ветки: пустите `unsure` и категорию по одному пути или две категории в один шаг
журнала.

## Решения { #decisions }

Три шага задают нативной модели решений типизированный вопрос о привязанном
`text`. Выберите профиль модели с его провайдером, ключом из хранилища секретов и
эндпоинтом. Существующие конфигурации с ключом TypeSafe и моделью Jev
по-прежнему загружаются без изменений. Возможности провайдера определяют, какие
формы вопросов принимаются.

Модель возвращает ответ и уверенность. Ниже `min_confidence` шаг идёт по
`unsure`; сценарий может передать вопрос человеку или выбрать другой путь. Нативные профили
используют OpenAI, Google, OpenRouter, TypeSafe или собственный эндпоинт
System One через Pydantic AI. О доступности провайдеров и отличии от оценок LLM
см. [модели решений](../models.md#decision-models).

| Шаг | Спрашивает | Выходит через |
|---|---|---|
| `decide.yes_no` | вопрос «да или нет» | `yes`, `no` или `unsure` |
| `decide.choose` | какой из до 255 вариантов подходит | `out` с `choice` или `unsure` |
| `decide.score` | где текст находится на шкале из 2–10 уровней | `out` с `score` или `unsure` |

Учётные данные и доступ проверяются при публикации и снова при каждом
выполнении. Удалённый унаследованный ключ даёт `SECRET_NOT_USABLE`; ненативный
профиль — `DECISION_MODEL_REQUIRED`. Сбои провайдера дают `DECISION_FAILED` по
политике повторов шага. Расходы идут в счёт бюджетов сценария и организации.
Соединить может снова свести ветки решений.

## Каналы { #channels }

У Slack, Mattermost и Telegram есть свои группы шагов, которые действуют как
один из ботов организации на этой платформе через адаптер, через который уже идут
его ответы, поэтому сообщение, отправленное сценарием, приходит от этого бота, а
шаг может прочитать то, что может прочитать бот. У платформы есть только те
шаги, которые могут выполнять её боты.

| Шаг | Slack | Mattermost | Telegram | Что передаёт |
|---|---|---|---|---|
| **Отправить сообщение** (Send a message) (`<platform>.message.send`) | да | да | да | куда отправлено |
| **Прочитать сообщения** (Read messages) (`<platform>.messages.read`) | да | да | - | `messages`, от старых к новым |
| **Список участников** (List members) (`<platform>.members.list`) | да | да | администраторы | `members`, с их идентификаторами на платформе |
| **Найти каналы** (Find channels) (`<platform>.channels.find`) | да | да | - | `channels` |

Шаг принимает только бота своей платформы, а бот говорит за всю организацию,
поэтому действие от его имени требует `channels:manage`: у автора графа — чтобы
опубликовать, у субъекта запуска — на каждом запуске. Бот, удалённый, выключенный
или с другой платформы, останавливает шаг с `CHANNEL_NOT_USABLE`. Платформа,
которая отказывает в вызове во время выполнения, завершает его с
`CHANNEL_UNSUPPORTED`, а та, что не отвечает, — с `CHANNEL_CALL_FAILED`. Отправка
никогда не повторяется сама по себе.

**Отправить сообщение** отвечает в ветке, когда задан `thread_id`: метка времени
ветки в Slack, идентификатор корневого сообщения в Mattermost или номер темы
форума в Telegram. Сообщение отправляется в эту ветку и никогда как ответ с
цитатой. Пустой `thread_id` отправляет в сам канал. Идентификатор канала или ветки
с `:` внутри, а также ветка Telegram, которая не является числом, завершает шаг
с `CHANNEL_TARGET_INVALID`, ничего не отправив.

## agent.run { #agent-run }

Спрашивает опубликованного агента, ровно в той версии, которую закрепляет шаг,
через тот же механизм выполнения, что и в чате и в API, с бюджетом агента,
согласованиями, защитными проверками и историей запусков. Запуск записывается со
способом запуска `workflow`. Привязанные `sources` добавляются к промпту как
нумерованный контекст. Вызов инструмента, требующий согласования,
приостанавливает шаг, и решение возобновляет тот же запуск агента.

Существующий инструмент `ask_user_question` тоже приостанавливает этот шаг.
Сценарий показывает `waiting_for_user`; карточка вопроса доступна в исходном
чате и в представлении запуска. Ответить может только тот, кого спросили.
Ответы сохраняются до того, как продолжение сценария ставится в очередь, и
возобновляют ожидающий вызов инструмента в рамках текущего бюджета сценария.
Перезагрузка страницы не отбрасывает вопрос. Отмена сценария закрывает его
ожидающие запуски агента; вопросы без ответа истекают через
`QUESTION_EXPIRY_HOURS` (по умолчанию 24).

Это относится к собственному агенту шага, когда за запуском стоит вошедший
пользователь. У запусков из публичных источников нет человека, которого можно
спросить. Агентам-исполнителям всё равно нужен действующий способ задать вопрос
человеку. Если модель объединяет вопрос с вызовом, требующим согласования,
согласование имеет приоритет, и этот вопрос считается отклонённым, когда
согласование возобновляет работу.

`inline` настраивает агента в шаге вместо `agent`, и задаётся ровно одно из
двух. Спецификация принадлежит шагу и версионируется вместе с графом: первый
запуск создаёт агента, которым владеет сценарий, не показывая его в каталоге и
открывая к нему доступ через доступ сценария; запуск, чья спецификация
отличается от новейшей версии этого агента, сначала публикует новую, с
проверками, как при публикации агента. Публикация сценария проверяет
спецификацию по доступу её автора. `max_cost_usd` ограничивает одно выполнение:
агент останавливается до запроса к модели, который вышел бы за него, а шаг
завершается с ошибкой `AGENT_BUDGET_EXCEEDED`.

Агент со своим форматом ответа передаёт свой объект как `structured`.
`structured_output_schema` просит вместо него другую форму: агент запускается с
этой схемой, а ответ, который её нарушает, отправляется модели на исправление.
Объект проверяется ещё раз, прежде чем выполнится что-либо ниже. Агент, который
так и не выдаёт подходящий объект, завершает шаг с ошибкой `AGENT_RUN_FAILED`, а
ответ без объекта там, где объект был запрошен, — с
`STRUCTURED_OUTPUT_MISMATCH`.

| Чем закончился запуск агента | Результат шага |
|---|---|
| Завершён | Завершён |
| Ожидает согласования | Ждёт, затем возобновляет тот же запуск |
| Ожидает ответа | Ждёт человека, затем возобновляет тот же диалог |
| Превышен бюджет | `AGENT_BUDGET_EXCEEDED` |
| Заблокировано защитной проверкой | `AGENT_GUARDRAIL_BLOCKED` |
| Иначе | `AGENT_RUN_FAILED` |

Привязанные `attachments` — это изображения из файлов запуска: скачанный файл,
отрисованная страница PDF, преобразованная фотография, — которые показываются
агенту как картинки, а не как ссылка, которую он не может открыть. Показываются
только PNG, JPEG, WebP и GIF. Любой другой файл даёт
`UNSUPPORTED_ATTACHMENT_TYPE`, поэтому сначала прочитайте текст документа через
`text.extract`.

Шаг никогда не повторяется автоматически, потому что агент мог вызвать
инструменты с побочными эффектами.

## http.request { #http-request }

Вызывает HTTP API. Каждый запрос и каждый редирект проходит SSRF-проверку
экземпляра и отправляется на адрес, который эта проверка одобрила. Частный хост,
который оператор указал в
[`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings), тоже
допускается, но только для URL, который там начинается: редирект с публичного
URL до него никогда не доходит.

URL, привязанный из публичного триггера (вебхука, формы, письма) или из
аргументов инструмента агента, может назвать любой хост из списка, поэтому
вносите в список только хосты, которые проверяют свои учётные данные.

Учётные данные — это [HTTP-учётные данные](../secrets.md#kinds) из хранилища
секретов, и они отправляются только тем источникам, которые разрешает секрет.
Ответ читается в пределах `max_response_bytes` и возвращается без `Set-Cookie`,
заголовков аутентификации и токена. Ответ, который является HTML, приходит
текстом в `body`; привяжите его к [`html.parse`](#html-parse), чтобы прочитать
текст, ссылки и элементы.

Учётные данные передаются Bearer-токеном, Basic-аутентификацией, названным вами
заголовком или, при `query`, названным вами параметром URL. **Импорт из cURL**
(Import cURL) в редакторе читает команду, вставленную из документации API, в
метод, URL, заголовки и тело JSON. Учётные данные из команды в шаге не
сохраняются: шаг настраивается отправлять их так же, а форма хранилища секретов
открывается уже заполненной.

`GET` может пройти список по страницам с `pagination`: переходя по следующему
URL, который называет ответ, отправляя обратно курсор или увеличивая параметр
страницы. Элементы `items_path` каждой страницы собираются в `items` по порядку.
Постраничный обход останавливается, когда нет следующей страницы, когда на
странице нет элементов или на `max_pages`, и тогда `complete` равен false. Все
страницы вместе читают не больше `max_response_bytes`, а следующая страница на
другом источнике не получает учётных данных.

| Что произошло | Результат |

| URL ведёт на loopback, метаданные, не http(s) или на частный адрес вне [`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings) оператора | `URL_REFUSED`, ничего не отправлено |
| URL вне источников, разрешённых учётными данными | `SECRET_ORIGIN_DENIED`, ничего не отправлено |
| Соединение так и не открылось | `HTTP_UNREACHABLE`, повторяется |
| Отправлено, ответа нет, `GET` или заголовок идемпотентности | `HTTP_NO_RESPONSE`, повторяется |
| Отправлено, ответа нет, любая другая запись | Неопределённый: запуск останавливается ради человека |

| Больше предела | `RESPONSE_TOO_LARGE` |
| `items_path` страницы находит что-то, что не список | `PAGE_ITEMS_NOT_A_LIST` |

## mcp.call { #mcp-call }

**Вызвать инструмент MCP** (Call an MCP tool) вызывает один инструмент на одном
из [MCP-серверов](../mcp.md) организации, с `arguments`, привязанными к более
ранним шагам. Редактор предлагает серверы со значком их службы, затем
инструменты, которые сервер перечислил при последней проверке; **Обновить
инструменты** (Refresh tools) проверяет его снова. Каждый аргумент, который
принимает инструмент, становится отдельным полем, введённым или привязанным, как
`arguments/<name>`. Подходит только сервер, принадлежащий организации, и никогда
собственный сервер участника, и публикация отклоняет сервер, который не
принадлежит организации, выключен или не перечислил инструмент. Учётные данные
берутся из хранилища секретов, как и для агента.

`approval` решает, когда человек сначала одобряет вызов: `writes` (по
умолчанию) — до любого инструмента, который сервер не помечает как доступный
только для чтения; `all` — до каждого вызова; `none` — никогда. Запрос уходит на
вкладку **Согласования** (Approvals), как у
[human.approval](#human-approval), к `approvers` или к любому, у кого есть
`approvals:decide`. После одобрения инструмент вызывается; при отказе шаг
завершается с ошибкой `MCP_CALL_REJECTED`. Пометка «только для чтения» — это
заявление самого сервера, поэтому выбирайте `all` для сервера, которому в этом
не доверяете.

Вывод — это `text` ответа, его данные `structured`, когда инструмент их
возвращает, и `is_error`. Ошибка, которой отвечает инструмент, завершает шаг с
ошибкой `MCP_TOOL_ERROR`, если только `on_tool_error` не равен `complete`.

У MCP нет собственного ключа идемпотентности. Сервер, который принимает такой
ключ как аргумент инструмента, всё равно можно сделать безопасным для повтора:
укажите в поле **Аргумент ключа идемпотентности** (Idempotency key argument)
(`idempotency_key_argument`) имя этого аргумента, и шаг отправит туда свой
стабильный ключ операции — одинаковый при каждой попытке шага и разный для
каждой итерации цикла — вместо любого привязанного значения. Инструмент должен
объявить этот аргумент как текст.

Публикация отклоняет аргумент, которого нет в записанной схеме инструмента, а
инструмент, чья схема не записана, проходит, поэтому сначала проверьте сервер;
во время выполнения шаг перечисляет инструменты сервера перед вызовом и
завершается с `MCP_IDEMPOTENCY_ARGUMENT_UNDECLARED`, ничего не вызывая, если в
текущей схеме такого аргумента нет. Шаг с ключом считается идемпотентным:
движок может выполнить его снова.

Когда вызов обрывается, что будет дальше, зависит от того, мог ли он дойти до
сервера:

- **До вызова** — до сервера не удалось достучаться или он не ответил на
  подключение либо на перечисление инструментов — ничего не отправлено, и шаг
  завершается с `MCP_CALL_FAILED`, которая повторяется.
- **После вызова: вызов с ключом или инструмент, который сервер помечает как
  доступный только для чтения** (в перечислении, которое шаг только что
  прочитал, иначе в записанном при проверке сервера) — тот же сбой, который
  повторяется, потому что повторять безопасно.
- **После вызова: любой другой инструмент, без ключа** — инструмент мог
  сработать, а ответа не пришло. Шаг завершается как **неопределённый**, с
  пояснением *инструмент был вызван, а ответа не пришло; он мог сработать*, и
  запуск ждёт человека, который смотрит в другой системе, прежде чем запустить
  шаг снова.

| Что произошло | Результат |
|---|---|
| Сервера больше нет или он выключен | `MCP_SERVER_UNAVAILABLE`, ничего не отправлено |
| Его учётные данные нужно снова авторизовать | `MCP_SERVER_UNAUTHORIZED`, ничего не отправлено |
| Сервер не предлагает этот инструмент | `MCP_TOOL_NOT_FOUND` |
| До сервера не удалось достучаться или вызов оборвался до или после безопасного вызова | `MCP_CALL_FAILED`, повторяется |
| Вызов оборвался после вызова без ключа к инструменту, о котором не известно, что он только для чтения | Неопределённый: запуск останавливается ради человека |
| Инструмент не объявляет **Аргумент ключа идемпотентности** | `MCP_IDEMPOTENCY_ARGUMENT_UNDECLARED`, ничего не отправлено |
| Инструмент ответил ошибкой | `MCP_TOOL_ERROR` или ответ как вывод |
| Структурированный ответ больше 1 MiB | `MCP_RESULT_TOO_LARGE` |
| Структурированный ответ не JSON | `MCP_RESULT_INVALID` |
| Шаг не называет сервер или инструмент | `MCP_CALL_NOT_CONFIGURED`, ничего не отправлено |
| Инструмент не разрешён на этом подключении | `MCP_TOOL_NOT_ALLOWED`, ничего не отправлено |
| Названный согласующий больше не может решать согласования | `APPROVER_UNAVAILABLE`, ничего не отправлено |
| Вызов не одобрен | `MCP_CALL_REJECTED`, ничего не отправлено |

::: app.workflows.nodes.mcp_call._handler.McpCallConfig

::: app.workflows.nodes.mcp_call._handler.McpCallOutput

## notification.send { #notification-send }

Уведомляет участников организации через центр уведомлений: в приложении, по
почте, push, в Slack, Telegram, Mattermost, Microsoft Teams, SMS или iMessage.
Получатели — участники, названные по идентификатору. Во время выполнения каждый
из них должен быть действующим участником, который видит сценарий; всех
остальных отбрасывают. Если не осталось никого, шаг завершается с ошибкой
`NO_PERMITTED_RECIPIENTS`. Настройки каждого человека для **Уведомления
сценариев** (Workflow notifications) по-прежнему действуют. Шаг завершается,
когда уведомление записано; почта доставляется после. Повторённый шаг не пишет
второе уведомление.

Для частных чатов нужны собственный явный маршрут уведомлений получателя и его
согласие на канал. Выбор канала здесь никогда не даёт согласия и не
перенаправляет уведомление в чат, заданный сценарием. При доставке доступ,
настройки и полномочия маршрута проверяются снова, прежде чем отправить.
Доставка провайдером происходит после завершения шага; завершение не доказывает
получение.

## email.send { #email-send }

Доставляющие провайдеры резервируют каждого уникального получателя в общих
лимитах Redis, прежде чем отправить всю пачку:
`WORKFLOW_EMAIL_MAX_PER_PRINCIPAL_PER_HOUR` (100),
`WORKFLOW_EMAIL_MAX_PER_ORG_PER_HOUR` (500) и
`WORKFLOW_EMAIL_MAX_PER_DEPLOYMENT_PER_HOUR` (1000). Лимит субъекта охватывает
ключи и организации одного и того же издателя этих ключей. Фиксированные часовые окна общие для
запусков и воркеров; на их границе может пройти вдвое больше лимита. Исчерпание
даёт `EMAIL_DELIVERY_LIMIT`; недоступные счётчики — `EMAIL_ALLOWANCE_UNAVAILABLE`,
без отправки. Резервирования консервативны и не возвращаются после частичного
резервирования, сбоя провайдера или отмены. Провайдеры, которые только пишут
журнал, не расходуют лимит доставки. Задавайте ёмкость экземпляра ниже квоты
почтового ретранслятора, чтобы оставить запас для транзакционной почты.

**Отправить письмо** (Send an email) отправляет до десяти адресов от
собственного отправителя экземпляра и через
[почтового провайдера](../configuration.md), по одной копии каждому, так что ни
один получатель не видит адрес другого. Он для людей вне организации, например
лида или клиента: участники получают сообщения через
[notification.send](#notification-send) и свои настройки. `to`, `subject` и
`body` в виде простого текста вводятся или привязываются к более ранним шагам, а
`reply_to` отправляет ответы не на адрес ответов экземпляра.

Вывод перечисляет адреса, которые провайдер принял. `delivered` равен false,
когда провайдер только пишет почту в журнал, а это значение по умолчанию при
разработке, поэтому запуск никогда не заявляет, что дошёл до кого-то, до кого не
дошёл. Копия, в которой провайдер отказал, завершает шаг с ошибкой
`EMAIL_NOT_SENT` и называет то, что уже отправлено. У почты нет ключа
идемпотентности, поэтому повторённый шаг отправляет снова.

## human.approval { #human-approval }

**Запросить согласование** (Ask for approval) останавливает запуск, пока человек не
одобрит или не отклонит то, что шаг собирается сделать, а затем запуск идёт дальше по
порту `approved` или `rejected`. Согласующий читает `title` шага и привязанные к нему
`details` на вкладке **Согласования** (Approvals) страницы «Активность» или через
`GET /api/v1/workflow-approvals`. `approvers` и `approver_groups` задают, кто может
решить: эти люди и участники групп, у которых есть `approvals:decide`
([группы согласования](../governance.md#approval-groups)). Им приходит уведомление в
приложении. Если оба поля пусты, решить может любой, у кого есть `approvals:decide`,
и уведомление получают все они. Запрос также попадает в начало «Входящих» у того, кто
может его решить. После `timeout_hours` запрос истекает, и шаг уходит по порту `rejected` с
`decision: "expired"`. Отмена запуска отменяет и запрос, и отмена сценария, вызвавшего
этот запуск, делает то же самое. Каждый запуск шага спрашивает один раз, поэтому
повтор или итерация цикла никогда не спрашивает дважды об одном и том же.

Указанные согласующие должны быть активными участниками с `approvals:decide`.
Публикация это проверяет, и шаг проверяет ещё раз перед запросом; а если названный
согласующий потерял это разрешение, шаг завершается с `APPROVER_UNAVAILABLE`, вместо того
чтобы оставить запрос, по которому нельзя принять решение.

Шаг может нести **Предложение** (proposal): текст, привязанный к `proposal`, например
подготовленный ответ. Согласующий читает его рядом с запросом. Включите `editable`, и
очередь покажет его в редакторе — как `text` или `markdown` (`proposal_format`) под
`proposal_label` («Предложение», когда пусто), — и согласующий может одобрить
изменённую версию. Шаг, к которому ничего не привязано, открывает пустой редактор — на
случай, когда подготовка ничего не дала. `details` не меняется и остаётся коротким;
предложение может быть до 100 000 символов.

Одобренный результат несёт три поля помимо решения:

- `final` — версия, которую одобрил согласующий; само предложение, если он ничего не
  изменил.
- `original` — предложение в том виде, в каком его запросили; `""`, если у
  редактируемого шага ничего не было привязано.
- `edited` — true, когда `final` отличается от `original`. Переводы строк, завершающие
  пробелы и пустое место вокруг текста различием не считаются.

Изменённая версия сохраняется без ведущих и завершающих пробелов, поэтому правка,
начинающаяся с блока кода с отступом, теряет этот первый отступ.

Одобренный запрос на шаге с `editable` также записывает долю правки — какую часть
предложения изменил согласующий, от `0` до `1`. [Статистика](../workflows.md#running-a-workflow)
сценария показывает её вместе с другими исходами согласования.

Шаг, у которого `editable` выключен, показывает предложение только для чтения и, будучи
одобрен, передаёт его дальше без изменений как `final` с `edited` false, так что
последующие шаги могут привязываться к `final` при любом режиме шага. Отклонение или
истечение срока не несёт `final`. Отправка изменённой версии на шаг без `editable` или
вместе с отклонением отклоняется с `422`. Согласующий, не названный в шаге, видит
предложение только для чтения.

Шаг может предлагать **Способы одобрения** (choices) вместо обычного согласования,
каждый — способ одобрить: сохранить черновик или отправить сейчас, например. Задайте до
пяти, у каждого свой `id` (строчные буквы, цифры и подчёркивания, не `in`, `approved`
и `rejected`) и `label` до 40 символов. Очередь показывает по одной кнопке на каждый
способ вместо **Одобрить** (Approve), с подписью как написано и без перевода, а
**Отклонить** (Reject) остаётся. У шага тогда есть выходной порт на каждый способ, по
порядку, затем `rejected` и нет порта `approved`: связь из `approved` отклоняется при
публикации сценария.

Выбор согласующего — это порт, по которому уходит шаг, а его `id` — это `choice` в
результате. Он равен null, когда у шага нет способов, а также при отклонении и истечении
срока. Шаг без способов не меняется: у него есть `approved` и `rejected`. Для
одобрения шага со способами нужно указать один из них как `choice`, а передача `choice`
при любом другом решении отклоняется с `422`. Статистика не разбивается по способам.

Если сценарий отправляет одобренный `final` через [`mcp.call`](#mcp-call), задайте у
этого шага `approval` равным `none`, иначе человека спросят дважды.

## flow.wait { #flow-wait }

**Ожидание** (Wait) задерживает запуск на шаге на `seconds` после того, как до него
дошли, или до привязанного `until`, а затем продолжает; не дольше тридцати дней. Шаг
припаркован на таймере, строка диспетчеризации которого наступает в этот момент,
поэтому ожидание переживает перезапуск воркера и не занимает воркер, а другие ветви
тем временем идут дальше. Момент, который уже прошёл, наступает сразу, и крайний срок
запуска по-прежнему действует. Привязанный `until` более чем через тридцать дней после
того, как дошли до шага, приводит к сбою шага с `WAIT_TOO_LONG`.

С включённым параметром **Ждать вызова по ссылке возобновления запуска** (Wait for a
call to the run's resume link) шаг ждёт вместо этого вызова адреса, который выдал шаг
**Ссылка для возобновления** (Resume link), не дольше `seconds` (тридцать дней, если
не задано). `POST` на этот адрес с JSON-объектом или без тела: шаг передаёт тело
дальше как `body` с `called` true, и запуск продолжается. Если никто не вызовет
вовремя, он продолжается с `called` false. Вызов, когда ничего не ждёт — до того, как
дошли до шага, после того, как он пошёл дальше, или после завершения запуска, —
отклоняется с `WORKFLOW_NOT_WAITING` (409), а ссылка, не принадлежащая запуску,
отвечает `404`.

## flow.await_reply { #flow-await-reply }

**Ждать ответа на письмо** (Await email reply). Выберите подключённый почтовый ящик
Gmail или Outlook организации, `thread_id` провайдера, точный `expected_sender`,
`not_before` и `deadline` с часовыми поясами и, при необходимости, исходный RFC
`anchor_message_id`. Outlook может указать общий ящик, который позволяет читать его
выданный доступ. Шаг читает только метаданные, каждые 60–3600 секунд (по умолчанию
300), используя существующий долговечный таймер сценария. Пока он ждёт, он не занимает
ни воркера, ни модель. Учётная запись и поколение её согласия (consent generation)
сохраняются между пробуждениями; замена учётной записи никогда не перенацеливает ожидание.

`reply` срабатывает, когда подходящий, аутентифицированный отправитель ответил после
`not_before` и не позже крайнего срока. Необязательные заголовки ответа RFC сужают это
совпадение; они никогда не подтверждают полномочия отправителя. Отправленная почта,
черновики, автоматические ответы и уведомления о прочтении не считаются. Последняя
успешная проверка без подтверждённого совпадения уходит по порту `deadline`, с
`ignored_unverified` для отклонённых совпадений отправителя. Это означает **нет подтверждённого подходящего ответа**, а не доказательство, что никто не писал.
Нечитаемые, слишком большие или отозванные ящики дают явный сбой и никогда не уходят в
ветвь `deadline`. Ограниченное сканирование принимает не более 500 сообщений и пяти
страниц Graph. Ответы, пришедшие до того, как шаг впервые припарковался, всё равно
учитываются.

На вкладке **Шаги** (Steps) запуска показано ожидание. Субъект запуска или редактор
сценария может приостановить или исправить его, пока шаг припаркован (для тестовых
запусков — только редакторы); выполняющаяся проверка отвечает 409. Пауза сохраняет
исходный крайний срок и не читает почтовый ящик. Явная проверка продлённого согласия
принимает только ту же учётную запись. Шаг, требующий внимания, по-прежнему требует
отдельного решения о повторном запуске. Отмена запуска закрывает его таймер и
предотвращает последующую работу. Ожидание длится не более тридцати дней; собственный
крайний срок сценария может завершить запуск раньше. Готовьте напоминания в ветви
`deadline` обычными узлами уведомлений и согласований; этот узел не отправляет почту.

Если крайний срок наступает, пока проверки на паузе, шаг завершается с ошибкой, не читая
почтовый ящик и не утверждая, что ответ не пришёл. Возобновите или исправьте его до этого момента.

## flow.resume_link { #flow-resume-link }

## Обработка ошибок { #error-handling }

Каждый узел принимает необязательный `policy` рядом со своей конфигурацией.

| Поле | По умолчанию | Действие |
|---|---|---|
| `timeout_seconds` | нет | Вызов, который всё ещё идёт дольше этого времени, обрывается. Шаг без внешней записи или с идемпотентным вызовом завершается с `NODE_TIMEOUT` и может быть повторён. Запись, которая могла пройти, становится неопределённой и останавливается для человека |
| `retry.max_attempts` | `WORKFLOW_RETRY_CEILING` | Попыток всего, включая первую. Повторяется только сбой, который узел помечает как повторяемый, а публикация отклоняет больше одной попытки для шага, чей вызов небезопасно повторять |
| `retry.backoff`, `base_delay_seconds`, `max_delay_seconds` | `exponential`, `2`, `60` | Ожидание между попытками: фиксированное или удваивающееся до потолка |
| `on_error` | `fail_run` | `route` выводит сбой, который не устранили повторы, через порт `error` узла вместо сбоя запуска |

У узла, чья политика направляет ошибки, есть дополнительный выходной порт `error`. Он
несёт `WorkflowError`: `code`, `message`, `details` и `retryable`. Обычный результат
узла существует только на его остальных портах, поэтому публикация отклоняет привязку,
читающую результат на пути ошибки или ошибку на пути успеха. Порт ошибки должен куда-то
вести, и оба пути могут снова сойтись на `logic.merge`.

Когда шаги идут параллельно, у каждой ветви свой обработчик. Если ветвь завершается с
ошибкой, а маршрута ошибки нет, запуск завершается с ошибкой, и шаги рядом с ней больше ничего не начинают: их
ожидающие согласования и таймеры отзываются, как и запуски агентов, на которых они
припаркованы. Шаг, работа которого уже шла, завершается и записывается завершённым после
остановки запуска, с сохранением результата. Повторный запуск использует его, а не
делает заново, и повторно использованный шаг **Результат** (Output) или **Ответ на
вебхук** (Respond to webhook) снова сообщает свой ответ. Публикация отклоняет
`error.handle`, в который подают два шага, способных завершиться с ошибкой в одном запуске.

Шаг, требующий внимания, можно уладить в том запуске, где он находится. Если считать
его сбойным, он завершается с `STEP_MARKED_FAILED`, что уходит через его порт `error`,
когда шаг направляет свои ошибки, или переходит к политике ошибок элементов его цикла.
Отметка запуска как сбойного завершает запуск с этой ошибкой, как бы ни был собран
граф. Отмена запуска или его сбой тоже закрывают шаг, требующий внимания.

`error.handle` принимает эту ошибку на свой порт `in` и уходит по первой ветви, у
которой совпадают и `code`, и `retryable`, либо по `default`, который должен быть
подключён. `error.raise` завершает свою ветвь ошибкой с кодом, сообщением и подробностями, которые
задаёт автор.

Некоторые сбои не направляются никогда. Отозванный доступ, израсходованный бюджет
(запуска или агента), отменённый запуск, пропущенный крайний срок, потолок узлов на
запуск и эффект с неизвестным исходом завершают запуск, как бы ни был собран граф.
Конфликт ревизии или ошибку проверки можно направить, но их никогда не повторяют слепо,
потому что тот же вход снова даёт ту же ошибку.

## Циклы { #loops }

`control.foreach` выполняет своё тело по разу для каждого элемента привязанного списка
`items`, по одному элементу за раз и по порядку. Затем он продолжает через свой порт
`done` с `results` в порядке входа, `errors` и `count`. Тело — это шаги, которые
называют цикл в `scope_id`; в него не ведёт ни одна связь. Оно начинается с `loop.item`,
который даёт `item`, `index` и `count`, и до каждого шага в нём нужно доходить от
`loop.item` по собственным связям тела. Оно заканчивается на `loop.yield`, чьё
привязанное `value` — результат итерации.

Ни одна связь не ведёт обратно к циклу. Шаг в теле может привязываться к чему угодно, что
выполнилось до цикла, а ничто вне тела не может привязываться внутрь него.

Список фиксируется, когда цикл начинается, поэтому итерация никогда не видит
источник, изменившийся во время запуска. Список длиннее `WORKFLOW_FOREACH_MAX_ITEMS` или
больше `WORKFLOW_FOREACH_MAX_MANIFEST_BYTES` отклоняется, а не обрезается. Пустой список
даёт `results: []` без выполнения тела. Шаги каждой итерации выполняются в своей
области, со своими попытками, ключами идемпотентности и затратами. Следующая итерация
планируется в транзакции, которая завершает предыдущую, поэтому перезапуск продолжает с
нужного индекса и никогда не повторяет подтверждённую запись. Согласование внутри
итерации возобновляет эту итерацию.

При `item_error_policy: stop`, значении по умолчанию, цикл завершается с ошибкой на первой неудачной
итерации, и подробности ошибки несут `scope_path` этой итерации. При `collect` результат
элемента равен `null`, ошибка добавляется в `errors`, и цикл продолжается. Циклы
вкладываются не глубже `WORKFLOW_FOREACH_MAX_DEPTH`, и каждый запуск узла, созданный
запуском, считается против `WORKFLOW_RUN_MAX_NODE_RUNS`. Цикла `while` и параллельного
map нет.

Тело может разветвляться на параллельные ветви, которые идут бок о бок внутри своей
итерации, и итерация заканчивается, когда ни один её шаг не активен. Когда шаг завершается с ошибкой в
итерации без маршрута ошибки, `collect` даёт его соседям в этой итерации завершиться, а
затем переходит к следующему элементу. `stop` отменяет их, отзывая их согласования,
таймеры и припаркованные запуски агентов, и завершает цикл с ошибкой. Следующая итерация никогда не
начинается, пока в более ранней ещё идёт какой-то шаг.

## Виртуальные таблицы { #virtual-tables }

Семь узлов читают и пишут [виртуальные таблицы](../virtual-tables.md) через тот же
сервис, которым пользуются консоль, API и табличные инструменты агента. Проверка,
конфликты ревизий, квоты, история, квитанции и аудит одинаковы на каждом способе
доступа.

| Узел | Что делает | Эффект |
|---|---|---|
| `table.record.create` | Добавляет запись | запись |
| `table.record.upsert` | Создаёт или обновляет запись с внешним id | запись |
| `table.record.update` | Меняет некоторые ячейки записи | запись |
| `table.record.delete` | Удаляет запись, сохраняя её историю | запись |
| `table.record.get` | Находит одну запись по id или внешнему id | чтение |
| `table.record.query` | Читает одну страницу записей с фильтрацией и сортировкой | чтение |
| `table.create` | Создаёт новую таблицу с типизированной схемой | запись |

Каждый узел записей закрепляет свою таблицу в конфигурации; это проверяется при
публикации относительно автора графа и ещё раз как субъект запуска при каждом запуске.
Значения привязываются, а ключом служит id столбца или подпись столбца. Запись
возвращается со своими значениями дважды: `values` по id столбца, для привязок, и
`fields` по подписи, для чтения. Ключ, который не называет существующий столбец, приводит к
сбою с `UNKNOWN_COLUMN`.

Запись несёт ключ операции шага, поэтому повторный шаг воспроизводит свою первую запись.
Обновление, upsert или удаление без привязанной ревизии пишет на текущей ревизии записи,
прочитанной под блокировкой записи, и воспроизведение срабатывает, даже если первая
запись уже сдвинула эту ревизию дальше. Сдвинувшаяся ревизия — это `REVISION_CONFLICT`,
который не повторяется: та же ревизия снова даст конфликт, поэтому направьте его на
свежее чтение через `error.handle`. Отсутствующая запись — это `found: false` от
`table.record.get`, а не сбой. `table.record.query` читает не более 100 записей на
страницу и сообщает `has_more`. Он никогда не читает всю большую таблицу целиком сам по
себе.

`table.create` — отдельный узел, и ему нужно `tables:create`. Его результат несёт новую
таблицу как ссылку, к которой можно привязать `table` последующего узла, и id каждого
столбца по подписи. Таблицу, которую читает или пишет действующий сценарий, или столбец,
который он закрепляет, нельзя архивировать, пока текущая версия этого сценария их
использует.

Ещё четыре шага только читают таблицы организации и ничего не меняют.

| Шаг | Что делает | Уходит по |
|---|---|---|
| `table.list` | перечисляет таблицы, которые видит субъект, с поиском по имени | `out`, с `tables` и `total` |
| `table.describe` | читает имя и столбцы одной таблицы | `out`, с `columns` |
| `table.exists` | есть ли таблица с точно таким именем | `yes` с её id или `no` |
| `table.record.exists` | есть ли запись, подходящая под фильтры | `yes` с id первой или `no` |

`table.exists` сравнивает имя целиком без учёта регистра, поэтому сценарий может создать
свою таблицу при первом запуске и потом использовать её повторно. Оба вопроса уходят
ровно по одному порту, и `logic.merge` может снова соединить ветви.

`table.record.exists` и `table.record.query` принимают в сохранённых фильтрах подписи
вариантов выбора наравне с ID. Перед запросом они сопоставляют подписи с текущей
таблицей; неизвестные или неоднозначные подписи остаются ошибками проверки.

## Файлы { #files }

Файл, который создаёт шаг, сохраняется как файл его запуска и передаётся дальше как
`FileRef`: id, тип, который оказался у его байтов, и размер. Шаг читает файл, только
если его создал собственный запуск шага или запуск был начат с ним — `FileRef`,
привязанный в графе, проверяется при публикации относительно запуска, который видит
автор. Любой другой файл, другой организации или другого запуска, — это
`FILE_NOT_FOUND`, поэтому знание id ничего не даёт. Файлы запуска перечисляются и
скачиваются с его страницы.

| Узел | Что делает | Эффект |
|---|---|---|
| `http.download` | Скачивает файл по HTTP потоком и сохраняет его | запись |
| `http.upload` | Отправляет файл на HTTP-эндпоинт потоком из хранилища | запись |
| `file.read` | Читает файл как текст, значение JSON или строки CSV | чтение |
| `file.write` | Сохраняет текст, значение JSON или строки как файл | запись |
| `text.extract` | Текст файла TXT, JSON, CSV, текстового PDF или DOCX | чтение |
| `convert.csv_to_json` | Файл CSV как файл JSON со строками | запись |
| `convert.json_to_csv` | Список JSON из плоских объектов как файл CSV | запись |
| `convert.text_to_file` | Текст как файл TXT | запись |
| `convert.pdf_to_png` | Выбранные страницы PDF как изображения PNG | запись |
| `image.transform` | Обрезает, масштабирует, поворачивает или конвертирует изображение | запись |

Скачивание подчиняется тем же правилам SSRF и учётных данных, что и `http.request`, —
до пяти перенаправлений. Его тело считается по мере поступления и отклоняется сверх
`max_bytes`, а тип определяется по байтам, поэтому `expected_content_types` нельзя
обмануть заголовком. `text.extract` не делает OCR: отсканированная страница завершает шаг с
`TEXT_EXTRACTION_NEEDS_OCR` и называет страницы. Повреждённый документ — это
`DOCUMENT_CORRUPT`, документ Word, который распаковывается сверх границ архива
загружаемого в чат файла, — `DOCUMENT_TOO_LARGE`, а PDF под паролем —
`DOCUMENT_ENCRYPTED`.

Изображение измеряется до декодирования. Его ширина, умноженная на высоту, рамка обрезки
и запрошенный размер проверяются против `CHAT_IMAGE_MAX_PIXELS`, и результат не несёт
метаданных источника. Каждый шаг, сохраняющий файл, сохраняет новый при каждой попытке,
поэтому это `at_least_once`. Файлы запуска могут складываться до
`WORKFLOW_RUN_MAX_FILE_BYTES`, а организации — до `WORKFLOW_ORG_MAX_FILE_BYTES`. Шаг,
файл которого превысил бы любой из них, завершается с `FILE_QUOTA_EXCEEDED` и ничего не
сохраняет. Чтобы освободить место, удалите старые запуски или задайте срок хранения
запусков у сценариев, которые создают файлы.

эффекты.

## Python { #python }

Два узла выполняют Python для двух видов работы.

`code.python.simple` выполняет короткий скрипт в песочнице Monty, у которой нет
файловой системы, нет сети и есть небольшая стандартная библиотека. Скрипт читает
привязанные значения как `args`, а его последнее выражение — это `result` шага, который
должен быть значением JSON. Он только вычисляет, поэтому это `pure`, и ему нужно
`code:execute`.

В редакторе скрипт шага кода пишется в редакторе кода: Python или JavaScript с подсветкой
в обеих темах, Tab и Shift+Tab для отступа, Enter, сохраняющий отступ, скобки и кавычки
закрываются по мере ввода, скобка рядом с курсором обведена вместе с парой, а ключи
привязанного `args` предлагаются, когда набирают `args["` или, в JavaScript, `args.`.
Esc, затем Tab — выход из редактора. **Проверить шаг** (Test step) выполняет скрипт
отдельно на том, что передали предыдущие шаги.

`code.python.sandbox` выполняет полный Python с пакетами и файлами запуска в подключении
`sandboxd` организации, и ему нужно `sandbox:execute`. Скрипт находит входные файлы в
`inputs`, пишет файлы в `outputs` и задаёт `result`. Это долговечная задача: первая
диспетчеризация запускает её в фоне, а каждая следующая проверяет её в том же сеансе,
поэтому перезапущенный воркер переподключается, а не запускает её заново. Никакие
учётные данные платформы никогда не попадают в песочницу, а всё, до чего скрипт может
дотянуться за пределами своих файлов, — это собственная конфигурация среды выполнения
хоста; для недоверенной работы выбирайте среду выполнения без сети.

| Что произошло | Результат |
|---|---|
| Результат не является JSON | `PYTHON_OUTPUT_NOT_JSON` |
| Скрипт выбросил исключение или превысил лимит | `PYTHON_ERROR` |
| Задача шла дольше `timeout_seconds` | `PYTHON_SANDBOX_TIMEOUT`, сеанс очищен |

| Хост недоступен | `SANDBOX_UNREACHABLE`, повторяется |

## JavaScript { #javascript }

`code.javascript.sandbox` выполняет JavaScript на Node той же долговечной задачей, в том
же подключении `sandboxd`, и ему нужно `sandbox:execute`. Скрипт — это тело асинхронной
функции: он читает привязанные значения как `args`, свои входные файлы в `inputs`, пишет
файлы в `outputs`, может `await`, а то, что он возвращает через `return`, — это `result`
шага (`null`, когда он ничего не возвращает). `require` загружает собственные модули
Node и всё, что установлено в среде выполнения. Выбирайте среду выполнения с Node.

Его сбои — те же, что у песочницы Python, с именами для JavaScript: выброшенная
ошибка — `JAVASCRIPT_ERROR`, результат, не являющийся значением JSON (функция,
`BigInt`), — `JAVASCRIPT_OUTPUT_NOT_JSON`, а таймаут и границы вывода —
`JAVASCRIPT_SANDBOX_TIMEOUT` и `JAVASCRIPT_OUTPUT_TOO_LARGE`.

## workflow.run { #workflow-run }

**Запустить сценарий** (Run a workflow). Выполняет опубликованную версию другого
сценария — того, который начинается с **Вызов из сценария** (Called by a workflow), — с
привязанным `input`, действуя как этот запуск. Шаг ждёт окончания вызванного запуска и
передаёт его `output` или завершается с `CALLED_WORKFLOW_FAILED` и ошибкой вызванного запуска;
если **Дождаться завершения** (Wait for it to finish) выключено, он сразу передаёт
начатый запуск. Вызванный запуск связан с шагом и с цепочкой этого запуска. Вызов
сценария, который уже выполняется выше в цепочке, завершается с `WORKFLOW_CALL_LOOP`, а вызов
глубже пяти — с `WORKFLOW_CALL_TOO_DEEP`. Тестовый запуск черновика вызывает
опубликованный сценарий по-настоящему.

## Добавление узла { #adding-a-node }

Узел — это пакет в `backend/app/workflows/nodes/`: `__init__.py` регистрирует
`NodeDefinition`, `_handler.py` его реализует, а `README.md` объясняет, зачем он
существует. `load_builtins` импортирует пакет. `tests/test_workflow_node_layout.py`
проверяет раскладку. Обработчик возвращает `Completed`, `Waiting`, `Failed` или
`Uncertain` и никогда не выбрасывает исключений. Запуск, для которого он выполняется, он
читает из `app.services.workflow_execution.context.current()`.

Типизированный узел объявляет три модели Pydantic: конфигурацию, задаваемую в редакторе и
фиксируемую при публикации; вход, поля которого заполняют привязки; и выход, к
которому привязываются последующие шаги. `extra="forbid"` в каждой не пускает опечатку в
опубликованный граф. Выбирайте `retry_guarantee` по тому, что сделает повтор вызова:
`idempotent`, когда обработчик сам делает повтор безвредным (табличная запись передаёт
`operation_key()`), `at_least_once`, когда повтор допустим, и `none`, когда нет. Узел,
который читает или пишет ресурс, объявляет `check_resources`; публикация выполняет его
относительно автора, а каждый запуск — относительно своего субъекта.

Консоль рисует узел по его определению, а его значок и оттенок — в
`frontend/src/components/workflows/node-visuals.ts`. Проверяйте обработчик напрямую на
его отказы и проведите его один раз через `tests/integration/workflow_run_support.py`,
чтобы его конфигурация, привязки и выход были доказаны в настоящем запуске.

::: app.workflows.contracts.definition.NodeDefinition

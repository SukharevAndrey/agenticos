# Настройте источники синхронизации { #configure-sync-sources }

Источники синхронизации самостоятельно забирают документы из внешних сервисов
(Google Drive, S3/MinIO, публичный сайт, репозиторий Git, сайт SharePoint или
OneDrive) в коллекции знаний. Каждый источник хранит тип коннектора, целевую
коллекцию, настройки коннектора, режим синхронизации, необязательное расписание
и идентификатор [секрета из хранилища секретов](../secrets.md), с которым он
проходит проверку подлинности, — сайту он не нужен.

Когда запускается синхронизация, коннектор получает список удалённых файлов,
скачивает их во временный каталог и пропускает через стандартный конвейер
индексации (разбор, нарезка на фрагменты, эмбеддинги, хранение). Когда перечисление
полное, документы, которые источник принёс раньше и больше не перечисляет,
удаляются. Каждая операция синхронизации оставляет запись `SyncLog` с
результатом.

### Кратко об архитектуре { #architecture-at-a-glance }

| Компонент | Расположение | Назначение |
|-----------|----------|------|
| `BaseSyncConnector` | `app/services/rag/connectors/__init__.py` | Абстрактная основа для всех коннекторов |
| `RemoteFile` | `app/services/rag/connectors/__init__.py` | Модель Pydantic, описывающая удалённый файл |
| `CONNECTOR_REGISTRY` | `app/services/rag/connectors/__init__.py` | Сопоставляет строки типов коннекторов с классами |
| `SyncSource` (модель БД) | `app/db/models/sync_source.py` | Хранит конфигурации источников |
| `SyncLog` (модель БД) | `app/db/models/sync_log.py` | Отслеживает отдельные операции синхронизации |
| `SyncSourceService` | `app/services/sync_source.py` | Логика CRUD и запуска |
| Команды RAG CLI | `app/commands/rag.py` | Интерфейс CLI для управления источниками |
| Маршруты RAG API | `app/api/routes/v1/rag.py` | REST API для управления источниками |

## Быстрый старт — CLI { #quick-start-cli }

### Список доступных типов коннекторов { #list-available-connector-types }

```bash
# Shows all registered connectors (e.g. gdrive, s3, git, sharepoint)
uv run agenticos cmd rag-sources
```

### Добавьте источник Google Drive — синхронизация каждые 2 часа { #add-a-google-drive-source-sync-every-2-hours }

```bash
uv run agenticos cmd rag-source-add \
  --name "Legal docs" \
  --type gdrive \
  --org 0c8f2b1e-... \
  --collection legal \
  --config '{"folder_id": "1abc123def", "include_subfolders": true}' \
  --sync-mode new_only \
  --schedule 120
```

### Добавьте источник S3 — только ручная синхронизация { #add-an-s3-source-manual-sync-only }

```bash
uv run agenticos cmd rag-source-add \
  --name "Marketing" \
  --type s3 \
  --org 0c8f2b1e-... \
  --collection marketing \
  --config '{"bucket": "my-docs", "prefix": "marketing/"}' \
  --sync-mode full \
  --schedule 0
```

### Добавьте источник Git — документация репозитория, каждую ночь { #add-a-git-source-a-repositorys-docs-nightly }

```bash
uv run agenticos cmd rag-source-add \
  --name "Handbook" \
  --type git \
  --org 0c8f2b1e-... \
  --collection handbook \
  --config '{"repository_url": "https://github.com/acme/handbook.git", "branch": "main", "path_prefix": "docs"}' \
  --sync-mode new_only \
  --schedule 1440
```

Затем выберите его токен доступа как учётные данные источника в интерфейсе или
передайте `secret_id` в `PATCH` — см. [Настройка репозитория
Git](#git-repository-setup).

### Добавьте источник SharePoint — одна папка библиотеки, каждые 6 часов { #add-a-sharepoint-source-one-library-folder-every-6-hours }

```bash
uv run agenticos cmd rag-source-add \
  --name "HR policies" \
  --type sharepoint \
  --org 0c8f2b1e-... \
  --collection hr \
  --secret-id <vault-secret-id> \
  --config '{"site_url": "https://contoso.sharepoint.com/sites/HR", "folder_path": "Policies"}' \
  --sync-mode new_only \
  --schedule 360
```

`--secret-id` — это приложение Microsoft Entra в хранилище секретов организации;
см. [Настройка SharePoint и OneDrive](#sharepoint-and-onedrive-setup).

### Запустите синхронизацию вручную { #trigger-sync-manually }

```bash
# Sync a single source by ID
uv run agenticos cmd rag-source-sync <source-id>

# Sync all active sources
uv run agenticos cmd rag-source-sync --all
```

### Удалите источник { #remove-a-source }

```bash
uv run agenticos cmd rag-source-remove <source-id>
```

`<source-id>` — это UUID, который выводится при создании источника и виден в
списке `rag-sources`.

## Быстрый старт — интерфейс { #quick-start-ui }

1. Перейдите в раздел **База знаний** (Knowledge Base) и откройте вкладку
   **Источники синхронизации** (Sync).
2. Нажмите **Добавить источник синхронизации** (Add source).
3. Выберите тип коннектора (Google Drive, S3, Website, Git repository,
   SharePoint & OneDrive). Поля формы строятся по JSON Schema модели
   `CONFIG_MODEL` коннектора. У сайта нет шага с учётными данными.
4. Заполните поля конфигурации коннектора (например, ID папки, имя бакета).
5. Выберите целевую коллекцию, режим синхронизации и интервал расписания.
6. Нажмите **Создать источник** (Create source).
7. Нажмите **Синхронизировать сейчас** (Sync now), чтобы запустить
   синхронизацию сразу, или дождитесь, когда сработает расписание.

Чтобы изменить источник позже, нажмите карандаш в его строке. Откроется тот же
мастер с заполненными значениями источника. Коннектор изменить нельзя, а
**Сохранить изменения** (Save changes) отправляет только изменённые поля.
Источник остаётся привязан к той базе знаний, в которой находится.

Интерфейс вызывает тот же REST API, описанный ниже, поэтому всё, что можно
сделать в интерфейсе, можно сделать и через `curl` или любой HTTP-клиент.

## Режимы синхронизации { #sync-modes }

| Режим | Поведение |
|------|----------|
| `full` | Синхронизировать всё заново. Все файлы индексируются заново, существующие документы заменяются. |
| `new_only` | Добавлять новые файлы и обновлять изменённые. Изменения определяются по хешу SHA-256 — неизменённые файлы пропускаются. |
| `update_only` | Обновлять только файлы, уже находящиеся в коллекции. Новые файлы пропускаются. Неизменённые файлы пропускаются по хешу SHA-256. |

!!! tip "`new_only` для большинства сценариев"

    Он добавляет новые файлы и обновляет изменённые, пропуская неизменённые;
    это самая быстрая добавочная синхронизация. `update_only` обновляет
    существующие документы, не добавляя новых; `full` каждый раз заново
    импортирует всё.

### Что удаляет синхронизация { #what-a-sync-removes }

В любом режиме синхронизация удаляет документы, которые источник принёс раньше
и больше не перечисляет: страницу, убранную с сайта, файл, удалённый из папки
Drive, объект, удалённый из бакета. В журнале синхронизации они учитываются
как `removed`.

Она ничего не удаляет, если перечисление не было **полным**. Обход,
дошедший до лимита страниц или не сумевший прочитать одну из страниц, не
видел того, чего нет в перечислении. Такой запуск сохраняет все документы и
сообщает об этом в сообщении журнала синхронизации. Следующая синхронизация с
полным перечислением удалит то, что исчезло. Документ, который не удалось
удалить, считается файлом с ошибкой, и следующая синхронизация попробует снова.

Одновременно выполняется только одна синхронизация источника. Синхронизация,
запущенная, пока другая синхронизация того же источника ещё идёт, не
начинается, и в её журнале это сказано.

Удаляются только документы самого источника. Загруженный документ или документ,
который принёс в ту же коллекцию другой источник, не затрагиваются никогда. Если
два источника в одной коллекции перечисляют один и тот же документ, он остаётся,
пока его не перестанут перечислять оба. Документ, проиндексированный до того,
как источник стал это записывать (сентябрь 2026 года), сохраняется, пока
синхронизация источника не перечислит его снова.

### Что делает вторая синхронизация { #what-a-second-sync-does }

Каждая следующая синхронизация делает минимум — ровно столько, сколько позволяет
источник:

- **Неизменённый файл стоит скачивания, а не эмбеддингов.** Его SHA-256
  совпадает с хешем сохранённого документа, поэтому он учитывается как
  `skipped`, и его больше не разбирают и не превращают в эмбеддинги.
- **Неизменённый источник стоит одного запроса.** Коннектор, который может
  сказать, на каком состоянии находится всё его содержимое, — последний коммит
  ветки Git, поток изменений библиотеки SharePoint, — записывает его после
  каждого запуска, завершившегося без ошибок. Следующий запуск `new_only` или
  `update_only`, обнаруживший то же значение при той же конфигурации,
  останавливается, ничего не перечислив: в его журнале нет обработанных файлов,
  и он ничего не удаляет. Изменение конфигурации, коллекции или режима
  заставляет следующий запуск прочитать всё заново, а `full` никогда не
  останавливается раньше.
- **Файл, который прерванная синхронизация оставила недоделанным, приводится в
  порядок.** Воркер, остановившийся после сохранения векторов файла и до их
  записи, оставляет их без учёта. Следующая синхронизация этого источника
  удаляет то, что ничем не учтено, и индексирует файл заново, и она не
  останавливается раньше, пока такой файл ждёт.

Запуск с файлом с ошибкой не записывает состояние, поэтому следующий запуск
читает источник целиком и повторяет попытку.

## Расписание { #schedule }

Поле `schedule_minutes` задаёт, как часто источник синхронизируется
автоматически:

| Значение | Смысл |
|-------|---------|
| `0` (или `null`) | Только вручную — запуск через CLI или интерфейс |
| `30` | Каждые 30 минут |
| `120` | Каждые 2 часа |
| `1440` | Раз в день |

!!! warning "Расписанию нужен воркер"

    Расписание `dispatch-due-syncs` просыпается каждые 60 секунд и ставит в
    очередь синхронизацию каждого источника, чей срок наступил, поэтому без
    контейнера `worker`, который запускает `make dev`, `schedule_minutes` ничего
    не делает. Без него и ручной запуск (CLI, API или интерфейс) ставит
    синхронизацию в очередь, и она так же ждёт воркер. У источника никогда не
    бывает двух одновременных синхронизаций.

## Настройка Google Drive { #google-drive-setup }

### 1. Создайте служебную учётную запись { #1-create-a-service-account }

1. Откройте [Google Cloud Console](https://console.cloud.google.com/).
2. Создайте новый проект (или выберите существующий).
3. Включите **Google Drive API**.
4. Перейдите в **IAM & Admin > Service Accounts** и создайте новую служебную
   учётную запись.
5. Создайте JSON-ключ для служебной учётной записи и скачайте его.

### 2. Откройте доступ к папке Drive { #2-share-your-drive-folder }

1. Откройте Google Drive и перейдите в папку, которую хотите синхронизировать.
2. Нажмите **Share** и добавьте адрес электронной почты служебной
   учётной записи (он выглядит как `name@project.iam.gserviceaccount.com`).
3. Предоставьте как минимум доступ **Viewer**.

### 3. Передайте источнику ключ { #3-give-the-source-the-key }

Вставьте содержимое JSON-файла ключа в поле **Service Account JSON**
источника. Источник `gdrive` работает на учётных данных,
которые несёт его собственная конфигурация, и ни на чём больше — общего для
всего экземпляра резервного варианта нет, потому что он позволил бы
`folder_id` источника решать, что будет перечислено под служебной учётной
записью оператора.

`GOOGLE_DRIVE_CREDENTIALS_FILE` в `.env` предназначен только для команды CLI
`rag-sync-gdrive`.

### 4. Получите ID папки { #4-get-the-folder-id }

ID папки — последний сегмент URL папки Google Drive:

```
https://drive.google.com/drive/folders/1abc123def456ghi
                                        ^^^^^^^^^^^^^^^
                                        This is the folder ID
```

### 5. Поля конфигурации коннектора Google Drive { #5-google-drive-connector-config-fields }

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `folder_id` | string | Да | -- | ID папки Google Drive из URL |
| `include_subfolders` | boolean | Нет | `true` | Рекурсивно включать файлы из подпапок |

Сама служебная учётная запись — **не** поле конфигурации. Добавьте её в
хранилище секретов как учётные данные `gcp_service_account` и укажите на них
источник через `secret_id`: они хранятся один раз, и на них ссылается каждый
источник, которому они нужны, а не вставляются в каждый
([#937](https://github.com/vstorm-co/agenticos/issues/937)). Передача их в
`config` отклоняется.

В `folder_id` допустимо только то, что выдаёт Google, — буквы, цифры, `-` и
`_`. Всё остальное отклоняется при создании источника: идентификатор
подставляется в запрос к Drive, и одна кавычка в нём расширяет то, что
перечисляет запрос.

Google Docs, Sheets и Slides при скачивании автоматически экспортируются в
переносимые форматы (PDF, XLSX, PPTX). Файл, имя которого в Drive содержит
разделители пути, записывается одним файлом внутри каталога синхронизации и
никогда — по пути, который складывается из его имени.

## Настройка S3 / MinIO { #s3-minio-setup }

### 1. Настройте окружение { #1-configure-the-environment }

Добавьте в `.env` следующие переменные:

```bash
S3_RAG_ENDPOINT=https://s3.amazonaws.com   # or your MinIO URL, e.g. http://localhost:9000
S3_RAG_ACCESS_KEY=your-access-key
S3_RAG_SECRET_KEY=your-secret-key
S3_RAG_REGION=us-east-1                    # required for AWS, optional for MinIO
```

Для MinIO эндпоинт обычно `http://minio:9000` (Docker) или
`http://localhost:9000` (локально).

Собственный `endpoint_url` источника проверяется так же, как начальный URL
веб-источника: при сохранении источника и ещё раз при запуске синхронизации.
Loopback-адрес, link-local-адрес или адрес облачных метаданных отклоняется всегда, а
эндпоинту в частной сети, например контейнеру MinIO, нужно, чтобы его хост
был указан в
[`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings).
`S3_RAG_ENDPOINT` оператора не проверяется.

### 2. Поля конфигурации коннектора S3 { #2-s3-connector-config-fields }

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `bucket` | string | Да | -- | Имя бакета S3 |
| `prefix` | string | Нет | `""` | Префикс ключа, ограничивающий область синхронизации (например, `documents/legal/`). Оставьте пустым для всего бакета. |

## Настройка сайта { #website-setup }

Источник `web` читает публичный сайт, обычно сайт документации продукта. Ему не
нужны ни учётные данные, ни запись в хранилище секретов. Задайте ему начальный
URL, и он либо переходит по ссылкам с этой страницы, либо читает страницы,
перечисленные в карте сайта.

```bash
uv run agenticos cmd rag-source-add \
  --name "Product docs" \
  --type web \
  --org 0c8f2b1e-... \
  --collection product-docs \
  --config '{"root_url": "https://docs.example.com/guide/", "max_depth": 3}' \
  --sync-mode new_only \
  --schedule 1440
```

### Поля конфигурации коннектора сайта { #website-connector-config-fields }

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `root_url` | string | Да | -- | Страница, с которой начинается обход. Её хост — единственный, который читает источник. |
| `max_depth` | integer | Нет | `2` | Сколько переходов по ссылкам от начального URL делать, от `0` до `10`. `0` читает только начальную страницу. |
| `path_prefix` | string | Нет | папка начального URL | Читаются только страницы, путь которых начинается с этого значения. `https://docs.example.com/guide/intro` по умолчанию читает `/guide/`; укажите `/`, чтобы охватить весь хост. |
| `sitemap_url` | string | Нет | -- | Читать страницы, перечисленные в этой карте сайта, вместо перехода по ссылкам. Она должна находиться на хосте начального URL и использовать `https://`, если его использует начальный URL. Индекс карты сайта раскрывается до самих карт. |
| `max_pages` | integer | Нет | `500` | Обход останавливается, прочитав столько страниц, от `1` до `5000`. |

### Что ограничивает обход { #what-bounds-a-crawl }

- **Один хост и один путь.** Ссылки на другие хосты и на пути вне
  `path_prefix` не открываются. Перенаправление, уводящее за их пределы, тоже
  не открывается. Начальный URL на `https://` никогда не покидается ради
  `http://`: ссылка или перенаправление на страницу без шифрования не
  открывается.
- **Сеть экземпляра недостижима.** Каждый запрос — robots.txt, карта сайта,
  каждая страница и каждое перенаправление — проверяется по той же политике
  SSRF, что вебхуки и MCP-серверы. Он отправляется на адрес, прошедший
  проверку. Начальный URL, разрешающийся в loopback-адрес, link-local-адрес или
  адрес облачных метаданных, отклоняется всегда при сохранении источника.
  Разрешающийся в частный адрес — тоже, если оператор не указал его хост в
  [`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings).
- **robots.txt соблюдается** для карт сайта и страниц, включая `Crawl-delay`
  до десяти секунд. Обход представляется как `AgenticOS-Crawler`.
  Между запросами выдерживается не менее полсекунды, а указания `noindex` и
  `nofollow` на странице соблюдаются. Страница, которую карта сайта всё ещё
  перечисляет после `noindex` или после её исчезновения, удаляется из
  коллекции.
- **Размер и время.** Страница размером больше 5 МБ не читается. Обход
  останавливается на `max_pages`. Синхронизация прекращает читать сайт через
  шесть часов, а остановившаяся синхронизация ничего не удаляет.

Каждая страница сохраняется документом Markdown с её текстом и URL, откуда она
взята, без строки запроса. Навигация, колонтитулы и скрипты опускаются.
Эмбеддинги страницы строятся заново, только когда меняется её текст. Новый номер
сборки или скрипт отслеживания в разметке изменением не считается.

### Кто может читать то, что он импортирует { #who-can-read-what-it-imports }

У веб-источника нет учётных данных, поэтому его охват — это то, что сайт
показывает любому в интернете. Вход он не проходит никогда. Всё, что он
импортирует, доступно для поиска всем, кто может искать в коллекции, которую он
питает, как и у любого другого источника. См. [кто в итоге может читать
проиндексированное источником](../file-processing.md#who-ends-up-able-to-read-what-a-source-ingested).

Импортируются только HTML-страницы. PDF и другие файлы, на которые ссылается
страница, не скачиваются.

## Настройка репозитория Git { #git-repository-setup }

Источник `git` читает документацию репозитория по HTTPS — на GitHub, GitLab или
любом другом хосте, отдающем git по HTTPS. Ему нужны URL клонирования и токен
доступа, а не API какой-либо из платформ.

### 1. Выпустите токен для одного репозитория { #1-issue-a-token-for-the-one-repository }

**Охват токена — это охват источника.** Всё, что индексирует источник, становится
доступно для поиска тому, кто может читать коллекцию, поэтому токен, читающий
все закрытые репозитории своего владельца, — это токен, который может
опубликовать их все этой аудитории. См. [кто в итоге может читать
проиндексированное источником](../file-processing.md#who-ends-up-able-to-read-what-a-source-ingested).

- **GitHub:** **fine-grained personal access token**, *Only select repositories*,
  с одним репозиторием и единственным разрешением **Contents: Read-only**.
- **GitLab:** project access token на одном проекте, роль **Reporter**, область
  **`read_repository`** и только она.

Задайте срок действия. Когда он истечёт, следующая синхронизация источника
завершится ошибкой *the repository refused the source's token*, а исправление —
новый токен в том же секрете хранилища.

### 2. Добавьте его в хранилище секретов { #2-add-it-to-the-vault }

Добавьте токен в хранилище секретов как **Git access token**, указав **хост**,
к которому он относится: `github.com`, `gitlab.com` или ваш собственный сервер
вроде `git.example.com:8443`. Хост с не-ASCII буквами вводится в закодированном
виде, например `xn--bcher-kva.example` для `bücher.example`. Затем выберите
токен на шаге учётных данных источника. Он отправляется в заголовке HTTP
`Authorization`, никогда в URL и никогда в командной строке, которую может
прочитать другой процесс.

**Хост принадлежит токену, а не источнику.** Кто редактирует источник, тот
выбирает URL его репозитория, а токен отправляется только на хост, вместе с
которым он добавлен. Поэтому редактирование источника не может нацелить токен
организации на другой сервер, и никакой другой ключ, например API-ключ
провайдера моделей, для источника Git выбрать нельзя.

### 3. Поля конфигурации коннектора Git { #3-git-connector-config-fields }

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `repository_url` | string | Да | -- | URL клонирования по HTTPS, например `https://github.com/acme/handbook.git`. Без имени пользователя и токена. |
| `branch` | string | Нет | `main` | Ветка для чтения. |
| `path_prefix` | string | Нет | -- | Каталог внутри репозитория, например `docs`. Оставьте пустым для всего репозитория. |
| `include` | список строк | Нет | `**/*.md`, `**/*.txt` | Какие файлы индексировать — шаблоны в стиле `.gitignore` относительно `path_prefix`. |

По умолчанию это документация, а не всё дерево: исходный код репозитория — не
корпус, и его индексация наполняет базу знаний кодом, который никто не просил
искать. Добавьте шаблон вроде `**/*.pdf` для другого формата, который читает
парсер коллекции. Шаблон не может начинаться с `!`.

Каждый файл — документ с адресом
`git://<host>/<owner>/<repo>@<branch>/<path>`, с `:<port>` после хоста, если
порт не 443. Ветка входит в адрес, поэтому два источника, читающие две ветки
одного репозитория в одну коллекцию, сохраняют отдельные документы.

### 4. Что передаёт синхронизация { #4-what-a-sync-transfers }

Первый запрос каждой синхронизации — `git ls-remote` для ветки, около
килобайта. Если последний коммит не изменился с прошлого чистого запуска,
синхронизация на этом заканчивается. Если изменился, коннектор делает
неглубокий частичный клон с разрежённой выборкой: один коммит и только файлы,
подходящие под шаблоны `include`. Поэтому документация монорепозитория стоит
ровно своей документации, а не всего дерева исходников.

Прежде чем клон что-либо запишет на диск воркера, коннектор измеряет каждый
файл, который записал бы. Файл сверх лимита размера документа базы знаний
(`MAX_UPLOAD_SIZE_MB`, по умолчанию 50 МБ) или более 512 МБ файлов в сумме
отклоняются, и ничего не записывается.

Символические ссылки и подмодули не раскрываются, и ссылка не индексируется как
документ.

### Сетевые правила { #network-rules }

URL должен быть `https://`. Его хост разрешается один раз и проверяется, как
любой другой адрес, который выбирает организация: хост, разрешающийся в частный
адрес, loopback-адрес или link-local-адрес, отклоняется при сохранении источника
и снова при синхронизации, и git подключается только к адресам, которые прошли
проверку. Оператор может допустить хост в сети экземпляра через
[`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings).
Перенаправления не выполняются. Экземпляр за прокси исходящего трафика
(`HTTPS_PROXY`) продолжает его использовать; тогда хост разрешает сам прокси.

Образ воркера содержит `git`. Воркеру, собранному из другого образа, нужен `git`
2.37 или новее в `PATH`.

## Настройка SharePoint и OneDrive { #sharepoint-and-onedrive-setup }

Источник `sharepoint` читает одну библиотеку документов через Microsoft Graph:
библиотеку сайта SharePoint или OneDrive человека, который Microsoft 365 хранит
как отдельный сайт. Он может читать всю библиотеку или одну папку в ней. Он
входит как регистрация приложения Microsoft Entra, которую администратор вашего
клиента создаёт один раз.

### 1. Зарегистрируйте приложение в Microsoft Entra { #1-register-an-app-in-microsoft-entra }

В [Центре администрирования Microsoft Entra](https://entra.microsoft.com)
откройте **App registrations → New registration**. Дайте приложению имя вроде
*AgenticOS sync*, оставьте **Accounts in this organizational directory only** и
не заполняйте URI перенаправления. Источник входит как само приложение, а не
как человек.

На странице приложения **Overview** запишите **Application (client) ID**
и **Directory (tenant) ID**. В разделе **Certificates & secrets** добавьте
секрет клиента и скопируйте его **Value**. Значение показывается
один раз. Источнику нужен не *ID* секрета.

### 2. Выдайте доступ к одному сайту, а не ко всему клиенту { #2-grant-it-one-site-not-the-tenant }

**Охват приложения — это охват источника.** Всё, что индексирует источник,
становится доступно для поиска всем, кто может читать коллекцию, которую он
питает. См. [кто в итоге может читать проиндексированное
источником](../file-processing.md#who-ends-up-able-to-read-what-a-source-ingested).

В разделе **API permissions** добавьте **разрешение приложения** Microsoft Graph
**`Sites.Selected`** и дайте на него согласие администратора. Само по себе
`Sites.Selected` ничего не читает. Затем администратор выдаёт приложению доступ
на чтение к одному сайту, который читает источник:

```http
POST https://graph.microsoft.com/v1.0/sites/{site-id}/permissions
Content-Type: application/json

{
  "roles": ["read"],
  "grantedToIdentities": [
    {"application": {"id": "<client-id>", "displayName": "AgenticOS sync"}}
  ]
}
```

Этот вызов требует `Sites.FullControl.All`, поэтому его делает администратор из
Graph Explorer или через `Grant-PnPAzureADAppSitePermission` из PnP PowerShell,
а не само приложение.
`GET https://graph.microsoft.com/v1.0/sites/contoso.sharepoint.com:/sites/HR?$select=id`
возвращает идентификатор сайта. OneDrive получает доступ так же — через свой
сайт: `contoso-my.sharepoint.com:/personal/jane_contoso_com`.

!!! danger "`Files.Read.All` или `Sites.Read.All` открывает на чтение все библиотеки клиента"

    Согласие на эти разрешения даётся на весь клиент. Источник с ними всё равно
    читает только ту библиотеку, которую называет. Но тот, кто может
    редактировать источник, может направить его site URL на любой сайт или
    OneDrive в организации, и следующая синхронизация сделает эту библиотеку
    доступной для поиска всем, кто может читать коллекцию. Ничто в этом продукте
    не может определить, какое разрешение выдано приложению, потому что токен об
    этом не говорит. Используйте `Sites.Selected` и выдавайте по одному
    приложению на каждую аудиторию.

### 3. Добавьте его в хранилище секретов { #3-add-it-to-the-vault }

Добавьте приложение в хранилище секретов как **Microsoft Entra app**:
идентификатор клиента (tenant id) — или домен клиента, например
`contoso.onmicrosoft.com`, — идентификатор приложения (client id) и значение
секрета клиента. Затем выберите его на шаге учётных данных источника. Секрет
отправляется только на `login.microsoftonline.com` — для входа.

Секрет клиента истекает — максимум через два года. Когда он истёк, следующая
синхронизация завершается ошибкой *Microsoft Entra refused the app registration's
credentials (invalid_client)*. Добавьте в приложение новый секрет и
замените значение в том же секрете хранилища. Каждый источник, который его
использует, подхватит новое значение при следующей синхронизации.

### 4. Поля конфигурации коннектора SharePoint { #4-sharepoint-connector-config-fields }

| Поле | Тип | Обязательно | По умолчанию | Описание |
|-------|------|----------|---------|-------------|
| `site_url` | string | Да | -- | Сайт, например `https://contoso.sharepoint.com/sites/HR`, или OneDrive, например `https://contoso-my.sharepoint.com/personal/jane_contoso_com`. Только сайт: URL библиотеки или страницы, скопированный из браузера, отклоняется. |
| `library` | string | Нет | библиотека сайта по умолчанию | Имя библиотеки так, как его показывает SharePoint, например `Documents`. У OneDrive есть только библиотека по умолчанию. |
| `folder_path` | string | Нет | -- | Папка внутри библиотеки, например `Policies/HR`. Оставьте пустым для всей библиотеки. |
| `include_subfolders` | boolean | Нет | `true` | Читать ли папки внутри `folder_path`. |
| `extensions` | список строк | Нет | `.pdf`, `.docx`, `.md`, `.txt` | Какие типы файлов индексировать. Добавляйте `.pptx`, `.xlsx` или другой тип, только если его читает парсер коллекции: файл, который он прочитать не может, считается файлом с ошибкой при каждой синхронизации. |

Каждый файл — документ с адресом `sharepoint://<drive-id>/<item-id>`. Адрес
следует за файлом, а не за его путём, поэтому переименованный или перемещённый
внутри библиотеки файл сохраняет свой документ. Документ сохраняет имя файла, с
которым был проиндексирован, пока не изменится содержимое файла.

Записные книжки OneNote и файлы других типов не индексируются.

### 5. Что передаёт синхронизация { #5-what-a-sync-transfers }

Каждая синхронизация начинается с потока изменений Microsoft Graph для
библиотеки. Если в библиотеке ничего не изменилось с прошлого чистого запуска,
синхронизация на этом заканчивается: один запрос и никакого перечисления. Поток
охватывает всю библиотеку, потому что Graph предлагает его только для корня
библиотеки. Поэтому изменение в другой папке той же библиотеки заставляет
следующую синхронизацию снова перечислить папку источника.

Когда что-то изменилось, синхронизация перечисляет папку и скачивает все файлы
настроенных типов. Файл, содержимое которого не изменилось, затем пропускается
до построения эмбеддингов, поэтому эмбеддинги строятся только для новых и
изменённых файлов. Файл скачивается по адресу, который выдаёт для него Graph,
без токена приложения. Файл сверх лимита размера документа базы знаний
(`MAX_UPLOAD_SIZE_MB`, по умолчанию 50 МБ) не скачивается и считается файлом с
ошибкой.

Graph притормаживает клиента, который читает быстро. Запрос, который Graph
ограничивает (HTTP 429) или который завершается ошибкой 5xx или сетевой
ошибкой, выполняется всего четыре раза, и синхронизация ждёт столько, сколько
просит `Retry-After` от Graph, — до минуты. Папку, которую всё равно не удалось
перечислить, называют в журнале синхронизации, и эта синхронизация ничего не
удаляет, потому что файлы в той папке не были видны. Файлы в остальных папках
всё равно индексируются.

Файл, удалённый после перечисления и до своего скачивания, удаляется так же,
как файл, которого не было в перечислении.

### Сеть { #network }

Воркеру нужен исходящий HTTPS к `login.microsoftonline.com`,
`graph.microsoft.com` и хостам `*.sharepoint.com` вашего клиента. Ничто из того,
что вводит редактор источника, не становится адресом, к которому подключается
воркер: site URL — лишь имя, по которому ищет Graph. Национальные облака
Microsoft, например для государственных органов США и для Китая, используют
другие хосты и не поддерживаются.

## Справочник API { #api-reference }

Все эндпоинты источников синхронизации находятся под `/api/v1/rag/sync/`.
Перечисление требует `collections:view`, а всё, что меняет источник, —
`collections:edit`. Роли администратора среди них нет. Абзацы ниже говорят, до
каких источников дотягивается каждый. См. [кто может добраться до
коллекции](../file-processing.md#who-may-reach-a-collection).

`GET /api/v1/rag/sync/sources` перечисляет все источники, включая неназначенные
шаблоны, только при наличии `connections:manage`. Иначе он перечисляет
источники, питающие читаемые базы. Создание, отсоединение, редактирование,
удаление или клонирование неназначенного шаблона требует права **Управление
подключениями** (Manage connections). Назначенные источники требуют доступа на
редактирование своей базы, в том числе при управлении через `/org/integrations`;
разрешение организации на этой странице не обходит доступ к базе. Клонирование
проверяет источник и цель по отдельности.

Правки источника проверяют удалённые адреса до взятия блокировок изменения.
Запись под блокировкой сверяет проверенную ревизию и отклоняет устаревшие
изменения. Синхронизации из очереди перепроверяют свою исходную цель перед
индексацией. Очистка учётной записи и организации использует те же проверки
владения и удаления, что и удаление базы; индексация через CLI также записывает
происхождение и участвует в этих проверках.

История синхронизаций сохраняет организацию-инициатора и целевую базу после
удаления источника. Запуск без источника виден только при доказанном владении и
доступе к этой базе. Старые журналы без источника и без доказанного владения
скрыты и никогда не приписываются по общему имени коллекции.

### CRUD источников синхронизации { #sync-sources-crud }

| Метод | Эндпоинт | Описание |
|--------|----------|-------------|
| `GET` | `/api/v1/rag/sync/sources` | Перечислить источники синхронизации (все — при `connections:manage`) |
| `POST` | `/api/v1/rag/sync/sources` | Создать источник синхронизации |
| `PATCH` | `/api/v1/rag/sync/sources/{id}` | Обновить существующий источник синхронизации |
| `DELETE` | `/api/v1/rag/sync/sources/{id}` | Удалить источник синхронизации |
| `POST` | `/api/v1/rag/sync/sources/{id}/trigger` | Запустить синхронизацию вручную |

### Коннекторы и журналы { #connectors-logs }

| Метод | Эндпоинт | Описание |
|--------|----------|-------------|
| `GET` | `/api/v1/rag/sync/connectors` | Перечислить доступные типы коннекторов со схемами конфигурации |
| `GET` | `/api/v1/rag/sync/logs` | Перечислить историю синхронизаций (с фильтром по `collection_name`) |

### Пример: создать источник через API { #example-create-a-source-via-api }

```bash
curl -X POST http://localhost:8000/api/v1/rag/sync/sources \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Legal Drive",
    "connector_type": "gdrive",
    "collection_name": "legal",
    "config": {
      "folder_id": "1abc123def",
      "include_subfolders": true
    },
    "sync_mode": "new_only",
    "schedule_minutes": 120
  }'
```

### Пример: запустить синхронизацию через API { #example-trigger-a-sync-via-api }

```bash
curl -X POST http://localhost:8000/api/v1/rag/sync/sources/{source_id}/trigger \
  -H "Authorization: Bearer $TOKEN"
```

### Пример: проверить историю синхронизаций { #example-check-sync-history }

```bash
curl http://localhost:8000/api/v1/rag/sync/logs?limit=10 \
  -H "Authorization: Bearer $TOKEN"
```

### Пример: узнать доступные коннекторы { #example-discover-available-connectors }

```bash
curl http://localhost:8000/api/v1/rag/sync/connectors \
  -H "Authorization: Bearer $TOKEN"
```

Ответ содержит `config_schema` каждого коннектора — по нему интерфейс строит
динамические формы. Он также полезен для программной сборки интеграций.

## Обновление источника { #updating-a-source }

Через `PATCH` можно обновить любое подмножество полей существующего источника:

```bash
curl -X PATCH http://localhost:8000/api/v1/rag/sync/sources/{source_id} \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "sync_mode": "full",
    "schedule_minutes": 60,
    "is_active": false
  }'
```

Обновляемые поля: `name`, `config`, `sync_mode`, `schedule_minutes`,
`is_active`, `collection_name`.

Новое значение `collection_name` переносит источник в базу знаний, в которую это
имя разрешается для вашей организации, и в неё у вас должен быть доступ на
запись; `null` отсоединяет источник от любой базы, а источник без базы не
синхронизируется.

Установите `is_active` в `false`, чтобы приостановить источник, не удаляя его.
Приостановленный источник не может работать по расписанию и не может быть
запущен через API или CLI. В консоли его кнопка синхронизации отключена. Задача
из очереди проверяет ещё раз перед скачиванием файлов и завершается ошибкой,
если источник был приостановлен, пока она ждала. Приостановка не прерывает уже
начатую синхронизацию; установите `is_active` в `true`, чтобы разрешить новые
синхронизации.

При разрешении имени коллекции побеждает самая старая база в организации
источника, с откатом к базе уровня приложения. При равном времени создания
порядок задаётся идентификатором базы. API отказывается назначать источник по
имени коллекции, когда несколько подходящих баз имеют одинаковое самое раннее
время создания. Используйте базу знаний с уникальным именем коллекции, чтобы
снять эту неоднозначность.

## Наблюдение за синхронизациями { #monitoring-sync-operations }

Каждая синхронизация создаёт запись `SyncLog` со следующими полями:

| Поле | Описание |
|-------|-------------|
| `source` | Тип коннектора или `"local"` для индексации через CLI |
| `collection_name` | Целевая коллекция |
| `status` | `running`, `done` или `error` |
| `mode` | `full`, `new_only` или `update_only` |
| `total_files` | Число обнаруженных файлов |
| `ingested` | Успешно проиндексировано (новых) |
| `updated` | Успешно проиндексировано заново (заменено) |
| `skipped` | Пропущено (уже есть или не изменилось) |
| `failed` | Не удалось проиндексировать, включая страницы или файлы, которые не удалось прочитать при перечислении, и документы, которые не удалось удалить |
| `removed` | Удалено, потому что источник больше их не перечисляет (см. [что удаляет синхронизация](#what-a-sync-removes)) |
| `error_message` | Что пошло не так или почему ничего не удалено. Запуск может быть `done` и всё равно иметь сообщение, например когда обход остановился на лимите страниц |
| `started_at` | Когда синхронизация началась |
| `completed_at` | Когда синхронизация завершилась |

Смотреть журналы можно в выводе CLI или через API:

```bash
curl http://localhost:8000/api/v1/rag/sync/logs?collection_name=legal&limit=5 \
  -H "Authorization: Bearer $TOKEN"
```

## Добавление собственных коннекторов { #adding-custom-connectors }

Чтобы добавить новый тип коннектора (например, Notion, Confluence, Dropbox), см.
[Добавление коннектора синхронизации](./add-sync-connector.md).

Коротко:

1. Создайте класс, наследующий `BaseSyncConnector`, в
   `app/services/rag/connectors/`.
2. Реализуйте `list_files()`, `_fetch()` и, необязательно, `validate_config()`.
3. Объявите `SECRET_KIND` — какой вид секрета хранилища его аутентифицирует — и
   `CONFIG_MODEL`, модель Pydantic, описывающую, как найти документы. Учётные
   данные никогда не входят в число его полей.
4. Зарегистрируйте его в `CONNECTOR_REGISTRY` в
   `app/services/rag/connectors/__init__.py`.

После регистрации коннектор автоматически появляется в CLI, API и интерфейсе.

## Устранение неполадок { #troubleshooting }

### «No sync sources configured» { #no-sync-sources-configured }

Вы ещё не создали ни одного источника. Создайте его через `rag-source-add`
(CLI) или `POST /api/v1/rag/sync/sources` (API).

### «Unknown connector type» { #unknown-connector-type }

Указанный тип коннектора отсутствует в `CONNECTOR_REGISTRY`. Проверьте доступные
типы через `rag-sources` или `GET /api/v1/rag/sync/connectors`.
Google Drive (`gdrive`) доступен.
S3 (`s3`) доступен.
Website (`web`) доступен.
Git (`git`) доступен.

### Google Drive: «this source has no credential» { #google-drive-this-source-has-no-credential }

`secret_id` источника пуст, или секрет хранилища, на который он указывал, удалён.
Добавьте JSON служебной учётной записи в хранилище секретов и выберите его на
шаге учётных данных источника: `GOOGLE_DRIVE_CREDENTIALS_FILE` его не заменяет,
и эту настройку читает только команда CLI `rag-sync-gdrive`.

### «A Google Drive source needs a service account credential» { #a-google-drive-source-needs-a-service-account-credential }

`secret_id` указывает на учётные данные не того вида — скажем, на пару ключей
AWS. Источнику Drive нужны `gcp_service_account`, а источнику S3 — пара
`aws_credentials`; мастер предлагает только подходящие, поэтому сюда можно
попасть через API.

### Google Drive: «folder ID may contain only letters, digits, '-' and '_'» { #google-drive-folder-id-may-contain-only-letters-digits-and-_ }

Значение не является ID папки Drive. Возьмите его из URL папки: это последний
сегмент, и больше ничего из этого URL в поле не входит.

### Google Drive: «Cannot access folder» { #google-drive-cannot-access-folder }

Убедитесь, что вы открыли доступ к папке для адреса электронной почты служебной
учётной записи. Служебной учётной записи нужен как минимум доступ Viewer.

### S3: «Cannot access bucket» { #s3-cannot-access-bucket }

Проверьте, что `S3_RAG_ACCESS_KEY`, `S3_RAG_SECRET_KEY` и `S3_RAG_ENDPOINT`
правильно заданы в `.env`. Для MinIO убедитесь, что эндпоинт включает порт
(например, `http://localhost:9000`).

### Сайт: «resolves to private/internal address» { #website-resolves-to-privateinternal-address }

Начальный URL или карта сайта указывает внутрь сети экземпляра, либо его имя
разрешается туда. Веб-источник читает только публичные адреса, если оператор не
указал хост сайта в
[`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings). В
противном случае опубликуйте его страницы где-нибудь в публичном месте или
загрузите файлы напрямую.

### Сайт: «The site's robots.txt could not be read, so it was not crawled» { #website-the-sites-robotstxt-could-not-be-read-so-it-was-not-crawled }

`/robots.txt` на хосте начального URL три раза подряд завершился по тайм-ауту
или ответил серверной ошибкой (5xx). Обход не угадывает, что разрешил бы
недоступный robots.txt, поэтому запуск останавливается. Отсутствующий robots.txt
(404) или запрещающий (403) означает отсутствие правил, и обход продолжается.

### Сайт: «The start URL … did not lead to an HTML page» { #website-the-start-url-did-not-lead-to-an-html-page }

Начальный URL ответил 404, перенаправил на другой хост или за пределы
`path_prefix` либо отдал не HTML. Откройте его в браузере и используйте как
`root_url` адрес, на котором он заканчивается.

### Сайт: «robots.txt does not allow the start URL» { #website-robotstxt-does-not-allow-the-start-url }

Сайт просит обход не заходить в этот путь. Выберите начальный URL, который сайт
разрешает, или попросите владельца сайта разрешить `AgenticOS-Crawler`.

### Сайт: «… answered HTTP 403» или «… could not be reached» { #website-answered-http-403-or-could-not-be-reached }

Странице нужен вход, либо сайт отклонил обход. Запрос завершился ошибкой после
трёх попыток, если ответом был тайм-аут, 429 или 5xx. Каждая такая страница
считается файлом с ошибкой. В этом запуске ничего не удаляется, потому что
страницы за ней не были видны.

### «The source could not be listed completely, so documents it may no longer hold were kept» { #the-source-could-not-be-listed-completely-so-documents-it-may-no-longer-hold-were-kept }

Перечисление остановилось раньше времени: обход достиг `max_pages`, некоторые
страницы не удалось прочитать или папку SharePoint не удалось перечислить.
Найденное проиндексировано, и ничего не удалено. Для сайта увеличьте `max_pages`
или сузьте обход с помощью `path_prefix`, пока запуск не завершится без этого
сообщения. Для SharePoint см. запись об этой папке ниже.

### Git: «The repository refused the source's token» { #git-the-repository-refused-the-sources-token }

Токен истёк, был отозван или не может читать этот репозиторий. Выпустите новый,
как описано в [Настройка репозитория Git](#git-repository-setup), и замените
значение секрета хранилища, который использует источник; каждый источник с этим
секретом подхватит его при следующей синхронизации.

### Git: «The repository was not found, or the source's token cannot see it» { #git-the-repository-was-not-found-or-the-sources-token-cannot-see-it }

Сначала проверьте URL клонирования. Закрытый репозиторий отвечает *not found*, а
не *forbidden* токену, который не может его читать, поэтому **fine-grained
personal access token**, выпущенный для другого репозитория, выглядит именно так.

### Git: «The repository has no branch named …» { #git-the-repository-has-no-branch-named }

Поле `branch` называет ветку, которой в репозитории нет. По умолчанию это
`main`; у более старого репозитория ветка по умолчанию может называться
`master`.

### Git: «… is … MB, and a synced file may be at most … MB» { #git-is-mb-and-a-synced-file-may-be-at-most-mb }

Файл, подходящий под шаблоны `include`, больше лимита размера документа базы
знаний. Сузьте `include` или `path_prefix`, чтобы файл не попал в выборку. Для
этой синхронизации ничего не записано.

### Git: «… over the … MB one sync may check out» { #git-over-the-mb-one-sync-may-check-out }

Все файлы, подходящие под шаблоны `include`, вместе весят больше 512 МБ. Сузьте
`include` или `path_prefix` либо разделите репозиторий на несколько источников,
у каждого со своим префиксом.

### Git: «This token was added for …, and the repository is on …» { #git-this-token-was-added-for-and-the-repository-is-on }

Репозиторий источника находится на другом хосте, не на том, вместе с которым
добавлен его токен. Либо URL неверен, либо источнику нужен токен, добавленный
для этого хоста. На хост репозитория ничего не отправлено.

### Git: «A Git source needs a Git access token» { #git-a-git-source-needs-a-git-access-token }

Источник указывает на секрет другого вида, например на API-ключ. Добавьте токен
как **Git access token**, указав его хост, и выберите его.

### «Another sync of this source is still running» { #another-sync-of-this-source-is-still-running }

Запуск запросили, пока шёл другой запуск того же источника, поэтому он не
начался. Текущий запуск завершится как обычно; запустите снова после него, если
источник за это время изменился.

### Git: «… resolves to a private address» { #git-resolves-to-a-private-address }

Хост репозитория разрешается внутрь сети экземпляра, поэтому источник
отклоняется. Источник синхронизации не может добраться до сервера Git на
собственной инфраструктуре с внутренним адресом, если оператор не указал его
хост в
[`OUTBOUND_PRIVATE_ALLOWLIST`](../configuration.md#project-settings).

### Git: «git is not installed on this worker» { #git-git-is-not-installed-on-this-worker }

Воркер работает из образа без `git`. Поставляемый `backend/Dockerfile`
устанавливает его; в собственный образ его нужно добавить.

### Git: синхронизация завершилась без обработанных файлов { #git-a-sync-finished-with-no-files-processed }

Последний коммит ветки — тот же, что прочитал прошлый чистый запуск при той же
конфигурации, поэтому делать было нечего. Переключите источник на `full` на один
запуск, чтобы прочитать всё заново, несмотря ни на что.

### SharePoint: «Microsoft Entra refused the app registration's credentials (…)» { #sharepoint-microsoft-entra-refused-the-app-registrations-credentials }

Microsoft Entra не выполнил вход приложения. `invalid_client` обычно означает,
что секрет клиента истёк или что в хранилище лежит ID секрета вместо его
значения. `unauthorized_client` или `invalid_request` обычно означает, что
неверен идентификатор клиента (tenant id) или идентификатор приложения (client
id). Сверьте три значения с разделами приложения **Overview** и
**Certificates & secrets** и замените их в секрете хранилища.

### SharePoint: «Microsoft Graph did not accept the app's token for …» { #sharepoint-microsoft-graph-did-not-accept-the-apps-token-for }

Приложение выполнило вход, но его токен не несёт разрешения Microsoft Graph.
Добавьте **разрешение приложения** `Sites.Selected`, а не делегированное, и
дайте согласие администратора, как описано в
[шаге 2](#2-grant-it-one-site-not-the-tenant).

### SharePoint: «Microsoft Graph denied the app access to … (accessDenied)» { #sharepoint-microsoft-graph-denied-the-app-access-to-accessdenied }

У приложения есть `Sites.Selected`, но нет выданного доступа к этому сайту.
Выдайте ему `read` на сайте, как описано в
[шаге 2](#2-grant-it-one-site-not-the-tenant). Если в сообщении названа папка
внутри папки источника, у этой папки есть собственные разрешения, которые
исключают приложение. Остальная часть библиотеки проиндексирована, и ничего не
удалено.

### SharePoint: «There is no SharePoint site at …, or the app cannot see it» { #sharepoint-there-is-no-sharepoint-site-at-or-the-app-cannot-see-it }

Сначала проверьте URL сайта: это собственный адрес сайта, например
`https://contoso.sharepoint.com/sites/HR`, а не библиотека или страница внутри
него. При `Sites.Selected` так же может ответить и сайт, на который у приложения
нет выданного доступа.

### SharePoint: «The site has no document library named …» { #sharepoint-the-site-has-no-document-library-named }

Сообщение перечисляет библиотеки, которые видит приложение. Скопируйте одно из
этих имён в `library` или оставьте `library` пустым для библиотеки сайта по
умолчанию. Библиотека по умолчанию названа на языке сайта, например *Documents*
или *Dokumente*.

### SharePoint: «The library has no folder …» или «… is a file, not a folder» { #sharepoint-the-library-has-no-folder-or-is-a-file-not-a-folder }

`folder_path` не называет папку в библиотеке. Он отсчитывается от верхнего
уровня библиотеки, например `Policies/HR`, и не повторяет имя библиотеки.

### SharePoint: «The folder … could not be listed: …» { #sharepoint-the-folder-could-not-be-listed }

Папку внутри папки источника не удалось прочитать. Причина указана после
двоеточия. Остальные папки проиндексированы, и в том запуске ничего не удалено.

### SharePoint: «Microsoft 365 stayed unavailable or kept throttling … after 4 attempts» { #sharepoint-microsoft-365-stayed-unavailable-or-kept-throttling-after-4-attempts }

Graph всё ещё ограничивал запросы или отвечал ошибкой после четырёх попыток.
Следующая синхронизация начнётся заново. Если это происходит при каждой
синхронизации, задайте источнику более редкое расписание или разделите очень
большую библиотеку на несколько источников, у каждого со своим `folder_path`.

### SharePoint: «A SharePoint source needs a Microsoft Entra app credential» { #sharepoint-a-sharepoint-source-needs-a-microsoft-entra-app-credential }

Источник указывает на секрет другого вида, например на API-ключ. Добавьте
приложение в хранилище секретов как **Microsoft Entra app** и выберите его.

### SharePoint: синхронизация завершилась без обработанных файлов { #sharepoint-a-sync-finished-with-no-files-processed }

В библиотеке ничего не изменилось с прошлого чистого запуска при той же
конфигурации, поэтому делать было нечего. Переключите источник на `full` на один
запуск, чтобы прочитать всё заново, несмотря ни на что.

### Синхронизации по расписанию не выполняются { #scheduled-syncs-are-not-running }

Должна работать система фоновых задач. Проверьте, что ваш процесс-воркер
активен:

Без воркера будут работать только ручные запуски через CLI или API.

# Настройте базу знаний { #set-up-a-knowledge-base }

Как заставить агента отвечать по вашим собственным документам, от начала до
конца. Около двадцати минут, без терминала — и одно решение в процессе, которое
нельзя отменить.

[Обработка файлов](../file-processing.md) объясняет конвейер; здесь — рецепт.

## 1. Создайте коллекцию { #1-create-the-collection }

**Знания → Новая база знаний** (Knowledge → New). Дайте ей название, которое
человек узнает, — именно его потом выбирают из списка, — и область видимости,
которая решает, ваша она или организации.

!!! danger "Модель эмбеддингов фиксируется при создании"

    Это единственный выбор на этой странице, который нельзя изменить задним
    числом. Векторный столбец создаётся с размерностью этой модели, а две модели
    одинаковой размерности всё равно пишут в *разные* пространства — и поиск
    продолжал бы сравнивать векторы, которые означают не одно и то же.

    Передумать позже — значит создать новую коллекцию и заново проиндексировать
    всё. Форма предлагает модели, которые обслуживает выбранный провайдер, и
    выбирает первую; берите её, если нет причины поступить иначе, а если есть —
    см. [Выбор модели](../choosing-models.md#embeddings-are-a-separate-permanent-choice).

В разделе **Эмбеддинги** (Embeddings) выберите провайдера, который обслуживает
модель, и ключ в хранилище секретов, которым оплачивается работа модели. Нужны
оба: ключа эмбеддингов для всего экземпляра нет, поэтому коллекция без него
отклоняется здесь, а не создаётся и остаётся неспособной проиндексировать свой
первый документ. Ключ должен принадлежать выбранному провайдеру; если у
организации его ещё нет, форма рядом с выбором сохранит его. Провайдера и ключ
можно сменить позже, модель — нельзя, см. [Обработка
файлов](../file-processing.md#embeddings-the-model-whose-endpoint-answers-and-whose-key-pays).

**Ollama** тоже есть в списке провайдеров. Ей не нужен ключ: выберите её, одну из
её моделей и сервер, на котором она отвечает, — локальный сервис,
зарегистрированный в разделе **Знания → Интеграции** (Knowledge → Integrations),
собственный сервер организации или тот, что администратор экземпляра
зарегистрировал для всех, — и документы коллекции никогда не покидают сеть
экземпляра. На той же вкладке хранятся серверы OCR для LiteParse, выбираемые в
настройках разбора.

База знаний, созданная с именем уже существующей коллекции, наследует её
провайдера и ключ — в том числе отсутствующий, потому что каждая строка одной
коллекции должна получать эмбеддинги одинаково. Такой коллекции потом нужно
задать ключ на её собственной странице.

## 2. Решите, как читаются документы { #2-decide-how-documents-are-read }

У каждой коллекции свои настройки индексации, и каждая загрузка может их
переопределить. Значения по умолчанию разумны; вот три, над которыми стоит
подумать.

**Какой парсер читает PDF.**

| | Что это | Когда выбирать |
|---|---|---|
| `pymupdf` | Локальный, быстрый, бесплатный — и единственный, который извлекает встроенные изображения для описания | Документы, где главное — текст. Начните с него |
| `liteparse` | Локальный, учитывающий вёрстку, сохраняет таблицы как ASCII-сетки, а не сплющивает их | Документы, смысл которых в таблицах |
| `llamaparse` | Облачный сервис, оплата за страницу, возвращает markdown | Сканы и неудобные документы, с которыми два локальных справляются плохо, — и вы согласны, что страницы уходят наружу |

**Нужен ли OCR.** Включайте для сканов и фотографий документов, иначе
выключайте. Он медленнее и придумывает символы на чистом тексте.

**Как страницы режутся на фрагменты.** `recursive` разбивает по структуре и
годится по умолчанию; `markdown` следует заголовкам, что лучше, когда в
документах они действительно есть; `fixed` — грубый счёт символов, на случай,
когда два других дают бессмыслицу.

!!! tip "Меняйте по одному"

    Эти настройки влияют друг на друга. Если поиск плох, смените парсер *или*
    разбиение, заново проиндексируйте один документ и задайте тот же вопрос
    снова.

## 3. Добавьте документы { #3-put-documents-in }

Два способа, и в одной коллекции можно использовать оба.

**Загрузить** (Upload) файлы напрямую — выбранный парсер читает их, режет на
фрагменты, строит по ним векторы, и документ показывается как `processing`, пока
это не закончится.

**Синхронизировать источник** — папка Google Drive или бакет S3, которые
перечитываются по расписанию, так что коллекция следует за папкой, а не за её
копией. См. [Настройка источников синхронизации](configure-sync-sources.md).

!!! warning "Если индексация не удаётся на свежей установке, проверьте образ базы данных"

    Хранилище выполняет `CREATE EXTENSION IF NOT EXISTS vector` при первой записи
    в коллекцию, и штатный Postgres возвращает *extension "vector" is not
    available* — ошибку 500 ещё до фиксации любой строки. Образ должен быть
    `pgvector/pgvector:pg16`.

## 4. Дайте её агенту { #4-give-it-to-an-agent }

В Конструкторе, у агента:

1. Включите возможность **Поиск по знаниям** (Knowledge search).
2. Привяжите коллекцию: агент ищет в названных вами коллекциях и ни в каких
   других.
3. Задайте `default_top_k` — число фрагментов, которые возвращает один поиск.

**Начните с трёх.** Восемь фрагментов там, где хватило бы трёх, — самый частый
незаметный перерасход в этом продукте: найденный текст читается в том ходе, где
он пришёл, и в каждом ходе, где он переносится дальше, и обычно это самое
объёмное в промпте.

Затем скажите об этом в инструкциях. Поиск кладёт текст перед моделью;
инструкции решают, что она с ним сделает:

```
Answer from the knowledge collection and cite the document you used.
If the collection does not cover it, say so rather than guessing.
```

Именно второе предложение превращает уверенную выдумку в «у меня этого нет» — и
его стоит проверить намеренно, спросив то, чего в документах заведомо нет.

## 5. Проверьте её { #5-test-it }

Опубликуйте, откройте вкладку **Проверка** (Test) у агента и задайте три
вопроса:

| Что спросить | Что вы проверяете |
|---|---|
| То, что явно есть в документах | То, что поиск вообще работает и что в ответе есть ссылка на источник |
| То, чего в них явно *нет* | То, что агент отказывается, а не выдумывает |
| Что-то на краю — деталь в таблице или в скане | Прочитал ли парсер именно эту часть |

Третий вопрос находит настоящие проблемы — вот почему выбор парсера из шага 2
стоит пересматривать, а не доверять ему.

## Когда агент не находит то, что точно есть { #when-it-cannot-find-something-that-is-definitely-there }

Идите по списку сверху вниз; он примерно упорядочен по частоте причин.

1. **Документ в состоянии `processing` или failed?** Ошибка неудавшегося
   документа написана на самом документе и говорит, на каком этапе он сдался.
2. **Коллекция привязана именно к *этому* агенту?** Привязка задаётся для
   каждого агента, и опубликованная версия несёт те привязки, что были при
   публикации.
3. **Парсер прочитал эту часть?** Откройте документ и посмотрите извлечённый
   текст. Таблица, сплющенная в прозу, или скан без OCR невидимы для поиска, как
   бы ясно вы их ни видели.
4. **`default_top_k` слишком мал?** Три — впору для узкого корпуса и слишком
   мало для широкого.
5. **Страница действительно пуста или запрос не удался?** Оба случая показывают
   одно и то же «здесь ничего нет». Прежде чем делать вывод, проверьте вкладку
   сети.

## Итог { #recap }

- **Модель эмбеддингов фиксируется при создании.** Это единственный необратимый
  выбор здесь.
- **Сначала `pymupdf`**, `liteparse` — для документов с обилием таблиц,
  `llamaparse` — когда страницы могут уходить наружу, а остальные не
  справляются.
- **Начните `default_top_k` с трёх** и повышайте, только если ответам
  действительно не хватает контекста.
- В инструкциях должно быть сказано **«скажите об этом, а не догадывайтесь»** —
  один поиск не останавливает выдумывание.
- Проверьте на том, чего в документах **нет**, и на том, что спрятано в таблице.

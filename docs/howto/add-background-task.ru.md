# Добавьте фоновую задачу { #add-a-background-task }

Работа, которая переживает запрос, — это **задача** в таблице `background_jobs`:
сервис ставит её в очередь в своей транзакции, а воркер (`python -m app.worker`)
забирает её, выполняет и записывает, чем она закончилась. Та же таблица несёт
периодические задачи экземпляра. `app/core/background.py` остаётся для мелкой
работы, которую запрос передаёт собственному процессу: она делается по мере
возможности.

Задача долговечна, а задача в цикле событий API — нет. Она переживает
перезапуск, повторяется с нарастающей паузой, а задача, которая убивает свой
воркер, — включая принудительное завершение из-за нехватки памяти, — уже
израсходовала попытку, поэтому не может зациклиться. Что она сделала, видно на
странице «Фоновые задачи».

## По шагам { #step-by-step }

### 1. Объявите задачу { #1-declare-the-job }

Вид задачи объявляется в `app/worker/jobs.py`: его полезная нагрузка, пул, число
попыток, тайм-аут и приоритет. Модуль импортирует Pydantic и больше ничего, поэтому
сервис, который ставит задачу в очередь, никогда не импортирует код, который её
выполняет.

```python
# app/worker/jobs.py
class SendNotification(Payload):
    notification_id: UUID


SEND_NOTIFICATION = Task(
    kind="send-notification",
    payload_type=SendNotification,
    pool=Pool.SYSTEM,
    max_attempts=3,
    timeout=timedelta(minutes=5),
    priority=Priority.INTERACTIVE,
)
```

Полезная нагрузка несёт **идентификаторы и примитивы**, а не строку таблицы и не
сеанс. Задача читает строку, когда выполняется, и восстанавливает нужные ей
полномочия тогда же: к моменту, когда воркер её заберёт, строка могла измениться, а
человек, который просил, мог уже не иметь на это права.

Выбирайте пул по тому, на что задача тратит ресурсы:

| Пул        | Для чего                                                          | Как выполняется                                             |
| ---------- | ----------------------------------------------------------------- | ----------------------------------------------------------- |
| `agent`    | Запуски агентов и срабатывания триггеров: долгие, ждут модели     | В цикле событий воркера, `WORKER_AGENT_CONCURRENCY` одновременно    |
| `eval`     | Запуски оценок: часы по набору данных, каждый держит свой слот всё время | В цикле событий воркера, `WORKER_EVAL_CONCURRENCY` одновременно     |
| `workflow` | Узлы сценария: шаги HTTP, файлов и песочницы, в основном ожидание | В цикле событий воркера, `WORKER_WORKFLOW_CONCURRENCY` одновременно |
| `ingest`   | Разбор и эмбеддинги: тяжёлые по процессору и памяти               | Одна задача на дочерний процесс, в пределах `WORKER_INGEST_MEMORY_MB`  |
| `system`   | Обходы, очистки, отчёты: короткие                                 | В цикле событий воркера, `WORKER_SYSTEM_CONCURRENCY` одновременно   |

### 2. Напишите обработчик и привяжите его { #2-write-the-handler-and-bind-it }

```python
# app/worker/tasks/notification_tasks.py
async def send_notification(job: SendNotification) -> None:
    async with get_worker_db_context() as db:
        notification = await notification_repo.get_by_id(db, job.notification_id)
        if notification is None:
            return  # deleted since it was queued: nothing left to send
        await NotificationDelivery(db).send(notification)
```

Привяжите его к виду в `production()` в `app/worker/handlers.py`:

```python
Handler(jobs.SEND_NOTIFICATION, notification_tasks.send_notification),
```

Исключение делает попытку неудачной, и задача повторяется до `max_attempts`; её
тип, сообщение и последние кадры попадают в строку задачи. Полезная нагрузка,
которая больше не проходит проверку, или вид, которого не знает ни один воркер,
падает сразу, без повтора: иначе она снова закончилась бы так же. Обработчик может
вернуть модель Pydantic, и она сохраняется как результат задачи.

### 3. Поставьте её в очередь из сервиса { #3-queue-it-from-a-service }

```python
from app.services.background_jobs import enqueue
from app.worker.jobs import SEND_NOTIFICATION, SendNotification

await enqueue(
    self.db,
    SEND_NOTIFICATION,
    SendNotification(notification_id=notification.id),
    organization_id=notification.organization_id,
)
```

Задача пишется в транзакции запроса, поэтому существует ровно тогда же, когда и
строка, которую она называет: откаченный запрос не ставит в очередь ничего, а
зафиксированный будит воркеров пула через `NOTIFY`, как только строку можно
прочитать. Это была гонка [#417](https://github.com/vstorm-co/agenticos/issues/417),
и её устранили самой конструкцией, а не через `spawn_after_commit`.

Три параметра определяют, как ведут себя копии задачи:

- `dedupe_key` держит не больше одной копии в очереди. С `dedupe_active=True`
  выполняющаяся копия тоже отбрасывает новую: синхронизация, которая уже идёт,
  делает второй запрос на неё лишним.
- `concurrency_key` позволяет копиям вставать в очередь, но выполняет их по одной,
  например две синхронизации одного источника.
- `run_after` откладывает первую попытку.

### 4. Запланируйте её (необязательно) { #4-schedule-it-optional }

Периодическая задача объявляется в `SCHEDULES` в `app/worker/schedules.py`. Её
полезная нагрузка — `Tick`, который называет срабатывание, для которого она
запущена, поэтому задача, покрывающая период, — недельный отчёт, — знает, какой
именно период:

```python
Schedule("send-digest", jobs.SEND_DIGEST, timedelta(days=1)),
```

Каждое расписание — это интервал на фиксированной сетке, хранящийся в
`background_schedules`, поэтому перезапуск продолжает с того места, где остановился
последний воркер. Две настройки решают, что делает неудобное срабатывание:

- **`misfire`** — для срабатывания, опоздавшего больше чем на `grace` (одна
  минута): `latest` запускается один раз за всё пропущенное, `skip` ждёт
  следующего. Никогда не бывает по одному запуску на каждое пропущенное
  срабатывание.
- **`overlap`** — для срабатывания, которое приходит, пока предыдущая задача в
  очереди или выполняется: `skip` отбрасывает его, `queue` позволяет одной
  подождать за ней, `allow` выполняет его параллельно.

Для задач, которые обходят текущее состояние, оставляйте значения по умолчанию:
`latest` и `skip`. Задача, чей запуск покрывает собственный период, как отчёты об
использовании, берёт `overlap=QUEUE`, чтобы медленная неделя не стала неделей, за
которую никому ничего не отправили.

### 5. Запустите воркер { #5-run-the-worker }

```bash
make dev                                   # API, worker, frontend, Postgres, Redis
uv run --directory backend python -m app.worker   # the worker on its own
```

`WORKER_POOLS` ограничивает, какие пулы обслуживает воркер, поэтому экземпляр может
запускать индексацию на более мощной машине. Расписания выполняет каждый воркер; при
захвате каждое наступившее расписание выполняется один раз, сколько бы воркеров ни
проснулось в один и тот же момент.

## Когда что-то идёт не так { #when-something-goes-wrong }

Задача, которая убила свой воркер пять раз подряд, ставит на паузу свой **вид**: ни
один воркер её не забирает, пока владелец экземпляра не возобновит её на странице
«Фоновые задачи», и каждый владелец узнаёт об этом в приложении и по электронной
почте.
Задачу, у которой кончились попытки, можно перезапустить с той же страницы, а
стоящую в очереди — отменить. Каждое действие попадает в аудит.

!!! note "Когда `spawn_after_commit` всё ещё уместен"

    Работа, потеря которой при перезапуске безвредна, — прогретый кеш,
    уведомление о том, что и так видно в другом месте, — всё ещё может идти через
    `spawn_after_commit`. Она выполняется в собственном цикле событий API, поэтому
    держите её короткой, а всё, что обязано произойти, отдавайте задаче.

## Тестирование { #testing }

Обработчик задачи запускайте прямо в модульном тесте: это обычная корутина.
Постановка в очередь и захват тестируются на настоящей базе в
`backend/tests/integration/test_background_job_queue.py`, а воркер, убитый
по-настоящему, — в `backend/tests/integration/test_worker_runtime.py`; начните
оттуда, если изменение касается самой очереди.

# Отвечайте на вопросы из своей базы данных { #answer-questions-from-your-database }

Подключите Postgres MCP-сервер, чтобы агент отвечал на вопросы из вашей
собственной базы данных, но сначала поставьте между агентом и вашими таблицами
роль только для чтения и схему из одних представлений. Это процедура, которую
нужно выполнить, а не отчёт об измеренном развёртывании: до MCP-сервера, который
нужен этому рецепту, из этого экземпляра не достучаться по причине, описанной
ниже, поэтому здесь ничего не запускалось целиком на работающем агенте.

## Что понадобится { #what-you-need }

- Работающий [экземпляр AgenticOS](../install.md) с профилем модели.
- Postgres MCP-сервер, который вы запускаете сами и который доступен по URL, до
  которого этот экземпляр может дозвониться. Запись `postgres` в каталоге — ровно
  об этом: хостингового URL нет, Bearer-токен проверяет *ваш собственный
  сервер*, и есть предупреждение направить его на представления только для
  чтения, а не на первичную базу с правом записи. См.
  [каталог](../mcp.md#data-and-analytics).
- `connections:manage`, чтобы зарегистрировать подключение организации.

## Зачем роль только для чтения и схема из одних представлений { #why-a-read-only-role-and-a-views-only-schema }

**Согласование не читает SQL за вас.** Политика `approval` привязки может
придерживать каждый запрос до решения человека — `all`, с точным SQL на
карточке, — но агент, задающий десятки вопросов, превращает это в пустую
формальность, а `writes` полагается на то, что сервер помечает свой инструмент
запросов как «только чтение». См. [какие вызовы ждут
человека](../mcp.md#which-calls-wait-for-a-person). Границей должны быть сами
учётные данные базы, а не настройка агента.

Эту работу делают два решения:

- **Роль без прав записи**, так что худшее, что может сделать ошибочный или
  подстроенный запрос, — прочитать то, что читать не следует, но никогда не
  изменить и не удалить строку.
- **Схема из представлений, а не из базовых таблиц**, выданная этой роли вместо
  самих таблиц. Представление может убрать столбцы, которые модель видеть не
  должна, и заранее агрегировать то, что возвращает, — это и граница
  приватности, и более дешёвый запрос, который агенту нужно написать.

## Подготовьте входные данные { #prepare-the-input }

Небольшая синтетическая таблица `orders` в отдельной базе:

```sql
CREATE TABLE orders (
    id           serial PRIMARY KEY,
    customer     text NOT NULL,
    status       text NOT NULL CHECK (status IN ('paid', 'refunded', 'pending')),
    amount_cents integer NOT NULL,
    created_at   date NOT NULL
);

INSERT INTO orders (customer, status, amount_cents, created_at) VALUES
    ('Ada',     'paid',     4200, '2026-09-01'),
    ('Grace',   'paid',     1800, '2026-09-02'),
    ('Ada',     'refunded', 4200, '2026-09-03'),
    ('Rex',     'paid',     9900, '2026-09-05'),
    ('Grace',   'pending',  2500, '2026-09-06'),
    ('Linus',   'paid',     3300, '2026-09-06'),
    ('Rex',     'paid',     1500, '2026-09-08'),
    ('Ada',     'paid',     6000, '2026-09-09');
```

Схема из одних представлений и роль, от имени которой аутентифицируется строка
подключения MCP-сервера:

```sql
CREATE SCHEMA reporting;

CREATE VIEW reporting.daily_paid_totals AS
SELECT created_at, count(*) AS paid_orders, sum(amount_cents) AS paid_amount_cents
FROM orders
WHERE status = 'paid'
GROUP BY created_at
ORDER BY created_at;

CREATE VIEW reporting.status_counts AS
SELECT status, count(*) AS orders, sum(amount_cents) AS amount_cents
FROM orders
GROUP BY status
ORDER BY status;

CREATE ROLE shop_readonly LOGIN PASSWORD 'change-me';
GRANT CONNECT ON DATABASE shop_demo TO shop_readonly;
GRANT USAGE ON SCHEMA reporting TO shop_readonly;
GRANT SELECT ON reporting.daily_paid_totals, reporting.status_counts TO shop_readonly;
REVOKE ALL ON SCHEMA public FROM shop_readonly;
```

Опора для сверки, чтобы проверить ответ по исходным строкам: `status_counts`
даёт paid — 6 заказов / 26700 центов, pending — 1 / 2500, refunded — 1 / 4200.
Запрос `shop_readonly` напрямую к `orders` отклоняется с
`permission denied for table orders` — представления остаются единственной
дверью.

## Подключите сервер { #connect-the-server }

1. В **Инструменты → MCP-серверы** (Toolbox → MCP servers) агента выберите
   **Подключить сервер** (Connect a server) и укажите **PostgreSQL** из
   каталога — или подключите его один раз в **MCP-серверы** (MCP servers) в
   настройках организации, чтобы его могли привязать несколько агентов.
2. Направьте подключение на ваш собственный работающий Postgres MCP-сервер
   (например, [`crystaldba/postgres-mcp`](https://github.com/crystaldba/postgres-mcp)),
   настроенный со строкой подключения `shop_readonly` и его ограниченным
   режимом только для чтения. Вставьте токен как Bearer-токен подключения —
   тот, который проверяет сервер, а не пароль базы.
3. В привязке агента сузьте `allowed_tools` до инструментов только для чтения,
   которые предоставляет сервер, поверх того, что уже разрешает само
   подключение.
4. Привяжите только это подключение, задайте бюджет и напишите инструкции,
   которые называют оба представления и велят агенту говорить, когда для
   вопроса нужен столбец или таблица, которых в представлениях нет, а не гадать.

## Почему это не запускалось здесь { #why-this-could-not-be-run-here }

Подключить сервер к этому экземпляру пробовали, и это было отклонено:

```text
This MCP server URL cannot be used: Blocked: 'localhost' resolves to
private/internal address '::1'. SSRF protection does not allow requests to
internal networks.
```

URL подключения MCP отклоняется для любого адреса loopback, приватного,
link-local или общего CGNAT, если только оператор не внесёт его хост в
[`MCP_ALLOWED_HOSTS`](../configuration.md#project-settings). См. [URL, до
которого экземпляр не должен достучаться,
отклоняется](../mcp.md#a-connection). Postgres MCP-сервер, доступный только на
`localhost` или по адресу приватной сети, — обычное место, где его впервые
запускают, — нельзя подключить с машины самого экземпляра.

Чтобы подключить его, запустите его под собственным именем хоста в сети
экземпляра и внесите это имя — никогда `localhost`. Или поставьте перед ним
маршрутизируемый адрес: небольшой хост с публичным IP или IP, доступным через
VPN, либо туннель.

SQL выше выполнялся и проверялся напрямую в Postgres; отказ роли и итоги по
представлениям настоящие. Не проверено одно: как агент на самом деле делает
запросы через подключённый сервер, потому что сервер так и не стал доступен для
подключения.

## Проверьте результат { #check-the-result }

| Проверка | Образец |
| --- | --- |
| Вопрос, называющий сумму оплаченного | 26700 (шесть оплаченных заказов) |
| Вопрос об ожидающих заказах | 2500 (один заказ) |
| Вопрос о столбце, которого нет ни в одном представлении (например, имя клиента) | Агент говорит, что не может ответить на это исходя из того, к чему привязан |
| Запрос, который роль выполнить не может (update, delete) | Отклоняется базой: `permission denied` |
| `allowed_tools`, суженные до инструментов только для чтения | Инструмента записи, который предлагает сервер, нет в наборе инструментов модели вовсе |

## Когда что-то идёт не так { #when-it-goes-wrong }

- **Подключение отклонено с сообщением об SSRF.** Адрес сервера — loopback,
  приватный или иным образом внутренний для сети самого экземпляра; см. выше.
  Поставьте перед ним маршрутизируемый адрес или внесите его хост в
  `MCP_ALLOWED_HOSTS`.
- **Агент читает базовую таблицу вместо представлений.** `shop_readonly`
  получила права на `public` наравне с `reporting`, или у неё так и не отозвали
  права на схему базовой таблицы. Повторите `REVOKE` выше.
- **Запрос агента выглядит так, будто что-то изменил.** Если у роли
  действительно нет прав записи, он не мог этого сделать; проверьте права роли,
  прежде чем решать, что агент повёл себя неправильно.
- **Подключение проверяется успешно, но Конструктор не показывает
  инструментов.** Его ещё ни разу не проверяли или последняя проверка не
  удалась: `POST
  /mcp-connections/{id}/test` обновляет список.
- **Двум агентам нужен разный доступ к одной базе.** Подключите сервер дважды,
  под двумя именами, каждое со своей ролью и своими представлениями: один
  сервер, две учётные записи, и никогда — одна роль, расширенная под более
  требовательного агента.

## Зафиксируйте проверку { #record-the-trial }

Сохраните SQL, создавший образец, права роли, определения представлений,
`allowed_tools` подключения и `allowed_tools` на уровне привязки агента. Человек
по-прежнему решает, какие столбцы попадут в представление, прежде чем агент до
него доберётся: сузить доступ после того, как агент уже задаёт вопросы, —
гораздо более трудный разговор, чем решить это заранее.

# Добавьте возможность { #add-a-capability }

**Возможность** — единица, из которой собран агент. Её Конструктор показывает как
переключатель, и её спецификация называет по `id`.

Она намеренно не «инструмент». Инструмент — деталь реализации: «Поиск по знаниям»
— одно решение для человека, настраивающего агента, и сколько функций она
выставляет — одну сегодня и три завтра — не его забота. Возможность покрывает и
то, что вообще не является инструментом: защиту бюджета, механизм согласования,
стратегию сжатия. Одно понятие покрывает всю сборку вместо двух, которые неуклюже
перекрываются.

!!! abstract "Код определяет, что существует; конфигурация только собирает это"

    Ничто из того, что вводит оператор, не создаёт новую возможность, и именно
    поэтому набор того, что агент умеет, можно проверить.

## Форма { #the-shape }

Одна папка на возможность в `backend/app/agents/capabilities/`:

```
weather/
  __init__.py       registration — the id, the name the picker shows, the builder
  _capability.py    the AbstractCapability subclass
  _toolset.py       the tools, and the text the model reads before calling them
  README.md         why this exists and what it deliberately does not do
```

!!! warning "Раскладка принудительна, и одно её правило — тихий сбой"

    `@register` встречается в `__init__.py` и больше нигде. Регистрация в
    подмодуле срабатывает, только если что-то импортирует этот модуль, — так
    возможность исчезает из Конструктора, а все тесты остаются зелёными. Вместо
    этого падает `tests/test_capability_layout.py`.

Эта раскладка — не предложение: её проверяет `tests/test_capability_layout.py`.
В каждом пакете есть `_capability.py`, и каждый пакет, предлагающий собственные
инструменты, имеет `_toolset.py`. Возможность без инструментов — `clock`,
`thinking` — перечислена в этом тесте с причиной, вместо того чтобы нести пустой
модуль.

Инструменты живут отдельно от класса возможности, потому что **имя и описание
инструмента — это промпт**: модель читает их, прежде чем решить вызвать, а автор
агента может переписать и то и другое для каждого агента. Спрятанные в замыкании
`get_toolset`, они доступны только тому, кто написал класс.

Посмотрите `clock/` — самый маленький полный пример — и `knowledge/` — пример со
схемой конфигурации, ресурсами и областью доступа.

## 1. Возможность { #1-the-capability }

`_capability.py` — dataclass, расширяющий `AbstractCapability` и строящий свой
набор инструментов лениво:

```python
"""Current weather for a place."""

from __future__ import annotations

from dataclasses import dataclass, field
from typing import Any

from pydantic_ai.capabilities import AbstractCapability
from pydantic_ai.tools import AgentDepsT
from pydantic_ai.toolsets import AbstractToolset, FunctionToolset


def _build_toolset(units: str) -> FunctionToolset[Any]:
    async def current_weather(city: str) -> dict[str, str]:
        """Get the current weather for a city.

        Use this when an answer depends on today's conditions rather than a
        seasonal average.
        """
        ...

    toolset: FunctionToolset[Any] = FunctionToolset()
    toolset.add_function(current_weather, takes_ctx=False)
    return toolset


@dataclass
class Weather(AbstractCapability[AgentDepsT]):
    """Gives an agent current conditions instead of a guess."""

    units: str = "metric"
    _toolset: AbstractToolset[Any] | None = field(
        default=None, init=False, repr=False, compare=False
    )

    def get_toolset(self) -> AbstractToolset[Any]:
        if self._toolset is None:
            self._toolset = _build_toolset(self.units)
        return self._toolset
```

Docstring инструмента — это промпт. Его читает модель, решая, вызывать ли
инструмент, поэтому он говорит, *когда это использовать*, а не что делает
функция, — см. `~/.claude/standards/prompting.md`.

## 2. Зарегистрируйте её { #2-register-it }

`__init__.py`:

```python
"""Weather capability — current conditions."""

from pydantic import BaseModel, Field

from app.agents.capabilities._registry import (
    CapabilityBuildContext,
    CapabilityToolInfo,
    register,
)
from app.agents.capabilities.weather._capability import Weather

__all__ = ["Weather"]


class WeatherConfig(BaseModel):
    units: str = Field(
        default="metric",
        pattern="^(metric|imperial)$",
        title="Units",
        description="metric for °C and km/h, imperial for °F and mph.",
    )


@register(
    id="weather",
    name="Weather",
    category="data",
    description="Read current conditions for a place instead of assuming them.",
    tools=(
        CapabilityToolInfo(
            id="current_weather",
            description="Get the current weather for a city.",
        ),
    ),
    config_schema=WeatherConfig,
    scopes=("weather:read",),
)
def _build(ctx: CapabilityBuildContext) -> Weather | None:
    """Build the capability from its validated config."""
    config = ctx.config if isinstance(ctx.config, WeatherConfig) else WeatherConfig()
    return Weather(units=config.units)
```

- **`id`** попадает в каждую опубликованную спецификацию, и это единственное, что
  не должно меняться никогда. Имя меняйте свободно; `id` — никогда.
- **`tools`** намеренно не имеет значения по умолчанию. Пропуск аргумента — это
  `TypeError`; возможность, у которой действительно нет инструментов, говорит
  `tools=()`. Именно с `id` каждой записи соотносятся `tool_approval` и
  `tool_overrides` в спецификации, а её `description` должна быть кратким изложением
  docstring самого инструмента: человек, выбирающий, что требует согласования, и
  модель, выбирающая, когда действовать, должны читать один и тот же текст, а не два
  пересказа, которые расходятся.
Записанные вызовы инструментов сохраняют этот стабильный `id` как `tool_id` вместе
с фактическим именем, которое вызвала модель. Рендереры чата и общие представления
используют эту идентичность, поэтому переименование для отдельного агента сохраняет
своё представление после перезагрузки. Старые вызовы без `id` откатываются к
записанному имени; вновь записанные вызовы внешних MCP несут явное общее
представление и не могут претендовать на встроенное представление по имени.

- **`config_schema`** порождает форму Конструктора и проверяется при публикации,
  поэтому плохое значение обнаруживается, пока кто-то смотрит на форму, а не
  посреди запуска. Дайте каждому полю `title` и `description`, написанные для
  человека, который его заполняет, и те же два поля под `capabilityConfig.<id>.<field>`
  в `frontend/messages/en.json`, `pl.json` и `de.json`. Без заголовка форма
  показывает имя поля по-английски на любом языке;
  `tests/test_capability_registry.py` падает на поле без заголовка или без записи в
  каталоге и на английской записи, которая расходится со схемой.
- **`scopes`** отклоняются во время сборки, когда организация их не выдала.
- **`side_effecting=True`** помечает инструменты возможности как действующие во
  внешнем мире, и Конструктор говорит об этом рядом с выбором согласования. Это
  ничего не ограничивает: ни один инструмент не ждёт человека, пока автор не
  попросит.
- **Возврат `None`** означает «ничего не добавляет *этому* агенту», и возможность
  вообще не подключается. `knowledge` делает так, когда не привязано ни одной
  коллекции: инструмент поиска, который всегда возвращает пусто, хуже
  отсутствующего, потому что модель продолжает его пробовать.
- **`ctx.resources`** несёт то, что было получено из базы для этого запуска: имена
  коллекций, навыки. Возможность никогда не запрашивает их сама; модель спрашивает,
  *что* искать, а не *где*.

!!! danger "Необъявленный инструмент выполняется без проверки, и никто об этом не скажет"

    `tools=` — это то, для чего Конструктор предлагает согласование по каждому
    инструменту, и то, с чем сверяется механизм согласования. Опасная половина
    сбоя тихая: автор добавляет второй инструмент, действующий во внешнем мире,
    забывает его объявить, и он навсегда выполняется без участия человека.
    `tests/test_capability_registry.py` сравнивает объявленный список с
    инструментами, которые модель действительно получает, — и это единственное, что
    это ловит.

**Сборщик может вернуть возможность, которую писали не мы.** Его сигнатура —
`CapabilityBuildContext -> AbstractCapability[Any] | None`, поэтому всё, что
поставляет Pydantic AI, — допустимый возврат: `thinking/` регистрирует
`pydantic_ai.capabilities.Thinking` и вообще не имеет `_capability.py`. Оборачивание
чужой возможности, чтобы сделать её «нашей», лишь добавляет второе место, где
задаётся то же значение. Реестр штампует возвращённый экземпляр `id` реестра, с
которым и сверяется механизм согласования, поэтому чужая возможность приходит с той
же идентичностью, что и локальная.

Сужение через `isinstance`, а не приведение типа, — так делает каждая встроенная
возможность: `ctx.config` типизирован базовой моделью, потому что реестр не знает,
какую схему объявила эта возможность, а возможность, привязанная вовсе без
конфигурации, получает свои значения по умолчанию вместо падения.

!!! important "Затем добавьте модуль в `load_builtins()` в `_registry.py`"

    Модуля, который никто не импортирует, для Конструктора не существует. Эта
    связанность намеренна: регистрация — это импорт, а не сканирование.

## 3. Напишите README { #3-write-the-readme }

Он есть в каждой папке возможности. Скажите, зачем она существует, чего она
намеренно не делает и какое решение будущий читатель иначе отменил бы. Здесь живёт
обоснование, а не в сообщении коммита.

## 4. Протестируйте её { #4-test-it }

!!! danger "`app/agents/**` покрыт на 100%, и это принуждается в CI"

    Новая возможность с непроверенной веткой ломает сборку. Вам **не** нужно
    расширять для неё порог: оба списка в `backend/pyproject.toml` уже содержат
    шаблон `app/agents/**`, а `test_every_file_in_a_platform_package_is_gated`
    существует, чтобы так и оставалось. Правка этих списков нужна для нового
    *пакета* платформы, вне уже охваченных шаблоном. См. `## Testing` в `AGENTS.md`
    и `tests/test_capability_registry.py` ради стиля.

Стоит покрыть отдельно:

- то, что схема конфигурации отклоняет плохое значение, потому что это проверка при
  публикации
- то, что сборщик возвращает `None`, когда должен ничего не добавлять
- отказ по области доступа, если возможность её объявляет
- сам инструмент, включая то, что он делает, когда то, что он вызывает, недоступно

## Где это появляется { #where-it-shows-up }

Больше ничего менять не нужно. `GET /api/v1/agents/capabilities` отдаёт реестр,
список выбора в Конструкторе строится по нему, а `schema-form.tsx` создаёт форму
настройки из `config_json_schema()`. Возможность, добавленная здесь, появляется
в продукте при следующем перезапуске.

При написании схемы стоит знать две вещи, которые читает сгенерированная форма:

- **Значение поля по умолчанию показывается как его значение**, а не серым цветом
  подсказки. Пока кто-то не изменит поле, ничего не сохраняется, поэтому поле
  продолжает следовать за значением по умолчанию, которое потом меняется
  в коде, — но то, что человек видит, и есть то, что произойдёт, если его
  не трогать. Дайте каждому необязательному полю разумное значение
  по умолчанию, и форма будет заполнена сразу при открытии.
- **`Literal` показывает свои сырые значения**, если схема не говорит иначе,
  а сырые значения — это формат спецификации: `clear_tool_results`
  в выпадающем списке — выбор, который человек делает наугад. Скажите, что
  делает каждый вариант, с помощью
  `json_schema_extra={"x-enum-labels": {value: "what it does"}}` у поля — это
  ключевое слово-расширение, потому что в JSON Schema такого нет; оно хранится
  рядом с определением по той же причине, по которой там `description`.
- **Строка — это однострочное поле**, если схема не говорит иначе, а промпт
  в нём — поле, в котором никто не разберёт, что он редактирует.
  `json_schema_extra={"x-multiline": True}` даёт ему тот же редактор Markdown,
  что и у собственных инструкций агента: исходный текст или предпросмотр и
  проверка, привязанная к полю. Та же форма расширения, та же причина.

## Добавление инструмента к существующей возможности { #adding-a-tool-to-an-existing-capability }

Обычно это верный шаг, когда новое поведение относится к уже принятому кем-то
решению: второй способ читать базу знаний — всё ещё «поиск по знаниям». Три
шага, и второй из них забывают чаще всего:

1. **Напишите функцию** в `_toolset.py` и добавьте её в набор инструментов.
   Её docstring — это промпт; скажите, *когда за неё браться*, а не что она
   делает.
2. **Объявите её** в кортеже `tools=` в `__init__.py`. Инструмент, о котором
   реестр не знает, нельзя согласовать, нельзя переименовать для отдельного
   агента, и в Конструкторе он не появляется — он просто выполняется.
3. **Проверьте тест на расхождения.** `tests/test_capability_registry.py`
   собирает каждую зарегистрированную возможность и сравнивает объявленный
   список с инструментами, которые модель действительно получает. Именно он
   ловит пропущенный шаг 2 и сообщает, когда вышестоящий пакет переименовывает
   один из инструментов, которые мы реэкспортируем: три инструмента возможности
   `skills` приходят из `pydantic-ai-skills`, так что их имена — чужое дело.

!!! tip "Инструмент с побочными эффектами рядом с инструментами только для чтения — это сигнал"

    `side_effecting` задаётся для возможности целиком, поэтому теперь
    возможность — это два решения под одним именем. Лучше заведите вторую
    возможность; `approval` для отдельного инструмента в спецификации позволяет
    *автору агента* быть строже значения по умолчанию и не заменяет
    объявления того, как обстоят дела.

## Добавление инструмента, который здесь никому не нужно писать { #adding-a-tool-nobody-here-has-to-write }

Если инструмент — это вызов стороннего API, который уже публикует MCP-сервер,
подумайте, место ли ему в коде вообще. Возможность подходит для того, что
платформа обязана гарантировать; для остального подходит сервер, который
поддерживает поставщик. См. [MCP](../mcp.md) и
[Добавление сервера в каталог MCP](add-mcp-server.md).

# Вызовите агента из своего приложения { #call-an-agent-from-your-own-application }

Вызывайте опубликованного агента так же, как это делают консоль, Slack и любой
другой способ доступа: один аутентифицированный `POST`, который проходит через
тот же механизм выполнения, ту же проверку бюджета и то же согласование. Эта
страница проходит [HTTP API](../api.md) с небольшим агентом и вставляет
настоящие, сокращённые ответы. Это процедура, которую нужно выполнить, с одним
записанным запуском для сверки.

## Что понадобится { #what-you-need }

- [Работающий экземпляр](../install.md) с профилем модели и учётная запись
  участника, под которой можно войти.
- Опубликованный агент, ни одна возможность которого не требует учётной записи,
  которой у вас нет: в записанном ниже запуске у агента нет возможностей вообще,
  поэтому здесь ничего не зависит от песочницы, коллекции или подключения MCP.

## Создайте агента { #build-the-agent }

Создайте агента в **Агенты → Новый агент** (Agents → New agent), выберите свой
профиль модели, оставьте вкладку **Инструменты** (Toolbox) пустой, задайте
небольшой бюджет и лимит шагов и напишите короткие инструкции:

```text
You are a small support assistant reachable over the HTTP API.
Answer briefly, in two or three sentences.
If asked something you cannot know, say so plainly rather than guessing.
```

**Опубликовать** (Publish) — и скопируйте его id из URL или из `GET /agents`.

## Пройдите аутентификацию и запустите его { #authenticate-and-run-it }

Войдите, чтобы получить токен доступа, затем вызовите эндпоинт запуска с ним
и заголовком организации:

```bash
TOKEN=$(curl -s -X POST "$BASE/api/v1/auth/login" \
  -d "username=$EMAIL&password=$PASSWORD" | jq -r .access_token)

curl -s -X POST "$BASE/api/v1/agents/$AGENT_ID/run" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID" \
  -H "Content-Type: application/json" \
  -d '{"prompt": "In one sentence, what is a model profile?"}'
```

```python
import httpx

login = httpx.post(f"{BASE}/api/v1/auth/login",
                    data={"username": EMAIL, "password": PASSWORD})
token = login.json()["access_token"]

resp = httpx.post(
    f"{BASE}/api/v1/agents/{AGENT_ID}/run",
    headers={"Authorization": f"Bearer {token}", "X-Organization-Id": ORG_ID},
    json={"prompt": "In one sentence, what is a model profile?"},
)
resp.raise_for_status()
print(resp.json()["output"])
```

`X-Organization-Id` определяет, в какой организации выполняется вызов, — см.
[заголовок организации](../api.md#the-organization-header). Заголовок `X-API-Key`
работает так же для сервиса, за которым не стоит человек; в двух вызовах выше
используется JWT участника.

## Получайте ответ потоком { #stream-it-instead }

`ws://…/api/v1/ws/agent` — тот же аутентифицированный сокет, который использует
собственный чат консоли, только токен передаётся в подпротоколе
(`access_token.<JWT>` и `chat`), а не в заголовке, потому что браузерный
`WebSocket` не может его задать. Кадр несёт `message`, `agent_id`
и необязательный `conversation_id`; сокет отвечает событиями `text_delta`, пока
модель пишет, `tool_call` и `tool_result` на каждый шаг, `tool_approval_required`,
если какой-то вызов встаёт на согласование, и `complete` с расходом запуска
в конце. См. [потоковую передачу](../api.md#streaming).

## Обрабатывайте ошибки, бюджеты и лимиты частоты { #handle-errors-budgets-and-rate-limits }

Каждый отказ возвращается в одном и том же конверте: `error.code`,
`error.message` и `error.details`:

```json
{"error": {"code": "VALIDATION_ERROR", "message": "prompt: Field required",
  "details": {"fields": [{"field": "prompt", "message": "Field required"}]}}}
```

Запуск, который этот эндпоинт принимает, всё равно проходит через управление:
[бюджет](../governance.md#budgets) проверяется до запроса к модели, и запуск
завершается ошибкой, а не перерасходом, а инструмент, требующий согласования,
[встаёт на согласование](../governance.md#approvals) точно так же, как в чате, —
вызывающая сторона API не может пропустить ни то, ни другое. Сам маршрут несёт не
разрешение, а лимит частоты, привязанный к вызывающему: по умолчанию 30 запусков в
минуту (`RATE_LIMIT_RUN_PER_MINUTE`); отказ — это сообщение с предложением
подождать, а не очередь.

## Проверьте результат { #check-the-result }

| Проверка | Образец |
| --- | --- |
| Обычный запуск | `status: "completed"`, строка `output`, `cost_usd` и счётчики токенов |
| Без заголовка `Authorization` | `401`, `www-authenticate: Bearer` |
| Неверный `X-Organization-Id` | `404`, `NOT_FOUND`, та же форма, что у несуществующего агента |
| Неизвестный `agent_id` | `404` с `agent_id` в `details` |
| В теле нет `prompt` | `422` (`VALIDATION_ERROR`), `details.fields` называет поле |
| Две организации, один вызывающий | Запуск видит только ту организацию, которая названа в заголовке этого вызова |

!!! example "Записано на v0.0.504, 25 сентября 2026"

    Модель: Claude Sonnet 4.6 через OpenRouter, агент `uc-api-demo`. `POST /run`
    с настоящим промптом ответил `{"status": "completed", "cost_usd": "0.000582", "output": "A model profile is a structured description of an AI model's key characteristics, capabilities, limitations, and intended use cases."}`.

    Если опустить `X-Organization-Id`, вызов здесь **не** отклонялся: он
    откатывался к личной организации вошедшего участника и выполнялся там, а не
    отвечал «нет организации, в которой действовать». Выдуманный идентификатор
    организации возвращал `404` с `"Organization not found or access denied"`.
    Без `Authorization` приходил `401` с `www-authenticate: Bearer`. Пустое тело
    возвращало `422` с `details.fields: [{"field": "prompt", "message": "Field required"}]`
    — в точности как в конверте выше.

## Когда что-то идёт не так { #when-it-goes-wrong }

- **`404` на id агента, который, как вы знаете, существует.** Сначала проверьте
  заголовок организации: чтение из другой организации отвечает `404` —
  намеренно так же, как для несуществующего агента.
- **`429` посреди проверки интеграции.** Лимит частоты маршрута запуска
  считается на вызывающего, а не на агента; отступите, а не повторяйте сразу.
- **Запуск отвечает, но так и не доходит до включённого вами инструмента.**
  Загляните в «Активность»: возможно, там ждёт согласования остановленный вызов —
  путь через HTTP встаёт на него точно так же, как чат, и `POST /run` сам себя не
  продолжает.
- **Стоимость, которую вы видите, не совпадает с панелью вашего провайдера.**
  `cost_is_partial` в ответе говорит, является ли число нижней границей,
  а не итоговой величиной; `true` здесь означает, что часть запуска не удалось
  оценить.

## Зафиксируйте проверку { #record-the-trial }

Сохраните запрос и ответ для каждой проверки, версию агента и профиль модели.
Какие возможности может держать агент, работающий между серверами, нужен ли ему
собственный API-ключ вместо общего и какой бюджет его ограничивает, по-прежнему
решает человек: эндпоинт эти решения исполняет, а не принимает.

## Что дальше { #next-steps }

Если обновлять токен не должен никто, используйте API-ключ вместо входа за JWT:
[аутентификация](../api.md#authenticating) описывает оба способа. О том, как
вызовы инструментов и стоимость запуска выглядят, когда попадают в продукт, см.
[управление](../governance.md#budgets).

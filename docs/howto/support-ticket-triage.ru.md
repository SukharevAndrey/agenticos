# Разбирайте входящие обращения в поддержку из своего приложения { #triage-incoming-support-requests-from-your-own-app }

Подключите свою форму поддержки или систему заявок к агенту через
[триггер по событию](../triggers.md) на источнике **API** — универсальном
источнике `webhook`, который срабатывает на любую подписанную доставку JSON. Три
синтетические заявки, одна из них — сообщение об уязвимости, проверяют, что
классификация, подготовка черновика и метка безопасности работают, прежде чем вы
направите на это настоящую систему. Это процедура, которую нужно выполнить; один
записанный запуск приведён как образец.

## Что понадобится { #what-you-need }

[Работающий экземпляр](../install.md) с профилем модели. Ни песочница, ни модель
эмбеддингов, ни внешняя учётная запись не нужны: источник API сам подписывает свои
доставки, так что настраивать консоль провайдера не нужно.

## Подготовьте входные данные { #prepare-the-input }

Три заявки в том виде, в каком их отправил бы ваш бэкенд: всё тело JSON попадает
в промпт агента, поэтому подойдёт любая форма, если написать инструкции под неё:

```json
{"ticket_id":"T-1001","from":"lena@acme-example.com","subject":"Charged twice this month","body":"I was billed 49 USD twice on the 3rd for the same Pro plan invoice. Can you refund the duplicate?"}
{"ticket_id":"T-1002","from":"marek@example.org","subject":"Export button does nothing","body":"Clicking Export CSV on the reports page just spins forever and nothing downloads. Chrome, latest version."}
{"ticket_id":"T-1003","from":"researcher@example.net","subject":"Found an issue with account access","body":"By changing the id in the /api/v1/invoices/{id} URL I was able to view another customer's invoice PDF without being logged in as them. Tested with three different ids, all worked."}
```

Образец: T-1001 — категория billing, приоритет medium. T-1002 — категория
technical, приоритет medium. T-1003 описывает IDOR — в ответе должны быть
категория security, приоритет urgent и явная метка.

## Создайте агента { #build-the-agent }

1. Создайте агента в **Агенты → Новый агент** (Agents → New agent) и выберите
   профиль модели. Для этой проверки возможности не нужны.
2. Задайте инструкции ниже, затем нажмите **Опубликовать** (Publish).

```text
You triage inbound support tickets for a small SaaS product.
Be concise and factual. Never invent facts not in the ticket.
```

3. Откройте **Автоматизации → Новый триггер по событию** (Routines → New event
   trigger), выберите агента и источник **API**. Задайте собственный промпт
   триггера — именно он отправляется перед доставкой при каждом срабатывании:

```text
A support ticket just arrived as JSON below. Classify it by category (billing,
technical, account, security, other) and priority (low, medium, high, urgent).
Draft a reply the support team can send. If the ticket describes a possible
security vulnerability or exposure of somebody else's data, say so explicitly in
a line starting with 'SECURITY:' and set priority to urgent.
```

4. Сохраните. Скопируйте **URL вебхука** (Webhook URL) и **Секрет подписи**
   (Signing secret), которые он покажет один раз: у источника API доставка
   `manual`, поэтому ничто не регистрируется само, и секрет вы выбираете сами.
   [Триггеры](../triggers.md#the-mechanism-once) объясняют, что означают оба.

## Запустите его { #run-it }

Подпишите точные байты каждой заявки секретом триггера и отправьте их методом
POST. О двух подводных камнях — в разделе
[подпишите доставку сами](../triggers.md#signing-a-delivery-yourself): не
сериализуйте тело заново и подписывайте только те байты, которые отправляете:

```bash
SECRET='your-signing-secret'
URL='http://localhost:8110/api/v1/webhooks/triggers/webhook/<trigger_id>'
BODY='{"ticket_id":"T-1001","from":"lena@acme-example.com","subject":"Charged twice this month","body":"I was billed 49 USD twice on the 3rd for the same Pro plan invoice. Can you refund the duplicate?"}'

SIG="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | sed 's/^.* //')"

curl -sS -X POST "$URL" \
  -H 'Content-Type: application/json' \
  -H "X-Signature-256: $SIG" \
  --data-raw "$BODY"
```

Повторите для T-1002 и T-1003. Каждая принятая доставка отвечает `202` — принято,
но не завершено. Смотрите сработавшие запуски в разделе **Активность** (Activity)
или в собственном диалоге триггера в разделе **Автоматизации** (Routines).

## Проверьте результат { #check-the-result }

| Проверка | Образец |
| --- | --- |
| T-1001 | Категория billing, приоритет medium, ответ признаёт двойное списание |
| T-1002 | Категория technical, приоритет medium, ответ просит детали воспроизведения |
| T-1003 | Категория security, приоритет urgent, строка, начинающаяся с `SECURITY:`, называет утечку |
| Ответ `202` | Приходит сразу; сам запуск завершается через несколько секунд, асинхронно |
| Неподписанная доставка того же тела | `403`, отклоняется ещё до запуска агента |
| Доставка, в которой тело пересобрано HTTP-клиентом, а не отправлено сырым | `403`: подпись больше не совпадает с фактически отправленными байтами |

!!! example "Записано на v0.0.504, 25 сентября 2026"

    Модель: Claude Sonnet 4.6 через OpenRouter. Все три доставки ответили `202` и
    завершились примерно за 6 секунд каждая и записаны со способом запуска
    `schedule` — срабатывания триггера по событию делят этот способ запуска с
    расписаниями.

    T-1001: *«Категория: billing, приоритет: medium»*, ответ просит
    идентификатор счёта, чтобы обработать возврат. T-1002: *«Категория:
    technical, приоритет: medium»*, ответ просит вывод консоли браузера. T-1003:
    *«Категория: security, приоритет: urgent»*, затем `SECURITY: Reporter claims
    unauthenticated/unauthorized access to other customers' invoice PDFs via
    IDOR (Insecure Direct Object Reference) on /api/v1/invoices/{id}. Multiple
    accounts confirmed affected."` — и черновик ответа с просьбой к автору
    сообщения не проверять дальше, пока идёт разбирательство. Суммарная
    стоимость трёх запусков: 0,013 USD.

    Оба пути отказа тоже проверены: то же тело, отправленное без заголовка
    `X-Signature-256`, получило `403`; а тело, подписанное как строка, но затем
    отправленное через собственную перекодировку клиента `json=` — то же
    содержимое, другие байты, — тоже получило
    `403 AUTHORIZATION_ERROR: Webhook signature
    did not verify`, что
    подтверждает: подпись покрывает точные байты, ушедшие по сети, а не
    логическое содержимое JSON.

## Когда что-то идёт не так { #when-it-goes-wrong }

- **Каждая доставка возвращает `403`.** Подпись покрывает *точные* отправленные
  байты. `echo` добавляет завершающий перевод строки, который может совпадать или
  не совпадать с подписанным; используйте `printf '%s'` и `curl --data-raw` и
  никогда не позволяйте клиенту перекодировать словарь после того, как вы
  подписали строку.
- **`202`, но запуск не появляется.** Это значит «принято, но не завершено» —
  задача выполняет его в воркере. Подождите несколько секунд и проверьте раздел
  «Активность» с фильтром по агенту; если ничего так и не появилось, поищите
  задачу `fire-trigger` на странице **Фоновые задачи** (Background jobs).
- **Метка безопасности не сработала.** Метка — это инструкции, а не встроенный
  классификатор: перечитайте промпт триггера и уточните, что считать сообщением
  об уязвимости, если синтетический пример вроде T-1003 пропущен.
- **Нужно проверить только промпт, а не путь доставки.** Сначала нажмите
  **Запустить сейчас** (Run now) у триггера: он запускает базовый промпт агента
  без контекста доставки, подписи и вебхука. Классификацию это не проверит,
  потому что классифицировать JSON заявки нечего, но подтвердит, что агент, его
  бюджет и состояние публикации работают.
- **Zapier или Make вместо скрипта.** Ни у одного нет встроенного действия HMAC;
  закладывайте час на шаг с кодом, который подписывает тело, а не пять минут
  кликов. См.
  [триггеры](../triggers.md#zapier-and-make-cannot-do-this-without-a-code-step).

## Зафиксируйте проверку { #record-the-trial }

Сохраните три тела заявок, промпт триггера, происхождение секрета подписи (а не
его значение), HTTP-статус каждой доставки и запуск, который каждая из них
создала в разделе «Активность». Человек по-прежнему читает каждый черновик,
прежде чем он уйдёт, и решает, достаточно ли строг порог метки безопасности для
настоящего почтового ящика, прежде чем направить на этот вебхук действующую
систему заявок.

## Что дальше { #next-steps }

Тот же источник API подходит для всего, что умеет подписывать JSON и отправлять
его методом POST: отправка формы, изменение объявления на маркетплейсе,
оповещение мониторинга. Вместо заявок из своего приложения для почтового ящика
см. [разберите почту и подготовьте черновики ответов](email-triage.md) — там
используется источник Gmail, а не подписанная доставка.

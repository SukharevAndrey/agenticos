# Виртуальные таблицы { #virtual-tables }

Выберите значок таблицы рядом с её названием в подробном виде. Карточка в каталоге и
строка на Обзоре используют тот же значок. **Использовать значок по умолчанию** (Use
default icon) возвращает исходный; выбор не меняет столбцы, записи и версии схемы.
Этот элемент управления подчиняется правилам доступа к управлению таблицей, включая
ограничения доски задач.

**Виртуальная таблица** — это типизированная таблица записей, которую организация
ведёт для своих агентов, [сценариев](workflows.md) и интеграций: заказы к сверке,
файлы к обработке, лиды к проработке.

Таблицы — это метаданные плюс JSONB. Физическая таблица SQL не создаётся, поэтому
создание таблицы обходится в одну строку, переименование столбца не меняет ни одной
записи, а ни одна организация не может раздуть каталог базы данных. Каждое чтение и
запись идут через один сервис, `VirtualTableService`, поэтому консоль, инструменты
агента, узлы сценария и публичный API подчиняются одним и тем же правилам. Эта
страница описывает сервис и его HTTP-маршруты под `/api/v1/tables`; контракт для них —
документ OpenAPI.


Рабочее пространство таблицы по умолчанию занимает доступную область, без кнопки
разворота. У панели записи есть собственная кнопка **Во весь экран** (Full screen),
разворачивающая все поля с сохранением правок; **Выйти из полноэкранного режима**
(Exit full screen) возвращает её вбок. Строки таблицы лежат прямо под панелью
инструментов, без второй рамки и пустой панели с отступами. Каталог занимает доступную
площадь страницы, имеет собственный элемент «Во весь экран» и показывает постраничную
навигацию, только когда страниц больше одной.

Каждая таблица показывает заблокированные поля записи `created_at`, `updated_at`,
`created_by` и `updated_by`. Это те же свойства, что показаны над Markdown, а не
редактируемые копии в значениях ячеек. До первого изменения `updated_at` показывает
время создания. Эти поля остаются видимыми, когда пользовательские столбцы скрыты. Их
имена зарезервированы для новых и переименовываемых столбцов; существующие
унаследованные имена остаются читаемыми.

Задайте типизированное **Значение по умолчанию** (Default value) в настройках столбца
или при его добавлении. Новые записи используют его, только когда поле опущено; явное
значение или null важнее. Значения по умолчанию столбцов-списков могут называть ID или
названия вариантов при отправке схемы; сервер хранит ID. Цвет каждого варианта
выбирается в его списке; **Автоматически** (Automatic) сохраняет исходную палитру.
Смена цвета сохраняет ID вариантов и ревизию смысла столбца.

Быстрое добавление располагается сразу после загруженных строк в области прокрутки. Экспорт
CSV из консоли включает четыре свойства записи. Экспорт через API сохраняет прежнюю
форму, если не запрошен `include_metadata: true`. Системные свойства пропускаются при
создании таблицы из экспортированного CSV; импортированные записи получают новые
системные метаданные.

В документе Markdown наберите `/` в начале строки, чтобы найти блок: список задач,
заголовок, список, цитата, блок кода, разделитель, таблица, изображение, видео или
ссылка. Стрелки и Enter выбирают блок; Escape закрывает меню. Вставляйте скопированные
изображения прямо в редактор. Изображения PNG, JPEG, GIF и WebP размером до 5 МиБ
хранятся вместе с таблицей, учитываются в её квоте хранения и подчиняются её текущим
выданным доступам. Изображения остаются доступными, когда таблица в архиве, включая
ссылки, сохранённые в истории записей.

Типы столбцов `user` и `agent` ссылаются на одного участника организации или
доступного ИИ-агента; `multi_user` и `multi_agent` — до 100 разных идентичностей.
Выбор идёт по имени из подсказок с аватарами. Хранимые значения — стабильные UUID, а
членство и видимость агента проверяются при записи и при значениях по умолчанию.
Одиночные ссылки поддерживают `eq`, `ne`, `in` и `is_null`; множественные —
`contains` и `is_null`. Столбцы идентичностей не сортируются.

**Шаблоны документов** (Document templates) в поле Markdown открывают многоразовую
библиотеку этого столбца. Сохраните текущий документ, настройте заготовку,
отредактируйте или удалите именованные шаблоны и выберите шаблон по умолчанию.
Выбранный шаблон по умолчанию автоматически подставляет содержимое новым записям; его
правка никогда не переписывает существующие документы. Каждый столбец хранит до 10
шаблонов общим объёмом не более 100 000 символов. Обычные свойства записи остаются над
телами документов на панели записи.

Выбор записей показывает плавающую панель действий, не сдвигая сетку. Кнопка открытия
записи остаётся прикреплённой рядом с флажком выбора даже в таблице с горизонтальной
прокруткой. Каждая панель записи показывает время и авторов создания и изменения, с
аватарами. Боковые панели открываются в режиме **Предпросмотр** (Preview); документы
на всю страницу — в режиме **Редактировать** (Write).

## Внешние клиенты { #external-clients }

Происхождение записи фиксируется отдельно от участника, который её авторизовал. Новые
записи хранят `created_source` и `updated_source` с видом источника, его ID и
отображаемым именем: человек, агент, API-ключ, сценарий или система. Консоль
показывает аватар человека, портрет агента или значок API/сценария рядом с именем в
системных столбцах и свойствах документа. Создание задаёт оба источника; последующие
записи сохраняют создателя. Существующие записи сохраняют записанного участника, не
выдумывая историческое происхождение. Эти поля нельзя передать через входные данные
записи или Markdown.

API-ключи организации принимаются на `/api/v1/tables`. Отправляйте
`Authorization: Bearer aos_…`; организация берётся из ключа. Чтение требует `tables:view`,
изменение записей и схемы — `tables:edit`, а создание таблицы — `tables:create`.
Действуют и текущий доступ того, кто выдал ключ, и области действия самого ключа.
Квитанции и история называют выдавшего; ключ не может расширить их доступ. Недоступная
таблица отвечает `404`, отсутствующее разрешение на коллекцию — `403`, устаревшая
ревизия — `409`, неверный запрос или запись — `422`. Повтор записи с теми же
`Idempotency-Key` и телом возвращает исходный результат без нового события создания.

`POST /api/v1/tables/{id}/records/query` принимает `columns` (до 100 ID живых
столбцов) вместе с фильтрами, сортировкой, skip и limit. В ответ попадают только эти
ячейки и названия связанных записей. `null` сохраняет полную запись; `[]` возвращает
только метаданные. Вычисляемые столбцы считаются до проекции, поэтому их зависимости
не обязательно выбирать. Те же записи сразу появляются в консоли; триггеры таблицы
срабатывают асинхронно и никогда не задерживают ответ CRUD.

## Как устроена таблица { #how-a-table-is-built }

| Часть | Что это | Идентичность |
|---|---|---|
| **Таблица** | Имя, владелец, видимость и выданные доступы, как у [файла контекста](context.md) | `id`, стабильный |
| **Версия схемы** | Неизменяемый снимок столбцов. Изменение добавляет версию N+1 | `version` |
| **Столбец** | Метка, тип, может ли быть пустым, необязательное значение по умолчанию | `id`, стабильный |
| **Вариант** | Один выбор столбца-списка | `id`, стабильный |
| **Запись** | Значения ячеек по ID столбцов, ревизия и необязательный `external_id` | `id`, стабильный |

Значения привязаны к **id** столбца и никогда — к его названию. Поэтому переименование
переписывает одну версию схемы и ни одной записи. Запись помнит версию схемы, под
которой её писали в последний раз.

Запись хранит только ячейки со значением. Ячейка, переданная как `null`, очищается, и
чтение ничего для неё не показывает. При создании значение по умолчанию столбца
заполняет только опущенные ячейки; ячейка, переданная как `null`, остаётся пустой.

## Типы столбцов { #column-types }

| Тип | Хранится как | Фильтры |
|---|---|---|
| `text` | Текст до 1 000 символов | `eq` `ne` `contains` `starts_with` `in` `is_null` |
| `long_text` | Текст до 100 000 символов | те же, что у `text` |
| `rich_text` | Исходный текст Markdown до 100 000 символов | те же, что у `text` |
| `email` | Адрес с одним `@` и точкой в домене, до 254 символов | те же, что у `text` |
| `url` | Адрес `http` или `https` с хостом, до 2 048 символов | те же, что у `text` |
| `phone` | Цифры, пробелы и `+ ( ) - . /`, не менее пяти цифр | те же, что у `text` |
| `number` | Конечное число | `eq` `ne` `lt` `lte` `gt` `gte` `in` `is_null` |
| `integer` | Целое число, не больше 2^53 - 1 | те же, что у `number` |
| `rating` | Целое число от 1 до 5 | те же, что у `number` |
| `boolean` | `true` или `false` | `eq` `ne` `is_null` |
| `date` | `YYYY-MM-DD` | те же, что у `number` |
| `datetime` | ISO 8601 с часовым поясом, хранится как UTC | те же, что у `number` |
| `single_select` | ID варианта | `eq` `ne` `in` `is_null` |
| `multi_select` | Список ID вариантов | `contains` `is_null` |
| `link` | Список до 100 ID записей таблицы, на которую ссылается | `contains` (ID записи) `is_null` |
| `lookup`, `rollup` | Ничего: вычисляется при чтении записи | нет |
| `formula` | Ничего: вычисляется из других столбцов записи при чтении | нет |

Текст хранится ровно как отправлен. Пробелы в начале и в конце, переводы строк и
значения из одних пробелов — данные пользователя, поэтому они не обрезаются.
Действует только ограничение длины, а символ NUL отклоняется — и в ячейках, и
одинаково в именах, названиях, описаниях и внешних id, потому что PostgreSQL не может его
хранить.

Сравнения совпадают только с ячейками, в которых есть значение. Пустые ищите через
`is_null`. `contains` и `starts_with` принимают часть значения, поэтому
`@example.com` находит адреса на домене в столбце `email`.

Инструменты таблиц у агента и шаги таблицы в сценарии называют выбор названием
варианта, без учёта регистра: они пишут и фильтруют по названию, а выбор записи
читают обратно как названия — в том числе архивного варианта. Значение, не называющее
ни одного живого варианта, отклоняется вместе со списком вариантов столбца.

### Форматированный текст и Markdown { #rich-text }

Выберите **Форматированный текст (Markdown)** (Rich text (Markdown)) для заметок с
заголовками, списками, задачами, таблицами, ссылками и кодом. Щелчок по ячейке
открывает запись. **Редактировать** (Write) даёт текстовую область документа и панель
инструментов для полужирного, курсива, ссылок, изображений и видео; **Предпросмотр**
(Preview) использует рендерер чата для ссылок и изображений, а прямые ссылки
HTTP(S) на MP4, WebM или Ogg становятся видео с элементами управления и без
автовоспроизведения. Необработанный HTML не выполняется. **Развернуть редактор**
(Expand editor) открывает более широкое рабочее пространство. Сохранённые документы
открываются в предпросмотре; **Редактировать** переключает на редактирование.

Карточки канбана перемещаются с предпросмотром под указателем и подсветкой
назначения, анимируются между дорожками и появляются в целевой дорожке во время
сохранения. Отклонённая запись возвращает прежнюю дорожку и сохраняет действия для
конфликта. Меню «Переместить в» остаётся доступным для тех, кто работает с клавиатуры.

Свойства документа лежат над редактором Markdown. **Создано** (Created), **Последнее
изменение** (Last updated) и **Создал** (Created by) берутся из записи и не меняются
через Markdown. Дата последнего изменения обновляется при каждом изменении записи,
включая изменения других ячеек; до первого изменения она равна дате создания.

Храните свойства документа в типизированных столбцах таблицы; редактор Markdown
больше не добавляет и не редактирует свойства YAML. Новые шаблоны блокнота содержат
только Markdown. Существующие импортированные заголовки сохраняются байт в байт при
правке тела, поэтому удаление редактора свойств не теряет исторические данные.
Автоматические даты и идентичности источников по-прежнему берутся из записи.

Выберите шаблон документа по умолчанию при создании столбца форматированного текста
или в разделе **Столбцы** (Columns). Начните с пустого документа, заметки, заметок о
встрече или краткого описания проекта и настройте текст. Для этого используется
существующее поле `default` столбца: консоль, API и создание сценария применяют его,
когда ячейка опущена. Явно переданное значение, в том числе пустая строка, важнее.
Смена шаблона влияет только на новые записи. **Использовать шаблон столбца** (Use
column template) заменяет тело существующего документа после подтверждения и
сохраняет его свойства. Текстовые запросы и преобразования сохраняют прежние
контракты.

## Ссылки, подстановки и сводные значения { #links-lookups-and-rollups }

Столбец `link` хранит записи другой таблицы или той же самой, заданной через
`link_table_id`. Запись в него проверяет, что каждая запись существует в той таблице и
что пишущий её видит, поэтому ссылку нельзя использовать, чтобы узнать, какие id
хранит приватная таблица. Запись читает свои ссылки обратно именованными, в `links`,
по первому текстовому значению каждой связанной записи, затем по её внешнему id.
Связанная запись, удалённая с тех пор, просто выпадает.

`lookup` читает один столбец связанных записей через столбец-ссылку той же таблицы
(`link_column_id`, `target_column_id`): значения, а выбор — по его названию. `rollup`
вычисляет одно значение: `count` по ссылкам или `sum`, `avg`, `min`, `max` по столбцу
чисел — `min` и `max` также по датам. Оба вычисляются при чтении записи и никогда не
хранятся, не записываются, не фильтруются и не сортируются по ним.

Подстановка показывает не больше, чем позволено её читателю: связанная таблица,
которую читатель не видит, оставляет ссылки безымянными, а все подстановки и сводные
значения через них — пустыми. Ссылка сохраняет свою таблицу навсегда. Подстановка
читает столбец со значениями, а не другую ссылку или подстановку, и архивация
столбца-ссылки отклоняется, пока через него ещё читает подстановка или сводное
значение. Экспорт записывает ссылку по именам её записей, а подстановку — по тому, что
она прочитала.

## Формулы { #formulas }

Столбец `formula` вычисляет значение из других столбцов записи: `{Price} * {Quantity}`,
`IF({Total} > 100, "large", "small")`, `ROUND({Total} / {Count}, 2)`,
`DAYS({Due}, TODAY())`. Столбец называется своим названием в фигурных скобках, и его
переименование переписывает каждую формулу, которая его называет. Формула считает с
`+ - * / %`, сравнивает с `= <> < <= > >=`, соединяет условия через `and`, `or` и
`not` и вызывает `IF`, `ROUND`, `ABS`, `MIN`, `MAX`, `CONCAT`, `LEN`, `UPPER`,
`LOWER`, `DAYS` и `TODAY`. Выбор читается как его название.

Она может читать любой живой столбец со значениями, включая результат подстановки или
сводного значения, но не ссылку и не другую формулу, а столбец, который читает
формула, нельзя архивировать. Сохранение схемы проверяет формулу и говорит, что с ней
не так. Значение, которое она не может вычислить, — деление на ноль, текст в сумме,
пустая ячейка, — оставляет ячейку этой записи пустой. Формула вычисляется при чтении
записи, как подстановка, и никогда не хранится, не записывается, не фильтруется и не
сортируется по ней.

Десятичные дроби пишутся с точкой, `{Price} * 1.23`, на любом языке: запятая разделяет
аргументы функции, поэтому `{Price} * 1,23` отклоняется с этой подсказкой, а не
читается как число; так же отклоняется вызов, которому дали лишнее значение, например
`IF({Price} > 0,5, "yes", "no")`.

Число значений вызова проверяется при сохранении его формулы: формула, сохранённая до
этой проверки, продолжает работать, и остальные столбцы таблицы всё ещё можно менять,
пока кто-нибудь не отредактирует эту формулу. Отказ называет стабильную причину
`details.formula.reason`, например `decimal_comma` или `not_a_column`; по ней консоль
говорит об отказе на языке читателя. Консоль показывает числа, включая результат
формулы, с десятичным разделителем читателя — `12,177` по-польски — и оставляет
четырёхзначное число без разделения разрядов.

## Изменение схемы { #changing-a-schema }

`PUT /tables/{id}/schema` принимает полный список столбцов, которые должны быть у
таблицы, и `expected_version`, который вызывающий прочитал последним. Сервис
согласует его с текущими столбцами:

- Столбец с `id` — это тот самый столбец. Столбец без него — новый.
- **Тип столбца меняется только на такой, каким читаются его значения**, и смена
  переписывает значение каждой записи. Любое значение становится текстом; текст
  становится числом, значением да/нет, датой или столбцом с одиночным выбором, если
  читается как одно из них, — столбец с выбором получает вариант на каждое отдельное
  значение; столбец целых чисел становится числовым, и обратно — когда все числа
  целые; дата становится датой и временем; одиночный выбор становится множественным
  и обратно — когда выбор один. Любая другая смена отклоняется, как и та, которую не
  переживёт какое-то значение: в отказе названо, сколько их и один пример, — и
  ничего не записывается. Всё, что использует столбец, отклоняет такую смену так же,
  как архивацию. Запись, значение которой в новом типе читается иначе, переходит на
  новую ревизию, поэтому правка против её старого значения — конфликт, а в её
  истории изменение числится за тем, кто его сделал; значение, которое смена
  оставила как было, сохраняет ревизию своей записи. Смена типа не запускает
  [триггер](#triggers): одна правка схемы не запускает сценарий на каждую запись.
- Текст становится столбцом `email`, `url`, `phone` или `rating`, когда каждое
  значение читается как таковое, а число становится оценкой, когда это целое
  число от 1 до 5. Каждый из них снова становится текстом, а оценка — числом.
- Ничего не удаляется. Столбец или вариант, которого нет в присланном списке,
  **архивируется**: его значения остаются доступными для чтения и фильтрации, а
  запись в него отклоняется с `ARCHIVED_COLUMN`.
- Архивные тоже считаются в лимитах. В таблице не больше 100 столбцов, а в столбце с
  выбором — не больше 100 вариантов, включая архивные. Смена, которая превысила бы
  любой из них, отклоняется с `INVALID_SCHEMA` и не добавляет версию, поэтому
  переписать полный список вариантов не получится; добавьте вместо этого новый
  столбец.
- Новому обязательному столбцу нужно значение по умолчанию, потому что у
  существующих записей для него ничего нет. Существующий столбец не может стать
  обязательным, пока хоть у одной записи нет для него значения, а обязательный
  столбец не может вернуться из архива без значения по умолчанию: записи,
  написанные, пока он был в архиве, не могли его содержать.
- Устаревший `expected_version` — это `SCHEMA_VERSION_CONFLICT`.
- Присланный набор, совпадающий с текущими столбцами, — те же `id`, порядок,
  названия и варианты, — ничего не меняет: версия не добавляется, и возвращается
  текущая таблица. Перестановка или изменённое название — это изменение.

Кроме смены типа, записи не переписываются. Запись, написанная под версией 1,
остаётся читаемой и редактируемой под версией 4; обязательный столбец, которого в
ней никогда не было, получает значение по умолчанию при следующей правке записи.

У каждого столбца есть доступная только для чтения **`revision`**, равная `0` для
нового столбца и для каждого столбца, который существовал до появления этого поля.
Она отслеживает изменения того, что значения столбца *значат*, поэтому опубликованная
[страница](artifacts.md#live-data) может понять, что столбец, против которого её
опубликовали, — уже не тот. Она растёт на единицу при:

- смене типа;
- изменении формулы — сравнение идёт после того, как через неё записали
  переименование, поэтому переименование столбца, который читает формула, не
  считается, а столбец, забравший название себе, — считается;
- другой цели связи, подстановки или сводного значения либо другом агрегате;
- архивации или восстановлении столбца либо архивации или восстановлении одного из
  его вариантов выбора.

Новое название, значение по умолчанию или обязательность, переименованный вариант
выбора и новый вариант оставляют её прежней. Фильтр хранит `id` вариантов,
поэтому ни одно из этих изменений не меняет совпадений фильтра. Столбец
`TableRead` можно прислать в изменении схемы как есть: поле принимается и
игнорируется, а задаёт его только само изменение.

Запись в таблицу и изменение схемы или архивация той же таблицы выполняются по
очереди: запись ждёт идущую операцию и затем проверяется по тому, что она
зафиксировала, поэтому запись никогда не окажется в таблице, архивированной
мгновением раньше.

Архивация столбца или всей таблицы сначала спрашивает каждую зарегистрированную
проверку зависимостей, не использует ли его ещё что-то, что вызывающий может и
видеть, и изменять. Сохранённые представления (см. [сохранённые
представления](#saved-views)) и сценарии, которые читают или пишут таблицу,
регистрируют свои в `app/services/virtual_tables/dependencies.py`, и триггеры
таблицы тоже: они блокируют того, кто архивирует, — триггер, фильтрующий по
исчезнувшему столбцу, вернулся бы сломанным.

Отказ перечисляет каждого зависимого в `SCHEMA_DEPENDENCY` с его `kind`, `id` и
`name`, а `name` равен null для триггера в сценарии, который вызывающий не может
открыть. Консоль перечисляет их в диалоге, из которого пришёл запрос, а сценарий —
ссылкой на него. Любой другой зависимый никогда не называется и никогда не блокирует
вызывающего: соответствующая функция сама справляется с изменением.

## Архивация и восстановление таблицы { #archiving-a-table }

Таблица никогда не удаляется — она архивируется. Архивированная таблица сохраняет
записи, столбцы, представления и историю, и каждое чтение по-прежнему отвечает.
Любая операция записи в неё отклоняется с `TABLE_ARCHIVED`, кто бы ни просил: ни
одна запись не создаётся, не меняется и не удаляется, и не меняются ни её название,
ни её столбцы. Её название свободно для новой таблицы, и она по-прежнему считается
в [лимите таблиц](#limits-and-retention) организации.

В консоли участник, который может редактировать таблицу, находит **Архивировать
таблицу** (Archive table) в меню **Ещё действия** (More actions) на её странице.
Диалог говорит, что делает архивация, до того, как что-то изменится.
Опубликованный сценарий, который всё ещё читает или пишет таблицу и который
вызывающий может редактировать, отклоняет архивацию с `SCHEMA_DEPENDENCY`, и
диалог перечисляет его ссылкой. Сохранённые представления и триггеры блокируют
только архивацию столбца.

Страница архивированной таблицы говорит, когда её архивировали. Для участника,
который может редактировать таблицу, уведомление несёт **Восстановить** (Restore),
и оно возвращает таблицу под её названием; любой другой читает её записи и получает
сведения о том, кто может её восстановить. Каталог перечисляет действующие
таблицы, пока над ним не выбрано **Включая архивные** (Archived included), а
карточка архивированной таблицы говорит, что она в архиве.

| Действие | Маршрут | Отклоняется с |
|---|---|---|
| Архивация | `POST /tables/{id}/archive` | `SCHEMA_DEPENDENCY` (409), пока что-то использует таблицу. Архивировать дважды — не ошибка |
| Восстановление | `POST /tables/{id}/unarchive` | `BAD_REQUEST` (400), когда таблица не архивирована; `ALREADY_EXISTS` (409), когда действующая таблица заняла её название тем временем |

Оба требуют права редактировать эту таблицу — по роли или по выданному доступу к
ней, — а любой другой получает 404. У архивированной таблицы `can_edit` равен
false, поэтому `TableRead.can_restore` говорит, может ли этот вызывающий её
восстановить. Каждое действие попадает в аудит как `table.archived` и
`table.unarchived` и считается в лимите частоты записи в таблицы. Занятое тем временем
название сначала меняется у действующей таблицы, потому что архивированную
переименовать нельзя.

## Записи и ревизии { #records-and-revisions }

У каждой записи есть `revision`, начиная с 1 и возрастая с каждым изменением.

| Операция | Маршрут | Нужен `expected_revision` |
|---|---|---|
| Создание | `POST /tables/{id}/records` | Нет |
| Обновление названных ячеек | `PATCH /tables/{id}/records/{record_id}` | Да |
| Удаление | `DELETE /tables/{id}/records/{record_id}?expected_revision=` | Да |
| Upsert | `PUT /tables/{id}/records/by-external-id/{external_id}` | Только когда запись существует |
| Чтение, существование | `GET .../records/{record_id}`, `.../by-external-id/{external_id}`, `.../exists` | Нет |

Обновление или удаление, называющее старую ревизию, отклоняется с
`REVISION_CONFLICT` (409) и `details.current_revision`; ничего не перезаписывается.
Прочитайте запись снова и повторите попытку. Upsert, который находит существующую
запись и не получает `expected_revision`, получает `REVISION_REQUIRED` (428), снова
с ревизией, которую надо отправить.

Внешний идентификатор — от 1 до 255 символов, и он может содержать `/`, как в
`2026/ORD-1`. Он не может содержать NUL или перевод строки. Сервис проверяет это
так же, как маршруты. По HTTP маршрут отклоняет его первым, с `VALIDATION_ERROR`;
вызывающий, который пользуется сервисом напрямую, получает `INVALID_RECORD`.

Одновременные операции upsert с одним внешним идентификатором создают одну запись.
Проигравший находит её и получает ответ как на обновление: ему нужна ревизия, или
ему говорят, какую отправить.

Обновление, которое оставило бы каждую ячейку как есть, ничего не меняет. Ревизия
остаётся, строка истории или квитанция не пишется, и возвращается текущая запись.
Устаревший `expected_revision` всё равно конфликт, потому что его проверяют первым.
Upsert, который находит запись, следует тому же правилу.

Удаление — жёсткое удаление. История записи остаётся, пока её не уберёт срок
хранения.

## Редактирование записей в консоли { #editing-in-the-console }

Каталог и представления «Таблица», «Канбан» и «Список» используют общую панель с
поиском и управлением сохранёнными представлениями. **Добавить запись** (Add record)
на больших экранах использует два столбца, а на телефоне — один; длинный текст и
связанные записи занимают всю ширину. Боковая панель записи использует общую
обработку клавиатуры и фокуса в консоли. В **Столбцах** (Columns) существующие
варианты выбора сворачиваются под их счётчик. Неудавшийся запрос записи предлагает
**Повторить** (Retry).

Карточки каталога говорят, сколько у каждой таблицы записей и действующих
столбцов, кто может до неё добраться и когда она последний раз менялась. На
странице таблицы каждый заголовок показывает тип своего столбца значком, числа
выровнены по правому краю, а даты читаются так, как пишет их ваш язык. Панель
записи озаглавлена первым столбцом записи и говорит, когда её добавили и когда
последний раз меняли.

Участник, который может редактировать таблицу, добавляет, меняет и удаляет записи
с её страницы. **Добавить запись** спрашивает значение для каждого действующего
столбца, и вводится оно по типу столбца. Столбец, обязательный и без значения
по умолчанию, помечен `*`, и его нужно заполнить до того, как запись будет
сохранена; любой другой пустой столбец получает своё значение по умолчанию. Щелчок
по ячейке редактирует её на месте: Enter или щелчок мимо сохраняет её, Escape
оставляет без изменений, а да/нет, которое не может быть пустым, переключается
одним щелчком. Стрелки перемещают между ячейками, а кнопка разворота в конце
строки открывает всю запись.

Строка под сеткой добавляет записи по мере набора: набранное попадает в первый
текстовый столбец, а Enter создаёт запись и оставляет строку готовой для
следующей. Таблица с другим обязательным столбцом открывает вместо этого
**Добавить запись** с уже заполненным набранным значением, поэтому ничего не
сохраняется, пока нет каждого обязательного значения.

Каждая правка — один `PATCH` против ревизии на экране, поэтому правка, проигравшая
более новому изменению, отклоняется, а не записывается поверх него. Тогда запись
открывается с сохранённым отклонённым значением рядом с **Перезагрузить и
применить снова** (Reload and reapply), а запись читается заново: поле говорит,
что в нём сейчас, кто менял запись последним и когда, и заголовок панели следует
за этим. Отметка строк флажками предлагает **Удалить** (Delete) для всех них,
каждую против её собственной ревизии: запись, которую кто-то изменил тем временем,
остаётся, и консоль говорит, сколько их было. Панель записи удаляет одну запись так
же.

Удаление ждёт несколько секунд с **Отменить** (Undo) в своём уведомлении, прежде
чем его отправят; записи уходят из всех представлений сразу, а «Отменить»
возвращает их нетронутыми. Участник, который может только смотреть таблицу, видит
ту же сетку только для чтения, а щелчок по строке открывает запись.

Участнику, который может редактировать таблицу, заголовок столбца открывает меню.
**Сортировать по возрастанию** (Sort ascending) и **Сортировать по убыванию**
(Sort descending) упорядочивают сетку по нему, а **Скрыть в этом представлении**
(Hide in this view) убирает его с экрана, пока кнопка скрытых столбцов не покажет
его снова; **Сохранить представление** (Save view) сохраняет и то и другое.
**Переименовать** (Rename) и **Архивировать столбец** (Archive column) меняют
таблицу для всех, каждый как та же новая версия схемы, которую записал бы диалог
«Столбцы», а архивация того, что ещё используется, отклоняется, с перечислением
сценариев, представлений и триггеров в диалоге. **+** после последнего столбца
добавляет столбец, поначалу необязательный. Тип столбца меняется в **Столбцах** на
те типы, в которые преобразуются его значения.

В **Столбцах** **Обязательный** (Required) делает столбец требующим значения, а
архивный столбец переезжает под **Архивные столбцы** (Archived columns), откуда
**Восстановить** (Restore) возвращает его вместе со значениями.

Открытие сравнения сохраняет несохранённые правки в других полях и их исходную
ревизию. При более позднем конфликте читается новое сравнение; ответ для записи,
которую вы закрыли, не может закрыть другую запись. Длинные значения показываются
сокращённым предпросмотром.

### Импорт и экспорт { #import-and-export }

Сопоставьте каждый столбец таблицы, включая **Внешний идентификатор** (External
id), только один раз при импорте CSV. Повторяющиеся цели помечаются и блокируют
импорт, пока вы не выберете другую цель или не пропустите один из столбцов файла.

Экспорт читает не более 4 МиБ декодированного JSON записей на страницу (или одну
запись), не более 500 записей на страницу. Организация может выгружать один
экспорт за раз и запускать десять в минуту. Следующие запросы возвращают `429` с
`Retry-After`; повторите после этого интервала. Без Redis лимит частоты запусков
действует как минимум на уровне процесса; база данных по-прежнему обеспечивает один
одновременный экспорт на организацию. Один серверный курсор держит снимок записей
экспорта стабильным, выбирая заранее не более четырёх записей. Он закрывается при
завершении или отмене; более поздние страницы не пересканируют ранние записи.

**Экспорт** (Export) под **…** рядом с **Поделиться** (Share) сохраняет то, что
показывает страница, в файл CSV: записи, подходящие под фильтры и поиск, в порядке
сетки, по её видимым столбцам. `POST
/tables/{id}/records/export` делает то же для вызывающего, с теми же фильтрами,
поиском, сортировкой и списком `columns`. Вариант записывается своим названием,
несколько — как `a; b`, а текстовая ячейка, которую электронная таблица прочитала
бы как формулу, начинается с `'`. Более 100 000 подходящих записей отклоняются с
`EXPORT_TOO_LARGE` (413).

**Импорт** (Import) в том же меню читает файл CSV, разделённый запятой или точкой
с запятой, первая строка которого называет его столбцы. Каждый столбец файла
сопоставляется столбцу таблицы с тем же названием или **Внешнему идентификатору**
и может быть направлен в другое место или пропущен. Значение, которое не читается
как тип его столбца, бракует свою строку до того, как что-либо отправлено.
Остальные идут по 200 за раз в `POST /tables/{id}/records/batch`, который пишет
каждую запись отдельно и перечисляет отклонённые с их кодами, а консоль
перечисляет каждую неудавшуюся строку с её номером. Каждая добавленная запись
запускает триггеры таблицы, как и любая другая.

С сопоставленным **Внешним идентификатором** **Обновлять уже существующие записи**
(Update records already here) импортирует файл снова, чтобы привести таблицу в
актуальное состояние: строка, чей внешний идентификатор есть в таблице, меняет
названные в ней ячейки этой записи, а не отклоняется как занятая (`update_existing`
на пакете), и импорт считает, что добавил и что обновил.

Запись, которую кто-то изменил после начала импорта, остаётся как есть и
перечисляется как `REVISION_CONFLICT`: первый пакет отвечает `as_of` — временем
начала по серверным часам, — а остальные отправляют его обратно. Строка,
повторяющая внешний идентификатор, уже названный в файле, перечисляется, а не
отправляется, а пакет отклоняет строку, повторяющую идентификатор, который у него
уже есть, с `INVALID_RECORD`.

**Новая таблица** (New table) начинается со столбца **Название** (Name). Назовите
таблицу, выберите, кто может её видеть, и добавьте её столбцы; описание — под
**Дополнительными параметрами** (More options). Таблица начинается как **Только я**
(Only me); вариант **Все** (Everyone) открывает её всей организации, а вариант
**Выбранные люди** (Some people) делится ею с выбранными группами и участниками,
каждый с `read`, в том же запросе (`group_ids` и `user_ids` на `POST /tables`).
Вместо этого она может начаться с файла: **Начать с файла CSV** (Start from a CSV
file) превращает заголовок в столбцы и даёт каждому самый узкий тип, каким читаются
все его значения, — целое число, число, да/нет, дату, дату и время ISO, адрес
эл. почты или связь, — а иначе текст или длинный текст, как только значение
содержит перевод строки или оно длиннее 1 000 символов. Название берётся из файла,
и оба можно изменить до создания, что стоит меньше, чем позже менять тип. Как
только таблица существует, импорт открывается с уже сопоставленными столбцами, а
после него открывается таблица.

## Безопасные повторы { #safe-retries }

Каждая операция записи в таблицу принимает заголовок `Idempotency-Key` (не более
128 символов). Повтор с тем же ключом и тем же телом возвращает первый ответ, с
`Idempotent-Replayed: true`, и ничего не пишет, даже если запись с тех пор
изменилась. Тот же ключ с другим телом отклоняется с `IDEMPOTENCY_KEY_REUSED`.

Заголовок отмечает повтор создания, обновления, upsert или пакета. Повторное
удаление отвечает 204, как и первое, и не отмечается.

Ключ принадлежит вызывающему и виду операции записи, поэтому двое вызывающих могут
использовать одну строку, а один вызывающий — и для создания, и для upsert.
Хранятся только успехи: отклонённая операция записи не оставляет квитанции,
поэтому исправьте её и повторите с тем же ключом.

Повтор получает ответ только тот вызывающий, который всё ещё может редактировать
таблицу. Как только доступ отозван, тот же повтор — это 404.

Квитанция живёт 24 часа. После этого ключ забыт, и тот же ключ с тем же телом —
новая операция записи: она выполняется снова, а не возвращает первый ответ.
Повторяйте в пределах окна, а более долгий перерыв считайте новым запросом. Срок
проверяется при использовании ключа, поэтому выдерживается с точностью до часа;
ежедневная уборка только освобождает место квитанций, которые никто не повторял.

Удаление группы, проекта или учётной записи стирает связанные квитанции её доски
задач, включая результаты пакетов. При обновлении старые результаты пакетов без
идентификатора таблицы стираются, потому что их таблицу нельзя восстановить. Их
ключи остаются до истечения срока: подходящий повтор возвращает
`IDEMPOTENCY_RESULT_PURGED` (409) и ничего не пишет. Проверьте таблицу, прежде чем
начинать новую запись. Другие виды квитанций не меняются.

## Перечисление и фильтрация { #listing-and-filtering }

`GET /tables/{id}/records` листает таблицу страницами;
`POST /tables/{id}/records/query` добавляет типизированные фильтры, и все они
должны выполняться. Оба ограничены: `limit` — от 1 до 100, `skip` — не более
10 000, а в запросе не более 20 фильтров.

`search` — текст, который должна содержать запись, без учёта регистра, в любом
действующем столбце текста или длинного текста или в названии варианта выбора,
который она содержит. Он сочетается с фильтрами, а пустой ничего не ищет.
Сохранённое представление хранит его рядом со своими фильтрами. В консоли поле
поиска отправляет его, а **Фильтр** (Filter) пишет условия: столбец, оператор,
который поддерживает его тип, и значение. Каждое полное условие сразу сужает
записи, а **Сохранить представление** (Save view) сохраняет условия, поиск и
сортировку в представлении на экране.

Порядок полностью определён. Запрошенная сортировка (`created_at`, `updated_at` или
сортируемый столбец) дополняется идентификатором записи, поэтому страница никогда
не повторяет и не пропускает запись в неизменённой таблице. Записи без значения в
сортируемом столбце идут последними в любом направлении. Столбец `multi_select`
сортировать нельзя. `updated_at` задаётся при создании записи и сдвигается при
каждой правке, поэтому записи, которые никто не правил, сортируются по времени
создания.

У списка нет `total`, потому что подсчёт отфильтрованной таблицы недёшев: `has_more`
говорит, следует ли другая страница. `POST /tables/{id}/records/count` отвечает на
этот вопрос отдельно, для фильтров и поиска запроса, и считает не дальше 100 000;
`capped` говорит, что подходит больше. Консоль показывает это число рядом с
вкладками представлений, а её сетка загружает по сто записей за раз по мере
прокрутки, рисуя только видимые строки. Сверх 10 000 записей, которые запрос может
пропустить, она просит фильтр или поиск.

## Сохранённые представления { #saved-views }

**Сортировка** (Sort) рядом с **Фильтр** (Filter) выбирает сортируемый столбец и
порядок по возрастанию или убыванию для таблицы, списка или карточек, в том числе в
каждой дорожке канбана. Скрытые сортируемые столбцы и системные даты остаются доступны.
Активный столбец и направление видны на кнопке. Упорядочивание применяется на
сервере до разбиения на страницы, включая ещё не загруженные записи. **Сохранить
представление** (Save view) сохраняет порядок вместе с фильтрами и оформлением
представления; **+** сохраняет его как новое представление. **Порядок по
умолчанию: сначала старые** (Default order: oldest first) возвращает порядок по
дате создания.

**Настройки представления** (View settings) управляют порядком и видимостью
столбцов, включая системные поля. Перетащите столбец или используйте его стрелки;
скрытие системного поля оставляет его автоматическое значение нетронутым.
Включите **Переносить текст** (Wrap text), чтобы показывать полный текст и переводы
строк, или выключите для компактных строк. Выберите автоматический, ISO, формат с
днём впереди, с месяцем впереди или длинный, а также автоматическое, 24-часовое,
12-часовое или скрытое время. Значения только с датой сохраняют свой календарный
день; отметки времени используют часовой пояс того, кто смотрит. **Сохранить
представление**
сохраняет эти выборы для выбранного представления; **+** создаёт новое
представление. Форматирование не меняет ни сохранённые значения, ни фильтры.

Доска канбана без сохранённой группировки автоматически использует единственный
действующий столбец с одиночным выбором. Если их несколько, выберите, какой
столбец задаёт её дорожки. Сохранение представления сохраняет эту группировку.
Строки списка называют свои вторичные поля и показывают **Запись без названия**
(Unnamed record), когда название пусто. **Триггеры** (Triggers) предлагают
**Открыть сценарии** (Open workflows), когда от таблицы пока не запускается ни один
сценарий.

**Представление** — это сохранённые фильтры, сортировка и группировка над записями
одной таблицы, то, что экраны таблицы, канбана и списка в консоли сохраняют, чтобы
человек не собирал одну и ту же доску при каждом заходе. Это вложенный ресурс таблицы,
а не самостоятельный ресурс, которым можно поделиться: у представления нет
собственных владельца и выданных доступов, а `shared` значит только «видно любому,
у кого уже есть `tables:view` на родительской таблице» — это никогда не расширяет
доступ сверх того, что допускает сама таблица.

В консоли экран без выбранного представления называется **Все записи** (All
records), а **+** рядом с ним сохраняет то, что показывает экран, как новое
представление. Доска канбана автоматически использует свой единственный действующий
столбец с одиночным выбором или спрашивает, какой столбец задаёт её дорожки, когда
их несколько; сохранение представления сохраняет группировку. Карточка перечисляет
под своим названием до четырёх столбцов экрана, пропуская пустые. Таблица без
столбца с одиночным выбором предлагает вместо этого **Добавить столбец** (Add a
column).

Владелец представления переключает его между **Приватным** (Private) и **Общим**
(Shared) кнопкой рядом с **Переименовать** (Rename). Тот, кто управляет
представлением другого участника, например администратор, переключателя не
получает: делиться личными фильтрами человека — его выбор.

На телефонах меню **Представления** (Views) сохранённого представления содержит
создание другого представления, переименование, открытие доступа и удаление — по
тем же разрешениям, что и элементы управления на компьютере.

`GET/POST /tables/{id}/views` и `GET/PATCH/DELETE /tables/{id}/views/{view_id}`
перечисляют, создают, читают, обновляют и удаляют их. Список листается с `skip` и
`limit` (не более 100): сначала собственные представления вызывающего, затем
общие, каждое по названию; `total` считает все. `config` — это `{filters, search, sort,
visible_columns, group_by, display}`: `RecordQuery` плюс поля оформления, которые
нужны собственной отрисовке консоли, — `visible_columns` (`null` значит каждый
действующий столбец) и `group_by` (действующий столбец `single_select` для дорожек
канбана). Объект `display` хранит `column_order`, `hidden_system_columns`,
`wrap_text`, `date_format` и `time_format`. Старые представления используют
существующее компактное оформление с учётом языка. Явно пустой `visible_columns: []`
скрывает все пользовательские столбцы.

| Поле | Значение |
|---|---|
| `kind` | `table`, `kanban` или `list` — представление сохраняется *для* одного вида |
| `visibility` | `private` (только его владелец) или `shared` (любой, кто может видеть таблицу) |
| `can_manage` | Может ли этот вызывающий переименовать или перенастроить его; открывает доступ заново только его владелец |
| `can_delete` | Может ли этот вызывающий удалить его |

Перечисление, чтение и удаление разрешаются против таблицы (`tables:view`);
создание или изменение требует `tables:edit` на таблице, поэтому владелец, у
которого отняли доступ на редактирование, всё ещё может удалять свои
представления, но больше не может их менять или открывать к ним доступ.

Изменение или удаление представления ещё уже: только его владелец или вызывающий,
чья [область](permissions.md) `tables:edit` — `ALL`, а не «любой, кто может
редактировать таблицу», поэтому редактор с общим доступом не может молча
перенаправить сохранённый фильтр другого участника. Отказ такой же, как у любой
другой записи в отдельный ресурс: `NOT_FOUND` (404), никогда не 403, который
раскрыл бы существование представления вызывающему, которому отказано. `can_manage`
и `can_delete` говорят, что из двух этот вызывающий может делать.

Приватное представление другого участника ещё уже: даже вызывающий с областью
`ALL` может только удалить его, но никогда не изменить и не прочитать обратно,
поэтому `PATCH` отвечает `NOT_FOUND`, как для несуществующего представления. И
только владелец представления меняет его `visibility`: любой другой, присылающий
другое значение, отклоняется с `AUTHORIZATION_ERROR` (403), раз представление уже
перед ним.

Архивация столбца отклоняется с `SCHEMA_DEPENDENCY`, называя представление, когда
представление, которое вызывающий может и видеть, и менять, фильтрует, сортирует
или группирует по нему: одно из своих или, для вызывающего с областью `tables:edit`
`ALL`, общее. Любое другое представление не блокирует архивацию и не называется,
потому что вызывающий не мог бы его очистить; это включает каждое приватное
представление другого участника, которое не раскрывается даже вызывающему с
областью `ALL`. Показ столбца в `visible_columns` тоже не блокирует.

Все упоминания столбца, который больше не действует, отбрасываются при чтении
представления: фильтр по нему уходит, сортировка по нему откатывается на
`created_at`, группировка по нему очищается, и он уходит из `visible_columns` —
представление, оставшееся без единого из своих выбранных столбцов, показывает каждый
действующий столбец. Сохранённая конфигурация не переписывается.

### Страницы и представления { #views-for-pages }

Опубликованное [приложение](artifacts.md#live-data) не читает через представление.
Его привязки — это **запросы страницы**: таблица, фильтры, сортировка, лимит и
поля, которые читает страница, и платформа сохраняет их на версии страницы при её
публикации. Привязка может начаться с сохранённого представления — агент находит
его с `list_views`, который возвращает `id` каждого представления, его столбцы и
то, общее ли оно, для таблиц, которые он может читать, — но фильтры и сортировка
представления тогда **копируются** в страницу. Правка, открытие доступа,
переименование или удаление представления потом ничего не меняет на странице, а
`visible_columns` и `group_by` представления игнорируются: столбцы решают `fields`
привязки.

Представление со свободным текстовым поиском привязать нельзя, потому что поиск
соответствует каждому действующему текстовому столбцу и потому расширялся бы по
мере добавления столбцов; публикация отклоняется и называет представление. Так же
и представление, чей фильтр называет исчезнувший столбец.

Кто может читать записи страницы, решает не представление. Их читают с доступом
владельца страницы, после того как владелец дал согласие, а доступ к таблице — всё
или ничего: `read` даёт каждую строку и каждый действующий столбец. Запрос
страницы — это то, как строки таблицы доходят до людей, которые не могли бы её
открыть, и владельца спрашивают первым. См.
[Приложения](artifacts.md#consent-the-owner-decides-who-reads-the-data).

Запрос страницы записывает `revision` каждого столбца, до которого доходит: столбцов
своих полей, фильтра и сортировки, входов формулы, связи и цели подстановки или
сводного значения и столбца, которым каждая связанная таблица подписывает свои
записи. Привязка становится `unavailable` (`source_changed`), когда что-то из этого
сдвинулось или было архивировано или когда архивировали таблицу, до которой она
доходит, а остальные привязки продолжают работать. Ничто не мешает изменить таблицу
из-за неё: страница не является зависимостью, которая блокирует архивацию.
`share_view` больше не существует; для страницы нет приватного представления,
которым можно поделиться.

## Триггеры { #triggers }

Дорожки канбана загружают по 25 карточек за раз. **Загрузить ещё** (Load more)
сохраняет существующие карточки; неудавшаяся страница предлагает **Повторить**
(Retry). Изменение группировки можно сохранить в активное представление. Чтение
приватного представления после того, как другой участник сменил типы его столбцов,
убирает несовместимые фильтры, сортировку и группировку из возвращённой
конфигурации, не переписывая сохранённое представление его владельца. Запрос
страницы, который потерял бы фильтр, требует нового согласия.

События таблицы используют время по часам сервера на момент вставки после блокировки
изменений, как и момент включения триггера. Транзакция, начатая до
включения, всё равно может дать более позднее подходящее событие. Миграция
`0229_table_event_wall_clock.py` меняет будущие отметки времени; она не повторяет
ранее пропущенные события, что могло бы удвоить эффекты.

[Сценарий](workflows.md#when-a-table-record-is-added), чей узел-триггер —
**Запись таблицы** (Table record), запускается, как только его опубликуют, на то,
что происходит с записями его таблицы, — добавление, изменение или удаление, смотря
что называет его `events`; по умолчанию только добавление, — как бы это ни
произошло: в консоли, по API, инструментом таблиц агента или шагом таблицы другого
сценария. Upsert, который создаёт запись, — это добавление, а тот, который её
обновляет, — изменение. Публикация требует доступа на чтение таблицы и разрешения
запускать сценарий, потому что он работает от имени участника, который его
опубликовал, а не автора записи. Доступ этого участника проверяется заново на каждом
событии.

Триггер выполняет версию, которая его включила, и следующая публикация переводит
его на новую версию. Его фильтры используют операторы из раздела [Перечисление и
фильтрация](#listing-and-filtering) и судят запись такой, какой её добавили или
изменили, или какой она была до удаления. Изменение запускает его, только когда
изменился один из выбранных для таблицы столбцов, если столбцы выбраны.

Он передаёт запуску запись: `record_id`, `event`, `values` по идентификатору
столбца, те же значения как `fields` по названию и `author_id`, а для изменения или
удаления — `before` и столбцы `changed` по названию. **Триггеры** (Triggers) на
странице таблицы перечисляют сценарии, которые от неё запускаются, приостанавливают
и возобновляют каждый и открывают его историю.

Приостановка одного там требует `tables:edit` на таблице. Возобновление снова
запускает сценарий от имени его издателя, поэтому ему нужны ещё `workflows:edit` и
`workflows:run` на этом сценарии, как и собственному переключателю **Активен**
(Active) сценария; участнику, который может редактировать таблицу, но не сценарий,
говорят, что сценарий не найден.

Триггер запускается только для записей, добавленных, пока он включён. Его
включение — публикация или возобновление — берёт блокировку схемы таблицы, ту самую,
которой ждёт каждая запись, поэтому ни одна запись, зафиксированная до этого
момента, его не запустит, и ничего добавленное, пока он был выключен, не
повторяется. Задача `workflow-table-triggers`, которая выполняется каждые десять
секунд, читает событие исходящей очереди каждой новой записи, поэтому триггер
запускается примерно в течение десяти секунд. Она решает один раз на триггер и
записывает решение; второй проход или второй воркер находит это решение и ничего не
запускает.

**История** (History) перечисляет каждое решение, начиная с новейшего, без значений
записи:

| Показано как | Почему |
|---|---|
| Запуск начат | Каждый фильтр совпал; запуск связан |
| Пропущено | Запись не подошла или была добавлена до включения триггера |
| Заблокировано | Он запустил бы сам себя снова, цепочка ушла глубже пяти триггеров или дальше 50 запусков, или запуск был отклонён квотой допуска |
| Не удалось запустить | Участник, от имени которого он работает, больше не может читать таблицу или запускать сценарий, или не удалось прочитать создание записи |

Сценарий, который пишет в таблицу, может запускать триггеры этой таблицы и так
далее через другие таблицы. Каждый запуск несёт цепочку, к которой принадлежит, а
триггер, через который цепочка уже прошла, блокируется, а не запускается снова, —
именно это и не даёт двум сценариям, добавляющим записи в таблицы друг друга,
зациклиться. Столбец, по которому фильтрует триггер, нельзя архивировать, пока
триггер его сценария не перестанет по нему фильтровать и не будет опубликован,
даже пока триггер приостановлен, а таблицу, от которой запускается опубликованный
сценарий, нельзя архивировать, пока этот сценарий не начнёт запускаться иначе.

## Что фиксируется вместе { #what-commits-together }

Запись в таблицу, её строка истории, её квитанция идемпотентности и, для создания,
строка `table.record.created` исходящей очереди пишутся в одной транзакции и
фиксируются или откатываются вместе. Сбой на любом шаге не оставляет ни одной из
них. Изменения таблиц и схемы записываются в [журнал аудита](governance.md);
изменения записей записываются в историю каждой записи, которая хранит ячейки,
которых коснулось каждое изменение.

Два из этих хранилищ держат копии того, что было записано. Квитанция хранит всю
запись в том виде, в каком её вернула операция записи, а история — то, что
изменилось, поэтому удаление записи убирает текущую строку и оставляет оба, пока их
не уберёт срок хранения. Строки исходящей очереди держат идентификаторы. Считайте
все три персональными данными, если ячейки таковы; см. [защиту
данных](data-protection.md#the-database) и [лимиты и
хранение](#limits-and-retention).

Строка исходящей очереди — это передача тому, что реагирует на новую запись:
сегодня — [триггерам](#triggers). Их сигнал активности забирает недоставленные
строки в своём сеансе, судит каждую по триггерам таблицы и помечает её отправленной
в той же транзакции. Неотправленная строка удаляется только по своему гораздо более
долгому сроку хранения (ниже) — это порог для воркера, который простоял так долго, а
не утверждение, что событие когда-либо было получено.

## Лимиты и хранение { #limits-and-retention }

Организация может увеличивать общую базу данных лишь настолько, насколько ей
позволяет экземпляр. Каждый лимит — настройка экземпляра, применяется **на
организацию**, поэтому расход одной организации никогда не засчитывается другой, и
операция записи, которая его превысила бы, отклоняется с `QUOTA_EXCEEDED` (402).

| Настройка | По умолчанию | Ограничивает |
|---|---|---|
| `TABLES_MAX_PER_ORGANIZATION` | 200 | Таблиц у организации. Архивные считаются, потому что таблица никогда не удаляется |
| `TABLES_MAX_RECORDS_PER_TABLE` | 100 000 | Записей в одной таблице. Обновлять запись в полной таблице разрешено |
| `TABLES_MAX_RECORD_BYTES` | 1 000 000 | Сериализованные значения одной записи в байтах |
| `TABLES_MAX_STORAGE_BYTES_PER_ORGANIZATION` | 1 073 741 824 | Байты полезной нагрузки JSONB, хранимой в PostgreSQL, на организацию — по записям, истории, квитанциям и исходящей очереди; физические накладные расходы таблиц и индексов отдельны |

Потолок совокупного объёма проверяется внутри точки сохранения изменения, под
блокировкой организации, до фиксации. Операция записи сверх лимита откатывает свою
запись и каждую сохранённую копию, включая строку пакета; остальные строки пакета
сообщаются как отклонённые. Повтор квитанции, ничего не меняющие записи, чтение и
удаление остаются доступны после понижения лимита. Уборка по срокам хранения
освобождает байты, которые убирает.

Отказ называет квоту и её потолок в `details` (`{"quota": "records", "limit":
100000}`), никогда содержимое, и пишет запись `table.quota_refused` в [журнал
аудита](governance.md) с теми же двумя полями. Отклонённый запрос ничего не пишет.
Записи также ограничены `RATE_LIMIT_TABLE_WRITES_PER_MINUTE` (300) на участника и
организацию, в консоли так же, как по API; участник сверх него получает 429 с
`Retry-After`. См. [конфигурацию](configuration.md#rate-limiting).

**Что хранит история.** Создание хранит всю запись в `after`, а удаление — всю
запись в `before`; лимит записи ограничивает и то и другое. Запись, существовавшая
до введения лимита или написанная до понижения `TABLES_MAX_RECORD_BYTES`, всё ещё
может его превышать — тогда её удаление хранит `before` как `{"omitted": {"bytes": <its size>, "limit": <the limit>}}`
вместо значений и всё равно завершается успешно. Обновление хранит только
изменившиеся ячейки: `before` держит их прежние значения, а `after` — новые, а
столбец, отсутствующий с одной стороны, был там пуст. Правка одной ячейки большой
записи поэтому стоит одной ячейки, как бы часто она ни повторялась.

**Хранение.** Ежедневная [уборка по срокам
хранения](governance.md#retention) убирает и данные таблиц, жёстко удаляя их
пакетами, для каждой организации:

| Что | Удаляется, когда | Настройка |
|---|---|---|
| Квитанции | Старше 24 часов | `TABLES_RECEIPT_TTL_HOURS` |
| Строки исходящей очереди | Отправлены более 3 дней назад | `TABLES_OUTBOX_RETENTION_DAYS` |
| Неотправленные строки исходящей очереди | Никогда не отправлены и им 30 дней: сигнал активности триггера не работал так долго, и ни один триггер не запустится для этих записей | `TABLES_OUTBOX_UNDISPATCHED_RETENTION_DAYS` |
| История | Старше 365 дней, для удалённой записи так же, как для действующей | `TABLES_HISTORY_RETENTION_DAYS` |

Уборка пишет одну запись аудита на организацию, называя класс (`table_receipts`,
`table_outbox`, `table_history`) и количество. Это настройки экземпляра, а не
каждой организации. Сами записи и таблицы она никогда не удаляет.

`RATE_LIMIT_TABLE_WRITES_PER_MINUTE` — это норма *на участника*, поэтому бюджет
одного прохода для каждого из трёх классов масштабируется и по ней, и по числу
активных участников организации, с запасом, чтобы накопленная очередь сокращалась,
а не просто держалась на уровне: каждый участник, пишущий на полную одновременно,
никогда не обгоняет уборку — вплоть до щедрого потолка на число участников, на
которое рассчитывает собственный проход одной организации. Числа см. в
[конфигурации](configuration.md#virtual-tables-limits-and-retention). Накопленное
сверх этого разбирается за несколько проходов, как и любой другой класс.

## Кто что может { #who-can-do-what }

| Разрешение | У кого |
|---|---|
| `tables:view` | Owner, Admin, Builder и Operator видят все таблицы; Member и Viewer — свои, видимые организации и общие |
| `tables:edit` | Owner и Admin редактируют все; Builder — свои и общие; Member — свои |
| `tables:create` | Owner, Admin, Builder, Member |

`tables:view` и `tables:edit` — разрешения на ресурс, поэтому [выданный
доступ](permissions.md) к одной таблице расширяет роль только для этой таблицы:
Viewer с `edit` на одной таблице редактирует эту таблицу и больше ничего. Открытие
доступа использует те же маршруты `/tables/{id}/sharing`, что и другие общие
ресурсы. Записи наследуют доступ своей таблицы, и схема это закрепляет: запись,
строка истории или исходящей очереди ссылается на свою таблицу вместе с
организацией, поэтому строка не может назвать таблицу из другой организации.

Может ли конкретный вызывающий редактировать конкретную таблицу, тоже видно прямо
в ответе: `TableSummary.can_edit` и `TableRead.can_edit` вычисляются на сервере
(область роли или явно выданный доступ) и передаются при каждом чтении, как и
`Agent.can_run`, — поэтому строка каталога или страница подробностей никогда не
должна угадывать, отклонят ли её элементы управления редактированием. Собственные
`can_manage` и `can_delete` сохранённого представления — та же идея на уровень
ниже (см. [Сохранённые представления](#saved-views)).

Таблица другой организации и таблица, до которой вызывающий не может добраться, —
обе 404. Контекст без вошедшего субъекта не достигает ничего.

## Ошибки { #errors }

Каждый отказ отвечает `{"error": {"code", "message", "details"}}`, и `code` — это
то, по чему ветвится клиент.

| Код | Статус | Значение |
|---|---|---|
| `REVISION_CONFLICT` | 409 | Запись изменилась с тех пор, как её прочитали |
| `REVISION_REQUIRED` | 428 | upsert существующей записи требует `expected_revision` |
| `SCHEMA_VERSION_CONFLICT` | 409 | Схема изменилась с тех пор, как её прочитали |
| `SCHEMA_DEPENDENCY` | 409 | Что-то зависит от того, что удаляет изменение |
| `TABLE_ARCHIVED` | 409 | Таблица отклоняет записи |
| `BAD_REQUEST` | 400 | Восстановление назвало таблицу, которая не архивирована |
| `ALREADY_EXISTS` | 409 | Название таблицы, название представления или внешний идентификатор заняты |
| `INVALID_RECORD` | 422 | Значение не соответствует своему столбцу; `details.fields` называет каждое |
| `ARCHIVED_COLUMN` | 422 | Значение называет архивный столбец |
| `INVALID_QUERY` | 422 | Фильтр или сортировка, на которые таблица не может ответить |
| `INVALID_SCHEMA` | 422 | Несогласованное изменение схемы |
| `IDEMPOTENCY_KEY_REUSED` | 422 | Ключ использовали для другого запроса |
| `IDEMPOTENCY_RESULT_PURGED` | 409 | Старый результат пакета стёрт при обновлении; его ключ всё ещё не даёт сделать другую запись до истечения срока |
| `QUOTA_EXCEEDED` | 402 | Операция записи превысила бы лимит хранения; `details` называет квоту (`tables`, `records`, `record_bytes`, `storage_bytes`) и её потолок |
| `RATE_LIMIT_EXCEEDED` | 429 | Слишком много операций записи в таблицы за последнюю минуту; см. `Retry-After` |
| `VALIDATION_ERROR` | 422 | Сам запрос некорректен: неверный тип, неизвестное поле, превышенный лимит или NUL, перевод строки или одиночный суррогат в идентификаторе, ключе или названии. Отклоняется маршрутом до запуска сервиса |
| `AUTHORIZATION_ERROR` | 403 | У вызывающего нет разрешения, которое требует коллекционный маршрут (`tables:view`, `tables:create`) |
| `CONCURRENT_CHANGE` | 409 | upsert проиграл гонку с удалением той же записи. Повторите его |
| `NOT_FOUND` | 404 | Нет такой таблицы или записи или она недоступна вызывающему |

## Вызов сервиса из Python { #calling-the-service-from-python }

```python
service = VirtualTableService(db)
table = await service.create_table(
    ctx,
    TableCreate(
        name="Orders",
        columns=[
            ColumnInput(label="Customer", type="text"),
        ],
    ),
)
customer = str(table.columns[0].id)

written = await service.upsert_record(
    ctx,
    table.id,
    "ORD-1042",
    RecordUpsert(values={customer: "Acme"}),
    operation_key="import-2026-09-21-row-17",
)

# Передайте ревизию обратно, чтобы изменить запись; устаревшая вызывает RevisionConflictError.
await service.upsert_record(
    ctx,
    table.id,
    "ORD-1042",
    RecordUpsert(values={customer: "Acme Ltd"}, expected_revision=written.record.revision),
)
```

Организация всегда берётся из `ctx`, никогда из аргумента. Сервис никогда не
фиксирует транзакцию: это делает сеанс запроса, а воркер владеет своей областью
сеанса.

## Добавление типа столбца { #adding-a-column-type }

Тип столбца — один элемент в `COLUMN_TYPES` в
`backend/app/services/virtual_tables/types.py`, с его именем в `ColumnTypeName` в
`backend/app/schemas/virtual_table.py`. Элемент задаёт, как ячейка читается из
записи для сравнения и сортировки (`SqlKind`), какие операторы фильтра она
принимает, сортируется ли она и через какой валидатор проходит каждая операция
записи и каждый операнд фильтра. Валидатор возвращает значение таким, каким оно
хранится, или вызывает `CellProblem` с сообщением для того, кто его написал. Каждый
способ доступа вызывает один и тот же сервис, поэтому консоль, API, агенты и
сценарии принимают новый тип сразу, и [триггер](#triggers) фильтрует по нему по тем
же правилам.

Консоли нужен тип в `ColumnTypeName` в `frontend/src/types/tables.ts`, редактор в
`record-cell-editor.tsx`, выбор в диалогах схемы и создания таблицы и его название в
трёх каталогах сообщений. Тесты валидатора принадлежат
`backend/tests/test_virtual_table_types.py`, а тест, который записывает, фильтрует и
сортирует запись нового типа, — интеграционному тесту.

При создании пустой таблицы обязательным столбцам не нужны значения по умолчанию:
каждая новая запись должна содержать их значения. Добавление обязательного столбца в
существующую схему всё равно требует значения по умолчанию, чтобы защитить
существующие записи.

## Задачи, переживающие перезапуск { #durable-tasks }

У **агента** тоже может быть общая доска задач. Её аудитория следует текущему
доступу к агенту; для правки задач дополнительно нужен доступ на редактирование
таблицы и разрешение запускать этого агента. Владелец агента или редактор агента
может управлять доской. Агент, назначенный на приватную задачу, не делает её общей.
Через AgenticOS MCP используйте `create_task` или `ensure_task_board`: существующая
таблица области используется повторно, а недостающая доска создаётся при первом
обращении. Выбирайте приватную для личных напоминаний, проектную — для результатов
проекта, а агентскую — для явно запрошенного списка задач агента. Спрашивайте,
когда область неоднозначна; не делитесь личным содержимым неявно.

Вы можете создать задачу проекта из приватного диалога вне этого проекта. Оставьте
рабочий чат неуказанным: задача откроет свой диалог в проекте, не связывая ваш
приватный транскрипт. Явное связывание диалога из другого проекта отклоняется.

**Таблицы** (Tables) (`/tables`) — это место управления задачами. **Фоновая
работа** (Background work) (`/work`) показывает идущие фоновые диалоги и их
историю. Задача — это запись виртуальной таблицы со ссылкой на рабочий чат и одним
инцидентом во «Входящих», когда нужно внимание. Правки в таблице и канбане используют
ту же ревизию, что и API задач; отдельно синхронизируемого списка TODO нет.

Доска создаётся при первом обращении для **человека**, **проекта**, **группы** или
**организации**, а затем используется повторно. У проектов и групп есть действие
**Задачи** (Tasks); **Таблицы** открывают вашу приватную доску. Пустые доски не
создаются при установке или для каждого нового членства. Первое создание требует
`tables:create`. Доски проектов наследуют текущий доступ к проекту, доски групп —
текущее членство в группе, а личные доски остаются приватными даже для другого
владельца организации. Эти проверки действуют и через общие API таблиц, связи и
сохранённые представления. Существующие пользовательские таблицы задач и шаблоны
отслеживания проектов автоматически не преобразуются.

У задач есть название, **Заметки** (Notes) с форматированным текстом, состояние,
связанные **Человек** (Person) и **Агент** (Agent), **Следующий шаг** (Next step) —
человек или агент, — **Начало** (Start at) и **Срок** (Due at). Пока агент готовит
работу, владельцем остаётся человек; следующий шаг возвращается к человеку на
проверку. «Срок» — только крайний срок.

Когда следующий шаг принадлежит человеку, **Начало** планирует напоминание во
«Входящих» без вызова модели. Когда он принадлежит агенту, **Начало** планирует
одно закреплённое выполнение через обычный механизм выполнения автоматизаций; без
начала — сейчас. Его проверенные источники, действующие разрешения, бюджеты и
согласования по-прежнему применяются. Назначение не даёт доступа к учётным записям
другого человека. Работа агента возвращается в связанный рабочий чат или в новый
приватный чат и ждёт проверки. Сбой оставляет её заблокированной.

Результаты наблюдений автоматизаций во «Входящих» тоже держат по одной приватной
задаче на инцидент источника. Новые ревизии источника используют ту же задачу и чат.
**Отметить выполненной** (Mark done) закрывает её инцидент во «Входящих»; решение
инцидента завершает задачу. Подтверждение означает только то, что её увидели. Отмена
или удаление задачи отзывает поставленные в очередь напоминания и останавливает
последующие инструменты агента; действие, уже отправленное внешнему провайдеру,
отменой не отменить. Подготовка письма его не отправляет: разрешите отправку в чате и
завершайте задачу только после успешной отправки.

AgenticOS MCP предоставляет `list_task_boards`, `ensure_task_board`, `list_tasks`,
`get_task`, `create_task` и `update_task`. Создание принимает стабильный
`external_id` для дедупликации источников. Обновления требуют `expected_revision`;
устаревшая правка возвращает 409. HTTP использует `/tasks/boards`, `/tasks` и
`/tasks/{id}` под `/api/v1`. Основные поля задачи и варианты состояния сохраняют
свои идентификаторы; добавляйте пользовательские столбцы, не меняя их типы и не
архивируя их. Сохранённые представления Board, Planned, Agent tasks и Waiting for
review устанавливаются вместе с доской. Контрольный список `write_plan` агента
остаётся внутренним для запуска и не создаёт запланированных обязательств.

Членство в группе позволяет читать доску задач группы; операции записи дополнительно
требуют разрешения на редактирование таблицы или явно выданного доступа на
редактирование. Если назначенный проверяющий напоминания теряет доступ, задача
становится заблокированной, а её создатель получает инцидент во «Входящих», чтобы
организовать передачу. Новые рабочие чаты для задач проекта остаются в этом
проекте. Квота таблиц может помешать необязательной проекции результата
автоматизации в задачу, но её рабочий чат, инцидент во «Входящих» и уведомление всё
равно доставляются.

Записи на доске задач проекта требуют доступа к проекту и разрешения на
редактирование таблицы или явно выданного доступа Edit к таблице. Удаление
проекта, группы или приватного владельца отменяет поставленную в очередь работу
над задачами, решает инциденты задач и стирает управляемую таблицу этой области,
записи, историю и медиа в той же транзакции. Другие области остаются нетронутыми.

Изменение самой доски задач — более узкое право, чем работа с ней. Переименование
доски, изменение её столбцов или представления по умолчанию, её архивация или
восстановление требуют `tables:edit` в области `ALL` (Owner или Admin)
или руководителя области доски: ведущего группы, владельца проекта, человека,
которому принадлежит приватная доска. Любой другой из аудитории доски по-прежнему
добавляет и правит задачи; `can_manage` таблицы говорит, что из двух доступно
вызывающему, и консоль показывает собственные элементы управления доски, только
когда это так. Попытка без этого отклоняется с `AUTHORIZATION_ERROR` (403).

## Представление по умолчанию { #default-view }

Редактор может выбрать **Сделать по умолчанию** (Set as default) в **Настройках
представления** (View settings). Текущая раскладка, фильтры и группировка
сохраняются как общее представление, которое затем открывается каждый раз, когда
кто-то заходит в таблицу без явного переопределения `view` или `viewId` в URL. Новые
доски задач начинаются в канбане. Представление по умолчанию должно принадлежать этой
таблице и быть общим; его нельзя сделать приватным, пока не выбрано другое по
умолчанию. Его удаление возвращает таблицу к простой раскладке. API использует
`PATCH /tables/{id}` с `default_view_id` или null, чтобы очистить его. Заметки —
это документы Markdown с тем же редактором форматированного текста и предпросмотром,
что и другие ячейки документов.

**Группировать по** (Group by) сохраняется автоматически, когда редактор выбирает
столбец. Такая группировка обновляет управляемое сохранённое представление
канбана; без него она создаёт приватное представление и выбирает его. Отклонённое
сохранение сохраняет прежнюю группировку. Читатели могут временно изменить
группировку. **Сделать по умолчанию** в **Настройках представления** сохраняет
текущий формат для всех; обычные таблицы начинаются с вкладки «Таблица», пока
редактор не выберет другое представление по умолчанию.

Агента нельзя удалить, пока управляемая задача всё ещё зависит от его
запланированного выполнения. Сначала переназначьте, завершите или отмените эти
задачи; удаление агента не должно молча выбрасывать его работу над задачами.

Восстановление архивированной управляемой доски задач ставит в очередь заново её
запланированные напоминания для людей, включая напоминания, время которых прошло,
пока доска была в архиве. Доставка всё равно проверяет текущий доступ исходного
создателя и получателя; восстановление доски не даёт разрешения на новую работу
агента. Архивная доска не принимает записей и от своих задач: инцидент, решённый во
«Входящих» тем временем, оставляет задачу как была, а восстановление доски переводит
задачу в «Выполнена» или «Отменена» тогда же. Повторное открытие инцидента, чья доска
задач архивирована, отклоняется с `TABLE_ARCHIVED`.

Участник с разрешением создавать таблицы получает свою недостающую приватную
таблицу задач при первом заходе в **Таблицы**. Существующие таблицы используются
повторно; открытие страницы не создаёт список задач организации или агента.
Проекты предлагают **Таблицу задач** (Task table), чтобы создать или открыть свою.
Без разрешения на создание доступные существующие таблицы остаются доступны, а
приложение не пытается выполнить отклонённое создание.

«Входящие» показывают задачу, когда человеку нужно действовать или проверить её
результат; это не второе хранилище задач. Наблюдения, почтовые триггеры и
автоматизации могут создавать инциденты во «Входящих», не создавая записей задач.
Создавайте задачу для конкретного обязательства, которое требует доведения до
конца, а не для каждого входящего события. Договорённость о том, какая таблица
используется, можно запомнить вместе с проверенным идентификатором этой таблицы;
действующее состояние задачи остаётся в таблице.

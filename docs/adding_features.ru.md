# Добавление функции { #adding-a-feature }

Четыре вида изменений, и у каждого есть разобранный пример в другом месте. Эта
страница — карта: чего касается изменение такого вида и где лежит его подробное
описание.

## Добавление эндпоинта API { #adding-a-new-api-endpoint }

!!! abstract "Один разбор — в разделе руководств"

    [Добавьте эндпоинт API](howto/add-api-endpoint.md) — это разобранный пример:
    схема, модель, репозиторий, сервис, зависимость, маршрут, роутер, миграция,
    тесты. Второй копии здесь намеренно нет: две копии, написанные для одного
    читателя, — это две копии, которые расходятся.

Форма, которую он показывает, в одном абзаце: **схема** на каждую операцию
(`*Create`/`*Update`/`*Read`/`*List`), **модель** на `Base, TimestampMixin` с
`__repr__`, **репозиторий** из функций без состояния, использующих
`flush()`/`refresh()` и никогда `commit()`, **сервис**, хранящий только сессию и
порождающий доменные исключения, `Annotated`-**зависимость** в `api/deps.py` и
**маршрут**, возвращающий `-> Any`, где сериализацию делает `response_model`.

## Добавление своей команды CLI { #adding-a-custom-cli-command }

Команды обнаруживаются автоматически в `app/commands/`.

```python
# app/commands/my_command.py
import click

from app.commands import command, success


@command("my-command", help="What this does")
@click.option("--name", "-n", required=True, help="Whose name")
def my_command(name: str) -> None:
    """One line, because `--help` prints it."""
    success(f"Done: {name}")
```

`success`, `error`, `warning` и `info` — помощники вывода: команда сообщает, что
произошло, через них, а не через `print`, поэтому все команды CLI читаются
одинаково. Запустите её так:

```bash
uv run agenticos cmd my-command --name test
```

!!! note "Новая команда должна добавить строку в `docs/commands.md`"

    Эту страницу читает оператор; команда, которой там нет, — команда, которую
    никто не найдёт.

## Добавление инструмента, который может вызывать агент { #adding-a-tool-the-agent-can-call }

Здесь нет единого модуля агента, к которому можно прицепить `@agent.tool`. Агенты
здесь — данные: они собираются при каждом запуске из возможностей, названных в их
спецификации, поэтому новый инструмент появляется как часть **возможности**:

- Новая возможность → [Добавьте возможность](howto/add-capability.md).
- Ещё один инструмент в уже существующей возможности →
  [Добавление инструмента в существующую
  возможность](howto/add-capability.md#adding-a-tool-to-an-existing-capability).
- Сторонний API, у которого уже есть MCP-сервер → никакого кода, см.
  [MCP](mcp.md).

!!! danger "К инструменту, не объявленному в реестре, нельзя применить согласование или переименование"

    Список в `@register(tools=...)` — это то, на что опираются согласование для
    отдельного инструмента и переименование для отдельного агента. Необъявленный
    инструмент всё равно работает — просто без согласования, и именно этой ошибки
    стоит избегать.

Что поставляется сегодня, описано в [каталоге возможностей](reference/capabilities.md).

## Добавление миграции базы данных { #adding-a-database-migration }

!!! warning "`make db-check` пропускает себя, когда не слушает ни одна база данных"

    `alembic check` нужна база, поэтому цель печатает предупреждение и
    **завершается с кодом 0**, если на `CHECK_DB_PORT` нет базы данных: изменение
    модели без миграции тогда проходит локальную `make check`. В CI у задачи
    **`test`** рядом есть Postgres, поэтому она не пропускается — именно там
    эта ошибка и обнаруживается. Сначала запустите `make docker-db`, если нужен
    локальный ответ.

!!! tip "Автогенерация — черновик, а не ответ"

    Прочитайте ревизию, прежде чем коммитить её, и дайте ей откат, который
    действительно её отменяет: `make test-migrations` проверяет всю цепочку в обе
    стороны.

```bash
# Create migration
uv run alembic revision --autogenerate -m "Add notifications table"

# Apply migration
uv run alembic upgrade head

# Or use CLI
uv run agenticos db migrate -m "Add notifications table"
uv run agenticos db upgrade
```

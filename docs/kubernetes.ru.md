# Разверните в Kubernetes { #deploy-on-kubernetes }

`charts/agenticos` устанавливает API, воркер и консоль из выпущенных образов. Ему
нужны внешние PostgreSQL с pgvector, Redis/Valkey и существующий бакет S3. Базы
данных он не устанавливает и их резервные копии не готовит. `appVersion` чарта —
версия образа по умолчанию; закрепите другой релиз через `image.tag` или
используйте `image.backendDigest` и `image.frontendDigest` для неизменяемых
образов.

Образы бэкенда старше 1.63.0 ожидают общие временные файлы индексации, и этот
чарт их не поддерживает.


## Kubernetes и OpenShift { #kubernetes-and-openshift }

Kubernetes планирует контейнеры и управляет ими. Red Hat OpenShift — платформа
Kubernetes с дополнительными компонентами и политиками, включая Security Context
Constraints (SCC), интеграцию с SELinux и Routes. Один и тот же чарт — отправная
точка для обеих; успешный тест в Kubernetes не проверяет эти компоненты OpenShift
или интеграцию облачного провайдера с идентичностью и хранилищем.

| Путь развёртывания | Подтверждение и оставшиеся проверки |
| --- | --- |
| Kubernetes с Helm | Воспроизводимый smoke-тест на kind, описанный ниже; публичный ingress и применение NetworkPolicy по-прежнему нужно проверить в вашем кластере |
| OpenShift с Helm | Локальный OpenShift 5.0.0 прошёл restricted-v2, жизненный цикл Helm, HTTPS Routes, WSS и применение NetworkPolicies; ваш кластер и хранилище проверяйте отдельно |
| Argo CD на локальном OpenShift | Argo CD Core 3.6.1 прошёл установку полной синхронизацией, отказ при неудавшейся миграции, обновление конфигурации и совместимый откат через Git на той же схеме базы данных |
| Песочница и OIDC | Необязательные интеграции с отдельной конфигурацией и приёмочными тестами ниже |

## Совместимость и ограничения { #compatibility-and-limits }

Воспроизводимый тест использует kind 0.33.0, Kubernetes 1.37.0 и Helm 4.3.1. Он
проверяет приём в режиме Pod Security restricted, корневые файловые системы только
для чтения, произвольные числовые UID, миграции, вход, ответ опубликованного
агента, загрузку в S3, индексацию и фоновый запуск, переживающий перезапуск.
Модель — детерминированная фикстура протокола; тест ничего не утверждает о
доступности платного провайдера или качестве ответов.

**OpenShift Local проверен** с CRC 2.65.0, OpenShift 5.0.0 (Kubernetes 1.36.5),
Helm 4.3.1 и образами приложения 1.80.0. API, воркер и консоль были приняты под
`restricted-v2`, с UID, назначенными пространством имён, корнями только для
чтения и без `anyuid`, привилегированных SCC или доступа к сокету узла.
`values-openshift.yaml` оставляет назначение UID и `fsGroup` за SCC. Эти данные не
охватывают другие выпуски OpenShift, интеграцию с Azure или драйверы хранилища.

В базовом чарте нет демона песочницы, сокета Docker, сервиса браузера или
рендерера артефактов. Выполнение контейнеров, работа с компьютером и браузером, а
также рендеринг, которым нужны эти сервисы, остаются недоступны, пока вы не
настроите подходящий внешний сервис. Для подключений песочницы используйте [конфигурацию
песочницы](sandbox.md) продукта и хранилище секретов; не монтируйте
`/var/run/docker.sock` узла в поды приложения.

## Подготовьте внешние сервисы { #prepare-external-services }

Создайте базу данных `agenticos` и пользователя на сервере PostgreSQL с pgvector.
Разрешите учётной записи миграций создать расширение vector или попросите
администратора базы данных установить его заранее. Дайте приложению доступ к его собственной
базе данных, базе Redis и бакету. См. [внешние сервисы и число
подключений](scaling.md).

Создайте бакет до первичной настройки: аватары стартовых агентов тоже используют
файловое хранилище. Настройте шифрование бакета по требованиям провайдера.
`sse-s3` — значение по умолчанию; `storage.encryption: sse-kms` требует ещё и
`storage.kmsKeyId`. Тестовый MinIO без KMS использует `none`; это не указание
отключать шифрование в промышленной эксплуатации.

Через свой менеджер секретов создайте Secret в пространстве имён приложения
**до запуска Helm**. В нём должны быть независимые значения `SECRET_KEY`,
`API_KEY`, `VAULT_MASTER_KEY`, сгенерированные `openssl rand -hex 32`, и
`POSTGRES_PASSWORD`. Сохраняйте эти ключи при обновлениях. Ключ хранилища секретов
нужен, чтобы расшифровывать сохранённые учётные данные организаций; его смена —
это [смена ключа](secrets.md), а не переустановка. Добавьте `REDIS_PASSWORD`,
когда он нужен, и пару `FILE_STORAGE_S3_ACCESS_KEY` /
`FILE_STORAGE_S3_SECRET_KEY` для статических учётных данных S3. Опустите оба
ключа S3, если используете цепочку учётных данных рабочей нагрузки вашего
провайдера.

Чарт ссылается на существующий ServiceAccount с отключённым автоматическим
монтированием токена API. Для идентичности рабочей нагрузки передайте его имя в
`serviceAccountName` и настройте проецируемый токен идентичности и аннотации
провайдера на этой учётной записи. Хуки миграции тоже его используют. Ключи
провайдеров моделей остаются секретами организации в хранилище секретов продукта.

Для `postgres.sslMode: verify-full` (значение по умолчанию) или `verify-ca`
создайте Secret `trust.existingSecret` с ключом `postgres-ca.crt`, содержащим
сертификат CA базы данных. Чарт монтирует его только для чтения в миграцию, API и
воркер и задаёт `PGSSLROOTCERT`. `trust.postgresCaKey` выбирает другое имя файла.
Для закрытого CA Redis добавьте ещё объединённый набор открытых и закрытых CA и
укажите его ключ в `trust.sslCaKey`; он задаёт `SSL_CERT_FILE`. Оставляйте в этом
наборе открытые корневые сертификаты, если провайдеры моделей используют
публичные сертификаты. Другие настройки CA в SDK, например `AWS_CA_BUNDLE`, могут
ссылаться на то же монтирование через `extraEnv`.

## Установка { #install }

Используйте чарт из тега репозитория того релиза, который разворачиваете.
Создайте `cluster-values.yaml`, которым владеет оператор, — с конфигурацией, а не
с учётными данными:

```yaml
existingSecret: agenticos-runtime
public:
  siteUrl: https://app.example.com
  apiUrl: https://api.example.com
  websocketUrl: wss://api.example.com
postgres:
  host: postgres.internal
  database: agenticos
  user: agenticos
  sslMode: verify-full
trust:
  existingSecret: agenticos-trust
  postgresCaKey: postgres-ca.crt
redis:
  host: valkey.internal
  ssl: true
storage:
  bucket: agenticos-files
  region: eu-central-1
  # endpoint: https://s3.example.com
  # pathStyle: true
image:
  tag: "1.80.0"
trustedProxy:
  enabled: true
  namespaceLabels:
    kubernetes.io/metadata.name: ingress-system
  podLabels:
    app.kubernetes.io/name: your-ingress-controller
ingress:
  enabled: true
  className: your-ingress-class
  siteHost: app.example.com
  apiHost: api.example.com
  tls:
    - secretName: agenticos-tls
      hosts: [app.example.com, api.example.com]
```

```bash
helm lint charts/agenticos --strict -f cluster-values.yaml
helm upgrade --install agenticos charts/agenticos \
  --namespace agenticos --create-namespace -f cluster-values.yaml \
  --wait --timeout 15m
kubectl -n agenticos exec deployment/agenticos-agenticos-api -- agenticos cmd bootstrap
```

Прочитайте [Установку](install.md) об учётных данных первичной настройки и
настройке провайдера. Если пространства имён ещё нет, создайте его до создания
Secret для среды выполнения. Задайте `imagePullSecrets` для реестров, требующих
аутентификации. Не применяйте `kubectl
apply` к отрендеренному выводу чарта: он обходит порядок миграций Helm.

Используйте два публичных имени хоста, как в [развёртывании через
Compose](deploy.md#why-two-hostnames). Ingress-контроллер должен поддерживать
обновление соединения до WebSocket, достаточно длинные тайм-ауты простоя и
запросов и размеры загрузки, которые вы разрешаете. Настройте это собственными
аннотациями контроллера; чарт сохраняет `ingress.annotations`. Завершайте TLS
своим существующим Secret с сертификатом или контроллером сертификатов. Операторы
OpenShift могут оставить ingress отключённым и предоставить свои два Routes.

Ограничивайте сетевой трафик политиками кластера: консоль обращается к API; API и
воркер — к Postgres, Redis, S3 и явно настроенным провайдерам или внешним
сервисам. Не открывайте порты базы данных или воркера наружу.

Публичный ingress требует `trustedProxy.enabled: true` и непустых селекторов
меток пространства имён и подов для ingress-контроллера. Замените примеры
селекторов на фактическое защищённое пространство имён и поды контроллера. Это
включает `RATE_LIMIT_TRUST_FORWARDED_FOR` вместе с NetworkPolicies: только этот
контроллер может войти в консоль; API принимает ещё и поды консоли этого релиза.
Используйте CNI, который применяет NetworkPolicy, и не открывайте ни один из
сервисов напрямую. Держите эти пространства имён защищёнными от создания
недоверенных подов. Без применения политик не включайте доверенное
перенаправление.

Настройте ровно один доверенный прокси, который дописывает реального клиента в
`X-Forwarded-For`. Модуль лимита частоты читает самый правый адрес, а консоль сохраняет
этот заголовок при проксировании аутентификации. Если CDN или балансировщик
нагрузки добавляет ещё один переход, нормализуйте проверенный адрес клиента на
своей границе. Smoke-тест через ClusterIP не проверяет выбранный вами
ingress-контроллер или CNI; проверьте их изоляцию и перенаправление, прежде чем
открывать боевой трафик. Внешним Routes и прокси нужны те же настройки
доверенного прокси.

## Учётные данные S3 и устранение неполадок первичной настройки { #s3-credentials-and-bootstrap-troubleshooting }

S3 — это протокол хранилища, а не требование использовать AWS. Для совместимого
сервиса вроде MinIO задайте `storage.endpoint`, `storage.bucket`,
`storage.region`, а также `storage.pathStyle` и требования к шифрованию
провайдера. Собственный API Azure Blob Storage не является эндпоинтом S3;
для этого чарта используйте S3-совместимый сервис.

Поместите статические учётные данные в Secret, указанный в `existingSecret`, с
точными ключами `FILE_STORAGE_S3_ACCESS_KEY` и `FILE_STORAGE_S3_SECRET_KEY`. Поды
API, воркера и миграции загружают этот Secret через `envFrom`. Не кладите ключи в
`storage` или `extraEnv`, в Git или в публичный комментарий при разборе
неполадок. Идентичность рабочей нагрузки должна давать цепочку учётных данных,
понятную клиенту S3; одна идентичность кластера Azure учётных данных S3 не даёт.

`botocore.exceptions.NoCredentialsError` при `agenticos cmd bootstrap` означает,
что клиент S3 не нашёл учётных данных, сохраняя аватар стартового агента.
Транзакция базы данных откатывается; показанная ранее строка «Created owner» не
доказывает, что она зафиксирована. Исправьте Secret, перезапустите API и воркер,
чтобы перечитать переменные окружения, дождитесь готовности и повторите первичную
настройку. Проверяйте существование бакета, доступность эндпоинта, доверие
TLS и права на запись по отдельности. Никогда не выводите значения Secret для
диагностики.

## Установка в OpenShift и каталоги для записи { #openshift-installation-and-writable-directories }

Сначала создайте проект, Secret для среды выполнения и ServiceAccount. Оставьте
имя релиза `agenticos` для команд ниже. Применяйте кандидатную конфигурацию до
значений, специфичных для вашего кластера, и не задавайте в ней UID и группу:

```bash
oc new-project agenticos
helm upgrade --install agenticos charts/agenticos --namespace agenticos \
  -f charts/agenticos/values-openshift.yaml -f cluster-values.yaml \
  --wait --timeout 15m
oc -n agenticos get pods
oc -n agenticos get pods -o 'custom-columns=NAME:.metadata.name,SCC:.metadata.annotations.openshift\.io/scc'
```

Убедитесь, что принятый SCC — это нужная ограниченная политика. Не решайте
проблемы с разрешениями, выдавая `anyuid`, привилегированные SCC или корневую
файловую систему для записи. Фронтенд монтирует записываемые тома `emptyDir` в
`/tmp`, `/app/.next/cache` и `/app/.next/server/route-cache` — туда Next.js
копирует каждую предварительно отрендеренную страницу при первой её отдаче (чарт
`0.1.2`; более старый чарт не может выполнить эту запись при корне только для
чтения). Записываемые монтирования бэкенда объявлены в `templates/_helpers.tpl`.
Не монтируйте поверх всего `/app/.next` или `/app/.next/server`: это скроет
собранное приложение.

С `ingress.enabled: false` предоставьте два HTTPS Routes к Service API и Service
фронтенда этого чарта, оба через именованный порт `http`. Задайте
`public.siteUrl`, `public.apiUrl` и `public.websocketUrl` равными их внешним
адресам. Настройте тайм-ауты маршрутизатора, WebSocket и ограничения загрузки, а
также селекторы защищённого маршрутизатора в `trustedProxy` и реализацию
NetworkPolicy, которая применяет политики. Одно лишь завершение TLS не
обеспечивает правильную обработку перенаправленного клиента.

## Порядок миграций в Argo CD { #argo-cd-migration-ordering }

Argo CD рендерит шаблоны Helm; он не запускает `helm upgrade`. Его [сопоставление
хуков Helm](https://argo-cd.readthedocs.io/en/stable/user-guide/helm/#helm-hooks)
превращает Job миграции с `pre-install` и `pre-upgrade` этого чарта в `PreSync`;
`before-hook-creation` разрешает ещё одну попытку при следующей синхронизации.
Подготовьте пространство имён, Secrets и ServiceAccount **до** этой фазы — вне
этого Application или в более ранней завершённой операции первичной настройки.

Используйте полную синхронизацию Application и убедитесь, что Job миграции
завершается успешно, прежде чем изменится хоть один Deployment. Выборочная
синхронизация пропускает хуки. Добавление аннотаций хуков Argo CD меняет
обработку хуков Helm; не смешивайте схемы жизненного цикла, не проверив
результат. Держите имя Application равным имени релиза Helm, если только вы
намеренно не настроили отслеживание ресурсов Argo CD так, чтобы сохранять
селекторы экземпляра этого чарта.

Откат в Git — не откат базы данных. Argo CD не реализует хук `pre-rollback` Helm;
полная синхронизация старого чарта идёт своим путём PreSync. Докажите отказ
при неудавшейся миграции, успешное обновление и совместимый откат на своей
фактической версии Argo CD, прежде чем включать автоматическую синхронизацию. Не
запускайте Helm и Argo CD как конкурирующих владельцев одного релиза.

Для OpenShift загрузите конфигурацию как **файл значений** Helm в Argo CD:

```yaml
helm:
  releaseName: agenticos
  valueFiles:
    - values-openshift.yaml
```

Это конфигурация `spec.source.helm` для пути исходников `charts/agenticos`;
добавьте туда свои несекретные настройки кластера и ссылки на существующие
Secret, как выше. Не полагайтесь на `null` во встроенном `valuesObject`, чтобы
убрать UID по умолчанию или `fsGroup`. В локальном тесте такие `null` не доходили
до Helm как задумано; загрузка файла конфигурации устранила отказ SCC для UID и группы
1000, не расширяя разрешения.

Локальный Argo CD Core 3.6.1 прошёл начальную полную синхронизацию, отказ PreSync
при неудавшейся миграции с неизменёнными спецификациями Deployment, обновление
конфигурации консоли и совместимый откат ревизии Git на той же схеме базы данных.
Его контроллер имел право записи только в пространстве имён проверки и использовал
[`resource.respectRBAC: strict`](https://argo-cd.readthedocs.io/en/stable/operator-manual/declarative-setup/).
Ему не выдавали `anyuid` или привилегированный SCC. Это не проверяет оператор Red
Hat OpenShift GitOps или понижение версии базы данных.

## Настройка OIDC и песочницы { #oidc-and-sandbox-configuration }

Локальная настройка OIDC сохраняет установленные Helm теги и дайджесты образов
и для бэкенда, и для консоли; настройка входа не выбирает другой образ приложения.

Задайте несекретные настройки OIDC бэкенда в `extraEnv` верхнего уровня, положите
`OIDC_CLIENT_SECRET` в `existingSecret` и отдельно включите кнопку входа:

```yaml
extraEnv:
  OIDC_ISSUER: https://identity.example.com/realms/company
  OIDC_CLIENT_ID: agenticos
  OIDC_REDIRECT_URI: https://api.example.com/api/v1/oauth/oidc/callback
frontend:
  extraEnv:
    OAUTH_PROVIDERS: oidc
    OIDC_DISPLAY_NAME: Company SSO
```

`frontend.extraEnv` доступен начиная с версии чарта `0.1.1`; более старые чарты
его игнорируют. В нём публичные настройки консоли, но никогда не секрет клиента.
Управляемые чартом адреса бэкенда и публичные адреса имеют приоритет над
повторяющимися ключами окружения фронтенда. Зарегистрируйте точный адрес
обратного вызова у провайдера идентичности. Проверьте кнопку, перенаправление,
обратный вызов, утверждение о подтверждённом адресе эл. почты, доступ к
организации, выход и ограничения регистрации экземпляра. См. [общий
OIDC](configuration.md#single-sign-on-generic-oidc) о том, какие утверждения и
настройки нужны конкретному провайдеру. Прошедший smoke-тест входа по паролю не
проверяет SSO.

Для инструментов песочницы запускайте отдельный сервер OpenSandbox и
зарегистрируйте его URL, образ и ключ хранилища секретов в разделе **Настройки →
Песочницы → Подключения** (Settings → Sandboxes → Connections). Базовый чарт его
не устанавливает. Локальная проверка OpenShift использовала
server/controller/execd/gateway 1.2.1, провайдер Kubernetes BatchSandbox и Secure
Access. Настоящий инструмент записал файл, а следующий ход диалога снова
подключился и прочитал его; проверка подключения задействовала оболочку POSIX. Это
проверяет аутентификацию эндпоинта и ограниченную рабочую нагрузку, но не gVisor,
изоляцию виртуальных машин, политику исходящего трафика, использование браузера
или рендеринг.

Чарт сервера 1.2.1 от поставщика открывает порт контейнера 80. Для этого
ограниченного теста `configToml` использовал `server.port = 8080`, а
`scripts/kubernetes/opensandbox_ports.py` менял именованный порт HTTP контейнера
на 8080, сохраняя ссылки Service и проверок. Используйте этот исполняемый
пост-рендерер с Helm 3 (проверен на 3.22.1); Helm 4 требует плагин
пост-рендеринга. Шаблон рабочей нагрузки монтировал закрытые тома `emptyDir` в
`/workspace` и `/tmp` и оставлял назначение UID и группы за SCC. Secure Access
использовал закрытый шлюз и отдельный Secret для связки ключей. Это настройки
провайдера, а не значения чарта AgenticOS.

**Для очистки нужно исправление удаления диалогов из этого изменения.** В выпуске
1.80.0 ссылки на рабочие пространства удалялись раньше, чем удалённое
уничтожение ставилось в очередь. Обработчик из этого изменения проверен на этом
образе: удаление диалога удаляло песочницу и под провайдера. Не выводите наличие
этого исправления из одного тега образа. Просмотр и скачивание файлов OpenSandbox через API архива
рабочего пространства в консоли не реализованы; файловые инструменты агента —
отдельный путь. См. [конфигурацию песочницы](sandbox.md).

Удаление авторизует доступ, блокирует диалог и снова проверяет доступ, прежде чем
удалить строки рабочего пространства. Так удаление учётной записи и очистка
рабочего пространства идут в одном порядке блокировок — сначала родитель.
Ожидающее уничтожение и его передача после фиксации транзакции сохраняют защиту
от отката.

## Работоспособность, хранилище и ёмкость { #health-storage-and-capacity }

API опрашивает `/api/v1/health/live` для проверки при старте и «жив ли процесс», а
`/api/v1/health/ready` — для готовности базы данных и Redis. Проверки воркера
смотрят на его файл сигнала активности в базе данных; проверки при старте и
готовности консоли используют `/login`, а «жив ли процесс» проверяет её слушающий
сокет. Из-за медленного провайдера проверка «жив ли процесс» не проваливается.
Каждой рабочей нагрузке даётся 60 секунд на остановку; воркер перестаёт брать
задачи, дорабатывает текущие и возвращает их в очередь.

Ресурсы задаются отдельно в `api.resources`, `worker.resources`,
`frontend.resources` и `migration.resources`. Рассчитывайте ресурсы воркера
с учётом всех настроенных дочерних процессов индексации: их память добавляется
к памяти родительского процесса. Согласуйте `extraEnv.WORKER_INGEST_CHILDREN` и
`extraEnv.WORKER_INGEST_MEMORY_MB` с лимитом пода. Масштабируйте через
`api.replicas`, `worker.replicas` и `frontend.replicas`; учитывайте пул
подключений к базе данных каждого процесса, прежде чем добавлять реплики.

Файлы хранятся в S3; воркер скачивает каждую индексацию в собственную временную
копию. Общая файловая система или том RWX не нужны. Каталоги кэша и промежуточных
файлов — ограниченные тома `emptyDir`. Их потеря ожидаема; это не резервные
копии. Принудительно завершённый процесс индексации может оставить временный
файл, пока не заменят его под; обычное завершение, сбои парсера и отмена удаляют
копию воркера.
Источники синхронизации из локальных каталогов должны быть доступны из воркера,
который их выполняет; этот чарт не монтирует каталоги оператора в поды.

## Обновление и откат { #upgrade-and-rollback }

Перед обновлением сделайте резервную копию Postgres, S3 и ключей среды
выполнения. Изучите примечания к выпуску и совместимость миграций и со старым, и с
новым приложением. Job с `pre-install` или `pre-upgrade` запускает
`agenticos db upgrade`; его сбой не даёт Helm изменить Deployment. Неудавшиеся Job
остаются для диагностики:

```bash
kubectl -n agenticos logs job/agenticos-agenticos-migrate
helm history agenticos -n agenticos
```

Сохраните журналы до повторной попытки: следующий хук удаляет Job предыдущего
хука. Не запускайте одновременные обновления одного релиза, не используйте
`--no-hooks` и не запускайте поды вручную после неудавшейся миграции. Частично
применённая миграция всё равно требует оценки оператора; Helm не может обратить
побочные эффекты в базе данных.

Обновления без простоя требуют совместимости схемы и задач в очереди, пока старые
процессы работают. При несовместимом изменении остановите входящий трафик,
доработайте активные задачи, сведите масштаб всех трёх Deployment к нулю, сделайте
резервную копию и затем обновитесь в окне обслуживания. Проверьте готовность и
настоящий запуск агента, прежде чем снова открыть трафик.

При первом обновлении до 1.63.0 в существующем развёртывании с S3 дождитесь
завершения текущей индексации и замените воркеры до обновления API или используйте
окно обслуживания. Новые процессы API больше не пишут общие временные копии, которых
ждут старые воркеры. Локальное файловое хранилище сохраняет свой контракт общего
каталога.

`helm rollback agenticos REVISION -n agenticos --wait --timeout 15m` восстанавливает
старую версию приложения, только если её хук миграции принимает текущую базу
данных. Базу данных он **не** понижает. Если старый образ не распознаёт новую
ревизию, его хук `pre-rollback` отклоняет откат до замены подов. Восстановите
подходящую резервную копию базы данных и совместимые объекты и ключи как
осознанную операцию восстановления, когда этого требуют примечания к выпуску.
`helm uninstall` удаляет приложение; внешние базы данных, бакет и Secret среды
выполнения остаются за оператором.

## Локальная проверка и приёмка { #local-validation-and-acceptance }

Обе платформы можно проверить локально, но им нужны отдельные кластеры. Для
Kubernetes используйте kind, для настоящего OpenShift — [OpenShift Local
(CRC)](https://crc.dev/docs/getting-started/). Установка `oc` в кластер kind не
добавляет SCC или Routes. CRC поддерживает Apple silicon для профиля OpenShift; его
профиль OKD — нет. [Текущие минимальные требования](https://crc.dev/docs/installing/)
для OpenShift — четыре физических ядра CPU, 10,5 ГБ свободной памяти и 35 ГБ
диска, не считая дополнительной ёмкости для приложения. Не запускайте оба
кластера одновременно на маломощном ноутбуке.

Smoke-тест Kubernetes создаёт одноразовые фикстуры pgvector, Valkey, MinIO и
протокола модели; ему не нужны ни учётная запись AWS, ни платный ключ модели.
Закрепите проверяемый релиз через `SMOKE_IMAGE_TAG`, который выбирает оба образа.
`SMOKE_BACKEND_IMAGE` и `SMOKE_FRONTEND_TAG` переопределяют соответствующий образ
при проверке сборок из исходников.

```bash
python3 scripts/kubernetes/test_chart.py
SMOKE_IMAGE_TAG=1.80.0 scripts/kubernetes/run-smoke.sh
```

Автоматическая проверка консоли подтверждает только конфигурацию отображения
OIDC; она не обращается к провайдеру идентичности. Фикстура модели проверяет
протокол запуска, а не реальное качество модели. Smoke-тест использует
перенаправление портов ClusterIP, поэтому не проверяет публичный TLS, WebSockets
через маршрутизатор, применение CNI или Argo CD.

Для OpenShift Local установите CRC от Red Hat, получите собственный pull secret,
затем подготовьте и запустите профиль OpenShift на хосте:

```bash
crc config set preset openshift
crc setup
crc start --cpus 6 --memory 13312 --disk-size 45 \
  --pull-secret-file /path/to/pull-secret
```

`crc setup` настраивает сеть и виртуализацию хоста и может потребовать прав
администратора. Следуйте инструкциям CRC по входу с отдельным kubeconfig.
Проверьте выбранный кластер, прежде чем его менять. Подготовьте доступные внешние
сервисы данных, Secrets и ServiceAccount, как выше, затем установите с профилем
OpenShift. Не применяйте фикстуры зависимостей kind к OpenShift вместо проверки
зависимостей, совместимых с ограниченной политикой. По завершении остановите
локальный кластер через `crc stop`.

Запишите дайджесты образов, ревизию чарта, версии кластера и Argo CD, принятый
SCC, команды, результаты и журналы сбоев с вырезанными чувствительными данными.
Прежде чем утверждать, что этот путь развёртывания работает, проверьте:

- Миграция завершается до изменения рабочих нагрузок; намеренно неудачная
  миграция не даёт развернуть новую версию. Совместимое обновление и откат
  сохраняют данные.
- API, воркер и консоль остаются готовы под нужной ограниченной политикой;
  навигация фронтенда и загрузки бэкенда не дают ошибок файловой системы только
  для чтения.
- Первичная настройка, вход, ответ агента, загрузка, индексация и фоновая задача,
  переживающая перезапуск, работают.
- Оба публичных адреса HTTPS, WebSockets, ограничения загрузки, перенаправление и
  сетевая изоляция работают через фактический ingress или Routes.
- OIDC проходит у выбранного провайдера идентичности с нужными утверждениями и
  ограничениями регистрации; файлы песочницы переживают ходы, а очистка удаётся.
- Если используется Argo CD, повторите установку, неудавшуюся миграцию,
  обновление и откат полными синхронизациями, а не считайте запуск Helm проверкой
  GitOps.

Успешная локальная проверка OpenShift — это подтверждение для той версии и
конфигурации. Идентичность Azure, сеть Azure, драйверы хранилища и настройка Argo
CD пользователя всё ещё требуют проверки в этом окружении. Сообщайте о неполных
пунктах как о непроверенных, а не как о пройденных.

### Измеренная локальная проверка OpenShift { #measured-local-openshift-validation }

Базовый запуск прошёл первичную настройку, вход, детерминированное выполнение
агента, загрузку в S3, индексацию воркером через pgvector и фоновую задачу,
переживающую перезапуск. Helm отказался продолжать при неудавшейся миграции, не
меняя спецификации Deployment; обновление и совместимый откат на той же схеме
прошли.
Проверенные HTTPS Routes прошли вход через BFF консоли, cookie Secure/HttpOnly,
серверный рендеринг страниц и аутентифицированное обновление и ping по WSS.
Недоверенное пространство имён не смогло подключиться напрямую ни к одному из
защищённых сервисов. Это не измеряет цепочки перенаправления реальных клиентов или
максимальные размеры загрузки.

Keycloak 26.8.2 прошёл discovery, PKCE, проверку подписанного токена, одноразовый
обмен кода консоли, доступ к организации и отзыв при выходе и обновлении через TLS
Routes. Неподтверждённая эл. почта, запрещённый домен и регистрация только по
приглашению были отклонены. Это подтверждение общего OIDC, а не проверка Microsoft
Entra или Azure. Проверки серверного рендеринга страниц не заменяют интерактивную
навигацию по каждому экрану.

Базовому запуску потребовались **6 CPU, 13 ГиБ памяти виртуальной машины и
виртуальный диск на 45 ГБ**. Минимум CRC в 10,5 ГБ не позволял разместить поды
миграции с этими фикстурами. Дополнительные интеграции запускались поэтапно:
SDK песочницы требует 2 ГиБ на рабочее пространство. Планируйте дополнительную
ёмкость и запас для обновления без простоя; 13 ГиБ — подтверждение для этой
базовой фикстуры, а не рекомендация по размеру для промышленной эксплуатации.

После запуска CRC используйте Python с PyYAML, `oc`, `helm` и отдельным kubeconfig:

```bash
export KUBECONFIG="$HOME/.crc/machines/crc/kubeconfig"
scripts/kubernetes/run-openshift-smoke.sh
python3 scripts/kubernetes/local_integrations.py --kubeconfig "$KUBECONFIG" routes
python3 scripts/kubernetes/local_integrations.py --kubeconfig "$KUBECONFIG" oidc
```

Базовый скрипт проверки отклоняет существующие пространства имён проверки;
помощник для интеграций требует их меток владения и отклоняет API, не являющийся
CRC. Он сохраняет одноразовые пространства имён и закрытые временные артефакты для
осмотра. `sandbox_probe.py` требует отдельно подготовленного набора провайдера,
соответствующего конфигурации выше; базовый скрипт его не устанавливает. После
осмотра удалите только созданные вами пространства имён и ресурсы провайдера,
удалите указанный каталог временных сертификатов и затем остановите CRC. Держите
свой pull secret в тайне.

## Воспроизведите тест { #reproduce-the-test }

Установите Docker, kubectl 1.37.0, kind 0.33.0, Helm 4.3.1 и Python с PyYAML. Из
корня репозитория запустите `python3 scripts/kubernetes/test_chart.py`, затем
`scripts/kubernetes/run-smoke.sh`. Последний создаёт и удаляет собственный кластер
kind, использует отдельный kubeconfig и отказывается заменять существующий
кластер. Он никогда не использует ваш текущий контекст Kubernetes. Ему нужны
свободные порты 18000/13000.

До первого выпуска приложения с этим изменением соберите бэкенд из исходников и
задайте `SMOKE_BACKEND_IMAGE=agenticos-smoke-backend:ci` и
`SMOKE_FRONTEND_TAG=1.62.8`, как это делает рабочий процесс GitHub Actions для
Kubernetes. Скрипт также проверяет неудавшуюся миграцию, успешное обновление,
откат на той же схеме и развёртывание с произвольным UID. Его фикстуры баз данных
и бакет S3 — одноразовые одноузловые тестовые сервисы, а не манифесты баз данных
для промышленной эксплуатации. CI записывает версии инструментов и идентификаторы
образов в журнал запуска. `SMOKE_KEEP_CLUSTER=true` сохраняет неудавшийся тестовый
кластер для осмотра; удалите его потом явно командой `kind delete cluster --name
agenticos-smoke`.

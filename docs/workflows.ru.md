# Сценарии { #workflows }

Выберите значок сценария рядом с его именем в редакторе. Та же нейтральная плитка
появляется в каталоге. Выбранный значок сохраняется при перезагрузке; **Использовать
значок по умолчанию** (Use default icon) сбрасывает его. Это меняет метаданные
оформления, а не ревизию черновика или опубликованный граф.

**Сценарий** связывает шаги в автоматизацию, которую выполняют ваши агенты:
прочитать [таблицу](virtual-tables.md), вызвать агента, ветвиться по результату,
пройти циклом по списку. Вы строите его на холсте, соединяете шаги и публикуете как
неизменяемую версию — той же формы, что и [агент](concepts.md): черновик, который вы
правите, и опубликованная версия, которая выполняется.

Эта страница описывает визуальный редактор: список, холст и выбор шагов, настройку
узла, автосохранение и публикацию, а также клавиатурные пути через всё это. Редактор
находится в разделе **Сценарии** (Workflows) консоли. Страница **списка** сценариев
несёт **«?»**, который заново проигрывает экскурсию по этому списку; в самом
редакторе экскурсии нет.

## Создание и дублирование сценария { #creating-and-duplicating-a-workflow }

**Новый сценарий** (New workflow) спрашивает имя и то, кто может им пользоваться, тем
же выбором аудитории, что и при создании агента: все, только вы или выбранные люди и
отделы. Выберите стартовый триггер, при желании добавьте описание и метки, затем
нажмите **Создать** (Create). Выбор триггера сам по себе никогда не создаёт сценарий.
**Шаблоны сценариев** (Workflow templates) — отдельная галерея категорий; выбор
шаблона открывает эту форму с уже заполненными именем и описанием.

Чтобы изменить, кто имеет доступ к существующему сценарию, откройте его и выберите
**Ещё → Настройки → Доступ** (More → Settings → Access). В разделе **Общий доступ**
(General access) выберите **Только люди с доступом** (Only people with access) или
**Все в организации** (Everyone in the organization). Если вы можете править сценарий,
здесь же можно добавлять и убирать выданные доступы для людей и групп. Переключение на
закрытый доступ сохраняет явные выданные доступы. Люди, чья роль достаёт только до
общих сценариев, могут потерять доступ; роли, достающие до всех сценариев, его
сохраняют. Общий доступ управляет и доступом к прошлым запускам; он не приостанавливает
расписания и не отключает вебхуки.

Каталог держит карточки и поиск в одной панели. **Фильтры** (Filters) показывают
статус, метки и сортировку вместе с числом активных фильтров. При неудачной загрузке
предлагается **Повторить** (Retry) вместо пустого каталога. Импорт начинается с выбора
файла; **Или вставьте JSON файла здесь** (Or paste the file's JSON here) открывает поле
с подписью.

Список показывает каждый видимый вам сценарий карточкой: его статус, кто до него
достаёт, есть ли действующая версия и когда его последний раз правили. **Фильтр по
статусу** (Filter by status) сужает список до **Черновиков** (Drafts), которые вы ещё
строите, **Опубликованных** (Published), которые выполняются, или **В архиве**
(Archived). С карточки вы открываете редактор, запуски сценария или копию.

**Дублировать** (Duplicate) копирует текущий черновик сценария в новый с именем
*{name} (копия)*. Дубликат — это новый сценарий со своим черновиком, никогда не копия
опубликованной версии.

!!! info "Пустой список может быть фильтром, а не пустой организацией"

    **Сценариев пока нет** (No workflows yet) и **Ничего не найдено** (Nothing
    matches) — разные состояния: первое — организация, где их нет, второе — фильтр
    по статусу, под которым нет строк. **Сбросить фильтр** (Clear filter) возвращает
    полный список. Сценарий, которым с вами поделились, появляется в том же списке,
    как только у вас есть `workflows:view`.

### Шаблоны, экспорт и импорт { #templates-exporting-and-importing }

Шаблоны с таблицами — **Публичный API → таблица** (Public API → table) и **Блокнот
Markdown** (Markdown notebook). Сервер готовит таблицу и полностью настроенный
черновик в одной транзакции. Шаблоны начинаются закрытыми; явная аудитория
применяется и к сценарию, и к его таблице. Ни учётная запись, ни API-ключ, ни выбор
таблицы не нужны. Первый берёт образец публикации с
[JSONPlaceholder](https://jsonplaceholder.typicode.com/) и сохраняет её заголовок и
текст; второй пишет заметку в Markdown. Последующие запуски переиспользуют таблицу и
вставляют или обновляют ту же примерную запись. Для их создания нужно разрешение
создавать и править таблицы. **Базовый сценарий** (Starter) и **Последовательность из
двух шагов** (Two-step sequence) остаются небольшими локальными примерами.

**Дождаться ответа** (Await a reply) запускает закрытый ручной сценарий для
подключённого почтового ящика Gmail или Outlook, который вы явно выбираете при
создании. Ему не нужны ни разрешение на таблицы, ни модель, ни учётные данные
отправителя сверх уже имеющегося доступа на чтение. Опубликуйте черновик, затем
**Запустить** (Run) спросит идентификатор цепочки у провайдера, точного отправителя,
метку времени начала и срок (ISO 8601 с часовым поясом). Подтверждённый ответ
завершает сценарий через ветвь ответа; иначе успешная финальная проверка почты пишет
одно напоминание создателю — просмотреть цепочку и подготовить последующее письмо.
Последующее письмо никогда не отправляется автоматически.

Для Outlook форма создания может также указать общий почтовый ящик, который
подключённая учётная запись вправе читать.

Уведомление по умолчанию — внутри приложения. Его шаг **Уведомить участников** (Notify
members) может выбрать другие поддерживаемые каналы уведомлений с учётом предпочтений
каждого получателя и согласия на закрытые каналы.
[Шаг ожидания ответа](reference/workflow-nodes.md#flow-await-reply) сохраняет семантику
сопоставления, паузы и исправления, отмены и крайнего срока.

История запусков по умолчанию занимает доступную площадь страницы, без элемента
разворачивания. Каталог занимает доступную площадь страницы и предлагает собственный
элемент «Во весь экран». Постраничный переход появляется, только когда есть другая
страница. Импорт файла имеет область загрузки с подписью, которая принимает выбор
файла или перетащенный JSON-файл.

История запусков держит постраничный переход внизу своей панели. Подробности запуска —
это компактная сводка, холст, занимающий рабочее пространство, и одна боковая панель с
шагами, выводом и доступными файлами. Нажмите на шаг, чтобы посмотреть записанные им
данные. У импорта файла и импорта вставленного JSON отдельные вкладки; у вставленного JSON
есть поле кода и действие форматирования, которое сообщает о некорректном JSON, не
отбрасывая его.

**Экспортировать сценарий** (Export workflow) — в меню **Ещё** (More) в шапке
редактора — выгружает черновик в файл `.workflow.json`. Файл не несёт идентификаторов
этого экземпляра: каждый выбранный шагом агент, таблица, секрет, участник, бот или
сценарий опускается и перечисляется, закреплённые тестовые данные опускаются, как и
сценарий ошибок. Значение секрета в нём не хранится никогда. **Импорт** (Import) в
списке создаёт из такого файла новый черновик, убирает любые идентификаторы, которые
всё ещё называет файл, сделанный вручную, и перечисляет каждый шаг и поле, чтобы выбрать их
заново перед публикацией. Файл с шагом, которого в этом экземпляре нет, отклоняется, и
ничего не создаётся.

### Поиск, имя и вывод из работы { #finding-naming-and-retiring-a-workflow }

Каждая карточка говорит, что запускает сценарий, сколько в нём шагов, действующий он
или черновик, а также как прошёл его последний запуск и когда — дату правки, пока он
ни разу не запускался.

Над карточками поиск находит сценарий по имени, описанию или меткам, фильтр по метке
сужает список до одной метки, а порядок — последнее изменение, имя или сначала новые.
Всё это хранится в адресе, поэтому перезагрузка или общая ссылка показывают тот же
список.

**Ещё → Настройки** содержит имя сценария, описание, метки и настройки выполнения,
сохраняемые автоматически. Редактор шага занимает доступное окно: **Вход** (Input)
слева, **Параметры** (Parameters) и **Настройки** (Settings) в середине, **Вывод**
(Output) справа. Триггеры используют две панели, потому что входящих данных у них нет. Каждая
панель прокручивается независимо на больших экранах; на телефонах — одна прокручиваемая
колонка. Записанные выполнения показывают параметры только для чтения рядом с их
данными. Значения записей — это поля, названные по столбцам таблицы. Заметки предлагают
**Открыть заметку** (Open note), готовые размеры и ручки изменения размера.

Выбор приложений включает MCP-серверы из каталога ещё до подключения; его общая строка
«Вызвать инструмент MCP» скрыта, а серверы, которые никто не подключил, ждут под
**Другие приложения для подключения** (more apps to connect) в конце своего раздела.
Подключите службу на месте, затем выберите один из найденных у неё инструментов. Список
разрешённых для подключения инструментов по-прежнему действует.

Холст начинается с цветных шагов и мини-карты. На телефоне он открывается со всем
потоком в поле зрения и скрытой мини-картой; **Параметры холста** (Canvas options) снова
её показывают.

Шаги модели ИИ показывают инструкции, температуру и глубину рассуждений; незаданные
элементы управления сохраняют умолчания провайдера. Шаги группы **Модели решений**
(Decisions), на которые отвечает модель решений Jev, показывают свою модель, вопрос и порог уверенности.
**Отправить письмо** (Send an email) использует отправителя платформы либо подключает Gmail или Outlook и
после подтверждения переключается на фактический MCP-инструмент этого ящика.
Переключение очищает несовместимые привязки входных данных, и его можно отменить.

Шаг **Отправить письмо** (Send an email) также предлагает **Учётная запись SMTP → Новая
учётная запись SMTP** (SMTP account → New SMTP account). Введите сервер, порт, имя
пользователя, пароль и отправителя в диалоге хранилища. STARTTLS обычно использует 587;
неявный TLS обычно использует 465, с проверкой сертификата в обоих режимах. В сценарии
хранится только `smtp_secret_id`. Выберите **Отправитель платформы** (Platform sender),
чтобы очистить его. Публикация и выполнение требуют доступа к секрету; недоступная
учётная запись даёт сбой, а не молча меняет отправителя.

HTTP-запрос, загрузка и скачивание используют общую панель **Аутентификация**
(Authentication): без аутентификации, Bearer, API-ключ в заголовке, API-ключ в параметре
URL или Basic Auth. Выберите существующие учётные данные **HTTP** в хранилище или
создайте их на месте; разрешённый источник подсказывается по URL шага. Сценарий хранит
только `auth.secret_id`. Собственные имена заголовков и необязательные префиксы
поддерживают такие API, как `Authorization: Token …`. Basic Auth использует имя
пользователя и токен учётных данных из хранилища как своё имя пользователя и пароль.
Переключение методов очищает несущественные настройки, сохраняя выбранную ссылку;
отключение аутентификации очищает ссылку.

Поиск приложений ищет и в зеркальном реестре MCP, включая службы, ещё не подключённые.
Подключённый сервер без списка инструментов предлагает **Обновить инструменты** (Refresh
tools) тем, кто управляет подключениями. Шаги каналов могут создавать и выбирать
учётную запись бота прямо на месте; это действие видят только участники, которым
разрешено управлять каналами.

Архитектор может просматривать каталог узлов, создавать и править закрытые черновики
сценариев, проверять их и смотреть результаты запусков. Он также создаёт типизированные
виртуальные таблицы и запрашивает или обновляет записи. Его навыки построения сценариев
и виртуальных таблиц объясняют, когда пользоваться этими возможностями. Если службы нет
в галерее MCP, Архитектор может обернуть её документированный API шагом HTTP-запроса и
открыть опубликованный вызываемый сценарий через MCP-сервер AgenticOS. Учётные данные
остаются в хранилище. Проверки могут выполнять настоящие действия, а публикация для
запусков без участия человека по-прежнему требует сеанса человека.

Под своим именем редактор показывает, в каком состоянии сценарий: **Черновик, не
опубликован** (Draft, not published) или **Действует · версия 3** (Live · version 3), а
рядом — **Неопубликованные изменения** (Unpublished changes), как только черновик
отличается от этой версии в том, что перенесла бы публикация. Перемещение шага или
закрепление тестовых данных не считается.

У опубликованного сценария, чей триггер запускается сам — вебхук, расписание или новая
запись таблицы, — в шапке редактора есть переключатель **Активен** (Active), и его
карточка говорит **Активен** или **На паузе** (Paused). Выключение сразу приостанавливает
триггер; включение возобновляет его от имени публикующего, поэтому для этого нужно
разрешение запускать сценарий. Меню **...** на карточке архивирует сценарий, что тоже
приостанавливает его триггер. Архивированный можно восстановить — по-прежнему на
паузе — или удалить вместе с версиями, запусками и общими доступами; сценарий, чьи
запуски не закончились, отклоняется с `WORKFLOW_IN_USE`.

Шаги агента держат закрытые диалоги для своей истории модели и рабочих пространств,
ограниченных диалогом. Ходы чата переиспользуют один и тот же контекст шага; видимый чат
получает результат сценария и любые вопросы агента. Тестовые чаты имеют изолированные
сеансы, и новый тестовый чат сбрасывает этот контекст. Эти внутренние диалоги
отсутствуют в списке чатов и удаляются вместе со своим сценарием или исходным чатом.

Шаг агента может вызвать `ask_user_question`, чтобы встать на паузу в состоянии
**Ожидает ответа пользователя** (Waiting for user). Ответьте на его карточку вопроса в
исходном чате или на странице запуска. Ваш ответ завершает ожидающий вызов инструмента,
и воркер сценария возобновляет тот же диалог агента. Агент может спросить снова, прежде
чем вернуть окончательный результат. Другие независимые ветви могут продолжаться, пока
этот шаг ждёт.

Агенты, вызванные из сценариев, могут пользоваться своими MCP-инструментами AgenticOS и
в фоновом воркере, и в веб-чате.

## Холст и добавление шагов { #the-canvas-and-the-palette }

После нажатия **Проверить черновик** (Test draft) холст показывает статус запуска и
число выполненных шагов. **Открыть запуск** (Open run) показывает его подробности. На узких
экранах строка состояния переносится внутри холста, чтобы ссылка и кнопка закрытия
оставались доступны.

Редактор держит видимыми **Запуски** (Runs), **Проверить черновик** и **Опубликовать**
(Publish). В **Ещё** (More) находятся **Версии** (Versions) и переключатель правки и
просмотра. **Параметры холста** (Canvas options) содержат мини-карту, стиль связей и
сочетания клавиш. Шаг без входящей связи оставляет больше места параметрам,
пропуская пустую панель входных данных; **Ожидаемые поля вывода** (Expected output fields)
разворачивают схему вывода. **Просмотреть настройку перед проверкой** (Review setup before
testing) открывает незавершённую настройку.

**Холст** — это место, где появляются шаги сценария и их связи, и он занимает всю
ширину редактора под шапкой. **Узел** — это один шаг; **связь** — это соединение, задающее
порядок: шаг, на который она указывает, выполняется после того, от которого она идёт.

Каждый узел — это карточка со значком шага, его именем и одной строкой под ним: сначала
агент, модель или таблица, с которыми он работает, затем что он настроен делать —
условие, URL, число сопоставленных полей. Шаг с несколькими выходами перечисляет свои порты по
именам: **true** и **false**, **Готово** (Done) у цикла и красный порт **Ошибка** (Error)
у шага, который обрабатывает свои ошибки. Шаг, который останавливает публикацию, несёт
отметку настройки (красную после проверки или публикации): наведение перечисляет первые
пункты, а нажатие открывает шаг.

Тачпад или колесо мыши двигают холст, а щипок — или Ctrl либо Cmd с колесом — меняет его
масштаб; его элементы управления стоят в углу.

Шаги выбираются в **выборе шагов**. Он перечисляет разделы — **Старт** (Start), **ИИ**
(AI), **Поток** (Flow), **Данные** (Data), **Приложения и интернет** (Apps and the web) —
с группами под каждым. Группа вроде **Slack**, **Таблицы** (Tables) или **Решения**
(Decisions) раскрывается в свои шаги, а группа из одного шага и есть этот шаг.
**Поиск шагов** (Search steps) находит любой шаг по имени, по тому, что он делает, или
по его группе. Добавить шаг можно четырьмя способами:

- **+** в левом верхнем углу холста — или **Добавить шаг** (Add step) посреди пустого
  холста — открывает выбор. Шаг встаёт после выбранного шага или в конце видимого
  потока, соединённый с ним, если их порты подходят. Стартовый шаг встаёт перед текущим
  стартом и становится им.
- **+** возле выхода шага открывает выбор для шага, который идёт после этого выхода.
  Когда выход уже ведёт к шагу, выбор спрашивает, куда идёт новый: **Вставить перед**
  (Insert before) этим шагом вставляет его в связь, а **Добавить параллельную ветвь**
  (Add a parallel branch) сохраняет связь и выполняет новый шаг рядом. Выход,
  который уже ведёт к нескольким шагам, может принять только ещё одну ветвь.
- **Правый щелчок** по холсту: тот же выбор открывается там, где вы щёлкнули, и шаг
  встаёт туда. Под ним — **Добавить заметку** (Add a note) и, как только что-то
  скопировано, **Вставить** (Paste).
- **Перетаскивание** шага из выбора ставит его туда, куда вы его бросили, ни к чему не
  подсоединяя.

Приложения Google Workspace (**Gmail**, **Google Calendar**, **Google Drive**, **Google
Docs**, **Google Sheets**) и Microsoft 365 (**Outlook**, **Outlook Calendar**,
**OneDrive**, **Excel**) — отдельные группы в **Приложения и интернет**. В каждой — родной
триггер приложения, если холст может его взять, и по одной строке на инструмент каждого
подключения MCP организации к соответствующему серверу, например **Создать черновик**
(Create draft) или **Отправить сообщение** (Send message). Инструменты подключения
разложены по этим группам по имени; инструмент, который не забрала ни одна из них,
остаётся в собственной группе сервера (**Google Workspace**, **Microsoft 365**), где
также показываются **Подключить** (Connect) и непроверенное подключение. Инструменты
входа (`start_google_auth`, `login`, `verify-login`) не предлагаются.

Выбор строки добавляет [вызов MCP](reference/workflow-nodes.md#mcp-call) уже настроенным
на это подключение и инструмент, поэтому сохранённые сценарии и контракт узла не
меняются. Строка никогда не скрывает, чем она является: она несёт значок **MCP** и имя
подключения, а собственное имя инструмента стоит отдельной строкой под ним, причём
сервер назван один раз в заголовке группы; ничего не обрезается.

**Поиск шагов** находит его по любому из имён или по приложению. На холсте шаг читается
как **Gmail · Создать черновик** со значком **MCP**, с подключением и собственным именем
инструмента под ним, а его настройки говорят, что это вызов MCP-инструмента на этом
подключении, и ведут к нему. У каждого инструмента Gmail, который предлагает сервер,
есть простое имя, например **Список меток** (List labels) или **Прочитать цепочку**
(Read thread); инструмент, которого нет в списке, показывает своё имя. Родной триггер не
является вызовом MCP и не несёт значка.

Без подходящего подключения собственная группа сервера показывает строку, чтобы
**Подключить** сервер. Перечисляются только подключения организации, а инструменты
подключения — те, что записала его последняя проверка, поэтому проверьте его снова,
чтобы увидеть новые. Участник, которому нельзя править сценарий, видит одни триггеры.
Участник, который правит сценарий, но не управляет MCP-серверами, видит каждое действие
и не получает строку **Подключить**: сервер подключает только тот, кто им управляет.
Строки действий приложения выбираются, а не перетаскиваются: перетащить на холст можно
только собственные строки шага.

Новый шаг никогда не встаёт поверх другого, оказывается выбранным, открывает свои
настройки, если они у него есть, а холст прокручивается к нему, когда он выпадает из
поля зрения. Шаг, добавленный или вставленный внутрь тела цикла, принадлежит этому телу
и соединён после последнего шага со свободным выходом или, когда такого нет, оставлен
вам, чтобы связать его самому. Новый цикл уже содержит **Элемент цикла** (Loop item) и **Результат
итерации** (Loop result), поэтому выбор никогда их не предлагает; циклы он предлагает,
пока они не вложены так глубоко, как позволяет публикация.

Правый щелчок по шагу предлагает **Открыть настройки** (Open settings), **Дублировать**
(Duplicate), **Выключить** (Switch off) и **Удалить шаг** (Delete step). Когда выбрано
несколько шагов, панель внизу удаляет их вместе.

**Перейти к просмотру** (Switch to view only) в шапке показывает тому, кто может править
сценарий, что видит читатель: на холсте ничего не двигается, не соединяется и не
удаляется, шаг открывается только для чтения одним нажатием, а **Проверить черновик** и
**Опубликовать** исчезают. **Перейти к редактированию** (Switch to editing) возвращает
всё обратно, и редактор всегда открывается в режиме правки. Сохранение, которое ещё идёт,
заканчивается в любом случае.

!!! note "Каталог шагов растёт со временем"

    Выбор питается зарегистрированными узлами экземпляра, а не фиксированным списком.
    Тип узла, зарегистрированный позже, появляется в нём сразу же, без изменений в
    сценарии, который вы уже построили.

### Заметки, упорядочивание и сочетания клавиш { #notes-tidying-and-shortcuts }

**Добавить заметку** (Add a note) в меню, которое открывает правый щелчок по холсту, —
ставит заметку рядом с шагами: Markdown, написанный двойным щелчком или её карандашом,
перемещаемый перетаскиванием и меняющий размер от углов; выбранная, она разворачивает
своей кнопкой палитру образцов, чтобы её подкрасить — серый, жёлтый, зелёный, синий,
фиолетовый или красный, — так предупреждение читается отдельно от списка дел. Заметка
хранится в графе, поэтому версии, восстановления и копии сценария её сохраняют, но
ничего её не выполняет и не проверяет. Выбор связи предлагает **+**, который ставит
следующий выбранный шаг в его середину, соединённый с обеих сторон, если порты подходят.
**Упорядочить** (Tidy up) на панели выстраивает шаги в поле зрения слева направо одной
отменяемой правкой, кнопка карты показывает мини-карту, кнопка палитры переключает шаги
между цветным видом и **Без цвета** (Simple), как описано в разделе [Как нарисован
шаг](#how-a-step-is-drawn), а кнопка клавиатуры — или **?** — перечисляет все сочетания;
**Tab** открывает выбор шагов.
Ни одно из них не срабатывает, пока вы печатаете в поле.

### Как нарисован шаг { #how-a-step-is-drawn }

Карточка говорит, какого рода шаг, прежде чем сказать, что он делает. Над именем
маленькая метка читается как **Семейство · Вид** — **ИИ · Классифицировать**, **Данные ·
Сохранить запись** — а значок стоит на плитке, нарисованной в семействе шага, тех же
разделах, что использует выбор шагов:

| Семейство | Его плитка |
|---|---|
| **Старт** | В цвете чернил — тёмная в светлой теме, светлая в тёмной — и круглая, на карточке, у которой левый край скруглён под неё |
| **ИИ** | Сплошной фиолетовый |
| **Поток** | Серый |
| **Данные** | Бирюзовый |
| **Приложения** | Белый с синим контуром, чтобы знак бренда лежал на нём без изменений |
| **Ошибка** | Красный |

Семейства различаются светлотой и формой не меньше, чем цветом, поэтому их различит
и тот, кто не различает цвета, и тот, кто смотрит на холст, уменьшенный настолько, что
читать на нём уже нельзя. Мини-карта тоже рисует каждый шаг в цвете его семейства. Рамка и
обводка карточки никогда не принадлежат семейству: они относятся к запуску (см. ниже),
к изменению, к выделению или к выключенному шагу.

Под именем строка начинается с того, с чем работает шаг, — агент, модель, таблица, — и
продолжается тем, что он настроен делать, как в **gpt-4.1-mini · 3 категории**.

Шаг, который может приостановить запуск, несёт полосу поперёк верха карточки,
сформулированную по его настройкам и никогда по запуску:

| Шаг | Полоса читается |
|---|---|
| **Запросить согласование** (Approval) | **Ждёт человека** (Waits for a person) |
| **Ожидание** (Wait) | **Ждёт 2 дня** (или часы, минуты, секунды), **Ждёт до указанного времени** либо **Ждёт заданное время**, когда время или длительность задаёт более ранний шаг, либо **Ждёт вызова** — оно побеждает, когда заданы и длительность, и вызов |
| **Запустить сценарий** (Run a workflow) | **Ждёт вызванный сценарий** (Waits for the called workflow); полосы нет, когда **Дождаться завершения** (Wait for it to finish) выключено |
| **Вызвать инструмент MCP** (MCP call) | **Спрашивает перед записью** (Asks before writes) или **Спрашивает перед каждым вызовом** (Asks before every call), по своей настройке согласования; полосы нет, когда он никогда не спрашивает |

Шаг, который спрашивает человека, показывает полосу розового цвета; таймер или вызов —
серого. У шага агента её нет: его согласования идут из собственной спецификации агента, которой
карточка не видит.

На холсте запуска шаг, ждущий человека, нарисован розовым, с песочными часами в своей
плашке, как бы ни были нарисованы шаги.

**Без цвета** (Simple) рисует каждую плитку нейтральной, а мини-карту серой — так, как
холст выглядел до того, как у шагов появились семейства. Этот режим сохраняет то, что не
зависит от цвета: метку серой, скруглённый конец старта и нейтральную полосу.
Переключите его кнопкой палитры на панели холста или в разделе **Настройки → Профиль →
Оформление → Шаги сценария** (Settings → Profile → Appearance → Workflow steps); выбор
запоминается для каждого браузера, как и тема.

Потяните правый край, нижний край или правый нижний угол выбранного шага, чтобы изменить
его размер. Карточка имеет ширину от 200 до 560 px и высоту до 400 px и никогда не
короче, чем нужно её собственному содержимому. Больше ширины вмещает больше имени и
сводки; больше высоты позволяет имени переноситься до трёх строк, а затем сводке — до
двух, и порты остаются внизу карточки.

Размер сохраняется вместе с черновиком, поэтому отмена, копирование, вставка,
дублирование, опубликованные версии и экспорт его сохраняют. **Сбросить размер** (Reset
size) в меню правого щелчка по шагу возвращает его к умолчанию, а **Упорядочить** (Tidy
up) расставляет шаги с учётом их размеров. Опубликованная версия, запуск и сравнение
показывают сохранённый размер без ручек.

## Настройка узла { #configuring-a-node }

Что делает каждый узел, чем он настраивается и что значат его сбои, описано в
[справочнике узлов](reference/workflow-nodes.md). Консоль называет каждый шаг, его порты
и настройки на языке читателя; справочник, API и экспортированный сценарий сохраняют
английские имена.

Щелчок выбирает шаг; двойной щелчок открывает его поверх холста. В опубликованной
версии или в режиме **Только просмотр** (View only) его открывает один щелчок. Шапка
называет шаг и складывает незавершённую настройку в одну раскрываемую сводку. Откройте
её, чтобы увидеть, чего не хватает; выбор поля ведёт к его вводу. После проверки или
попытки публикации сводка открывается с подробностями проверки.

**Подключить учётную запись** (Connect account) в шаге или в выборе приложений открывает
существующую настройку учётной записи над сценарием. Подключите учётную запись
организации, завершите настройку и выберите её в шаге. Выбор секрета предлагает
**Добавить API-ключ** (Add API key) или **Новый секрет** (New secret), автоматически
выбирает сохранённый секрет и держит в черновике только его идентификатор. Триггеру,
которому не хватает учётных данных приложения OAuth, предлагается **Добавить учётные
данные** (Add credentials) на месте; та же форма хранилища сохраняет их для организации.

**Параметры** (Parameters) — это то, с чем шаг работает и что он настроен делать, одним
списком, причём список, с которым работает шаг, идёт первым: **Элементы** (Items) фильтра
перед его **Условием** (Condition). **Настройки** (Settings) — это то, как он выполняется.
Каждая правка сохраняется в черновик по мере внесения, поэтому **Готово** (Done) только
закрывает диалог, а **Удалить шаг** (Delete step) удаляет шаг. Диалог только для чтения
показывает каждую настройку неактивной, при её значении.

Параметр, принимающий текст, — это одно поле и для набранного текста, и для значений из
более ранних шагов, например `New lead: {{Form.payload.name}} from {{Form.payload.company}}`.
**Данные** (Data) рядом вставляет значение в позицию курсора,
и то же делает поле, перетащённое из панели **Вход** (Input). Ввод `{{` перечисляет
те же значения, а внутри полезной нагрузки триггера или элемента цикла — поля, которые
там увидел последний тестовый запуск; дальнейший ввод сужает список, и `Enter` или `Tab`
записывает подстановку.

Подстановка называет шаг и путь в его вывод, подсвечивается в поле — красным, как только
вы выйдете из поля, если она не называет ничего, что этот шаг может прочитать, —
проверяется при публикации, как любое значение, прочитанное из шага, и следует за шагом
при переименовании. С данными тестового запуска результат показывается ниже. Ничего не
вычисляется: когда шаг выполняется, каждая подстановка становится текстом своего значения
— JSON для списка или объекта, — а та, за которой ничего нет, завершает шаг с ошибкой
`INVALID_BINDING`, называя её.

Любой другой параметр — число, выбор, переключатель, список, набранный как JSON, — это
собственный элемент управления, и **Данные** рядом берут значение из более раннего шага
вместо него. **Данные** перечисляют только достижимые здесь значения с совместимым типом,
сгруппированные по шагу, каждое с видом значения, которое оно содержит, и говорят **Нет
подходящих выводов предыдущих шагов** (No compatible upstream outputs), когда их нет. Тогда
параметр показывает, что он читает, — *Запустить агента › текст* — а **×** возвращает к
набранному значению.

Обязательный параметр без значения — это проблема проверки, отмеченная на шаге, а не
заполненная молчаливым умолчанием. Некоторые параметры держат структурированные значения:
список строк, в котором можно **Добавить строку** (Add row), переставить их и удалить, или
типизированный выбор, который подменяет форму под ним. Диалог разворачивает их внутри
себя, а не отправляет вас на отдельный экран.

### Условия { #conditions }

**Отфильтровать список** (Filter a list), **Если / иначе** (If) и **Переключатель**
(Switch) решают условием, собранным из строк: поле элемента или значение, проверка —
**равно** (is equal to), **не меньше** (is at least), **содержит** (contains), **не пусто**
(is not empty) и остальные — и то, с чем сравнивают. Число, `true` и `false` сравниваются
как таковые, всё остальное — как текст. При нескольких строках **Совпадает со всеми из
них** (Match all of these) или **с любым** (any) говорит, как они объединяются, а поля,
которые показал последний запуск или тестовые данные, предлагаются. Условие хранится как
выражение JMESPath, которое вычисляет шаг. **Записать как выражение** (Write it as an
expression) правит его именно так, а условие, которое строки показать не могут, остаётся
выражением.

Переименование правила **Переключателя**, категории классификатора, ветви ошибки, ветви
**Разделить** (Split) или варианта согласования переносит связи, привязки и быстрый
журнал, которые использовали старое имя, если только строки не переупорядочены, не
вставлены или не удалены либо два имени не меняются сразу.

### Имя шага, заметка и выключение { #naming-noting-and-switching-off-a-step }

Щелчок по имени шага в верхней части его диалога даёт шагу собственное имя. Оно
видно на карточке шага и везде, где следующий шаг выбирает, что читать: два шага
**Отправить сообщение** (Send a message) становятся *Tell sales* и *Tell support*.
Два шага не могут иметь одинаковое имя без учёта регистра.

В разделе **Настройки** (Settings) поле **Заметка** (Note) хранит строку для того,
кто будет редактировать сценарий следующим; она отмечается на карточке, а вкладка
получает точку, как только в ней что-то изменено.

Если выключить **Выполнять этот шаг** (Run this step) там же или **Выключить**
(Switch off) в контекстном меню, шаг остаётся на холсте, но тускнеет, и запуск его
пропускает: шаг ничего не делает и передаёт дальше то, что в него пришло.
Публикация отклоняет выключенный триггер или соединённый шаг, определяющий
маршрут, а также шаг, который читает выключенный шаг, — если только то, что
приходит в него по единственной входящей связи от включённого шага, не содержит
читаемого поля: тогда оно передаётся дальше. Все три вещи сохраняются в графе,
поэтому их хранят и версии.

Выключенный шаг, соединён он или нет, не проверяется ни по входным данным, ни по
настройкам: он не читает ни того, ни другого. Включить его снова — значит внести
изменение для публикации, и тогда публикация их проверит.

Выключенный шаг без единой связи откладывается в сторону: он может лежать рядом со
сценарием или внутри цикла — скажем, **Объединить списки** (Combine lists) с
тестовыми данными — и оставаться недостижимым. Запуск его игнорирует, и в лимит
шагов запуска он не входит. Соедините его хоть с чем-нибудь — и он снова должен
быть достижим. Отложить можно любой шаг, даже определяющий маршрут, например
**Если / иначе** (If): без связи ему нечем выбирать. Включёнными всегда остаются
только триггер, а также **Элемент цикла** (Loop item) и **Результат итерации** (Loop
result) цикла.


Выключенный шаг может сохранять заданную политику ошибок и привязки к файлам или
таблицам, даже когда ресурс больше недоступен. Он ничего из этого не читает; при
обратном включении всё проверяется заново. Отложенный шаг показывается в разделе
**Шаги** (Steps) запуска как **Отключён** (Switched off), без строки выполнения.
Прежде чем использовать **Проверить шаг** (Test step), соедините его с триггером.

### Данные шага, тестовые данные и проверка одного шага { #a-steps-data-pinning-and-testing-one-step }

При редактировании сценария диалог ставит параметры шага между двумя панелями.
**Вход** (Input) показывает то, что передал один из предыдущих шагов, — ближайший
первым; если их несколько, заголовок панели позволяет выбрать любой шаг, который
этот шаг может читать. **Вывод** (Output) показывает то, что передал сам шаг; обе
панели берут данные из последнего тестового запуска, начатого в редакторе, или из
самого свежего, если диалог только открыли. **Таблица** (Table) раскладывает данные
по строкам, список записей — по строке на запись. **JSON** показывает их как есть, а
**Поля** (Fields) перечисляет каждое поле по пути с простым словом о том, что в нём
лежит: текст, число, список, ID — это пути, которые читает следующий шаг.

До первого запуска обе панели так же перечисляют поля, которые шаг передаёт дальше,
и их тоже можно перетаскивать; шаг, к которому ничего не ведёт, говорит **Пока не
соединён** (Not connected yet). Таблица показывает первые 50 строк, пока
**Показать больше** (Show more) не разложит остальные, а ячейка, обрезанная по
столбцу, показывает всё значение при наведении.

Столбец или поле из **Входа** можно перетащить на параметр — и параметр будет
читать его из того шага, как если бы вы выбрали его через **Данные** (Data): в
текст — как подстановку. Неподходящее поле отклоняется с указанием причины: тип,
который параметр не принимает, или шаг, который выполняется не всегда раньше
этого.

Внутри значения свободной формы — например, `values` у сопоставления или `payload`
у триггера — тип тот, который показал запуск. **Данные** предлагают значения
свободной формы и любому другому параметру, а **Поле внутри** (Field inside it)
задаёт путь. Если держать перетаскиваемое поле у верхнего или нижнего края формы,
она прокручивается, так что до параметра вне поля зрения можно добраться.

**Сохранить как тестовые данные** (Keep as test data) оставляет вывод на шаге, а
**Задать тестовые данные** (Set test data) позволяет ввести их вручную как объект
JSON не больше 64 000 байт. Пробный запуск передаёт тестовые данные дальше вместо
выполнения шага, поэтому медленный вызов модели или запись в реальную систему
делаются один раз и переиспользуются. Шаг, который определяет маршрут, тестовых
данных не хранит никогда, а публикация снимает их все: опубликованная версия
всегда выполняет свои шаги. Значок булавки отмечает карточку, а **Удалить
тестовые данные** (Remove test data) убирает их.

**Проверить шаг** (Test step) выполняет только этот шаг и остаётся главной кнопкой
панели, пока данных ещё нет. Запуск берёт лишь шаг и шаги, ведущие к нему, и
каждый из них, у которого есть известный вывод, тестовые данные или данные прошлой
проверки, передаёт их дальше вместо выполнения. Остальные выполняются, а всё, что
после шага, — нет. Шаг, который пишет, сначала спрашивает, ведь проверка
действительно пишет. Шаг внутри цикла нельзя проверить отдельно, потому что он
выполняется для каждого элемента, — проверяйте цикл. Пока проверка идёт, квадрат
рядом с **Проверить шаг** её останавливает. Если она завершилась, не выполнив шаг,
— остановлена, ушла по другой ветке или закончилась раньше, — значок
предупреждения рядом скажет, что именно. Через API то же делает `step` в
`POST /api/v1/workflow-runs`.

### Выбор ресурсов { #resource-pickers }

Настройка, закрепляющая ресурс, открывает средство выбора, а не поле свободного
ввода, — так шаг называет реальную вещь, которая есть у вашей организации:

| Средство выбора | Что оно закрепляет |
|---|---|
| **Агент** (Agent) и **Версия** (Version) | Агента — по лицу и описанию, затем одну из его опубликованных версий, причём действующая помечена, а у каждой есть дата и примечание к версии. Смена агента сбрасывает закреплённую версию, потому что версия принадлежит одному агенту. Карточка шага показывает лицо агента и «имя · v3» |
| **Таблица** (Table) и **Столбцы** (Columns) | [Виртуальную таблицу](virtual-tables.md), затем столбцы, которые читает шаг, — в пределах текущей схемы этой таблицы |
| **Секрет** (Secret) | Секрет из [хранилища секретов](secrets.md) — по ссылке. Шаг хранит идентификатор секрета, но никогда его значение |
| **MCP-сервер** (MCP server) и **Инструмент** (Tool) | Один из [MCP-серверов](mcp.md) организации, с отметкой его сервиса, затем один из инструментов, которые сервер перечислил при последней проверке. Чтобы выбрать его, нужен доступ на редактирование сценария — по роли или по выданному доступу к нему, как и для публикации шага, — а не `mcp:manage`; проверить сервер или добавить новый может только участник, который управляет серверами |

Каждое средство выбора различает одноимённые строки по контексту и помечает
ссылку, цель которой исчезла. У **Агента** и **Секрета** есть ещё ссылка на
создание нового — всегда, а не только когда список пуст, — а у **Таблицы** её
нет.

Когда схема таблицы меняется после того, как шаг был привязан к ней, редактор сам
переводит шаг на новую схему — при условии, что каждый читаемый шагом столбец
по-прежнему существует с тем же типом: добавленный столбец или изменение того,
который шаг не читает, ничего от вас не требует. Если читаемый столбец удалён или
сменил тип, шаг вместо этого показывает проблему, и поле **Таблица** у шага, и
список проблем на панели инструментов предлагают **Обновить до текущей схемы**
(Update to the current schema), что сохраняет все выбранные столбцы, которые ещё
существуют. После этого проверьте, что читает шаг.

Фильтры, столбцы сортировки и привязки значений тоже проверяются. Уберите или
замените зависимые настройки, которые используют изменённые столбцы, до обновления
схемы таблицы: массовое обновление оставляет такие шаги без изменений. Привязка
значения всей записи тоже требует такой ручной проверки.

### Оценки для шага с моделью { #evals-for-a-model-step }

У шага, на который отвечает модель, — агента, **Спросить модель** (Ask a model),
**Классифицировать** (Classify), **Извлечь данные** (Extract data), **Пересказать
или перевести** (Summarize or translate) или решающего шага, — есть вкладка
**Оценки** (Evals): кейсы, которые он должен обрабатывать, и что должен затем
говорить его ответ. **Добавить кейс** (Add a case) берёт входные данные, с
которыми шаг проверяли последний раз, — вход запуска и то, что передали
предыдущие шаги, — поэтому сначала проверьте шаг, затем назовите кейс, укажите,
где в ответе смотреть (`text`, `category`, путь вроде `structured.amount` или
ничего для всего вывода), и должно ли там быть значение — **содержит** (contain),
**не содержит** (not contain) или **совпадает с** (equal), — без учёта регистра и
пробелов вокруг.

**Запустить кейсы** (Try) выполняет тестовый запуск шага для каждого кейса — с
проверками и оплатой, как у любого другого, — и каждый кейс помечается пройденным
или непройденным по завершении своего запуска, вместе с тем, что ответил шаг или
почему он ничего не ответил. Кейс, чей запуск не может начаться, — слишком много
работы в процессе, месячный бюджет израсходован, — помечается непройденным с
указанием причины. Запускайте кейсы после изменения промпта, модели или
инструкций. Шаг хранит до 50 кейсов, а для их запуска нужно `workflows:edit`, как
и для проверки черновика.

### Агенты из каталога { #an-agent-configured-in-the-step }

**Запустить агента** (Run an agent) выбирает опубликованного агента из каталога.
Выбор закрепляет его текущую опубликованную версию; выбор версии позволяет взять
более старую. Опубликованный сценарий сохраняет это закрепление неизменным. У
существующего незавершённого шага **Использовать опубликованную версию** (Use
published version) заполняет недостающее закрепление перед проверкой. Создавайте и
редактируйте агентов в Конструкторе.

Старые графы, в которых агент настроен внутри шага, остаются выполнимыми. Редактор
сохраняет эту настройку, пока вы намеренно не замените её агентом из каталога.
Новых встроенных агентов в сценариях создать нельзя. **Макс. стоимость (USD)**
(Max cost (USD)) по-прежнему ограничивает выполнение наряду с другими применимыми
бюджетами.


### Когда шаг медленный или завершается ошибкой { #when-a-step-is-slow-or-fails }

Раздел **Настройки** (Settings) шага содержит настройку **Когда шаг медленный или
завершается ошибкой** (When it is slow or fails), которая задаёт его политику.
**Обрабатывать ошибки** (Handle errors) даёт шагу порт **Ошибка** (Error): сбой,
который не уладили повторы, уходит через него — на шаг **Обработать ошибку** (Handle
error) или на что угодно ещё, что вы подключите, — вместо того чтобы завершить
запуск ошибкой.

**Попытки** (Tries) — сколько всего раз шаг пытаются выполнить, а **Пауза между
попытками** (Wait between tries) и **Первая пауза (с)** (First wait) задают паузу
между попытками. Шаг, вызов которого небезопасно повторять, — например, запуск
агента, — так и говорит и никогда не повторяется. **Лимит времени (с)** (Time
limit) обрывает вызов через столько секунд. Что каждая настройка делает во время
выполнения, сказано в [справочнике
узлов](reference/workflow-nodes.md#error-handling).

Привязка к значению без объявленной формы — текущий элемент цикла, `payload`
триггера — предлагает под источником поле **Поле внутри** (Field inside it): там вы
вводите путь внутри этого значения, например `record_id` или `fields.Email`.
Запуск проверяет этот путь при отправке шага на выполнение, потому что только
запуск знает, что лежит в значении.

### Быстрый журнал { #quick-log }

Быстрый журнал пишет одну строку в журнал сценария каждый раз, когда шаг
завершается в запуске, — так видно, что делал сценарий, не открывая каждый запуск.
Это настройка шага. Наведите курсор на карточку и выберите **+ Журнал** (+ Log):
справа снаружи карточки пристраивается полоса **Журнал** (LOG), маркеры выводов
шага переезжают на её внешний край, и у каждого вывода, который журналируется,
появляется полоска. Уберите быстрый журнал, чтобы перестать записывать этот шаг.

**Сообщение** (Message) — шаблон от 1 до 500 символов, по умолчанию
`{{step}} → {{outcome}}`. В нём можно использовать `{{step}}` — имя шага — и `{{outcome}}` —
вывод, через который ушёл шаг. Можно также использовать поля вывода шага по их
пути, например `{{record.id}}`, а для сбоя — `{{error.code}}` и
`{{error.message}}`. Ссылка, которая не разрешается, выводится пустой, как и
индекс списка: пути идут только через объекты.

Поле **Записать строку, когда шаг выходит через** (Outputs) задаёт, какие исходы
пишут строку. По умолчанию пишет каждый вывод; отметьте меньше, чтобы журналировать
только их, а чтобы не журналировать ничего, уберите быстрый журнал. Быстрый журнал
не разрешён на шаге **Элемент цикла** (Loop item) или **Результат итерации** (Loop
yield). Ставьте его на сам шаг **Для каждого** (For each): когда его цикл
закрывается, он пишет строку через свой вывод `done`. Шаг без выводов журналирует
свои сбои.

Сбои записываются всегда. Сбой, который не направлен ни в один порт `error`,
журналируется независимо от отмеченных выводов: журнал и нужен для того, чтобы не
пропустить тихий сбой запуска. Сбой, направленный портом `error`, подчиняется
фильтру выводов, как и любой другой исход.

Строка не пишется для шага, который был пропущен, выключен или так и не начался, а
также для шага, который [повтор с неудавшегося шага](#running-a-workflow)
переиспользовал вместо выполнения. Журнал никогда не меняет запуск: сообщение,
которое не удаётся записать, отбрасывается, а запуск идёт дальше так, как пошёл бы.
Тестовый запуск тоже пишет свои строки, помеченные как тест, а строка от шага,
передавшего закреплённые тестовые данные, помечается как закреплённая.

Строки хранятся вместе со своим запуском и удаляются вместе с ним, когда хранение
истории удаляет запуск (см. [Настройки сценария](#workflow-settings)). Читайте их
на [странице журнала](#the-logs-page) или, по шагам, в представлении запуска.

## Связи и область цикла { #connections-and-foreach-scope }

Связь проводится, когда вы соединяете порт вывода одного узла с портом входа другого.
Редактор отклоняет связь между портами с разной формой данных ещё до того, как её
нарисует, поэтому несовместимая связь никогда не попадает на холст, а рисование уже
существующей связи ничего не делает.

Связь задаёт порядок выполнения шагов; данные она не перемещает. Значения, которые
читает шаг, — это его **привязки**, о них сказано в разделе [Настройка
узла](#configuring-a-node).

Чтобы связь не заставляла вас привязывать каждое поле вручную, соединение двух
портов с совершенно одинаковой формой — скажем, вывода **Эхо** (Echo) со входом
**Ретранслятора** (Relay) — ещё и привязывает каждый вход цели к одноимённому полю
источника. Поле, которое вы уже привязали, остаётся как было.

Когда формы различаются или порт не несёт данных, за вас всё равно делается один
выбор: шаг, который работает с одним списком, соединённый после шага, передающего
ровно один, — **Отфильтровать список** (Filter a list) после **Списка записей**
(List records) — читает этот список. Больше ничего не привязывается, и каждый
источник вы выбираете сами через **Данные** (Data). Отмена (`Ctrl`/`Cmd` + `Z`)
возвращает связь и её привязки вместе, а удаление связи позже оставляет привязки на
месте, так что уберите или перепривяжите их в настройках шага.

Чтобы удалить связь, выберите её: щёлкните по ней, и она нарисуется толще, а на ней
появится кнопка **Удалить связь** (Delete connection). Нажмите кнопку или клавишу
`Delete` или `Backspace` — и связь исчезнет, а два шага останутся. Связи
опубликованной версии выбрать нельзя, поэтому и удалить их нельзя.

Шаг **Для каждого** (For each) выполняет своё тело один раз на каждый элемент
списка. Тело — не отдельный документ: это часть того же плоского графа, показанная
отдельно. **Редактировать тело цикла** (Edit loop body) на шаге, где указано,
сколько шагов в теле, открывает этот вид, а навигационная цепочка **Область
сценария** (Workflow scope) в углу холста показывает, где вы, — от **Сценария**
(Workflow) до открытого цикла. Каждый её элемент ведёт обратно наружу.

Тело начинается на **Элементе цикла** (Loop item) и заканчивается на **Результате
итерации** (Loop result). Каждый шаг помнит цикл, к которому относится, поэтому
удаление связи никогда не выносит шаг из тела; шаг, к которому **Элемент цикла**
не ведёт, отмечается как проблема, пока вы его не соедините. Ни одна связь не идёт
из цикла в его тело или обратно в цикл, который продолжается через **Готово**
(Done), когда все элементы прошли через тело. **Элемент цикла** и **Результат
итерации** бывают только со своим циклом: удаление цикла удаляет всё его тело, а
копирование копирует тело.

Выбор шагов и источники привязки следуют за областью, в которой вы находитесь, а
шаг в теле может читать всё, что выполнилось до цикла. Что делает цикл, сказано в
[справочнике узлов](reference/workflow-nodes.md#loops).

### Параллельные ветки { #parallel-branches }

Любой шаг может направить один порт вывода в несколько шагов, и эти шаги
выполняются одновременно. Шаг **Разделить** (Split) делает то же с именованными
ветками и запускает их все: у него нет условия, и он не умеет направлять ошибки.
Какая ветка закончится первой, не определено, поэтому ничто не может полагаться на
порядок. Нарисуйте ветви, а там, где следующему шагу нужно то, что они сделали,
сведите их вместе.

Шаг с несколькими входящими связями сам сводит их вместе, и **Соединить** (Merge) ему
не нужно. Он выполняется, когда улягутся все ведущие к нему шаги, если хотя бы одна
его связь жива: ветку, по которой не пошёл **Если / иначе** (If), он не ждёт. Шаг
пропускается, когда ни одна связь не жива, а также когда ведущий к нему шаг
завершился сбоем без маршрута ошибки. Его привязки могут читать только шаги,
которые точно выполнились до него, поэтому такой шаг может читать каждую ветку
параллельной группы, но не ветвь **Если / иначе**, которая могла и не выполниться.

У **Соединить** есть настройка **Ждать** (Wait for). **Ветка, которая выполнилась**
(The branch that ran) передаёт дальше вывод той единственной ветки, что до него
дошла; публикация отклоняет шаг с этой настройкой, когда два его входа могут
выполниться вместе. **Все ветки** (All branches) ждёт каждый вход и передаёт дальше
каждый по имени как `branches`, так что следующие шаги читают `branches.<name>`; у
каждой связи есть **Имя ветки** (Branch name). Публикация отклоняет шаг с этой
настройкой, когда какой-то вход может не выполниться, называя его, или когда
выполниться может только один вход. Вторая связь, подведённая к **Соединить**, выбирает
настройку, нужную графу, а переименование имени ветки переносит и шаги, которые его
читают, — одной отменой. Подробности — в
[справочнике узлов](reference/workflow-nodes.md#logic-if-and-logic-merge).

Публикация также отклоняет граф с двумя шагами **Результат** (Output) или двумя
шагами **Ответ на вебхук** (Respond to webhook), которые могут выполниться в одном
запуске, и шаг **Обработать ошибку** (Error handler), в который входят два шага,
способные сбоить в одном запуске. Дайте каждой ветке свой.

Ветка, которая сбоит без маршрута ошибки, завершает запуск сбоем. Шаги рядом с ней
больше ничего не начинают, а то, что у них было в работе, закрывается: ожидающие
согласования, таймеры и запуски агентов, на которых стоит шаг. Шаг, завершившийся
после этого, записывается как **Завершился после остановки запуска** (Finished after
the run stopped), его работа сохраняется, и [повтор](#running-a-workflow)
переиспользует её, а не делает заново. Статус запуска следует за шагами, которые ещё
выполняются, поэтому ветка, ожидающая согласования, видна, даже пока другая ещё выполняется.

Бюджет запуска общий. Каждый шаг, который тратит, и каждый вызываемый им сценарий
черпает из того, что осталось от лимита после расходов и что держат другие
выполняющиеся шаги, и никогда больше, чем его собственный `max_cost_usd`. Шаг,
обнаруживший, что остальное держат соседние шаги, ждёт и спрашивает снова, каждый
раз чуть позже, вместо того чтобы получить весь остаток. Удержание заканчивается,
когда уляжется шаг, который его взял.

Соседние шаги с ИИ работают бок о бок при бюджете запуска, только когда у каждого
есть свой `max_cost_usd`: шаг без него держит всё, что осталось, поэтому соседи ждут,
пока он уляжется.

Сколько веток выполняется одновременно, задаёт воркер, а не запуск. Ограничения на
запуск нет, поэтому ветки одного запуска могут занять все слоты сценариев в
воркере — `WORKER_WORKFLOW_CONCURRENCY` (по умолчанию пять, см.
[Настройку](configuration.md)), — а остальные встанут в очередь. Запуск, которого
кто-то ждёт, идёт впереди запуска, начавшегося сам. Поэтому ветвление на много
веток в одном запуске замедляет другие запуски на этом воркере: держите его
настолько широким, насколько нужно работе.

## Проверка и её сообщения { #validation-feedback }

Редактор проверяет граф по ходу редактирования. До проверки незавершённые шаги несут
нейтральный индикатор настройки, а холст говорит **Завершить настройку** (Finish
setup). Откройте индикатор, чтобы увидеть перечень того, что осталось, и перейти к
шагу. Проверка или публикация выявляют ошибки, а если оставить пустым обязательное
поле, его сообщение появится прямо там. Публикация остаётся заблокированной, пока
не решена каждая проблема проверки.

Настройки шага остаются короткими. То, что нужно шагу, и всё, что вы уже задали,
видно сразу; необязательные настройки со значениями по умолчанию ждут за кнопкой,
которая их считает, — **ещё 3 варианта** (3 more options): она выводит их над собой,
пока не станет **Меньше вариантов** (Fewer options), — а то, как шаг выполняется,
ждёт под **Настройками** (Settings). Обязательное значение, которого вы ещё не дали,
не помечается рядом с полем, пока вы не покинете это поле или не попробуете
запустить либо опубликовать: отметка шага на холсте говорит об этом с самого
начала. Описание, которое лишь повторяет имя своего поля, становится подсказкой на
имени, а не строкой под полем.

Сообщения называют конкретную неисправность: обязательный вход без значения; вход,
заданный более чем одним источником; связь, порты которой несут разную форму; шаг,
до которого нельзя добраться от начала; петля обратно к более раннему шагу;
значение, читающее шаг, который выполнялся не на каждом пути, ведущем сюда; или
связь, пересекающая границу тела цикла.

!!! info "Проверка в редакторе — лишь предварительный просмотр; решает публикация"

    Проверка в редакторе — быстрое отражение правил, которые применяет сервер. Она
    нужна, чтобы поймать проблему, пока вы на неё смотрите, но последнего слова за
    ней нет: публикация заново выполняет полную проверку на сервере, и проблема,
    которую редактор пропустил, всплывает так же — при узле или поле, к которому
    относится.

## Автосохранение и баннер о конфликте ревизий { #autosave-and-the-revision-conflict-banner }

Черновик сохраняется сам. После короткой паузы в редактировании записывается текущий
граф, и статус под заголовком, после меток, отражает это: **Несохранённые
изменения** (Unsaved changes), пока сохранение ожидается; **Сохранение…**
(Saving…), пока оно идёт; **Сохранено** (Saved), когда оно завершилось; и **Не
удалось сохранить — повторим** (Save failed — will retry), если не удалось.

Каждое сохранение записывается относительно той ревизии, которую вы открыли, поэтому
черновик, редактируемый в двух местах одновременно, не может молча перезаписаться.
Когда это происходит, редактор показывает баннер **Кто-то ещё редактировал этот
сценарий** (Someone else also edited this workflow): *Пока вы редактировали, были
сохранены изменения. Оставьте свои изменения или загрузите их версию и потеряйте
несохранённые правки.* Вы выбираете:

- **Оставить мои изменения** (Keep my changes) — сохранить вашу версию и записать её
  поверх той, что сохранена в другом месте.
- **Загрузить их версию** (Load their version) — отбросить несохранённые правки и
  взять последний сохранённый черновик.

## Публикация версии и история версий { #publishing-a-version-and-version-history }

Настройка полномочий для запусков без участия человека требует сеанса участника:
публикация триггера вебхука, расписания, таблицы, формы, GitHub, почты или канала;
включение его доступа; смена его секрета или ссылки формы; изменение его
расписания; выбор сценария ошибок. API-ключи организации могут публиковать ручные
сценарии, начинать разрешённые запуски и ставить автоматизацию на паузу; они не
могут сохранять полномочия выпустившего их пользователя для будущих событий. В
предрелизных экземплярах с уже существующей автоматизацией опубликуйте заново из
сеанса доверенного участника: исторические записи не фиксируют, каким ключом
публиковали.

Шаги MCP при публикации и при отправке на выполнение применяют текущую видимость
подключения, доступ группы и ресурса и `allowed_tools`. Пустой список разрешённых не
даёт доступа ни к одному инструменту. Отзыв доступа после публикации отклоняет
выполнение ещё до чтения учётных данных и обращения к серверу.

Извлечение DOCX читает XML документа потоком и останавливается на заданном лимите
символов, с ограниченным раскрытием архива и вложенности. Полное дерево документа
не строится до применения этого лимита.


История версий загружается по 50 записей метаданных за раз; **Ещё** (More)
запрашивает более старые версии. API принимает `before` и `limit` (1–100) и
возвращает `next_before`, пока есть более старые версии. Графы загружаются только
при открытии версии. Неудачную страницу можно запросить снова, сохранив уже
загруженные записи.

**Опубликовать** (Publish) замораживает текущий черновик как неизменяемую версию,
которая выполняется, — версия никогда не меняется после создания. Диалог
публикации называет версию, которую создаёт, и принимает необязательное
**Примечание к версии** (Release note) с описанием изменений; если черновик не
изменился с действующей версии, диалог сначала говорит об этом. Если в графе ещё есть
проблемы, публикация блокируется сообщением **Исправьте проблемы ниже перед
публикацией** (Fix the problems below before publishing), поэтому версия, которая
не прошла бы проверку, никогда не создаётся.

Некоторые вещи стоит проверить, хотя они и не ошибочны, и янтарный значок на шаге
их отмечает: исход **Запросить согласование** (Ask for approval), который никуда не
ведёт, или шаг, выбирающий между выводами, когда ни один из них никуда не ведёт.
Запуск просто заканчивается там. Диалог публикации перечисляет их тоже, но они
никогда не блокируют тестовый запуск или публикацию.

Публикация не прекращает ваше редактирование. Черновик продолжает существовать
независимо от любой опубликованной версии, так что вы сразу же продолжаете его
редактировать. **Версии** (Versions) в меню **Ещё** в заголовке редактора открывают
каждую опубликованную версию с её примечанием к версии, а действующая помечена
**Действующая** (Live). **Просмотреть** (View) открывает прошлую версию только для
чтения: опубликованная версия доступна только для чтения, а чтобы внести изменения,
вы продолжаете редактировать черновик.

Чтобы вернуться к опубликованной версии, откройте её через **Просмотреть** и
выберите **Восстановить в черновик** (Restore to draft). После подтверждения
черновик получает граф этой версии, а всё неопубликованное в черновике
отбрасывается. Сама версия не меняется, и ничего не публикуется, пока вы не
опубликуете черновик снова. Отмена начинается заново от восстановленного графа.
Если кто-то изменил черновик с тех пор, как вы его открыли, восстановление
отклоняется с тем же баннером о конфликте ревизий, что и сохранение, вместо того чтобы
отбросить чужие правки. Для восстановления нужно `workflows:edit` на сценарии, а
архивный сценарий восстановить нельзя. Каждое восстановление записывается в [журнал
аудита](governance.md) как `workflow.version_restored`.

**Сравнить с черновиком** (Compare with draft) в предпросмотре версии рисует версию
и черновик на одном холсте: каждый шаг, который черновик добавил, изменил или
удалил, отмечается на своей карточке, а список рядом называет каждый изменённый шаг
и то, что в нём изменилось, — настройка, вход, его имя, заметка или версия,
выключен ли он и что он делает, когда работает медленно или сбоит. Перемещение шага и
закреплённые тестовые данные изменениями не считаются. **Показать эту версию**
(Show this version) возвращает к одной версии.

## Настройки сценария { #workflow-settings }

**Настройки** (Settings) собирают в раскрывающиеся разделы время выполнения и
обработку ошибок, историю запусков и хранение, а также лимиты. Разделы со
значениями, отличными от заданных по умолчанию, открыты с самого начала. Страница
запусков начинается с истории; **Показатели действующей версии** (Live performance)
раскрывает статистику опубликованных запусков. Запуски и Журнал держат
второстепенные элементы управления под **Фильтрами** (Filters). Отклонённый фильтр
запусков в ссылке сам открывает своё поле и ошибку.

Хранимые встроенные результаты имеют общие потолки:
`WORKFLOW_RUN_MAX_INLINE_RESULT_BYTES` (64 МиБ на запуск) и
`WORKFLOW_ORG_MAX_INLINE_RESULT_BYTES` (1 ГиБ на все хранимые запуски).
Резервы учитывают компактные результаты попыток, включая синтетические выводы
циклов, и возможные копии для запуска, вебхука и ошибки. Они не измеряют физическое
хранилище PostgreSQL и не заменяют общую политику хранения экземпляра. Небольшие
записи о сбое в конце запуска могут превысить исчерпанную квоту, чтобы запуск мог
закрыться. `WORKFLOW_INLINE_RESULT_LIMIT` нельзя обойти маршрутизацией ошибок;
понесённые расходы сохраняются, а побочные действия автоматически не повторяются.
Обработчик мог уже сделать своё дело к моменту, когда его результат отклонён.
Используйте ссылки на файлы или настройте хранение истории, чтобы освободить
резервы.

Возобновлённый агент ограничен более строгим из двух: потолком времени жизни, пока
он ожидал, и суммой уже потраченного плюс текущие оставшиеся средства сценария.
Расходы соседних веток, пока согласование ожидается, не восстанавливают
прежний запас. Каждый кейс оценки расходует допуск запусков сценария, в том числе
кейсы внутри одного пакета; исчерпанные кейсы записываются как отклонённые. Первое
резервирование HTTP-запроса засчитывается его первому кейсу.

Закреплённые выводы импортируют вложенные ссылки на файлы после текущих проверок
доступа. Допуск и хранение делят блокировку жизненного цикла файлов: зафиксированный
импорт защищает своего создателя, а хранение перепроверяет ссылки, дождавшись этой
блокировки. Недавние примеры редактора сохраняют данные самого нового запуска,
несмотря на задержку старых ответов; вставка сохраняет заметки, а смешанные
изменения заметок и шагов применяются вместе.

Миграция `0231_workflow_result_bytes.py` заполняет счётчики из существующего
несжатого текста JSON, консервативно относительно новых компактных резервирований.
Во время этого заполнения остановите записи из API и воркеров. Существующая
история сверх лимита сохраняется, но блокирует дальнейшие крупные результаты, пока
её не почистят или не поднимут заданный лимит. Уже удалённое содержимое миграция не
восстанавливает.

Резервы хранимых данных включают также начальный вход запуска, снимок черновика для
тестового режима и каждые сохранённые данные для возобновления шага **Ожидание**
(Wait). Допуск и возобновление резервируют эти байты до записи или пробуждения
шагов; отказ возвращает `WORKFLOW_INLINE_STORAGE_LIMIT` (429). Ссылки возобновления
аутентифицируются до чтения тела. Миграция `0232_workflow_input_bytes.py` добавляет
эти существующие данные к счётчикам, сохраняя результаты и оплату. Во время
заполнения остановите записи из API и воркеров; организация, уже вышедшая за лимит,
должна почистить хранимую историю или поднять свой лимит, прежде чем принимать
новые данные.

Сохранённые черновики, опубликованные версии и хранимые импорты защищают файлы, на
которые ссылаются, от удаления при хранении. Удаление сценария-создателя отклоняется,
пока другой сценарий ещё ссылается на его файлы; уберите эти ссылки или отправьте
сценарий в архив. Правки реестра, допуск, импорт и очистка используют одну и ту же
блокировку жизненного цикла организации. Удаление проверяет межсценарные зависимости
запусков, прежде чем убирать триггеры, и пытается снять вебхуки GitHub через
существующую интеграцию учётной записи; сбои очистки у провайдера остаются видны в
журналах.

Объединение по ключу (Combine by key) принимает скалярные значения для соединения и
отклоняет списки и объекты, не повторяя попытку. Создание кейсов оценки сериализует
потолок числа кейсов и выделение позиции. Итоги на «Обзоре» включают каждый видимый
сценарий, даже сверх 500, а завершённый запуск обновляет свой список файлов
независимо от того, когда пришли его шаги.

Вложенные импорты дедуплицируются по идентификатору файла и ограничиваются
`WORKFLOW_GRAPH_MAX_BINDINGS` до проверки в базе данных.

Исходный запуск хранится, пока активен повтор или пока другой хранимый запуск
импортирует один из его файлов. Завершение повтора не делает недействительными
файлы, на которые ещё ссылаются его следующие шаги.

**Настройки** — в меню **Ещё** в заголовке редактора — хранят то, с чем сценарий
выполняется, а не то, что он делает. Настройки принадлежат сценарию, а не версии:
изменение действует на каждый запуск, начатый после него, и публикация их сохраняет.

- **Часовой пояс** (Timezone) — в нём читается cron-выражение расписания, в том
  числе с учётом перехода на летнее время, и в нём пишет шаг **Дата и время** (Date
  & time), не называющий часового пояса. Запуск сохраняет тот, что был задан при его
  старте. Если не задан — UTC. Поле говорит, сколько там сейчас времени, и отклоняет
  пояс, которого браузер не знает.
- **Срок по умолчанию (минуты)** (Default deadline) — срок, который получает запуск, когда
  то, что его начинает, не называет своего.
- **Сценарий ошибок** (Error workflow) — опубликованный сценарий с триггером
  **Сбой сценария** (On failure of a workflow); он запускается один раз, когда
  запуск завершается сбоем. См. [Когда сбоит другой
  сценарий](#when-another-workflow-fails).
- **Хранить запуски (дней)** (Keep runs for) и **Хранить успешные запуски** (Keep runs
  that succeeded) — ежедневная очистка удаляет запуск и сохранённые им файлы через
  столько дней после его завершения, а успешный запуск — на следующий день, когда
  успешные запуски не хранятся. Если не задано, запуски хранятся бессрочно.

**Лимиты** (Limits) ограничивают, что его запуски делают одновременно и сколько
тратят, поверх собственных лимитов каждого шага — включая потолок стоимости шага
агента:

- **Одновременных запусков** (Runs under way at once) — настоящий запуск, начатый
  сверх него, отклоняется с `429`, пока один не завершится. Отправителю вебхука или
  GitHub сообщают о необходимости повторить, расписание ждёт следующего тика, а
  событие таблицы или ответ формы сверх лимита отклоняется. Ящик читается снова
  через минуту, каким бы ни был его интервал, поэтому сообщение ждёт окончания
  запуска — если только запуски, держащие лимит, не ждут согласования: тогда
  сообщение пропускается для этого сценария, и журнал аудита это записывает
  (`workflow.mail_message_skipped`). Тестовые запуски не считаются и не
  задерживаются.
- **Максимум расходов одного запуска (USD)** (Most one run may spend) — собственный
  бюджет запуска, более строгий из него и бюджета версии: запуск, достигающий его,
  останавливается перед следующим шагом как превысивший бюджет.
- **Максимум расходов его запусков в месяц (USD)** (Most its runs may spend a month) —
  считается за календарный месяц в UTC, включая тестовые запуски. После его
  достижения ни один запуск не начинается — `402` — пока не сменится месяц или не
  поднимут бюджет. Страница запусков показывает расходы за месяц в сопоставлении с ним.

Через API `PUT /api/v1/workflows/{id}/settings` заменяет их.

Хранение истории удаляет содержимое запусков и файлы, но сохраняет суммы без
содержимого и отметки времени допуска для учёта месячного бюджета. Удаление истории
не пополняет месячный бюджет сценария. Расходы, удалённые до появления этого учёта,
восстановить нельзя.

## Запуск сценария { #running-a-workflow }

**Проверить черновик** (Test draft) в заголовке редактора сразу выполняет черновик,
а не опубликованную версию; `Ctrl`/`Cmd` + `Enter` делает то же. Сначала запуск
спрашивает поля, которые объявляет триггер **Вручную** (Manual) или **Запрос API**
(API request). Дальше запуск показывается на холсте по ходу дела. Плашка в углу
каждого шага говорит, где он: **В очереди** (Pending), **Запускается** (Starting),
**Выполняется** (Running) с идущим временем, **Ожидает** (Waiting), **Ошибка**
(Failed), **Требует внимания** (Needs attention), **Пропущен** (Skipped) или **Не
выполнен** (Not reached); а шаг, который завершился успешно, показывает, сколько это
заняло.

Связь, ведущая в выполняющийся шаг, движется, пройденный путь зеленеет, а ветка, по которой
запуск не пошёл, тускнеет. Шаг, завершившийся сбоем, показывает свою ошибку под
карточкой и один раз вздрагивает.

Связь говорит, сколько элементов прошло по ней, когда шаг до неё передал список, а
полоса внизу говорит, как идут дела у запуска, и
содержит **Открыть запуск** (Open run) для его страницы. Пока запуск идёт, квадрат
рядом с **Проверить черновик** останавливает его, ничего не спрашивая. Завершённый
запуск холст сохраняет; следующая правка его скрывает и оставляет полосу о том, что
граф с тех пор изменился, — по-прежнему с **Открыть запуск**. Шаг, который ждал и
пошёл дальше, считается за одну попытку, а не за две. **Проверить черновик** ждёт,
пока сохраняется правка, и говорит, почему нельзя запустить, пока в черновике есть
проблемы.

**Запуски** (Runs) в заголовке редактора и значок запусков на карточке сценария
открывают его запуски, сначала новые; у каждого есть статус, выполнял ли он черновик
или опубликованную версию, что его начал, когда, сколько он длился и сколько стоил.
**Запустить** (Start a run) начинает запуск вручную: **Проверить черновик** (Test the
draft) выполняет черновик в текущем виде, а **Опубликованная версия** (Published
version) — действующую. Его **Входные данные (JSON)** (Input (JSON)) — это то, что
шаг **Вход** (Input) сценария передаёт как `payload`.

Над списком **Как он проходил** (How it ran) подводит итог по настоящим запускам за
последние 7, 30 или 90 дней: сколько прошло и сколько сбоило, какая доля
завершившихся была успешной, типичное время и время, в которое уложились 95 из 100, и
сколько они стоили по дням. Карточка стоимости даёт ещё расходы за этот месяц,
включая тестовые запуски, в сопоставлении с месячным бюджетом сценария — красным, когда он
израсходован. **По шагам** (By step) показывает, откуда пришли время, стоимость и
сбои, сначала самые дорогие. Через API это
`GET /api/v1/workflows/{id}/stats?days=30`.

Когда сценарий за этот период просил у человека согласования, **Согласования**
(Approvals) подводят итог решений: **Одобрено как предложено** (Approved as
proposed), **Изменено до одобрения** (Edited before approval) с медианной долей
изменённого текста, **Отклонено** (Rejected), сколько запросов помечено **Истекло**
(Expired) и **Время до решения** (time to decide) — типичное и то, в которое
уложились 95 из 100. Таблица перечисляет те же цифры по каждому шагу согласования.

Окно — те же дни, отсчитанные по тому, когда человека попросили, а тестовые запуски
исключены. Доля одобренных и доля одобренных как предложено (`acceptance_rate` и
`unchanged_rate` в API; карточка показывает вторую) считаются из запросов, по
которым решение принято, — одобрения или отклонения: запрос, который истёк или был
отменён вместе с запуском, так и не был решён, поэтому он учитывается, но в эти
доли не входит. Шаг, который нельзя редактировать, считается одобренным как
предложено. Цифры говорят, что произошло, и не судят об этом.

Цифры считаются по шагу и по дню, а не по виду сообщения. Чтобы сравнить
категории, направьте каждую в свой шаг согласования.

То, насколько изменила текст правка, измеряется один раз — когда человек решает, —
тем же модулем оценки, что и [`text.compare`](reference/workflow-nodes.md#text-compare),
по символам: `0`, если предложение одобрено без изменений на шаге, который можно
редактировать, вплоть до `1`, когда от него ничего не осталось. У шага, который
нельзя редактировать, у отклонения и у истечения срока такой цифры нет. Правка,
решённая до того, как согласования начали измерять, тоже её не имеет и исключается
из медианы, а не считается отсутствием изменения; когда в периоде не измерено ни
одной правки, карточка говорит **Изменение не измерялось** (Change not measured).

Те же цифры приходят через API в блоке `approvals` статистики. По всем сценариям,
которые вы видите, за выбранные даты `GET
/api/v1/workflow-approvals/stats?from=2026-10-01&to=2026-10-31` даёт итоги и пять
сценариев с наибольшим числом запросов, а карточка [**Исходы
согласований**](console.md#the-dashboard) на «Обзоре» показывает их.

Карточка **Сценарии** (Workflows) на «Обзоре» суммирует то же по всем сценариям,
которые вы видите, за период, заданный на «Обзоре»: запуски, сбои, стоимость и пять
самых занятых сценариев. Над ними она считает запуски, ожидающие человека сейчас, —
согласование или шаг, требующий внимания, — независимо от того, когда они начались.
Через API это `GET /api/v1/workflows/summary?from=2026-10-01&to=2026-10-31`.

Запуск открывается своей длительностью, стоимостью (расход меньше 0,0001 $ читается
как `<$0.0001`, а не ноль) и числом пройденных шагов, а затем — ошибкой, с которой
он завершился, если она была. Рядом — граф, который он выполнил, нарисованный так
же, как редактор рисует запуск: плашка каждого шага, его попытки и его ошибка, а
шаги, до которых он не дошёл, — потускневшие. Движется только страница, открытая, пока
запуск шёл; открытая позже остаётся неподвижной. **Открыть тело цикла** (Open loop
body) показывает итерации цикла так же.

Ответ запуска — его текст, структурированный результат, фрагменты, на которые он
опирался, и сколько файлов он создал, причём сам JSON лежит под **Необработанный
вывод** (Raw output), — и каждый пройденный шаг, итерация за итерацией, стоят рядом.

Список содержит шаги, которые начались, в порядке их начала. Сбои остаются
видимыми, даже если шаг сбоил до старта. Остальные шаги, которые так и не начались,
остаются на холсте; пропущенные выглядят потускневшими. Щелчок по строке шага цикла
показывает его вход и вывод в этой итерации. Запуск, который ещё идёт, обновляется
сам каждые пару секунд, а **Отменить запуск** (Cancel run) останавливает его и
снимает таймеры, которые поставили в очередь его ожидающие шаги. Его **Файлы**
(Files) перечисляют то, что сохранили его шаги, — загрузку, отрисованную страницу,
вывод скрипта, — и каждое можно скачать.

Запуск, ожидающий шага [**Запросить согласование**](reference/workflow-nodes.md#human-approval),
виден на вкладке **Согласования** (Approvals) в «Активности». Когда шаг настроен на
**Разрешить согласующему редактировать** (Let the approver edit) и имеет привязанное
предложение, например черновик ответа, согласующий меняет его в редакторе прямо там
— с кнопками **Восстановить исходное** (Restore original) и **Показать изменения**
(Show changes) — и одобряет свою версию. Затем шаг передаёт дальше `final`, `original`
и `edited`, так что следующий шаг отправляет то, что одобрил человек. Тот, кого шаг не
назвал в числе решающих, видит предложение только для чтения, а запрос, решённый с
изменённой версией, показывает значок **Изменено** (Edited) под **Решено**
(Decided).

В самом запуске завершённый шаг согласования открывается тем, кто и когда его
решил, — **Одобрено** (Approved by) или **Отклонено** (Rejected by) с именем
человека и временем, а когда учётная запись удалена или читатель не может
перечислять участников, только решением и временем, — над выводом шага. Когда
согласующий изменил предложение, **Показать изменения** сравнивает два варианта.
Запрос, срок которого истёк или который отменили вместе с запуском, вместо этого
говорит об этом.

Когда шаг перечисляет **Способы одобрения** (Ways to approve), очередь показывает по
кнопке на каждый, с подписью, которую задал автор, вместо **Одобрить** (Approve);
**Отклонить** (Reject) остаётся. Каждый способ — порт вывода шага, поэтому сценарий
идёт дальше по тому, который нажал согласующий, и решённая строка называет его.
Правка идёт с той кнопкой, которую нажали.

В списке проверка всего черновика читается как **Черновик (тест)** (Draft (test)),
[проверка одного шага](#a-steps-data-pinning-and-testing-one-step) — как **Тест
шага** (Step test) с именем шага, а настоящий запуск — как **Опубликованный**
(Published). **Версия** (Version) может показывать только тесты шагов или исключать
их.

Запуск, начатый из консоли или через HTTP API, читается как **Консоль или API**
(Console or API). **Статус** (Status), **Версия**, **Источник запуска** (Started by)
и **Начало** (Started) — последний час, день, неделя или 30 дней — сужают список
запусков, и он отвечает постранично; каждый фильтр хранится в адресе, поэтому
отфильтрованный список можно передать ссылкой. **Запуски** в списке сценариев
показывают запуски всех сценариев вместе. На странице запуска щелчок по шагу
показывает его **Вход** (Input) и **Вывод** (Output) из этого запуска. Строки,
которые записал [быстрый журнал](#quick-log) шага, видны под шагом.

**Повторить с неудавшегося шага** (Retry from failed step) начинает новый запуск той
же версии и с тем же входом, в котором каждый успешный шаг передаёт дальше то, что
передавал раньше, поэтому выполняются только сбойный шаг и то, до чего он не дошёл,
а запись никогда не делается дважды. Цикл выполняется снова и переиспользует шаги
каждого элемента, которые уже были успешны. **Отладка в редакторе** (Debug in
editor) закрепляет на шагах черновика то, что каждый шаг вне цикла передал в том
запуске, поэтому тестовый запуск начинается с того места, где был тот. Через API
повторяет `POST
/api/v1/workflow-runs/{id}/retry`, а `GET /api/v1/workflow-runs`
принимает `status`, `mode`, `triggered_by`, `created_after` и `created_before`.

**Разобрать** (Resolve) предлагается для шага, требующего внимания, пока его запуск
ещё идёт. Шаг требует внимания, когда он, возможно, уже сделал своё дело и никто не
видел его завершения, или когда он перестал ждать и разбудить его больше нечему.
Диалог называет шаг и говорит, что именно. **Выполнить снова** (Run it again) ставит
шаг в очередь на новую попытку в том же запуске, а у шага, который мог что-то
записать, предупреждает, что так можно сделать это дважды. **Считать неудачным**
(Treat it as failed) — это **Перейти по его маршруту ошибки** (Take its error route),
когда шаг направляет свои ошибки или стоит в цикле, либо **Завершить запуск сбоем**
(Fail the run). Если шаг сообщил результат уже после того, как его перестали ждать,
**Использовать этот результат** (Use that result) продолжает с него. Остальное
в запуске не трогается, поэтому его соседние ветки, согласования и таймеры идут
дальше.

Только человек, начавший запуск, или редактор сценария может разобрать шаг, а в
тестовом запуске только редактор может разобрать шаг или повторить запуск.
Отменённый запуск повторяет только тот, кто его начал, или редактор — те, кто могли
бы его отменить. Через API это
`POST /api/v1/workflow-runs/{id}/steps/{node_run_id}/rerun` с `choice`, и решение
проходит аудит. У запуска, который отменили или который сбоил, нет шага для разбора:
**Повторить с неудавшегося шага** начинает новый запуск. Шаг, завершившийся после
остановки своего запуска, помечается **Завершился после остановки запуска**
(Finished after the run stopped), и повтор переиспользует его.

### Страница журнала { #the-logs-page }

**Журнал** (Logs), в меню **Ещё** в заголовке редактора, перечисляет то, что быстрые
журналы сценария записали во всех его запусках, сначала новые: когда, шаг, его
результат и сообщение. Сузьте строки по **Шагу** (Step), **Результату** (Outcome) и
**Записано** (Written) — последний час, день, неделя или 30 дней, — ищите по
сообщению и включите **Включая тестовые запуски** (Include test runs), которые до
этого исключены. Чтобы увидеть строки одного запуска, вставьте его id в поле
**Запуск** (Run) или введите первые несколько символов (не меньше четырёх);
**Показать только этот запуск** (Show only this run) на строке заполняет его, а
**Открыть в журнале** (See in Logs) на странице запуска открывает журнал с фильтром
по этому запуску. Строка открывает запуск, который её записал. В представлении
запуска собственные строки каждого шага лежат под ним, в порядке записи. API-ключ
организации с `workflows:view` тоже читает их, для запусков публичного
происхождения: см. [Чтение журнала сценария](api.md#reading-a-workflows-log).

Новые строки быстрого журнала показывают имена шагов по умолчанию на языке читателя,
в том числе на «Обзоре». Сохранённый граф запуска распознаёт имена по умолчанию,
включая старые строки. Пользовательские подписи и строки, шаг которых сохранённый
граф больше не распознаёт, сохраняют записанные слова.

### Оповещения { #log-alerts }

Оповещение сообщает людям, когда в журнале чего-то становится слишком много. Под
списком карточка **Оповещения** (Alerts) хранит правила сценария; **Добавить
оповещение** (Add alert) открывает новое. У правила есть название, и оно считает
подходящие строки:

- **Результаты** (Outcomes) — те результаты, что учитываются: записанные журналом
  выбранного шага плюс `error`. Строка, ушедшая через несколько портов, подходит под
  каждый из них.
- **Шаг** (Step) — один шаг или каждый шаг, который пишет в журнал.
- **Сообщение содержит** (Message contains) — необязательные слова, сравнение без
  учёта регистра.
- **Число срабатываний** (Occurrences) и **В течение** (Within) — не меньше стольких
  подходящих строк (от 1 до 1000) за 5, 15, 30 или 60 минут, 4 часа или сутки.

Правило срабатывает не чаще одного раза за окно: после срабатывания оно молчит
столько же, сколько длится окно, затем считает заново с этого момента, и одна строка
никогда не засчитывается двум срабатываниям. Учитываются только настоящие запуски;
строки тестового запуска никогда не поднимают оповещение. Сценарий хранит до 25
правил, и переключатель на каждом ставит его на паузу.

**Кому сообщать** (Who is told) предлагает три варианта: **Владельцу сценария**
(Workflow owner), с которого начинает новое правило, **Администраторам** (Admins)
организации и **Выбранным людям** (Specific people), которых вы укажете; человек,
покинувший организацию, пропускается. Каждый из них получает уведомление в колокольчике и
письмо, насколько позволяют его собственные [настройки
уведомлений](governance.md#alerts), а тот, кто больше не может видеть сценарий,
больше его не видит. Уведомление говорит, сколько строк подошло, а ссылка из него
открывает страницу журнала с фильтром по шагу и результатам правила. Правило с
результатом, которого нет у шага действующей версии, помечается в списке.

Любой, кто может видеть сценарий, видит его правила; тот, кто может редактировать
его — по роли или по выданному доступу к нему, — добавляет, изменяет,
приостанавливает и удаляет их. Правила не входят в публичный API.

## Запуск сценария извне консоли { #starting-a-workflow-from-outside-the-console }

У сценария может быть несколько независимых **триггеров** — например, **Вручную**
(Manual), **Вебхук** (Webhook) и **Расписание** (Schedule). Добавление триггера
сохраняет существующие начала и их связи. Каждый запуск выбирает одно начало и идёт
только по достижимой от него ветке; он никогда не ждёт срабатывания другого
триггера. Общий шаг может читать только те данные, которые доступны от каждого
начала, до него доходящего. Если полезные нагрузки различаются, нормализуйте входы
по отдельности, прежде чем делать шаги общими.

Публикация включает каждое настроенное начало без участия человека от имени
публикующего. У сценария не больше одного начала каждого вида без участия человека. Повторная
публикация сохраняет адреса и учётные данные для сохранённых узлов и убирает
регистрации удалённых. **Триггер** (Trigger) в меню **Ещё** показывает каждое
опубликованное начало и его элементы управления. Переключатель **Активен** (Active)
в заголовке ставит на паузу или возобновляет все регистрации. **Проверить черновик**
позволяет выбрать начало; запросы API могут передавать `entry_node_id`, но настоящие
запросы могут выбирать только начала **Вручную**/API, никогда — триггер без участия
человека.

Версию, которая начинается с триггера **Вручную** (Manual) или **Запрос API**
(API request) либо вовсе без триггера, запускает тот, кому можно её запускать, — от
своего имени: **Запустить** (Start a run) в разделе «Запуски», [HTTP
API](api.md#running-a-workflow) или WebSocket. Каждый запуск проверяется,
оплачивается и проходит аудит так же, как начатый здесь. Эти двери не начинают
другой триггер, и у каждого другого триггера есть своя дверь. Пробный запуск
черновика принимает любой триггер, а **Запустить** открывает его на входе в форме
этого триггера.

**Вручную** — триггер, который человек запускает кнопкой **Проверить черновик**;
**Запрос API** — тот, который вызывает система, и **Триггер** показывает его
эндпоинт и пример запроса. Задайте любому из них **Поля входа** (Input fields) — и
запуск спросит, что ему нужно: **Проверить черновик** и **Запустить** показывают
форму с отдельным полем на каждое вместо JSON, с тем типом, который у поля, а вызов
API, чей вход не подходит, отклоняется с указанием неверных полей. См.
[core.input](reference/workflow-nodes.md#core-input).

Для вложенных объектов и массивов настройте необязательную схему `input_schema` JSON
Schema Draft 2020-12 на триггере **Вручную**, **Запрос API** или **Вызов из сценария**
(Called by a workflow) вместо простых полей. Схема сохраняется вместе с
опубликованной версией, и каждый запуск должен удовлетворять контракту этой версии
до старта. Вызывающие через API и MCP могут проверить тот же контракт до отправки
входа. См. [Контракты входных данных JSON
Schema](reference/workflow-nodes.md#json-schema-input-contracts) о настройке, ссылках
и ошибках проверки. Существующие входы из простых полей и сценарии без контракта
сохраняют прежнее поведение.

### Из чата { #from-the-chat }

Список выбора отвечающего в чате перечисляет под агентами опубликованные сценарии,
которые начинаются с **Сообщения в чате** (Chat message). Когда выбран один, каждое
сообщение начинает его запуск, а триггер передаёт следующим шагам сообщение как
`prompt` вместе с `conversation_id` и `user_id` отправителя. В ветке появляется
карточка со статусом запуска и ссылкой на его шаги, а ответ сценария появляется
после завершения запуска.

Ответ записывается в диалог, когда запуск завершается, открыт ли чат или нет, поэтому
при повторном открытии диалога его можно прочитать. Запуск пишет в диалог, из
которого начался, и никуда больше: чтобы добраться до кого-то ещё, в графе нужен шаг
HTTP или уведомления.

**Открыть чат** (Open chat) в заголовке редактора пробует черновик, начинающийся с
сообщения в чате, не выходя из редактора. Каждое сообщение, отправленное в панели,
начинает тестовый запуск черновика с этим сообщением, запуск открывается на холсте, а
его ответ — текст шага **Результат** (Output) — показывается под сообщением. Это
тестовые запуски, у них нет диалога, в который отвечать, поэтому сказанное в панели
не попадает в настоящий чат. **Новый чат** (New chat) начинает заново с новым id
диалога.

### Через WebSocket { #over-a-websocket }

`/api/v1/ws/workflow-runs` начинает запуск и передаёт потоком его события или следит
за уже идущим. Клиент, потерявший соединение, переподключается с курсором последнего
увиденного события и продолжает ровно с того места, где остановился. События
записываются до отправки, поэтому ничего не теряется и ничего не выполняется
дважды. Сокет заново проверяет сеанс и доступ участника перед каждым кадром и каждым
чтением потока. Кадры описаны в [HTTP
API](api.md#following-a-run-over-a-websocket).

### Вебхук или расписание { #a-webhook-or-a-schedule }

Триггер **Вебхук** (Webhook) получает свой адрес и **Секрет подписи** (signing
secret) при первой публикации версии с ним. Публикация показывает секрет один
раз, а последующие публикации того же узла сохраняют и то и другое; узел
вебхука, удалённый и добавленный заново, получает новый адрес. Отправитель
подписывает точное тело запроса секретом, HMAC-SHA256 в `X-Signature-256`, и
называет каждую доставку в `X-Delivery-Id`; собственные заголовки GitHub тоже
подходят. Триггер передаёт дальше JSON доставки как `body` вместе с её
`delivery_id`. Повторная доставка с тем же идентификатором получает в ответ
первый запуск и не начинает ничего, потому что идентификатор записывается вместе
с принятым запуском в одной транзакции.

Идентификатор не входит в то, что подписывает отправитель, поэтому тот же
подписанный запрос под другим идентификатором в течение 24 часов — тоже копия:
он получает в ответ первый запуск и не начинает ничего, какой бы из двух
заголовков подписи его ни нёс. Идентичное содержимое, отправленное снова после
24 часов, начинает запуск. Отправитель, который намеренно шлёт одно и то же тело
чаще, делает каждую отправку отличающейся — своим идентификатором или временем в
теле, — либо подписывает время: с `X-Signature-Timestamp` (секунды Unix) подпись
покрывает `{timestamp}.{body}` и отклоняется, если расходится с часами сервера
больше чем на пять минут.

Доставки, принятые до того, как стали записываться подписанные дайджесты,
сохраняют дедупликацию по идентификатору доставки. Их подписанные копии под
другим идентификатором нельзя распознать по этим старым строкам; обнаружение
копий по подписи начинается с доставок, записанных новой версией.

Триггер **Расписание** (Schedule) запускается через равные промежутки, ежедневно
в заданное время или по cron-выражению, в часовом поясе сценария (UTC, если в его
**Настройках** (Settings) не указан другой) и не чаще раза в минуту. Он
срабатывает в свой тик, а не на следующем минутном обходе после него. Его
**Входные данные** (Input) — то, с чем начинается каждый запуск; они передаются
дальше как `input` рядом с `fired_at` тика. Тик, который застаёт последний запуск
ещё идущим, пропускается, а не ставит второй запуск за ним; тик, который
отклоняет квота приёма, ждёт следующего.

Оба работают от имени участника, опубликовавшего версию, и его доступ проверяется
заново при каждом срабатывании. Вебхук, чей участник больше не может запускать
сценарий, отклоняет свои доставки, а такое расписание выключается и записывается
в журнал аудита. **Приостановить** (Pause) на панели **Триггер** (Trigger)
останавливает любой из них без публикации, а **Новый секрет** (New secret)
заменяет секрет вебхука; старый перестаёт проверять подписи сразу.

Тела запросов вебхука ограничены по размеру во время потоковой передачи, даже без
Content-Length. Тестовые доставки останавливаются на лимите закреплённых данных в
64 КБ; живые доставки вебхука и GitHub используют `WORKFLOW_RUN_MAX_INPUT_BYTES`.
Шаг **Ответ на вебхук** (Respond to webhook) со статусом 204, 205 или 304 не отправляет тело, как
требует HTTP, сохраняя при этом разрешённые заголовки. Преобразование PDF в
изображения отклоняет документы больше 2 000 страниц, прежде чем перечислять
размеры их страниц, даже если запрошена только одна страница.

### Когда запись таблицы добавлена, изменена или удалена { #when-a-table-record-is-added }

Триггер **Запись таблицы** (Table record) называет таблицу, `events` записи, на
которых он запускается, — добавление, изменение, удаление, — и фильтры по записи
в том виде, в каком она добавлена или изменена, или в каком была до удаления;
неважно, пришло изменение из консоли, через API, от агента или из шага таблицы
другого сценария. Изменение запускает его, только когда изменился выбранный
столбец, если столбцы таблицы выбраны.

Он передаёт дальше запись: её `record_id`, `event`, `values` по идентификаторам
столбцов, те же значения как `fields` по названиям, выбор — как название его
варианта, `before` и `changed` — столбцы для изменения или удаления, и `author_id`
того, кто это сделал. Публикация требует доступа на чтение таблицы, и ничто
сделанное до публикации его не запускает.

Запуск, начатый так, несёт цепочку триггеров, через которую он прошёл, поэтому
сценарий, который пишет обратно в таблицу, чей триггер его запустил, блокируется,
а не зацикливается.

Собственные **Триггеры** (Triggers) таблицы перечисляют сценарии, которые с неё
запускаются, приостанавливают и возобновляют их и показывают, что каждый решил по
каждой записи. См. [Виртуальные таблицы](virtual-tables.md#triggers).

### Из формы { #from-a-form }

**Проверить черновик** (Test draft) открывает предпросмотр формы для одного
триггера **Форма** (Form), доступный только участникам, выполнившим вход. Его URL включает
узел входа, поэтому независимые формы остаются разными. Отправка использует
сохранённый черновик и начинает пробный запуск с введёнными ответами; откройте
этот запуск, чтобы посмотреть его результат. Предпросмотр не публикует публичную
ссылку. Читатель может осмотреть страницу, но выполнить черновик не может.

Шаг **Форма** (Form) показывает ссылки для проверки и для опубликованной формы рядом со
своей конфигурацией. **Оформление** (Appearance) задаёт акцентный цвет,
стандартную или широкую ширину страницы и макет — карточкой или простой.
**Предпросмотр оформления** (Preview appearance) использует тот же отрисовщик,
что и публичная страница. Описания поддерживают Markdown; поля ввода, текст
кнопки и сообщение об успехе остаются настраиваемыми. Пробные запуски по-прежнему
могут выполнять действия сценария.

Триггер **Форма** (Form) даёт сценарию публичную страницу: заголовок, описание и
по одному полю на каждое объявленное поле, с типами как у полей **Вручную**
(Manual), и собственными словами на кнопке и после отправки. Публикация создаёт
страницу, а **Триггер** (Trigger) показывает её ссылку, чтобы скопировать или
открыть. Любой, у кого есть ссылка, заполняет её без входа, и каждый ответ,
подходящий под поля, начинает один запуск от имени участника, опубликовавшего
форму. Шаги после него читают ответы как `payload`, а страница запусков говорит,
что его начала форма.

Ссылка — единственные учётные данные страницы, и она переживает каждую
публикацию того же узла. **Новая ссылка** (New link) заменяет её, и старая после
этого отвечает так, как будто формы нет; пауза триггера закрывает страницу.
Ответы, которые не подходят, перечисляются на странице и ничего не начинают,
скрытое поле ловит скрипты, а каждая форма принимает не больше
`RATE_LIMIT_FORM_SUBMISSIONS_PER_MINUTE` ответов в минуту. См.
[trigger.form](reference/workflow-nodes.md#trigger-form).

### Из GitHub { #from-github }

Триггер **GitHub** запускает сценарий, когда что-то происходит в одном
репозитории: задача, комментарий, пул-реквест или его проверка, пуш, релиз или
запуск Actions — в зависимости от того, что названо в **События запуска** (Starts
on), и только перечисленные **действия**, например `opened`, если они указаны.
Публикация выдаёт ему собственный адрес и секрет подписи. Если включено
**Настроить вебхук за меня** (Set up the webhook for me), а учётная запись GitHub
организации подключена с разрешением управлять вебхуками, публикация
регистрирует хук в репозитории и регистрирует его снова при каждой следующей
публикации; иначе она один раз показывает секрет, чтобы вставить его вместе с
адресом из **Триггера** в **Settings > Webhooks** репозитория.

Каждая доставка, которую GitHub подписывает для этого репозитория, события и
действия, начинает запуск от имени участника, опубликовавшего сценарий, с
`event`, `action`, `repository`, `sender` и всем `payload`. Повторная доставка
получает в ответ свой первый запуск, а всё остальное — включая `ping` от GitHub —
пропускается. **Новый секрет** (New secret) заменяет секрет и снова регистрирует
хук там, где его настроила учётная запись. См.
[trigger.github](reference/workflow-nodes.md#trigger-github).

### Из письма { #from-an-email }

Триггер **Gmail** запускает сценарий, когда письмо приходит в ящик Gmail
организации — тот, что подключён через портал **Gmail**. Панель шага говорит,
подключён ли ящик, и подключает его, а публикация отклоняется, пока он не
подключён. Ящик читает тот же опрос, что запускает триггеры Gmail у агентов,
каждую минуту, и каждое новое письмо, подходящее под все заданные фильтры —
**Тема содержит** (Subject contains) и **Отправитель содержит** (Sender contains)
без учёта регистра, а **Ярлык** (Label) точно, — начинает запуск от имени
участника, опубликовавшего сценарий.

**Проверять новую почту каждые** (Check for new mail every) в блоке ящика шага
меняет этот темп (1, 5, 15, 30 или 60 минут). Это настройка ящика, и она
действует для каждого триггера на этом ящике.

**Отправитель содержит** (Sender contains) читает адрес отправителя и никогда
отображаемое имя: `@acme.com` совпадает ровно с этим доменом, но не с его
поддоменами, полный адрес совпадает с этим адресом, а другой текст — с частью
адреса. Если фильтр задан, письмо должно ещё пройти проверку подлинности
отправителя — пройден DMARC или домен отправителя подписал письмо через DKIM, —
поэтому поле `From`, которое может набрать кто угодно, запуск не начнёт. Письма с
ярлыками `SENT`, `DRAFT`, `SPAM` или `TRASH` — не новые поступления и ничего не
начинают, если **Ярлык** (Label) не назвал один из них.

Запуск получает `sender`, `to`, `subject`, `text`, `snippet`, `labels` и
`message_id` ящика, а также цепочку, которой принадлежит письмо: `thread_id`,
`rfc_message_id` (заголовок `Message-ID`), `in_reply_to`, `references`,
`received_at` и тело `html`. Три поля заголовка пишет отправитель, поэтому ответ
можно собрать в цепочку с их помощью, но они ничего не доказывают о том, кто
отправил письмо. Письмо, прочитанное дважды, начинает свой запуск один раз, а
письмо, для которого у организации ещё не было места, прочитается снова через
минуту. См. [trigger.gmail](reference/workflow-nodes.md#trigger-gmail). Чтобы
прочитать тело `html` как текст, ссылки или то, что выберет CSS-селектор,
привяжите его к [`html.parse`](reference/workflow-nodes.md#html-parse).

Триггер **Outlook** делает то же для ящика Microsoft 365 организации,
подключённого через портал **Outlook**. Microsoft Graph читается по одной папке
за раз, поэтому шаг называет **Папку** (Folder), которую он отслеживает, —
входящие, если не указано иное, — и, чтобы читать общий почтовый ящик, который
может открыть подключённая учётная запись, **Общий почтовый ящик** (Shared
mailbox). Фильтры — **Тема содержит**, **Отправитель содержит**, **Есть
вложения** (Has attachments), **Важность** (Importance) и **Категория**
(Category). Когда папка читается впервые, отсчёт начинается с момента, когда
сценарий был опубликован или последний раз включён, поэтому письма, которые там
уже лежали, ничего не начинают.

Если назван общий почтовый ящик, который может открыть предоставленный
организации доступ Microsoft, требуется разрешение управлять подключениями — как
и для триггеров Outlook у агентов; оно нужно при каждой публикации, где такой
ящик назван, потому что опубликовавший становится участником, от имени которого
читается ящик, и письмо, дошедшее до сценария, чей публикующий такого доступа уже
не имеет, не начинает запуск. Если Outlook сообщает, что папку больше нельзя
прочитать, сценарий выключается, а журнал аудита объясняет причину.

Прежде чем обновиться до выпуска с этой проверкой, администратор может найти
триггеры Outlook, которые она остановит: те, что читают общий почтовый ящик для
публикующего, который не Owner, Admin или Builder и потому не имеет `mcp:manage`.
Каждый требует повторной публикации участником с этим разрешением или повышения
роли его публикующего. Выполните на базе данных экземпляра:

```sql
SELECT o.name AS organization,
       w.name AS workflow,
       u.email AS publisher,
       m.role AS publisher_role,
       node -> 'config' ->> 'mailbox' AS shared_mailbox
FROM workflow_exposures AS e
JOIN workflow_versions AS v ON v.id = e.workflow_version_id
JOIN workflows AS w ON w.id = e.workflow_id
JOIN organizations AS o ON o.id = e.organization_id
JOIN users AS u ON u.id = e.execution_principal_user_id
LEFT JOIN organization_members AS m
  ON m.organization_id = e.organization_id AND m.user_id = e.execution_principal_user_id
CROSS JOIN LATERAL jsonb_array_elements(v.graph -> 'nodes') AS node
WHERE e.adapter = 'outlook'
  AND e.is_active
  AND (node ->> 'id')::uuid = e.node_instance_id
  AND coalesce(node -> 'config' ->> 'mailbox', '') <> ''
  AND NOT u.is_app_admin
  AND coalesce(m.role, '') NOT IN ('owner', 'admin', 'builder');
```

Запуск получает те же поля, что и запуск Gmail, причём в `labels` лежат категории
письма, а в `mailbox` — общий почтовый ящик, из которого оно пришло. См.
[trigger.outlook](reference/workflow-nodes.md#trigger-outlook).

Оба почтовых триггера принимают внешние данные: любой может отправить письмо в
ящик, поэтому привязывайте то, что запуск с ним делает, так же, как для вебхука.

`attachments` письма перечисляет имя каждого файла, объявленный тип и размер;
ящик перечисляет не больше 20 на письмо, а тело `text` или `html` читается до
20 000 символов. Запуск, начатый ящиком, сохраняет их как файлы запуска, и каждый
несёт свой `file` и `stored: true`. Из перечисленных вложений рассматриваются
только первые 10, вместе не больше 25 МиБ, и каждое должно укладываться в лимит
размера загрузки в чат, список разрешённых типов файлов и квоту хранилища
организации.

Вложение, оставленное за пределами, несёт `reason`: `too_many` (дальше первых
10), `too_large`, `type_not_allowed`, `quota` или `unreadable` — ящик ответил на
него 400, 401, 403 или 404, либо его доступ отсутствует, выключен или не может
быть продлён. Пробный запуск ничего не читает из ящика, поэтому его вложения —
`not_fetched`. Когда ящик отказывает так, что это может исправить повтор, шаг
завершается ошибкой `MAIL_ATTACHMENT_UNREACHABLE` и повторяется.

### Из сообщения в канале { #from-a-channel-message }

Триггер **Сообщение в канале** (Channel message) передаёт сценарию сообщения
бота Slack, Mattermost или Telegram. Каждое сообщение, на которое бот ответил бы
своим агентом, — сообщение прошло политику доступа бота, отправитель сообщения был
допущен, а в канале оно назвало бота, — начинает запуск от имени участника,
опубликовавшего сценарий, когда подходит под **Где** (Where) и **Только если
сообщение содержит** (Only when the message contains). Сообщение, которое называет
агента через
`@handle`, всё равно доходит до этого агента, а на неподходящее, как и раньше,
отвечает агент бота, поэтому сценарий может забирать возвраты, а остальное
оставлять.

Триггер передаёт дальше `text`, `sender` — вместе с участником, которого
отправитель связал, если связал, — и `channel_id` и `thread_id`, которые
принимает шаг **Отправить сообщение** (Send a message) той же платформы, так что
ответ попадает в ветку, откуда пришло сообщение. Триггеры Slack и Mattermost
передают ветку даже для сообщения верхнего уровня, потому что само сообщение её
создаёт, поэтому привязанный ответ уходит в ветку; триггер Telegram передаёт
тему только внутри темы форума.

Шаг **Отправить сообщение**, добавленный после триггера **Сообщение в канале**,
начинает работать как бот триггера, с привязанными `channel_id` и `thread_id`,
когда платформы совпадают. Сообщения бота начинают не больше одного сценария, а
чтобы слушать бота, нужно `channels:manage`, проверяемое заново на каждом
сообщении: как только публикующий теряет его, отвечать снова начинает собственный
агент бота. Голосовая заметка приходит своим транскриптом; другие вложения дальше
не передаются. См.
[trigger.channel_message](reference/workflow-nodes.md#trigger-channel-message).

### Когда его вызывает другой сценарий { #when-another-workflow-calls-it }

Триггер **Вызов из сценария** (Called by a workflow) превращает сценарий в шаг,
который выполняют другие: общая логика — обогатить лид, завести тикет — хранится
в одном месте. Он объявляет свои поля так же, как **Вручную** (Manual), а шаг
**Запустить сценарий** (Run a workflow) другого сценария, который предлагает
только сценарии, опубликованные так, запускает его с привязанными входными
данными, сначала проверив их по этим полям.

Шаг ждёт вызванный запуск и передаёт дальше его `output` или продолжает сразу,
если **Дождаться завершения** (Wait for it to finish) выключено. Вызванный запуск
связан с вызывающим в обе стороны: его страница говорит **Вызван из:** (Called
by) этого запуска, а строка шага на странице вызывающего открывает запуск,
который он начал, — и он показывается на страницах запусков, как любой другой.
Запуск, начатый сценарием ошибок, говорит, сбой какого запуска его начал. Вызов
обратно в сценарий, который уже выполняется в цепочке, или глубже пяти вызовов
отклоняется.

Вызванные сценарии наследуют оставшийся бюджет запуска вызывающего и более
ранний срок. Их расходы идут в общий итог вызывающего; `own_cost` показывает
прямые расходы вызывающего для тех, кто собирает записи запусков, не считая
потомков дважды. При конечном бюджете вызывающего **Дождаться завершения** должен
оставаться включённым.

Отмена вызывающего или исчерпание его бюджета отменяет каждый незавершённый
вызванный им запуск и каждый запуск, вызванный теми, вместе с их запросами
согласования и вопросами. Вызванный запуск, чей шаг выполняется в этот момент,
останавливается перед следующей отправкой на выполнение — как и тот, чей
вызывающий потерял доступ; внешний запрос, уже находящийся в пути, может
завершиться.

Повтор неудавшегося вызова переиспользует успешные шаги его исходного,
замороженного дочернего запуска, а не повторяет их эффекты. Исходный дочерний
запуск, если он всё ещё идёт, должен сначала завершиться или быть остановлен.
Файловые выводы явно импортируются в вызывающий сценарий, а доступ вызываемого
перепроверяется, когда ожидающий вызов возобновляется.

Ежедневный график вызывающего и статистика по шагам тоже включают расходы
вызванных запусков.

Восстановление останавливается, если успешный шаг потерял свой вывод, либо
вызванный запуск был удалён или имеет циклическую историю повторов. Оно не
повторяет эффекты, чтобы воссоздать эту историю. Отмена вызванного запуска,
исчерпание бюджета и отозванные полномочия тоже остаются сбоями, которые не может
скрыть ветка ошибок.

### От агента { #from-an-agent }

Для новых инструментов агента привяжите MCP-сервер платформы AgenticOS и выберите
нужные инструменты: обнаружение сценариев, `run_workflow` и чтение выполнения.
Объявленные входные данные опубликованного сценария передаются как `fields`;
возвращённый запуск нужно читать до его завершения. Вызовы MCP используют
разрешения запрашивающего участника и сохраняют согласование на запись. Агент,
выполняющийся внутри сценария, должен вызывать другой сценарий через узел
`workflow.run`. Существующие привязки возможности «Сценарии» остаются
совместимыми: они сохраняют свои явные идентификаторы сценариев, лимит ожидания и
выданные доступы к действиям страницы.

Запуск, за которым не стоит участник (посетитель виджета, встраивания или
размещённой страницы, отправитель из несвязанного канала, доставка событийного
триггера агента), не начинает ни одного сценария.

### Из приложения { #from-an-app }

Опубликованная [размещённая страница](artifacts.md#actions) может запустить
сценарий, который привязал её агент и чей триггер — **Вручную** (Manual)
или **Запрос API** (API request). Страница только спрашивает. Участнику, который
её просматривает, показывают диалог с собственным именем сценария и каждым
значением входных данных, и запуск начинается только после подтверждения. Запуск
принадлежит этому участнику: его доступ, его бюджет и его страница запусков — с проверками,
оплатой и аудитом, как у запуска, начатого кнопкой **Запустить** (Start a run), и с той же
квотой приёма.
Запуск, за которым не стоит участник или который пришёл из сеанса, где выполнен
вход от имени другого пользователя, не начинается.

Страница запусков говорит, что источник такого запуска — **Страница** (A page), и
**Источник запуска** (Started by) фильтрует по нему; в API его `triggered_by`
равен `app`. Запуск также записывает страницу и версию, которую смотрел участник,
и повтор их сохраняет. Страница читает обратно только статус запуска, его ответ и
первую строку ошибки.

### Когда другой сценарий завершается сбоем { #when-another-workflow-fails }

Триггер **Сбой сценария** (On failure of a workflow) делает сценарий сценарием
ошибок. Выбранный как сценарий ошибок другого сценария в его **Настройках**
(Settings), он запускается один раз на каждый настоящий запуск того сценария,
который завершился сбоем, с `run_id` этого запуска, его `workflow_id` и
`workflow_name`, `step_id` и `step_name` шага, который завершился сбоем, и `error`, с которым
тот закончился. Он выполняется от имени участника, который его выбрал, и этот
участник должен по-прежнему иметь право его запускать. Пробный запуск ничего не
начинает, и сбой запуска, который сам является сценарием ошибок, тоже, поэтому
сбойный сценарий ошибок никогда не запускает себя снова.
## Когда что-то идёт не так { #when-something-goes-wrong }

**Что обещает запуск.** Результат шага и отправка следующих за ним шагов
сохраняются вместе, поэтому воркер, остановившийся между шагами, ничего не
теряет: другой подхватывает запуск с того места. Воркер, остановившийся внутри
шага, оставляет попытку, конца которой никто не видел. Шаг, который безопасно
повторить, выполняется снова. Запись в таблицу повторяет свою первую запись
по квитанции, а не пишет дважды, а уведомление отправляется один раз. Шаг,
который мог уже что-то сделать вовне и больше ничего не обещает, — запуск агента
из таких, — сам по себе никогда не повторяется: запуск останавливается как
**Требует внимания** (Needs attention), чтобы модель не была оплачена дважды и
сообщение не ушло дважды без чьего-либо решения.

Больше ничего не выполняется ровно один раз. HTTP-вызов, загрузку или запись
файла могут сделать снова после такой остановки, поэтому принимающей системе,
которая не должна увидеть запрос дважды, нужен собственный ключ идемпотентности.
Что обещает повтор каждого шага, перечислено в
[справочнике узлов](reference/workflow-nodes.md).

| Что вы видите | Почему | Что делать |
|---|---|---|
| **Требует внимания** | Шаг, который мог уже что-то сделать, был прерван или перестал ждать, и разбудить его нечем | Проверьте, случился ли его эффект, затем **Разобрать** (Resolve) шаг в запуске: выполните его снова, используйте результат, о котором он сообщил позже, переведите его по маршруту ошибки или завершите запуск сбоем. Отмена запуска и затем **Повторить с неудавшегося шага** (Retry from failed step) начинает заново |
| `PRINCIPAL_REVOKED` | Участник, от имени которого работает запуск, потерял доступ, его учётная запись была деактивирована или API-ключ, начавший запуск, был отозван | Пусть участник, который может запускать сценарий, опубликует его снова, чтобы триггер работал от имени этого участника |
| `WORKFLOW_TRIGGER_MISMATCH` | Запуск запросили через дверь, которой у его действующего триггера нет: вручную или через API для сценария, который начинается с вебхука, либо в чате для того, который начинается не с сообщения в чате | Запустите его так, как говорит его триггер, или проверьте черновик, который принимает любой триггер |
| `INVALID_BINDING` | Значение не подошло к полю, к которому его привязали | Ошибка шага называет поле; исправьте привязку или значение выше по потоку |
| `REVISION_CONFLICT` | Кто-то изменил запись после того, как шаг её прочитал | Направьте ошибку шага на свежее чтение через `error.handle` |
| История триггера таблицы говорит **Заблокировано** (Blocked) | Запуск запустил бы себя снова, или его цепочка оказалась слишком глубокой | См. [Триггеры](virtual-tables.md#triggers) |
| Вебхук отвечает `403` | Подпись не совпадает с телом, или участник, от имени которого он работает, больше не может запускать сценарий | Подпишите точные отправленные байты текущим секретом или попросите участника, который может его запускать, опубликовать сценарий снова |

## Клавиатура и доступность { #keyboard-and-accessibility }

У каждой части редактора есть путь, которому не нужен указатель. Выбор шагов — это
список, по которому вы перемещаетесь стрелками и выбираете клавишей Enter, каждый
элемент управления, показанный только значком, несёт подпись, которую произносит
экранный диктор, а холст принимает фокус клавиатуры, так что по его шагам и связям
можно проходить клавишей Tab. Связь можно создать с клавиатуры: начните её от
узла, а затем завершите на совместимой цели.

Сочетания клавиш холста срабатывают, только пока фокус внутри редактора, поэтому
они никогда не отнимают клавишу у поля в другом месте страницы:

Перетаскивайте левой кнопкой мыши, чтобы выделять объекты. Удерживайте Shift при
перетаскивании, чтобы панорамировать; средняя и правая кнопка тоже панорамируют.
`Ctrl`/`Cmd` + `A` выделяет каждый объект в текущей области, включая заметки в
корне.

За наблюдаемыми запусками в активный шаг идёт движущийся импульс, а по карточке
этого шага бежит рамка. Короткая волна завершения помогает читать быстрые
запуски, не меняя их фактический статус и время. Исторические запуски остаются
неподвижными; системные настройки уменьшения движения отключают анимацию.
Длительность, стоимость и число завершённых шагов выровнены в сводке, а время
начала стоит рядом со статусом.

| Клавиши | Что делает |
|---|---|
| `Tab` | Открыть выбор шага |
| `Ctrl`/`Cmd` + `Enter` | Пробный запуск черновика, где бы на странице ни был фокус |
| `Ctrl`/`Cmd` + `Z` | Отменить |
| `Ctrl`/`Cmd` + `Shift` + `Z` или `Ctrl`/`Cmd` + `Y` | Повторить |
| `Ctrl`/`Cmd` + `C` | Копировать выделенное |
| `Ctrl`/`Cmd` + `X` | Вырезать выделенное |
| `Ctrl`/`Cmd` + `V` | Вставить со смещением, чтобы не накрыть оригинал |
| `Delete` или `Backspace` | Удалить выделенное |
| `Escape` | Отменить рисуемую связь |
| `?` | Показать эти сочетания |

Вставка получает новые идентификаторы и переназначает привязки среди
скопированных шагов, поэтому вставленные шаги читают друг из друга, а не из
оригиналов. Любое сочетание редактирования не действует, пока редактор доступен
только для чтения, — опубликованная версия или **Только просмотр** (View only);
`Escape` по-прежнему отменяет случайно начатую связь, а `?` по-прежнему показывает
сочетания.

Копирование и вставка имеют четыре ограничения:

- **Привязанный шаг читает оттуда, откуда читал раньше.** Скопированный шаг
  сохраняет свои привязки. Шаг, который читает из шага, не скопированного вами,
  продолжает читать из оригинала, но ничто не соединяет вставленный шаг с ним,
  поэтому он не проходит проверку, пока вы их не соедините. Выделите оба шага,
  чтобы скопировать пару, — и копия будет читать из своего собственного
  вышестоящего шага.
- **Связь переезжает только вместе с двумя своими шагами.** Выделить связь
  отдельно и скопировать — ничего не даст.
- **Сочетания принадлежат холсту.** Они работают, пока фокус на холсте, и щелчок в
  любом его месте — по шагу, пустому холсту, связи — оставляет его там. Фокус в
  настройках шага или в выборе шага оставляет клавиши этим полям, поэтому щёлкните
  по холсту, прежде чем их нажимать.
- **Вставка попадает только туда, куда её положила бы палитра.** Внутри цикла
  вставка триггера отклоняется, как и цикл, который вместе со своими циклами
  оказался бы вложен глубже трёх уровней. Вся вставка отклоняется, и буфер обмена
  её сохраняет, поэтому откройте верхний уровень или цикл помельче и вставьте там.

Вложения изображений у агента делят потолок в 20 МБ, проверяемый до загрузки
каждого файла, включая повторяющиеся ссылки. Результаты MCP вырезают раскрытые
заголовки аутентификации и учётные данные из текста и вложенных данных. Имена
файлов сценария нормализуются централизованно перед сохранением, расширения
сохраняются в пределах 255 символов. Поля CSV могут использовать настроенный для
шага лимит байтов файла — до 50 МБ; отказы разборщика типизированы.

Цикл измеряет свои последние переданные результаты и необработанные ошибки в SQL,
прежде чем их загрузить. `WORKFLOW_FOREACH_MAX_OUTPUT_BYTES` по умолчанию равен
10 МиБ, включая накладные расходы коллекции; при превышении шаг завершается
ошибкой `FOREACH_OUTPUT_TOO_LARGE`. Передавайте меньшие значения или файловые
ссылки для больших результатов. Сводка, сгенерированный ключ которой совпадает с
полем группы, завершается ошибкой `SUMMARY_KEY_COLLISION`.

Входные данные запусков, конфигурации черновиков и закреплённые выводы должны
помещаться в JSONB PostgreSQL. Результат обработчика, который нельзя сохранить,
становится `INVALID_NODE_OUTPUT`, без автоматического повтора и с сохранением
понесённых расходов. Внешнее действие могло уже завершиться, поэтому проверьте
его, прежде чем вручную повторять узел.

Встроенные результаты узлов делят `WORKFLOW_NODE_MAX_OUTPUT_BYTES` (10 МиБ по
умолчанию), включая результат попытки, вывод запуска и ответ вебхука вместе.
Более крупные результаты завершаются ошибкой `NODE_OUTPUT_TOO_LARGE`, сохраняют
расходы и не повторяются автоматически. Шаг **Разделить** (Split) проверяет свой
развёрнутый размер (не больше 10 000) до копирования элементов и консервативно
ограничивает повторяющиеся поля прогнозируемыми байтами; превышение любого из
пределов возвращает `SPLIT_OUTPUT_TOO_LARGE`. Для больших данных используйте
файловые ссылки.

Поверхностная предварительная проверка полей модели тоже отклоняет повторяющиеся
большие значения, прежде чем сериализация скопирует весь результат.

Сокеты сценариев сохраняют идентичность API-ключа организации и потолки его
областей действия на каждом кадре и каждом опросе потока. Ключ только для
просмотра не может начинать запуски, а ключи не могут присоединяться к личным
запускам участника или писать в личные чаты. Запуски, начатые ключом, сохраняют
потолок ключа для воркеров; отзыв закрывает поток при следующем опросе.

Галереи навыков и контекста встроенного агента загружают каждую страницу
метаданных и предлагают «Повторить» при сбое. Новые входные данные для оценок
подчиняются тем же границам JSONB и байтов, что и приём запусков; старые слишком
большие кейсы остаются читаемыми для удаления. Неудачные пакеты PDF-файлов или
файлов песочницы удаляют файлы, сохранённые раньше в этом пакете, сохраняя
существующие файлы. Скрипт, сообщивший об ошибке, всё равно сохраняет свой
диагностический журнал.

## Итог { #recap }

- Сценарий — это **черновик, который вы редактируете, и опубликованная неизменяемая
  версия, которая выполняется**; начните его с триггера или шаблона, а
  **Дублировать** (Duplicate) копирует черновик в новый сценарий.
- **Выбор шагов** добавляет шаги — из **+**, из вывода шага или по
  правому щелчку; **Холст** соединяет их и отклоняет связь между
  несовместимыми портами.
- Связь задаёт **порядок**, а привязки несут **значения**; соединение портов
  одинаковой формы создаёт привязки за вас.
- Параметр — это **значение или данные из шага**: **Данные** (Data) читают его из
  достижимого, совместимого по типу вышестоящего вывода или вставляют в текст.
- Черновик **сохраняется сам**, а правка из двух мест поднимает баннер с
  **Оставить мои изменения** (Keep my changes) или **Загрузить их версию** (Load
  their version).
- **Опубликовать** (Publish) блокируется, пока стоит проблема, и перепроверяет на
  сервере; прошлые версии остаются доступными для чтения, а **Восстановить в
  черновик** (Restore to draft) делает одну из них черновиком снова.
- У каждого действия есть **путь с клавиатуры**, а сочетания редактирования не
  действуют в опубликованной версии, доступной только для чтения, или в **Только
  просмотр** (View only).
- У сценария может быть несколько независимых **триггеров**, например «Вручную»,
  «Вебхук» и «Расписание». Добавление триггера сохраняет существующие начала и их
  связи. Каждый запуск выбирает одно начало и идёт только по достижимой от него
  ветке; он никогда не ждёт срабатывания другого триггера. Общий шаг может читать
  только данные, доступные из каждого начала, которое до него доходит.
  Нормализуйте входные данные отдельно, прежде чем делить шаги, если их полезные
  нагрузки различаются.
- **Политика** шага задаёт его попытки, лимит времени и то, уходят ли его сбои
  через порт **Ошибка** (Error); тело шага **Для каждого** (For each) выполняется
  от **Элемент цикла** (Loop item) до **Результат итерации** (Loop result) по
  одному разу на элемент.
- **Запуски** (Runs) перечисляют каждый запуск, кнопка **Запустить** (Start a
  run) проверяет черновик или выполняет опубликованную версию, а запуск
  показывает свой граф шаг за шагом так, как он происходил.

Новые автоматизации можно отправлять через `prepare_workflow_draft`: одно
согласование атомарно создаёт приватную таблицу и полный граф. Неудачная
проверка не оставляет ни того, ни другого ресурса. `check_workflow_draft`
проверяет граф и его ссылки на ресурсы, не выполняя обработчики и не требуя
согласования записи. Он явно сообщает, что интеграции остаются непроверенными.
Пробные запуски с действиями по-прежнему требуют согласования; проверки расписания
принимают обычные примерные входные данные и сами подставляют метку времени
события и настроенные значения по умолчанию. Страница запуска отличает проверки
скелета от проверки интеграций.


### Черновики напоминаний { #follow-up-drafts }

В диалоге создания шаблона **Дождаться ответа** (Await a reply) можно также включить
**Подготовить черновик напоминания после дедлайна** (Prepare a follow-up draft after the
deadline). Выберите существующую модель и максимальную стоимость одного
черновика. Начиная сценарий, предоставьте контекст, который должен использовать
черновик. Этого агента запускает только успешно проверенная ветка дедлайна;
проверенный ответ её пропускает, а сбой почтового ящика означает, что проверка не прошла. У
агента нет инструментов. Его черновик сохраняется в результате сценария, и вы
получаете уведомление со ссылкой туда. Просмотрите текущую цепочку, прежде чем
что-то отправлять. Этот шаблон не создаёт черновик в Gmail/Outlook и не
отправляет почту.

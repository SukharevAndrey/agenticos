# Безопасность { #security }

Эта страница — то, что передаёт проверка безопасности в духе HIPAA или SOC 2: границы
доверия, какие данные покидают экземпляр и кому они достаются, что и где шифруется, и
матрица мер защиты, которая для каждой меры защиты называет механизм в этой кодовой
базе, который её выполняет, и тест, который её удерживает.

Она описывает то, что **есть**, а не то, что было бы хорошо. Строка без механизма прямо
об этом говорит и ссылается на задачу, которая его построит. О том, как сообщить об
уязвимости, и о чек-листе усиления защиты для эксплуатации см.
[`SECURITY.md`](https://github.com/vstorm-co/agenticos/blob/main/SECURITY.md) в корне
репозитория; здесь всё остальное, в одном документе.

Две соседние страницы отвечают на вопросы, которые проверка задаёт следующими, и здесь
не повторяются: [Защита данных](data-protection.md) — о том, где живут персональные
данные, до чего на самом деле добирается удаление и какие пробелы ещё открыты, и
[Лицензии](licenses.md) — о каждом стороннем компоненте, который поставляют образы.

## Модель угроз { #threat-model }

Платформа размещается на собственной инфраструктуре и обслуживает несколько организаций.
Допущение дизайна: инфраструктура оператора заслуживает доверия, а каждый запрос в неё —
нет, поэтому важны те границы, которые запрос пересекает на пути к данным.

| Граница | Что её пересекает | Доверяем ли дальней стороне? |
|---|---|---|
| Браузер → BFF (обработчики маршрутов Next.js) | Cookie сеанса, заголовок организации, ввод форм | Нет — но BFF не проверяет cookie: он читает `httpOnly` `agenticos_access_token` и пересылает его как bearer-заголовок (`frontend/src/lib/platform-proxy.ts`). Это граница пересылки учётных данных; проверка — дело API |
| BFF → API (FastAPI) | JWT, привязанный к сеансу в БД, заголовок `X-Organization-Id` | Нет — токен проверяется на каждый запрос, сеанс проверяется на отзыв, а организация определяется по токену |
| API → PostgreSQL / Redis | Запросы и чтения кэша, по TLS, когда он настроен | Да — хранилище принадлежит оператору; что оно защищает при хранении, сказано в разделе «Что и где шифруется» |
| API / воркер → провайдеры моделей, каналы, MCP-серверы, поисковые сервисы, Logfire | Промпты, вызовы инструментов, запросы, ответы, трассы | Нет — это третьи стороны; что до них доходит, решается для каждого агента, кроме трассировки всего экземпляра (ниже) |
| Браузер ↔ провайдер реального времени ([голосовой звонок](voice.md) по WebRTC) | Микрофонный звук звонящего и произнесённый ответ агента | Нет — в браузере нет учётных данных провайдера: сервер отвечает на его предложение SDP, предложение, открывающее канал данных, отклоняется, и клиентский секрет не выпускается никогда. Инструменты, согласования и транскрипты работают на sideband-канале сервера |
| Воркер → коннекторы (Google Drive, S3, …) | Учётные данные, расшифрованные из хранилища секретов, полученные документы | Нет — учётные данные коннектора — это секрет хранилища, на который ссылаются по id |
| Визуализация или приложение → консоль | Запрос открыть ссылку или отправить последующее сообщение от имени человека | Нет — страница — это написанный моделью скрипт, который мог прочитать враждебный ввод. Ссылка открывается, а последующее сообщение отправляется только после того, как человек прочитал его и нажал, в собственном DOM консоли; последующее сообщение без действия пользователя за ним отбрасывается |
| Воркер → публичные сайты (коннектор `web`) | GET-запросы страниц, карт сайта и robots.txt; учётных данных нет | Нет — начальный URL вводит организация, а каждую следующую ссылку выбирает сайт, поэтому каждый запрос и перенаправление проверяются на SSRF, а соединение устанавливается по проверенному адресу (`app/core/pinned_http.py`), оставаясь на одном хосте. Начальный URL на хосте, который оператор перечислил в `OUTBOUND_PRIVATE_ALLOWLIST`, может достичь этого перечисленного хоста; публичный начальный URL — никогда |

Полномочия внутри организации никогда не задаются именем роли на маршруте: это строка
членства плюс каталог разрешений (`app/core/permissions.py`), определяемые для каждого
ресурса. Два вызывающих с одной ролью могут добраться до разных строк, потому что
выданный доступ к одному ресурсу расширяет то, что позволяет роль, никого не повышая.

## Что покидает экземпляр { #what-leaves-the-deployment }

Помимо [диагностики экземпляра](configuration.md#diagnostics), которая включена по
умолчанию, каждый исходящий вызов — это вызов, который настроил экземпляр, и вместе с
тем граница, о которой спросит проверка заказчика.

| Куда | Что | Когда |
|---|---|---|
| Настроенный провайдер моделей | Промпт, вывод модели, аргументы и результаты инструментов | Каждый запуск — если только модель не работает на инфраструктуре самого оператора, и тогда наружу ничего не уходит |
| Настроенный канал (Slack, Teams, Telegram, Mattermost) | Сгенерированные ответы агента — текст, изображения и вложения | Всякий раз, когда агент доступен через этот канал; каждый `send_message` отправляется провайдеру (`app/services/channels/`) |
| Logfire | Трассы, которые несут промпты и выводы, если агент не сказал иначе | Два независимых пути. Токен наблюдаемости отдельного агента трассирует этого агента, и его режим `content` решает, сколько несёт спан: `none` сводит его к времени, токенам, стоимости и именам инструментов (#1413). `LOGFIRE_TOKEN` для всего экземпляра инструментирует **каждый** запуск, и в API, и в воркере (`app/core/logfire_setup.py`), поэтому с ним содержимое любого агента, который не попросил `none`, уходит; агент, который попросил, привязан к инструментированию без содержимого и на этом трейсере (`suppress_content`), так что режим держится на обоих путях, а специалист этого агента наследует его — записанный в тексте или придуманный посреди запуска. Один случай это не покрывает: неудачное подключение инструментирования, которое попадает в лог и остаётся как есть. Ни один путь не включён по умолчанию. Отфильтрованной середины намеренно нет — частично вычищенный экспорт — это гарантия, которую никто не может проверить ([#1616](https://github.com/vstorm-co/agenticos/issues/1616)) |
| MCP-серверы | Вызовы инструментов и их аргументы | Только для инструментов, к которым привязан агент |
| Поисковый сервис (Tavily, DuckDuckGo) | Поисковый запрос | Только когда выдана возможность поиска |
| Провайдер эмбеддингов | Текст документа, при индексации | Только для базы знаний, провайдер которой удалённый |
| Сервер плиток карты, названный в `VISUAL_MAP_TILES` | От этого экземпляра, никогда от страницы: координаты каждой плитки карты, которой ещё нет в кэше | Только когда настройка включена и кто-то открывает карту. Страница отправляет экземпляру три числа, каждое проверяется по уровню масштабирования; адрес и ключ сервера остаются на сервере ([Приложения](artifacts.md#how-the-page-is-isolated)) |
| Провайдер голоса реального времени (OpenAI, Azure OpenAI, Google, xAI) | Во время [голосового звонка](voice.md): звук звонящего, инструкции агента, определения и результаты инструментов, а также ранние ходы диалога текстом, когда звонок начинается или переподключается | Только для агента, в разделе «Голос» которого назван этот провайдер, пока звонок открыт. Аудио здесь не хранится; что хранит провайдер, определяется вашим договором с ним |
| Провайдер распознавания речи | Запись: голосовая заметка из канала, диктовка в `/chat` или диктовка посетителя на размещённой странице или в виджете, настроенном на `server` | Каждый раз, когда что-то транскрибируется. Диктовка посетителя анонимна и вне любого бюджета моделей, поэтому её ограничивает лимит частоты ссылки, умноженный на самую длинную диктовку. По умолчанию диктовка — это сырой PCM, чьи отсчёты считаются и отклоняются сверх лимита до отправки, поэтому эта граница точна; экземпляр, который [принимает сжатый звук](deployment.md#what-a-dictation-may-be-uploaded-as), читает длину из заголовка файла, и собранный вручную файл может её занизить — [каналы](channels.md#dictation-on-a-widget-or-a-hosted-page) разбирают худший случай в любом из вариантов. На `browser` браузер посетителя отправляет звук своему провайдеру сам, и через этот экземпляр ничего не проходит |
| Сборщик диагностики | Версия, состояние базы данных и воркера, примерные счётчики использования, счётчики упавших запусков, задач и индексаций по закрытым категориям и псевдонимный сигнал активности; никогда промпты, диалоги, имена файлов, имена учётных записей, адреса электронной почты, ключи провайдеров или тексты исключений | Ежечасно из воркера и, из каждого браузера или приложения, пока кто-то активен; отключается через `DIAGNOSTICS_ENABLED=false` или отправляется сборщику, который вы запускаете, через `DIAGNOSTICS_COLLECTOR_URL` ([конфигурация](configuration.md#diagnostics)) |

## Что и где шифруется { #what-is-encrypted-where }

Механизм шифрования на уровне приложения один, и он намеренно единственный: хранилище
секретов (`app/core/vault.py`). Любые **учётные данные коннектора и API** при хранении
зашифрованы в конверте для своего владельца, ключ обёртки которого выводится через HKDF
из организации (или пользователя), которым они принадлежат, — поэтому шифртекст,
скопированный в строку другой организации, не расшифруется. Мастер-ключ можно ротировать,
не перешифровывая полезные нагрузки.

Не всё, что хранит платформа, — учётные данные из хранилища, и это сказано прямо, потому
что проверка это обнаружит:

- **Короткоживущие bearer-токены** — приглашения в организацию
  (`OrganizationInvitation.token`), запросы привязки канала
  (`ChannelLinkRequest.token`) и ссылки на общий доступ к диалогу
  (`ConversationShare.share_token`) — это случайные столбцы `String(64)`, которые ищутся
  по равенству и не зашифрованы хранилищем. Кто держит значение, тот может им
  воспользоваться, поэтому их защищают срок жизни и однократность, а не шифрование.
  Токены обновления сеанса — исключение: они хешируются при хранении
  (`sessions.refresh_token_hash`).
- **Загруженные файлы и файлы чата** лежат там, куда их положит `FILE_STORAGE_BACKEND`
  (`app/services/file_storage.py`). При `local` по умолчанию это файловая система
  контейнера API в открытом виде, защищённая только шифрованием тома. При `s3` это
  объекты в бакете, который называет экземпляр, и `FILE_STORAGE_S3_ENCRYPTION` решает,
  что запрашивает каждая запись: `sse-s3` по умолчанию или `sse-kms` под ключом, которым
  управляет заказчик, — либо `none`, который не отправляет заголовок шифрования вовсе и
  существует для S3-совместимого хранилища без KMS за ним. При `none` объекты зашифрованы
  настолько, насколько это делает само хранилище, и не больше. `agenticos cmd doctor`
  печатает, в каком бэкенде работает экземпляр.
- **Тела сообщений, `rag_documents` и их векторы, а также рабочие пространства песочниц**
  хранятся как столбцы с открытым текстом, строки pgvector и файлы рабочих пространств.
  Хранилище секретов шифрует учётные данные, а не содержимое; защита этих данных при
  хранении — на уровне диска.

Бэкенд S3 — выбор на время развёртывания, и он не переносит то, что уже хранит локальный;
[конфигурация](configuration.md#uploaded-files-at-rest) содержит настройки, а [обработка
файлов](file-processing.md#storage) — обоснование.

## Что хранится об одном человеке и что с этим происходит { #what-is-held-about-one-person-and-what-happens-to-it }

Статья 15 GDPR спрашивает, что вы храните о человеке, а статья 17 требует это удалить.
Обе статьи отвечаются этой таблицей намеренно: перечень, который называет таблицу для
экспорта и забывает её для удаления, хуже отсутствующего, потому что читается как полный.

Граница, которую она проводит, — **о человеке** против **создано человеком**. То, что о
человеке, уходит вместе с ним; то, что он создал от имени организации, — агент, на
котором работает команда, база знаний, сохранённые учётные данные, — передаётся дальше,
потому что удаление учётной записи коллеги не должно удалять агента, от которого зависит
команда.

| Таблица | При удалении | В экспорте | Почему |
|---|---|---|---|
| `users` | Удаляется | Профиль, без хеша пароля | Сама учётная запись |
| `conversations`, `messages`, `tool_calls` | Каскадом, кроме чатов проекта, которые остаются у команды | Начатые ими ветки диалогов, каждый ход в них; в чате проекта, где бы они ни писали, только их ходы и ответы на них | Их собственные, а транскрипт, из которого удалён каждый второй ход, ни на что не отвечает. Чат проекта принадлежит нескольким людям, и ходы других участников — их |
| `chat_files` | Каскадом; байты удаляются с диска после коммита | Не указываются | Строка каскадируется от сообщения, а файл на диске — нет, поэтому пути собираются до удаления и удаляются после коммита — иначе байты переживут запрос, который просил их удалить, и до них не дотянется никто и не удалит никто. Транскрипт в экспорте называет вложение; байты можно скачать, пока учётная запись существует, но они не упаковываются в неё |
| `message_ratings` | Каскадом | Да | Высказанное ими мнение |
| `sessions` | Каскадом | Устройство, адрес и время — никогда учётные данные, ведь это хеш | Где они входили |
| `api_keys`, `oauth_grants` | Каскадом, вместе с кодами и токенами, на которые обменивали согласие | Ключи, которые они выпустили, и клиенты, которым позволили действовать от их имени: имя, префикс, разрешения и даты — никогда ключ, хеш или токен | Учётные данные, действующие от их имени, — их дело их видеть; собственные ключи платформы для помощника, выдаваемые на каждый запуск, не указываются |
| `conversation_favourites`, `dashboard_layouts`, `dashboard_presets`, `user_slash_commands` | Каскадом | Раскладки и ярлыки | Личные настройки, бессмысленные для кого-либо ещё |
| `agent_memory_files` (`owner_key = person:<id>`) | **Вычищаются явно**, под блокировкой, которую берёт и параллельная запись | Да | Строковый ключ без внешнего ключа: ничего не каскадировалось, поэтому каждая заметка переживала учётную запись — а запуск, писавший заметку посреди удаления, создал бы её заново |
| `agent_workspaces` (`scope = user`) | **Вычищаются явно** | Нет | `owner_ref` — строка по той же причине, что и `owner_key`, поэтому за ним не следует каскад, а рабочее пространство с состоянием хранит сами файлы |
| `organization_members` | Каскадом | В каких организациях, в качестве кого, с какого времени | Строка, называющая их напрямую, уже видна администратору |
| `channel_identities` | **Вычищаются явно** | Да | `SET NULL` оставлял строку с id Slack, именем пользователя и отображаемым именем о человеке, которого больше нет, ни с кем не связанную |
| `agent_runs` | `SET NULL` — сохраняются | Запуски, которые они начали, и стоимость каждого | Расходы — это запись организации; анонимный запуск по-прежнему идёт в счёт месяца |
| `agents`, `knowledge_bases`, `skills`, `contexts`, `agent_triggers`, `agent_environments`, `agent_exposures`, `local_services` | `SET NULL` — сохраняются | Нет | Создано *для организации*. Их удаление забрало бы работу команды вместе с человеком |
| `organization_secrets` | `SET NULL`, а приватный секрет повышается до секрета организации | Нет | Учётные данные, на которых работает организация. Именно это повышение не даёт приватному секрету без владельца заблокировать удаление |
| `organizations` | Личная организация удаляется; общая, которую создали они, переназначается другому владельцу | Нет | Никто не должен остаться с организацией без владельца |
| `resource_grants` | Каскадом на получателя; `SET NULL` на выдавшего | Нет | Выданный доступ *им* — их; выданный *ими* — запись организации о том, кому что можно |
| `app_admin_audit_logs` | **Сохраняются**, id действующего лица остаётся | **Нет** | Запись организации о том, что в ней делали. Запись, называющая удалённую учётную запись, честна; запись с удалённым действующим лицом хуже бесполезной, и это не человеку забирать |
| `embed_visitors` | Не трогаются | Нет | Посетитель — это ключ браузера, а не учётная запись: здесь нет ничего о человеке с логином |

!!! warning "До чего стирание не добирается — и документация говорит об этом, а не экземпляр узнаёт на опыте"

    **Память в удалённой интеграции mem0.** Экземпляр, который использовал mem0 (удалена
    в #2090), может хранить эту память во внешнем сервисе. Обновление теперь отклоняется,
    пока остаются устаревшие привязки, сохраняя сопоставления эндпоинтов и учётных данных,
    пока оператор не проверит внешнее стирание и явно не удалит привязки. Оно не удаляет
    учётные данные хранилища и не стирает и не импортирует удалённые данные. Забывание
    человека или очистка агента здесь больше не достигают того сервиса. Проверьте
    неиспользуемые ключи хранилища, отзовите выведенные из эксплуатации учётные данные
    провайдеров и разберитесь с внешней памятью отдельно. См. [чек-лист
    обновления](deploy.md#native-memory-upgrade).

    **Резервные копии.** Удаление убирает строки из живой базы данных. Любое расписание
    резервного копирования, которое ведёт экземпляр, хранит их, пока не перезапишется, и
    никакое стирание на уровне приложения этого не меняет.

    **Собственное хранение провайдера моделей.** То, что было отправлено для ответа на
    ход, подчиняется политике провайдера, которую описывают [модели](models.md) и которой
    этот экземпляр не управляет.

### Самостоятельное обслуживание и что добавляет администратор { #self-service-and-what-an-administrator-adds }

Человеку не нужен администратор для обычных случаев.
`GET /me/data/export` — это вся таблица выше в одном JSON-документе, с лимитом частоты
раз в час и записью в журнал аудита, в том числе когда человек экспортирует сам
себя, потому что экспорт — это форма утечки, когда вызывающий не тот, за кого себя выдаёт.

Документ собирается и сериализуется целиком, поэтому у него есть предел:
`PERSONAL_DATA_EXPORT_MAX_CHARS` (16 миллионов символов по умолчанию) — сколько текста
диалогов может нести один документ, а учётная запись, где его больше, отклоняется с обоими
числами, а не получает молча частичный документ. Сделать такой документ — работа
оператора, из базы данных. `DELETE /conversations/{id}` удаляет одну ветку диалога, её
ходы и файлы, которые к ней пришли, с проверкой по собственному владению вызывающего
(FA-015).

Администратор добавляет две вещи, и обе проходят аудит:
`GET /admin/users/{id}/export`, который **требует причины** — прочитать всю историю
диалогов коллеги законно примерно дважды в год и серьёзно каждый раз, — и
`DELETE /admin/users/{id}`, где причина необязательна, потому что вывод сотрудника обычно
не требует объяснений.

## Данные страницы и её адрес { #a-pages-data-and-its-address }

[Опубликованная страница](artifacts.md#live-data) может читать данные таблиц. Это
единственное место, где данные участника доходят до других участников работой
агента, поэтому меры защиты перечислены здесь, а не только строками матрицы.

**Делегированное чтение.** Каждый читатель связанной страницы читает одни и те же
записи через замороженные запросы страницы, **с доступом владельца страницы**. Это
сознательная передача доступа владельца к таблицам аудитории страницы. Её меры
защиты:

- Данные открываются только по
  [подтверждению](artifacts.md#consent-the-owner-decides-who-reads-the-data)
  владельца, данному для каждой версии, — после того как он прочитал запросы
  словами и каждую связанную таблицу, до которой они доходят; подтверждение
  привязано к членству владельца и к отпечатку того, что было показано. Повторная
  публикация, которая читает что-то другое, ждёт его. Отозвать его может любой
  редактор, и это также понижает каждый выданный доступ `edit_data` на странице до
  `edit`.
- Владелец проверяется заново при каждом показе: действующий участник с правом
  `read` на каждую таблицу, до которой доходят запросы. Владелец, потерявший
  доступ или ушедший, оставляет страницу без данных.
- Запрос разрешается в идентификаторы при публикации и при каждой загрузке
  сравнивается с таблицами в их текущем виде: столбец, чей смысл изменился или
  который заархивирован, заархивированная таблица или связанная таблица,
  подписанная другим столбцом, не отдают ничего, пока страницу не опубликуют снова.
- Расширять круг тех, кто открывает такую страницу, может владелец — или Owner либо
  Admin за него; редактор или агент через `share_artifact` могут только подать
  запрос. Администраторам доверяют, и они действуют напрямую; меры защиты нацелены
  на агентов, вход от имени другого пользователя и посторонних.
- Автоподтверждение и `edit_data` — два заранее данных согласия. Автоподтверждение
  включает только владелец, от своего имени. `edit_data` выдаёт владелец либо Owner
  или Admin, от своего имени. И то и другое идёт через окно, текст которого
  записывается в запись аудита.

**Адрес содержимого.** Страница участника загружается с `/artifact-content/<token>`.
Токен подписан, называет одну версию и несёт аудиторию — `member` или `public`;
маршрут принимает обе. В `frame-ancestors` каждого ответа с содержимым входит
консоль: она показывает страницу внутри себя и для участника, и для собственной
страницы публичной ссылки (`/a/<key>`), которая живёт там же. Origin документа
встраивания и перечисленные у ссылки сайты встраивания добавляются только для
встраиваемой страницы — той, у которой есть публичная ссылка и нет пароля. Данные
может нести только токен `member`. Когда консоль запрашивает данные при загрузке,
токен говорит и об этом, и маршрут читает привязки для названного в нём читателя
в том виде, в каком они отдаются сейчас: участник ищется заново, доступ к странице
ему по-прежнему должен быть разрешён, и данные он получает только для версии,
которую получает. Миниатюры, карточки и версии из истории не получают ничего.
Токен `public` тоже может нести данные — по [условиям ниже](#public-data); за
пределы названной в нём ссылки ему не доверяют никогда.

### Публичный адрес { #public-data }

Публичный токен несёт `pk` — хеш ключа ссылки, который маршрут содержимого при
каждой загрузке должен найти как текущий ключ ссылки: заменённый или удалённый
ключ — это 404, каким бы ни был оставшийся срок жизни токена. Он несёт `pw` —
дайджест хеша пароля ссылки (без пароля его нет), — и `inj`, равный true, только
если на момент выпуска токена условия показа данных страницы выполнялись.

Данные записываются в страницу, только пока в силе ключ, состояние пароля, срок
действия, обслуживаемая версия, выключатель организации `public_live_data`,
публичное подтверждение данных страницы, подтверждение участников и доступ
владельца, — и всё это проверяется заново при каждой загрузке, до любого чтения и
любого кеша. Неудачная загрузка показывает каждую привязку как `unavailable` без
причины. Публичная обёртка и встраивание данных никогда не запрашивают и
обновления не имеют. См.
[актуальные данные на публичной ссылке](artifacts.md#live-data-on-a-public-link).

**URL — это Bearer-токен.** Пока он жив — пять минут по
умолчанию (`ARTIFACT_VIEW_TTL_SECONDS`), не больше десяти загрузок в минуту на
адрес, — любой, у кого есть адрес страницы участника, выпущенный для данных,
загрузит её с внедрёнными записями этого читателя откуда угодно, и ответ никогда не
кешируется. Поэтому адрес не попадает в журналы, а лимит частоты считает его
по дайджесту. Не вставляйте такой адрес в заявку или чат. Записи публичного адреса
— те, которые его ссылка может показывать сейчас, и он перестаёт нести
какие-либо, когда ключ заменён, пароль изменён или подтверждение отозвано.

**Это не действие.** `share_artifact` ничего не открывает. Он подаёт запрос владельцу,
который отвечает в консоли, войдя от своего имени; поэтому страница, которую
уговорили попросить, не может расширить себя сама.

**Не в журналах.** Значения записи никогда не попадают в журналы, трассы или
записи аудита: в журнале аудита хранятся отпечаток, версия, кто подтвердил и какой
текст он подтвердил, но никогда строка или значение фильтра.

## Страница, которая запускает сценарии { #a-page-that-starts-workflows }

Скрипт страницы недоверенный: его написала модель, которая могла прочитать
что-то враждебное. [Действия](artifacts.md#actions) позволяют ему попросить
запустить сценарий, поэтому то, что он может, ограничено мерами, которые страница
изменить не в силах:

- **Список разрешённых, который проверил публикующий.** Страница объявляет не
  больше пяти сценариев, каждый привязан в возможности «Сценарии» агента,
  действующий, запускаемый вручную и доступный для запуска человеку, стоящему за
  публикующим запуском. Запуск, за которым никого нет, объявить или изменить их не
  может. Восстановление проверяет их заново.
- **Формулировка страницы ничего не решает.** Метка — открытый текст без скрытых
  символов; консоль называет своё окно именем самого сценария и приводит метку
  дословно.
- **Каждый запуск подтверждает человек.** Окно показывает каждое входное значение
  текстом, невидимые символы выписаны; кнопка «Запустить» недоступна полсекунды и
  никогда не получает фокус; одновременно открыт один вопрос, а три отказа
  прекращают вопросы до тех пор, пока страницу не откроют снова.
- **Запрос проверяется дважды.** Консоль принимает сообщение только из собственного
  фрейма страницы под nonce этой загрузки и только для действия, которое сервер
  перечислил для этого читателя и обслуживаемой версии; перед вопросом она сверяет
  ввод с полями сценария. Маршрут запуска повторяет проверки: версия должна быть
  той, что отдаётся, сценарий — объявленным и доступным вызывающему сейчас, а
  сеанс — не входом от имени другого пользователя.
- **Спрашивать может только читатель страницы.** Адрес несёт утверждение `acts`,
  выставленное только для читателя из консоли. Публичные ссылки, встраивания,
  предпросмотры и миниатюры отклоняют вызов и не несут никаких действий.
- **Запуск принадлежит человеку.** Его разрешения, бюджет и лимит частоты (10
  запусков в минуту по умолчанию), записанный с триггером `app` и проведённый в
  аудите без его ввода.
- **Страница узнаёт немного.** Статус запуска, текст ответа, структурированный
  ответ без ссылок на файлы и первую строку ошибки — не больше 200 символов — и
  только для запуска, который эта страница начала для этого человека.

## Профиль HIPAA и на что он не претендует { #the-hipaa-profile-and-what-it-does-not-claim }

Проверка безопасности не спрашивает «соответствует ли это ПО требованиям». HHS не
сертифицирует никакое ПО, а OCR не признаёт частную сертификацию. Она спрашивает:
**можем ли мы запустить это в своей среде, соответствующей требованиям, и можете ли
вы это доказать** — и ответ на него — конфигурация, поставляемая с продуктом, плюс
команда, которая сверяет с ней работающий экземпляр (#1448).

```bash
uv run agenticos cmd doctor --profile hipaa
```

По строке на каждую проверку, где названа настройка, которая её выполняет, или та,
которая не выполняет, и ненулевой код выхода при любом сбое, чтобы это можно было
запускать в CI самого клиента. Конфигурация лежит в `deploy/profiles/hipaa/`:
оверлей compose, который отказывается запускаться без настроек, значения по
умолчанию для которых он дать не может, и файл env с комментариями.

**Читайте эту строку вместе с профилем.** Он отвечает за **технические** меры защиты,
§164.312, и только за них. Административные меры защиты (§164.308 — анализ рисков,
обучение персонала, политика санкций, план на случай чрезвычайных ситуаций,
соглашения с деловыми партнёрами) и физические меры (§164.310) принадлежат оператору
и всегда будут его. Профиль, подразумевающий обратное, был бы утверждением, которое
никто не может обосновать.

### Таблица { #the-sheet }

| Проверка | Мера защиты | Чем выполнена |
|---|---|---|
| `postgres-tls` | §164.312(e)(1) | `POSTGRES_SSLMODE=verify-full`. `require` шифрует, но не проверяет сертификат, поэтому профиль его не принимает |
| `redis-tls` | §164.312(e)(1) | `REDIS_SSL=true`. Оба хранилища должны быть вашими: входящие в репозиторий `db` и `redis` не имеют TLS-слушателя, поэтому оверлей отказывается запускаться без `POSTGRES_HOST` и `REDIS_HOST` |
| `browser-tls` | §164.312(e)(1) | `FRONTEND_URL` и `PUBLIC_BASE_URL` на https, а завершает его ваш обратный прокси. Подтверждается вручную, и адрес http здесь **отклоняется**: все остальные меры могут пройти, пока вход пересекает границу клиента открытым текстом |
| `vault-key` | §164.312(a)(2)(iv) | Мастер-ключ хранилища секретов не короче 64 символов. HKDF выводит из чего угодно ключ обёртки нужного размера и не может добавить энтропии угадываемому секрету |
| `content-at-rest` | §164.312(a)(2)(iv) | **Оператора.** Данные Postgres, том медиа и корень рабочего пространства песочницы шифруются томом или диском, а не этим приложением |
| `local-model` | §164.312(e)(1) | Каждый профиль модели отдаётся из вашей собственной сети. Разбирается **имя хоста** — частный адрес, `localhost`, голое `ollama`/`litellm`/`vllm` или имя `.internal`/`.local`/`.svc`, — поэтому `https://ollama.vendor.example` не локальный, а профиль без `base_url` по определению публичный API провайдера |
| `traces-local` | §164.312(e)(1) | `LOGFIRE_TOKEN` не задан, **и** ни у одного опубликованного агента или именованного окружения нет собственного токена трассировки: каждый подключает экспортёр, а `observability.content` по умолчанию равен `full` |
| `private-network` | §164.312(e)(1) | `OUTBOUND_PRIVATE_ALLOWLIST` и `MCP_ALLOWED_HOSTS` оба пусты. Тогда мера выполнена, и ни один HTTP-шаг сценария, источник git, web или S3, вызов A2A или подключение MCP не может дойти до частного адреса. Если записи есть в любом из них, это подтверждается вручную, и таблица называет каждый список с его записями и его охватом: каждый участник каждой организации может дойти до этих хостов, а доказать, что каждый проверяет свои собственные учётные данные, — дело оператора |
| `sso` | §164.312(d) | `OIDC_ISSUER`, настроенный одним обнаружением: issuer — единственный URL, а эндпоинты авторизации, токена и JWKS берутся из его `.well-known/openid-configuration`; либо `KERBEROS_ENABLED`, вход с билетом самого домена. Если не задано ни то ни другое, мера не выполнена, и таблица так и говорит: при одном `LDAP_URL` она сообщает, что пароли принадлежат каталогу, но вводятся здесь без единого входа, а иначе — что люди входят с паролями, которые хранит этот экземпляр. Многофакторная аутентификация — дело провайдера идентификации, и таблица её не приписывает себе ни в какую сторону |
| `signup` | §164.312(a)(1) | `invite_only` или `closed` |
| `audit-retention` | §164.312(b) | Нижняя граница аудита не меньше 2190 дней — шесть лет по §164.316(b)(2) |
| `audit-chain` | §164.312(c)(1) | Хеш-цепочка и её контрольная точка. Обнаружение, а не предотвращение, — см. [Меры аудита](#audit-controls-hipaa-164312b-soc-2-cc7) |

Исходов три, и средний из них значим. `ok` и `!!` — ответы этого кода. `--` — проверка, которая
действительно за оператором, **названная**, а не тихо пропущенная: таблица,
пропускающая то, чего не видит, читалась бы как полная, но не была бы ею, — и она
не проваливает команду, потому что проверка, которую отсюда никто не может подтвердить,
— та, которую никто не смог бы пройти.

### Кто такой деловой партнёр { #who-is-the-business-associate }

Клиент, который запускает это на своей инфраструктуре, получает программное
обеспечение. Здесь никто не касается его PHI, и соглашение не нужно. Если экземпляр
для него эксплуатирует кто-то другой, этот оператор становится деловым партнёром,
а это договор, а не флаг конфигурации.

### Почему профиль по умолчанию выбирает локальную модель { #why-the-profile-defaults-to-a-local-model }

Размещённая модель уносит с собой содержимое каждого запуска, поэтому её
использование означает соглашение с этим провайдером — а такие соглашения уже, чем
люди ожидают. Организация с включённым HIPAA у крупного провайдера обычно исключает
выполнение кода и загрузку веб-страниц, а это ровно форма здешних возможностей
`sandbox`, `code_execution` и `web_fetch`. Клиент, который подпишет такое соглашение,
а потом построит агента на этих возможностях, узнает об этом во время инцидента.

Локальный вывод снимает вопрос, поэтому это значение по умолчанию профиля, а не
рекомендация.

## Итог { #recap }

- Доверяйте инфраструктуре оператора; не доверяйте ни одному запросу в неё. Важные
  границы — браузер → BFF → API → хранилище и API/воркер → третьи стороны. BFF
  пересылает cookie сеанса; запрос проверяется в API.
- Уходят только те данные, которым экземпляр велел уходить — провайдеры моделей,
  каналы, MCP-серверы, провайдеры поиска и эмбеддингов и Logfire, — и всё это
  по выбору; а как только задан токен для всего экземпляра, он трассирует каждый
  запуск, с содержимым каждого агента, который не попросил `none`.
- Учётные данные коннекторов и API зашифрованы по организациям в единственном
  хранилище секретов; короткоживущие bearer-токены и остальное содержимое в состоянии
  покоя (сообщения, RAG, песочницы) — нет. Загруженные файлы — то, что сдвинулось:
  `FILE_STORAGE_BACKEND=s3` кладёт их в объектное хранилище, которое шифрует каждую
  запись.
- Каждая мера защиты в матрице называет механизм и тест и тут же называет свои пробелы:
  защита от подмены ссылается на задачу, которая её построит.
- Сообщайте об уязвимостях и выполняйте чек-лист усиления защиты из
  [`SECURITY.md`](https://github.com/vstorm-co/agenticos/blob/main/SECURITY.md);
  читайте [Защиту данных](data-protection.md) и [Лицензии](licenses.md) рядом с этой
  страницей.

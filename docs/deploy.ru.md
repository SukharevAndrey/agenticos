# Разверните на сервере { #deploy-to-a-server }

Один хост, Docker Compose и обратный прокси остаются поставляемым путём для одного
сервера. Для кластеров используйте поддерживаемый [Helm-чарт для
Kubernetes](kubernetes.md) с внешними сервисами данных и блокирующей задачей
миграции. У OpenShift есть кандидатная конфигурация, но она ещё не проверена.
Быстрых стартов в один щелчок для PaaS нет.

Всё, что дальше одного хоста, — управляемый Postgres, несколько хостов API,
несколько экземпляров, — описано в разделе [Масштабирование за пределами одного
хоста](scaling.md).

!!! tip "Сначала прочтите [контрольный список для production](configuration.md#production-checklist)"

    Девять настроек поставляются со значениями по умолчанию, которые хороши на
    ноутбуке и неверны на хосте, доступном кому-то ещё. `scripts/server-init.sh`
    ниже создаёт все девять, поэтому контрольный список — это то, что вы
    проверяете после, а не то, что вы вводите.

## Что нужно { #what-you-need }

| | |
|---|---|
| **Хост** | Его хватит с 4 vCPU и 8 ГБ оперативной памяти. См. [размер хоста](#sizing-the-host) |
| **Движок контейнеров** | Engine 24+ с плагином Compose (2.24 или новее) и вашим пользователем в группе `docker`. На хосте ничего не собирается: образы скачиваются из GHCR. Как вариант — [ручной путь через Podman](#podman-support). |
| **Два имени хоста** | одно для сайта, одно для API — см. [почему два](#why-two-hostnames) |
| **Обратный прокси** | [Traefik](#option-a-traefik) или [Nginx](#option-b-nginx). Он завершает TLS |
| **Без ключа провайдера** | для чат-моделей и эмбеддингов ключи задаются отдельно для каждой организации, в хранилище секретов продукта. В окружении нет учётных данных ни для того, ни для другого — см. [Защита данных](data-protection.md#nothing-leaves-by-default) |

Хосту также нужны открытые порты 80 и 443, и больше ничего. Postgres и Redis не
опубликованы ни на одном интерфейсе, а воркер ничего не обслуживает.

### Почему два имени хоста { #why-two-hostnames }

Браузер обращается к обоим. Большинство вызовов идут через собственные серверные
маршруты фронтенда, но WebSocket чата подключается к API напрямую, поэтому API
нужно имя, которое браузер может разрешить, и собственный сертификат.

`app.example.com` и `api.example.com` — вот их вид. Это могут быть любые два имени;
чего быть не должно, так это одного имени с префиксом пути, потому что cookie API и
cookie сайта привязаны к хосту.

### Поддержка Podman { #podman-support }

**Podman поддерживается через ручной путь развёртывания, где провайдером
Compose выступает Docker Compose.** Проверки среды выполнения использовали Podman 6.1.4 и
Docker Compose v2.40.3 на Fedora CoreOS 44 (машина Podman на macOS, ARM64,
cgroups v2, SELinux в режиме enforcing). Поставляемому файлу нужен Compose 2.24 или
новее.

**Не используйте `podman-compose` 1.6.0.** Он запустил стек и агент ответил, но
намеренно неудачная миграция всё равно запустила зависимое приложение. Docker
Compose правильно отклонил этот запуск. Номера версий провайдеров независимы;
`podman-compose` 1.6.0 — не Docker Compose 1.6.0.

Быстрый старт остаётся только для Docker и направляет обнаруженный Podman на этот
ручной путь, в том числе с `--no-sandbox`. Из корня настроенного репозитория укажите
настоящий исполняемый файл Docker Compose (отдельный бинарник или плагин CLI):

```bash
export PODMAN_COMPOSE_PROVIDER=/absolute/path/to/docker-compose
podman compose version
podman compose -f docker-compose.yml up -d
```

Убедитесь, что `podman compose version` определяет именно Docker Compose. Явное
указание `-f` не даёт переопределению для сборки из исходников этого клона попасть в
установку из опубликованных образов. После запуска сервисов следуйте разделу
[«Установка»](install.md), чтобы создать организацию и модель.

**Необязательная песочница.** `pydantic-ai-backend` 0.2.39 работал с сокетами
Podman как rootful, так и rootless. Ему не нужен новый бэкенд или выпуск.
Используйте `docker-compose-podman.yml`, чтобы адаптировать монтирования сокета и
рабочего пространства; настройте права на них до включения профиля.

В нативном Linux с rootless Podman:

```bash
systemctl --user enable --now podman.socket
export SANDBOX_DOCKER_SOCKET="$XDG_RUNTIME_DIR/podman/podman.sock"
export SANDBOX_WORKSPACE_ROOT="$HOME/.local/share/agenticos/sandbox-workspaces"
mkdir -p "$SANDBOX_WORKSPACE_ROOT"
podman unshare chown 10001:10001 "$SANDBOX_WORKSPACE_ROOT"
export DOCKER_GID=0
```

Для rootful Linux включите вместо этого системный `podman.socket`, задайте
`SANDBOX_DOCKER_SOCKET=/run/podman/podman.sock` и подготовьте рабочее пространство
командой `sudo install -d -o 10001 -g 10001 "$SANDBOX_WORKSPACE_ROOT"`. Запускайте
Compose против этого rootful-движка. Группа его сокета обычно 0; настроенному
rootful-сокету нужна его фактическая группа в `DOCKER_GID`.

На машине Podman с rootless в macOS оба источника монтирования принадлежат
Linux-виртуалке, а не macOS. Подготовьте их внутри этой виртуалки:

```bash
export SANDBOX_DOCKER_SOCKET="$(podman machine ssh 'printf "%s/podman/podman.sock" "$XDG_RUNTIME_DIR"')"
export SANDBOX_WORKSPACE_ROOT=/tmp/agenticos-sandbox-workspaces
podman machine ssh 'mkdir -p /tmp/agenticos-sandbox-workspaces && podman unshare chown 10001:10001 /tmp/agenticos-sandbox-workspaces'
export DOCKER_GID=0
```

Сохраните существующие ключи экземпляра. Задайте непустой `SANDBOXD_TOKEN` и
`SANDBOX_URL=http://sandboxd:8080` в файле окружения, который читает стек, как
описано в разделе [настройка песочницы](sandbox.md). Затем запустите с обоими
файлами:

```bash
podman compose -f docker-compose.yml -f docker-compose-podman.yml \
  --profile sandbox up -d
```

Переопределение отключает разметку SELinux только для `sandboxd`, который и так
держит сокет движка. Рабочее пространство он помечает общей меткой `:z`, потому что
его монтируют и соседние песочницы. Контейнеры песочницы сохраняют свои метки и
`no-new-privileges`; не перемаркируйте сокет и не отключайте SELinux глобально.
Владение rootless-сокетом отображается на группу 0 внутри пространства имён
пользователя.

На сервере используйте постоянный путь рабочего пространства: `/tmp` — лишь
локальный пример. Сохраните настройки сокета, рабочего пространства и группы в
окружении оператора для последующих команд Compose. `DOCKER_HOST` на хосте не
меняет сокет, смонтированный внутри `sandboxd`.

Проверенные пути включают запуск агента по HTTP, сохранённое завершение, файлы
рабочего пространства, ненулевые коды выхода, тайм-ауты, принудительные лимиты
памяти/CPU/PID и сборку образов во время выполнения. Поставляемый образ рабочей
среды также читал и записывал XLSX, строил график и запускал Node и LibreOffice.
Моделью был детерминированный тестовый сервер, совместимый с OpenAI; среда
выполнения для компьютера и каждый дистрибутив Linux не проверялись. Версии, охват и
воспроизведение сбоя миграции см. в [записанных
проверках](https://github.com/vstorm-co/agenticos/blob/main/docs/audits/podman-2026-11-03.md).

## Размер хоста { #sizing-the-host }

Измерено на простаивающем экземпляре, а не оценено:

| | в покое | потолок |
|---|---|---|
| `app` (2 воркера uvicorn) | ~1,0 ГБ | 2,5 ГБ при 4 воркерах по умолчанию |
| `db` | ~1,3 ГБ с настройкой ниже | 2 ГБ |
| `worker` (один дочерний процесс индексации) | 387 МиБ | 2,5 ГБ (`WORKER_MEMORY_LIMIT`) |
| `frontend` | ~300 МБ | 1 ГБ |
| `redis` | 9 МиБ | 512 МБ |

Число, которое определяет хост, — **`UVICORN_WORKERS`**. Каждый воркер — отдельный
процесс, который импортирует всё приложение: 460 МиБ, и он порождается как новый
процесс, а не ответвляется от родительского, поэтому ничего не разделяется. Четыре
таких — 1,9 ГБ ещё до прихода запроса.

Двух воркеров хватает команде из десяти, и один всё ещё обслуживает, пока
[сторожевой процесс](configuration.md#a-worker-whose-event-loop-has-stopped-turning)
заменяет зависшего собрата. Одного воркера стоит избегать: тогда заблокированный
цикл событий — это весь экземпляр, пока он не убьёт себя.

Хост, которому не хватает CPU, показывает другой симптом: строки
`Child process [N] died` в журнале `app` без вердикта сторожевого процесса над ними,
при этом каждая страница медленная. Это воркеры, которых супервизор uvicorn убил за
поздний ответ на его ping, а не воркеры, которые сломались. Он ждёт
[`UVICORN_WORKER_HEALTHCHECK_TIMEOUT`](configuration.md#a-worker-whose-event-loop-has-stopped-turning)
секунд, по умолчанию 60. Прежде чем поднимать его, посмотрите на показатель CPU steal
у хоста.

Две настройки сохраняют медленный экземпляр диагностируемым:

- **Каждый журнал ограничен.** Каждый сервис в production-файлах compose пишет не
  более пяти файлов по 20 МБ. По умолчанию Docker хранит журнал контейнера, пока
  контейнер не удалён, и ничто на хосте не выполняет его ротацию.
- **Postgres записывает, сколько стоит каждый запрос.** Сервис `db` предзагружает
  `pg_stat_statements`, а миграция создаёт расширение. Там, где роль базы данных не
  может его создать, миграция пишет уведомление и продолжает.
  `agenticos cmd doctor` в любом случае печатает строку `query statistics`.

!!! note "База данных настроена под собственный лимит"

    `docker-compose-prod.yml` запускает Postgres с `shared_buffers=512MB` при лимите
    2 ГБ и даёт ему 512 МБ `/dev/shm` — по умолчанию Docker даёт 64 МБ, и
    параллельное сканирование по векторам коллекции их исчерпывает, сообщая
    `could not resize shared memory segment`. Меняете лимит — меняйте вместе с ним и
    настройку; именно поэтому они записаны рядом.

    Он также задаёт `max_connections=200`, потому что пулы могут открыть больше
    стандартных 100 у Postgres: два пула по 15 на воркер uvicorn, то есть 120 при
    четырёх по умолчанию, и ещё 30 для фонового воркера. Поднимайте его вместе с
    `UVICORN_WORKERS` или `DB_POOL_SIZE`, иначе Postgres отказывает в соединениях с
    «too many clients» раньше, чем пул успеет поставить их в очередь или сбросить
    нагрузку.

## Направьте имена на хост { #point-the-names-at-the-host }

Две A-записи, прежде всего остального. Let's Encrypt доказывает, что имя вам
подконтрольно, забирая файл по HTTP оттуда, куда оно разрешается, поэтому
сертификат не выдаётся, пока это не так и не распространилось.

```
app.example.com   A   203.0.113.10
api.example.com   A   203.0.113.10
```

!!! warning "Wildcard-запись этого за вас не сделает"

    Если `*.example.com` уже указывает куда-то — обычно на сайт маркетинга, — оба
    имени разрешаются туда. Запись для конкретного имени важнее wildcard, поэтому
    исправление — добавить две записи выше, а не удалять wildcard.

Проверьте откуда-нибудь не с хоста, потому что у хоста может быть свой ответ:

```bash
dig +short app.example.com api.example.com
```

## Доставьте код на хост { #get-it-onto-the-host }

```bash
sudo install -d -o "$USER" -g "$USER" /opt/agenticos
git clone https://github.com/vstorm-co/agenticos.git /opt/agenticos
cd /opt/agenticos
bash scripts/server-init.sh
```

`server-init.sh` записывает `backend/.env`: он создаёт пять секретов, спрашивает два
имени хоста и адрес для Let's Encrypt и выводит публичные URL и источник CORS из
того, что вы дали. Ключ провайдера он не спрашивает: они живут в хранилище секретов
каждой организации. Существующий файл он перезаписывать отказывается.

Клон — это место, где живут файлы compose и тот файл окружения; никакой код из него
не выполняется. Выполняются два образа, которые публикует репозиторий.

### Образы { #the-images }

| | |
|---|---|
| `ghcr.io/vstorm-co/agenticos-backend` | API, воркер и миграции — один образ, три команды |
| `ghcr.io/vstorm-co/agenticos-frontend` | Консоль |

Оба собираются для `linux/amd64` и `linux/arm64` в `.github/workflows/images.yml`.
Выпуск (`v0.0.380`) публикует `0.0.380` и сдвигает `latest`; каждый коммит в `main`
публикует `edge` и `sha-<short>`. Файлы compose читают тег из `AGENTICOS_VERSION` в
`backend/.env` и по умолчанию берут `latest`.

Три правила, которых держится рабочий процесс GitHub Actions — и каждое стоит
знать, прежде чем полагаться на тег:

- **Публикуется только коммит в `main`.** Тег `v*`, отправленный из ветки, или
  запуск, направленный на ветку, отклоняются до того, как что-либо собрано, —
  поэтому `latest` не может проскочить границу pull request.
- **Выпуск на коммите, который `main` уже собрал, не пересобирается.** Его манифест
  `sha-<short>` получает версию и `latest` как дополнительные имена, поэтому
  дайджесты, закреплённые на хосте, — ровно те, что называет выпуск.
- **Коммиту без образов их можно дать.** Запустите этот рабочий процесс вручную с
  его входом `sha` — `gh workflow run images.yml --ref main -f sha=<commit>` — и он
  опубликует тег `sha-<short>` этого коммита и не сдвинет ни одного плавающего тега.
  Это путь для коммита старше этого рабочего процесса и для того, чей запуск потерялся.

!!! warning "Закрепите выпуск на хосте, который вам важен"

    `AGENTICOS_VERSION=0.0.380` в `backend/.env`, чтобы `make prod` в плохой день
    скачивал то, что работало вчера, а не то, что выпустили сегодня утром.
    `scripts/deploy.sh` закрепляет за вас — на тег `sha-` развёртываемого коммита —
    ровно на время выполнения развёртывания.

    Закрепляйте его из рабочей копии того выпуска: `git checkout v0.0.380` рядом с
    переменной. Образ сервиса песочницы закреплён в файле compose на версии, с
    которой говорит бэкенд того же коммита, поэтому старый бэкенд, запущенный из
    более новой копии, встречает более новый `sandboxd` — а `latest` из старой
    копии — то же несоответствие в другую сторону. `scripts/deploy.sh` переключается
    на развёртываемый коммит, поэтому развёртывание скриптом или откат держат эти
    две вещи вместе.

Оба пакета скачиваются анонимно. Если скачивание отвечает `unauthorized`, пакет
сделали приватным или мешает устаревший `docker login ghcr.io`; ни то ни другое хост
не может исправить сам.

!!! danger "`backend/.env` хранит ключ, который распаковывает любые сохранённые учётные данные"

    `VAULT_MASTER_KEY` — это то, что делает читаемыми ключи провайдеров организации,
    токены ботов и учётные данные MCP. Потеря ключа не запирает вас в продукте; она
    делает каждый секрет в нём невосстановимым. Сохраните резервную копию файла там,
    куда не доберётся потерянный диск, и меняйте ключ через
    [`agenticos cmd vault-rotate`](secrets.md#operations), а не правкой.

Две необязательные вещи, о которых он не спрашивает, обе в том же файле: `SMTP_*`,
без которых нельзя отправить приглашения и сбросы пароля, и `LOGFIRE_TOKEN`, куда
уходят трассировки запусков агентов.

## Выберите обратный прокси { #choose-a-reverse-proxy }

Что-то должно завершать TLS и маршрутизировать два имени. Оба варианта ниже ведут к
одним и тем же контейнерам; выбирайте по тому, есть ли у вас уже нужный.

!!! note "Оставьте сжатие приложению"

    API сам сжимает свои ответы gzip, прокси консоли `/api/*` снова сжимает для
    браузера то, что сжал API, а Next сжимает свои страницы. Поэтому прокси не нужен
    `gzip on`, и он не должен обнулять `Accept-Encoding` клиента: это только
    отключает сжатие. Ответ, уже несущий `Content-Encoding`, проходит через Nginx и
    Traefik без изменений.

### Вариант A: Traefik { #option-a-traefik }

Более короткий путь, и его стоит выбрать на хосте, где Traefik уже есть: контейнеры
несут метки, Traefik находит их, запрашивает сертификат и продлевает его. Ничего не
нужно перезагружать, и нет второго файла конфигурации, который надо держать в
согласии.

Если Traefik ещё нет, репозиторий поставляет свой: `docker-compose-traefik.yml` —
точка входа на 443 с резолвером Let's Encrypt и перенаправлением 80 на неё.

```bash
docker network create traefik_webgateway
docker compose --env-file backend/.env -f docker-compose-traefik.yml up -d
```

Где Traefik **уже** работает, не трогайте его и укажите в `TRAEFIK_NETWORK` сеть,
которую он отслеживает. Оверлеи читают это имя, поэтому в существующем прокси менять
ничего не нужно.

Затем поднимите стек с `PROXY=traefik`, что добавляет два файла-оверлея с метками:

```bash
make prod PROXY=traefik
make prod-frontend PROXY=traefik
```

`server-init.sh` уже записал `PROXY=traefik` в `backend/.env`, откуда его читает
`scripts/deploy.sh` — поэтому последующие развёртывания сохраняют прокси, с которым
настраивали этот хост, а не тот, что предположил скрипт.

Поставляемый прокси читает все статические настройки из аргументов команды Compose,
включая `ACME_EMAIL` и `TRAEFIK_NETWORK`. Не монтируйте ещё и статический
`traefik.yml`: Traefik выбирает один статический источник и игнорирует эти
аргументы, когда присутствует статический файл. `traefik/dynamic.yml` остаётся
конфигурацией маршрутизации файлового провайдера, включая HSTS. Переключение на
WebSocket проходит без дополнительного middleware; загрузки передаются потоком без
ограничения тела на прокси.

!!! info "`exposedByDefault: false` выполняет здесь важную работу"

    Это единственная настройка в `docker-compose-traefik.yml`, которую стоит
    прочитать перед запуском. Только `app` и `frontend` несут `traefik.enable=true`,
    поэтому Postgres, Redis, воркер и демон песочницы недостижимы ниоткуда извне
    хоста — и это свойство *отсутствия метки*, поэтому оно переживает добавление
    сервиса кем-то, кто не подумал о прокси.

!!! warning "Некоторые пути запросов и строки запроса — это учётные данные"

    Эти сегменты пути открывают что-то каждому, кто их прочитает:

    - ключ публичной ссылки в `/a/<key>`, `/api/v1/public/artifacts/<key>` и
      `/api/v1/artifact-embed/<key>`, пока ссылку не сменят;
    - подписанный адрес содержимого `/api/v1/artifact-content/<token>` на время его
      жизни;
    - токен общего диалога в `/shared/<token>` и
      `/api/v1/conversations/shared/<token>`;
    - токен формы сценария в `/f/<token>` и
      `/api/v1/public/workflow-forms/<token>`;
    - токен проверки вебхука в `/api/v1/workflow-webhook-tests/<token>` и
      `/api/v1/workflows/<id>/webhook-test/<token>`;
    - токен привязки канала в `/link/<token>` и
      `/api/v1/me/channel-link/<token>`;
    - токен приглашения в `/invitations/<token>`,
      `/api/v1/invitations/<token>` и `/api/v1/invitations/<token>/accept`;
    - токен возобновления запуска сценария в
      `/api/v1/workflow-resume/<run_id>/<token>`.

    То же и с этими параметрами запроса:

    - `visitor` и `token` на сокете виджета агента,
      `/api/v1/embed/<key>/ws`: ключ размещённой страницы, который возобновляет
      диалог посетителя, и подписанный токен посетителя заказчика;
    - `code` и `state` на возврате провайдера входа,
      `/api/v1/oauth/<provider>/callback`, и `code` на `/auth/callback` консоли;
    - `invitation_handle` на `/api/v1/oauth/<provider>/login` и
      `/api/v1/auth/kerberos/login`, который погашает приглашение, за которое
      отвечает;
    - `token` на `/reset-password`, `/auth/magic-link` и `/auth/email-change`
      консоли — ссылках, которые отправляют сброс пароля, ссылка для входа и смена
      адреса электронной почты.

    Запрос, сделанный с одной из таких страниц, может нести её адрес в заголовке
    `Referer`. API заменяет сегменты API и значения этих параметров на `[REDACTED]`
    в собственном журнале доступа, в строке uvicorn для каждого принятого WebSocket,
    в каждой записи журнала и в спанах Logfire — включая вывод консоли, аргументы
    эндпоинта и копию, которую Logfire делает при старте спана. Остальные
    параметры запроса, например `q`, `skip`, `limit` и id, сохраняются.

    Traefik может сохранить, отбросить или вырезать целое поле, но не может
    переписать часть поля, поэтому `docker-compose-traefik.yml` отбрасывает
    `RequestPath`, включающий строку запроса, из журнала доступа Traefik. Nginx
    может переписать часть значения, но `nginx/nginx.conf` отбрасывает путь, строку
    запроса и `Referer` так же, форматом журнала `agenticos_no_path`, который
    называет каждый блок сервера, чтобы список секретных путей хранился в одном
    месте. В обоих журналах остаются клиент, статус, размер и длительность. Журнал
    ошибок Nginx записывает первую строку запроса и `Referer` для неудачного запроса,
    и никакая настройка это не меняет, поэтому держите журнал ошибок на хосте. Если пути нужны
    в журнале доступа, уберите это правило поля или формат журнала и обращайтесь с
    журналом как с секретом: держите его на хосте и не отправляйте в сервис
    журналов.

### Вариант B: Nginx { #option-b-nginx }

Для хоста, где Nginx уже завершает TLS или где прокси вообще не в Docker. Стек
публикует оба порта на `127.0.0.1`, и Nginx достаёт их там:

```bash
make prod
make prod-frontend
```

`nginx/nginx.conf` — это шаблон. Прежде чем он начнёт что-либо обслуживать, нужно
сделать две замены: `server_name` в каждом блоке равен `${DOMAIN:-localhost}`, а Nginx
это не раскрывает — впишите два имени хоста вручную. Получать и продлевать сертификаты
— ваша забота, как и заголовок `Strict-Transport-Security`, который бэкенд намеренно
оставляет тому, что завершает TLS. Журнал доступа шаблона опускает путь запроса, строку
запроса и `Referer`; раздел *Некоторые пути запросов и строки запроса — это учётные
данные* выше говорит почему и что журнал ошибок всё же пишет.

Шаблону нужен **Nginx 1.25.1 или новее**, потому что он использует `http2 on`.
Nginx 1.24 из Ubuntu 24.04 требует либо более нового пакета, либо
`listen 443 ssl http2;` (и его IPv6-эквивалент) вместо отдельных директив
`http2 on;`. Установите шаблон внутри контекста `http`, например как
`/etc/nginx/conf.d/agenticos.conf`, затем выполните `nginx -t` перед перезагрузкой.

Хост API и перечисленные маршруты загрузки multipart в консоли задают
`client_max_body_size 55m;`: наибольшее из `MAX_UPLOAD_SIZE_MB`,
`CHAT_MAX_UPLOAD_SIZE_MB`, `EMBED_MAX_UPLOAD_SIZE_MB` и `ML_MAX_UPLOAD_SIZE_MB` плюс
5 МиБ на служебную разметку multipart. Поднимая это наибольшее значение, поднимите
**оба** лимита прокси. Иначе Nginx по умолчанию берёт 1 МиБ, включая разметку, и
отклоняет загрузки раньше, чем они дойдут до приложения. Консоль пересылает загрузки
со своего хоста; размещённые страницы обращаются к хосту API.

Страницы консоли, аутентификация и обычный JSON сохраняют лимит 1 МиБ. Вводя новые
маршруты загрузки в консоли, добавляйте их в список мест загрузки шаблона. Прокси API
пересылает переключения на WebSocket на каждом пути, включая `/api/v1/ws/`, встроенный
чат и голос и медиа с телефона. Обычный HTTP сохраняет `Connection: close`.

!!! warning "`BIND_HOST` — настройка безопасности, а не удобства"

    Именно значение loopback по умолчанию придаёт смысл лимиту частоты для
    аутентификации. `RATE_LIMIT_TRUST_FORWARDED_FOR` велит API считать попытку по
    адресу, который пересылает прокси, поэтому то, что может добраться до API *мимо*
    прокси, выбирает адрес, по которому считаются его попытки. Задавайте
    `BIND_HOST=0.0.0.0` только для прокси на другой машине и закройте порт
    файрволом для него.

!!! warning "Фронтенд — отдельный проект compose"

    Compose называет проект по каталогу, поэтому оба стека были `agenticos`, и
    подъём фронтенда тогда отчитывался о пяти контейнерах бэкенда как о **сиротах**, а
    compose при этом сам предлагал запустить команду снова с `--remove-orphans`.
    Если послушаться, остановятся API, база данных, Redis и воркер. Цели `make` и
    `scripts/deploy.sh` передают `-p agenticos-frontend`, поэтому предупреждения
    больше нет. Файлы compose также не задают имён контейнеров — каждый проект
    называет свои, поэтому два стека на одном хосте не могут захватить контейнеры
    друг друга, а `deploy.sh` ждёт сервисы `app` и `frontend`, а не имя. Экземпляр,
    предшествующий обоим исправлениям, пересоздаётся под новыми именами при
    следующем `up`; вручную ничего удалять не нужно.

    Два проекта всё равно встречаются в сети с фиксированным именем —
    `agenticos_edge` в production, `agenticos_backend` на dev-сервере, — потому что
    фронтенд присоединяется к ней как к внешней сети. Хост с **двумя** стеками
    AgenticOS разводит `AGENTICOS_EDGE_NETWORK` и `AGENTICOS_DATA_NETWORK` (или
    `AGENTICOS_NETWORK`) в `backend/.env` каждого стека; иначе `db`, `redis` и `app`
    обоих стеков разрешаются на одном мосту, и запрос может дойти до соседней базы
    данных.

## Запустите и создайте первую учётную запись { #start-it-and-create-the-first-account }

`make prod` скачивает образы, запускает стек и выполняет миграции — последние как
сервис `migrate`, которого ждёт API, поэтому ручной `docker compose up -d` на тех же
файлах делает то же самое. Первое скачивание — около 2 ГБ; следующее — только
изменившиеся слои.

Затем создайте организацию, владельца и работающего агента:

```bash
docker compose --env-file backend/.env -f docker-compose-prod.yml \
  exec -T app agenticos cmd bootstrap \
  --email you@example.com --password 'a real password' \
  --org 'Your Company' --provider anthropic --api-key sk-ant-...
```

Ключ провайдера здесь — то, на чём работают два стартовых агента. Без него они
создаются и не могут отвечать; каждый другой провайдер добавляется в продукте, для
каждой организации, из хранилища секретов.

!!! tip "Проверьте снаружи, а не с хоста"

    ```bash
    curl -fsS https://api.example.com/api/v1/health
    curl -fsSo /dev/null -w '%{http_code}\n' https://app.example.com
    ```

    Стек, здоровый на хосте и недостижимый из интернета, — это DNS, файрвол или
    сертификат: три вещи, которых проверка работоспособности внутри хоста не видит.

Затем один раз вручную: войдите, пригласите кого-нибудь (это докажет `SMTP_*`) и
отправьте AgenticOS сообщение (это докажет ключ провайдера и WebSocket). Каждый из них
задействует путь, который больше здесь ничто не проверяет.

!!! info "Заголовки безопасности приходят от бэкенда, поэтому любой прокси покрыт"

    Content-Security-Policy, `X-Frame-Options: DENY`,
    `X-Content-Type-Options: nosniff`, `Referrer-Policy` и `Permissions-Policy`
    задаются на каждом ответе — включая 500 для необработанного исключения, который
    строится вне стека middleware и проставляет их сам. Интерактивная документация
    API отбрасывает только CSP, потому что Swagger загружает ресурсы, которые
    строгая политика запрещает.

    **HSTS намеренно оставлен прокси**, где завершается TLS. Прокси, задающий
    собственный CSP, должен быть по крайней мере так же строг, как этот.

### Сервисы в вашей сети { #services-on-your-own-network }

Запрос, который настраивает участник, — шаг HTTP сценария, источник Git, веб-сайта
или S3, агент A2A или подключение MCP, — отклоняется, когда его хост разрешается в
приватный адрес, поэтому вики, сервер Git или MCP-сервер внутри вашей сети по
умолчанию недостижимы. Чтобы открыть один, перечислите его в
`OUTBOUND_PRIVATE_ALLOWLIST` в `backend/.env` как хост, `.suffix`, адрес или диапазон
CIDR и перезапустите API и воркер. Формы записи, то, что отклоняется независимо от
списка, и то, что после этого сможет достичь каждая учётная запись, описаны в строке
этой настройки в [справочнике конфигурации](configuration.md#project-settings).
Перечисляйте только сервисы, которые проверяют собственные учётные данные.

`agenticos cmd doctor` сообщает список в строке `private network`. Он завершается
ошибкой, когда перечисленный диапазон покрывает базу данных или Redis, и
предупреждает о диапазоне шире /16 (IPv4) или /48 (IPv6).

### Включение песочницы { #turning-the-sandbox-on }

Сервис, который выполняет код агента, спрятан за профилем compose, потому что это
единственный контейнер, держащий сокет Docker, а монтировать его на общем хосте
должно быть решением, а не значением по умолчанию. Три вещи, один раз:

```bash
make sandbox-token                       # writes SANDBOXD_TOKEN to backend/.env
sudo mkdir -p /var/lib/agenticos/sandbox-workspaces
sudo chown 10001:10001 /var/lib/agenticos/sandbox-workspaces
```

Затем его поднимает развёртывание: `scripts/deploy.sh` передаёт `--profile sandbox`,
когда `SANDBOXD_TOKEN` в `backend/.env` имеет значение, поэтому сам хост говорит,
запускает ли он её. Как `make` и быстрый старт, он экспортирует `DOCKER_GID` в
`group_add` песочницы: группу сокета в Linux (с переходом по симлинкам) или `0` в
Docker Desktop, где смонтированный сокет принадлежит виртуалке. Явный `DOCKER_GID` в
окружении или в командной строке `make` имеет приоритет. Больше ничего в `.env` не
нужно: бэкенд обращается к демону через *подключение* песочницы, которое кто-то создаёт в
консоли, а `http://sandboxd:8080` распознаётся как собственный для этого экземпляра.

!!! warning "Сервис, о профиле которого compose не знает, compose останавливает"

    `up -d` в том же проекте без `--profile sandbox` не оставляет песочницу в
    покое — он её останавливает. Поэтому у хоста, запустившего её вручную, её
    забирало следующее развёртывание, и выполнение кода агента падало по причинам,
    никак не связанным с развёртыванием, которое это вызвало (#1506). Вот почему
    скрипт читает токен, а не принимает флаг.

## Развёртывание изменения { #deploying-a-change }

### Встроенная память и непрерывность автоматизаций { #native-memory-upgrade }

Перед этим обновлением сделайте [резервные копии базы данных, файлов и ключа
хранилища секретов](#backups) и скоординируйте обновление API и воркеров. Используйте
обычный шаг миграции этого экземпляра; не копируйте строки и не создавайте вручную
расписания взамен.

Перед применением `0285_member_proactivity.py` остановите источники задач в API и в
фоновом проходе, дождитесь завершения активных проактивных задач и только потом
остановите воркеры. Миграция отклоняется, пока выполняется наблюдение или ночная
задача модели, и заполняет очередь общим для участника ключом параллелизма.
Обновляйте API и воркеры вместе, чтобы новые задачи использовали тот же ключ:
наблюдение и ночной просмотр за одним человеком не должны независимо расходовать
один и тот же остаток.

- `0248_drop_memory_mem0.py` отклоняет обновление, пока `memory_mem0` остаётся в
  любом сохранённом черновике или опубликованной спецификации. Прежде чем повторить
  попытку, составьте по резервной копии опись всех эндпоинтов и привязок учётных
  данных в хранилище секретов, удалите внешние записи памяти и убедитесь в
  завершении удаления у каждого провайдера. Только после этого уберите эти привязки
  явно из `agents.draft_spec` и `agent_versions.spec`. Один экспорт — это не
  удаление. Сохраните подтверждение очистки, проверьте неиспользуемые ключи
  хранилища секретов и отзовите выведенные из оборота учётные данные. Миграция не
  делает удалённых запросов и никогда не предполагает, что очистка удалась. Если
  более ранняя сборка для разработки уже вырезала привязки, восстановите опись из
  её резервной копии до обновления и выполните ту же очистку; встроенное
  удаление человека и агента до этих внешних данных не достаёт.
- `0251_primary_conversations.py` и `0258_primary_channel_history.py` устанавливают
  основные личные чаты. Уже существующая привязка сохраняется. Однократно
  перенимается только доказуемо личная связанная история канала; история проекта
  или группы и неоднозначная история остаются отдельными. Не запускайте заполнение
  повторно после того, как кто-то очистил основной чат.
- Существующие идентификаторы, расписания и журналы автоматизаций остаются на
  месте. Миграция доставки `0255_trigger_delivery.py` даёт старым автоматизациям
  `run_log`; новые автоматизации по умолчанию используют основной чат или свой
  доверенный исходный диалог. Проверьте назначение, действующее лицо, окончание и
  бюджет в разделе **Автоматизации** (Routines), а не создавайте копии.
- `0259_trigger_version_pin.py` поддерживает неизменяемые закрепления версии.
  Закрепление и именованное окружение взаимоисключающие. Снимите закрепление,
  прежде чем удалять его версию. Отложенный запуск сохраняет допущенную версию;
  `0260_routine_run_origin.py` сохраняет его источник, чтобы удаление
  автоматизации не снимало проверку авторизации.
- `0261_watch_attempt_status.py` начинает явный учёт попыток, не домысливая старую
  историю успехов и сбоев. Недоступная или незавершённая проверка не сдвигает
  отметку успеха. Проверьте существующие наблюдения и доступ к их учётным записям:
  исторические строки не доказывают, как изначально было дано согласие.

Выберите модель явно, прежде чем включать обслуживание памяти; ежедневная сводка
сохраняет прежние настройки модели и бюджета организации. С миграцией
`0262_watch_agent_sources.py` наблюдения используют выбранного агента и сохраняют
одобренные источники в запусках. Существующим наблюдениям нужно, чтобы владелец
выбрал агента и одобрил его источники, прежде чем они снова заработают;
идентификаторы и результаты наблюдений сохраняются. Проверьте
[управление](governance.md#proactive-work) и [настройку каналов](channels.md#sms),
включая `PUBLIC_BASE_URL` и просроченные ссылки подтверждения личности по SMS. В
тестовой организации проверьте один личный чат, «Активность» и доставку одной автоматизации,
паузу и истечение срока, а также одно наблюдение с недоступным источником, прежде
чем включать это для более широкого круга.

### Граница истории повторов в 1.25.0 { #retry-history-upgrade }

Версия 1.25.0 принимает исходы инструментов `retried` и отдельные сообщения
`retry-feedback` из Pydantic AI 2.61. Существующие истории и контрольные точки
запусков загружаются без миграции базы данных и без повторной публикации агентов.
Истории, содержащие такие части, требуют нового читателя: более старый бэкенд не
может воспроизвести эти формы сообщений.

Обновляйте все процессы API и воркеров вместе, дождавшись завершения работы старых
процессов или остановив их, прежде чем новые начнут принимать работу. Не смешивайте
старые и новые реплики бэкенда на одной базе данных. После записи любой из новых форм повтора откат
только кода через эту границу не поддерживается; нужно либо оставить нового
читателя, либо восстановить снимок базы данных, сделанный до обновления.

### Вручную { #by-hand }

```bash
remote=$(ssh you@your-host 'mktemp -t agenticos-deploy.XXXXXX')
ssh you@your-host "cat > $remote" < scripts/deploy.sh
ssh you@your-host "trap 'rm -f $remote' EXIT; bash $remote <commit-sha>"
```

`scripts/deploy.sh` загружает этот коммит, ждёт образы, опубликованные для него CI
(`sha-<short>`, обычно уже готовы), скачивает их, перезапускает и ждёт, пока API,
фоновый воркер и фронтенд не сообщат о готовности, — только после этого он завершается:
с нулевым кодом, если дождался, и с ненулевым, если нет. Скрипт принимает **коммит**, а
не ветку, поэтому разворачивается то, что прошло проверку, а не то, куда с тех пор ушёл
`main`; а работает байт в байт то, что собрал CI, на хосте, которому никогда не нужен
инструментарий.

!!! warning "Скопируйте скрипт на хост и запустите — не передавайте его в `bash -s` через конвейер"

    При `bash -s` скрипт становится собственным стандартным вводом оболочки, и
    первая же команда в нём, читающая stdin, съедает остаток. `docker compose exec`
    передаёт stdin в контейнер даже с `-T`, поэтому миграция съела всё, что было
    ниже неё, bash дошёл до конца файла, и развёртывание завершилось с кодом **0**,
    так и не собрав фронтенд и не дождавшись ни одного контейнера. Сайт лежал, а
    развёртывание было зелёным
    ([#1488](https://github.com/vstorm-co/agenticos/issues/1488)).

    Именно два соединения вместо одного не дают процедуре обрезать саму себя.

Это не развёртывание без простоя. Compose пересоздаёт контейнеры, чей образ
изменился, поэтому сайт недоступен те несколько секунд, пока это происходит.

### Хранение образов выпусков { #release-image-retention }

Перед скачиванием скрипт удаляет старые неиспользуемые образы выпусков только из
`ghcr.io/vstorm-co/agenticos-backend`, `agenticos-frontend` и `agenticos-browser`.
Он оставляет по два дополнительных неиспользуемых ID образа на репозиторий, начиная
с самых новых; несколько тегов SHA или версии на одном ID считаются одним образом.
Под удаление попадают только теги `sha-<hex>` и числовые теги версий. Все псевдонимы
удаляемого ID удаляются вместе, без `--force`. `--no-prune` также предотвращает
неявное удаление родительских образов без тегов.

Каждый работающий или остановленный контейнер на хосте защищает свой образ, в том
числе контейнеры других проектов Compose. Целевой образ, любой изменяемый или ручной
тег, а также тег или дайджест в другом репозитории тоже защищают весь ID. Образы
песочницы и среды выполнения, висячие образы и тома приложений в эту очистку не
входят. Из-за этих защит образов может остаться больше, чем допускает лимит
неиспользуемых.

Хеш каталога развёртывания разделяет закрепления для стеков, живущих на одном хосте.
Локальные теги `deploy-<stack-hash>-current` и `deploy-<stack-hash>-rollback`
сохраняют последний исправный образ каждого компонента и его предшественника после
замены контейнеров. При первом использовании `deploy-<stack-hash>-current`
заполняется из исправных контейнеров этого стека, а не из рабочей копии;
несогласованные ID исправных образов отклоняют развёртывание. Закрепления сдвигаются
только после того, как новые сервисы пройдут проверки работоспособности. Неудачные
развёртывания сохраняют записанные закрепления, а повторное развёртывание того же
образа не заменяет записанную для него откатную версию. Откатывайтесь по-прежнему по
одобренному SHA коммита; эти локальные теги — отметки для хранения, а не выпуски в
реестре.

Скрипт требует не меньше **5 GiB свободного места** в файловой системе хранилища
Docker перед каждым скачиванием и после необязательной подготовки среды выполнения.
Он проверяет `DockerRootDir` и стандартное хранилище `/var/lib/containerd`, если оно
есть. Это нижняя граница ёмкости, а не резервирование и не оценка размера образов; за
пользовательскими хранилищами containerd следите отдельно. Оба образа, бэкенда и
фронтенда, скачиваются до перезапуска любого из сервисов. Отказ из-за нехватки
ёмкости сообщает файловую систему и доступное место: освободите место за пределами
защищённых образов или расширьте хранилище, затем повторите одобренное развёртывание.
Никогда не применяйте для этой политики сплошной `docker image prune -a`.

В Docker Desktop каталог хранилища находится внутри его виртуальной машины Linux.
Скрипт измеряет свободное место в этой машине через временный контейнер только для
чтения, изолированный от сети, на уже закэшированном образе бэкенда — лучше на
последнем исправном. Такая проба не может скачивать образы и удаляется
автоматически. Скрипт также проверяет файловую систему хоста, где лежит каталог
развёртывания; за файловой системой хоста, на которой размещён диск пользовательской
виртуальной машины, следите отдельно. Эта процедура обновления требует
закэшированного образа бэкенда; сначала выполните обычную первоначальную установку.

### Из GitHub, с одобрением { #from-github-with-an-approval }

`.github/workflows/deploy.yml` предлагает к развёртыванию каждый опубликованный
стабильный выпуск и ждёт, пока кто-нибудь его одобрит. Этот шлюз —
**настройка репозитория, а не шаг в файле**: без неё рабочий процесс разворачивает
каждый опубликованный стабильный выпуск без участия человека.

Настройте это один раз:

1. **Settings → Environments → New environment** с именем `production`.
2. Отметьте **Required reviewers** и добавьте тех, кто может одобрять. Это и есть
   шлюз.
3. Добавьте переменные этого окружения: `SITE_URL`, `API_URL` и `APP_DIR`, если
   рабочая копия лежит не в `/opt/agenticos`.
4. Добавьте секреты, перечисленные ниже.

!!! warning "Отменяйте развёртывание, которое не собираетесь одобрять"

    Каждый запуск входит в группу параллелизма `deploy-production`, и запуск,
    застрявший на шлюзе одобрения, держит её. Сам по себе он не истекает — GitHub
    отменяет запуск без действий через 30 дней, — поэтому пока кто-нибудь не одобрит
    или не отменит его, следующие выпуски стоят в очереди за решением, которого
    никто не примет, а сервер продолжает работать на том, что было развёрнуто
    последним.

    Поэтому развёртывание, от которого вы отказались, отменяют, а не оставляют.
    Один такой запуск, ждавший на устаревшем коммите, заблокировал три следующих,
    прежде чем кто-то заметил очередь, а не сами запуски.

    `deploy-queue.yml` — это то, что происходит, если запуск всё же оставили: каждые
    шесть часов он отменяет запуск Deploy, прождавший одобрения больше двенадцати
    часов, и открывает задачу на GitHub (issue), где называет запуск и насколько последний стабильный
    выпуск ушёл вперёд от последнего успешного развёртывания. Он ничего не одобряет и
    ничего не разворачивает — он разгружает очередь, чтобы следующий опубликованный
    выпуск дошёл до шлюза, и сообщает, что сделал это. Запустите его вручную:
    `gh workflow run deploy-queue.yml`.

!!! danger "Одобрение из очереди окружения одобряет **самый старый** запуск"

    То есть устаревший. Позднее одобрение, данное там, разворачивает коммит тех
    времён, когда очередь застряла, а не только что отправленный — именно так на
    этот сервер попал коммит двухнедельной давности. Одобряйте со страницы запуска
    нужного коммита или начните новый командой
    `gh workflow run deploy.yml --ref main -f ref=v1.34.3` и одобрите его.

| Секрет | Что это |
|---|---|
| `DEPLOY_HOST` | Адрес хоста |
| `DEPLOY_USER` | Учётная запись, которой принадлежит рабочая копия |
| `DEPLOY_SSH_KEY` | Закрытый ключ, открытая половина которого лежит в `authorized_keys` этой учётной записи |
| `DEPLOY_KNOWN_HOSTS` | Вывод `ssh-keyscan your-host`, снятый откуда-то, чему вы доверяете |

Создайте ключ для этого и ни для чего другого:

```bash
ssh-keygen -t ed25519 -N '' -C 'github-actions-deploy' -f deploy_key
ssh-copy-id -f -i deploy_key.pub you@your-host
ssh-keyscan your-host                    # → DEPLOY_KNOWN_HOSTS
cat deploy_key                           # → DEPLOY_SSH_KEY, then delete it locally
```

!!! note "Ключ хоста — секрет, а не `ssh-keyscan` во время развёртывания"

    Сканирование во время развёртывания доверяет тому, кто отвечает по этому
    адресу — а ключ хоста и существует, чтобы этого не допустить. Отсканируйте
    один раз откуда-то, чему доверяете, и сохраните ответ.

После этого появляется запуск с кнопкой **Review deployments**; одобрение запускает
задание. `workflow_dispatch` запускает то же задание для указанного вами ref (так и
делается откат), и он проходит то же одобрение.

## Резервные копии { #backups }

Важен один том, и не сразу понятно, какой именно:

| Том | Что хранит | Резервная копия |
|---|---|---|
| `postgres_data` | всё — агенты, диалоги, запечатанные учётные данные | **да** |
| `media_data` | загруженные файлы до индексации | да |

У кэша тома нет вовсе. Корзины лимитов частоты, отметки о дубликатах в каналах и
ответы о членстве несут TTL и восстанавливаются сами, поэтому Valkey работает с
`--save ''` и после перезапуска стартует пустым. Хост, где работал более ранний
выпуск, всё ещё хранит том `agenticos_redis_data`, который уже никто не монтирует;
удалить его: `docker volume rm agenticos_redis_data`.

```bash
docker compose --env-file backend/.env -f docker-compose-prod.yml exec -T db \
  sh -c 'pg_dump -U "$POSTGRES_USER" -Fc "$POSTGRES_DB"' > "agenticos-$(date +%F).dump"
```

Идентификаторы берутся из собственного окружения контейнера, а не вписаны явно,
потому что обе — настройки: экземпляр, где изменили любую из них, иначе получил бы
пустой файл и ошибку, которую никто не замечает.

!!! danger "Резервная копия базы данных без `backend/.env` — не резервная копия"

    Учётные данные в ней запечатаны `VAULT_MASTER_KEY`. Если восстановить её рядом с
    другим ключом, каждый ключ провайдера, токен бота и учётные данные MCP в дампе
    станут нечитаемы — и продукт будет сообщать об этом по одному отказу за раз.

## Откат { #rolling-back }

| | Как |
|---|---|
| **Код** | Разверните предыдущий коммит: `workflow_dispatch` с его sha или `scripts/deploy.sh`. Образы всё ещё в реестре, так что это скачивание, а не сборка. Коммит без образов `sha-<short>` — старше `images.yml` или с потерянным запуском — сначала публикуется командой `gh workflow run images.yml --ref main -f sha=<commit>`; развёртывание называет эту команду, когда перестаёт ждать |
| **Схема** | `agenticos db downgrade --revision=-1`, затем разверните подходящий код |
| **Данные** | `pg_restore` дампа, затем проверьте миграцию, которую ждёт код |

Откат кода **через миграцию — это решение, а не команда**. Старый код встречает
схему, которую никогда не видел; сработает ли это, зависит от миграции. Прочитайте
её, прежде чем предполагать.

## Итог { #recap }

- **Один хост, Compose, прокси впереди.** Семь контейнеров — один из них выполняет
  миграции и завершается, два хранят состояние, каждый образ скачивается: на хосте
  ничего не собирается. Закрепите `AGENTICOS_VERSION`.
- **`UVICORN_WORKERS` определяет, во сколько обходится хост.** 460 MiB на воркер,
  ничего общего. Два для команды, четыре для настоящего трафика.
- **DNS прежде всего.** Сертификат не выдаётся, пока имена не укажут на хост.
- **Одобрение — настройка репозитория**, а не строка в рабочем процессе. Без
  обязательных рецензентов в окружении `production` каждое слияние разворачивает
  себя само.
- **Резервируйте `postgres_data` и `backend/.env` вместе.** Одно без другого — не
  восстановление.

## Образы для ответвления и локальная проверка { #fork-images-and-local-verification }

Compose и `scripts/deploy.sh` принимают `AGENTICOS_IMAGE_PREFIX` со значением по
умолчанию `ghcr.io/vstorm-co/agenticos`. Задайте в нём префикс образов приложения из
ответвления, а в `AGENTICOS_SOURCE_REPOSITORY` — его GitHub-путь `owner/repository`.
Образы бэкенда, фронтенда и браузера используют этот префикс; отдельно версионируемый
демон песочницы остаётся внешней зависимостью. Рабочий процесс Images по умолчанию
берёт префикс GHCR собственного репозитория в нижнем регистре. Переменная репозитория
GitHub с тем же именем может его переопределить; права на пакеты должны покрывать это
назначение.

Ответвление не настраивает секреты SSH, рецензентов окружения и защиту репозитория.
Проверьте их, прежде чем включать развёртывание по выпуску. О плагине и одноразовой
локальной проверке опубликованных образов см.
[Работа с AgenticOS через ИИ-клиент](howto/operate-with-ai.md).

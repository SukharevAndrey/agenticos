# HTTP API { #the-http-api }

Всё, что делает консоль, она делает через этот API. Закрытого интерфейса нет:
те же эндпоинты доступны и вам.

Интерактивный справочник генерируется из кода и обслуживается самим экземпляром по
адресу **`/docs`**, а схема лежит в `/api/v1/openapi.json`. Оба включены в
разработке и отключены в рабочей среде — решает `ENVIRONMENT`, поэтому рабочий
экземпляр не публикует свой список маршрутов.

## Аутентификация { #authenticating }

Три способа входа — для трёх разных клиентов.

| | Заголовок | Для кого |
|---|---|---|
| **API-ключ организации** | `Authorization: Bearer aos_…` | Скрипт, HTTP-клиент вроде Postman или MCP-клиент. Действует от имени участника, который его выдал, в пределах разрешений, с которыми он выдан |
| **JWT** | `Authorization: Bearer <access token>` | Человек или что-то, действующее от его имени. Живёт недолго, обновляется refresh-токеном |
| **Куки сеанса** | устанавливает консоль | Только браузер — токен имеет флаг HttpOnly и никогда не доходит до JavaScript |

Для ключей организации используйте `Authorization: Bearer aos_…`. `X-API-Key` —
отдельные учётные данные службы экземпляра; ключ `aos_…`, отправленный туда, не
аутентифицирует запрос организации. Маршруты хранилища секретов, например
`GET /api/v1/secrets`, и маршрут сообщений консоли требуют сеанса со входом.
Клиенты API читают сообщения диалога через
`GET /api/v1/conversations/{id}/transcript`.

### API-ключи организации { #organization-api-keys }

Ключ выдаёт участник — в одной организации, из раздела **Настройки → API**
(Settings → API), или запросом `POST /api/v1/api-keys` из сеанса со входом. Он
несёт полномочия этого участника, суженные дважды:

- **До разрешений, с которыми он выдан.** Выберите набор — *Только чтение*,
  *Индексация знаний*, *Полный доступ* — или отметьте разрешения из
  [каталога](permissions.md). Выдать можно только то, что есть у вас.
- **До того, что выдавший может делать сейчас.** Каждый запрос заново читает его
  членство, поэтому понижение в роли сужает сразу все его ключи. Исключение из
  организации или его уход отзывает все выданные им ключи и все подключённые им
  приложения — навсегда, поэтому повторное приглашение ничего из этого не оживит.
  Выданный доступ расширяет то, что *человек* может делать с одной записью; но он
  никогда не расширяет ключ сверх его разрешений.

Ключ показывается **один раз**, в ответе, который его создаёт. Хранится только его
SHA-256, и он никогда не появляется ни в строке журнала, ни в записи аудита, ни в
тексте ошибки. В списках виден его префикс (`aos_1a2b3c4d`) — по нему же запись
аудита называет ключ, от имени которого выполнено действие: каждая запись,
сделанная во время запроса с ключом, несёт `via_api_key` в своих деталях. У ключа
может быть срок действия, а отзыв (`DELETE /api/v1/api-keys/{id}`) действует уже на
следующий запрос.

Консоль показывает ваши ключи выше руководства по подключению, активные — первыми.
Ищите по названию, префиксу или тому, кто выдал; на телефоне карточки показывают
срок действия и последнее использование. В окне **Создать ключ** (Create key)
разверните разрешения набора или выберите **Свой набор** (Custom), чтобы искать
отдельные разрешения. Поиск не сбрасывает выбранное. Enter в поле названия создаёт
ключ; Enter в поиске разрешений не отправляет форму.

Пока ключ создаётся, поля и закрытие окна заблокированы. При отказе черновик
сохраняется для повтора. После создания скопируйте ключ до закрытия; если буфер
обмена отказал, значение остаётся доступным для новой попытки. Закрытие очищает
состояние создания. Отклонённый отзыв оставляет окно подтверждения открытым для
повтора.

**Ключ — не человек, который его выдал.** Запуск, который он начинает,
принадлежит выдавшему, считается в его бюджете и попадает в аудит от его имени, но
доступа к его личному состоянию у ключа нет: ни
[памяти](reference/capabilities.md#whose-notes-and-who-may-hear-them), ни поиска по
его прошлым диалогам, ни сайтов, где он оставил вход для браузера, ни рабочего
пространства песочницы, заведённого на пользователя. Кто держит ключ — скрипт, а не
человек, поэтому запуск отвечает так же, как на публичном виджете.

Чтобы одобрять личные автоматизации и наблюдения, нужно явное разрешение
`personal:consent`, выбранное в разделе **Свой набор** при выдаче ключа или
авторизации MCP-клиента. Оно исключено из всех наборов, включая
**Полный доступ** (Full access). Подтверждение позволяет учётным данным одобрять постоянные
автоматизации и наблюдения, использующие ваши личные подключения и данные;
обычные разрешения `agents:run` и `runs:view` этого не дают. Существующие ключи и
авторизации MCP не получают персональное согласие автоматически.

**Настраивать работу, которая действует от вашего имени, можете только вы — ключом,
который выдали.** Ключ, который вы создали, или токен MCP-клиента, который вы
авторизовали, может создавать и менять ваши собственные
[автоматизации](triggers.md), действующие от вашего имени (`runs_as_creator`), и
ваши [наблюдения](console.md), просматривать источники автоматизации и публиковать
агента, не отзывая согласие автоматизаций, которые вы создали для действий от
вашего имени. Запуск, который начинают эти автоматизации, всё равно принадлежит
автоматизации, с её выбранной политикой источников, текущими разрешениями и
бюджетом. Собственные учётные данные запуска агента не могут этого сделать за
пределами вашего личного чата, и администратор, вошедший от вашего имени, тоже не
может.

Для автоматизаций `source_mode=follow_agent` делает первичную настройку
автоматической в пределах полномочий создателя; она не одобряет последующее
расширение источников или поведения. Владелец может явно согласиться с текущей
конфигурацией через эндпоинт источников, привязанный к токену. Метаданные проверки
источников отделяют `required_unavailable_sources` от необязательных пробелов MCP в
`unavailable_sources`. Устаревшая политика следования без подтверждения поведения
требует проверки; существующие ограниченные политики сохраняют свои правила.

Диалоги тоже доступны: `GET /api/v1/conversations` перечисляет чаты выдавшего ключ
(`runs:view`), а `POST /api/v1/conversations` с `title` и
`PATCH /api/v1/conversations/{id}` открывают и переименовывают чат (`agents:run`) —
например тематический чат, в котором отвечает автоматизация.
`POST /api/v1/me/mcp-connections/{id}/test` проверяет одно из ваших подключений и
обновляет его инструменты (`agents:run`).

Поиск подключений только на чтение тоже доступен: `GET /sandbox-connections`,
`GET /sandbox-connections/runtimes` и `GET /sandbox-connections/{id}/policy` требуют
`connections:view`; `GET /mcp-connections` требует `mcp:manage`. Ограничения
организации и ключа при этом действуют. Изменение подключений и операции с учётными
данными по-прежнему только в сеансе.

```bash
curl "$BASE/api/v1/me/permissions" \
  -H "Authorization: Bearer $AGENTICOS_KEY"
```

Стоит знать о двух отказах:

- **`403` «API keys are not accepted on this endpoint»** — ключи принимаются только
  в публичном API: агенты, запуски и согласования, базы знаний и RAG, навыки, файлы
  контекста, проекты, приложения, ML-сервисы, `/me/permissions`, а также участники,
  приглашения, группы и настройки организации. Собственные маршруты консоли, ваша
  учётная запись, выход из организации и передача её другому, а также управление
  ключами остаются только для сеанса, поэтому утёкший ключ не может выпустить себе
  замену.
- **`401` «Invalid, expired or revoked API key»** — одна и та же фраза для всех
  случаев, поэтому неверный ключ ничего не узнаёт о том, какие ключи существуют.

У каждого ключа есть и собственный лимит частоты — `RATE_LIMIT_API_KEY_PER_MINUTE`
запросов в минуту (по умолчанию 600), и запуск или вызов ML-сервиса, который он
делает, считается в лимиты ключа, а не того, кто его выдал. Обе проверки
выполняются до поиска ключа — и для HTTP-запроса, и при установке соединения: ключ
учитывается по дайджесту всего токена — никогда по префиксу, который виден в
списках, — а адресу, отправившему `RATE_LIMIT_AUTH_PER_MINUTE` несуществующих
ключей, отвечают `429` без поиска до конца минуты.

### Без браузера { #without-a-browser }

Скрипт может получить собственный ключ, не открывая консоль. Войдите с телом формы
(это grant типа password в OAuth2, поэтому запрос с JSON получает `422`), выберите
организацию, выдайте ключ сеансовым токеном и отзовите его тем же способом, когда
закончите:

```bash
SESSION=$(curl -s -X POST "$BASE/api/v1/auth/login" \
  -d "username=$EMAIL" --data-urlencode "password=$PASSWORD" | jq -r .access_token)

ORG_ID=$(curl -s "$BASE/api/v1/orgs" -H "Authorization: Bearer $SESSION" \
  | jq -r '[.items[] | select(.is_personal)][0].id')

curl -s -X POST "$BASE/api/v1/api-keys" \
  -H "Authorization: Bearer $SESSION" -H "X-Organization-Id: $ORG_ID" \
  -H "Content-Type: application/json" \
  -d '{"name": "nightly import", "scopes": ["collections:view", "collections:edit"]}'
# -> {"id": "...", "key": "aos_...", "prefix": "aos_1a2b3c4d", ...}

curl -s -X DELETE "$BASE/api/v1/api-keys/$KEY_ID" \
  -H "Authorization: Bearer $SESSION" -H "X-Organization-Id: $ORG_ID"
```

`GET /api/v1/api-keys/scopes` перечисляет, что участник со входом может поместить в
ключ, и наборы поверх этого. В экземпляре, где вход возможен только через SSO,
пароля для отправки нет; там участник выдаёт ключ в консоли.

[`examples/public-api.sh`](examples/public-api.sh) — весь цикл одним скриптом: он
выдаёт ключ только на чтение, перечисляет им агентов и запуски, показывает `403`
для маршрута вне разрешений ключа, запускает агента и читает запуск обратно, если
задан `AGENT_ID`, и отзывает ключ при выходе.

```bash
BASE=http://localhost:8000 EMAIL=you@example.com PASSWORD=... bash docs/examples/public-api.sh
```

### Сеансы и отзыв { #sessions-and-revocation }

Токен доступа JWT привязан к сеансу, который открыл вход, — идентификатор сеанса
путешествует внутри токена. Выход из всех сеансов (`DELETE /sessions`) деактивирует
эти сеансы, и привязанный токен затем отклоняется при следующем использовании, а не
доживает свои оставшиеся минуты. Это доходит и до открытого WebSocket чата: сокет
закрывается уже на следующем кадре в отозванном сеансе, а не только на следующем
HTTP-запросе.

Обновление не начинает новый сеанс: refresh-токен меняется на месте, а токен
доступа продолжает называть тот же сеанс, поэтому долгоживущее соединение не
обрывается из-за обычного обновления.

### Работа, которая выполняется после запроса { #work-that-runs-after-the-request }

Ключ организации не может начать [запуск оценки](evals.md) или запрос к
[помощнику по редактированию](authoring.md): эти маршруты предназначены для людей
со входом, и ключу на них отвечают `403`. Работа, которая выполняется позже, в фоне,
подчиняется полномочиям своего инициатора в том виде, в каком они есть к моменту её
начала, — роль, потерянная с тех пор, её останавливает. Если бы ключу когда-нибудь
разрешили начинать такую работу, для ключа действовало бы то же самое: его
разрешения в том виде, в каком они есть тогда, а ключ, отозванный или удалённый с
тех пор, останавливает работу, с причиной в запуске или в запросе.

Срок действия ограничивает только то, что ключ может начать: работа, начатая им,
пока он был действителен, продолжается и после его истечения.

### Явное делегирование личных подключений MCP { #explicit-personal-mcp-delegation }

В разделе **Настройки → API → Создать ключ → Свой набор**
(Settings → API → Create key → Custom) выберите `agents:run` и `mcp:personal:use`,
чтобы внешний запуск мог использовать собственные учётные записи MCP того, кто
выдал ключ. OAuth-клиенты делают тот же явный выбор разрешений. Ни один набор не
включает это разрешение, в том числе **Полный доступ** (Full access), и
существующие учётные данные не получают доступ автоматически.

Это касается только опубликованных привязок MCP с `account: personal`. Привязки
организации сохраняют настроенную учётную запись; отсутствующее личное подключение
никогда не подменяется учётной записью организации или публикующего. Подключите или
восстановите личную учётную запись в консоли, прежде чем повторять запрос к API. Это
разрешение не открывает личную память, старые чаты, браузерные сеансы со входом,
личные терминалы и рабочие пространства, заведённые на пользователя. Внутренние
учётные данные агента не могут передать его дальше.

Исходные учётные данные, их выдавший и доступ к агенту проверяются при приёме,
при возобновлении и перед вызовами MCP, в том числе у агентов-исполнителей. Истечение
или отзыв этих учётных данных блокирует последующие вызовы; запрос, который уже
выполняется выше по цепочке, не отменяется. Отключение, замена или сужение
привязанной учётной записи MCP тоже блокирует её кэшированные инструменты;
подключите её заново и начните новый запуск.

Приостановленный запуск остаётся привязан к исходным учётным данным, включая срок
действия токена доступа OAuth, и не может позаимствовать учётные записи того, кто
согласует. Клиент может начать новый запуск с новыми учётными данными. Старые
приостановленные запуски не получают делегирование личных подключений MCP. Запуски
и источники инструментов сохраняют прежнюю привязку к пользователю или ключу и
идентификаторы подключений; учётные данные не попадают ни в промпты, ни в аудит.

## Заголовок организации { #the-organization-header }

**API-ключ действует в своей организации** и не нуждается в заголовке. Отправлять
`X-Organization-Id` вместе с ключом можно, только если он называет ту же
организацию; если он называет другую, ответ — `400` с
`details.header = "X-Organization-Id"`, а не переключение на другую организацию.

**Сеансовый токен берёт организацию из `X-Organization-Id`.** Вызывающий, который
состоит в трёх организациях, — в каждой разный субъект, с другой ролью и другими
выданными доступами, поэтому отправляйте заголовок с каждым запросом. Если его нет,
запрос переходит к **организации по умолчанию** экземпляра, если вызывающий в ней
состоит, затем к его **личной организации**, затем к его единственной — скрипт,
забывший заголовок, действует там, с теми агентами, доступами и бюджетом, какие
есть у этой организации, и ошибки не получает. Вызывающий, который состоит в
нескольких и не имеет ни организации по умолчанию, ни личной, получает `400` с
`details.header = "X-Organization-Id"`, а не догадку
([откуда начинается новая учётная запись](deployment.md#where-a-new-account-starts)).
Отправьте не ту — и получите отказ, который выглядит ровно как отсутствие ресурса;
намеренно, чтобы идентификаторы нельзя было перебрать.

## Запуск агента { #running-an-agent }

```bash
curl -X POST "$BASE/api/v1/agents/$AGENT_ID/run" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt": "How do I rotate a provider key?"}'
```

Ответ содержит идентификатор запуска, вывод, статус, токены и стоимость.
`environment_id` в теле выбирает, [какое окружение](environments.md) отвечает. Агент
с [форматом ответа](concepts.md#spec) отвечает объектом: он лежит в `structured`,
уже проверенный по `output_schema` агента, а `output` показывает тот же объект
блоком JSON. `"draft": true` запускает вместо этого неопубликованный черновик, как
это делает панель **Проверка** (Test) в Конструкторе: это тестовый запуск, доступный
ключу, чей выдавший может редактировать агента; он отклоняется с причиной, если
черновик не прошёл бы публикацию, и никогда не принимается с
`Prefer: respond-async`.

Синхронные запуски, включая тесты черновика, возвращают `status: awaiting_answer` и
`questions`, когда агент задаёт вопрос человеку. Отвечайте через
`POST /api/v1/runs/{run_id}/answers` телом
`{"responses":{"<tool_call_id>":[{"selected":["Choice"]}]}}`; используйте `answer`
для своего текста или `skipped: true`, чтобы пропустить осознанно. Отсутствие
ответа не считается отказом автоматически. MCP платформы предоставляет то же
самое как `test_agent_draft` и `answer_agent_questions`.

История диалога сохраняет отвеченные карточки вопросов и успешные отложенные
подгрузки возможностей. Зарегистрированные сейчас навыки на следующем ходе диалога
используют свои текущие инструкции; отозванные навыки не включаются снова. Прежние
результаты таблиц не кэшируются как актуальные данные. Верхнеуровневое поле
`starters` описывает опубликованную версию; первые сообщения черновика лежат в
`draft_spec.starters`.

Ключ также даёт доступ к автоматизациям агента — `GET /api/v1/triggers` и `GET`,
`POST`, `PATCH` и `DELETE` по пути `/api/v1/agents/{agent_id}/triggers`, а также
`POST .../{trigger_id}/run`, чтобы запустить её сейчас, — и к моделям организации
через `GET /api/v1/providers/model-profiles`. Три маршрута действуют на самого
выдавшего: `GET /api/v1/me/mcp-connections` перечисляет сервисы, которые он
подключил своей учётной записью, `PUT /api/v1/users/me/locale` задаёт ему язык
консоли на всех устройствах, а `PATCH /api/v1/users/me/agent-context` сохраняет его
роль (`job_title`) и то, чем он занимается (`about`), о чём сообщают каждому агенту.
Каждому нужен ключ, выданный для `agents:run`.

`POST /api/v1/agents` создаёт агента из спецификации в теле запроса и оставляет
пустое поле пустым. С `"from_starter": true` он заполняет то, что спецификация не
задаёт, — инструкции, навыки, собственные инструменты платформы и бюджет — из
стартового агента AgenticOS, как это делает **Новый агент** (New agent) в консоли.

**Запуск продолжает диалог.** Вызов без `conversation_id` открывает новый диалог для
выдавшего ключ и возвращает его идентификатор как `conversation_id`; отправьте его
со следующим вызовом, и агент прочитает сказанное раньше — последние ходы диалога
или сводку более ранних и то, что было после. Рабочее пространство, общее на диалог
(по умолчанию), принадлежит этому диалогу. Неизвестный идентификатор или чужой даёт
`404`; диалог самого выдавшего из консоли или канала даёт `400` — ключу, которому
разрешено запускать агентов, личные чаты человека не выданы. Так же и с
приостановленным запуском: ключ возобновляет или отвечает только на запуск, начатый
ключом, а запуск, начатый человеком, даёт `403`, потому что продолжение действует
от его имени. Диалог попадает в список чатов выдавшего с меткой **API** и скрыт,
пока он не включит там такие диалоги.

Запуск, запрошенный в чате, — исключение из правила возобновлять его самому. Когда
человек принимает его последнее ожидающее согласование или отвечает на его вопросы,
сервер продолжает запуск от его имени и публикует ответ в чате. Решение ключа не
продолжает ничего: человек должен возобновить этот запуск из консоли примерно в
течение часа после последнего решения, иначе запуск завершается.

`continues_in_chat` говорит об этом: он есть в `ApprovalRead`, в `AgentRunRead`
(чтение одной записи) и в результате возобновления и ответа. На
`POST /agents/{id}/run` и для API-ключа он всегда false. Когда он true, не вызывайте
`/resume`. Второй пришедший `/resume` получает прежний `400`, со `status` запуска.
См. [Решение вне чата](channels.md#decided-outside-the-chat).

`GET /api/v1/conversations/{id}/transcript` читает один из диалогов выдавшего ход за
ходом, с инструментами, которые вызывались на каждом ходе, и их стоимостью, — для
ключа с `runs:view`.

!!! info "Вызывающий через API не может обойти управление"

    Этот эндпоинт идёт через тот же механизм выполнения, что консоль, Slack и
    виджет. Запуск записывается, бюджет проверяется перед запросом к модели,
    согласование действует, а стоимость попадает в тот же «Обзор». В этом и смысл
    единого механизма выполнения, и поэтому «быстрого пути», который его обходит,
    нет.

### Не удерживая соединение { #without-holding-the-connection }

Запуск, который длится минуты, — просмотр сайтов, длинная цепочка
инструментов, — держит запрос открытым всё это время, и тайм-аут чтения у
прокси может оборвать его, пока запуск продолжается. Отправьте
`Prefer: respond-async`, и вызов сразу ответит `202`, вернув запрос на запуск,
который нужно опрашивать:

```bash
curl -X POST "$BASE/api/v1/agents/$AGENT_ID/run" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -H "Prefer: respond-async" \
  -H "Idempotency-Key: ticket-4711" \
  -d '{"prompt": "Summarise this quarter for the board"}'
# 202, Location: /api/v1/run-requests/{id}, Preference-Applied: respond-async

curl "$BASE/api/v1/run-requests/$REQUEST_ID" -H "Authorization: Bearer $AGENTICOS_KEY"
```

Запрос на запуск проходит `queued`, `running`, затем `completed` с `result` —
тем же телом, которым отвечает синхронный вызов, — либо `failed` с `error`. Его
`conversation_id` известен с первого ответа, поэтому следующий вопрос можно
отправить до конца запуска. Воркер выполняет его через тот же механизм
выполнения, с тем же бюджетом и согласованиями, что и любой другой способ
запуска.

Что можно проверить сразу, проверяется сразу: неизвестный диалог или
вложение — это `404` на `POST`, а не сбой, который надо обнаружить опросом.
Полномочия ключа проверяются заново при старте запуска, поэтому ключ,
отозванный, пока его запуск ждал, этот запуск не выполнит; ключ, который за это
время только истёк, — выполнит. Читать запрос на запуск может только тот, кто
его отправил, или его ключ; на чужой запрос отвечает `404`. Асинхронный запуск
получает одну попытку: запуск, завершившийся сбоем, записывается вместе со
своими расходами и не повторяется, чтобы не потратить их дважды.

У маршрута **лимит частоты, а не проверка разрешения**. Разрешение
решается внутри сервиса, по выданному доступу именно к этому агенту, —
ролевая проверка на маршруте ресурса [не видит его](permissions.md).

`PATCH /api/v1/agents/{id}/metadata` задаёт **категории** и **теги** агента
телом вида `{"categories": [...], "tags": [...]}`, где пустой список очищает
соответствующий аспект. Значения нормализуются — обрезаются, схлопываются по
пробелам, приводятся к одному регистру и освобождаются от дубликатов — и
ограничены: не больше 10 категорий и 20 тегов, каждый не длиннее 32 символов;
более длинный элемент даёт `422`. Как и маршрут запуска, он обходится без
ролевой проверки; решение принимает проверка `agents:edit` внутри сервиса, которая
учитывает выданный доступ, — поэтому Viewer, имеющий доступ на редактирование
одного агента, может изменить его теги.

`GET /api/v1/agents` фильтрует этот каталог повторяемыми параметрами запроса
`category` и `tag`: значения соединяются по **ИЛИ в пределах одного аспекта** и по
**И между аспектами**, сравнение идёт без учёта регистра (значение из запроса
приводится к тому же виду, что и сохранённое, а пустое значение игнорируется).
Фильтр только сужает то, что вы и так могли видеть, — он никогда не пересекает
границу организации или выданного доступа.

Ответ также несёт `categories` и `tags`: все различные метки на агентах,
которые вы можете перечислить, независимо от фильтра и страницы, — то есть
варианты, которые предлагает меню фильтра. Личный агент, которого вы не видите,
не добавляет ничего.

## Запуск сценария { #running-a-workflow }

Ключи API организации могут начинать запуски и читать их статус, граф, шаги,
файлы и события через `/api/v1/workflow-runs`. Запуск требует `workflows:run`;
чтение — ещё и `workflows:view`, а тесты черновика — `workflows:edit`. Воркер
удерживает допущенный потолок разрешений ключа и перепроверяет ключ и
выпустившего его участника на каждом шаге, в том числе после согласования или
ожидания. Отзыв или удаление прекращает новую работу с `PRINCIPAL_REVOKED`;
продолжение при этом никогда не повышается до полной роли выпустившего.

С истечением срока иначе: истёкший ключ ничего не начнёт, но запуск, начатый им,
пока он был действителен, продолжается, так что час жизни OAuth-токена не
обрывает долгое ожидание. Запуски, начатые ключом, не имеют доступа к личному
состоянию выпустившего. Создание сценариев по-прежнему возможно только в сеансе.

Ключи API могут перечислять и читать запуски публичного происхождения, включая
запуски, начатые ключами; личные запуски, начатые участником, отвечают `404` —
это касается и их графа, шагов, событий, файлов, а также маршрутов повтора и
отмены. Импортировать файлы из таких запусков ключ не может.

```bash
curl -X POST "$BASE/api/v1/workflow-runs" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID" \
  -H "Content-Type: application/json" \
  -d '{"workflow_id": "'"$WORKFLOW_ID"'", "input": {"question": "How long do refunds take?"}, "deadline_seconds": 3600}'
```

Так начинается запуск опубликованной версии сценария, и ответ `201` приходит
сразу; узлы работают в фоне. `input` — то, что передаёт триггер
[`core.input`](reference/workflow-nodes.md#core-input) графа, не больше
`WORKFLOW_RUN_MAX_INPUT_BYTES` в виде JSON (дальше — `413`). Здесь запускается
только версия, которая начинается с этого триггера или не начинается ни с
какого: любая другая отвечает `409
WORKFLOW_TRIGGER_MISMATCH`, потому что её запускает вебхук, расписание,
сообщение в чате или запись таблицы. `"mode": "test"` запускает вместо этого
текущий черновик, с любого триггера, и требует `workflows:edit`.

Перед вызовом прочитайте `GET /api/v1/workflows/{id}/input-schema` с
`workflows:view`. Он возвращает `version_id` опубликованной версии и список
`entries` с `entry_node_id`, `trigger` и действующей `input_schema` для каждой
точки входа: «Вручную», «API», «Вызывается из сценария» или «Форма». Передайте
`version_id`, чтобы посмотреть конкретную опубликованную версию. Контракты
JSON Schema возвращаются без изменений; простые поля представляются как
JSON Schema, а нетипизированные точки входа возвращают `{"type": "object"}`.
Используйте контракт нужной точки входа и передавайте её `entry_node_id` при
запуске.

Устаревшие простые поля `integer` дополнительно требуют целочисленных токенов
JSON: `1` принимается, а `1.0` и `1e0` отклоняются. Обнаружение помечает такие
поля признаком `x-agenticos-strict-integer: true`, в том числе внутри
необязательных полей, допускающих null. Обычная JSON Schema не может выразить
это различие токенов, поэтому одной проверки схемы для таких устаревших полей
недостаточно; решающим остаётся допуск на сервере. Контракты Raw JSON Schema
используют вместо этого стандартную семантику целых чисел.

Необязательный [контракт входных данных JSON
Schema](reference/workflow-nodes.md#json-schema-input-contracts) проверяется до
допуска. Несоответствие отвечает `422 WORKFLOW_RUN_INPUT_INVALID` с путями
полей и сообщениями в `error.details.fields`; запуск не создаётся. Каждая
запись имеет `field` и `message`; вложенные пути запроса включают индексы
массивов, например `input.items.0.sku`. Для существующих вызывающих
`error.details.problems` также сохраняет `field`, `message` и `type` с путями
относительно объекта входных данных. Контракт берётся из текущей опубликованной
версии или из черновика для `"mode": "test"`. Он действует одинаково через
WebSocket и MCP и когда его вызывает другой сценарий.

`deadline_seconds` (до тридцати дней) задаёт срок, который проверяется каждый раз
перед отправкой узла на выполнение: первый узел, чей черёд наступил после
срока, завершает запуск с ошибкой `DEADLINE_EXCEEDED`, а уже работающий узел
или запуск, остановленный на согласовании, этим сроком не прерываются. У маршрута,
как и у маршрута запуска агента, есть лимит частоты для каждого вызывающего:
сверх нормы он отвечает `429` с `Retry-After`.

`GET /api/v1/workflow-runs/{id}` возвращает статус запуска, `spent_cost`,
`error` и, после того как выполнился его узел
[`core.output`](reference/workflow-nodes.md#core-output), — `output`, а
`POST /api/v1/workflow-runs/{id}/cancel` останавливает его. `GET
/api/v1/workflow-runs/{id}/events?after=<cursor>` возвращает поток событий
запуска от старых к новым, с `next_cursor`, который передаётся обратно как
`after`: он остаётся тем же, пока не появится что-то новее, поэтому опрос с
ним тянет живой запуск. Кто что из этого может, сказано в
[разделе о разрешениях](permissions.md#workflow-runs).

`GET /api/v1/workflow-runs/{id}/nodes` перечисляет каждый шаг запуска, включая
итерации циклов, с его `scope_path`, статусом, числом попыток, стоимостью и
типизированной ошибкой последнего сбоя, а `GET /api/v1/workflow-runs/{id}/graph`
возвращает граф, который выполняет запуск: граф его версии или снимок черновика
для тестового запуска.

### Чтение журнала сценария { #reading-a-workflows-log }

Строки, которые записал [Быстрый журнал](workflows.md#the-logs-page) сценария,
можно читать извне консоли — скриптом, электронной таблицей или инструментом
визуализации вроде Grafana или Metabase — с ключом API организации, имеющим
`workflows:view`.

Ключ читает строки запусков публичного происхождения, включая запуски, начатые
ключами: начатые любым ключом организации, начатые извне (вебхук, форма,
сообщение в канале, событие Gmail, Outlook или GitHub) и любой запуск в цепочке,
начатой одним из них. Строки запусков, начатых участником, расписанием, записью
таблицы, чатом, агентом или приложением, не включаются, поэтому журнал сценария
по расписанию через ключ читается пустым, и его счётчики отличаются от
счётчиков консоли. Сценарий другой организации или тот, который участник,
выпустивший ключ, не может просматривать, отвечает `404`; ключ без
`workflows:view` отклоняется.

```bash
# Самые новые строки, по 100 за раз (больше страница не вмещает); тестовые запуски не включаются
curl "$BASE/api/v1/workflows/$WORKFLOW_ID/logs?outcome=error&from=2026-10-01T00:00:00Z&limit=100" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID"

# Сколько строк оставил каждый день, по результату, за последние 30 дней по дням Варшавы
curl "$BASE/api/v1/workflows/$WORKFLOW_ID/logs/summary?days=30&tz=Europe/Warsaw" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID"
```

`GET /api/v1/workflows/{id}/logs` перечисляет сначала новые — по `created_at`,
затем по `seq`, позиции, которую строка заняла в журнале при записи. Сузьте
выборку с помощью `node_instance_id` (один шаг), `outcome` (порт или `error`;
повторите параметр, чтобы совпал любой из нескольких, и строка, вышедшая через
несколько портов, совпадёт с каждым из них), `run` (идентификатор запуска или
его первые 4 и более символов), `q` (текст в сообщении) и временного окна `from`
(включительно) и `to` (не включая); `include_test=true` добавляет строки,
записанные тестовыми запусками. `skip` и `limit` листают по страницам — `limit`
не больше 100, — а `total` считает все подходящие строки, так что клиент листает,
пока `skip` не достигнет этого значения.

`GET /api/v1/workflows/{id}/logs/summary` — это данные, которые нужны графику:
за последние `days` дней (7, 30 или 90, включая сегодня) он отвечает одной
записью на день, от старых к новым, со счётчиком, который оставил каждый
результат; день без строк тоже присутствует. `tz` — имя из базы IANA — задаёт,
чьи дни считать, по умолчанию UTC; остальные фильтры те же, что у списка. Чтобы
забрать это в инструмент визуализации, направьте туда источник данных JSON на этот
маршрут, передав ключ в заголовке bearer, и читайте `by_day`.

```bash
# Ошибки и тайм-ауты за день на протяжении месяца: один источник данных JSON для панели
curl "$BASE/api/v1/workflows/$WORKFLOW_ID/logs/summary?days=30&outcome=error&outcome=timeout" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID"
```

`GET /api/v1/workflow-runs/{id}/logs` перечисляет строки одного запуска от
старых к новым по `seq` (`limit` до 500), а `GET /api/v1/workflow-logs` — самые
новые строки по всем сценариям, которые ключ может просматривать, с названием
сценария у каждой, плюс сколько строк оставил каждый результат за последние
24 часа. Правила оповещений для журнала не входят в публичный API.

### Экспорт и импорт сценария { #exporting-and-importing-a-workflow }

`GET /api/v1/workflows/{id}/export` (`workflows:view`) возвращает черновик
переносимым файлом: `name`, `description`, `tags`, `settings`, `graph` и
`unresolved` — шаг и поле каждой привязки к ресурсу, которую он не включил. В нём
нет ни идентификатора этого экземпляра, ни значения секрета.
`POST /api/v1/workflows/import` (`workflows:create`) принимает такой файл и
отвечает `201` с новым черновиком `workflow` и его привязками `unresolved`;
граф, который не разбирается или называет шаг, которого в этом экземпляре нет, —
это `400`, и ничего не создаётся.

### Отслеживание запуска через WebSocket { #following-a-run-over-a-websocket }

`/api/v1/ws/workflow-runs?organization_id=<org>` аутентифицируется так же, как
сокет чата: токен доступа передаётся подпротоколом `access_token.<token>`.
Отправьте `{"type": "start", "workflow_id": ..., "input": {...}}`, чтобы начать
запуск, или `{"type": "attach", "run_id": ..., "after": <cursor>}`, чтобы
следить за ним. Сервер присылает `{"type": "run", "run": {...}}`, когда
начинает следить, и снова, когда запуск заканчивается, а
`{"type": "event", "event": {...}, "cursor": ...}` — для каждого события между
ними. Отклонённый кадр получает `{"type": "error", "code": ..., "message": ...}`,
а отозванный сеанс закрывает сокет кодом `4001`. Один сокет следит за одним
запуском; новый кадр заменяет запуск, за которым он следил. Кадр `start`
расходует поминутную норму `POST /workflow-runs` и сверх неё получает
`RATE_LIMIT_EXCEEDED`.

### Вебхуки и расписания { #workflow-webhooks-and-schedules }

Идентификаторы доставки вебхука и GitHub переживают очистку содержимого
запусков, сохраняясь как минимальные метки удаления, принадлежащие способу
доступа и организации. Дубликат по-прежнему возвращает UUID исходного запуска
после удаления его содержимого; его статус и прежний ответ вебхука могут быть уже
недоступны. Удаление способа доступа или организации прекращает это время жизни
дедупликации. Миграция `0230_webhook_delivery_tombstones.py` не может
восстановить отметки, уже удалённые прежней политикой хранения; откат удаляет
осиротевшие метки удаления, прежде чем восстановить старый каскадный внешний
ключ.

Публикация триггера без участия человека и изменения полномочий требуют сеанса
участника (`403` для ключа API организации). Ключи могут публиковать сценарии с
ручным запуском, начинать запуски в пределах своих разрешений и
приостанавливать способы доступа, но не могут включать их, менять секреты и
ссылки на формы, менять время расписаний или выбирать новый субъект для
сценария обработки сбоев. Эти операции сохраняют полномочия пользователя для
будущих событий.

Отправки публичной формы сценария соблюдают байтовый лимит входных данных
сценария во время чтения потока запроса — до разбора JSON и поиска токена. Тела
с превышенным объявленным размером или в chunked-кодировке получают `413`;
некорректный JSON и недопустимые поля отправки — `422`. Каждая запись в
`details.problems` ответа `422` имеет вид `{field, message, type}`, где `type` —
собственный тип ошибки валидатора (`missing`, `int_type`, `extra_forbidden`,
...), так что форма может сказать по каждому ответу, чего ему не хватило.


Сценарий, у которого узел-триггер — вебхук или расписание, получает свой способ
доступа при публикации этой версии, и ответ публикации несёт его как `exposure`.
Секрет подписи вебхука находится в `webhook_secret` ответа публикации при первом
включении и больше нигде. `GET /api/v1/workflows/{id}/exposure` читает его
обратно, или `null` для сценария, который начинается иначе. `PATCH
.../exposures/{exposure_id}` с `{"is_active": false}` приостанавливает его, а
`POST
.../exposures/{exposure_id}/rotate-secret` заменяет секрет вебхука и один
раз возвращает новый. Оба требуют `workflows:edit` и `workflows:run` на
сценарии. `webhook_url` вебхука — это адрес, по которому доставляет отправитель:

```bash
BODY='{"lead": 42}'
SIGNATURE="sha256=$(printf '%s' "$BODY" | openssl dgst -sha256 -hmac "$SECRET" | cut -d' ' -f2)"
curl -X POST "$WEBHOOK_URL" \
  -H "X-Signature-256: $SIGNATURE" \
  -H "X-Delivery-Id: lead-42" \
  -H "Content-Type: application/json" \
  -d "$BODY"
```

Он отвечает `202` с `{"run_id": ..., "duplicate": false}`, как только запуск
допущен, никогда не дожидаясь самого запуска. Идентификатор доставки, уже
допущенный, отвечает `"duplicate": true` с идентификатором первого запуска; так
же отвечает тот же подписанный запрос под другим идентификатором в течение
24 часов. Подпись, которая не проходит проверку, — `403`, доставка без
идентификатора или с телом, которое не является объектом JSON, — `400`, а
приостановленный или неизвестный вебхук — `404`.

Граф с шагом [Ответ на вебхук](reference/workflow-nodes.md#webhook-respond)
отвечает вместо этого статусом, заголовками и телом JSON этого шага, и повтор
доставки получает тот же ответ. Запрос ждёт его до
`WORKFLOW_WEBHOOK_RESPONSE_TIMEOUT_SECONDS`, затем отвечает `202`, как выше;
запуск, который завершился сбоем, отменён или исчерпал бюджет, не ответив, — это
`500` `WORKFLOW_WEBHOOK_UNANSWERED` с именем запуска.

До публикации `POST /api/v1/workflows/{id}/webhook-test` (`workflows:edit`)
открывает тестовый URL для черновика: он возвращается как `url` с `test_token`
внутри и открыт для одного вызова в течение двух минут. Вызов не требует
подписи, получает ответ `{"captured": true}` и не начинает запуск.
`GET .../webhook-test/{token}` читает обратно `state` (`listening`, `caught` или
`expired`) и пойманную `delivery`.

Строки истёкших внутренних ключей и ключей OAuth сохраняются, пока они ещё нужны
сценарию, оценке, запуску улучшения, запросу помощника по редактированию,
проверке навыка, генерации кейсов или поставленной в очередь либо выполняющейся
фоновой задаче. Когда эта работа завершается, обычная очистка может их удалить.

## Работа с таблицами { #working-with-tables }

`values` записи индексируются идентификатором столбца; `GET /api/v1/tables/{id}`
перечисляет столбцы. Каждая операция записи требует `Idempotency-Key`: повтор с
тем же ключом и телом отвечает результатом первой операции записи и заголовком
`Idempotent-Replayed: true` вместо повторной записи, а тот же ключ с другим
телом — `422`.

```bash
curl -X POST "$BASE/api/v1/tables/$TABLE_ID/records" \
  -H "Authorization: Bearer $TOKEN" \
  -H "X-Organization-Id: $ORG_ID" \
  -H "Idempotency-Key: lead-ada-2026-09-29" \
  -H "Content-Type: application/json" \
  -d '{"external_id": "ada@example.com", "values": {"'"$EMAIL_COLUMN"'": "ada@example.com"}}'
```

`PATCH .../records/{record_id}` меняет отдельные ячейки и требует
`expected_revision`, который вы прочитали последним; устаревшая ревизия —
`409 REVISION_CONFLICT`. `PUT
.../records/by-external-id/{external_id}` создаёт
запись или обновляет её, причём `expected_revision` обязателен, как только она
существует. `POST .../records/query` фильтрует, ищет и сортирует по одной
странице за раз, а `POST .../records/count` сообщает, скольким записям
соответствуют те же фильтры и поиск, вплоть до 100 000.

Сценарий, у которого узел-триггер — **Запись таблицы** (Table record), после
публикации срабатывает на добавленные, изменённые или удалённые записи своей
таблицы — те, что названы в его триггере. `GET .../triggers` перечисляет
сценарии, начинающиеся с таблицы, `PATCH .../triggers/{trigger_id}` с
`{"is_active": false}` приостанавливает один, а
`GET .../triggers/{trigger_id}/admissions` перечисляет, что он решил по каждой
записи. См. [Триггеры](virtual-tables.md#triggers).
## Агенты через A2A { #agents-over-a2a }

Агент, которого организация предоставляет через A2A, отвечает JSON-RPC по
`POST /api/v1/a2a/{agent_id}` с теми же ключами, что и `/run`; его карточка
агента находится по `GET /api/v1/a2a/{agent_id}/.well-known/agent-card.json` и
ключа не требует. `PUT /api/v1/agents/{id}/a2a` с `{"enabled": true}` включает
это для вызывающего, у которого есть `agents:publish` на этого агента.

```bash
curl -X POST "$BASE/api/v1/a2a/$AGENT_ID" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc": "2.0", "id": 1, "method": "message/send",
       "params": {"message": {"role": "user", "messageId": "m1",
                              "parts": [{"kind": "text", "text": "Review clause 7"}]}}}'
```

Ответ — это `Task`, идентификатор которой совпадает с идентификатором запуска, а
`contextId` продолжает диалог. `tasks/get` читает её снова. Остальное — в
разделе [Каналы](channels.md#a2a).

Внешние агенты, которым поручает эта организация, регистрируются в
`/api/v1/external-agents`: `GET` перечисляет их (`agents:view`); `POST` с
`card_url`, необязательным `slug` и необязательным `secret_id` API-ключа читает
карточку и регистрирует её, а `POST /{id}/refresh` читает её снова;
`DELETE /{id}` удаляет одного (`agents:edit` для всех трёх).

## Примеры { #worked-examples }

Каждый из них выполняется с ключом организации в `$AGENTICOS_KEY` и адресом API
в `$BASE`. Создайте ключ в разделе **Настройки → API** (Settings → API) с
разрешениями, которые называет пример; консоль показывает ключ один раз.

**Поместите документ в базу знаний и найдите его** — ключ с `collections:view` и
`collections:edit` (набор *Индексация знаний*). Индексация идёт в фоне, поэтому
поиск сразу после загрузки может ещё не найти документ;
`GET /api/v1/kb/$KB_ID/documents` показывает его статус, а
`GET /api/v1/kb/$KB_ID/ingestion` отвечает `complete`, когда уже ни один документ
не обрабатывается.

```bash
# Найдите базу знаний, загрузите в неё файл и найдите его поиском.
curl "$BASE/api/v1/kb" -H "Authorization: Bearer $AGENTICOS_KEY"

curl -X POST "$BASE/api/v1/kb/$KB_ID/documents" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -F "file=@policy.pdf"

curl -X POST "$BASE/api/v1/rag/search" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -d "{\"collection_name\": \"$COLLECTION_NAME\", \"query\": \"refund window\"}"
```

**Запустите агента и прочитайте, сколько это стоило** — `agents:run` и
`runs:view`. Чтение запуска несёт его статус, его токены и его стоимость.

```bash
RUN_ID=$(curl -s -X POST "$BASE/api/v1/agents/$AGENT_ID/run" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"prompt": "Summarise this week'"'"'s tickets"}' | jq -r .run_id)

curl "$BASE/api/v1/runs/$RUN_ID" -H "Authorization: Bearer $AGENTICOS_KEY"
```

**Пригласите участника** — `members:manage`. Приглашение отправляется по почте;
ответ один раз несёт его токен — для приглашающего, чьё письмо может не дойти.

```bash
curl -X POST "$BASE/api/v1/orgs/$ORG_ID/invitations" \
  -H "Authorization: Bearer $AGENTICOS_KEY" \
  -H "Content-Type: application/json" \
  -d '{"email": "new.hire@example.com", "role": "member"}'
```

**Повторяйте только то, что ограничено по частоте, и ничего больше.** Ответ
`429` несёт `Retry-After`; любой другой отказ для этого запроса окончателен, а
`401` означает, что ключа больше нет — он отозван, истёк или удалён выпустивший
его участник, — поэтому повтор только расходует лимит.

```python
import time

import httpx


def call(client: httpx.Client, method: str, path: str, **kwargs) -> httpx.Response:
    for _ in range(5):
        response = client.request(method, path, **kwargs)
        if response.status_code != 429:
            response.raise_for_status()
            return response
        time.sleep(int(response.headers.get("Retry-After", "60")))
    response.raise_for_status()
    return response


client = httpx.Client(
    base_url="https://agenticos.example.com/api/v1",
    headers={"Authorization": f"Bearer {KEY}"},
)
print(call(client, "GET", "/me/permissions").json())
```

## Потоковая передача { #streaming }

Два эндпоинта WebSocket, для двух аудиторий.

- **`/api/v1/ws/agent`** — аутентифицированный, его использует консоль. Кадр с
  `agent_id` запускает этого опубликованного агента; кадр без него получает
  общего помощника. `conversation_id` кадра продолжает этот диалог; `null`
  начинает новый, а если ключ не передан, продолжается тот, в который этот сокет
  писал последним. Аутентификация — подпротоколом `access_token.<token>`, где
  токен — JWT сеанса. Ключ API организации здесь отклоняется: ход на этом
  сокете — это человек за клавиатурой со своими личными подключениями.
  Интеграции запускают агентов через `POST /api/v1/agents/{id}/run`.
- **`/api/v1/embed/{public_key}/ws`** — публичный, за
  [встраиванием](channels.md), для посетителя без учётной записи.

Оба передают токены по мере поступления (агент с защитной проверкой вывода
передаёт по шагу за раз, см.
[Защитные проверки](reference/capabilities.md#guardrails)) и оба порождают
обычный запуск, с той же бухгалтерией, что и всё остальное.

Третий, **`/api/v1/ws/events`**, только слушает. Так открытая консоль
[узнаёт об изменениях, сделанных в другом месте](console.md#changes-made-elsewhere):
аутентификация та же, организация — в `?organization_id=`; на каждую успешную
публичную запись в этой организации сокет присылает один кадр JSON —
`resource`, `id`, `action` (`created`, `updated` или `deleted`), `surface`
(`console`, `api_key`, `mcp` или `assistant`) и кто её сделал, — и только для
строк, которые вызывающий может читать. Изменения, которых никто не писал,
приходят так же: `run` для запуска, проходящего через свои состояния, и
`system` для собственной плановой работы платформы, например прохода
группировки пробелов в знаниях.

## Голосовые звонки { #voice-calls }

У [голосового звонка](voice.md) есть собственный сокет, потому что звонок — не
цикл ходов: **`/api/v1/ws/voice`** для участника и
**`/api/v1/embed/{public_key}/voice/ws`** для посетителя на виджете или
размещённой странице ([допуск](channels.md#the-call-socket)). Оба говорят
одними и теми же кадрами, определёнными в `backend/app/schemas/voice.py`.

Сокет консоли аутентифицируется так же, как `/ws/agent`: токен — запись
`Sec-WebSocket-Protocol` вида `access_token.<JWT>` (или cookie того же
источника), никогда в строке запроса, а организация — в `?organization_id=`. Он
закрывается с кодом `4001` без действительного сеанса и `4003`, когда
вызывающий не участник или аутентифицирован ключом API организации: звонок — это
человек у микрофона, как ход в чате — человек за клавиатурой.

Сокет встраивания закрывается с `4029` при превышении лимита частоты и
`4003` при любом отказе, связанном со встраиванием. Каждый сигнал активности
заново проверяет сеанс, поэтому звонок не переживает выход из системы.

**Клиент отправляет** кадры JSON, а через релей — ещё и двоичное аудио:

| Кадр | Поля | Когда |
|---|---|---|
| `start` | `agent_id`, `conversation_id`, `sdp_offer` (WebRTC), `resume_of` и `resume_token` (переподключение), `context` (переменные встраивания) | Первым, в течение 10 секунд |
| `approval` | `id`, `decision` (`approve` или `deny`) | Решение по согласованию, которого ждёт звонок |
| `mute` | `muted` | Релей: микрофон выключен |
| `played` | `bytes` | Релей: сколько аудио агента уже проиграно |
| `end` | - | Положить трубку |
| *binary* | 16-битный PCM с частотой входа модели | Релей: аудио вызывающего |

**Сервер отправляет:**

| Кадр | Поля | Значение |
|---|---|---|
| `answer` | `sdp` | WebRTC: ответ провайдера для однорангового соединения браузера |
| `ready` | `call_id`, `run_id`, `conversation_id`, `transport`, `input_sample_rate`, `output_sample_rate`, `cap_seconds`, `resume_token` | Звонок настроен. `resume_token` отправляется только здесь и только этому вызывающему; при переподключении он возвращается обратно |
| `state` | `state`: `connecting`, `listening`, `user_speaking`, `thinking`, `agent_speaking`, `interrupted`, `tool_running`, `awaiting_approval` | Кто говорит или что делает агент |
| `caption` | `role`, `turn_id`, `part` и одно из `delta` (дописать), `text` (заменить отфильтрованным текстом на данный момент) или `final` | Субтитр в реальном времени |
| `turn_saved` | `message` | Завершённый ход в том виде, в каком он сохранён; он заменяет субтитры с его `turn_id` |
| `tool` | `name`, `status` (`running` или `done`) | Инструмент, который выполняет агент |
| `approval_required` | `id`, `tool`, `args`, `said`, `timeout_seconds` | Согласование для человека на звонке: точные аргументы и то, что от него услышали |
| `approval_unavailable` | `tool`, `args` | Вызов инструмента, который этот вызывающий не может одобрить голосом |
| `approval_settled` | `id`, `outcome` (`approved`, `denied` или `expired`) | Чем закончилось согласование |
| `notice` | `kind`, `message` (необязательно) | То, что нужно сказать словами: сработала защитная проверка, приближается лимит |
| `limit` | `seconds_left` | Время звонка почти истекло |
| `clear_playback` | - | Релей: отбросить поставленное в очередь аудио агента |
| `ended` | `reason`, `message` | Звонок окончен |
| *binary* | 16-битный PCM с частотой выхода модели | Релей: аудио агента |

**Посетителю на виджете или размещённой странице говорят меньше.** `ready`
опускает `run_id`; его `cap_seconds` — это лимит звонка: самый долгий звонок
агента или то, что осталось от возобновляемого звонка. Кадры инструментов
следуют переключателям `show_tool_steps` и `show_tool_results` встраивания, как
и у напечатанного ответа. Без шагов инструментов кадр `tool` не отправляется, а
`tool_running` отправляется как `thinking`. Без результатов инструментов
`approval_unavailable` отправляется с пустыми `args`. `turn_saved` посетителя
несёт только `id`, `role`, `content`, `interrupted` и `turn_id` сообщения, что
бы ни было включено: никогда — идентификаторы запуска, агента или версии, его
стоимость или его вызовы инструментов.

**Переподключение подтверждает право на звонок.** `start` с `resume_of` должен
нести и `resume_token` из `ready` того соединения. Без него или с неверным
переподключение отклоняется как `resume_refused`, а звонок, который оно
называет, не затрагивается. Сервер хранит только хеш токена. Звонок, уже
состоявший из 20 соединений, больше не возобновляется: его следующее
переподключение тоже отклоняется как `resume_refused`.

Сокет, не отправивший `start` в течение 10 секунд, получает `ended` с
`no_start`. Звонок, который не начнётся, отвечает `ended` с устойчивым
`reason`: `no_agent`, `forbidden`, `not_configured`, `bad_offer`,
`data_channel`, `resume_refused`, `call_limit`, `not_priced`, `budget`, `busy`
или `line_busy` — с `message`, который можно показывать. `busy` говорится
только после того, как звонку, который этот же человек положил мгновение назад,
дали до четырёх секунд на завершение. Начало, которое не удаётся по любой другой
причине, отвечает `ended` с `error`.

Посетитель, которому отказано как `not_configured`, `not_priced` или `budget`,
или звонок посетителя, заканчивающийся как `budget`, получает вместо этого
`unavailable` с сообщением «Звонки сейчас недоступны»: код и полное сообщение
предназначены оператору агента. Звонок в архивный диалог отклоняется как
`forbidden` — так же, как отклоняется напечатанное сообщение в такой диалог.

Состоявшийся звонок заканчивается как `user`, `time_limit`, `budget`,
`disconnected`, `revoked`, `guardrail`, `shutdown` или `error`; `time_limit` —
когда достигнут самый долгий звонок агента. Звонок посетителя заканчивается как
`revoked`, когда его встраивание приостановлено, звонки в нём выключены или оно
указывает на другого агента. Ни один кадр никогда не несёт учётных данных
провайдера.

К нему прилагаются пять HTTP-маршрутов:

| Маршрут | Проверка | Отвечает |
|---|---|---|
| `GET /api/v1/agents/{agent_id}/voice` | `agents:run` на этого агента, включая выданный доступ; иначе `404` | Начнётся ли звонок, почему нет (`no_voice`, `not_offered` или `no_key`), транспорт и самый долгий звонок |
| `POST /api/v1/agents/{agent_id}/voice/preview` | `agents:edit` на этого агента, включая выданный доступ; иначе `404` | Голос из раздела «Голос» черновика, произносящий одно фиксированное предложение, в виде `audio/wav`. Кешируется по голосу и языку; `RATE_LIMIT_VOICE_PREVIEW_PER_MINUTE` на человека |
| `GET /api/v1/providers/realtime-models` | `agents:view` | Каталог моделей реального времени, из которого выбирает раздел «Голос» |
| `GET /api/v1/voice/usage?start=…&end=…` | `runs:view` | Секунды звонков и их число для звонков, начатых не раньше `start` и до `end`, по агентам (звонки удалённого агента — одной строкой без идентификатора и имени). `end`, который не позже `start`, отклоняется с `422` |
| `GET /api/v1/runs?modality=voice` | `runs:view` | Только звонки (`text` — только для текстовых запусков); звонок, который переподключался, — одна строка с `voice_chain`, все соединения суммированы |

Согласование, относящееся к идущему звонку, решается в звонке:
`POST /api/v1/approvals/{id}` отклоняет его с `400`.

## Ошибки { #errors }

Один конверт повсюду:

```json
{
  "error": {
    "code": "NOT_FOUND",
    "message": "Agent not found",
    "details": { "agent_id": "..." }
  }
}
```

`details` несёт значения, а не строки таблиц, поэтому он называет поле,
объясняющее отказ, и никогда — запись базы данных. Когда отказ относится к тому,
что прислал вызывающий, `details.fields` — это список `{field, message}`, и именно
он позволяет форме пометить поле ввода, а не показывать предложение, ради которого
человеку пришлось бы перечитывать страницу.

`401` несёт `WWW-Authenticate: Bearer`. Чтение через границу организаций
отвечает `404`, а не `403`, по причине, указанной выше.

**Запуск, который начался и затем сломался, называет себя.** `POST /agents/{id}/run`
отвечает `502` с `MODEL_CALL_FAILED`, когда провайдер модели отказал в запросе
или сорвал его — включая все модели цепочки резервных моделей, — и `500` с
`RUN_FAILED` при любом другом сбое, если запуск уже начался. Оба несут
`details.run_id` и `details.status`, а `details.conversation_id` — когда запуск
писал в диалог, так что повтор продолжает этот диалог, а не открывает новый;
`message` объясняет причину словами платформы, а не сырым ответом провайдера.
Запуск записывается как неудавшийся вместе со своими расходами, поэтому
`GET /api/v1/runs/{run_id}` его читает; повторная отправка запроса начинает
новый запуск.

## Повторы, идемпотентность и ревизии { #retries-idempotency-and-revisions }

В v1 нет предусловий ревизии: ни `ETag`, ни `If-Match`. Запись применяется,
когда приходит, и побеждает последняя. `Idempotency-Key` учитывается на одном
маршруте — асинхронном запуске.

- **`GET`, `PUT` и `DELETE` безопасно повторять.** Два чтения — это два чтения;
  удаление того, чего уже нет, отвечает `404`, и повтор может считать это
  выполненным.
- **`PATCH` безопасно повторять с тем же телом**, и только тогда: два клиента,
  правящих одно поле, перезаписывают друг друга, а не конфликтуют.
- **`POST` — нет.** Повторный `POST /agents/{id}/run` начинает второй запуск и
  оплачивается как второй; повторное создание делает вторую строку. После
  тайм-аута или оборванного соединения сначала посмотрите, а потом повторяйте:
  `GET /api/v1/runs?agent_id=…&surface=api` перечисляет запуски сначала новые, и
  чтение списка находит строку, которую первая попытка всё-таки создала.
- **Асинхронный запуск — да, с `Idempotency-Key`.** Отправьте
  `Prefer: respond-async` и ключ на ваш выбор, не длиннее 255 символов; повтор с
  тем же ключом и тем же телом отвечает тем же запросом на запуск, в каком бы
  состоянии он ни был. Тот же ключ с другим телом — `409`, а не второй запуск.
  Ключи действуют в пределах организации. Синхронный вызов с этим заголовком
  отклоняется с `400`, чтобы вызывающий не решил, будто повтор безопасен.
- **`429` — единственный отказ, который стоит повторять**, выждав `Retry-After`,
  который он несёт. Любой другой `4xx` для этого запроса окончателен.

## Соглашения { #conventions }

| | |
|---|---|
| Префикс | `/api/v1` |
| Создание | `POST`, `201` |
| Частичное обновление | `PATCH` |
| Удаление | `DELETE`, `204`, без тела |
| Пагинация | параметры запроса `skip` (≥ 0) и `limit` (1–100); ответы списков несут `items` и `total` |
| Пути | kebab-case |

## Стабильность, честно { #stability-honestly }

**У публичного API есть письменное обещание совместимости; у остального
`/api/v1` его нет.** Маршруты, которые может вызывать ключ API, перечислены в
собственном документе OpenAPI по адресу **`/api/v1/public/openapi.json`**,
который отдаётся в любом окружении. В пределах v1 изменение в одном из них —
это дополнение: новый маршрут, новое необязательное поле, новое поле ответа или
значение перечисления, — а клиент обязан игнорировать поля ответа, которых не
знает. Удаление или переименование чего-либо там происходит только после того,
как это помечено в том документе как `deprecated` не меньше 90 дней и указано
в [примечаниях к выпуску](release-notes.md); изменение, которое так сделать
нельзя, уходит в `/api/v2`, рядом с v1.

Консоль читает тот же документ как страницу: **Настройки → API → Справочник
API** (Settings → API → API reference) перечисляет каждый эндпоинт с его
параметрами, телом, ответами и готовым вызовом `curl`.

Первое переименование по этому правилу — приложения (#2071): то, что было
артефактами, теперь отдаётся по `/api/v1/apps` и `/api/v1/public/apps`, а старые
пути `/api/v1/artifacts` и `/api/v1/public/artifacts` отвечают так же, помеченные
`deprecated`, пока не истекут 90 дней. Имена разрешений (`artifacts:view`,
`artifacts:edit`), имена инструментов и адреса, по которым отдаётся
опубликованная страница, сохраняют свои названия.

Собственные маршруты консоли таких обещаний не дают и меняются вместе с
консолью; ключ не может их вызывать. Клиентской библиотеки пока нет.

Чего публичный API пока не умеет — чтобы клиент на это не рассчитывал:

- **Виртуальных таблиц** в нём нет; чтение и запись таблицы ключом — это
  [#1795](https://github.com/vstorm-co/agenticos/issues/1795).
- **Никакой потоковой передачи для ключа.** Сокет чата принимает только сеанс
  человека.
- **Ни ключей идемпотентности, ни ревизий**, как сказано выше.

У [спецификации агента](reference/spec.md) своё обещание: она версионируется и
движется только вперёд.

## Итоги { #recap }

- **`/docs`** на экземпляре — это сгенерированный справочник; в рабочей среде он
  по замыслу выключен.
- Три способа войти: **ключ API организации, JWT или cookie консоли**.
- Ключ несёт полномочия выпустившего его участника, **суженные до его
  разрешений и текущей роли выпустившего**, показывается один раз и работает
  только в публичном API.
- **Ключ действует в своей организации; сеанс читает `X-Organization-Id`** и без
  него откатывается к организации по умолчанию, личной или единственной.
  Неверная выглядит как отсутствующий ресурс.
- Запуск агента по HTTP идёт через **тот же механизм выполнения** — бюджет,
  согласование и аудит действуют.
- Скрипт получает свой ключ **без браузера** — войти, выпустить, отозвать — и
  `examples/public-api.sh` проделывает весь этот круг.
- **Повторять стоит только `429`**; `POST` не идемпотентен, поэтому прежде чем
  повторять его, посмотрите — кроме асинхронного запуска, отправленного с
  `Idempotency-Key`.
- **`Prefer: respond-async`** превращает запуск в `202` и запрос на запуск для
  опроса, так что долгий запуск не держит соединение открытым.
- **Публичный API — в `/api/v1/public/openapi.json`**, и в пределах v1 он
  меняется только дополнениями, с 90-дневным сроком устаревания; SDK пока нет.


Навыки, загрузка которых требует согласования, должны быть одобрены заново в
каждом ходе; прежние загрузки никогда не обходят эту проверку.
